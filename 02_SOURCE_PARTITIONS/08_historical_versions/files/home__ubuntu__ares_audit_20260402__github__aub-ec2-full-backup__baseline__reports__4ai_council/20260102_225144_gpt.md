아래는 **다음 24~48시간 자동 루프(48h)** 안에서 바로 돌릴 수 있는 **TOP5 우선순위(코드/아키텍처/전략)**입니다. 각 항목은 **(a) 필요 이유 (b) 위험/부작용 (c) 최소 실험(2~3 변형 run) (d) PASS 조건**으로, 그리고 **누수/과최적화/서바이버십/비용/운영리스크**를 먼저 때립니다.  
(미국주식 only, Tech+Healthcare 8~14종목, ETF 매매 금지·관측지표로만)

## TOP1) 평가 무결성: Fold degeneracy + 누수 방지 게이트를 “하드”로 박기
### (a) 왜 필요한지
- 현재 `degenerate_folds: [1,2,3,8]`는 **OOS 평균이 높아도 신뢰 불가** 신호입니다. (샘플 부족/라벨 편향/폴드 분할 오류/특정 기간 데이터 결측 등)
- `lane_hash/run_hash: None`는 실험 재현성/추적성이 깨진 상태라 **과최적화 탐지 및 회귀(regression) 차단 불가**.

### (b) 위험/부작용
- 게이트 강화로 **실험 대부분이 FAIL**할 수 있음(단, 그게 정상).
- 누수/폴드 문제가 잡히면 **기존 champion 성능이 급락**할 수 있음(그게 “진짜” 성능).

### (c) 최소 실험(패치 1개 + 2~3 run 변형)
**[패치/실험 패키지 #1: “Fold Health + Leakage Gate”]**
- 실험 정의(48h 루프용)
  - **RUN A (baseline 재현)**: 기존 champion 설정 그대로, 단 **fold health report**를 저장.
  - **RUN B (purged/embargo split)**: 이벤트/리밸런스 기준으로 `purge + embargo`(예: 5~10 trading days) 적용.
  - **RUN C (walk-forward only)**: 고정 폴드 대신 walk-forward(rolling) 평가 1회 추가(최소 구간만).
- 게이트(하드 FAIL)
  - `degenerate_folds == []` (하나라도 있으면 FAIL)
  - 각 폴드 **거래 발생 횟수/샘플 수/유효 bar 수** 최소치 통과 (예: 폴드당 trade >= N, 유효일수 >= M)
  - `lane_hash`, `run_hash` 반드시 채움(없으면 FAIL)
- 기대 관측치
  - RUN B/C에서 OOS mean이 내려가더라도 **분산 감소**, 폴드별 성능이 “정상” 분포로 수렴
  - 누수 있으면 RUN A >> RUN B/C로 급격한 격차 발생(그 자체가 진단 성공)

### (d) PASS 조건
- `degenerate_folds` 0개
- RUN B 또는 C에서 **OOS mean이 RUN A의 60% 이상** 유지(대충이 아니라 “누수 제거 후에도 남는지” 확인)
- 폴드별 성능 분산이 과도하지 않을 것(예: 최상/최하 폴드 격차가 비정상적으로 크지 않음)

## TOP2) 비용/리밸런스 로깅 복구: “비용 미반영 + 리밸런스 데이터 유실”을 즉시 차단
### (a) 왜 필요한지
- `aub_rebalance_pinpoint`가 **base-log 경로 오류**, `rebalance.csv/jsonl` 파싱 실패로 **리밸런스/턴오버/슬리피지/비용을 검증 못하는 상태**입니다.
- 비용이 빠지면 OOS가 움직여도 실전에서 무의미해지고, 반대로 성능이 “안 움직이는” 원인이 **비용/턴오버로 상쇄**되는 건지 확인 불가.

### (b) 위험/부작용
- 비용을 넣으면 성능이 급락할 수 있음(정상).
- 로그 스키마 변경 시 기존 리포트 툴과 호환 문제 발생.

### (c) 최소 실험(패치 1개 + 2~3 run 변형)
**[패치/실험 패키지 #2: “Rebalance Log Canonicalization + Cost Switch”]**
- 실험 정의
  - **RUN A (log-only)**: 전략/알파는 그대로, 리밸런스 로그를 **항상 JSONL로 강제 출력**(스키마 고정) + `--base-log` 자동 탐색/기본값 지정.
  - **RUN B (cost on: conservative)**: 수수료+스프레드+슬리피지 보수적 가정(예: 5~15bp + spread proxy).
  - **RUN C (cost on: mild)**: 완화 가정(예: 1~5bp).
- 게이트
  - `rebalance.jsonl` **필수 생성**, 0바이트/파싱 실패면 FAIL
  - 각 리밸런스 이벤트에 `timestamp, target_weights, executed_weights, turnover, est_cost_bps` 필드 존재(없으면 FAIL)
- 기대 관측치
  - RUN B에서 성능 하락 폭이 과도하면 **턴오버가 원인**임이 바로 드러남
  - RUN B vs RUN C 차이로 “비용 민감도” 확보

### (d) PASS 조건
- 리밸런스 pinpoint 리포트가 **에러 없이 생성**
- 비용 ON에서도 OOS mean이 **0 이상 유지** + (턴오버 상한 내)  
  *(상한은 내부 기준으로 고정: 예 “일평균 turnover X% 이하” 같은 하드 게이트)*

## TOP3) 리스크/노출/최대낙폭(MDD) 산출을 “필수 지표”로 강제 + 노출 안정화
### (a) 왜 필요한지
- `worst_mdd: None`는 **리스크 리포팅/게이트가 붕괴**했다는 뜻입니다(운영 리스크 1순위).
- `exposure_min/max: 0.0 / 0.8388`로 노출이 널뛰기면, 성능 “불변”이 사실은 **현금구간 과다/트리거 미발생**일 수 있습니다.

### (b) 위험/부작용
- 노출 하한을 강제하면 시장 역풍에서 손실 확대 가능.
- MDD 계산을 실현손익 기준으로 바꾸면 과거 대비 수치가 달라져 회귀 판정이 바뀔 수 있음.

### (c) 최소 실험(패치 1개 + 2~3 run 변형)
**[패치/실험 패키지 #3: “MDD Mandatory + Exposure Guardrail”]**
- 실험 정의
  - **RUN A (metrics-only)**: 기존 전략 유지, MDD/Calmar/turnover/exposure histogram 계산을 **필수 산출**.
  - **RUN B (exposure floor)**: `gross_exposure_min` 또는 `target_exposure`를 소폭 부여(예: 최소 0.3) + 상한 유지.
  - **RUN C (cash-penalty)**: 노출이 0에 붙는 구간이 길면 페널티(또는 “신호가 없으면 최소 코어 포지션 유지”)를 실험.
- 게이트
  - `worst_mdd`가 None이면 FAIL
  - `exposure_max`가 설정 상한(예 0.85) 초과하면 FAIL
  - “노출 0” 구간 비율이 임계치 초과(예: 30%+)면 FAIL
- 기대 관측치
  - 성능 정체의 원인이 “신호 부재→현금 과다”인지 즉시 판별
  - 노출 바운드가 성능 분산을 줄일 가능성

### (d) PASS 조건
- `worst_mdd` 산출 + 리포트 포함
- RUN B/C에서 OOS mean 악화가 크지 않으면서(예: -X% 이내) 노출 0 구간이 유의미하게 감소

## TOP4) 서바이버십/유니버스 고정(Tech+Healthcare 8~14) + 유동성/거래가능성 게이트
### (a) 왜 필요한지
- 서바이버십/데이터 결측은 **폴드 degeneracy**의 대표 원인입니다.
- “8~14 종목” 제약에서 종목 교체 로직이 있으면, 백테스트는 살아남은 종목만 남아 **상향 편향**이 생기기 쉽습니다.
- 운영 측면에서 티커 변동/분류 변동은 장애 원인입니다.

### (b) 위험/부작용
- 고정 유니버스는 적응력이 떨어질 수 있음.
- 유동성 게이트로 거래가 줄어 OOS가 낮아질 수 있음(하지만 더 진짜).

### (c) 최소 실험(패치 1개 + 2~3 run 변형)
**[패치/실험 패키지 #4: “Universe Deterministic + Tradability Gate”]**
- 실험 정의
  - **RUN A (fixed universe)**: Tech+Healthcare에서 8~14개를 **정적으로 고정**(운영 안정 우선).
  - **RUN B (fixed + liquidity gate)**: ADV(달러거래대금)·가격·스프레드 프록시 조건 미달이면 매수 금지.
  - **RUN C (fixed + sector-balance)**: Tech/HC 비중을 고정(예: 6:6 등)해 섹터 쏠림 완화.
- 게이트
  - 종목별 데이터 커버리지(유효 바 비율) 임계치 미달이면 FAIL
  - 거래 불가(가격 0/거래정지/극단적 스프레드 프록시) 이벤트가 있으면 FAIL 또는 해당 일자 거래 스킵 기록 필수
- 기대 관측치
  - 폴드 degeneracy 감소
  - 거래 실패/데이터 결측으로 인한 “가짜 성능” 제거

### (d) PASS 조건
- 결측/거래불가로 인한 스킵이 발생해도 **로그로 완전 추적 가능**
- OOS mean이 크게 떨어져도(가능) 분산/안정성이 개선되고, 비용 ON에서 붕괴하지 않음

## TOP5) “No-Delta” 원인 제거: 파라미터가 실제로 성능에 영향 주는지(배선/적용 시점/단위) 검증
### (a) 왜 필요한지
- 이미 `No-Delta Diagnoser`가 돌았고, “성능이 안 움직임”은 흔히
  1) 파라미터가 코드에 **미적용(배선 끊김)**  
  2) 적용되지만 **게이트에서 전부 clamp**  
  3) 신호가 너무 약해 **포지션 변화가 없음**  
  중 하나입니다.
- `lane_hash/run_hash None`도 “실제로 설정이 먹었는지” 추적을 어렵게 합니다.

### (b) 위험/부작용
- 파라미터 민감도 실험은 과최적화 유혹이 큼 → 반드시 “게이트 먼저”가 필요.
- 적용 시점 변경은 과거 결과와 비교가 어려워질 수 있음.

### (c) 최소 실험(패치 1개 + 2~3 run 변형)
**[패치/실험 패키지 #5: “Sensitivity Probe (Wiring Test)”]**
- 실험 정의
  - **RUN A (extreme toggle + audit log)**: 핵심 파라미터 1~2개를 극단값(예: 스케일 0.1 vs 2.0)으로 바꾸고, 매 리밸런스마다 `signal_raw, signal_scaled, final_weight`를 로깅.
  - **RUN B (gate-off probe in sandbox)**: 운영용 게이트는 유지하되, “디버그 모드”에서만 clamp 직전 값을 기록(실제 주문은 기존대로).
  - **RUN C (position-change count KPI)**: 기간당 포지션 변경 횟수/변경 크기 분포를 KPI로 고정.
- 게이트
  - 파라미터 변경 시 `signal_scaled` 분포가 유의하게 변하지 않으면 FAIL(배선 끊김)
  - 변했는데 `final_weight`가 안 변하면 FAIL(게이트/clamp가 전부 막음)
- 기대 관측치
  - “안 움직임”이 알파 문제인지, 구현/게이트 문제인지 즉시 분리

### (d) PASS 조건
- 극단 토글 시 `signal_scaled` 및 `final_weight`의 분포 변화가 관측됨(둘 다 무변이면 FAIL)
- position-change KPI가 0에 수렴하지 않음(전략이 실제로 작동)

# 48시간 자동 루프 운영 형태(명령형 체크리스트)
아래 순서로 **패키지 #1~#5를 그대로** 돌리면 됩니다.

1) **[게이트 먼저]** 패키지 #1 실행 → `degenerate_folds==[]` 통과 전엔 성능 비교 중단  
2) 패키지 #2로 **리밸런스 로그/비용 ON**을 먼저 복구 → “순이익” 기준으로만 평가  
3) 패키지 #3로 **worst_mdd 필수화 + 노출 분포** 확보 → 성능 정체 원인(현금 과다/과도 clamp) 확인  
4) 패키지 #4로 **유니버스 고정+거래가능성 게이트** → 서바이버십/결측 제거  
5) 패키지 #5로 **No-Delta 배선 테스트** → 전략 파라미터가 실제로 포지션을 바꾸는지 확인

# 성능이 “안 움직일 때” 원인 분해 아이디어 (Trigger/적용/노출/비용/레짐)
아래는 **질문 없이** 바로 점검 가능한 “분해 트리”입니다(각 노드별 관측치 포함).

## A. Trigger(신호 발생) 문제
- **점검**
  - 신호(예: score, alpha)의 일별 분포(평균/표준편차/상위 5% 분위) 로그 고정
  - 신호가 0/상수에 붙는지 확인
- **관측치**
  - `std(signal_raw) ≈ 0`이면: 데이터/피처/정규화 문제 또는 배선 끊김

## B. 적용(게이트/클램프) 문제
- **점검**
  - `signal_raw → signal_scaled → pre_clamp_weight → final_weight` 4단계 로그
  - clamp에 걸린 비율(%)을 KPI로 고정
- **관측치**
  - signal은 변하지만 final_weight가 안 변하면: **게이트가 전부 막음** 또는 포지션 라운딩/최소 주문단위 문제

## C. 노출(Exposure) 문제
- **점검**
  - `exposure histogram`, `exposure=0` 구간 비율, 평균 보유종목수
- **관측치**
  - 노출이 자주 0이면: 신호가 없거나, 거래가능성/리스크게이트 과도, 또는 리밸런스가 실행되지 않음

## D. 비용/턴오버 상쇄 문제 (가장 흔한 “무변” 원인)
- **점검**
  - gross return vs net return(비용 차감)의 괴리
  - turnover와 성과 상관(턴오버 높은 구간에서 성과 악화)
- **관측치**
  - gross는 개선인데 net이 무개선이면: **비용 모델/리밸런스 빈도/거래 필터**가 핵심 레버

## E. 레짐(Regime) 문제 (ETF는 “관측지표”로만)
- **점검**
  - 관측 ETF 예: `QQQ(테크), XLV(헬스케어), SPY, IWM, TLT, HYG`  
    - 변동성(VIX 대용), 금리(IEF/TLT), 크레딧(HYG) 등과 성과를 구간별로 분해
  - “레짐별 성과 표”(저변동/고변동, 금리상승/하락 등)
- **관측치**
  - 특정 레짐에서만 성과가 나면: 레짐 필터/노출 스케일링이 필요(단, 과최적화 금지 게이트 필수)

## 즉시 보이는 운영 리스크(현재 로그 기반) 요약
- `rebalance` 로딩 실패: **비용/턴오버 검증 불가** → TOP2가 최우선
- `degenerate_folds`: **OOS 신뢰 불가** → TOP1이 최우선
- `worst_mdd None`: **리스크 통제 붕괴** → TOP3 즉시

위 5개 패키지(#1~#5)만 48시간 루프에 태우면, “성능이 안 움직이는” 상태가 **알파 문제인지/평가 문제인지/운영·비용 문제인지**가 분해되어 다음 사이클에서 케이스 폭발 없이 개선 방향이 고정됩니다.
