## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — 명령형 체크리스트
> 우선순위는 **누수/과최적화/서바이버십/비용 미반영/운영 리스크**를 먼저 깨고, 그 다음 전략 레짐으로 이동한다.  
> 거래 유니버스는 **미국주식 Tech+Healthcare 8~14개**로 고정 유지(ETF는 **관측지표만**, 매매 금지).

---

# 1) 누수/서바이버십(상장폐지 포함) 가드레일을 “강제”로 넣어라
### (a) 왜 필요한지
- 현재 챔피언 메타에 `file/lane_hash/run_hash/worst_mdd`가 비어 있고, `degenerate_folds`가 다수(1,2,3,8)면 **데이터 정렬/누수/폴드 구성 문제가 성능을 ‘가짜로’ 평탄화**시키는 전형 패턴이다.
- 상장폐지/합병/티커 변경/데이터 공백을 무시하면 **서바이버십 바이어스**로 OOS가 “안 움직이거나” 비정상적으로 좋아진다.

### (b) 위험/부작용
- 단기적으로 OOS mean이 떨어질 수 있다(“진짜 성능”으로 수렴).
- 데이터 소스가 상장폐지 리턴을 제공하지 않으면 결측이 늘고 거래가 줄어든다.

### (c) 최소 실험(1개 패치 안에 3-variant로 묶어서 실행)
**[E1] As-Of 조인 + 상장폐지/기업행위 처리 강제 패치 (3 variants)**  
- V0: 현행(참조용)  
- V1: 모든 피처/라벨을 **as-of join(시점 엄수)**로 재구성 + “미래 데이터 탐지” assert  
- V2: V1 + **delisting return(가능하면)** 반영(불가하면 “delist 시 0으로 청산” 같은 보수적 대체 규칙을 옵션으로)

### (d) PASS 조건 (게이트)
- **Leak gate**: 미래시점 참조 탐지 0건(룰 기반 assert), 학습/예측 타임스탬프 단조성 위반 0건
- **Survivorship gate**: 백테스트 구간 내 “티커 소멸/교체 이벤트”가 로그로 표기되고, 포지션이 자동 청산/대체 처리됨
- **성과 gate**: `oos_min` 악화 금지(또는 -5%p 이내), `degenerate_folds` 감소(최소 절반 이하)

**48시간 자동 루프 형태**
- (1) 실험 정의: E1(V0/V1/V2) 동시 러닝  
- (2) 게이트: Leak/Survivorship/성과 gate 통과 못 하면 즉시 롤백 + 원인 로그 저장  
- (3) 기대 관측치: OOS mean은 약간 하락 가능, 대신 `oos_min`/폴드 안정성 개선 및 “No-Delta” 원인(누수/정렬)이 드러남

# 2) 과최적화/폴드 퇴화(Degraded fold) 차단: “폴드 유효성 검사+거래 최소조건+엠바고”를 넣어라
### (a) 왜 필요한지
- `degenerate_folds`가 여러 개면, 폴드 일부에서 **거래가 거의 없거나(노출=0) / 한쪽 방향만 베팅 / 데이터가 비정상**이라서 OOS가 의미 없어지고 “개선이 안 보이는” 상태가 된다.
- 특히 노출 `min=0.0`이 장기간 지속되면, 모델이 사실상 **캐시 포지션으로 회피**하면서 지표가 굳는다.

### (b) 위험/부작용
- 엠바고/퍼지로 학습 데이터가 줄어 성능이 단기 하락할 수 있음.
- 거래 최소조건을 걸면 일부 시점에서 강제로 포지션을 만들어 리스크가 증가할 수 있음(따라서 “최소조건=완전 강제”가 아니라 “폴드 폐기/리젝”이 우선).

### (c) 최소 실험(1개 패치 안에 2-variant)
**[E2] CV 폴드 유효성 프레임워크 패치 (2 variants)**  
- V1: Purged/Embargoed CV 적용(예: 라벨/피처 룩어헤드 윈도우만큼 엠바고)  
- V2: V1 + **폴드 거래 유효성 검사**(예: 각 폴드별 최소 거래 수, 최소 non-zero exposure 비율, 수익률 분산 하한) 미달 시 폴드 리젝/재샘플

### (d) PASS 조건 (게이트)
- `degenerate_folds == 0`
- 폴드별 `non_zero_exposure_ratio`가 하한 이상(예: 20% 이상) 또는 미달 폴드 자동 제외가 정상 동작
- `oos_min` 개선 또는 최소 유지, 그리고 **폴드별 성과 분산이 감소**

**48시간 자동 루프**
- (1) 실험 정의: E2(V1/V2)  
- (2) 게이트: degenerate 0 달성 못 하면 실패로 기록하고 CV 파라미터 자동 보수화(엠바고↑, 폴드 길이↑)  
- (3) 기대 관측치: OOS mean이 출렁이던 원인이 “폴드 퇴화”였으면, mean보다 먼저 **oos_min/분산**이 개선된다

# 3) 비용/턴오버 미반영을 즉시 반영: “거래비용 + 리밸런스 히스테리시스”를 넣어라
### (a) 왜 필요한지
- 비용이 없으면 전략이 **미세한 신호에 과도하게 리밸런스**해서 OOS가 “좋아 보이거나/변화가 없어 보이는” 착시가 난다.
- 현재 rebalance 로그도 깨져 있어(핀포인트 툴이 base-log/csv/json 로딩 실패), 비용/턴오버 문제가 숨어도 못 본다.

### (b) 위험/부작용
- 비용 반영 즉시 성과가 크게 하락할 수 있음(그게 정상).
- 히스테리시스(리밸런스 임계값)를 너무 키우면 신호 추종이 느려진다.

### (c) 최소 실험(1개 패치 안에 3-variant)
**[E3] 비용모델+턴오버 억제 패치 (3 variants)**  
- V0: 고정 bps(예: 5~15bp 구간 sweep를 한 실험 안에서 돌림)  
- V1: V0 + **ADV 기반 임팩트(단순 모델)**(포지션 변화/ADV 비율로 비용 증가)  
- V2: V1 + **리밸런스 히스테리시스**(목표비중 변화가 임계값 미만이면 거래 스킵)

### (d) PASS 조건 (게이트)
- Net 성과 기준으로 비교: `oos_mean(net)`이 챔피언 대비 -X 이내(예: -0.2 이내)면서 `oos_min(net)` 개선이면 통과
- Turnover 상한: 일/주간 turnover가 상한 이하로 떨어질 것(예: 주간 < 200% 같은 내부 기준)
- 비용 민감도: bps sweep에서 **단조 감소/비정상 급락**이 없고 합리적인 곡선

**48시간 자동 루프**
- (1) 실험 정의: E3(V0/V1/V2)  
- (2) 게이트: 비용 적용 시 성과 붕괴 + 턴오버 과다 지속이면 실패로 기록하고 “리밸 임계값↑/노출↓” 자동 적용  
- (3) 기대 관측치: OOS mean 자체보다 먼저 **턴오버 감소 + oos_min 개선**이 나타나야 정상

# 4) 운영 리스크 제거(로그/아티팩트/재현성): rebalance pinpoint가 “항상” 돌게 고쳐라
### (a) 왜 필요한지
- 지금 상태는 툴이 `--base-log`를 파일로 해석하다 실패했고, cand csv/json도 파싱 실패했다. 즉 **원인 진단 루프가 끊겨서 “안 움직이는 이유”를 영원히 못 본다.**
- 챔피언 메타에 `file/lane_hash/run_hash`가 None이면 **재현 불가/롤백 불가**다.

### (b) 위험/부작용
- 코드 변경량이 작아도 파이프라인 인터페이스가 바뀌면 기존 스크립트가 깨질 수 있음(그래서 스키마 버전이 필요).

### (c) 최소 실험(1개 패치 안에 2-variant)
**[E4] 로깅/아티팩트 스키마 v1 패치 (2 variants)**  
- V1: `rebalance.jsonl`(라인 단위 JSON) 표준화: timestamp, universe, target_w, filled_w, trades, est_cost, realized_cost, reason_code  
- V2: V1 + run 메타 강제 기록: `run_hash/lane_hash/commit/seed/champion_file_path/worst_mdd`를 결과 JSON에 필수 필드로

### (d) PASS 조건 (게이트)
- `aub_rebalance_pinpoint.py`가 **base/cand 모두 정상 로딩**하고 리포트 생성
- 챔피언 메타에서 None 필드 0개(`file/lane_hash/run_hash/worst_mdd` 채워짐)
- 동일 seed/run_hash에서 결과 재현(요약 지표 동일)

**48시간 자동 루프**
- (1) 실험 정의: E4(V1/V2)  
- (2) 게이트: 툴/리포트 생성 실패 시 즉시 실패 처리 + “로그 포맷 회귀 테스트”를 CI처럼 강제  
- (3) 기대 관측치: 성능 변화보다 먼저 **진단 가능성(핀포인트/노델타 원인)이 급상승**해야 한다

# 5) 레짐/노출 제어(Tech+Healthcare 집중 포트): ETF 관측지표로 “노출 게이트”를 걸어라
### (a) 왜 필요한지
- 8~14개 집중 포트는 사실상 **숨은 베타/레짐 민감도**가 크다. 레짐이 바뀌면 모델이 “맞아도” 노출이 줄거나(0으로 회피) 비용만 내고 성능이 안 움직인다.
- ETF는 매매 금지지만 **레짐 인디케이터로는 최적**(XLK/XLV/QQQ/IEF/TLT 등).

### (b) 위험/부작용
- 레짐 게이트가 과도하면 거래 기회가 줄어 mean이 떨어질 수 있음.
- 잘못된 레짐 정의는 “필터가 알파를 제거”한다.

### (c) 최소 실험(1개 패치 안에 3-variant)
**[E5] ETF 관측 기반 노출/리스크 게이트 패치 (3 variants)**  
- V0: 현행 노출 스케일  
- V1: **리스크-온/오프 게이트**(예: QQQ 모멘텀↓ 또는 (XLK/XLV) 상대강도 악화 시 gross exposure 상한을 0.3~0.5로 clamp)  
- V2: V1 + **변동성 타게팅**(최근 실현변동성↑이면 노출 자동 축소)

### (d) PASS 조건 (게이트)
- `exposure_max` 상한 안정화(예: 0.85 유지) + 레짐 오프에서 노출이 실제로 감소하는 로그가 남을 것
- `oos_min` 개선(최우선), 그리고 `worst_mdd`가 계산되고 악화 금지
- 레짐 필터 발동 비율이 극단적이지 않을 것(예: 전체 기간의 5~80% 범위 내)

**48시간 자동 루프**
- (1) 실험 정의: E5(V0/V1/V2)  
- (2) 게이트: oos_min/MDD 악화 시 실패, 레짐 발동이 과도하면 임계값 자동 보수화  
- (3) 기대 관측치: mean보다 먼저 **드로다운/최저 OOS 개선**이 관측돼야 한다

## 48시간에 “실제로” 돌릴 실행 묶음 (3~5개 패치/실험으로 제한)
- E4(로깅/아티팩트) → E2(CV 퇴화 제거) → E1(누수/서바이버십) → E3(비용/턴오버) → E5(레짐/노출) 순으로 큐에 넣어라.  
- 각 E는 variant를 한 번에 돌리고, **게이트 실패 시 다음 단계로 진행하지 말고 롤백/리포트만 남겨라.**

# 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐)
아래 트리를 그대로 로그/리포트 섹션으로 만들어서, 매 48시간 루프마다 자동 채우게 만들어라.

## A. Trigger(신호 발생) 문제
- **신호 발생 빈도**(일별/종목별 trigger rate)와 **분포 변화**(최근 3개월 vs 과거) 로그화
- 트리거가 너무 희박하면: 임계값 과도/피처 스케일링 붕괴/결측 증가 가능
- 트리거가 과다하면: 누수/정렬 오류/과민 신호 가능

## B. Apply(적용/리밸런스) 문제
- “신호는 나오는데 체결이 안 됨”을 분리:  
  - target_w 생성 → clamp/정규화 → 거래 생성 → 비용 적용 → 최종 filled_w  
- 단계별로 **왜 스킵됐는지 reason_code**를 강제 기록(E4에 포함)

## C. Exposure(노출) 문제
- `non_zero_exposure_ratio`, `gross/net exposure`의 시간추이를 OOS 리포트 1페이지에 고정
- 노출이 0으로 붙으면: 레짐 게이트 과도 / 거래 최소조건 부족 / 비용이 과대 / 신호가 상쇄

## D. Cost(비용) 문제
- Turnover와 성과의 상관(턴오버↑인데 성과 정체면 비용 누락 또는 알파 미세)
- bps sweep 곡선이 비정상(조금만 비용 넣어도 붕괴)면: 알파가 비용보다 작거나 과최적화

## E. Regime(시장 국면) 문제
- 관측 ETF(예: QQQ, XLK, XLV, IEF/TLT)를 이용해 구간을 2~4개 레짐으로 태깅
- 레짐별 성과/노출/턴오버를 분해해서 “안 움직임”이 특정 레짐에 국한되는지 확인
- 레짐별로 동일하면: 신호 자체가 약하거나(Trigger) 비용/폴드 문제가 상위 원인

## F. Data/Backtest Plumbing(배관) 문제 — 최우선
- 폴드별 샘플 수/거래 수/결측률/기업행위 이벤트 수를 표로 자동 출력
- `worst_mdd`가 None이면 **리스크 지표 산출 파이프가 깨진 것**이므로 성능 논의 중단하고 배관부터 고쳐라(E4에서 강제)

---

## 고정 유니버스(미국 Tech+Healthcare, 8~14개) 운용 규칙(권고)
- 유니버스를 **정적 리스트로 고정**해서 서바이버십/유니버스 드리프트를 먼저 제거하라.  
  예시(14): AAPL, MSFT, NVDA, GOOGL, AMZN, META, AVGO, AMD + LLY, UNH, JNJ, MRK, ABBV, TMO  
- 이후에만 “유니버스 동적화”를 실험으로 분리하라(지금은 금지).

--- 

위 TOP5를 위 순서대로 적용하면, 48시간 안에 최소한
1) 왜 핀포인트가 안 도는지(운영),  
2) 왜 폴드가 퇴화하는지(과최적화/데이터),  
3) 비용을 넣으면 살아남는지(현실성),  
4) 레짐에서 죽는지(전략 구조)  
가 **서로 섞이지 않고 분리**돼서 보이게 된다.
