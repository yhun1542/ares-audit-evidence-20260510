## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — “명령형 체크리스트”
아래 5개는 **누수/과최적화/서바이버십/비용 미반영/운영 리스크**를 먼저 깎는 순서로 정렬.  
(실험은 총 5개 풀(E1~E5)만 정의하고, 각 제안은 그중 2~3개를 재사용)

---

### 1) **Point-in-time 누수(lookahead) 제거 + “as-of” 강제**
**(a) 왜 필요한지**
- 현재 champion/candidate에서 **tuning↔lockbox 괴리**가 작아 보이는 구간은 오히려 “누수/동일 데이터 경유/피처 정렬 오류”가 숨어도 겉으로 티가 덜 남음.
- 8~14종목 소수 포트는 **한두 개 누수 피처가 전체 성능을 지배**하기 쉬움.

**(b) 위험/부작용**
- 누수가 있으면 성능이 크게 떨어지며, 단기적으로 “퇴보”처럼 보임.
- 피처 생성/정렬 로직 변경으로 재현성이 깨질 수 있음(시드/캐시/병렬).

**(c) 최소 실험(2~3개)**
- **E1 (PIT Shift/Shuffle 누수 스위트)**  
- **E4 (1-bar execution delay / rebalance 지연)**  
- **E5 (신호 기여도/노출 어트리뷰션; 누수 의심 피처 탐지)**

**(d) PASS 조건**
- E1에서 **1-bar shift 적용 시 성능이 “의미 있게” 하락**(정상)하고, 동시에 **shuffle(시간 섞기)에서는 거의 무력화**되어야 함.  
- E4에서 **1일 딜레이에도 lockbox_mean이 과도 붕괴하지 않음**(예: -10% 이내) + worst_mdd 악화 제한(예: 1~2%p 이내).  
- 누수 플래그(“shift에도 유지/셔플에도 유지”) 발견 시 **즉시 FAIL → 해당 피처/정렬 제거 patch로 전환**.

---

### 2) **서바이버십/코퍼레이트액션(스플릿/상장폐지) 리스크 고정**
**(a) 왜 필요한지**
- Tech/Healthcare는 **M&A, delist, ticker change**가 잦고, 소수 종목 포트는 **상장폐지 누락**이 곧 “유령 알파”로 변함.
- adjusted/unadjusted 가격 혼용, split 처리 오류는 **무비용 알파**를 만들 수 있음.

**(b) 위험/부작용**
- 데이터 소스/로더 변경으로 백테스트 결과가 크게 바뀔 수 있음(정상).
- delisted 데이터 포함 시 빈 데이터/NA 증가로 파이프라인이 깨질 수 있음.

**(c) 최소 실험(2~3개)**
- **E2 (Survivorship + CA 재빌드 검증)**  
- **E1 (PIT 검증과 결합: delist 구간에서 shift/shuffle 민감도 확인)**

**(d) PASS 조건**
- E2에서 **락박스 성능이 “합리적 범위 내” 변화**(예: lockbox_mean 변동 ±5% 이내) + **거래 가능 일수/가격연속성 경고가 0 또는 허용 범위**.  
- delisted/CA 이벤트가 있는 티커에서 **리턴 급등/급락이 split-adjust로 설명 가능**해야 함(설명 불가하면 FAIL).

---

### 3) **비용/슬리피지/임팩트 반영 + turnover 상한(과최적화 차단)**
**(a) 왜 필요한지**
- 8~14종목은 리밸런싱이 잦아지면 **거래비용이 샤프를 직접 파괴**.  
- “비용 0 가정”에서만 살아남는 전략은 운영에서 즉시 붕괴.

**(b) 위험/부작용**
- 비용을 올리면 성능이 내려가고, 그 과정에서 “전략 자체가 불필요하게 보수화”될 수 있음.
- turnover cap이 과하면 신호 적용이 늦어짐(알파 감소).

**(c) 최소 실험(2~3개)**
- **E3 (Cost/Slippage 멀티플라이어 스트레스 + turnover cap)**  
- **E4 (리밸런스 주기/딜레이로 자연 turnover 감소)**

**(d) PASS 조건**
- E3에서 비용 1x→2x에서도 **락박스 샤프/목표지표가 급붕괴하지 않음**(예: lockbox_mean -15% 이내)  
- turnover cap 적용 후 **worst_mdd 개선 또는 동등**(예: 개선 ≥0.5%p 또는 악화 ≤0.5%p)  
- “비용 반영 후에도” champion 대비 열위면 FAIL(거래비용 의존 알파로 판단).

---

### 4) **운영 리스크(데이터 결측/지연/재현성) 차단: 48h 자동 루프 품질 게이트 강화**
**(a) 왜 필요한지**
- 자동 루프는 “가끔 성공”보다 **항상 동일하게 실패/성공하는 재현성**이 핵심.
- 결측/스파이크/소스 지연이 있으면 **우연히 좋은 fold만 남는 서바이버십**이 발생.

**(b) 위험/부작용**
- 게이트 강화로 PASS 빈도가 줄어듦(단기 생산성 저하).
- 로그/메타데이터 증가로 저장비용 상승.

**(c) 최소 실험(2~3개)**
- **E1 (누수+재현성: 시드 고정/피처 체크섬)**  
- **E2 (데이터 소스 스냅샷/CA 정합성 체크)**  
- **E5 (노출/기여도 리포트 자동 생성으로 이상탐지)**

**(d) PASS 조건**
- 동일 커밋/동일 스냅샷/동일 시드에서 **결과 해시(요약 메트릭)가 반복 일치**(허용 오차 정의).  
- 결측/스파이크/리턴 상한 초과 등 **데이터 품질 경고 0(또는 임계치 이하)**.

---

### 5) **레짐(국면) 미스매치 완화: ETF는 “관측지표”로만 써서 리스크 오버레이**
(ETF 매매 금지 준수. QQQ/XLK/XLV/IHI 등은 “상태지표”로만 사용)

**(a) 왜 필요한지**
- Tech/Healthcare는 금리/리스크온오프에 민감. 소수 포트는 레짐 한 번 잘못 맞으면 MDD가 깊어짐.
- “신호는 맞는데 레짐이 틀려서 못 먹는” 케이스를 분리해야 함.

**(b) 위험/부작용**
- 레짐 필터가 과하면 트레이드 수가 줄고 기회손실.
- 레짐 정의가 또 다른 과최적화 포인트가 될 수 있음.

**(c) 최소 실험(2~3개)**
- **E5 (레짐/노출 어트리뷰션 + 간단 오버레이 on/off)**  
- **E3 (레짐별 비용 민감도: 변동성 확장 구간에서 슬리피지 확대)**

**(d) PASS 조건**
- E5에서 레짐 오버레이 적용 시 **worst_mdd 개선(예: ≥1%p)** 또는 **tail 구간 손실 축소**가 관측.  
- 레짐 on/off의 차이가 tuning에만 크고 lockbox에는 작으면 FAIL(과최적화 신호).

---

## 실험 풀(총 5개만 운용) — 48시간 자동 루프 형태로 고정
각 실험은 (1) 실험 정의 (2) 게이트 (3) 기대 관측치로 구성.  
이 5개만 “토글/파라미터”로 돌려 케이스 폭발 방지.

---

### E1) PIT Shift/Shuffle 누수 스위트(+재현성 해시)
1) **실험 정의**
- 모든 예측 피처/라벨 정렬에 대해:
  - `shift(+1 bar/day)` 버전
  - `time-shuffle`(시계열 순서 교란) 버전
  - `seed固定 + feature checksum + dataset snapshot id` 기록
2) **게이트**
- Shuffle에서 성능이 유지되면 **즉시 FAIL(누수/데이터 누출 의심)**  
- Shift에서 성능이 “거의 동일”이면 **FAIL(정렬/체결가/라벨 누수 의심)**  
- 동일 시드/스냅샷 반복 실행 결과가 흔들리면 FAIL(재현성 문제)
3) **기대 관측치**
- 정상이라면: shift 성능 하락, shuffle 성능 붕괴, 재현성 일치

---

### E2) Survivorship + Corporate Actions 정합성 재빌드
1) **실험 정의**
- delisted 포함 가능 데이터 소스로 universe를 재구성(가능 범위 내)
- split/dividend adjustment 정책을 단일화(혼용 금지)
- ticker change/m&a 이벤트 구간에 대해 가격연속성 체크
2) **게이트**
- “상장폐지/CA 이벤트 포함 구간”에서 비정상 수익 스파이크 탐지 시 FAIL
- 거래가능일수 급감/NA 폭증 시 FAIL(파이프라인 보강 필요)
3) **기대 관측치**
- 성능은 일부 변해도, 이벤트 구간 이상치가 사라지고 결과 해석 가능해짐

---

### E3) 비용/슬리피지 스트레스 + turnover cap
1) **실험 정의**
- 비용 모델을 최소 3단으로 백테스트:
  - cost=1x(기본), 2x(보수), “vol-spread 연동”(변동성 확대 구간 슬리피지↑)
- turnover cap(일/주 단위) 1~2개 값만 테스트
2) **게이트**
- cost 2x에서 lockbox가 과도 붕괴하면 FAIL(비용 의존 알파)
- turnover cap 적용 시 체결 불능/포지션 튐(딱딱한 클리핑) 발생하면 FAIL(스무딩 필요)
3) **기대 관측치**
- 비용을 올려도 성능 형태가 유지되고, MDD가 개선되거나 최소한 악화 제한

---

### E4) 리밸런스 주기/체결 딜레이(실전성) 패치
1) **실험 정의**
- daily → weekly(또는 2~3일) 리밸런스 토글 1개
- “신호 생성일 다음 거래일 체결(1-bar delay)” 강제
2) **게이트**
- 딜레이에서 성능이 무너지면 FAIL(체결가 누수/초단기 의존)
- 주기 변경에 tuning만 민감하고 lockbox 둔감하면 과최적화 의심 → FAIL
3) **기대 관측치**
- 성능 소폭 하락은 정상이나, lockbox의 형태(순위/안정성)가 유지

---

### E5) 노출/기여도/레짐 어트리뷰션(+간단 오버레이 on/off)
1) **실험 정의**
- 리포트 자동 생성:
  - 종목별 PnL 기여도, 섹터(Tech/Healthcare) 내 비중 편향
  - 팩터 근사(시장베타/모멘텀/변동성) 노출 추정
  - 레짐 지표(관측용 ETF: QQQ/XLK/XLV/IHI의 추세/변동성)로 구간 분해
- 간단 오버레이: “risk-off 레짐에서 총 익스포저 0.7x로 축소” 같은 1개 토글만
2) **게이트**
- PnL이 1~2개 종목/1개 기간에 과집중이면 FAIL(서바이버십/우연 가능)
- 오버레이가 tuning만 개선하고 lockbox에선 악화면 FAIL(과최적화)
3) **기대 관측치**
- MDD가 줄고, 손실 구간이 특정 레짐과 연결되어 “설명 가능”해짐

---

## PASS 조건(공통) — champion 대비 “교체 가능” 기준을 명문화
아래 중 **하나라도 위반 시 FAIL**로 고정해 루프 품질을 우선 확보.
- **누수 게이트 통과(E1 필수)**: shuffle 무력화, shift 민감도 정상
- **비용 스트레스 통과(E3 필수)**: cost 2x에서도 lockbox_mean 급붕괴 금지(예: -15% 이내)
- **드로우다운 방어**: worst_mdd가 champion(-0.1118) 대비 **악화 금지**(또는 허용 악화폭 ≤0.5%p)
- **락박스 개선 목표(선택)**: lockbox_mean이 champion(1.7927) 대비 **+1% 이상**이면 “교체 후보”, +0.3~1%는 “보류”

---

## 성능이 안 움직일 때: 원인 분해(트리거/적용/노출/비용/레짐) 실행 체크리스트
아래는 “왜 개선이 안 되는지”를 **한 번에 분해**하기 위한 관측 포인트. (질문 금지 → 바로 계측/리포트로 고정)

### A) Trigger(신호가 발생하나?)
- **신호 발생률/포지션 변경률**: 일별(또는 리밸런스 시점) 신호 non-zero 비율
- **엔트리/익싯 빈도**: 너무 낮으면(필터 과함) 알파가 안 생김, 너무 높으면 비용에 먹힘
- **관측**: E4에서 주기 바꿨을 때 트레이드 수가 어떻게 변하는지 자동 로그

### B) Apply(신호가 적용되나? 게이트/클리핑/제약 때문에 죽나?)
- 포지션 한도, 현금 비중, 섹터 편향 제한, 리스크 타겟팅이 **신호를 상시 클리핑**하는지 확인
- **관측**: “원시 신호 → 최종 주문” 변환에서 클리핑 비율(%)을 리포트

### C) Exposure(노출이 알파를 지우나?)
- 8~14종목이면 **사실상 2~3개의 공통요인(시장/금리/리스크온)**에 좌우됨
- **관측**: E5에서 베타/변동성/모멘텀 근사 노출을 구간별로 찍고, PnL과 상관을 분해

### D) Cost(비용이 다 먹나?)
- “그로스 알파”와 “넷 알파”를 분리 기록:  
  - gross_return, cost, net_return을 일별로 저장
- **관측**: E3에서 cost 1x/2x/vol연동 간 성능 민감도(곡선 형태)가 핵심 진단 지표

### E) Regime(맞는 구간이 제한적이라 평균이 안 뜨나?)
- 레짐별 성능 분해:  
  - QQQ 추세↑/↓, (XLK-XLV) 상대강도, ETF 변동성 상/하위 분위
- **관측**: E5에서 레짐별 샤프/승률/최대낙폭을 표로 고정 → “먹는 구간”이 존재하는지 확인  
- 먹는 구간이 분명하면: 오버레이로 “안 먹는 구간” 익스포저 축소가 유효(단, 과최적화 게이트 필수)

---

## 48시간 실행 순서(명령형)
1) **E1을 최우선으로 실행**하고, FAIL이면 해당 피처/정렬/체결가를 먼저 제거(성능 개선 실험 금지).  
2) **E2로 survivorship/CA 정합성**을 고정하고, 이벤트 구간 이상치가 있으면 데이터 파이프라인부터 패치.  
3) **E3로 비용 스트레스 + turnover cap**을 걸어 “넷 알파” 생존 여부를 확정.  
4) **E4로 딜레이/주기 변경**에 버티는지 확인(실전성).  
5) **E5로 노출/레짐 리포트 자동화**하고, 필요 시 오버레이 1개만 토글로 실험.

이 흐름을 따르면, 성능이 안 움직일 때도 “누수/데이터/비용/적용/레짐” 중 어디가 병목인지 48시간 안에 분해되어 다음 patch가 자동으로 좁혀진다.
