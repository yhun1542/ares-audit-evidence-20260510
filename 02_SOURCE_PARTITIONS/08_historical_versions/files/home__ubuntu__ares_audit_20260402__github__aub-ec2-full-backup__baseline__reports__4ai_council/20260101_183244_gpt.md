## TOP1) 데이터/피처 누수(Leakage) 차단 + 체결(Execution) 시점 정합 패치
### (a) 왜 필요한지
- 현재 후보가 lockbox에서 매우 강함(특히 lockbox_min > 0). 이런 형태는 “진짜 개선”일 수도 있지만, **타임스탬프 누수/동일봉 체결/룩어헤드 피처**가 섞이면 lockbox가 가장 먼저 과대평가되는 패턴이 자주 나옴.
- “오늘 종가로 피처 계산 → 오늘 종가 체결” 같은 미세 누수는 성능을 크게 왜곡.

### (b) 위험/부작용
- 성능이 단기적으로 크게 하락(좋은 신호일 수 있음).
- 피처 지연(shift)로 신호가 늦어져 turnover/수익구조가 변형.

### (c) 최소 실험(2~3개, 하나의 번들로 실행)
**실험 번들 #1: `leakage_execution_hardening`**
1) **피처 전부 1-bar lag 강제**(EOD 기반이면 D+1 오픈/클로즈 체결만 허용)  
2) **체결 시점 2안 비교**: `next_open` vs `next_close` (둘 다 “미래정보 0” 보장)  
3) **ETF/지수 관측치(예: QQQ/XLV) 사용 시**: 동일 일자 값 금지(무조건 lag 적용)

### (d) PASS 조건
- **Leakage Sentinel 통과**(필수):  
  - 라벨을 +1일 뒤로 밀거나(shift) / 피처-라벨 alignment를 일부러 깨면 성능이 **유의하게 붕괴**해야 함(붕괴하지 않으면 누수 의심).
- 정합 버전에서 **lockbox_min ≥ 0** 유지 또는, 최소한 **champion 대비 worst_mdd 악화 금지(예: -0.09 이하 유지)**.
- `next_open`/`next_close` 중 하나가 일관되게 우세하면 그쪽으로 체결 규칙 고정.

### 48시간 루프
- (1) **실험 정의**: 모든 피처에 timestamp “as-of” 강제 + 1-bar lag + 체결시점 2안 A/B  
- (2) **게이트**: Sentinel 붕괴 확인 + lockbox_min + worst_mdd  
- (3) **기대 관측치**:  
  - 누수가 있으면: “강함 유지”가 아니라 **급락**이 나옴  
  - 누수가 없으면: 성능 소폭 하락 또는 비슷, 대신 안정성 지표가 정직해짐

## TOP2) 서바이버십/상장폐지/IPO 편향 제거 + 8~14종목 Universe PIT(시점정합) 패치
### (a) 왜 필요한지
- “지금 알고 있는 좋은 종목 12개”로 과거를 돌리면 **서바이버십 편향**이 잠깐의 개선처럼 보이는 착시를 만들 수 있음.
- Tech/Healthcare 8~14개는 전략상 합리적이지만, **PIT(시점정합) Universe 규칙**이 없으면 lockbox가 과대평가되기 쉬움.

### (b) 위험/부작용
- Universe가 바뀌면서 전략 특성이 변함(특히 신호의 평균 회귀/모멘텀 민감도 변화).
- 데이터 소스가 PIT를 지원하지 않으면 구현 난이도 증가.

### (c) 최소 실험(2~3개, 하나의 번들로 실행)
**실험 번들 #2: `pit_universe_tech_health_8_14`**
1) **Universe “시작일 고정” 안전버전**:  
   - 8~14개 고정 티커를 쓰되, **백테스트 시작일을 ‘가장 최근 IPO 이후’로 강제**(IPO 룩어헤드 차단)  
2) **Rolling Liquidity Universe 버전**(월 1회 리밸):  
   - 거래대금(ADV$) 기준 상위에서 Tech/Healthcare만 뽑아 **8~14개 유지**  
   - 이때 사용 변수는 **당시점 가격/거래량만**(기본은 PIT 보장)  
3) **상장폐지/거래정지 처리 강제**:  
   - 데이터에 delist가 있으면 delist return 반영, 없으면 **거래 불가로 처리 + 현금화** 규칙 고정

### (d) PASS 조건
- Universe가 바뀌어도 **락박스 성능이 “완전 붕괴하지 않을 것”**:  
  - 예: lockbox_mean이 기존 candidate 대비 **-10% 이내 감소**, worst_mdd **-0.10 이내 유지**
- 평균 종목 수가 **항상 8~14 유지**, 결측/거래불가 처리로 오류 없이 완주.

### 48시간 루프
- (1) **실험 정의**: “시작일 고정 안전버전” + “rolling liquidity PIT 버전” + “delist 처리”  
- (2) **게이트**: 8~14 유지, 오류 0, worst_mdd 상한  
- (3) **기대 관측치**:  
  - 서바이버십이 원인이면 rolling/PIT에서 성능이 크게 내려가며  
  - 진짜 알파면 **일정 수준 유지 + 안정성 개선**이 남음

## TOP3) 비용(수수료/슬리피지) + 회전율(turnover) 목적함수 반영 패치
### (a) 왜 필요한지
- 지금 지표는 좋지만, **비용 미반영은 “실전에서 0이 되는 알파”의 1순위 원인**.
- Tech 대형주는 스프레드가 좁아도, 8~14개 집중 포트에서 잦은 리밸이면 비용이 누적.

### (b) 위험/부작용
- 비용을 넣는 순간 전략이 “안 움직이는 것처럼” 보일 수 있음(사실은 현실화).
- 비용 모델을 과하게 잡으면 과도한 보수화(기회 손실).

### (c) 최소 실험(2~3개, 하나의 번들로 실행)
**실험 번들 #3: `cost_turnover_aware`**
1) **고정 bps 비용 모델**(매수/매도 각각): 2~10bps 그리드  
2) **참여율 기반 슬리피지**: `k * (trade_value / ADV$)^α` (간단히 α=0.5 고정)  
3) **turnover penalty on**: 목적함수에 `λ * turnover` 추가(λ 그리드 2~3개만)

### (d) PASS 조건
- 비용 포함 “net” 기준으로  
  - lockbox_mean이 champion 대비 **유지 또는 소폭 개선**,  
  - turnover가 **유의하게 감소**(예: -20% 이상)하면서  
  - worst_mdd 악화 금지.
- 비용 그리드에서 성능이 “딱 1점”만 튀지 않고 **완만한 내성(curve)**이 보일 것(과최적화 방지 신호).

### 48시간 루프
- (1) **실험 정의**: 비용모델 2종 + turnover penalty 1종을 작은 그리드로  
- (2) **게이트**: net 성능 + turnover 감소 + 곡선 내성  
- (3) **기대 관측치**:  
  - 과거가 비용에 민감하면 net이 급락  
  - 견고하면 비용 증가에도 순위가 크게 안 바뀜

## TOP4) 레짐(금리/변동성) 내성 + 노출(베타/섹터) 게이트 추가 패치 (ETF는 관측지표만)
### (a) 왜 필요한지
- Tech/Healthcare는 레짐에 따라 동행/역행이 갈리고, 8~14 집중은 **베타 노출이 수익을 ‘가짜 알파’처럼 보이게** 만들 수 있음.
- ETF(예: QQQ, XLV)는 **매매 금지**여도 “시장/섹터 레짐 관측지표”로는 매우 유용.

### (b) 위험/부작용
- 노출 제약이 강하면 수익이 줄고 “현금 비중↑”이 생김.
- 베타 억제가 과하면 추세장에서 뒤처짐.

### (c) 최소 실험(2~3개, 하나의 번들로 실행)
**실험 번들 #4: `regime_exposure_guardrails`**
1) **베타 캡**: (관측지표 QQQ로) 포트폴리오 60일 회귀베타를 `|β| ≤ 0.8`로 제한(초과 시 비중 축소/현금)  
2) **Vol targeting**: 20일 실현변동성 기준 목표 변동성으로 레버리지/현금 조절(레버리지는 금지면 현금조절만)  
3) **리스크-오프 필터**: VIX(지수) 또는 QQQ drawdown 기반으로 “신호 적용 게이트” on/off(단순 1~2개 임계치)

### (d) PASS 조건
- lockbox에서 **worst_mdd 개선 또는 유지**(악화 금지)  
- fold별 성능 편차 감소(최악 폴드 개선)  
- 리스크-오프 구간에서 포지션이 자동 축소되는지(운영상 설명 가능성 확보)

### 48시간 루프
- (1) **실험 정의**: 베타캡/볼타겟/리스크오프를 작은 조합으로  
- (2) **게이트**: worst_mdd, 최악 폴드 개선, 과도한 현금화(예: 평균 노출 < 30%면 FAIL)  
- (3) **기대 관측치**:  
  - 진짜 알파면 레짐필터가 “수익 일부”를 줄여도 **MDD를 줄여 효율이 유지**  
  - 가짜면 대부분이 베타였어서 수익이 크게 사라짐

### (a) 왜 필요한지

- 초기에는 로그/해시 계산으로 실행시간이 소폭 증가.
- 너무 엄격한 게이트는 탐색 속도를 늦춤.

### (c) 최소 실험(2~3개, 하나의 번들로 실행)
**실험 번들 #5: `ops_reproducibility_hardening`**
1) **데이터 해시/스냅샷 고정**:

2) **시드/정렬/멀티스레딩 결정성 강제**:

3) **실험 실패내성**:

### (d) PASS 조건

# 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐)
아래 순서대로 **한 번에 하나씩 고정/교란**해서 병목을 특정:

## 1) Trigger(신호 생성) 문제
- **신호가 실제로 발생하는가**: 트리거 빈도(일/주), 트리거 후 평균 보유기간 로그  
- **과소/과대 트리거**:  
  - 너무 적으면 수익이 ‘없어 보임’(표본 부족)  
  - 너무 많으면 비용/노이즈에 먹힘

## 2) Apply(적용/체결) 문제
- **신호→주문→체결 시점**이 한 칸이라도 미래로 새면(또는 반대로 너무 늦으면) 결과가 왜곡/둔화  
- next_open/next_close 바꿔도 성능이 비슷해야 정상(극단적으로 달라지면 실행 가정 문제)

## 3) Exposure(노출) 문제
- 포트 수익을 **요인 분해**: QQQ(시장), XLV/XLK(섹터) 관측지표에 대한 베타/상관  
- 알파가 아니라 **베타 + 레버리지 효과**면, 노출 캡 걸자마자 성능이 멈추는 게 정상(원인 확정)

## 4) Cost(비용) 문제
- gross는 움직이는데 net이 안 움직이면 비용 문제 확정  
- turnover 상위 10% 거래일을 뽑아 “그 날만 거래 금지”했을 때 성능 변화로 비용 민감도 확인

## 5) Regime(레짐) 문제
- 동일 전략을 레짐별로 쪼개서(예: VIX 상/하, 금리 급등/완만) 성능 표를 만들면  
  - “특정 레짐에서만” 작동하면: 필터/노출조절이 답  
  - “모든 레짐에서 조금씩”이면: 피처/모델 신호 품질 문제

---

원칙적으로, 지금 단계에서의 최우선은 **(TOP1) 누수/체결 정합을 확정**하고, 그 다음이 **(TOP2) PIT Universe로 서바이버십 제거**, 그리고 **(TOP3) 비용을 net으로 고정**하는 것입니다. 이 3개를 통과한 성능만이 이후 개선(모델/전략)을 의미 있게 만듭니다.
