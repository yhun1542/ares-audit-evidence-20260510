### 2) 제안별 상세 실행 계획

#### 1. [System] MDD 계산 로직 및 로그 파서 긴급 복구
*   **(a) 필요성:** `worst_mdd: None`은 리스크 관리 불능 상태. Rebalance 로그 로딩 실패(`Expecting value...`)로 인해 트레이딩 원인 분석 불가.
*   **(b) 리스크:** 시스템 내부 코어 수정 시 기존 벤치마크와의 호환성 일시 단절 가능성.
*   **(c) 실험 (Experiments):**
    1.  `FIX_MDD_CALC`: 자산 곡선(Equity Curve)이 0 또는 NaN일 때 예외 처리 제거하고 0으로 채운 뒤 MDD 재계산.
    2.  `FIX_LOG_PARSER`: `rebalance.csv`가 비어있거나 헤더만 있을 경우 `rebalance.jsonl`로 우회하여 파싱하도록 로더 수정.
    3.  `TEST_UNIT`: 임의의 손실 데이터를 주입하여 MDD가 음수로 찍히는지 단위 테스트.
*   **(d) PASS 조건:** `worst_mdd`가 숫자(예: -0.15)로 출력됨 AND `aub_rebalance_pinpoint.py`가 에러 없이 실행됨.

#### 2. [Data] Degenerate Folds(1,2,3,8) 원인 규명 및 유니버스 확장
*   **(a) 필요성:** 특정 기간(Fold 1,2,3,8)에 거래가 전무하거나 수익률이 0인 것은 데이터 결측 혹은 필터가 너무 강력하여 Tech/Health 종목이 모두 탈락했기 때문.
*   **(b) 리스크:** 억지로 거래를 발생시키면(Over-trading) 손실폭 확대 가능.
*   **(c) 실험 (Experiments):**
    1.  `EXP_UNIVERSE_DENSITY`: 해당 Fold 기간 내 Tech+Healthcare 시총 상위 20개 종목의 데이터(OHLCV) 존재 여부 전수 검사.
    2.  `EXP_RELAX_FILTER`: 유동성/변동성 필터(예: ADV, ATR)를 50% 수준으로 완화하여 해당 Fold에서 진입 신호 발생하는지 확인.
    3.  `EXP_REFILL_DATA`: 데이터 공급자 변경 혹은 해당 구간 결측치 보간(Interpolation) 적용.
*   **(d) PASS 조건:** Degenerate Folds 개수가 0개 또는 1개 이하로 감소.

#### 3. [Cost] 강제 슬리피지/수수료 주입 후 OOS 재검증
*   **(a) 필요성:** OOS Mean 3.32는 비현실적. 비용 0 가정 시 발생하는 과최적화(Overfitting) 환상을 걷어내야 함.
*   **(b) 리스크:** OOS Mean이 급락하여 전략 폐기 수순으로 갈 수 있음(그러나 이는 필요한 고통임).
*   **(c) 실험 (Experiments):**
    1.  `EXP_COST_BPS_10`: 매매당 슬리피지 10bps + 수수료 5bps 강제 적용.
    2.  `EXP_COST_BPS_25`: 매매당 슬리피지 25bps(보수적) 적용.
    3.  `EXP_DELAY_EXEC`: 시그널 발생 다음 틱/봉이 아닌, 1분 뒤 체결 가정(Latency 시뮬레이션).
*   **(d) PASS 조건:** 비용 적용 후에도 OOS Mean > 0.5 유지 AND Sharpe Ratio > 1.5.

#### 4. [Logic] Exposure 강제 하한 설정 (0.0 -> 0.2)
*   **(a) 필요성:** 현재 `exposure_min: 0.0`은 시장 관망이 너무 잦음을 의미. Tech/Health 중심 포트폴리오라면 최소한의 베타 노출이 있어야 함.
*   **(b) 리스크:** 하락장에서 현금 비중 축소로 인한 MDD 증가.
*   **(c) 실험 (Experiments):**
    1.  `EXP_MIN_EXP_02`: 포트폴리오 내 주식 비중 최소 20% 강제 (종목이 없으면 QQQ/XLV라도 매수 로직 검토하되, ETF 매매 제외 규칙상 현금성 자산 대신 변동성 낮은 대형주 강제 보유).
    2.  `EXP_FORCE_TOP3`: 시그널 강도 상위 3개 종목은 필터 통과 시 무조건 매수.
*   **(d) PASS 조건:** `exposure_min` >= 0.15 AND `oos_mean` 급락 없음.

#### 5. [Alpha] Tech/Bio 섹터 모멘텀 팩터 가중치 재조정
*   **(a) 필요성:** Tech/Healthcare 특성상 모멘텀 지속성이 강함. 현재 팩터가 Mean Reversion(역추세)에 치우쳐있다면 추세를 놓치고 있을 가능성.
*   **(b) 리스크:** 추세 전환점(Whipsaw)에서 손실 누적.
*   **(c) 실험 (Experiments):**
    1.  `EXP_FACTOR_MOM_WT`: 12개월 모멘텀 및 1개월 리버설 팩터 비중을 7:3으로 조정.
    2.  `EXP_SECTOR_NEUTRAL`: 섹터 내 랭킹(Sector Neutral) 대신 전체 유니버스 절대 모멘텀 사용 실험.
*   **(d) PASS 조건:** Tech/Healthcare 종목 보유 기간 평균 5일 이상 증가.

### 3) 성능(Delta)이 움직이지 않을 때의 원인 분해 아이디어

만약 위 실험을 해도 `No-Delta`가 지속된다면 다음 5단계를 체크하십시오.

1.  **Trigger (신호 발생):** 파라미터를 변경했음에도 `Buy Threshold`에 도달하는 종목 집합이 수학적으로 100% 동일한가? (예: `Score > 0.9`인데 모든 종목이 0.5 미만인 경우)
2.  **Allocation (비중 할당):** 신호는 바뀌었으나, `Risk Parity`나 `Max Weight` 로직에 의해 최종 주문 수량이 0 혹은 동일 수량으로 수렴하는가?
3.  **Execution (주문 집행):** 백테스팅 엔진이 주문을 생성했으나 `Cash Constraint`(현금 부족) 또는 `Volume Filter`(거래량 부족)로 인해 체결 거부(Reject) 당하고 있는가?
    *   *확인법:* 체결 로그에서 `Order Rejected` 카운트 확인.
4.  **Data Caching (데이터 고착):** 실험 실행 시 Feature를 다시 계산하지 않고 기존에 저장된 `.pkl`이나 캐시를 계속 로드하고 있는가?
    *   *조치:* 캐시 폴더(`artifacts/cache/`) 강제 삭제 후 재실행.
5.  **Survivorship Bias Filter (생존 편향 필터):** 현재 시점에 상장 폐지된 종목이 과거 데이터에는 존재하나, 상장 유지 조건 필터가 너무 강력하여 과거의 유효한 종목들을 모두 날려버렸는가?
