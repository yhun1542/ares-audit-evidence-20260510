## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — **명령형 체크리스트**

1) **리포트/아티팩트/리밸런스 로그 파이프라인 복구(운영 리스크 최우선)**
- `champion.file`, `lane_hash`, `run_hash`, `worst_mdd`, rebalance 로그(CSV/JSONL) **필수 필드 강제 생성**
- `aub_rebalance_pinpoint.py` 입력 경로/포맷 검증(현재 `--base-log`가 문자열로 들어가며 파일 오픈 실패) 및 **자동 폴백 로더(JSON→CSV 변환)** 추가
- “재현 불가(run 식별자 없음)” 상태를 제거해 **48h 자동 루프의 디버깅 가능성 확보**

2) **누수/폴드 퇴화(degenerate_folds) 차단(과최적화/검증 붕괴 우선)**
- degenerate_folds=[1,2,3,8] 원인(표본 부족/결측/필터 후 공집합/시간 누수)을 **실험 전 게이트로 차단**
- 시계열 split에 **purge/embargo**(예: 5~20일) 적용 + 폴드별 최소 샘플/커버리지 하한 설정
- OOS Mean이 높아도 “검증이 퇴화된 승자” 가능성을 먼저 제거

3) **서바이버십/포인트-인-타임(PIT) 정합성 강제(서바이버십/누수 동시 점검)**
- 유니버스(미국주식, Tech+Healthcare) 구성 시 **당시점 상장/거래가능/섹터 분류**만 사용
- 액션(분할/합병/상폐) 처리 및 조정가/리턴 정합성 점검(“미래에 알게 되는 종목만 남는” 편향 제거)

4) **거래비용/슬리피지/턴오버를 성능지표에 강제 반영(비용 미반영 우선)**
- 백테스트 PnL에 **고정 수수료+스프레드+충격(impact)** 최소모델 적용
- 턴오버 상한/페널티를 포트폴리오 구성에 넣어 “순이익이 움직이는지” 확인

5) **노출(Exposure) 및 레짐 게이팅 재설계(노출/레짐/운영 안정성)**
- 현재 exposure_min/max = 0.0/0.839 → “자주 0이거나 과도하게 흔들림” 가능성 점검
- ETF는 **관측지표**로만 사용: 예) `XLK/XLV`, `SPY` 모멘텀/드로다운으로 **위험온/오프 레짐**을 정의하고 총익스포저/섹터 틸트를 스케일링
- 종목은 **미국 Tech+Healthcare 8~14개**로 제한(ETF 매매 금지)

## 제안별 상세: (a) 필요성 (b) 위험/부작용 (c) 최소 실험(2~3 arms) (d) PASS 조건  
아래는 **실험 5개로 제한**(각 실험은 2~3개 arms 포함) + **48시간 자동 루프** 형태로 작성.

# EXP-1) 리밸런스/아티팩트 로깅 복구 실험 (운영 리스크)
### (a) 왜 필요한지
- 현재 상태에서 `champion.file/lane_hash/run_hash=None`, `worst_mdd=None`, rebalance pinpoint가 입력 파싱 실패 → **진단/회귀/재현이 불가능**.
- “성능이 안 움직이는 원인”이 모델이 아니라 **로그/파이프라인 결함**일 수 있음.

### (b) 위험/부작용
- 로깅/검증 강화로 런타임 증가(경미).
- 필수 필드 누락 시 런이 Fail-fast로 더 자주 멈춤(의도된 안정성).

### (c) 최소 실험(2~3 arms) — 48h 자동 루프
**(1) 실험 정의**
- Arm A: 현행 유지(컨트롤)  
- Arm B: `run_manifest.json` 강제 생성(필수키: run_hash, lane_hash, data_range, universe_hash, cost_model_hash, git_sha) + rebalance 로그를 **단일 JSONL 스키마**로 표준화  
- Arm C: `aub_rebalance_pinpoint.py`에 **입력 검증/폴백**(CSV/JSONL/JSON 자동감지, 파일 없으면 “실험 실패”로 명시 종료)

**(2) 게이트(실험 전/후 통과 조건)**
- 모든 런에서 다음 파일 생성 확인(없으면 FAIL):  
  - `artifacts/<run>/run_manifest.json`  
  - `reports/<run>/rebalance.jsonl` (0바이트 금지)  
  - `reports/<run>/metrics.json`에 `worst_mdd` 포함
- `aub_rebalance_pinpoint`가 exit code 0 & 리포트 생성

**(3) 기대 관측치**
- “리밸런스가 없어서 성능이 안 변함/노출이 0으로 붙음” 같은 문제를 **리밸런스 이벤트 단위로** 추적 가능
- 이후 실험(비용/노출/레짐)의 효과를 **실제 매매 이벤트 변화로 연결** 가능

### (d) PASS 조건
- 48시간 내 모든 런에서 **재현 식별자(run_hash/lane_hash) 100% 생성**
- rebalance pinpoint 리포트가 **누락 없이 생성**되고, 리밸런스 이벤트 수/턴오버/비용이 확인 가능

---

# EXP-2) Degenerate folds/누수 차단 실험 (과최적화/검증 붕괴)
### (a) 왜 필요한지
- degenerate_folds 존재는 “폴드 일부가 공집합/상수 타깃/커버리지 붕괴”를 시사 → OOS Mean이 높아도 **신뢰 불가**.
- 누수는 성능이 “갑자기 올라가고” “패치해도 안 움직이는 것처럼 보이는” 대표 원인.

### (b) 위험/부작용
- purge/embargo로 학습 데이터 감소 → 단기적으로 OOS Mean 하락 가능(정상).
- fail-fast 게이트로 실험 실패가 늘 수 있음(정상).

### (c) 최소 실험(2~3 arms) — 48h 자동 루프
**(1) 실험 정의**
- Arm A: 현행 split  
- Arm B: 시계열 CV에 `purge=5 trading days`, `embargo=5` 적용 + 폴드별 최소 표본수/유효리턴 비율 하한  
- Arm C: Arm B + “라벨/피처 시간정렬 검증(assert feature_timestamp < decision_timestamp)” 추가

**(2) 게이트**
- `degenerate_folds == []` 아니면 FAIL
- 각 폴드별 유효 샘플 수 `>= N_min`(예: 500 row-equivalent) 미달 시 FAIL
- 폴드별 예측 분산이 0에 수렴(상수 예측)하면 FAIL

**(3) 기대 관측치**
- OOS Mean이 다소 떨어져도, oos_min/분산/폴드 안정성이 개선
- “승자가 바뀌어도 성능이 안 움직임” → 사실상 검증이 퇴화되어 구분력이 없던 상태를 제거

### (d) PASS 조건
- degenerate_folds 제거 + 폴드별 메트릭 분산이 합리적
- OOS Mean이 약간 하락해도 **oos_min 개선 또는 변동성 감소(검증 신뢰도 상승)**

---

# EXP-3) 서바이버십/PIT 유니버스 정합성 실험 (서바이버십/누수)
### (a) 왜 필요한지
- “미국 Tech+Healthcare 8~14개” 전략에서 서바이버십이 있으면 **실제로는 선택 불가능한 승자 종목**만 남아 성능이 고정/왜곡될 수 있음.
- 섹터 분류/상장상태가 PIT가 아니면 미래정보 누수.

### (b) 위험/부작용
- 유니버스가 줄어 신호가 약해질 수 있음.
- 데이터 소스에 PIT 메타가 불완전하면 커버리지 하락.

### (c) 최소 실험(2~3 arms) — 48h 자동 루프
**(1) 실험 정의**
- Arm A: 현행 유니버스/섹터 필터  
- Arm B: PIT 유니버스 강제(당일 기준: 상장/거래가능/가격존재/섹터존재) + 결측 시 제외 규칙 표준화  
- Arm C: Arm B + “상폐/합병 등 이벤트 발생 시 마지막 거래일까지 포함 + delist return 처리(가능 범위 내 최소모델)” 적용

**(2) 게이트**
- 매 리밸런스 시점에 종목 리스트가 8~14개 유지(미달이면 “현금”이 아니라 **대체 규칙으로 채우거나** 그 시점은 FAIL로 기록)
- 미래 섹터/상장정보 참조 탐지(타임스탬프 역전) 시 FAIL

**(3) 기대 관측치**
- 성능이 과장되어 있던 경우 OOS Mean 하락 + 안정성(일관성) 증가
- 종목 교체/공백이 로그로 명확해져 “적용/노출 문제” 분리가 쉬워짐

### (d) PASS 조건
- PIT 강제 후에도 OOS Mean이 크게 붕괴하지 않거나(예: -10% 이내), 대신 **oos_min/턴오버/폴드 안정성**이 개선
- 유니버스 규칙이 재현 가능(해시/매니페스트로 고정)

---

# EXP-4) 거래비용/턴오버 반영 실험 (비용 미반영)
### (a) 왜 필요한지
- 비용 미반영이면 모델이 “자주 갈아타는” 방향으로 고정되고, 패치를 해도 실현가능 성능은 안 움직임.
- rebalance 데이터가 현재 깨져 있어 비용/턴오버를 못 보고 있음(→ EXP-1과 결합 효과).

### (b) 위험/부작용
- 비용 반영 즉시 성능 하락 가능(정상).
- 너무 보수적 비용이면 거래가 사라져 노출 0이 늘 수 있음(게이트로 관리).

### (c) 최소 실험(2~3 arms) — 48h 자동 루프
**(1) 실험 정의**
- Arm A: Gross PnL(현행)  
- Arm B: Net PnL = Gross - (bps_cost * turnover) - (half_spread * |delta|)  
  - 예: 기본 5~20bp 수준에서 시작(파라미터는 매니페스트에 기록)  
- Arm C: Arm B + 턴오버 페널티/상한(예: 일/주간 turnover cap)로 포트폴리오 최적화에 제약 추가

**(2) 게이트**
- 리밸런스 이벤트마다 `turnover`, `cost`, `net_return` 기록(누락 시 FAIL)
- 평균 노출이 0으로 붕괴하면 FAIL(예: avg gross exposure < 0.2)

**(3) 기대 관측치**
- Gross는 비슷해도 Net이 갈라지며, “성능이 안 움직임”의 원인이 **턴오버/비용 상쇄**인지 확인 가능
- 비용을 견디는 신호만 남아 다음 실험(레짐 게이팅)의 효과가 명확해짐

### (d) PASS 조건
- Net 기준 OOS Mean이 컨트롤 대비 개선 또는, 최소한 **oos_min 개선 + turnover 유의미 감소**
- 비용 파라미터가 매니페스트로 고정되어 재현 가능

# EXP-5) 레짐 관측(ETF) 기반 노출 스케일링 실험 (노출/레짐)
### (a) 왜 필요한지
- exposure가 0~0.84로 넓고, “언제 왜 0이 되는지/과노출 되는지”가 불명확하면 성능이 정체되기 쉬움.
- Tech/Healthcare는 레짐(금리/리스크온오프)에 민감 → 동일 신호라도 레짐 필터로 실현 성능이 달라짐.
- ETF는 매매 금지, **관측지표로만** 사용 가능.

### (b) 위험/부작용
- 레짐 필터가 과도하면 기회 손실(언더트레이딩).
- 지표가 지연되면 반응이 늦어짐.

### (c) 최소 실험(2~3 arms) — 48h 자동 루프
**(1) 실험 정의** *(종목 매매는 미국 개별주만, 8~14개, Tech+Healthcare로 제한)*
- Arm A: 현행 익스포저/헤지/스케일  
- Arm B: 레짐 스케일링만 추가  
  - 관측지표: `SPY` 20/60일 모멘텀, `XLK/XLV` 상대강도(Tech vs Healthcare), `SPY` 최근 드로다운  
  - 규칙 예: 위험오프(모멘텀↓ 또는 DD↑)면 gross exposure 0.3~0.5로 축소, 위험온이면 0.7~0.9  
- Arm C: Arm B + 섹터 내부 비중 스케일(위험오프 시 Healthcare tilt, 위험온 시 Tech tilt)

**(2) 게이트**
- 종목 수 항상 8~14 유지, 섹터는 Tech/Healthcare만(분류 기준 해시 고정)
- gross exposure 상한/하한 강제(예: 0.2~0.9), 급변(1회 리밸런스에 Δexposure > 0.4)이면 FAIL로 기록

**(3) 기대 관측치**
- oos_min(꼬리)이 개선되고 drawdown이 감소
- 성능이 그대로여도 “레짐별 기여”가 분리되어 다음 단계(신호 자체 개선 vs 노출 개선)를 결정 가능

### (d) PASS 조건
- OOS Mean이 비슷해도 **oos_min 개선** 또는 **추정 MDD/변동성 감소**
- 레짐별 성과 테이블에서 위험오프 구간 손실이 유의미하게 축소

## 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 명령형 트리아주

### 1) 트리거(신호 생성) 레벨
- **피처/라벨 시간정렬 감사**: `feature_ts < decision_ts < return_window_end` 위반 로그를 0으로 만들기
- **신호 품질 관측치 고정 출력**: 매일/리밸런스마다  
  - signal coverage(% non-null), cross-sectional std, rank autocorr  
  - IC/RankIC(가능하면) 및 폴드별 분포 저장
- 신호가 있는데 성능이 안 움직이면 → 아래 “적용/노출/비용”으로 이동

### 2) 적용(포트폴리오 구성/제약) 레벨
- 리밸런스 이벤트 단위로 다음을 반드시 로깅하고 비교:
  - target weights vs executed weights (차이=제약/라운딩/결측 때문인지)
  - 종목 수가 8~14를 벗어나는 순간과 원인(필터/가격결측/거래불가)
- “신호가 변해도 weights가 거의 고정”이면 → 제약/정규화/버그(스케일링, 클리핑) 의심

### 3) 노출(Exposure) 레벨
- gross/net exposure, beta-to-SPY(회귀 또는 근사), sector exposure를 시계열로 저장
- exposure_min=0이 잦으면:
  - 게이팅 조건이 과도한지
  - 비용/턴오버 제약이 거래를 막는지
  - 유니버스 공집합이 나는지(=PIT/결측) 점검

### 4) 비용(Execution) 레벨
- “Gross 개선인데 Net이 정체”이면:
  - turnover 분해(신규진입/퇴출/리밸런싱)와 비용 기여도를 리포트로 고정
  - 비용 파라미터를 2~3배로 스트레스 테스트(실험이 아니라 **리포트 산출**로)해서 민감도 확인
- 거래비용이 원인이면 해결책은 신호가 아니라 **턴오버 제어/리밸런스 주기/스케일링**임

### 5) 레짐(Regime) 레벨
- ETF는 관측지표로만: `SPY`, `XLK`, `XLV`로 레짐을 2~3개로 단순 분류(위험온/중립/위험오프)
- 레짐별 성과/노출/턴오버를 분해해 “어느 구간에서만 죽는지” 고정 출력
- 특정 레짐에서만 죽으면 → 신호를 바꾸기 전에 **레짐 게이팅/섹터 틸트**부터 패치

## 48시간 자동 루프 운영 형태(공통 템플릿)
- **(1) 실험 정의**: EXP-1~5 중 1개만 “활성” + arms는 최대 3개
- **(2) 게이트**: fail-fast(로그/폴드/유니버스/비용/노출) 중 1개라도 불만족 시 “성능 비교” 자체를 중단하고 원인 로그를 남기기
- **(3) 기대 관측치**: OOS Mean만 보지 말고 `degenerate_folds`, `oos_min`, `worst_mdd`, turnover, net PnL, exposure 분해를 **고정 패널**로 저장

이 순서대로 하면, 현재처럼 “성능이 안 움직이는” 상태에서 가장 흔한 5대 원인(누수/과최적화/서바이버십/비용 미반영/운영 리스크)을 48시간 내에 우선 제거하고, 그 다음에야 신호 자체(알파) 개선이 의미 있게 진행됩니다.
