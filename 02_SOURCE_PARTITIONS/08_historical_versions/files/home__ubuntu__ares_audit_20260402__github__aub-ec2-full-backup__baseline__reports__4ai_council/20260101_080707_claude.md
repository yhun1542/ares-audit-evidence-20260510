### P1. Lockbox 동일 원인 규명 (누수/무효 점검)

```
WHY: Candidate가 lockbox에서 Champion과 100% 동일 = 
     (a) 신호가 lockbox 구간에서 0회 발동, 또는 
     (b) 코드 버그로 모듈 미적용
```

| 항목 | 내용 |
|------|------|
| **(a) 필요성** | 실험 자체가 무효인지 확인 필수—이게 안 되면 모든 후속 실험 의미 없음 |
| **(b) 위험** | 없음 (진단 전용) |
| **(c) 최소 실험** | |

```
EXP-1.1: Lockbox 구간 신호 발동 로그 추출
──────────────────────────────────────────
- 명령: python3 tools/signal_audit.py --config candidate_*.json --period lockbox --output logs/lb_signal_firing.csv
- 게이트: firing_count > 0 이면 PASS
- 기대치: MRD/ARS/FSA 중 최소 1개가 lockbox에서 10회 이상 발동

EXP-1.2: Champion vs Candidate 포지션 diff
──────────────────────────────────────────
- 명령: python3 tools/position_diff.py --a champion_v5.json --b candidate_*.json --period lockbox
- 게이트: diff_days > 5 이면 모듈 유효, == 0 이면 버그
- 기대치: 최소 5거래일 포지션 차이
```

| **(d) PASS 조건** | EXP-1.1 firing ≥ 10 AND EXP-1.2 diff_days ≥ 5 → 모듈 유효, 아니면 코드 버그 |

### P2. Threshold 과최적화 점검

```
WHY: tuning_min = 0.0508 (거의 0) → 특정 fold에서 
     파라미터가 극단 세팅, 다른 fold에서 무력화
```

| 항목 | 내용 |
|------|------|
| **(a) 필요성** | 0.05 수익률 fold가 lockbox와 유사 regime이면 실전 붕괴 |
| **(b) 위험** | 해당 fold 제거 시 낙관 편향 발생 가능 |
| **(c) 최소 실험** | |

```
EXP-2.1: Worst-fold 레짐 분석
──────────────────────────────────────────
- 명령: python3 tools/regime_tag.py --fold worst --output logs/worst_fold_regime.json
- 게이트: regime == "high_vol" or "drawdown" 이면 정상, "normal_bull"이면 위험
- 기대치: 2022 Q2~Q3 (Fed hike) 구간과 매핑

EXP-2.2: Threshold 민감도 sweep (좁은 범위)
──────────────────────────────────────────
- 명령: python3 tools/param_sweep.py --module MRD --param threshold --range 0.8,1.2 --step 0.05
- 게이트: std(fold_returns) < 0.3 이면 robust
- 기대치: 현재 대비 std 20% 감소
```

| **(d) PASS 조건** | EXP-2.2 std < 0.3 AND worst_fold_return > 0.5 |

## 2. 성능 미동 원인 분해 (Null Result 진단)

```
성능이 안 움직일 때 5-Layer 점검
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Layer 1: TRIGGER (신호 발동)
├─ 점검: lockbox 구간 신호 firing count
├─ 의심: threshold 너무 tight → 0회 발동
└─ 진단: EXP-1.1 실행

Layer 2: APPLICATION (적용 로직)
├─ 점검: 신호 fired 후 실제 포지션 변경 여부
├─ 의심: rebalance 주기와 신호 타이밍 불일치
└─ 진단: EXP-1.2 position diff

Layer 3: EXPOSURE (노출 크기)
├─ 점검: 포지션 변경 size가 유의미한지
├─ 의심: max_position_delta 제약으로 미미한 변화
└─ 진단: avg_position_change 계산

Layer 4: COST (비용 상쇄)
├─ 점검: 수익 있으나 turnover로 상쇄
├─ 의심: 잦은 in/out으로 gross > net
└─ 진단: EXP-3.1, 3.2 실행

Layer 5: REGIME (시장 구조)
├─ 점검: lockbox 구간이 신호 무효 레짐인지
├─ 의심: mean-reversion 신호인데 trending market
└─ 진단: EXP-2.1 regime 태그
```

## 3. 48h 자동 루프 스케줄

```yaml
# schedule.yaml (cron 등록)

T+0h (즉시):
  - run: EXP-1.1, EXP-1.2  # 누수/무효 확인
  - gate: firing > 0 AND diff_days > 0
  - on_fail: HALT (코드 디버그)

T+4h:
  - run: EXP-2.1, EXP-2.2  # Threshold 검증
  - gate: std < 0.3
  - on_fail: param 범위 축소 후 재실험

T+12h:
  - run: EXP-3.1, EXP-3.2  # 비용 검증
  - gate: cost_20bps > 1.5
  - on_fail: turnover penalty 추가

T+24h:
  - run: EXP-4.1, EXP-4.2  # 레짐/섹터 검증
  - gate: FSA 기여 > 0.1
  - on_fail: FSA 모듈 제거 검토

T+36h:
  - run: EXP-5.1, EXP-5.2  # MDD 방어
  - gate: worst_mdd > -10%
  - on_fail: vol_scale 강화

T+48h:
  - aggregate: 모든 PASS 모듈 조합
  - run: full backtest --lockbox
  - promote_if: lockbox_mean > 1.80 AND worst_mdd > -10%
```
