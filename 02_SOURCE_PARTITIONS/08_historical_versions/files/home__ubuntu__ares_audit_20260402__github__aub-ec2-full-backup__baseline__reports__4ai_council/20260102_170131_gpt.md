아래는 **24~48시간 내 우선순위 TOP5(코드/아키텍처/전략)**이며, 전체 제안은 **실행 가능한 patch/실험 5개(E1~E5)**로만 제한했다. 각 TOP5는 이 5개 실험 중 **2~3개를 재사용**해 연결한다. (48시간 자동 루프: **(1) 실험 정의 → (2) 게이트 → (3) 기대 관측치** 포함)

---

## TOP5 우선순위 제안 (24~48h)

### 1) (운영/아키텍처) Rebalance 로그/스키마를 “항상” 남기고 pinpoint 도구가 깨지지 않게 고쳐라
- **왜 필요한가**
  - 현재 `aub_rebalance_pinpoint`가 **base-log/candidate-log 로드 실패**로 “무슨 리밸런스가 일어났는지”가 완전히 블라인드 상태다.
  - Champion 메타에도 `lane_hash/run_hash=None`, `worst_mdd=None` 등 **추적 불가/리포팅 누락** 징후가 있어, 성능 정체(No-Delta) 원인이 “전략”인지 “파이프라인”인지 분리 불가다.
- **위험/부작용**
  - 로그를 강제하면 저장/IO 비용 증가, 실패 시 파이프라인이 더 자주 중단될 수 있음(하지만 이건 의도된 fail-fast로 운영리스크 감소).
- **연결 실험(2~3개)**: **E1, E5**

---

### 2) (누수/과최적화 우선) Degenerate folds를 “실패 조건”으로 승격하고, Purge/Embargo로 누수 가능성을 먼저 끊어라
- **왜 필요한가**
  - `degenerate_folds: [1,2,3,8]`는 **OOS 추정이 무의미해지는 구조적 결함** 신호다(예: 거래 0건, 항상 동일 포지션, 지표 상수, 라벨 누수 등).
  - 이 상태에서 평균 OOS가 좋아 보여도 **과최적화/데이터 분할 오류**일 확률이 높고, 다음 실험들이 전부 무의미해진다.
- **위험/부작용**
  - 규제가 강화되면 단기적으로 OOS 평균이 떨어질 수 있음(“진짜 성능”으로 수렴하는 과정).
  - trade 수가 적은 전략은 통과가 어려워질 수 있음.
- **연결 실험(2~3개)**: **E2, E5, (선택)E4**

---

### 3) (비용 미반영 우선) 비용/슬리피지/턴오버를 “게이트”로 걸고, 비용 민감도를 자동으로 스윕하라
- **왜 필요한가**
  - Tech+Healthcare 8~14 종목은 유동성은 대체로 좋지만, **턴오버/리밸런스 빈도**가 높으면 “백테스트 알파”가 비용에 즉시 증발한다.
  - 현재 리밸런스 로그가 깨져 있어(1번), 비용이 실전에서 어떻게 누적되는지 추적도 어렵다.
- **위험/부작용**
  - 비용을 올리면 백테스트 성능이 급락할 수 있음(그러나 그게 현실).
  - 과도한 비용 보수화는 “거래를 안 하는 전략”으로 퇴행할 수 있음(이를 E2/E4로 방지).
- **연결 실험(2~3개)**: **E3, E1, (선택)E4**

---

### 4) (노출/운영 리스크) “현금화/과도 노출”을 동시에 막는 노출/포지션 규칙을 표준화하라 (8~14종목, Tech+HC 고정)
- **왜 필요한가**
  - `exposure_min/max: 0.0 / 0.8388`는 **때때로 완전 현금(0)** 으로 내려가는 동작이 있다는 뜻이다. 이건 레짐/신호 꺼짐일 수도 있지만, 종종 “적용 로직 오류/게이트 과도/스케일링 버그”로도 발생한다.
  - 동시에 max 0.84로 **상시 풀투자도 아니어서** 수익/리스크 추정이 불안정할 수 있음. (특히 폴드 degeneracy와 결합 시)
- **위험/부작용**
  - 최소 노출을 강제하면 손실 구간에서 MDD가 커질 수 있음 → 대신 변동성 타겟/리스크 컷을 같이 둬야 한다.
  - 종목 수(8~14) 고정은 분산 부족 가능 → 하지만 이번 규칙에서 이게 요구사항.
- **연결 실험(2~3개)**: **E4, E2, (선택)E3**

---

### 5) (성능 정체 해결) “No-Delta”를 자동으로 잡아내는 델타 리포트/감도 테스트 하네스를 먼저 붙여라
- **왜 필요한가**
  - 이미 “No-Delta Diagnoser”가 돌아갔고, 성능이 안 움직이는 국면이다. 이 때 1순위는 **전략 변경이 실제로 포지션/거래를 바꾸는지**를 기계적으로 증명하는 것이다.
  - 지금은 `rebalance` 로깅 실패도 겹쳐서, **실험이 적용되지 않았는데 성능이 같은 것인지** vs **적용됐는데도 알파가 없는 것인지** 구분이 안 된다.
- **위험/부작용**
  - 강제 델타 임계값을 두면 일부 “미세 개선” 실험이 걸러질 수 있음 → 하지만 48시간 루프에서는 오히려 효율이 올라간다.
- **연결 실험(2~3개)**: **E5, E1, (선택)E2**

---

# 48시간 자동 루프용 “실행 가능한 Patch/실험” 5개 (E1~E5)

아래 5개만 돌려라. 각 실험은 (1)정의 (2)게이트 (3)기대 관측치로 고정.

---

## E1) Rebalance 로깅/스키마 강제 + pinpoint 입력 포맷 통일 (운영/관측 복구)
1) **실험 정의**
   - 매 런마다 `rebalance.jsonl`(또는 csv 단일 포맷) **반드시 생성**.
   - 각 이벤트에 최소 필드 강제:
     - `timestamp, symbol, target_weight, current_weight, delta_weight, price, shares, notional, est_cost, reason(signal/risk/cash), run_hash, lane_hash`
   - `aub_rebalance_pinpoint.py`가 읽는 경로를 “옵션 문자열”이 아니라 **실제 파일 경로**로만 받도록 방어(존재/JSON 파싱 검사).
2) **게이트 (PASS 조건)**
   - `aub_rebalance_pinpoint`가 **base/cand 모두 로드 성공**하고,
   - 최근 1개 런에서 `rebalance` 이벤트가 **0건이 아니거나**, 0건이면 “왜 0인지(reason=NO_TRADE + 조건값)”가 남아야 함.
3) **기대 관측치**
   - 성능 변화와 무관하게, 다음이 즉시 가능:
     - “리밸런스 발생일/종목/비중 변화/비용”이 눈으로 검증됨
     - No-Delta의 1차 원인(적용 실패 vs 전략 무효) 분리 가능

---

## E2) Degenerate fold 방지 게이트 + Purge/Embargo로 누수 차단 (과최적화/누수 우선)
1) **실험 정의**
   - 폴드별 최소 조건을 코드로 강제:
     - `fold_trade_count >= N` (예: 10)
     - `fold_weight_std > eps` (항상 같은 포지션이면 탈락)
     - `fold_exposure_mean`이 0 근처이면 탈락(완전 캐시 전략 방지)
   - 시계열 split에 **purge(lookahead buffer)** + **embargo(리밸런스 영향 기간)** 적용(예: 5~20거래일 스윕은 금지, 이번 48h에는 1개 값만 고정)
2) **게이트 (PASS 조건)**
   - `degenerate_folds == []` (0개)
   - OOS 리포트에 폴드별 `trade_count/exposure/turnover`가 출력됨
3) **기대 관측치**
   - OOS mean이 떨어져도 정상(“허수” 제거)
   - 폴드별 분산이 “거래 없음” 때문에 생기던 왜곡이 사라짐

---

## E3) 비용/슬리피지/턴오버 게이트 도입 + 비용 민감도 1회 점검 (비용 미반영 우선)
1) **실험 정의**
   - 거래비용 모델 최소 구성:
     - 고정 수수료(0도 가능) + bid-ask(스프레드) + 슬리피지(체결가 불리) + (선택)시장충격(턴오버 비례)
   - 출력 지표 강제:
     - `gross_return`, `net_return`, `total_cost_bps`, `turnover`, `avg_holding_days`
2) **게이트 (PASS 조건)**
   - `net_oos_mean`이 `gross_oos_mean` 대비 합리적으로 감소(예: 비용 0이 아닌데 차이가 0이면 FAIL)
   - turnover 상한: `annualized_turnover <= T` (예: 600% 같은 상한을 임시로 설정)
3) **기대 관측치**
   - “수익이 비용에 얼마나 취약한지”가 즉시 드러남
   - 리밸런스 로그(E1)와 합쳐 “어느 날/어느 종목”이 비용을 태우는지 pinpoint 가능

---

## E4) 노출/포지션 규칙 표준화 (8~14 Tech+HC) + 현금화 방지/과노출 방지 동시 해결
1) **실험 정의**
   - 종목 수: 8~14 강제(요구사항)
   - 섹터: Tech+Healthcare만 허용(요구사항)
   - 노출 규칙:
     - `gross_exposure`를 목표 구간으로 강제(예: 0.6~0.95)
     - 단일 종목 최대 비중 제한(예: 15~20%)
     - (선택) 변동성 타겟팅(포트 변동성 목표) 또는 DD 기반 리스크 컷
2) **게이트 (PASS 조건)**
   - OOS에서 `gross_exposure`가 설정 구간 밖으로 나간 일수가 일정 비율 이하(예: 5% 미만)
   - 종목 수가 8~14를 항상 만족
3) **기대 관측치**
   - “가끔 0 노출” 같은 운영상 이상행동이 줄고,
   - 수익률 분포가 “거의 거래 안 함”에서 벗어나 정상화

---

## E5) No-Delta 차단: 실험 적용 델타(포지션/거래/노출) 리포트 + 감도 테스트(1회) 자동화
1) **실험 정의**
   - base vs cand에 대해 아래 델타를 자동 산출:
     - `weight_L1_distance`(일별 |w_c-w_b| 합), `trade_count_diff`, `turnover_diff`, `exposure_diff`
   - “감도 테스트” 1회만 추가:
     - 핵심 파라미터 1개를 의도적으로 큰 폭으로 바꿔(예: 스케일 0.5→1.5) **델타가 실제로 커지는지** 확인
2) **게이트 (PASS 조건)**
   - 후보 실험은 최소 델타 임계값 만족:
     - 예: `median_daily_weight_L1_distance >= 0.10` 또는 `turnover_diff >= X`
   - 임계값 미만이면 “전략 성능 비교” 자체를 스킵하고 FAIL 처리(시간 절약)
3) **기대 관측치**
   - “성능이 안 움직이는” 원인이
     - (A) 적용/파이프라인 문제(델타 0)
     - (B) 적용은 되나 알파 없음(델타>0인데 성능 동일/악화)
     로 즉시 분해됨

---

# 성능이 안 움직일 때: 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)

아래를 **위에서부터 순서대로** 체크하라(질문 금지, 체크리스트로 실행).

## A. Trigger(신호 생성) 레벨
- **신호가 시간에 따라 변하는지** 확인: `signal_std_by_symbol`, `signal_turnover`
- 신호가 특정 날짜 이후 0/상수로 붙으면:
  - 피처 결측/스케일링 버그/리밸런스 캘린더 mismatch 의심
- **데이터 누수 방지**: 라벨/미래 가격/리포트 날짜(Healthcare 이벤트) PIT(시점일치) 여부 검사

## B. Application(신호→포지션 변환) 레벨
- 신호가 변해도 포지션이 안 변하면:
  - 랭킹/최적화가 클리핑(상한/하한)으로 포화
  - 리스크 모델이 항상 동일 해(상관/공분산 상수)로 수렴
  - 거래 최소단위/수량 라운딩으로 0 체결
- **E5 델타 리포트**로 “신호는 변하는데 포지션이 고정”을 자동 검출하라

## C. Exposure(노출/제약) 레벨
- 성능이 둔하면 먼저 “노출이 너무 낮거나(현금)” “과도하게 한쪽 섹터/메가캡”인지 확인:
  - `gross/net exposure`, `top1/top3 weight`, `sector concentration`, `effective_n`(유효 종목 수)
- **E4**로 목표 노출 밴드를 강제해 “노출 흔들림”을 제거한 뒤 성능을 다시 보라

## D. Cost(비용) 레벨
- gross는 움직이는데 net이 안 움직이면 비용이 원인:
  - `cost_bps per rebalance day`, `turnover spikes`, `small trades frequency`
- **E3**로 비용 민감도(슬리피지/스프레드) 반영 후에도 알파가 남는지 확인하라

## E. Regime(시장/섹터 레짐) 레벨  *ETF는 관측지표로만 사용*
- 거래/성능이 특정 레짐에서만 살아나는지 체크:
  - 관측 지표(매매 금지): **XLK, XLV, QQQ, IHI** 등으로 레짐 태깅만 수행
  - `VIX`, 금리(2Y/10Y), breadth 같은 보조지표로 “리스크온/오프” 구간 태그
- 레짐별로 `hit-rate, avg_return, mdd`를 쪼개서 “전략이 죽는 환경”을 명시화하라

---

## 24~48시간 실행 순서(명령형)
1) **E1 먼저 적용**해서 rebalance/trace를 복구하라(지금은 관측 불능).
2) **E5를 바로 붙여** “No-Delta(적용 실패)”를 런타임에 걸러라(시간 절약).
3) **E2를 게이트로 승격**해 degenerate fold를 0으로 만들고(누수/과최적화 우선 제거),
4) 그 다음에만 **E3(비용)**, **E4(노출/포지션 표준화)**를 돌려 “실전성”을 확보하라.
5) 어떤 실험도 **델타(E5) 통과 못 하면 성능 비교하지 말고 즉시 실패 처리**하라.

이 5개만 제대로 돌아가면, 다음 48시간 루프에서는 “전략을 더 복잡하게” 하기 전에 **(1) 적용됨 (2) 누수 없음 (3) 비용 반영 (4) 노출 정상**이 보장돼서 성능 정체 원인을 빠르게 고립할 수 있다.
