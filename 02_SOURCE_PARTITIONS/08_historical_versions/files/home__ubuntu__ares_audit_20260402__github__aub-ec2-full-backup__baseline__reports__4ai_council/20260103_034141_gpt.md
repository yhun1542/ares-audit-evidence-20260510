아래는 **다음 24~48시간**에 바로 돌릴 수 있는 **우선순위 TOP5(코드/아키텍처/전략)** 패치 제안이다. 전부 **미국주식 only / Tech+Healthcare 중심 / 8~14종목 / ETF 매매 제외(관측지표만)**을 전제로 하고, **누수→과최적화→서바이버십→비용 미반영→운영 리스크** 순으로 먼저 건드린다.  
각 항목은 **48시간 자동 루프**에서 그대로 “실험 정의→게이트→기대 관측치”로 끝나게 구성했다.

## TOP1) 데이터 누수/타임라인 무결성 “강제 봉인” 패치
### (a) 왜 필요한지
- 현재 Champion이 lockbox가 매우 강한데(평균 4.01), 이런 형태는 **실거래 가능한 엣지**일 수도 있지만, 반대로 **as-of 시점 누수(리포트/재무/리밸런스 캘린더), 라벨 선행, corporate action 처리 타이밍**이 섞이면 lockbox에서 과도하게 좋아질 수 있다.
- 누수는 한 번 잡으면 성능이 내려가더라도 “진짜 성능”이 남아 이후 개선이 가능해진다.

### (b) 위험/부작용
- 단기적으로 성능 하락(특히 tuning_mean)이 발생할 수 있음.
- 과도한 embargo/purge는 샘플을 줄여 변동성을 키움.

### (c) 최소 실험(동일 패치 안에서 2~3개 체크를 함께 수행)
**Patch 1 = “as-of + purge/embargo + event-time 정렬” 한 번에 적용**
1) **As-of join 강제**: 모든 피처/펀더멘털/리포트 계열에 `available_at <= decision_time` 규칙 강제(없으면 해당 피처 drop 또는 lag 1).
2) **Purged K-fold + Embargo**: 폴드 경계에 최소 1~5거래일 embargo를 스윕(코드 상 config로).
3) **Corporate action 타이밍 고정**: split/dividend 반영 시점을 **거래일 마감 이후**로 고정(결정 시점에 미래 조정가가 섞이지 않게).

### (d) PASS 조건(게이트)
- **Leakage gate**: 누수 의심 피처/조인 0건(리포트에 “violation count=0”)
- **성능 gate(보수적)**:  
  - `worst_mdd >= -0.085` (Champion -0.081 대비 과도 악화 금지)  
  - `lockbox_mean >= 3.6` (누수 제거로 일부 하락 허용, 대신 현실성 확보)  
  - 폴드 간 성능 분산(표준편차) **감소 또는 동일**
- **운영 gate**: 재현성(동일 seed/동일 데이터 스냅샷에서 동일 결과) 100%

### 48시간 루프 형태
- **(1) 실험 정의**: “누수 봉인 패치 on” vs 기존 Champion 파이프라인
- **(2) 게이트**: violation=0, worst_mdd, lockbox_mean
- **(3) 기대 관측치**: tuning/lockbox 평균이 다소 낮아져도, 폴드 간 편차 감소 + MDD 안정화

## TOP2) 비용/슬리피지/체결 실패를 “전략 성능”에 실제로 반영하는 패치
### (a) 왜 필요한지
- Tech/Healthcare 8~14종목은 유동성은 대체로 좋지만, **리밸런스 빈도/회전율**이 높으면 비용이 성능을 잠식한다.
- 비용 미반영은 “실험 성능이 안 움직이는” 대표 원인이다(알파를 미세하게 개선해도 비용으로 상쇄).

### (b) 위험/부작용
- 비용을 넣으면 성능이 떨어져 “개선이 후퇴”처럼 보일 수 있음.
- 과도한 비용 추정은 전략을 불필요하게 보수화.

### (c) 최소 실험(동일 패치 안에서 2~3개 체크를 함께 수행)
**Patch 2 = “현실 비용모델 + 회전율 제한(soft)”**
1) **거래비용 모델 추가**:  
   - 고정 수수료(0도 가능) + bid-ask proxy(예: `k * ATR/Price`) + 슬리피지(체결가 불리)  
   - 최소한 “왕복 bps”를 보수적으로 가정해 백테스트 PnL에서 차감
2) **Turnover soft-cap 페널티**:  
   - 목적함수에 turnover 페널티(예: `score -= λ * turnover`) 또는 주문 크기 감쇠
3) **체결 실패/부분체결 모사(간단형)**:  
   - 갭이 큰 날/변동성 급증일에 주문량 일부만 체결 처리(단순 룰)

### (d) PASS 조건(게이트)
- **비용 반영 후에도**  
  - `lockbox_mean (net) >= 3.6`  
  - `worst_mdd (net) >= -0.085`
- **운영 가능성**: 일평균 turnover가 **상한(예: 30~60%/day)**을 초과하지 않도록(프로젝트 내부 기준치로 고정)
- **민감도**: 비용 bps를 +50% 올려도 순성과가 “즉시 붕괴”하지 않을 것(단조 감소는 정상)

### 48시간 루프 형태
- **(1) 실험 정의**: 비용모델 on + turnover 페널티 λ 스윕(작게 2~3점)
- **(2) 게이트**: net lockbox_mean, net worst_mdd, turnover
- **(3) 기대 관측치**: gross는 비슷해도 net에서 안정적인 후보만 남음(가짜 개선 제거)

## TOP3) “8~14개 / Tech+Healthcare” 유니버스 강제 + 노출(Exposure) 제약 패치
### (a) 왜 필요한지
- 유니버스/섹터 제한이 코드 레벨에서 느슨하면, 실험마다 종목 구성이 흔들려 **서바이버십/룩어헤드/구성 변화**가 섞인다.
- 또한 Tech/Healthcare 내에서도 **메가캡 쏠림**이 생기면 사실상 “단일 팩터/단일 종목” 베팅이 되어 MDD가 커진다.

### (b) 위험/부작용
- 제약이 강하면 수익률이 줄어들 수 있음.
- 과도한 동적 유니버스 교체는 오히려 매매를 증가시킴.

### (c) 최소 실험(동일 패치 안에서 2~3개 체크를 함께 수행)
**Patch 3 = “유니버스 스냅샷 + 섹터/종목 수 제약 + 집중도 제한”**
1) **유니버스 스냅샷팅**: 월 1회(또는 분기 1회) 유니버스를 스냅샷으로 고정(당월엔 변경 금지)  
2) **종목 수 하드 제약**: 항상 8~14개만 보유(부족하면 현금/대기)  
3) **집중도/상관 제약**:  
   - 단일 종목 비중 상한(예: 12~15%)  
   - 섹터(Tech/Healthcare) 내 하위군 쏠림 완화(간단히 상관/베타 높은 종목 동시 최대 N개)

### (d) PASS 조건(게이트)
- **제약 준수 100%**: 보유 종목 수, 섹터 규칙 위반 0
- **리스크 개선**:  
  - `worst_mdd` 개선 또는 동일(<= 절대값 감소)  
  - tail risk 지표(하위 5% 일수익 VaR proxy) 악화 금지
- **성능**: `lockbox_mean`이 5~10% 이내만 감소하면 “리스크 개선”을 우선 채택 가능

### 48시간 루프 형태
- **(1) 실험 정의**: 유니버스 스냅샷 on + 종목수/집중도 제약 on
- **(2) 게이트**: 제약 위반 0, worst_mdd, tail risk
- **(3) 기대 관측치**: 수익률이 약간 줄어도 MDD/꼬리위험이 내려가 “운영 가능한 챔피언”으로 수렴

## TOP4) 레짐(국면) 기반 리스크 스로틀: “ETF는 지표로만” 사용
### (a) 왜 필요한지
- Tech/Healthcare는 레짐(금리/변동성)에 민감해, 같은 알파라도 **변동성 급등/리스크오프**에서 급격히 깨진다.
- ETF는 매매하지 않더라도 **QQQ/XLV/IEF/VIX proxy** 같은 지표로 “포지션 크기 스로틀”을 걸면 MDD가 크게 줄 수 있다.

### (b) 위험/부작용
- 스로틀이 잦으면 수익 기회를 놓치고, 알파가 “항상 조금만” 먹는 형태가 될 수 있음.
- 레짐 신호가 느리면 전환 구간에서 손해.

### (c) 최소 실험(동일 패치 안에서 2~3개 체크를 함께 수행)
**Patch 4 = “레짐 신호 1개 + 사이징 룰 1개”로 단순화**
1) **리스크오프 신호(관측만)**:  
   - 예: QQQ 20일 모멘텀 < 0 또는 (QQQ/XLV) 추세 하락, 혹은 VIX proxy 급등(가능한 데이터로 대체)
2) **사이징 스로틀**:  
   - 신호가 risk-off면 총 노출 30~60%로 축소, 또는 신규 진입 금지 + 기존 감산
3) **신호 히스테리시스**:  
   - on/off를 하루 단위로 뒤집지 않게 2~3일 확인 규칙(운영 안정)

### (d) PASS 조건(게이트)
- **MDD gate 우선**: `worst_mdd >= -0.075`(챔피언보다 개선 목표) 또는 동일 성과에서 MDD 개선
- **성과 gate**: `lockbox_mean >= 3.8` 유지(방어만 하고 수익이 사라지지 않게)
- **거짓경보**: risk-off 상태 일수 비율이 과도(예: >50%)하면 FAIL(항상 브레이크 걸린 전략은 운영 비효율)

### 48시간 루프 형태
- **(1) 실험 정의**: 레짐 스로틀 on/off A/B
- **(2) 게이트**: worst_mdd, lockbox_mean, risk-off 비율
- **(3) 기대 관측치**: 수익률 소폭 감소 대신 tail/MDD가 구조적으로 깎임

## TOP5) 과최적화/서바이버십 방지용 “검증 체계 강화” 패치(후보가 안 나올 때 특히)
### (a) 왜 필요한지
- 현재 candidate가 tuning 대비 lockbox에서 힘을 못 쓰거나 MDD가 커지는 모습이 보인다(최근 PASS 후보 fold14_mdd -0.099, worst_mdd -0.112).  
  → 전형적으로 **튜닝 구간에서 맞춘 파라미터/특징이 레짐 이동에 취약**한 패턴.
- 검증이 흔들리면 실험을 아무리 돌려도 “성능이 안 움직임”으로 체감된다.

### (b) 위험/부작용
- 제약/검증이 빡세면 통과 후보가 줄어들어 탐색 속도가 느려짐.
- 너무 많은 메트릭을 게이트로 걸면 false negative 증가.

### (c) 최소 실험(동일 패치 안에서 2~3개 체크를 함께 수행)
**Patch 5 = “검증 강화(간단 3종)”**
1) **파라미터 안정성 체크**: 핵심 하이퍼파라미터 1~2개만 ±10~20% 흔들어도 lockbox 성능이 급락하지 않아야 통과  
2) **Feature ablation(상위 기여도 drop)**: 상위 1~3개 피처 제거 시 성능이 “완전 붕괴”하면 과의존으로 간주하고 FAIL  
3) **Walk-forward 리밸런스 캘린더 고정**: 폴드마다 재학습/리밸런스 빈도 동일(캘린더 누수 제거)

### (d) PASS 조건(게이트)
- **견고성 gate**:  
  - 파라미터 흔들림에서 `lockbox_mean` 감소폭이 -10% 이내  
  - 상위 피처 drop에도 `lockbox_mean`이 -15% 이내
- **리스크 gate**: `worst_mdd >= -0.085` 유지
- **선정 gate**: 위 견고성 조건 만족하는 후보만 `--select-best` 대상으로 올리기

### 48시간 루프 형태
- **(1) 실험 정의**: 동일 후보에 대해 “안정성/ablation/walk-forward” 자동 리포트 생성
- **(2) 게이트**: 민감도 감소폭, worst_mdd
- **(3) 기대 관측치**: 후보 수는 줄어도 “락박스에서 다시 깨지는” 낭비 실험 감소

# 24~48시간 실행 순서(명령형 체크리스트)
1) **TOP1(누수 봉인) 패치부터 적용하고 리포트 강제 생성**  
2) **TOP2(비용/슬리피지) 적용하여 net 성능을 기본 지표로 승격**  
3) **TOP3(유니버스/종목수/집중도)로 운영 제약을 코드 레벨에서 불변화**  
4) **TOP4(레짐 스로틀)로 MDD를 먼저 깎는 방어 레이어 추가**  
5) **TOP5(검증 강화)로 후보 선별을 “견고성 통과” 중심으로 전환**  

(기존 명령 3줄은 그대로 유지하되, 위 패치들이 config/모듈로 registry에 등록되어 자동 루프에서 선택되게 만드는 쪽이 운영상 안정적이다.)

# 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래는 **원인 분해용 관측 지표**를 강제로 뽑아 “어디가 막혔는지”를 바로 특정하기 위한 체크리스트다(질문 없이 실행 항목만).

## 1) Trigger(신호 생성) 문제
- **신호 발생 빈도**: 일/주 단위로 신호 0에 수렴하면 알파가 죽은 것  
- **신호 분포 붕괴**: 스코어 분산이 과거 대비 급감(모든 종목이 비슷한 점수)  
- **레이블 정렬**: 예측 horizon과 실제 수익 계산 window 불일치(신호는 5일을 보는데 라벨은 1일 등)

## 2) Apply(집행/리밸런스) 문제
- **리밸런스 캘린더 불일치**: 백테스트는 매일, 운영은 주간이면 성능 괴리  
- **포지션 업데이트 지연**: decision_time과 execution_time 차이로 실현 수익이 증발  
- **제약으로 인한 무효 주문**: 상한/하한/종목수 제약 때문에 신호가 포지션으로 반영되지 않음(“signal≠position”)

## 3) Exposure(노출) 문제
- **베타/섹터 노출 드리프트**: 의도는 Tech+Healthcare인데 실제로는 “QQQ 베타”만 커짐  
- **집중도 폭증**: 상위 2~3종목이 성과를 지배(서바이버십/특정 종목 의존)  
- **상관 구조 변화**: Tech+Healthcare 내부 상관이 레짐마다 달라 분산효과 상실

## 4) Cost(비용) 문제
- **Turnover가 알파를 상쇄**: gross는 좋은데 net이 0 근처면 비용/슬리피지가 원인  
- **갭/변동성 구간 손실**: 고변동 구간에 체결가 불리함이 누적  
- **부분체결/미체결**: 현실에서는 못 산/못 판 구간이 백테스트엔 반영되어 있음

## 5) Regime(국면) 문제
- **금리/변동성 레짐**에서 Tech/Healthcare 알파가 반대로 작동(리스크오프에서 깨짐)  
- **레짐 전환 구간**(추세↔역추세)에서 신호가 가장 취약  
- **관측 지표(ETF)는 매매하지 말고**, 사이징/진입 금지 같은 “브레이크”로만 사용해 MDD를 관리

## “정체”를 빠르게 끝내는 운영 원칙(명령형)
- **gross 성능 개선보다 net 성능 안정화부터** 우선하라.  
- **lockbox에서만** 의사결정하라(튜닝 개선은 참고만).  
- **패치당 변경점 1개 묶음(위 TOP1~TOP5 단위)**으로만 실험하라(동시 다발 변경 금지).  
- **누수/비용/제약 위반이 하나라도 있으면 성능 수치와 무관하게 FAIL** 처리하라.

원하면, 위 TOP1~TOP5가 각각 `module_registry.yaml`에 “토글 가능한 모듈”로 들어가도록 설계할 때의 **모듈 인터페이스(입력/출력/리포트 필드)**까지 바로 패치 형태로 정리해줄 수 있다.
