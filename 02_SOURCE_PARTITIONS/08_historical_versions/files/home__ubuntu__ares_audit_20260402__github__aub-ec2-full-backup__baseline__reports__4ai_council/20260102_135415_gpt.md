## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — **명령형 체크리스트**
우선순위는 **누수/과최적화/서바이버십/비용 미반영/운영 리스크**부터 잡는다. (현재 로그상 `worst_mdd: None`, rebalance pinpoint가 **입력 로그 부재/파싱 실패**로 멈춤 → “성능이 안 움직임” 이전에 **관측/계측이 깨진 상태** 가능성이 큼)

---

# 1) 운영 리스크: **Rebalance 로그/아티팩트 스키마 고정 + 리스크/비용 지표 자동 산출**
### (a) 왜 필요한지
- `aub_rebalance_pinpoint`가 **--base-log 파일 부재**, rebalance.csv/jsonl 파싱 실패 → **리밸런스/턴오버/비용/슬리피지 영향이 관측 불가**.
- `worst_mdd: None` → 리스크 산출 파이프라인이 비활성/누락일 가능성. “OOS Mean”만 보고 튜닝하면 **과최적화**로 간다.

### (b) 위험/부작용
- 로그/스키마 변경으로 과거 리포트와 호환 깨짐(단기 혼란).
- MDD/비용 반영 후 **성능 수치가 하락**(하지만 이게 정상적인 현실 반영).

### (c) 최소 실험(대기열 포함) — *48h 실행은 1개만*
**[실험 1-A | 48h 실행] “Rebalance JSONL + Metrics 스키마 강제”**
1) **실험 정의**
   - 모든 백테스트/워크포워드 실행에서 `rebalance.jsonl`(라인 단위 JSON) 강제 생성.
   - 필드 최소셋 고정: `ts, universe, target_w, fill_w, turnover, est_cost_bps, realized_slip_bps, exposure_gross/net, cash, n_names`.
   - run artifact에 `run_hash/lane_hash/data_hash/code_hash` 동봉.
2) **게이트**
   - (필수) `rebalance.jsonl` 0바이트 금지, 파싱 100% 성공.
   - (필수) `worst_mdd` 산출(숫자) + turnover, cost 지표 리포트에 표시.
3) **기대 관측치**
   - pinpoint 리포트가 “No rebalance data” 없이 생성.
   - 성능 변화가 없더라도 **원인 분해 가능한 축(턴오버/비용/노출)**이 생김.

**[대기열 1-B] “리스크 리포트 단위테스트”**
- 게이트: 최근 10회 run에서 `worst_mdd`/`turnover`/`est_cost_bps` 결측 0건.

**[대기열 1-C] “결측/NaN 방어(데이터-전략 경계)”**
- 게이트: 입력 피처 NaN 비율, forward-fill 발생 횟수, 미래값 참조 가능성(시간역전) 0으로 강제.

### (d) PASS 조건
- rebalance pinpoint 정상 생성 + `worst_mdd`가 None이 아니고 + 비용/턴오버가 리포트에 일관되게 찍힘(다음 실험들이 “유효한 관측”이 됨).

# 2) 비용 미반영: **슬리피지/수수료/임팩트 모델 도입(최소형)**
### (a) 왜 필요한지
- 현재 챔피언 노출이 0.47~0.84로 꽤 높음 → 리밸런스가 잦거나 편향이면 **비용이 알파를 먹는다**.
- “성능이 안 움직임”은 종종 **비용이 진짜 성능을 상쇄**하는 형태로 나타남.

### (b) 위험/부작용
- 단기적으로 OOS mean 하락 가능(현실 반영).
- 너무 보수적 비용이면 트레이딩 자체가 위축되어 기회 손실.

### (c) 최소 실험(대기열 포함) — *48h 실행은 1개만*
**[실험 2-A | 48h 실행] “2-항 비용모델(고정+임팩트) on/off A/B”**
1) **실험 정의**
   - 거래비용(bps) = `fixed_bps + k * (abs(dollar_traded)/ADV)^α`
   - 최소형 권장: `fixed_bps=1~3`, `k=10~30`, `α=0.5` (상수는 단순 시작값)
   - 백테스트에서 “비용 미반영” vs “비용 반영” 2개만 비교.
2) **게이트**
   - (필수) 비용 반영 후에도 월별/분기별 PnL이 전기간 음수로 붕괴하지 않을 것.
   - (필수) turnover 상위 10% 구간에서 비용이 상승하는 단조성(모델이 작동함).
3) **기대 관측치**
   - 성능이 유지되면 전략이 “구조적으로 비용 친화적”.
   - 성능이 크게 꺾이면 **리밸런스/신호 빈도/포지션 변경량**이 병목임이 확정.

**[대기열 2-B] “턴오버 페널티(목표가중치 스무딩) 실험”**
- 게이트: est_cost_bps 20~40% 감소 vs OOS mean 하락 폭 제한.

**[대기열 2-C] “최소 주문/리밸런스 임계치(Δw deadband)”**
- 게이트: 작은 변경 거래 제거로 turnover 감소 + 성능 유지.

### (d) PASS 조건
- 비용 반영 OOS가 “완전 붕괴”하지 않고, 비용/턴오버 변화가 원인분해 가능하게 드러남.

# 3) 누수(lookahead)/시점 정합: **피처/라벨/리밸런스 타이밍 1-bar 지연 검증**
### (a) 왜 필요한지
- “OOS mean이 안 움직임” 이전에, **미세한 누수**가 있으면 실험 간 차이가 희석되거나(모두 좋게 보임) 반대로 (차이가 모두 사라짐) 같은 현상이 난다.
- 특히 리밸런스가 close 기준인지 next open 기준인지 섞이면 성능이 불안정.

### (b) 위험/부작용
- 1-bar 지연을 걸면 성능이 하락할 수 있음(정상).
- 잘못된 지연 적용은 오히려 “진짜 실행가능”보다 더 보수적으로 만들 수 있음.

### (c) 최소 실험(대기열 포함) — *48h 실행은 1개만*
**[실험 3-A | 48h 실행] “전 피처/신호 1-bar 지연(강제) A/B”**
1) **실험 정의**
   - 주문/체결 기준을 명시적으로 고정(예: 신호는 t일 종가까지, 체결은 t+1일 시가).
   - 모든 피처를 `asof=t`로 고정하고, 포지션 적용은 `t+1`로 이동.
2) **게이트**
   - (필수) 지연 적용 버전에서 미래값 접근(인덱스 역전/merge_asof 잘못) 경고 0건.
   - (필수) OOS가 “완전 사망”이면 기존이 누수/타이밍 착시일 가능성으로 플래그.
3) **기대 관측치**
   - 성능이 비슷하면 누수 가능성 낮아짐(다음 최적화로 진행 가능).
   - 성능 급락이면 **타이밍 누수**가 1순위 원인.

**[대기열 3-B] “Purged/Embargo CV로 재검증”**
- 게이트: fold 경계에서 성능 튀는 현상 완화.

**[대기열 3-C] “피처별 time-travel 테스트(shift sensitivity)”**
- 게이트: shift(+1)에서만 비정상 급등하는 피처 제거.

### (d) PASS 조건
- 1-bar 지연 버전이 최소한 “실행가능 백테스트”로 정상 동작하고, 누수 여부에 대한 결론이 나옴(유지 vs 급락).

# 4) 과최적화/서바이버십: **유니버스 고정(8~14, Tech+Healthcare) + 가용성(당시 존재) 필터**
### (a) 왜 필요한지
- “현재 챔피언 성능이 안 움직임”은 실험들이 사실상 **같은 과최적화 영역**에서 돌고 있거나,
- 유니버스가 암묵적으로 “현재 살아남은 종목만” 포함하는 **서바이버십 편향**이 있으면 OOS가 왜곡된다.

### (b) 위험/부작용
- 가용성 필터 강화 시 표본이 줄어 성능 변동성 증가.
- 유니버스 고정으로 기회 제한(하지만 정책상 8~14 집중이 요구됨).

### (c) 최소 실험(대기열 포함) — *48h 실행은 1개만*
**[실험 4-A | 48h 실행] “Point-in-time 존재성 필터 + 유니버스 고정 리런”**
1) **실험 정의**
   - 유니버스: Tech+Healthcare에서 8~14개로 **명시 리스트**(예: mega-cap 위주) 고정.
   - 각 날짜 t에 대해, 가격/거래량/상장 상태 데이터가 **t 이전부터 존재**하는 종목만 tradable 처리(미래 존재로 편입 금지).
2) **게이트**
   - (필수) 특정 시점에 tradable 종목 수가 8 미만으로 붕괴하면 해당 날짜는 cash/대기 규칙 적용(강제).
   - (필수) 실험 간 유니버스 변동 로그 출력.
3) **기대 관측치**
   - 성능이 크게 변하면 과거에 **암묵적 survivorship** 또는 universe drift가 있던 것.
   - 성능이 안정적이면 다음 단계(레짐/비용 최적화)로.

**[대기열 4-B] “Leave-one-out(종목 1개씩 제외) 민감도”**
- 게이트: 단일 종목 제거 시 OOS mean 붕괴 방지(집중 리스크 탐지).

**[대기열 4-C] “기간별 OOS(rolling) 안정성 스코어”**
- 게이트: 특정 1개 구간만 과도하게 성능 기여 시 경고.

### (d) PASS 조건
- 유니버스/가용성 규칙이 완전히 명시되고, survivorship 의심 신호가 사라짐(또는 원인 확정).

# 5) 레짐/노출: **ETF는 “관측지표”로만 사용해 리스크 게이트(진입/노출 조절)**
*(ETF 매매 금지 준수: QQQ/XLV/SMH 등은 “시장 상태 관측”에만 사용)*

### (a) 왜 필요한지
- 현재 노출 범위가 0.47~0.84로 높고, `worst_mdd`도 미산출 상태였음 → 레짐 악화 시 방어장치 부재 가능.
- “성능이 안 움직임”은 레짐 혼합(상승장/하락장)에서 신호가 상쇄되는 전형적 패턴.

### (b) 위험/부작용
- 게이트가 과도하면 기회 손실로 평균 수익 하락.
- 레짐 지표가 불안정하면 잦은 on/off로 turnover 증가(→ 비용 악화).

### (c) 최소 실험(대기열 포함) — *48h 실행은 1개만*
**[실험 5-A | 48h 실행] “레짐 게이트 1개만: QQQ 추세 필터로 노출 스케일”**
1) **실험 정의**
   - 지표: QQQ의 50DMA vs 200DMA(또는 20/100)로 risk-on/off 판정(관측만).
   - risk-off면 목표 노출을 `exposure *= 0.5` 또는 `max_exposure=0.4`로 캡.
   - 종목은 Tech+Healthcare 8~14 내에서만 그대로 운용.
2) **게이트**
   - (필수) risk-off 구간에서 MDD가 감소(최소한 tail 악화 방지).
   - (필수) turnover 증가가 비용 모델(2번)에서 감당 가능한 수준인지 확인.
3) **기대 관측치**
   - 하락장/변동성 확대 구간에서 손실 폭이 줄고, 전체 OOS가 안정화(평균은 비슷해도 분산/꼬리 개선).

**[대기열 5-B] “XLV 상대강도(Tech vs Health)로 내부 회전 힌트만 제공”**
- 게이트: 포지션 회전이 비용 대비 유의미한 성능 개선.

**[대기열 5-C] “변동성(예: VIX proxy) 기반 position sizing”**
- 게이트: 고변동 구간에서 노출 자동 감소가 MDD를 유의미하게 낮춤.

### (d) PASS 조건
- 레짐 게이트가 **MDD/꼬리위험을 개선**하거나, 최소한 원인(레짐 상쇄)을 명확히 보여줌.

## 48시간 자동 루프 형태(고정 템플릿) — 실행 순서
아래 5개만 “실행”으로 고정(나머지는 대기열):
1. **1-A(로그/지표 스키마 고정)** → 관측 가능 상태 만들기
2. **2-A(비용모델 A/B)** → 비용 병목 확정/배제
3. **3-A(1-bar 지연 A/B)** → 누수/타이밍 착시 확정/배제
4. **4-A(존재성 필터+유니버스 고정)** → survivorship/universe drift 확정/배제
5. **5-A(QQQ 레짐 게이트로 노출 스케일)** → 레짐 상쇄/리스크 병목 확인

각 실험 공통 게이트(필수):
- 리포트에 `oos_mean, worst_mdd, turnover, est_cost_bps, exposure_stats( min/mean/max ), n_names` 반드시 포함
- rebalance.jsonl 파싱 성공률 100%

# 성능이 안 움직일 때 “원인 분해” 아이디어(트리거/적용/노출/비용/레짐)
아래 트리를 **로그로 숫자화**해서, “어디서 신호가 죽는지”를 하루 안에 특정한다.

## A. Trigger(신호 발생) 단계
- **신호 발생 빈도**: 일/주당 신규 진입·청산 이벤트 수
- **신호 강도 분포**: 상위/하위 분위 신호의 평균 수익(정보계수/랭크IC)
- 트리거 고장 징후:
  - 신호가 너무 드물거나(거의 0) 너무 상시(항상 1) → 과도한 필터/버그

## B. Application(집행/리밸런스) 단계
- **목표가중치 vs 체결가중치 괴리**: `|target_w - fill_w|`
- **deadband 적용 전후 turnover**
- 고장 징후:
  - 신호는 좋은데 PnL이 안 움직이면 “집행이 신호를 훼손(리밸런스/제약/타이밍)”

## C. Exposure(노출/제약) 단계
- `exposure_min/max`가 현재 0.47~0.84 → 실제로는 **거의 상시 베타**일 가능성
- **gross/net exposure, cash 비중, 단일종목 최대비중**
- 고장 징후:
  - 노출이 항상 비슷하면 실험이 바뀌어도 결과가 비슷해짐(“베타만 먹는 전략”)

## D. Cost(비용) 단계
- **turnover → est_cost_bps → net PnL 차감**의 단조 관계 확인
- 고장 징후:
  - gross는 개선되는데 net이 정체면 비용이 상쇄(2-A로 확정)

## E. Regime(레짐) 단계
- 기간을 3~4개로 쪼개서(예: 상승/하락/횡보/고변동) **구간별 성능 테이블** 생성
- 지표(관측): QQQ 추세, XLV 상대강도, (가능하면) 변동성 프록시
- 고장 징후:
  - 구간별로 +/−가 상쇄되어 전체 평균이 “안 움직임”
  - 해결: 5-A 같은 노출 스케일/게이트

## 즉시 적용할 “실패 시 해석 규칙”(결론 강제)
- **3-A(1-bar 지연)에서 급락** → 타이밍 누수/체결 기준 오류를 최우선 버그로 처리(전략 튜닝 중단).
- **2-A(비용 반영)에서 급락** → 리밸런스/턴오버 억제 패치로만 진행(신호 개선보다 먼저).
- **4-A(존재성/유니버스 고정)에서 성능 변화 큼** → survivorship/universe drift 문제 확정, 데이터/유니버스 규칙 고정 전까지 성능 비교 금지.
- **5-A에서 MDD 개선** → “평균 수익”보다 “꼬리/레짐”이 병목이었음. 이후는 게이트 파라미터를 소수 실험으로만 미세조정.

위 5개를 돌리면, 48시간 내에 “성능이 안 움직이는 이유”가 **(1) 관측불가(로그) (2) 비용 (3) 누수/타이밍 (4) survivorship/universe (5) 레짐/노출** 중 어디인지 하나로 수렴한다.
