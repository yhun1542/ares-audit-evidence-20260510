## 24~48시간 TOP5 우선순위(명령형 체크리스트)

1) **(CODE/ARCH) 리밸런스/아티팩트 로깅을 “핀포인트 도구가 읽을 수 있게” 즉시 복구하라**  
2) **(LEAK/OVEROPT) degenerate fold(현재 [1,2,3,8])를 0으로 만들고, walk-forward + purge/embargo로 검증계를 고정하라**  
3) **(COST) 거래비용/슬리피지/스프레드/체결지연을 net 성과에 강제 반영하라(“gross 성과” 보고 중단)**  
4) **(OPS/RISK) 노출(현재 max 0.84)·턴오버·보유기간·주문 실패를 게이트로 묶고, 운용 가능성부터 확보하라**  
5) **(STRAT/REGIME) Tech/Healthcare 내 8~14종목 고정 유니버스에서 레짐(리스크온/오프) 게이트로 현금비중을 자동 조절하라(ETF는 관측만)**

# 1) 리밸런스/아티팩트 로깅 복구 (CODE/ARCH)
### (a) 왜 필요한지
- 현재 로그에서 **rebalance pinpoint가 입력을 못 읽음**:  
  `--base-log`가 실제 파일이 아니고, cand 파일은 JSON 파싱 실패.  
- champion에 **lane_hash/run_hash가 None** → 실험 추적/재현/회귀검증 불가.  
- “성능이 안 움직임”의 1순위 원인은 종종 **비교/측정 자체가 깨진 것**이다.

### (b) 위험/부작용
- 로깅 포맷 변경 시 기존 리포트/도구 호환성 깨짐
- 디스크/IO 증가, 런타임 증가(경미)

### (c) 최소 실험 2~3개 *(아래 5개 실험 풀 중에서만 사용; 총 5개로 제한)*
- **[E1] 로그 스키마 고정 + 핀포인트 도구 입력 보장**
  - (1) experiment runner가 항상 `rebalance.jsonl`(JSONL)과 `rebalance.csv`(CSV) 동시 저장
  - (2) `baseline-log` 인자를 실제 경로로 강제(placeholder 금지), 없으면 즉시 FAIL
  - (3) `run_hash/lane_hash`를 config+git SHA+universe hash로 생성해 메타에 저장
- **[E3] 비용 로그 포함(슬리피지/수수료/스프레드 항목을 rebalance row에 기록)**  
- **[E4] 운영 게이트 결과(주문 수, 실패 수, turnover, gross/net gap)를 리밸런스 로그에 함께 기록**

### (d) PASS 조건(게이트)
- `aub_rebalance_pinpoint.py`가 **base/cand 모두에서** 리밸런스 이벤트를 로드하고 리포트를 생성할 것
- 모든 run artifact에 `run_hash/lane_hash`가 **None이 아니어야 함**
- 리밸런스 로그에 최소 컬럼/필드 존재: `{ts, symbol, target_w, fill_px, mid_px, cost, slippage, reason}`

# 2) degenerate fold 제거 + 누수/과최적화 방지 검증 고정 (LEAK/OVEROPT)
### (a) 왜 필요한지
- 현재 champion에 **degenerate_folds [1,2,3,8]** → 일부 구간에서 학습/평가가 깨졌거나 샘플이 부족/비정상.  
- 이런 상태에서 OOS mean이 좋아도 **통계적으로 무의미**하거나 재현 실패 확률이 큼(서바이버십/누수/분할오류 가능).

### (b) 위험/부작용
- 올바른 분할로 바꾸면 성과가 “즉시 하락”할 수 있음(하지만 그게 정상)
- 학습 데이터 감소로 분산 증가 가능

### (c) 최소 실험 2~3개
- **[E2] Walk-forward splitter 하드닝 + purge/embargo**
  - fold당 최소 거래일/이벤트 수 미달이면 fold 생성 자체를 금지(=degenerate 0 강제)
  - feature lookback 기반으로 purge window 적용, embargo 적용(미래정보 누수 차단)
- **[E2-variant] 유니버스 고정(12종) + delisted/merge 처리 규칙 명시**
  - 백테스트 시점별 “그때 존재했던 종목”만 쓰는 옵션이 있더라도, 이번 48시간 루프에서는 **고정 유니버스**로 누수/서바이버십 논쟁을 일단 차단
- **[E1] split/feature metadata를 run artifact에 저장(재현성)**

### (d) PASS 조건(게이트)
- `degenerate_folds == []` (0개)
- 각 fold에서 **거래 횟수/리밸런스 횟수**가 최소 기준 이상(예: fold당 리밸런스 ≥ 20)
- OOS 리포트에 “purge/embargo 설정”이 명시되고 재현 가능

# 3) 비용(수수료/슬리피지/스프레드/체결지연) net 반영 강제 (COST)
### (a) 왜 필요한지
- “성능이 안 움직임”이 아니라 **net에서 이미 죽고 있는데 gross만 보고 있는 상태**일 수 있음.  
- 특히 Tech/Healthcare 대형주는 스프레드가 작아도 **턴오버가 높으면 비용이 누적**된다.

### (b) 위험/부작용
- 성과 하락(정상), 전략이 과거 대비 “작동 안 함”처럼 보일 수 있음
- 비용 파라미터 과대 설정 시 과도한 보수화

### (c) 최소 실험 2~3개
- **[E3] 비용 모델 ON (net only champion 선정)**
  - per-trade fixed + bps(예: 1~3bps) + half-spread + 슬리피지(거래대금/ADV 기반)  
  - 체결지연(예: 신호일 close → 다음날 open 체결)을 옵션으로 켬
- **[E4] turnover penalty / 최소 보유기간 게이트 추가**
  - 과도한 리밸런스(일별 뒤집기) 억제
- **[E1] 비용 구성요소를 리밸런스 로그에 기록해 원인추적 가능하게**

### (d) PASS 조건(게이트)
- `net_oos_mean` 기준으로 champion 갱신(=gross 기준 랭킹 금지)
- `gross - net` 차이가 과도하면(예: 연환산 8%p 이상) **턴오버가 원인인지 로그로 분해 가능**해야 함
- 동일 설정에서 2회 재실행 시 net 지표가 허용오차 내 재현(데이터/랜덤 고정)

# 4) 운영 리스크/노출/턴오버 게이트로 “돌아가는 시스템” 만들기 (OPS/RISK)
### (a) 왜 필요한지
- 현재 노출 max가 **0.84**로 찍힘 → 의도치 않게 위험자산 비중이 높아질 수 있음.  
- worst_mdd가 None인 것도 **리스크 측정 파이프라인 결손** 가능성.  
- 48시간 자동 루프에서는 “돈 벌기”보다 먼저 **깨지지 않는 운용 제약**이 필요.

### (b) 위험/부작용
- 수익 기회 일부 제한
- 게이트가 과도하면 신호가 “거의 미적용”되어 성능 정체로 보일 수 있음(그래서 적용률을 함께 기록해야 함)

### (c) 최소 실험 2~3개
- **[E4] 하드 리스크 게이트**
  - gross exposure cap(예: 0.65), per-name cap(예: 0.12), 섹터(Tech/HC) 내 집중 상한
  - 최소 보유기간(예: 2~3일) + 일간 turnover cap(예: 25~35%)
  - 주문 실패/가격결측 발생 시 해당 심볼 weight=0으로 강등 + 이벤트 로깅
- **[E1] MDD/VAR/노출 타임시리즈를 표준 리포트에 강제 저장**
- **[E3] 비용 포함 net에서만 게이트 평가(운영 제약은 비용과 결합)**

### (d) PASS 조건(게이트)
- `exposure_max <= 0.65`(설정값) 준수 + 위반 0회
- turnover가 캡 이내이며, **신호 적용률(=게이트 통과 비율)**이 리포트에 표시됨
- MDD가 None이 아니고, 기간별 리스크 지표가 산출됨

# 5) 레짐(리스크온/오프) 게이트로 Tech/Healthcare 현금비중 자동 조절 (STRAT/REGIME)
### (a) 왜 필요한지
- Tech는 레짐 민감도가 높고, Healthcare는 상대적으로 방어적.  
- “성능이 안 움직임”은 레짐이 바뀌어 **신호의 기대값이 0 근처**가 된 상태일 수 있음.  
- ETF는 매매하지 않더라도(QQQ/XLV/VIX) **레짐 관측**에는 매우 유용.

### (b) 위험/부작용
- 레짐 판단이 틀리면 성과 악화(whipsaw)
- 게이트가 자주 바뀌면 오히려 비용 증가 → [E4]/[E3]와 함께 봐야 함

### (c) 최소 실험 2~3개
- **[E5] 레짐 게이트(관측: QQQ/XLV/VIX)**
  - 예: VIX 상승+QQQ 모멘텀 약화 시 Tech 비중 상한을 낮추고 현금 비중 확대
  - Healthcare는 완전 고정이 아니라 “축소 덜” 하는 방식으로 완만하게
- **[E4] 레짐 전환 시 리밸런스 빈도 상한(급격한 회전 방지)**
- **[E1] 레짐 상태/전환 시점을 로그로 남겨 원인 추적 가능하게**

### (d) PASS 조건(게이트)
- 레짐별(ON/OFF)로 **성과/노출/턴오버/비용**이 분해되어 보고됨
- 리스크오프 구간에서 MDD 또는 tail loss가 감소(예: 하위 5% 일수익률 개선)
- 레짐 게이트가 성과를 못 올려도 “적용률/전환 횟수/비용 변화”가 관측 가능해야 함

## 48시간 자동 루프 형태(실험 5개만 운용)
아래를 그대로 “반복 실행 가능한” 형태로 고정하라.

### 실험 정의(5개)
- **E1 (Observability Patch)**: run_hash/lane_hash 생성, rebalance.jsonl+csv 강제, 핀포인트 입력 검증, 비용/게이트/레짐 필드 스키마 고정  
- **E2 (Validation Patch)**: walk-forward splitter 최소샘플 보장, purge/embargo, degenerate fold=0 강제  
- **E3 (Cost Patch)**: net 비용모델(스프레드/슬리피지/수수료/지연) ON, gross는 참고만  
- **E4 (Ops/Risk Patch)**: exposure/turnover/min-hold/order-fail 게이트 + 로그화  
- **E5 (Regime Patch)**: QQQ/XLV/VIX로 레짐 관측 → Tech/HC/현금 비중 상한을 동적으로 변경(매매는 주식만)

### 게이트(공통 PASS/FAIL)
- (측정) rebalance pinpoint 리포트 생성 가능(E1)  
- (검증) degenerate folds=0(E2)  
- (현실성) net 기준 성과만 평가(E3)  
- (운영) 노출/턴오버/주문실패 위반=0(E4)  
- (해석성) 레짐별 분해 리포트 존재(E5)

### 기대 관측치(“성능”이 아니라 “원인”을 먼저 움직여라)
- E1: 비교 불능 상태 해소(핀포인트/리밸런스 원인 추적 가능)  
- E2: OOS 분산이 줄거나, 기존 성과가 허상이라면 합리적으로 하락(정상)  
- E3+E4: gross는 비슷해도 net이 안정화(턴오버/비용이 설명변수로 잡힘)  
- E5: 레짐별 tail 손실 감소(수익이 아니라 손실 구조가 먼저 변해야 함)

# 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
질문 없이 바로 적용 가능한 분해 순서만 제시한다.

## A) 트리거(신호 발생) 문제
- **신호 발생률(일/주 단위)**을 로그로 남겨라: “0에 수렴”이면 모델이 아무 것도 안 하고 있는 것  
- feature 분포 드리프트(최근 구간에서 z-score 포화/클리핑 연속 발생) 체크하라

## B) 적용(게이트/제약) 문제
- “신호는 있는데 주문이 막힘”을 분해하라:  
  - 게이트별 차단 횟수(노출캡/턴오버캡/min-hold/데이터 결측/가격 이상치)를 카운트로 저장하라  
- 적용률이 낮으면 성능은 정체가 정상 → 성능 개선 전에 **게이트 설계**부터 조정 대상

## C) 노출(포지션 사이징) 문제
- 포지션이 너무 작거나(현금 과다) 너무 커서(0.84 같은 과노출) 성과가 “우연”이 된다  
- 심볼별 평균 weight/활성일수, 섹터별 비중(Tech vs HC) 타임시리즈를 고정 리포트로 만들어라

## D) 비용(슬리피지/스프레드/턴오버) 문제
- `gross_pnl`, `cost`, `net_pnl`을 같은 축으로 그리고  
- 비용을 **원인별로 분해**하라: spread vs impact vs fee vs delay  
- “net이 안 움직임”은 대부분 turnover 구조/체결 가정이 원인이다

## E) 레짐(시장 상태) 문제
- 레짐 태그(예: VIX high/low, QQQ trend up/down, XLV 상대강도)를 붙여  
  - 각 레짐에서의 기대수익/분산/MDD/턴오버를 테이블로 고정 출력하라  
- 레짐별 기대값이 모두 0이면 “전략 자체가 정보가 없음”이므로 다음 단계는 신호 재설계(하지만 이번 48시간 범위 밖)

## 실행 우선순위(48시간 내)
1) **E1 먼저**: 지금은 “측정 불능” 징후가 있으니 관측/로그 복구가 0순위  
2) 다음 **E2**: degenerate fold 제거 없이는 어떤 개선도 신뢰 불가  
3) 그 다음 **E3+E4 동시**: net+운영제약을 기준으로 챔피언 정의를 바꿔야 함  
4) 마지막 **E5**: 레짐 게이트는 “원인 분해가 가능한 상태(E1~E4)”가 된 뒤에 의미가 생김
