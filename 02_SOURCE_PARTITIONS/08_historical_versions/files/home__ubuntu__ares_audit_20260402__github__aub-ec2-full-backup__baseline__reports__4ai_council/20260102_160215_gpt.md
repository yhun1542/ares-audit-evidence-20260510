## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — 명령형 체크리스트

### 1) **리밸런스/메트릭 로깅 복구 + 결정론 고정(재현성)**
**(a) 왜 필요한지**
- 현재 `aub_rebalance_pinpoint`가 **로그 입력을 못 읽음**:  
  `--base-log`가 실제 파일 경로가 아니고, `rebalance.csv`는 JSON 파싱 에러 → **운영 관측 불능(원인 추적 불가)**.
- `worst_mdd: None` → **리스크 핵심 지표 누락**(운영 리스크).
- Champion OOS가 1.88 vs Diagnoser 2.63 **불일치** → 메트릭 버전/구간/데이터 스냅샷 불일치 가능(누수/과최적화 탐지 불가).

**(b) 위험/부작용**
- 로깅/메트릭 정의 변경으로 과거 결과와 비교가 흔들릴 수 있음(단, “정확한 비교 불가 상태”를 해소하는 게 우선).
- 결정론 고정 시(시드/정렬/병렬) 일부 과거 성능이 재현되지 않는 이슈가 드러날 수 있음(오히려 건강한 신호).

**(c) 최소 실험(아래 공통 실험 세트에서 2~3개만 실행)**
- **[E1] 리밸런스/체결/비용/노출 JSONL 로깅 + MDD 계산 패치**
- **[E2] 입력 시프트(1D) 누수 스모크 테스트 + 메트릭 정합성 체크**

**(d) PASS 조건**
- `rebalance_pinpoint`가 **Base/Cand 모두**에서 리밸런스 이벤트를 로드하고, 날짜별 포지션/턴오버/비용이 출력됨.
- `worst_mdd`가 **항상 실수 값**으로 채워짐(Null 금지).
- “동일 base 파일”로 계산한 OOS가 툴 간 **±1~2% 이내**로 수렴(정의/구간이 같아졌다는 의미).

---

### 2) **누수/과최적화/서바이버십 우선 점검(데이터 무결성)**
**(a) 왜 필요한지**
- 성능이 “안 움직이거나”, 갑자기 좋아지는 경우의 최상위 원인은 대체로  
  **(1) lookahead 누수 (2) survivorship (3) corporate action 처리 (4) split/dividend 조정**입니다.
- Tech+Healthcare(8~14) 소수 종목 구성은 **서바이버십/데이터 구멍의 영향이 더 큼**.

**(b) 위험/부작용**
- 포인트-인-타임/상장폐지 반영 시 성능이 하락할 수 있음(하지만 이게 “진짜 성능”).
- 누수 차단 후 신호가 약해져 노출이 줄 수 있음.

**(c) 최소 실험**
- **[E2] 입력 시프트(1D) 누수 스모크 테스트**(가장 싸고 빠름)
- **[E5] 유니버스 포인트-인-타임 + delist return/거래정지 처리 패치**

**(d) PASS 조건**
- 입력 시프트(+1D)에서 성능이 **급락(예: OOS mean -30% 이상)**하면 → 기존 파이프라인에 누수 가능성 “높음”으로 판정하고 차단 조치 완료.
- delist/거래정지 이벤트가 리밸런스 로그에 **명시적으로 기록**되고, 해당 구간의 수익률 계산이 NaN 없이 종결됨.

### 3) **비용/턴오버를 Net 기준으로 내재화(과대평가 제거)**
**(a) 왜 필요한지**
- 현재 상태 출력에 **비용/슬리피지/스프레드/임팩트/차입비용**이 보이지 않음 → 백테스트가 “Gross”일 가능성이 높음.
- 노출 0.47~0.84 구간이면 리밸런스 빈도에 따라 비용 민감도가 큼(운영 리스크).

**(b) 위험/부작용**
- 비용을 넣으면 성능이 내려갈 수 있음(하지만 실거래 근접).
- 턴오버 페널티가 과하면 신호 반응이 둔해져 레짐 전환에서 손해 가능.

**(c) 최소 실험**
- **[E3] 거래비용(commission+spread+impact) 3레벨 스트레스 + 턴오버 페널티**
- **[E1] 비용/턴오버 로깅 추가**(E3의 관측을 가능하게 함)

**(d) PASS 조건**
- 비용 3레벨(낮음/중간/높음)에서 OOS mean이 **단조 감소**하며(상식적),  
  중간 비용에서 성능이 **여전히 양(+)**이고, 높은 비용에서도 “폭망”이 아니면(예: OOS mean의 50% 이상 유지) 실전 내구성 통과.
- 턴오버가 챔피언 대비 **의미 있게 감소**(예: -15% 이상)하면서 OOS가 **동급 이상 또는 -5% 이내**면 채택.

### 4) **레짐/리스크 게이트(ETF는 ‘관측/게이트’만)로 드로우다운 방어**
**(a) 왜 필요한지**
- `worst_mdd`가 비어 있고, 노출이 0.84까지 올라감 → 레짐 악화 시 급락 방어 체계가 없을 수 있음.
- 규칙상 ETF 매매는 금지지만, **ETF는 관측지표/게이트로 사용 가능**.

**(b) 위험/부작용**
- 게이트가 잦으면 수익 기회 상실(특히 Tech 랠리 구간).
- 과도한 게이트는 “항상 덜 위험하지만 항상 덜 버는” 체계로 굳을 수 있음.

**(c) 최소 실험**
- **[E4] ETF 관측지표 기반 노출 게이트(예: QQQ 모멘텀/XLV 상대강도/VIX)**
- **[E3] 비용 내재화 상태에서 게이트 효과 재측정**(게이트가 turnover를 줄이는지 확인)

**(d) PASS 조건**
- OOS에서 worst MDD가 **의미 있게 개선**(예: -15% 이상 완화)되면서, OOS mean 저하가 **-5% 이내**면 채택.
- 게이트 발동 비율이 극단적이지 않을 것(예: 전체 리밸런스의 5~40% 범위 안).

### 5) **유니버스(미국 Tech+Healthcare 8~14) 운영 안정화 + 편입/제외 규칙 고정**
**(a) 왜 필요한지**
- 8~14 종목의 소수 포트폴리오는 “한 종목의 데이터/상폐/거래정지/급락”이 시스템 전체를 흔듦.
- 유니버스 룰이 흔들리면 서바이버십/과최적화가 쉽게 발생.

**(b) 위험/부작용**
- 유니버스 고정으로 단기 성능이 낮아질 수 있음(하지만 운영 일관성이 우선).
- 유동성 필터 강화 시 후보가 줄어 분산도가 하락할 수 있음(8~14 유지 룰과 충돌 가능).

**(c) 최소 실험**
- **[E5] 포인트-인-타임 유니버스 + 유동성/가격/거래정지 하드 필터**
- **[E1] “편입/제외 사유” 로깅(왜 빠졌는지 운영 추적 가능)**

**(d) PASS 조건**
- 모든 거래일에 보유 종목 수가 **항상 8~14 범위**(결측 시 fallback 룰로 채움)로 유지.
- 종목 편입/제외가 리밸런스 로그에 “사유 코드”로 남고, 재현 실행에서 동일 결과가 나옴(결정론).

## 공통 “실행 가능한 patch/실험” 5개 (48시간 자동 루프 형태)

아래 5개만 돌려도 TOP5 우선순위를 모두 커버합니다(케이스 폭발 방지).

### [E1] Rebalance/Trade/Cost/Exposure JSONL 로깅 + MDD 산출 패치
1) **실험 정의**
- 엔진이 매 리밸런스마다 아래를 `rebalance.jsonl`로 append:
  - timestamp, universe(티커 리스트), target_weights, filled_weights
  - turnover(절대가중치 변화 합), trades(수량/가격 가정), cost_breakdown
  - gross_return, net_return, exposure, cash, borrow(해당 시)
- 성과 리포트에 `worst_mdd`를 반드시 계산/저장(Null 금지).
2) **게이트**
- 로그 파일이 비어있거나 파싱 실패 시 즉시 FAIL.
- `worst_mdd is None` 또는 NaN이면 FAIL.
3) **기대 관측치**
- pinpoint 도구가 base/cand 모두에서 “리밸런스 구간” 비교 리포트를 생성.
- 성능 정체 시 “거래가 없어서 정체”인지 “비용으로 깎여서 정체”인지 즉시 분해 가능.

---

### [E2] 누수 스모크 테스트(입력 +1D 시프트) + 메트릭 정합성 체크
1) **실험 정의**
- 피처/신호/라벨 중 “모델 입력”을 일괄 +1 trading day lag(미래값 사용 차단).
- 동일 구간/동일 metric 함수로 Champion/Diagnoser OOS를 재계산해 불일치 제거.
2) **게이트**
- 시프트 후에도 성능이 거의 유지되면(예: OOS mean -10% 이내) → 누수 의심 HIGH로 FAIL 처리(원인 찾기 전까지 배포 금지).
- 툴 간 OOS 불일치가 지속되면 FAIL(정의/구간/스냅샷 통일 전까지 다음 단계 금지).
3) **기대 관측치**
- 정상이라면 시프트 후 성능이 **유의미하게 하락**(신호가 미래 의존이 아니라면 어느 정도 감소는 자연스러움).
- 불일치 원인이 “데이터 스냅샷”인지 “metric 구현”인지 드러남.

---

### [E3] 비용/슬리피지 내재화 + 턴오버 페널티(넷 성능 최적화)
1) **실험 정의**
- Net return = gross - (commission + spread + impact + borrow).
- 비용 3레벨 스트레스(예: 낮음/중간/높음)로 동일 전략을 재평가.
- 목적함수에 `lambda * turnover` 페널티(예: λ 0 / mid / high) 추가.
2) **게이트**
- 비용을 올렸는데 성능이 역으로 좋아지면(비상식) → 계산/로깅 오류로 FAIL.
- Turnover가 줄지 않으면(λ 증가에도) → 구현 오류로 FAIL.
3) **기대 관측치**
- 중간 비용에서 OOS가 유지되면 실전 가능성 상승.
- 정체 원인이 “신호 약함”이 아니라 “비용 누수”인지 확인 가능.

---

### [E4] ETF 관측지표 기반 노출 게이트(매매 금지, 게이트만)
1) **실험 정의**
- ETF는 매매하지 않고 다음과 같은 “노출 스케일”만 산출:
  - 예: (QQQ 20D 모멘텀 < 0) 또는 (VIX 급등) 시 exposure_scale = 0.5
  - XLV/QQQ 상대강도로 Tech vs Healthcare risk-on/off 스케일(포트 내 비중 이동은 **개별주 내부에서만**)
2) **게이트**
- 게이트가 상시 발동(예: 60%+) 또는 거의 미발동(예: <2%)이면 FAIL(무의미).
- 게이트 적용 후 worst MDD가 개선되지 않으면 FAIL.
3) **기대 관측치**
- 급락 레짐에서 노출이 낮아지고, 드로우다운이 완화.
- 비용/턴오버도 동반 감소할 가능성(관측).

---

### [E5] 포인트-인-타임 유니버스 + 상폐/거래정지/코퍼레이트액션 처리
1) **실험 정의**
- 매일 “그날 기준 존재했던” 미국 Tech+Healthcare 종목에서만 선택(서바이버십 차단).
- delist return(가능하면), 거래정지/상폐 시 강제 청산/현금화 룰을 명시.
- 8~14 유지 규칙: 결측 발생 시 유동성 상위 대체 후보로 즉시 채움(룰 고정).
2) **게이트**
- 유니버스가 사후 정보로 구성되면 FAIL(포인트-인-타임 증거 로그 필요).
- 8~14 범위를 벗어나는 날이 발생하면 FAIL.
3) **기대 관측치**
- 성능이 하락해도 정상(과대평가 제거). 대신 운영 안정성과 재현성이 상승.
- 특정 종목 이벤트가 결과를 왜곡하는지 명확히 드러남.

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)

아래 순서대로 “관측 가능한 지표”로 쪼개서, 48시간 루프에서 자동 진단되게 만드십시오.

### A. 트리거(신호가 발생하는가?)
- **신호 변화율/제로 비율**: 신호가 거의 변하지 않으면 전략이 사실상 멈춤.
- **리밸런스 빈도 vs 임계치**: 임계치가 너무 커서 거래가 안 나갈 수 있음.
- **진단 로그**: (E1)에서 리밸런스마다 “신호 상위/하위 종목 및 점수”를 기록해 정체 구간을 확인.

### B. 적용(신호가 포지션으로 반영되는가?)
- **target_weights vs filled_weights 괴리**: 체결/제약(8~14 유지, 상한, 현금, 거래정지)으로 목표가 반영 안 될 수 있음.
- **제약 충돌 카운터**: “제약 때문에 못 샀음/못 팔았음” 카운트를 리밸런스 로그로 남김(E1).

### C. 노출(리스크가 의도대로 움직이는가?)
- **노출(min/max), 섹터 비중, 단일종목 상한**: 노출이 고정/클리핑되면 성능이 둔화.
- **게이트 발동률**(E4): 상시 발동이면 수익 기회가 차단되어 “안 움직이는” 것처럼 보일 수 있음.

### D. 비용(성과가 비용에 먹히는가?)
- **턴오버 × 스프레드**가 커지면 Gross는 움직여도 Net이 정체.
- (E3)에서 비용 레벨 스트레스로 “비용 민감도 곡선”을 확보:  
  민감도가 과하면 → 턴오버 페널티/리밸런스 완화로 이동.

### E. 레짐(시장 환경이 전략 가정과 맞는가?)
- **관측 레짐 지표(ETF 사용)**  
  - QQQ 모멘텀/변동성(VIX)/금리(TLT)로 “risk-on/off”를 태깅(매매는 금지, 태깅만).
- 레짐별 성능 분해: OOS를 레짐 라벨로 stratify 해서 “정체가 특정 레짐에 국한”인지 확인(E4 관측치로 자동화).

## 48시간 운영 루프(자동 실행 순서) — 명령형 체크리스트
1) **E1 먼저 적용**: 로깅/리스크 지표가 없으면 이후 모든 실험이 해석 불가.
2) **E2 실행**: 누수/정의 불일치가 발견되면 다른 개선은 전부 보류하고 차단.
3) **E5 실행**: 유니버스/상폐 처리 고정 후에만 성능 논의.
4) **E3 실행**: Net 기준으로 전략을 다시 평가(비용 민감도 확보).
