## TOP5 우선순위(24~48h) — 명령형 체크리스트(코드/아키텍처/전략)

### 1) **누수/과최적화 최우선 차단: Purge/Embargo + 피처 라인리지 강제**
**(a) 왜 필요한지**
- `degenerate_folds: [1,2,3,8]`는 OOS가 “진짜 OOS”가 아닐 확률이 큼(시간축 섞임/샘플 수 부족/중복/리밸런스 시점 누수).
- Champion 메타가 비어 있음(`file:`, `lane_hash`, `run_hash` None). 재현 불가 = 누수/운영 리스크 즉시 상승.

**(b) 위험/부작용**
- 단기적으로 OOS 하락 가능(누수 제거의 정상 반응).
- purge/embargo가 과도하면 학습 샘플이 줄어 변동성 증가.

**(c) 최소 실험 2~3개 (아래 E1 사용)**
- E1-A: 리밸런스 시점 기준 **purge-k + embargo-e**(기본값 소/중) 적용.
- E1-B: “리밸런스 직전 N일”에 계산된 피처만 허용(피처 timestamp 검사로 미래 참조 차단).
- (옵션) E1-C: 훈련/검증 분리에서 **동일 종목-동일 기간 중복 샘플 제거**(row hash de-dup).

**(d) PASS 조건**
- `degenerate_folds`가 **0개**로 감소(또는 fold당 유효 샘플 수 하한 충족).
- OOS mean이 단기 하락하더라도 **OOS min 개선(꼬리 리스크 감소)** 또는 성능-노출 상관이 “정상화”(과도한 0.84 레버리지 의존 감소)되면 통과.


---

### 2) **서바이버십/유니버스 고정: Tech+Healthcare 8~14 종목을 “과거시점으로” 재구성**
**(a) 왜 필요한지**
- “현재 살아남은 종목 기준”으로 백테스트하면 성능이 움직이지 않거나 과대평가될 수 있음(서바이버십 편향).
- 요청 조건(미국주식 only, Tech+Healthcare, 8~14개)에서 **유니버스가 실험마다 흔들리면** 비교가 무의미해짐.

**(b) 위험/부작용**
- 데이터 소스에 따라 과거 구성 복원이 어려워 결측/상폐 처리 필요(운영 난이도 증가).
- 유니버스가 고정되면 전략 자유도가 줄어 단기 수익 감소 가능.

**(c) 최소 실험 2~3개 (아래 E2 사용)**
- E2-A: **8~14개 종목 “고정 리스트”**(Tech/Healthcare 혼합)로만 학습/검증(전 기간 동일).
- E2-B: “과거 시점 선택” 규칙 추가: 리밸런스 시점에 **시총/거래대금/상장상태**로 필터(미래정보 없이).
- (옵션) E2-C: 상폐/합병 등 이벤트 시 **가격=0 처리 금지**, 마지막 거래일 정리 및 현금화 룰 명시.

**(d) PASS 조건**
- 동일 기간/동일 파이프라인에서 **유니버스 변동 0**(실험 간 비교 가능).
- OOS 분산이 줄고, 성능이 “조금이라도” 반응(정체 해소)하면 통과.


---

### 3) **비용 미반영/거래 과다 차단: 비용모델 + 턴오버 게이트**
**(a) 왜 필요한지**
- 성능이 안 움직이는 대표 원인: “예상수익 변화 < 비용/슬리피지”로 알파가 소거.
- 현재 `exposure 0~0.84`면 리밸런스/포지션 변동에 따른 비용 민감도가 큼.

**(b) 위험/부작용**
- 비용을 넣으면 백테스트 성능 급락 가능(하지만 그게 현실).
- 턴오버 캡은 기회 손실 발생(다만 운영 안정성↑).

**(c) 최소 실험 2~3개 (아래 E3 사용)**
- E3-A: 고정 비용(예: bps) + 슬리피지(변동성/거래대금 기반) **단계적 온**.
- E3-B: **턴오버 캡(일/주 기준)** + 리밸런스 “미세 변경 무시”(δ-weight 임계값) 적용.
- (옵션) E3-C: 비용 포함 후에도 살아남는지 **alpha per turnover** 지표로 비교.

**(d) PASS 조건**
- 비용 포함 후에도 OOS mean이 유지되거나, 최소한 **OOS min(최악) 개선**.
- turnover가 목표 상한 이하로 내려가고, “리밸런스 잦음”이 원인인지 판별 가능해지면 통과.


---

### 4) **노출(Exposure)·레짐 게이트 도입: 48시간 루프에서 “켜짐/꺼짐”이 명확해야 함**
**(a) 왜 필요한지**
- 현재 노출이 0~0.84로 넓음 → “알파”가 아니라 “노출 타이밍”이 성과를 좌우할 수 있음(과최적화/레짐 의존).
- 48시간 자동 루프에서는 **게이트로 실패를 조기 차단**해야 비용(시간/컴퓨트) 절감.

**(b) 위험/부작용**
- 게이트가 과하면 거래가 거의 안 나가 “정체”처럼 보일 수 있음.
- 레짐 필터가 과거에만 맞는 오버핏이 될 수 있음(간단한 규칙부터).

**(c) 최소 실험 2~3개 (아래 E4 사용)**
- E4-A: **노출 하드캡**(예: max 0.60) + 현금 비중 바닥(예: min 0.05) 적용.
- E4-B: 관측지표(ETF는 매매 금지, 관측만)로 **QQQ/XLV 변동성 또는 스프레드** 기반 “Risk-Off → 노출 축소” 룰.
- (옵션) E4-C: 손실 구간에서만 작동하는 **MDD 기반 디레버리지**(단순/비선형 금지).

**(d) PASS 조건**
- worst-MDD가 산출되고(지금 `None`은 계측 결함 가능), MDD 또는 OOS min이 개선.
- 노출 변화가 성능을 “지배”하는지(상관↑) 줄어들면 통과.


---

### 5) **운영/재현성 리스크 제거: 리밸런스 로그/메타데이터를 단일 포맷으로 강제**
**(a) 왜 필요한지**
- `aub_rebalance_pinpoint`가 로그 로딩 실패(`--base-log` 파일 없음, JSON 파싱 실패). 현재는 “왜 성능이 안 움직였는지” 추적 불가.
- Champion에 `file/lane_hash/run_hash`가 비어 있으면 자동 루프에서 롤백/비교가 불가능.

**(b) 위험/부작용**
- 로그가 커져 저장비용/IO 증가.
- 포맷 강제는 초기 마이그레이션 비용 발생.

**(c) 최소 실험 2~3개 (아래 E5 사용)**
- E5-A: 리밸런스 출력물을 **JSONL(라인 단위)** 로 통일(각 리밸런스 이벤트 1줄).
- E5-B: run 메타에 **lane_hash/run_hash/data_hash/code_hash**를 필수 필드로 강제(없으면 실패).
- (옵션) E5-C: `rebalance.csv` 의존 제거하고, pinpoint 툴이 **JSONL만 읽게** 단순화.

**(d) PASS 조건**
- `aub_rebalance_pinpoint.py`가 base/cand 모두에서 **에러 없이 리포트 생성**.
- Champion JSON에 필수 메타가 채워지고, 48시간 루프에서 “이전 대비 변경점”이 자동 요약되면 통과.

## 48시간 자동 루프용 “실행 가능한 패치/실험” 5개(케이스 폭발 방지)
아래 5개만 돌리고, 나머지는 금지(실험 수 고정).

### E1) Purge/Embargo + 피처 타임스탬프 검사(누수/과최적화 차단)
1) **실험 정의**: 리밸런스 기준 워크포워드 분할에 purge-k, embargo-e 적용 + 피처 생성 시점이 리밸런스 시점 이후를 참조하면 실패 처리  
2) **게이트**: degenerate_folds=0, fold당 최소 샘플/리밸런스 수 하한 통과, OOS 계산에 미래 캔들 참조 0건  
3) **기대 관측치**: OOS mean이 단기 하락해도 OOS min 개선/분산 감소, 성능 재현성 상승

### E2) Tech+Healthcare 8~14 종목 유니버스 “고정/과거시점 규칙화”(서바이버십 제거)
1) **실험 정의**: 고정 8~14개 리스트 또는 과거시점 필터(시총/거래대금/상장상태)로 유니버스 생성(ETF 매매 금지)  
2) **게이트**: 실험 간 유니버스 변경 0, 상폐/결측 처리 룰에 따른 현금화 일관성  
3) **기대 관측치**: 성능이 “정체”였다면 반응(위/아래) 발생, 원인 분해 가능해짐

### E3) 비용/슬리피지 모델 + 턴오버 캡(비용 미반영 제거)
1) **실험 정의**: bps+슬리피지 온 + δ-weight 임계값 + 턴오버 상한  
2) **게이트**: 비용 포함 후도 거래비용/매매대금 산출 100%, turnover 상한 준수  
3) **기대 관측치**: 비용 전/후 성능 괴리로 “정체 원인=비용” 여부 즉시 판별

### E4) 노출/레짐 게이트(운영 안정성 + 꼬리 개선)
1) **실험 정의**: 노출 하드캡 + Risk-Off 관측지표(예: QQQ/XLV 변동성)로 노출 축소  
2) **게이트**: max exposure 준수, worst-MDD 산출(계측 결함이면 실패)  
3) **기대 관측치**: OOS min 및 MDD 개선, 성능이 노출 타이밍에 과도하게 좌우되는 현상 완화

### E5) 리밸런스 JSONL 단일화 + run 메타 필수화(운영/재현성 리스크 제거)
1) **실험 정의**: 모든 런에서 rebalance.jsonl 생성 + 메타(data/code/run hash) 없으면 런 실패  
2) **게이트**: pinpoint 리포트 자동 생성, champion 메타 null 필드 0개  
3) **기대 관측치**: “왜 안 움직였는지”가 리밸런스/노출/비용 단위로 추적 가능

## 성능이 안 움직일 때: 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 실행 순서
아래는 **질문 없이** 바로 적용 가능한 분해 트리(각 노드는 로그/지표로 판정).

### A) 트리거(신호가 실제로 변하나?)
- **명령**: 리밸런스 시점별로 `signal_rank_entropy`, `top_k 구성 변화율`, `신호 표준편차`를 로그로 저장  
- **판정**  
  - 변화율이 낮다 → 신호가 정체(피처 업데이트 주기/정규화/결측 처리 문제)  
  - 변화율이 높은데 성과 무변 → 아래 B/C로 이동

### B) 적용(신호가 포지션으로 반영되나?)
- **명령**: 리밸런스마다 `target_weight`, `executed_weight`, `δ-weight`, “임계값으로 인해 무시된 변경량” 저장  
- **판정**  
  - δ-weight가 항상 작다 → 포지션이 거의 안 바뀜(게이트 과함/신호 스케일 문제)  
  - δ-weight는 큰데 성과 무변 → 비용/슬리피지 또는 레짐 가능성

### C) 노출(성과가 알파가 아니라 베타/노출인가?)
- **명령**: 포트폴리오 수익을 `노출(총익스포저)`, `섹터 더미(Tech/HC)`, 관측 ETF(예: QQQ/XLV)와 회귀해 `beta` 추정(ETF는 거래 금지, 분석만)  
- **판정**
  - 설명력 대부분이 beta면 → 알파가 아니라 노출 타이밍 게임(노출캡/리스크오프 필요: E4)  
  - beta 낮은데 성과 무변 → 비용/슬리피지 or 신호 자체 품질 문제

### D) 비용(알파가 비용에 먹히나?)
- **명령**: 거래비용을 “리밸런스 이벤트별”로 분해해 `gross PnL`, `cost`, `net PnL`, `alpha_per_turnover` 기록  
- **판정**
  - gross는 움직이는데 net이 정체 → 비용이 원인(E3)  
  - gross부터 정체 → 신호/유니버스/누수 점검(E1/E2)

### E) 레짐(특정 국면에서만 작동하나?)
- **명령**: 기간을 3~5개 레짐(변동성 상/하, 금리 급등/완만 등)으로 나누고 레짐별 OOS mean/min/MDD를 출력(관측지표 기반, 거래 금지)  
- **판정**
  - 특정 레짐에서만 성과 → 레짐 게이트(E4) 또는 모델 단순화/규제 필요  
  - 모든 레짐에서 정체 → 데이터/누수/서바이버십/비용/포지션 반영 중 하나가 “구조적으로” 막힘(E1~E5 로그로 역추적)
