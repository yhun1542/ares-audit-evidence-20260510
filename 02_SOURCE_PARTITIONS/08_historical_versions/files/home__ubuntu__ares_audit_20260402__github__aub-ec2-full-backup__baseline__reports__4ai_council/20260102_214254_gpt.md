# 1) 다음 24~48시간 우선순위 TOP5 (코드/아키텍처/전략)
아래 5개는 “**운영 가능한 48시간 자동 루프**”를 만들고, 성능이 안 움직이는 원인을 **분해 가능한 상태로 만드는 것**에 집중.

## TOP1) 리밸런스/실행 로그 표준화 + 핀포인트 복구(운영 리스크 최우선)
### (a) 왜 필요한지
- 지금 상태에선 “**언제/왜 성능이 변했는지**”를 리밸런스 단위로 추적 불가.  
- 자동 루프에서 가장 치명적인 건 성능이 아니라 **원인 미추적 + 재현 불가**.

### (b) 위험/부작용
- 로그량 증가(디스크/IO 비용), 파이프라인 느려짐.
- 포맷 전환 시 과거 리포트 호환성 깨질 수 있음(버전 태그 필요).

### (c) 최소 실험 2~3개 (아래 ‘실험 Backlog’의 E1, E5 재사용)
- E1: `rebalance.jsonl`/`rebalance.csv` 동시 기록 + 스키마 버전
- E5: `worst_mdd` 계산/저장 강제(없으면 실패 처리)

### (d) PASS 조건
- [ ] `aub_rebalance_pinpoint.py`가 **base/cand 둘 다** 로드 성공
- [ ] 각 run에 `run_hash/lane_hash/git_sha/data_fingerprint` 존재
- [ ] `worst_mdd`가 None이 아닌 실수로 산출되고 리포트에 포함

## TOP2) CV 분할/폴드 퇴행 제거(누수·과최적화 1차 방어선)
### (a) 왜 필요한지
- `degenerate_folds`는 “학습/검증 샘플이 거의 없거나”, “purge 실패로 정보 누수”, “리밸런스 이벤트가 특정 폴드에 몰림” 신호.  
- 이 상태에선 OOS mean이 좋아도 **착시일 확률이 높음**.

### (b) 위험/부작용
- 훈련 데이터 유효량 감소 → 단기 성능 하락 가능
- 기존 챔피언과 비교가 불리해질 수 있음(하지만 신뢰성은 증가)

### (c) 최소 실험 2~3개 (E2 중심)
- E2: Purged Walk-Forward + 최소 이벤트 수/폴드 강제
- (옵션) 같은 E2에서 “리밸런스 빈도/홀딩 기간”을 고정해 폴드 균형 확인

### (d) PASS 조건
- [ ] `degenerate_folds == []`
- [ ] 폴드별 거래 횟수/평균 노출/턴오버가 **극단치 없이** 분포
- [ ] OOS mean이 떨어져도 **분산(폴드 간 편차)**가 감소

## TOP3) 비용(슬리피지/수수료/스프레드) + 턴오버 게이트 추가(비용 미반영 방지)
### (a) 왜 필요한지
- Tech/Healthcare 8~14종목 집중은 신호가 약간 좋아도 **턴오버가 성과를 잡아먹는** 경우가 많음.  
- “성능이 안 움직임”의 흔한 원인이 **알파는 있는데 비용으로 상쇄**되는 것.

### (b) 위험/부작용
- 백테스트 성과 급락 가능(현실 반영으로 정상)
- 과도한 비용 가정 시 기회 손실(보수적 과잉)

### (c) 최소 실험 2~3개 (E3 중심)
- E3: 거래비용 모델 on(고정+변동 슬리피지) + 최대 턴오버 게이트
- (옵션) E3에서 “리밸런스 시그널 임계값”만 1개 축으로 스윕(케이스 폭발 금지)

### (d) PASS 조건
- [ ] **비용 차감 후** OOS mean 유지/개선 또는 MDD/변동성 개선
- [ ] 월간(또는 리밸런스 기준) turnover 상한 준수
- [ ] “gross → net” 성과 갭이 설명 가능 범위로 축소

## TOP4) 서바이버십/Point-in-Time 유니버스 고정(Tech+Healthcare, 8~14종목) 
### (a) 왜 필요한지
- 종목 유니버스를 “현재 생존자”로 만들면, OOS가 좋아도 **서바이버십 바이어스**로 성능이 고정/왜곡될 수 있음.
- Tech/Healthcare는 상장/합병/퇴출이 잦아 편향이 커짐.

### (b) 위험/부작용
- 데이터 준비 비용↑(히스토리컬 컨스티튜언트/상장폐지 처리)
- 유니버스가 바뀌며 기존 결과와 단절

### (c) 최소 실험 2~3개 (E4 중심)
- E4: Point-in-time 유니버스(Tech+Healthcare) 생성 + “동일 규칙으로 매 시점 8~14개 강제”
- (옵션) 유니버스 선정 룰은 1개만: 예) 시총/유동성 상위 + 섹터 분류 고정(변형 금지)

### (d) PASS 조건
- [ ] 동일 기간 재실행 시 종목풀이 재현(데이터 핑거프린트 동일)
- [ ] OOS 성능이 하락하더라도 **폴드 안정성/리스크 지표가 정상화**
- [ ] 8~14종목 제약이 항상 만족(빈 포트폴리오/과집중 방지)

## TOP5) 노출(Exposure)·레짐(ETF 관측지표) 게이트로 “움직이지 않음” 원인 분리
*(ETF는 매매 금지, 관측/게이트만)*

### (a) 왜 필요한지
- 현재 노출 max가 0.84까지 뜸 → “신호가 있어도 적용이 안 돼서 성능이 안 움직이는지”, “레짐에서만 죽는지” 분해 필요.
- 레짐 분해 없이는 개선이 랜덤 워크가 됨.

### (b) 위험/부작용
- 게이트가 과하면 거래가 줄어 성과가 더 정체될 수 있음
- 레짐 지표 선택을 잘못하면 과최적화 위험(지표 수 최소화)

### (c) 최소 실험 2~3개 (E5 중심)
- E5: ETF 관측지표(예: QQQ, XLK, XLV)로 레짐 라벨링만 추가(“리포트/게이트”)  
- E5에 포함: **노출 하한(예: 최소 투자비율) 또는 ‘현금 대기’ 규칙** 중 하나만 택해 단일축 비교

### (d) PASS 조건
- [ ] 레짐별(상승/하락/횡보) 성과/턴오버/노출 리포트가 자동 생성
- [ ] “성능 정체” 구간이 **(노출 부족 vs 비용 vs 레짐 부적합)** 중 하나로 귀속 가능
- [ ] worst_mdd/드로우다운이 악화되지 않거나 개선

# 2) 48시간 자동 루프용 “실행 가능한 Patch/실험” 5개(총 5개로 제한)
아래 5개만 돌리면 TOP1~TOP5를 커버하도록 설계(케이스 폭발 방지).  
각 항목은 **(1) 실험 정의 (2) 게이트 (3) 기대 관측치**로 고정.

---

## E1) Rebalance 로그/아티팩트 스키마 고정(핀포인트 복구)
1) **실험 정의**
- 리밸런스 이벤트마다 `rebalance.jsonl` 기록(필수 필드: timestamp, universe, target_weights, fills, slippage, fees, turnover, exposure, cash, reason_codes)
- 동시에 `rebalance.csv`도 생성(최소 컬럼만)  
- run 시작 시 `run_hash/lane_hash/git_sha/data_fingerprint/config_hash`를 메타에 강제 기록

2) **게이트**
- `aub_rebalance_pinpoint.py`가 base/cand 모두 **로드 성공**(에러=FAIL)
- 필수 필드 누락 시 run 자체를 FAIL 처리

3) **기대 관측치**
- “어느 리밸런스에서 성과가 깨졌는지” 1분 내 pinpoint 가능
- 성능 변화가 없더라도 **원인(거래 없음/노출 제한/비용 급증)**이 로그로 드러남

---

## E2) Purged Walk-Forward + 폴드 최소 이벤트 보장(퇴행 폴드 제거)
1) **실험 정의**
- 시간 순 워크포워드에 purge/embargo 적용
- 각 폴드에 “최소 리밸런스 이벤트 수/최소 거래 수/최소 유효 노출 기간”을 강제(미달 폴드는 합치거나 스킵)

2) **게이트**
- `degenerate_folds == []`
- 폴드별 거래 수가 하한 미달이면 FAIL

3) **기대 관측치**
- OOS mean이 내려가도 폴드 편차 감소
- “성능이 안 움직임”이 분할 문제인지 아닌지 즉시 판별

---

## E3) 비용 모델 + 턴오버 상한 게이트(순수익 기준으로 재평가)
1) **실험 정의**
- 비용 모델: 고정 수수료 + 스프레드/슬리피지(단순 선형 1개로 시작)  
- 포트폴리오에 turnover 상한(기간 기준 1개) 적용

2) **게이트**
- Net 성과 리포트 필수 생성
- turnover 상한 위반 시 FAIL(또는 패널티)

3) **기대 관측치**
- Gross는 좋은데 Net이 안 나오던 케이스를 비용으로 귀속
- 성능 정체가 “비용 상쇄”인지 확인

---

## E4) Point-in-time Tech+Healthcare 유니버스(8~14종목 강제)
1) **실험 정의**
- 섹터 분류 기반(Tech+Healthcare) + 시점별 유동성/시총 기준으로 후보 생성  
- 매 시점 포트폴리오 종목 수를 8~14로 강제(부족 시 규칙적으로 보완)

2) **게이트**
- 동일 run 재실행 시 universe 스냅샷 해시 일치(재현성)
- 종목 수 제약 위반 시 FAIL

3) **기대 관측치**
- 서바이버십 제거 후 성과가 변하면 원인이 “유니버스 편향”으로 귀속
- 이후 전략 튜닝이 의미를 갖게 됨

---

## E5) 리스크 메트릭 정상화(worst_mdd) + 레짐 리포트(QQQ/XLK/XLV 관측)
1) **실험 정의**
- worst_mdd를 반드시 계산/저장(없으면 예외)  
- ETF(예: QQQ/XLK/XLV)로 레짐 라벨(단 2~3구간)만 만들어 성과/노출/비용을 구간별로 리포트

2) **게이트**
- `worst_mdd`가 float로 존재
- 레짐별 리포트 파일 생성 실패 시 FAIL

3) **기대 관측치**
- 성능 정체가 특정 레짐(예: 헬스케어 언더퍼폼)에서만 발생하는지 확인
- “노출이 낮아 안 움직임” vs “레짐에서만 손실”을 분리

# 3) “성능이 안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래를 **순서대로** 자동 진단 리포트에 넣어, 48시간 루프에서 매번 동일하게 판정되게 만드세요(질문 없이 실행 체크리스트).

## A. Trigger(신호 발생) 문제인지
- [ ] 리밸런스 시점별 **신호 분포(상위/하위 스코어, 분산, 동률 비율)** 저장
- [ ] “매수/매도 임계값 통과 건수” 타임시리즈 생성  
- 판정: 신호 분산이 거의 0 / 동률 과다 / 임계값 통과가 희박하면 **트리거가 죽어있음**

## B. Apply(적용/제약)에서 막히는지
- [ ] 제약 위반으로 주문이 잘렸는지 reason code 기록(종목수 8~14, 섹터, 단일종목 상한, 현금비중, 리밸런스 최소단위)
- [ ] 목표가중치 → 체결가중치 괴리(슬리피지/유동성) 저장  
- 판정: 신호는 있는데 체결/제약으로 포지션이 못 바뀌면 **적용단 문제**

## C. Exposure(노출) 부족/과다인지
- [ ] 노출(총/순/섹터별) 시계열, “노출 0에 가까운 기간 비율” 산출
- [ ] 8~14 종목인데도 노출이 낮으면 “현금 대기 규칙/게이트 과다” 의심  
- 판정: 성과 변동이 시장 변동 대비 너무 작으면 **노출 부족**

## D. Cost(비용)로 알파가 상쇄되는지
- [ ] gross pnl / net pnl / 비용(수수료+슬리피지) / turnover를 동일 축으로 리포트
- [ ] “거래 1회당 기대 알파” 대비 비용 비율 산출  
- 판정: gross는 움직이는데 net이 평평하면 **비용 상쇄**

## E. Regime(레짐) 편향인지
- [ ] ETF 관측지표로 레짐(예: QQQ 200D 위/아래, XLK-XLV 상대강도 양/음) 2~3개 구간만
- [ ] 구간별 hit-rate, 평균 보유기간, MDD, 비용을 분해  
- 판정: 특정 레짐에서만 손실/거래폭증이면 **레짐 미스매치**

---

## 24~48시간 실행 순서(명령형)
- [ ] E1부터 적용해 **핀포인트/재현성 복구**(실패하면 나머지 보류)
- [ ] E5로 `worst_mdd` 및 레짐 리포트 강제(리스크/원인분해 기반 확보)
- [ ] E2로 폴드 퇴행 제거(신뢰 가능한 OOS로 교체)
- [ ] E3로 비용/턴오버 게이트 적용(“움직임 없음”이 비용인지 판정)
- [ ] E4로 point-in-time 유니버스 고정(서바이버십 제거 후 재평가)

이 5개만 완료하면, 다음 루프부터는 “성능이 왜 안 움직이는지”가 **트리거/적용/노출/비용/레짐** 중 어디인지 자동으로 귀속되고, 그때부터 전략 개선이 랜덤워크가 아니라 **원인 기반 패치**로 전환됩니다.
