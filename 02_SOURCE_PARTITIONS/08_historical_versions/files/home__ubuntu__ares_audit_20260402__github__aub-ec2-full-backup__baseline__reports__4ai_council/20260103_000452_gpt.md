## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — **명령형 체크리스트**
(누수/과최적화/서바이버십/비용 미반영/운영 리스크 순으로 점검)

---

# 1) **리포트/로그/아티팩트 파이프라인 복구(운영 리스크 최우선)**
현재 `--base-log` 없음 + `rebalance.csv/jsonl` 파싱 실패 + champion에 `file/lane_hash/run_hash/worst_mdd=None` → **재현/디버깅 불가 상태**.

### (a) 왜 필요한지
- 성능 정체/악화의 원인이 **전략**인지 **관측/로깅 오류**인지 분리 불가.
- Rebalance pinpoint가 “데이터 없음”으로 막혀 **거래/비용/노출 문제**를 못 봄.
- `worst_mdd=None`은 리스크 산출이 깨졌거나 시뮬레이션 결과가 불완전하다는 신호.

### (b) 위험/부작용
- 로그 강제/검증 추가로 런타임 증가.
- 기존 “우연히 통과하던” 비정상 런이 **실패 처리**되어 단기적으로 챔피언 갱신이 느려짐(의도된 안전장치).

### (c) 최소 실험(공유 실험 ID 사용)
- **E1 + E1b** (아래 “실험 정의” 섹션 참조)
- **E1 + E2**(fold 산출물까지 강제 저장)
- **E1 + E3**(비용/체결 로그까지 강제 저장)

### (d) PASS 조건
- 모든 런에서 아래가 **항상 채워짐**: `run_hash/lane_hash/champion_file_path/worst_mdd/rebalance.jsonl(or csv)/daily_pnl_series/exposure_series`
- `aub_rebalance_pinpoint.py`가 base/cand 모두에서 **에러 없이** 리포트 생성
- “OOS mean(챔피언)” 값이 diagnoser 리포트와 **동일한 정의로 재계산 시 ±1% 이내**로 일치

---

# 2) **Degenerate folds 제거(과최적화/검증 붕괴 방지)**
현재 `degenerate_folds: [1,2,3,8]` → OOS가 “좋아 보이지만” 검증이 무너졌을 가능성 큼.

### (a) 왜 필요한지
- 시간축 CV에서 fold가 깨지면 **누수/중복/샘플 부족**으로 OOS가 허상일 수 있음.
- “성능이 안 움직임”이 아니라 **검증이 민감도를 잃은 상태**일 수 있음.

### (b) 위험/부작용
- 제대로 고치면 성능이 **하락**할 수 있음(그게 정상).
- 데이터가 적으면 안정적 폴드를 만들기 위해 학습 구간이 줄어들 수 있음.

### (c) 최소 실험
- **E2 + E2b**
- **E2 + E4**(point-in-time/서바이버십 수정과 함께 재검증)
- **E2 + E5**(포트폴리오 제약으로 fold별 분산 감소)

### (d) PASS 조건
- `degenerate_folds == []` (0개)
- 모든 fold에서 최소 거래일/샘플 수가 사전 기준 이상(예: 각 fold OOS 구간 ≥ 126 trading days)
- Fold 간 성능 분산(예: OOS 샤프/평균)의 극단치가 완화(“한 fold만 특출” 현상 감소)

---

# 3) **비용/체결/슬리피지 모델을 “게이트”로 승격(비용 미반영 제거)**
현재 rebalance 로그 자체가 없어서 비용을 사실상 못 보고 있을 확률이 큼.

### (a) 왜 필요한지
- Tech/Healthcare 대형주라도 48시간 루프에서 빈번 리밸런스면 **슬리피지+스프레드+임팩트**가 엣지를 잠식.
- OOS mean이 “움직이지 않는” 주된 이유가 **비용이 0으로 간주**된 채 과회전 전략이 상위로 남는 현상일 수 있음.

### (b) 위험/부작용
- 비용을 넣는 순간 성능이 크게 감소할 수 있음.
- 비용 파라미터를 잘못 잡으면 과도하게 보수적으로 되어 거래 기회를 놓칠 수 있음(그래서 “게이트+민감도”로 처리).

### (c) 최소 실험
- **E3 + E1**(비용 로그 강제)
- **E3 + E5**(회전율 상한/최소 홀딩기간로 비용 절감)
- **E3b**(비용 민감도: low/base/high 3점만; 케이스 폭발 금지)

### (d) PASS 조건
- (비용 포함) OOS mean이 (비용 0 대비) 합리적 수준으로만 하락하고, **turnover 대비 성과**가 개선
- 비용 high 시나리오에서도 OOS mean이 0 근처로 붕괴하지 않음(“비용에 전부 먹힘” 전략 탈락)

---

# 4) **서바이버십/Point-in-Time(PTI) 데이터 무결성 점검(누수/환상 수익 제거)**
미국주식 백테스트에서 가장 흔한 “성능이 고정/허상” 원인.

### (a) 왜 필요한지
- 현재 champion 메타가 비어있는 것(파일/해시 없음)과 함께 보면, 데이터 로더/캐시 레이어가 **대체/재사용**되며 PTI가 깨졌을 가능성.
- delisting/심볼 변경/기업행동(분할, M&A) 누락은 Healthcare에서도 빈번.

### (b) 위험/부작용
- 데이터 정합성 교정 후 성능 급락 가능(정상).
- 데이터 소스 교체/보강이 필요하면 단기 운영 복잡도 증가.

### (c) 최소 실험
- **E4 + E2**(누수 제거 후 폴드 정상화)
- **E4b**(심볼/상장폐지 포함 유니버스 재생성)
- **E4 + E3**(정합성 교정 후 비용 포함 성능 재측정)

### (d) PASS 조건
- 과거 시점 유니버스 재구성 시 **미래 상장 종목 유입이 차단**(룩어헤드 0)
- 기업행동 반영 후 가격/수익률 시계열에 비정상 점프(스플릿 미반영 등) 자동 탐지 0건 또는 격감
- 교정 후에도 OOS가 fold 전반에서 “일관된 신호”를 유지(특정 기간만 폭발하는 현상 감소)

---

# 5) **포트폴리오 제약/노출 관리(8~14개, Tech+Healthcare 중심) + ETF는 지표로만 사용**
현재 `exposure_max ~0.84`는 “현금 비중 높음/신호 희소/리밸런스 제약” 중 하나 신호. 노출 구조를 강제해서 “움직이지 않는 성능” 원인을 분해.

### (a) 왜 필요한지
- 포지션 수/섹터가 흔들리면 성과 분산이 커지고, fold degeneracy와 결합 시 “챔피언이 고착”되기 쉬움.
- **8~14개**로 강제하면 과최적화(종목 선택 편향)와 운영 리스크(과도한 집중)를 동시에 감소.

### (b) 위험/부작용
- 제약이 강하면 알파가 희석될 수 있음.
- 강제 리밸런스가 증가하면 비용이 늘 수 있어 E3와 함께 봐야 함.

### (c) 최소 실험
- **E5 + E3**(제약+비용 동시 적용)
- **E5b**(ETF 지표: SPY/QQQ/XLK/XLV로 레짐 스케일링만; ETF 매매 금지)
- **E5 + E2**(검증 붕괴 제거 후 제약 효과 확인)

### (d) PASS 조건
- 항상 **미국주식, 8~14개**, Tech+Healthcare 비중이 정책 범위 내(예: 두 섹터 합 70% 이상 같은 하드룰을 둔다면 그 준수)
- 단일 종목 익스포저 상한 준수(예: 15%~20%)
- 노출(exposure) 시계열이 “0 또는 0.84 근처로 붙는” 현상이 완화(연속 구간에서 자연스러운 변동)

## 48시간 자동 루프용 “실행 가능한 패치/실험” 5개 (3~5개 제한 준수)
아래 5개만 돌리고, 각 TOP5 제안은 이 5개 조합으로 커버.

---

## **E1) 아티팩트/로그 스키마 강제 + 실패-패스트(Fail-fast)**
### (1) 실험 정의
- 모든 런 종료 시 다음을 **필수 산출물**로 생성/저장:
  - `run_hash, lane_hash, git_sha, config_hash`
  - 일별 `pnl.csv`, `exposure.csv`, `positions.csv`
  - `rebalance.jsonl`(각 거래: timestamp, symbol, target_w, delta_w, est_cost, fill_price 가정)
  - `metrics.json`에 `worst_mdd` 포함(없으면 런 실패)
- `aub_rebalance_pinpoint.py`가 요구하는 경로/포맷으로 **동일 스키마** 제공(옵션 파싱 포함).

### (2) 게이트
- 위 필수 파일 중 하나라도 누락/파싱 실패 시 런을 **FAIL**로 마킹하고 챔피언 후보에서 제외.

### (3) 기대 관측치
- “No rebalance data found”, “Expecting value…” 유형 오류 0건.
- OOS mean 불일치(챔피언 vs diagnoser) 재현 가능해지고 원인(정의/기간/비용포함 여부) 추적 가능.

---

## **E2) 시간축 CV 재설계: Purge/Embargo + 최소 샘플 보장**
### (1) 실험 정의
- Walk-forward 또는 Purged K-Fold로 변경:
  - 학습/검증 경계에 **embargo window**(예: 5~20 trading days) 적용
  - fold별 최소 OOS 길이 보장
  - 훈련 구간에 미래 가격/지표가 섞이면 즉시 탐지(타임스탬프 단위 assert)

### (2) 게이트
- `degenerate_folds`가 1개라도 발생하면 FAIL.
- 각 fold OOS 표본 수가 기준 미달이면 FAIL.

### (3) 기대 관측치
- OOS가 단일 fold에만 의존하는 형태가 줄고, 평균 성능은 내려가더라도 **분산이 감소**.

---

## **E3) 비용/슬리피지 모델 + 회전율(턴오버) 제약**
### (1) 실험 정의
- 비용을 단순 1개 숫자가 아니라 거래당 구성요소로 로그:
  - spread(고정 bps) + slippage(변동, 예: |delta_w|/ADV proxy) + 수수료
- 포트폴리오 레벨 제약:
  - 일간/주간 turnover 상한
  - 최소 홀딩기간(예: 2~5거래일) 중 하나만 적용(케이스 폭발 방지)

### (2) 게이트
- 비용 포함 OOS mean이 비용 0 대비 과도하게 붕괴(예: 70% 이상 감소)하면 FAIL(전략이 비용에 취약).
- turnover가 상한을 지속 위반하면 FAIL.

### (3) 기대 관측치
- 거래 횟수 감소, rebalance 로그에서 작은 잔챙이 트레이드가 사라짐.
- “성능이 안 움직임”이 비용 때문인지 아닌지 즉시 판별 가능.

---

## **E4) PTI/서바이버십 방어: 유니버스/기업행동 정합성 체크**
### (1) 실험 정의
- 유니버스 생성 시점에 “그 날짜에 실제로 거래 가능했던” 종목만 포함(상장/상폐 반영).
- Adjusted price/return 계산에 split/dividend 반영 일관화.
- (가능하면) 지표/펀더멘털은 발표일 기준 PTI로 스냅샷 사용(미래값 금지).

### (2) 게이트
- 임의 과거 날짜에 대해 “미래 상장 종목”이 포함되면 FAIL.
- split 미반영 징후(비정상 점프) 자동 탐지시 FAIL(또는 자동 수정 후 재시도).

### (3) 기대 관측치
- 일부 기간에서만 비정상적으로 좋던 성과가 사라지고, 신호가 더 현실적으로 변함.

---

## **E5) 포트폴리오 정책 고정: 8~14개, Tech+Healthcare 중심 + 레짐 스케일(ETF는 지표)**
### (1) 실험 정의
- 거래 대상: 미국 상장 개별주 only, 섹터는 Tech/Healthcare 중심.
- 포트폴리오 정책:
  - 보유 종목 수 8~14 강제
  - 단일 종목 상한, 섹터 상한/하한
  - 노출 스케일: ETF(관측지표)로만 레짐 판단  
    - 예: `XLK/SPY 모멘텀`, `XLV/SPY 방어 우위`, `QQQ 변동성 proxy` 등을 사용해 총 익스포저를 0.3~1.0 범위에서 스케일  
    - **ETF 매매 금지**

### (2) 게이트
- 보유 종목 수가 범위 밖이면 FAIL.
- 섹터 정책 위반이면 FAIL.
- ETF 거래가 발생하면 FAIL(지표 전용).

### (3) 기대 관측치
- 익스포저가 장기간 0에 붙거나(미진입) 과도하게 고정되는 현상 완화.
- 챔피언이 특정 종목/기간에 과도 의존하는 패턴 감소.

# 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 명령형 트리
아래를 위에서부터 순서대로 실행(상단일수록 누수/운영 문제 가능성이 큼).

## A. 트리거(신호가 발생하는가?)
- 신호(스코어) 분포를 날짜별로 저장하고, **0/상수/클리핑** 여부를 검사하라.
- 상위 20%/하위 20%의 종목이 **매일 동일**한지(정렬이 고착) 확인하라.
- 신호가 “가끔만” 움직이면, 해당 날짜의 입력 피처 결측/리샘플링 오류를 의심하고 E1/E4로 추적하라.

## B. 적용(신호→타겟 포지션 변환이 정상인가?)
- 스코어→가중치 변환 후 `sum(|delta_w|)`가 0에 가까운 날이 지속되면:
  - 포지션 제약이 과도한지,
  - 리밸런스 트리거(예: threshold)가 너무 큰지,
  - rounding/lot-size 처리로 모두 0이 되는지 점검하라(E5/E1).

## C. 노출(포트폴리오가 시장에 노출되는가?)
- `exposure` 시계열이 0 또는 특정 값(현재 0.84 근처)으로 **붙는 구간**을 찾아:
  - 현금화 규칙/리스크오프 규칙이 상시 발동하는지,
  - 섹터/종목 수 제약 때문에 편입 불가 상태인지 확인하라(E5).

## D. 비용(거래가 성과를 먹는가?)
- 날짜별 `gross_pnl` vs `cost`를 분리 로그로 저장하고,
- `cost/gross_pnl` 비율이 특정 구간에서 폭증하면:
  - 회전율 상한/최소 홀딩기간을 켜고(E3),
  - 잔거래(미세 delta_w) 컷오프를 적용하라(E3).

## E. 레짐(시장 국면에서 신호가 죽는가?)
- ETF는 **지표로만** 사용해 레짐 태깅을 만들고(예: XLK 상대강도, SPY 추세, 변동성 proxy),
- 레짐별 성과를 분해하라:
  - “레짐 A에서만 작동”이면 익스포저 스케일링(E5)로 국면 적응 실험을 돌려라.
  - 전 레짐에서 동일하면 신호 자체가 약하거나 과최적화였을 가능성이 크니 E2/E4 우선.

## 운영상 실행 순서(48시간)
1. **E1 먼저 적용 후 전 실험 재런**(재현/관측 없으면 어떤 결론도 무의미)
2. **E2로 degenerate folds 0** 만들기
3. **E3로 비용 포함 성능/회전율 게이트** 적용
4. **E4로 PTI/서바이버십 교정**
5. **E5로 8~14개/섹터/노출 정책 고정 + ETF 레짐 스케일** 적용

위 5개가 통과되면, 그 다음에야 “알파(신호) 개선” 작업을 하는 게 비용 대비 효율이 가장 좋다.
