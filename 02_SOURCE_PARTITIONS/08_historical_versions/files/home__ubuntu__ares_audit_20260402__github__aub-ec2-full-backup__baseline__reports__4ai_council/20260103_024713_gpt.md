아래는 **다음 24~48시간**에 바로 넣어 돌릴 **우선순위 TOP5(코드/아키텍처/전략)**이며, 전체 제안은 **실행 가능한 패치/실험 5개(E1~E5)**로만 제한한다. 각 항목은 **(a) 필요성 (b) 위험 (c) 최소 실험(=E1~E5 중 매핑, 각 실험 내 2~3개 변형 run) (d) PASS 조건**을 포함하고, **48시간 자동 루프** 형태로 작성한다.  
(우선 점검: **누수/과최적화/서바이버십/비용 미반영/운영 리스크**)

## TOP1) 누수/시간정렬/폴드 퇴화(degenerate_folds) 제거 (가장 먼저)
### (a) 왜 필요한지
- 현재 **degenerate_folds: [1,2,3,8]**는 “학습/검증 분할이 사실상 무의미”하거나 “표본이 깨짐/누수/피처 결측 처리 버그” 가능성이 높다.
- OOS mean이 높게 보여도 **시간 누수(lookahead)**면 48시간 루프에서 재현 불가.

### (b) 위험/부작용
- 단기 성능 급락 가능(정상화).
- 데이터 손실(embargo/purge)로 학습 표본 감소 → 분산 증가.

### (c) 최소 실험 (E1 사용)
- **E1-RunA:** 기존 split 그대로 + “누수 센티넬(Leakage Sentinel) 검사만 추가” (성능은 건드리지 않음, 진단 목적)
- **E1-RunB:** **Purged/Embargo TimeSeries split**로 교체 (예: lookback window와 동일/혹은 1~5 trading days embargo)
- **E1-RunC:** “라벨/피처 time alignment 강제(assert)” + shift 검증(예: 모든 피처 timestamp ≤ 주문결정 시각)

### (d) PASS 조건
- degenerate_folds **0개**
- 누수 센티넬 경고 **0건**
- OOS mean이 하락하더라도(정상), **OOS min이 안정(극단 음수 완화)** 또는 **분산 감소**가 관측되면 통과

---

## TOP2) 비용/슬리피지/턴오버/리밸런스 로그(현재 로딩 실패) 반영
### (a) 왜 필요한지
- 지금 “Rebalance Pinpoint”가 **기본 로그 파일 로딩 실패** + 리밸런스 데이터 부재 → 비용/회전율/체결가정이 사실상 공백일 가능성.
- 비용 미반영은 가장 흔한 **과최적화 원인**.

### (b) 위험/부작용
- 성능 급락 가능(현실화).
- 거래제약 추가 시 신호가 둔화되어 알파가 줄어들 수 있음.

### (c) 최소 실험 (E2 사용)
- **E2-RunA:** 비용 0(현 상태) vs **고정 bp 비용(예: 5~15bp 왕복)**만 추가 비교
- **E2-RunB:** **슬리피지 = k * (ADV 대비 주문비율)** 단순 모델 추가
- **E2-RunC:** **턴오버 캡(예: 일 20~40% notional)** + 리밸런스 빈도(48h 루프에 맞춰 1~2일) 고정

### (d) PASS 조건
- 비용 반영 후에도 **OOS mean이 “의미 있게” 유지**(예: 20~40% 이내 하락)하면서,
- **턴오버/거래횟수/평균 비용**이 리포트에 명시되고,
- **rebalance 로그가 항상 생성/로드 성공**(실패 0건)

---

## TOP3) 노출(Exposure)·레짐·리스크 제약을 “게이트”로 승격 (운영 안정화)
### (a) 왜 필요한지
- 현재 exposure max가 **0.8388**까지 올라가는데, worst_mdd가 None인 상태는 **리스크 계측 누락** 가능성도 시사.
- 레짐(Tech risk-on/off) 변화에 따라 48시간 자동 루프가 “한 번에 무너지는” 운영 리스크가 큼.
- ETF는 매매 금지이므로 **관측지표**로만 사용해 레짐 게이트를 만들면 규칙 준수.

### (b) 위험/부작용
- 필터/게이트가 과하면 거래 기회 감소.
- 잘못된 레짐 신호는 알파를 차단.

### (c) 최소 실험 (E3 사용, ETF는 지표만)
- **E3-RunA:** 변동성 타겟(예: 10~15% 연환산) + 포지션 스케일링
- **E3-RunB:** 레짐 지표(관측): **XLK/XLV 비율**, **QQQ vs SPY 상대강도**, **VIX 대체지표**(가능한 내부 데이터) → risk-off면 exposure 상한 축소(예: 0.85→0.30)
- **E3-RunC:** 하드 리스크 게이트: (1) 최근 N일 손실/드로다운 임계 초과 시 신규 진입 금지 (2) 갭리스크 큰 이벤트일(실적)엔 사이즈 절반

### (d) PASS 조건
- worst_mdd가 **항상 계산**되고, 리스크 게이트가 발동한 날/횟수가 로그로 남음
- OOS min(꼬리)이 개선되거나, 동일 수익이면 **MDD/변동성**이 개선
- “리스크오프 구간”에서 exposure가 자동으로 내려가는 것이 관측됨

## TOP4) 서바이버십/유니버스 고정(8~14) + Tech/Healthcare 집중 검증
### (a) 왜 필요한지
- 자동화 루프에서 유니버스가 흔들리면 **서바이버십/선택편향**이 들어가기 쉽다.
- “미국주식 only, Tech+Healthcare 중심 8~14”를 **코드 레벨로 고정**해야 재현성과 운영이 산다.

### (b) 위험/부작용
- 종목 수가 줄면 알파가 특정 종목에 과의존.
- 고정 유니버스가 특정 기간에 불리할 수 있음.

### (c) 최소 실험 (E4 사용)
- **E4-RunA:** 유니버스 고정(예시 12종) 후 재학습/재백테스트  
  - Tech: AAPL, MSFT, NVDA, GOOGL, AMZN, META, AVGO, ORCL  
  - Healthcare: LLY, UNH, JNJ, MRK  
  (ADR/해외상장/ETF 제외 준수)
- **E4-RunB:** 위 12종에서 **Tech 8 + Healthcare 4 고정 비중 제약(섹터 쏠림 방지)**만 추가
- **E4-RunC:** “데이터 무결성”: delist/split/dividend 처리(미래정보 금지) 검증 플래그 ON

### (d) PASS 조건
- 유니버스가 백테스트 전 기간 동안 **완전 고정**(변동 0)
- corporate action 반영이 **미래정보 없이** 처리되었음을 로그로 증명
- 성능이 떨어져도 **재현성(동일 시드/동일 입력 → 동일 결과)**이 확보되면 통과

## TOP5) 운영 리스크(아티팩트/해시/로그/스키마) 제거: “조용한 실패” 금지
### (a) 왜 필요한지
- 현재 **lane_hash/run_hash None**, rebalance pinpoint가 **파일 포맷/경로 문제로 실패**.  
  → 자동 루프에서 “좋아 보이는 결과”가 사실은 **로그 미생성/로드 실패/기본값 fallback**일 수 있다.
- 운영 안정성이 없으면 어떤 전략 개선도 의미가 없다.

### (b) 위험/부작용
- 초기에 실패가 더 많이 드러남(정상). 파이프라인이 자주 멈출 수 있음.
- 로그/검증 추가로 실행 시간 증가.

### (c) 최소 실험 (E5 사용: 코드/아키텍처 패치 검증)
- **E5-RunA:** 모든 실행에 대해 `run_hash = hash(config+code_version+data_snapshot)` 강제 + 결과 메타데이터 저장
- **E5-RunB:** 리밸런스 로그를 **CSV/JSONL 중 하나로 표준화**하고, 로더는 둘 다 지원(현재 “Expecting value”류 실패 제거)
- **E5-RunC:** “실패 게이트”: (1) rebalance 로그 없음 (2) worst_mdd None (3) degenerate_folds>0 이면 **자동 FAIL** 처리(성능값 저장 금지)

### (d) PASS 조건
- 48시간 동안 모든 run이 **(1) 해시 존재 (2) 로그 로드 성공 (3) 필수 리포트 생성**을 만족
- 실패 시 조용히 넘어가지 않고 **명시적 FAIL**로 루프가 상태를 남김

# 48시간 자동 루프 (명령형 체크리스트)
아래 순서로 5개 실험만 돌리고, 각 실험은 “정의→게이트→기대 관측치”를 만족해야 다음으로 진행.

## E1) Purge/Embargo + Leakage Sentinel
1) **실험 정의:** Purged time split + embargo + 피처/라벨 타임정렬 assert + leakage sentinel 리포트 저장  
2) **게이트:** degenerate_folds==0 AND leakage 경고==0  
3) **기대 관측치:** OOS mean 변동(보통 하락) + OOS min/분산 안정화, fold별 성능 편차 감소

## E2) 비용/슬리피지/턴오버 캡 + 리밸런스 로그 표준화(성능 관점)
1) **실험 정의:** 고정 bp + ADV 기반 슬리피지 + turnover cap을 단계적으로 켬  
2) **게이트:** rebalance 로그 로드 성공 AND 비용/턴오버 리포트에 숫자 노출  
3) **기대 관측치:** gross→net 격차가 생기며, turnover 과다 전략이 자연스럽게 약화/퇴출

## E3) 레짐(ETF는 지표만) + 노출 상한/변동성 타겟
1) **실험 정의:** XLK/XLV, QQQ/SPY, 변동성 지표로 risk-off 구간 exposure 축소 + vol targeting  
2) **게이트:** exposure가 레짐에 따라 실제로 변하는지(로그로 검증), worst_mdd 계산 필수  
3) **기대 관측치:** OOS min 개선 또는 MDD 개선, 리스크오프에서 손실 꼬리 완화

## E4) 유니버스 고정(Tech+Healthcare 8~14) + 서바이버십 방지
1) **실험 정의:** 12종 고정 유니버스에서만 학습/거래, corporate action/결측 처리 검증 플래그 ON  
2) **게이트:** 전 기간 유니버스 변동 0, 데이터 무결성 체크 통과  
3) **기대 관측치:** 성능 변동이 있더라도 결과 재현성 증가, 특정 종목 편향/누수 신호 감소

## E5) 운영 안정화: 해시/스키마/필수 산출물 강제 + Fail Fast
1) **실험 정의:** run_hash/lane_hash 생성 강제, 로그 포맷 표준화, 필수 리포트 없으면 FAIL  
2) **게이트:** 48시간 동안 silent failure 0건(모든 실패는 FAIL로 기록)  
3) **기대 관측치:** “성능이 안 움직이는 이유”가 로그에서 즉시 드러나며 디버깅 시간 단축

# 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래를 **리포트/로그에 강제 출력**해서, 어디에서 막히는지 즉시 분해한다.

## 1) Trigger(신호 발생) 문제
- 신호 발생 빈도(일별/주별), 상위/하위 퍼센타일 신호 값 분포
- “신호가 0으로 뭉침/클리핑” 여부
- fold별 신호 분포 차이(한 fold만 이상하면 분할/누수 의심)

## 2) Apply(주문 적용) 문제
- 신호→목표비중→실제체결비중 단계별로 **숫자** 저장
- 포지션이 목표를 못 따라가면: 최소주문단위/현금부족/제약조건(턴오버 캡) 때문에 “막힘”인지 표시
- 리밸런스 발생 횟수, 주문이 스킵된 이유 코드(제약/게이트/데이터결측)

## 3) Exposure(노출) 문제
- gross/net exposure 타임시리즈
- 종목별 기여도(PnL attribution)와 상위 3개 종목 쏠림도
- 섹터(Tech vs Healthcare) 노출이 의도대로 유지되는지

## 4) Cost(비용) 문제
- gross PnL vs cost vs net PnL 분해
- turnover 대비 비용 민감도(비용 5/10/15bp에서 기울기)
- ADV 대비 주문비율 분포(슬리피지 폭탄 구간 확인)

## 5) Regime(레짐) 문제
- XLK/XLV, QQQ/SPY(지표) 구간별 성과를 분리 출력: risk-on vs risk-off
- 레짐별로 “신호 품질(IC, hit rate)”이 달라지는지
- 레짐 게이트가 너무 자주 발동해 기회를 제거하는지(발동률)

---

## 실행 우선순위(24~48h)
1) **E5(운영 Fail Fast) → E1(누수/폴드) → E2(비용) → E3(레짐/노출) → E4(유니버스)** 순으로 고정 실행  
2) 어떤 실험이든 **게이트 FAIL이면 성능 비교/챔피언 교체 금지**(로그/데이터 문제를 성능 문제로 착각하는 리스크 차단)

이 5개만으로도 “성능이 안 움직이는” 문제를 **누수/분할/적용/노출/비용/레짐/운영**으로 빠르게 분해하고, 48시간 자동 루프에서 재현 가능한 개선만 남길 수 있다.
