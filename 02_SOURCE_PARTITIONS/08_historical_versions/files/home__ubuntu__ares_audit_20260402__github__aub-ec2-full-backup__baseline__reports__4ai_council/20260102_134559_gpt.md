- [ ] **서바이버십 리스크 차단**: 유니버스가 현시점 구성으로 과거에 투영되지 않도록(상장폐지/인수/티커변경 포함) 검증 로그를 남김.
- [ ] **노출/턴오버/리밸런스 빈도에 상한 게이트**: 성능이 안 움직이는 원인이 ‘포지션이 실제로 거의 안 바뀌는 것’인지 ‘너무 자주 바뀌며 비용에 상쇄되는 것’인지 먼저 분리.

# 1) 다음 24~48시간 TOP5 우선순위 제안 (코드/아키텍처/전략)

아래 TOP5는 **“실행 가능한 patch/실험 5개(총 5개만)”**로 묶어 돌리도록 구성했습니다. 각 제안은 동일한 5개 실험을 2~3개씩 재사용합니다(케이스 폭발 방지).

## TOP1) **Rebalance/주문/포지션 로그 파이프라인을 ‘단일 진실’로 고정(운영 리스크 제거)**
### (a) 왜 필요한지
- 현재 상태에서 `aub_rebalance_pinpoint`가 **base-log/cand-log 로딩 실패** → 리밸런스 데이터 부재 → “성능이 안 움직이는 이유(트리거 vs 적용 vs 노출 vs 비용)”를 **분해 불가**.
- 48시간 자동 루프에서 가장 흔한 실패 원인은 “전략”이 아니라 “아티팩트/로그 불일치”임.

### (b) 위험/부작용
- 로그 스키마 변경 시 기존 리포트/도구가 깨질 수 있음(호환 레이어 필요).
- 디스크/IO 비용 증가(압축/샘플링 필요).

### (c) 최소 실험(아래 공통 실험 중 선택)
- **E1**(필수), **E5**, (옵션) **E2**

### (d) PASS 조건
- 모든 run에서 아래가 **항상 생성**되고 도구가 **무에러 로드**:
  - `rebalance.jsonl`(주문/체결/목표비중/실현비용 포함)
  - `positions_daily.parquet`(종가 기준 보유/노출)
  - `costs_daily.parquet`
- `aub_rebalance_pinpoint.py`가 base/cand 모두에서 **pinpoint report 생성 성공**.

## TOP2) **누수/과최적화(시간정렬·embargo·fold 퇴행) 자동 차단**
### (a) 왜 필요한지
- “성능이 안 움직임”은 종종 **(1) 누수 제거로 진짜 성능이 낮아졌거나**, **(2) fold가 퇴행/degenerate로 학습이 실질적으로 동일**해져 변화가 사라진 경우.
- 특히 리밸런스 기준시점(예: T close vs T+1 open) 혼동은 OOS를 고정시켜버리는 대표 원인.

### (b) 위험/부작용
- 누수 제거 후 성능이 단기적으로 하락할 수 있음(하지만 이 하락이 ‘진짜’).
- embargo/워크포워드 강화 시 샘플 수 감소로 분산 증가.

### (c) 최소 실험
- **E2**, **E5**

### (d) PASS 조건
- 시간시프트(+1일, +2일)에서 성능이 **급락하지 않고**(누수였다면 급락), 또는 급락 시 **누수 가능성 플래그**가 자동으로 올라감.
- `degenerate_folds`가 재발하지 않거나, 발생 시 원인(샘플 수/결측/필터링)이 리포트에 자동 기록.

## TOP3) **비용/슬리피지/턴오버 상한을 기본 스코어에 포함(‘공짜 매매’ 제거)**
### (a) 왜 필요한지
- 비용 미반영은 **과최적화 + 실전 실패**의 1순위.
- “성능이 안 움직임”이 사실 **비용 포함 시 알파가 상쇄**되어서 생기는 현상인지 먼저 확정해야 함.

### (b) 위험/부작용
- 비용 모델을 너무 보수적으로 잡으면 좋은 전략도 죽일 수 있음(하지만 이 편이 안전).
- 턴오버 캡이 알파를 깎을 수 있음(대신 실전 일관성↑).

### (c) 최소 실험
- **E3**, **E5**

### (d) PASS 조건
- 비용 ON에서 OOS mean이 비용 OFF 대비 **과도하게 붕괴하지 않음**(예: 성능의 60~80% 이상 유지 같은 내부 기준).
- 일별/주별 **turnover, 거래횟수, 비용 기여도**가 리포트에 표준 출력.
- 비용이 PnL의 주된 설명변수로 뜨면(>X%) “턴오버 캡/슬리피지 재보정” 액션이 자동 트리거.

## TOP4) **유니버스(미국 Tech+Healthcare, 8~14종목) 고정 + 노출/비중 게이트(운영가능 포트폴리오)**
### (a) 왜 필요한지
- 유니버스가 흔들리면(티커 추가/제외) 백테스트/실전 비교가 무의미해지고 서바이버십 리스크가 증가.
- 8~14 종목 고정은 “전략 변동”을 “실제 적용”으로 연결시키는 데 필요(리밸런스/비용/리스크 관리가 현실화).

### (b) 위험/부작용
- 종목 수가 적어 idiosyncratic 리스크 증가 → 변동성 타기팅/비중 상한 필요.
- 특정 대형주 쏠림(Magnificent7)로 팩터 노출이 단조로워질 수 있음.

### (c) 최소 실험
- **E4**, **E3**

### (d) PASS 조건
- 항상 **8~14개 종목** 유지(결측/거래정지 시 대체 규칙 포함).
- 단일 종목 비중 상한(예: 15~20%) 및 섹터 편중 상한이 지켜짐.
- exposure_min/max가 목표 범위에 안정적으로 머뭄(현재 0.47~0.84처럼 중途반단이면 원인 로그로 남김).

> 예시 유니버스(미국, Tech+Healthcare, 8~14):

> Healthcare: UNH, LLY, JNJ, ABBV, MRK, ISRG

## TOP5) **“성능 No-Delta”를 신호/적용/노출/비용으로 자동 분해(원인 규명 루프)**
### (a) 왜 필요한지
- 이미 “No-Delta Diagnoser”가 돌고 있으나, 현재 rebalance 로그 부재로 **적용 단계(주문/체결/노출 변화)**가 빠져 원인 규명이 반쪽.
- 성능이 안 움직일 때는 “모델이 바뀌었는데 포지션이 안 바뀜”이 가장 흔함.

### (b) 위험/부작용
- 분해 지표가 많아지면 운영 복잡도 증가 → **핵심 6~8개 KPI만 고정**해야 함.
- 잘못된 어트리뷰션(예: 비용을 가격변동으로 오인) 위험 → 로그 스키마 정합이 선행되어야 함.

### (c) 최소 실험
- **E5**, **E1**, (옵션) **E2**

### (d) PASS 조건
- 각 run마다 아래 분해가 **자동 출력**되고, “변화 없음”일 때 원인이 1~2개로 수렴:
  - Signal 변화(예측/스코어 분포)
  - 적용 변화(목표비중 변화량, 거래 발생 여부)
  - 노출 변화(gross/net, top weights)
  - 비용 변화(슬리피지/스프레드/수수료)
  - 레짐 변화(변동성/금리/섹터 상대강도)

# 2) 48시간 자동 루프용 “실행 가능한 Patch/실험” 5개 (정의/게이트/기대 관측치)

## E1) Rebalance 로그/아티팩트 스키마 고정 패치
- **(1) 실험 정의**
  - 백테스트/리밸런스 실행 시 아래를 필수 생성:
    - `rebalance.jsonl`: timestamp, universe, target_w, prev_w, trade_qty, fill_px, est_slippage_bps, fee, reason_code
    - `rebalance.csv`: 요약(턴오버/거래수/비용/상위 변경 종목)
  - 도구(`aub_rebalance_pinpoint.py`) 입력 경로를 “옵션 문자열”이 아니라 “실제 파일경로”로 강제(현재 `--base-log`가 파일로 해석되는 형태의 실패 차단).
- **(2) 게이트**
  - 파일 생성 0개면 run을 **FAIL** 처리(리포트 생성 중단).
  - JSONL 파싱 실패 시 스키마/샘플 5줄을 stderr에 출력하고 FAIL.
- **(3) 기대 관측치**
  - pinpoint report가 매 run 생성
  - “거래가 없어서 no-delta” vs “거래는 있었는데 성과가 0”이 분리됨

---

## E2) 누수/시간정렬 방지: +1D/+2D shift & embargo A/B
- **(1) 실험 정의**
  - 동일 파이프라인에서:
    - A: 원본
    - B: 피처를 **+1일 지연**
    - C: 피처를 **+2일 지연**
  - 워크포워드 split에 embargo(예: 5~10 trading days) 적용 버전도 병행(단 하나의 설정으로 고정).
- **(2) 게이트**
  - B/C가 A보다 “말도 안 되게” 좋아지면(임계치 초과) **누수 경보**.
  - A가 B/C 대비 극단적으로 좋으면(급락) 역시 누수/시점오류 의심 플래그.
- **(3) 기대 관측치**
  - 정상이라면 A≈B(소폭 하락)이고 C는 추가 하락
  - 누수라면 shift에서 성능이 붕괴하거나 반대로 비정상 패턴 발생

---

## E3) 비용/슬리피지 ON + 턴오버 캡 스트레스
- **(1) 실험 정의**
  - 고정 비용 모델(보수적으로 시작):
    - 슬리피지: `k * daily_vol` 또는 고정 bps(예: 5~15bps) + 스프레드 절반
    - 수수료: 주당/거래당
  - 턴오버 캡: 일/주 단위 상한(예: 일 20%, 주 60%)을 걸어 목표비중을 스무딩.
- **(2) 게이트**
  - 비용 ON 성과가 OFF 대비 일정 비율 미만이면 FAIL(내부 기준).
  - 턴오버가 캡을 반복적으로 치면 “신호 과민/스케일 과다” 플래그.
- **(3) 기대 관측치**
  - 비용 기여도(음수)가 리포트에 분리 표기
  - 성능이 안 움직이던 케이스가 “비용에 먹힘”인지 즉시 판별

---

## E4) 유니버스 고정(8~14 Tech+Healthcare) + 비중/노출 게이트
- **(1) 실험 정의**
  - 유니버스를 위 예시처럼 10~12개로 고정하고(ETF 매매 금지), 결측 시 대체 규칙을 코드화.
  - 제약:
    - 종목당 max weight
    - 섹터(Tech/Healthcare) 비중 범위
    - gross/net 노출 목표 범위(예: gross 0.6~0.9 고정)
- **(2) 게이트**
  - 종목 수가 8 미만 또는 14 초과면 FAIL
  - 단일 종목 비중 상한 위반 시 FAIL
- **(3) 기대 관측치**
  - 포지션 변화가 해석 가능해지고(항상 같은 종목군), no-delta 원인(적용/비용)이 선명해짐

## E5) No-Delta 원인 분해 리포트(트리거→적용→노출→비용→레짐)
- **(1) 실험 정의**
  - 매 run마다 아래 KPI 테이블을 **고정 포맷**으로 출력:
    - signal drift(예측 상관/분포 변화)
    - target turnover / realized turnover
    - trade count / notional
    - gross/net exposure, top-5 weights
    - cost breakdown(슬리피지/스프레드/수수료)
    - regime proxies(ETF는 관측만: XLK/XLV 상대강도, VIX, 10Y 등)
- **(2) 게이트**
  - “성능 변화 미미”인데도 `target turnover`가 큰데 `realized turnover`가 0이면 **적용/체결 버그**로 FAIL 플래그.
  - signal drift가 거의 0인데 모델이 바뀌었다면 **파라미터 적용 누락** 플래그.
- **(3) 기대 관측치**
  - 성능 No-Delta가 아래 중 하나로 자동 분류:
    1) 신호가 안 변함(학습/피처/파라미터 적용 문제)
    2) 신호는 변했는데 거래가 안 남(게이트/리밸런스 로직/로그 버그)
    3) 거래는 있는데 비용이 상쇄(비용/턴오버 문제)
    4) 레짐 변화로 알파 무력화(레짐 문제)

# 3) “성능이 안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 실행용 트리

아래는 **질문 없이** 바로 자동 판별 로직으로 옮길 수 있는 분해 트리입니다.

## A. 트리거(신호 생성) 단계
- [ ] **Signal drift**: 예측값/스코어 분포(평균·표준편차), 상위/하위 분위 스프레드, 전일 대비 rank 상관(ρ)
- [ ] **파라미터 적용 여부**: run_hash 바뀌었는데 signal summary가 동일하면 “config 미적용/캐시 재사용” 의심
- [ ] **시간 정렬 검사**: +1D shift 실험(E2)에서 성능 패턴이 비정상이면 누수/시점오류

## B. 적용(포트폴리오 변환/리밸런스) 단계
- [ ] **Target turnover vs Realized turnover** 갭:
  - target 큼 + realized 0 → 리밸런스 실행 누락/게이트 과도/체결 로직 버그
  - target 0 → 신호가 포트폴리오로 매핑되지 않음(스케일=0, 클리핑 과도)
- [ ] **리밸런스 빈도/스케줄**이 실제로 호출되는지(캘린더/휴장 처리 포함)

## C. 노출(Exposure) 단계
- [ ] gross/net 노출이 고정값에 붙어 있으면(예: 항상 0.50 근처) **게이트가 모든 변화를 죽이는지** 확인
- [ ] 상위 1~2종목 비중이 과도하면 “실질적으로 단일 베팅”이라 성능이 레짐에 종속

## D. 비용 단계
- [ ] 거래 발생 시점에 비용이 PnL의 대부분을 설명하면:
