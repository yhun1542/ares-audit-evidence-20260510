아래는 **다음 24~48시간**에 바로 돌릴 수 있게, **누수/과최적화/서바이버십/비용 미반영/운영 리스크**를 최우선으로 잡는 **명령형 체크리스트**다. (미국주식 only, **Tech+Healthcare 중심 8~14종목**, ETF는 **관측지표로만** 사용)

---

## TOP5 우선순위 제안 (코드/아키텍처/전략)

### 1) **운영 리스크 제거: 실험/리밸런스 로깅·아티팩트 파이프라인 복구**
- **왜 필요한지**
  - 현재 로그에서 `aub_rebalance_pinpoint`가 **입력 파일을 못 읽음**(base-log/cand-log 경로 및 포맷 오류) → “무슨 변화가 성능을 만들었는지”를 추적 불가.
  - `lane_hash/run_hash=None`, `worst_mdd=None` → 실험 재현성/리스크 평가가 끊겨 **서바이버십(좋은 결과만 남는) 운영 오류**로 이어짐.
- **위험/부작용**
  - 전략 성능은 그대로인데 “보이는 지표”만 바뀔 수 있음(실제로는 필수).
  - 로깅 I/O 증가로 런타임 소폭 증가.
- **최소 실험(재사용 ID)**
  - **[E1] 리밸런스 로그/메타데이터 강제 생성 패치**
  - **[E2] MDD/노출/턴오버 등 리스크 메트릭 계산 강제 패치(누락 시 실패 처리)**
- **PASS 조건**
  - (게이트) `rebalance.csv 또는 rebalance.jsonl`이 **항상 생성**되고 `aub_rebalance_pinpoint.py`가 **0 error**로 diff 리포트 생성.
  - (게이트) 모든 run에 `run_hash/lane_hash` 채워짐, `worst_mdd`가 None이 아님.
  - (관측) “성능 변화 없음” 실험에서도 **리밸런스 횟수/턴오버/비용/노출**이 추적 가능해짐.

---

### 2) **과최적화/데이터 문제 최우선: degenerate fold 제거 + 워크포워드 검증 강화**
- **왜 필요한지**
  - `degenerate_folds: [1,2,3,8]`는 CV가 깨졌거나(빈 폴드/거래 0/라벨 편향) **OOS mean이 의미 없을 수 있음**을 시사.
  - 이런 상태에서 파라미터 튜닝은 대부분 “움직이지 않거나(노-델타)” 또는 “가짜 개선”로 끝남.
- **위험/부작용**
  - 폴드 강화 후 OOS가 일시적으로 나빠질 수 있음(그게 정상; 기존이 과대평가였을 수 있음).
  - 트레이드 수가 줄어 분산이 커질 수 있음(대신 신뢰도↑).
- **최소 실험**
  - **[E3] 폴드 유효성 게이트 도입(거래수/표본수/기간 최소치) + 실패 시 재샘플/스킵**
  - **[E4] Purged/Embargo 적용(룩어헤드·근접 누수 차단) + 워크포워드 고정**
- **PASS 조건**
  - (게이트) `degenerate_folds == []` (또는 허용 0~1개 이하)로 수렴.
  - (게이트) 각 폴드에서 최소 거래수/리밸런스 수 충족(예: fold당 리밸런스 ≥ N).
  - (관측) OOS mean이 다소 하락해도 **oos_min(최악 폴드)**가 안정(급락 완화), 성능 분산 감소.

---

### 3) **비용 미반영 제거: 슬리피지/스프레드/턴오버/차입(공매도) 비용을 “게이트”로 승격**
- **왜 필요한지**
  - 현재 `exposure_max≈0.84`이고 리밸런스 로그도 불명 → 실제로는 턴오버/체결비용이 성능을 잡아먹는데, 모델은 “수익이 안 움직이는(no-delta)” 형태로 보일 수 있음.
  - Tech/Healthcare 8~14종목 집중이면 종목별 스프레드/유동성 차이가 크고, 비용 민감도가 성능을 지배할 확률이 큼.
- **위험/부작용**
  - 비용을 올리면 백테스트 성능이 감소(정상). 대신 실거래 괴리↓.
  - 비용 모델이 과도하면 알파가 과소평가될 수 있음(민감도 실험으로 방지).
- **최소 실험**
  - **[E5] 비용 민감도 스윕(슬리피지/스프레드/수수료 배수 0.5x~2x) + 성능/턴오버 탄력성 측정**
  - **[E2 재사용] 턴오버/비용/체결가정 리포트 누락 시 런 실패**
- **PASS 조건**
  - (게이트) 비용 1.5x에서도 OOS mean이 **심각 붕괴하지 않음**(예: 1.5x에서 OOS mean ≥ 0.7×baseline).
  - (관측) 성능이 안 움직이던 실험들이 “턴오버/비용 차이”로 분해되어 원인이 보임(수익률 대신 비용이 변하고 있었는지 확인).

---

### 4) **노출/집중/유동성 리스크: 8~14종목 포트폴리오 운영 제약을 코드로 고정**
- **왜 필요한지**
  - `exposure_min/max: 0.0 / 0.8388` → 현금화 구간 존재 + 최대 노출이 꽤 큼.  
    성능 정체가 “신호”가 아니라 “노출이 안 실림/갑자기 줄어듦”에서 올 수 있음.
  - 소수종목에서 유동성/갭/실적 이벤트에 취약 → 운영 리스크.
- **위험/부작용**
  - 제약 강화로 알파 일부 손실 가능.
  - 너무 타이트하면 거래가 줄어 OOS 분산 증가.
- **최소 실험(기존 E2/E5와 같이 관측)**
  - **[E2 재사용] 노출/섹터/단일종목 비중/현금비중 리포트 의무화**
  - **[E5 재사용] 비용 민감도와 함께 “턴오버 캡/리밸런스 최소 변화량(Δw)” 적용 시나리오 포함**
- **PASS 조건**
  - (게이트) 단일 종목 비중 상한, 최소 8~최대 14종목 유지, 평균 거래대금/스프레드 필터 통과(운영 가능성).
  - (관측) OOS mean이 크게 변하지 않더라도 **oos_min 개선** 또는 **worst_mdd 개선**(계산이 가능해졌다는 전제).

---

### 5) **레짐(시장 상태) 반영: ETF를 “트리거 지표”로만 써서 온/오프(또는 노출 스케일)**
- **왜 필요한지**
  - Tech/Healthcare는 레짐 의존이 큼. “항상 같은 방식”이면 특정 구간에서 신호가 죽고 **no-delta**로 보일 수 있음.
  - ETF는 거래하지 않되(규칙 준수), **XLK/XLV/QQQ/SMH/IHI** 등을 관측지표로 사용해 리스크 온/오프를 분기하면, 포트폴리오가 **불필요한 노출을 줄여 MDD/최악폴드**를 개선할 여지가 큼.
- **위험/부작용**
  - 레짐 규칙이 과적합되면 OOS에서 악화.
  - 너무 자주 on/off면 턴오버/비용 증가.
- **최소 실험(추가 폭발 방지: 기존 E3/E4 게이트 위에서만)**
  - **[E3 재사용] 레짐별 폴드 성능 분해 리포트(폴드/구간 태깅)**
  - **[E5 재사용] 레짐 on/off에 따른 비용·턴오버 변화 동시 측정**
- **PASS 조건**
  - (게이트) 레짐 필터가 “진입/이탈 빈도 상한” 만족(예: 월 X회 이하).
  - (관측) OOS mean이 동일해도 **oos_min(최악 구간)** 또는 **worst_mdd**가 유의미하게 개선.

---

## 48시간 자동 루프용 “실행 가능한 Patch/실험” 5개 (케이스 폭발 방지)

아래 5개만 돌려도 위 TOP5의 핵심을 커버하도록 **재사용**으로 구성했다.

### [E1] 리밸런스 로그 표준화 패치
1) **실험 정의**
   - 모든 백테스트 run 종료 시 `rebalance.csv`와 `rebalance.jsonl`을 **동시에** 내보내고, 스키마 고정(시간, 티커, 목표비중, 체결비중, 가격, 수수료, 슬리피지 가정, turnover).
2) **게이트**
   - 파일 미생성/JSON 파싱 실패/빈 파일이면 run 실패 처리.
3) **기대 관측치**
   - `aub_rebalance_pinpoint.py`에서 base/cand diff가 즉시 생성되고, “성능 무변화”의 원인이 리밸런스/턴오버/노출인지 분해 가능.

### [E2] 필수 리스크 메트릭 계산 + 누락 시 실패
1) **실험 정의**
   - `worst_mdd`, `max_gross/net`, `cash_ratio`, `turnover`, `cost_drag`를 표준 산출하고 아티팩트에 저장. None이면 실패.
2) **게이트**
   - `worst_mdd is None` 또는 `run_hash/lane_hash None`이면 실패.
3) **기대 관측치**
   - “챔피언 성능”이 아니라 “챔피언의 리스크 형태”가 고정 포맷으로 남아, 서바이버십/운영 오류 방지.

### [E3] degenerate fold 제거 게이트(거래/표본 최소치)
1) **실험 정의**
   - 폴드별 최소 거래수/리밸런스 수/유효일수 미달이면 해당 폴드는 무효 처리하고 스플릿을 재구성(또는 전체 run 실패).
2) **게이트**
   - `degenerate_folds` 발생 시 즉시 실패(허용치 0).
3) **기대 관측치**
   - OOS mean이 일시 하락해도 신뢰도↑, 실험 간 비교가 가능해져 “no-delta”가 실제인지 확인 가능.

### [E4] Purged/Embargo 워크포워드(누수 차단)
1) **실험 정의**
   - 피처/라벨 생성 시점 기준으로 purge window + embargo를 적용해 근접 누수 제거.
2) **게이트**
   - purge/embargo 적용 후에도 폴드 유효성(E3) 통과 못 하면 실패.
3) **기대 관측치**
   - 진짜 알파면 유지, 가짜 알파면 붕괴(빠르게 누수 여부 판별).

### [E5] 비용 민감도 + 턴오버 캡 동시 스윕(작게)
1) **실험 정의**
   - 슬리피지/스프레드/수수료 배수 {0.5, 1.0, 1.5, 2.0} × (턴오버 캡 on/off 또는 Δw 최소변화량 on/off) **총 4~8개 이내**로 제한.
2) **게이트**
   - 비용 1.5x에서 성능이 0으로 붕괴하면(예: OOS mean이 baseline의 50% 미만) 해당 전략군 중단.
3) **기대 관측치**
   - 성능 정체가 “알파 부재”인지 “비용/턴오버가 먹는지”가 즉시 갈림.
   - 실거래 가능 파라미터(턴오버·비용 내성)만 남김.

## 성능이 안 움직일 때(“no-delta”) 원인 분해 아이디어: 트리거/적용/노출/비용/레짐

아래 트리를 **리포트 템플릿으로 고정**해서, 48시간 루프가 자동으로 원인을 찍어내게 만들어라.

### A) Trigger(신호가 실제로 변하나?)
- **체크**: 예측 스코어 분포(평균/분산/상위10% 점유), 랭크 상관(전일 대비), 신호 엔트로피.
- **증상**: 스코어 분산이 거의 0 → 모델이 사실상 상수 출력(피처 깨짐/스케일링/결측 처리 문제).

### B) Apply(신호가 포지션으로 제대로 적용되나?)
- **체크**: 목표비중→체결비중 편차, 제약으로 인한 컷 비율(clip rate), 리밸런스 트리거 발생률.
- **증상**: 신호는 움직이는데 포지션이 안 변함 → 제약/버그/리밸런스 로직 문제.

### C) Exposure(노출이 원하는 대로 실리나?)
- **체크**: gross/net, 현금비중, 상위 종목 편중, 섹터(Tech/Healthcare) 유지율.
- **증상**: 성과 정체 + 노출이 0 근처로 자주 떨어짐 → “안 하는 전략”이 되어버림(게이트/레짐/리스크 컷 과도).

### D) Cost(비용이 수익을 상쇄하나?)
- **체크**: turnover, 비용 드래그(%), 거래당 기대 엣지 대비 비용 비율(edge-to-cost).
- **증상**: 총수익은 비슷한데 순수익만 정체 → 비용 모델 반영 시 바로 드러남(E5).

### E) Regime(특정 구간에서만 먹나?)
- **체크**: 구간 태그(고변동/저변동, 금리급등, 나스닥 추세)별 성능 분해.
- **증상**: 전체 OOS mean은 정체인데 최악 구간이 반복 → 레짐 오버레이로 최악폴드(oos_min)/MDD 개선 여지.

---

### 최종 실행 순서(24~48h)
1) **E1→E2를 최우선 적용**(운영·재현성 복구가 먼저).
2) 그 다음 **E3→E4로 CV/누수 리스크 확정 제거**.
3) 마지막으로 **E5로 비용/턴오버 내성 확인**(여기서 살아남는 것만 다음 사이클로).

이 5개가 통과되면, 그때부터 “전략 알파 개선” 튜닝이 의미가 생긴다. 지금 상태에서는 먼저 **측정·재현·검증이 가능한 시스템**으로 만드는 게 수익 개선보다 우선이다.
