## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — 명령형 체크리스트

### 1) **누수/지표 불일치부터 “즉시 차단” (Leakage + Metric Parity)**
- **해야 할 일**
  - `Champion OOS Mean: 2.6276`(Diagnoser) vs `Current Champion oos_mean: 1.8815`(HANDOFF) **불일치 원인**을 “같은 입력/같은 스코어러/같은 기간”으로 정렬해 재현.
  - 모든 피처/라벨 조인에 대해 **as-of(시점 고정) 검증**을 자동화(미래 데이터 참조 탐지).
  - **서바이버십**(상장폐지/티커변경/합병) 반영 여부를 유니버스 레벨에서 강제 체크.
- **(a) 왜 필요한지**
  - 성능이 “안 움직임”의 1순위 원인이 **(1) 실제로는 개선됐는데 지표가 달라서 못 보거나 (2) 누수로 과대평가 후 OOS에서 평평해지는 것**임.
- **(b) 위험/부작용**
  - 누수 차단 시 OOS가 단기 하락할 수 있음(정상).
  - 과거 실험 기록과 호환 깨질 수 있음(스코어 정의/기간 정렬로 인한).
- **(c) 최소 실험 2~3개 (공용 실험 재사용: E1)**
  - **E1-a (Parity Replay)**: 동일 run_hash 조건으로 runner/diagnoser가 산출하는 `oos_mean/oos_min` 차이 로그 출력.
  - **E1-b (As-of Sentinel Test)**: 랜덤 날짜 t에서 피처 계산이 t 이후 바를 참조하면 즉시 실패(피처별 “최대 참조 시점” 기록).
  - **E1-c (Survivorship Delta)**: “현재 유니버스” vs “당시점 유니버스”로 백테스트 1회씩 돌려 수익률 갭/종목 수 변화를 리포팅.
- **(d) PASS 조건**
  - Parity: 동일 입력에서 `|oos_mean_runner - oos_mean_diag| < 1e-6` (또는 허용오차 명시) 달성.
  - As-of: 누수 플래그 0건.
  - Survivorship: 유니버스 정의 변경 시 성과 급변(예: OOS mean 20%+ 점프) 발생하면 **실패로 간주하고 원인 수정**.

### 2) **비용/리밸런스 텔레메트리 복구 (비용 미반영 + 리밸런스 로그 파손)**
- **해야 할 일**
  - 현재 에러: `--base-log` 파일 없음 + `rebalance.csv` JSON 파싱 실패 + “No rebalance data found” → **리밸런스 로그 포맷/경로를 단일화**.
  - 백테스트 결과에 **turnover, fills, spread/impact, borrow(쇼트면), 수수료**를 최소 모델로라도 반영.
- **(a) 왜 필요한지**
  - Tech/Healthcare는 이벤트/갭/유동성 차이로 **매매 비용이 성과를 ‘평평하게’ 만드는** 대표 케이스.
  - 리밸런스 데이터가 없으면 “왜 성과가 안 움직이는지(트리거/적용/노출)” 분해가 불가.
- **(b) 위험/부작용**
  - 비용 반영 후 성과가 내려갈 수 있음(정상).
  - 로그 스키마 변경으로 기존 분석 도구가 깨질 수 있음(버전 태그 필요).
- **(c) 최소 실험 2~3개 (공용 실험 재사용: E2)**
  - **E2-a (Schema Lock)**: `rebalance.jsonl`(권장)로 단일화하고, 각 라인에 `ts, universe_hash, orders, target_w, executed_w, turnover, est_cost_bps` 포함.
  - **E2-b (Cost Toggle A/B)**: (i) 비용 0, (ii) 고정 5~15bps, (iii) turnover 비례 비용(예: k * turnover) 3단으로 동일 기간 재생.
  - **E2-c (Pinpoint Fix)**: `aub_rebalance_pinpoint.py` 입력을 “CSV or JSONL 자동 감지”로 바꾸고, 파일 없으면 즉시 실패(조용히 통과 금지).
- **(d) PASS 조건**
  - 모든 실험 산출물에 `turnover`, `est_cost`, `net_return` 필드가 존재.
  - 비용 3단 A/B에서 **성과 민감도**가 합리적(비용↑ → 성과 단조 감소). 단조성 깨지면 비용 적용/정의 오류로 실패.
  - pinpoint 리포트가 1회 이상 정상 생성(빈 리포트 금지).

### 3) **운영/리스크 구멍 봉합: MDD가 None인 상태부터 제거 (운영 리스크 + 과최적화 방지)**
- **해야 할 일**
  - `worst_mdd: None` → MDD 계산 경로가 누락/비활성. **항상 계산/저장**하도록 강제.
  - 48시간 자동 루프에 **가드레일 게이트**를 넣어 “이익이 아니라 생존” 우선.
  - `exposure_min/max: 0.47/0.84`가 구조적으로 높은 편이면, **노출 상한/턴오버 상한**을 걸고 전략 평가를 “net-of-cost + risk”로 통일.
- **(a) 왜 필요한지**
  - 성과가 안 움직이는 동안에도 “운영 실패/리스크 폭발”은 언제든 발생.  
  - MDD 미산출은 과최적화 탐지 실패(좋아 보이는 평균 뒤에 꼬리 리스크 숨음).
- **(b) 위험/부작용**
  - 가드레일이 성과 상단을 제한할 수 있음.
  - 잘못된 리스크 계산(분모/기간)로 과도한 차단이 생길 수 있음.
- **(c) 최소 실험 2~3개 (공용 실험 재사용: E3)**
  - **E3-a (MDD Always-on)**: 모든 run artifact에 `equity_curve` 저장 + `worst_mdd` 산출 실패 시 전체 run fail.
  - **E3-b (Turnover Cap)**: `turnover <= X` 강제(예: 일/리밸런스당 20~40% 등) vs 기존 비교.
  - **E3-c (Exposure Cap + Position Cap)**: 종목별 max weight, 섹터(Tech/HC) 내 분산 제한, 총 익스포저 상한(예: 0.75) A/B.
- **(d) PASS 조건**
  - `worst_mdd`가 모든 fold/OOS 구간에서 숫자로 존재.
  - 가드레일 적용 후 `oos_min`이 악화되지 않거나(또는 악화 폭이 작은 대신) **tail-risk 지표 개선**(MDD 감소, 변동성 감소) 확인.
  - 루프에서 “리스크 계산 실패로 조용히 통과” 0건.

### 4) **레짐(국면) 기반 노출 스케일링 도입 (ETF는 관측지표로만 사용)**
- **해야 할 일**
  - 매매는 개별 미국주식(Tech+Healthcare)만 유지.
  - ETF/지표(예: QQQ, XLV, IWM, TLT, VIX류 지표)는 **‘지표 관측용 피처’로만** 사용해 레짐을 분류하고, 레짐별로 총 노출(또는 롱/숏 비율)을 스케일.
- **(a) 왜 필요한지**
  - “성능이 안 움직임”의 흔한 원인: 평균적으로는 괜찮은데 **레짐 변화에서 모델이 같은 행동을 반복**(노출이 고정에 가깝고, `exposure_max ~0.84`로 높음).
- **(b) 위험/부작용**
  - 레짐 피처가 사실상 lookback 과최적화가 될 수 있음(특히 임계값 튜닝).
  - 레짐 전환에서 whipsaw(빈번한 노출 변화)로 비용 증가 가능.
- **(c) 최소 실험 2~3개 (공용 실험 재사용: E4)**
  - **E4-a (Regime Simple 2-state)**: risk-on/risk-off를 단순 규칙(예: QQQ 추세 + 변동성)로만 정의하고, 노출을 {0.3, 0.8} 두 단계로 스케일.
  - **E4-b (Hysteresis)**: 레짐 전환에 히스테리시스(2~5일 유지 조건) 넣어 turnover 증가 억제.
  - **E4-c (Regime-aware Gate)**: 레짐별 OOS 성과를 따로 보고, 최악 레짐의 `oos_min` 개선을 1차 목표로 설정.
- **(d) PASS 조건**
  - 레짐별 분해에서 최악 레짐의 `oos_min` 개선(또는 MDD 감소)이 확인될 것.
  - 전체 `turnover`가 E2 비용모델 하에서 악화되지 않거나(혹은 개선) 설명 가능할 것.

### 5) **“트리거→적용→노출” 파이프라인을 분리해 성능 정체 원인을 강제 가시화 (아키텍처/분석)**
- **해야 할 일**
  - 신호 생성(Trigger) / 포지션 변환(Application) / 체결·비용·노출(Exposure/Cost)을 **서로 다른 로그 스트림**으로 분리 저장.
  - 각 단계에 “불변조건(invariants)”을 넣어, 성능이 평평할 때 어느 단계가 평평한지 자동 리포트.
- **(a) 왜 필요한지**
  - 지금 상태는 rebalance 로그가 비어 pin-point가 실패.  
  - 성능 정체는 보통 “신호는 움직이는데 적용에서 죽음(제약/클리핑)” 또는 “신호가 아예 안 움직임(스케일/정규화/버그)” 둘 중 하나.
- **(b) 위험/부작용**
  - 로그/아티팩트 용량 증가(비용 증가).
  - 단계 분리로 구현 복잡도 증가.
- **(c) 최소 실험 2~3개 (E2+E3에 포함되는 ‘계측 패치’로 처리)**
  - **(계측1)** Trigger 분산/영(0) 비율/상위 k 종목 집중도 저장.
  - **(계측2)** Application에서 클리핑/제약으로 잘린 비율(“원신호 대비 최종 w 감소량”) 저장.
  - **(계측3)** Exposure/Cost에서 turnover·추정비용·체결 실패(가격결측 등) 카운트 저장.
- **(d) PASS 조건**
  - 매 리밸런스마다 위 3단계 지표가 누락 없이 기록되고, “정체 원인”이 최소 1개 축으로 자동 분류됨(아래 트리거/적용/노출 분해 규칙 적용 가능).

## 48시간 자동 루프에 넣을 “실행 가능한” 공용 Patch/실험 4개 (3~5개 제한 준수)

> 아래 4개만 실제로 돌리고, TOP5 제안은 이 4개 안에서 검증/계측까지 해결.

### E1) Leakage + Metric Parity Audit
1) **실험 정의**: 동일 데이터/기간/스코어러로 runner vs diagnoser 지표 일치 + as-of 센티널 + survivorship 비교  
2) **게이트**: 지표 불일치/누수 플래그/서바이버십 급변 발견 시 이후 실험(E2~E4) 진행 금지  
3) **기대 관측치**: 불일치 원인이 (a) 기간/샘플 정의, (b) 비용/슬리피지 반영 차이, (c) 누수 중 하나로 좁혀짐

### E2) Rebalance Telemetry + Cost Model Baseline
1) **실험 정의**: rebalance.jsonl 단일 로그 + 비용 3단 A/B + pinpoint 도구 입력 자동감지  
2) **게이트**: turnover/est_cost/net_return 누락 시 실패, 빈 pinpoint 리포트면 실패  
3) **기대 관측치**: “성과가 안 움직임”이 비용/턴오버 때문인지 정량화(비용 민감도 곡선)

### E3) Risk Always-on (MDD/Exposure/Turnover Guardrails)
1) **실험 정의**: worst_mdd 강제 산출 + turnover cap + exposure/position cap A/B  
2) **게이트**: worst_mdd None 발생 즉시 실패(조용한 통과 금지)  
3) **기대 관측치**: oos_mean이 크게 안 올라가도 oos_min/MDD가 개선되면 “운영 안정화”로 다음 단계 진행

### E4) Regime-based Exposure Scaling (ETF는 관측만)
1) **실험 정의**: QQQ/XLV/IWM/TLT/VIX류 지표 기반 2-state 레짐 → 총 익스포저 스케일(주식 매매만)  
2) **게이트**: turnover 급증 + 비용 반영 후 성과 악화가 크면 중단(whipsaw)  
3) **기대 관측치**: 레짐별 최악구간 oos_min 개선 또는 MDD 감소(“평평함”을 꼬리 개선으로 깨기)

## 성능이 안 움직일 때 원인 분해 아이디어 (트리거/적용/노출/비용/레짐) — 명령형 트리아주 규칙

### A) Trigger(신호) 문제인지 확인
- **신호 분산/표준편차가 0에 수렴하는지** 확인(정규화/클리핑/결측 대체 버그 의심).
- **상위 k 종목이 매번 동일**하면(집중도 고정) 유니버스/랭킹 버그 또는 서바이버십/가격 결측 가능.
- **폴드별 신호 상관이 0.95+로 과도하게 높으면** 과최적화(또는 동일 정보 재탕) 가능.

### B) Application(제약/포트 변환)에서 죽는지 확인
- 원신호 대비 최종 가중치의 **클리핑 손실률**(잘린 총량)을 기록하고, 손실률이 높으면 제약이 알파를 제거 중.
- 리밸런스마다 **목표 w 변화량 vs 실제 변화량** 비교(적용 단계에서 변화가 막히는지).

### C) Exposure(노출) 고정/왜곡인지 확인
- `exposure_min/max`가 항상 비슷하면(예: 0.47~0.84 고정) 전략이 사실상 **항상-on 베타**일 수 있음.
- 섹터/팩터(Tech/HC 내부에서도) 노출을 분해해, 특정 서브그룹(메가캡/바이오텍) 편향이 고착됐는지 확인.

### D) Cost(비용)로 평평해지는지 확인
- 비용 0 vs 비용 on에서 **성과 차이가 대부분**이면 “알파는 있는데 비용이 먹는다” → turnover/체결 모델/리밸런스 빈도 문제.
- 반대로 비용 on/off 차이가 거의 없는데도 성과가 평평하면 비용이 원인이 아님(신호/적용/레짐 쪽).

### E) Regime(국면) 미스매치인지 확인
- 레짐별로 OOS를 분해해 **최악 레짐의 oos_min이 전체를 끌어내리는지** 확인.
- 레짐 전환 시점 주변에서 turnover가 폭증하면 레짐 필터/히스테리시스 필요.

---

### 실행 순서(중요도)
1) **E1 먼저**(누수/지표 불일치 해결 전까지 다른 개선은 “환상” 가능성 큼)  
2) **E2**(비용·리밸런스 로그 복구)  
3) **E3**(MDD None 제거 + 운영 가드레일)  
4) **E4**(레짐 기반 노출 스케일링으로 oos_min/MDD 개선 시도)

위 4개가 48시간 루프에서 “자동으로 실패/통과가 명확한” 형태로 돌아가면, 성능이 안 움직일 때도 원인이 최소 한 축으로 강제 분해됩니다.
