아래는 **다음 24~48시간 자동 루프**에서 바로 돌릴 수 있게, “누수/과최적화/서바이버십/비용 미반영/운영 리스크”를 최우선으로 잡는 **TOP5 우선순위**입니다.  
(미국주식 only, Tech+Healthcare 8~14종목, ETF는 관측지표로만 사용 / ETF 매매 제외)

## 0) 48시간 루프 공통 “명령형 체크리스트(필수 게이트)”
- [ ] **run_hash / lane_hash / git_sha / data_snapshot_id**를 모든 실험 산출물(JSON + 리포트 상단)에 강제 저장하라.
- [ ] **worst_mdd**가 `None`으로 남으면 해당 런을 **즉시 FAIL** 처리하라(리포트 생성 중단).
- [ ] **rebalance 로그(시점별 target/filled/price/turnover/cost)**를 **CSV + JSONL**로 동시 저장하라. (지금은 `--base-log` 미존재/CSV 파싱 실패로 pinpoint가 무력화됨)
- [ ] OOS/IS/폴드별 **샤프/평균/최저일수익(oos_min)/턴오버/거래비용/노출(min/max)**를 한 테이블로 고정 출력하라.
- [ ] **degenerate_folds**가 0이 아니면(현재 [1,2,3,8]) → 그 실험은 “성능 비교 대상”에서 제외하고 **데이터/스플릿 오류 티켓**으로 분리하라.

# TOP5 제안 (코드/아키텍처/전략)

아래 5개 제안은 **서로 다른 5개의 패치/실험 묶음(E1~E5)** 안에서만 돌게 설계했다.  
각 제안은 **E1~E5 중 2~3개**만 조합해서 검증한다(케이스 폭발 방지).

## 1) [운영 리스크] 리밸런스/코스트/성과 로그 “단일 진실” 복구 (E1 중심)
### (a) 왜 필요한지
- 현재 **rebalance pinpoint가 입력 파일 부재/파싱 실패**로 동작하지 않아, “성능이 왜/어디서 변했는지”를 추적 불가.
- **worst_mdd: None**, **lane_hash/run_hash: None** → 동일 런 재현/비교 불가(운영 리스크 + 실험 신뢰도 붕괴).

### (b) 위험/부작용
- 로그 강제/스냅샷 고정으로 **디스크/저장비용 증가**, 런 시간이 소폭 늘어날 수 있음.
- 기존 리포트 경로/포맷 의존 코드가 깨질 수 있음(마이그레이션 필요).

### (c) 최소 실험 2~3개 (E1 + E2/E3 중 택)
- **E1-1 (패치)**: 백테스트 실행 시 `rebalance.csv`와 `rebalance.jsonl`을 **항상 생성**(빈 리밸런스여도 헤더/메타만 기록).
- **E1-2 (패치)**: `--base-log` 같은 “문자열이 파일로 오인”되는 입력을 사전 검증하고, 없으면 **즉시 FAIL + 친절한 에러**로 종료.
- **E1-3 (검증 런)**: 챔피언을 1회 재실행하여 `worst_mdd != None`, `run_hash/lane_hash != None`, `rebalance.*` 생성 확인.

### (d) PASS 조건
- `aub_rebalance_pinpoint.py`가 **base/cand 모두**에서 “No rebalance data found” 없이 리포트 생성.
- 모든 런에서 `worst_mdd` 산출 + 폴드별 요약표 출력.
- 동일 git_sha/data_snapshot_id에서 **재실행 시 지표가 동일**(허용오차 범위 내).

## 2) [누수/스플릿] degenerate_folds 제거 + 시간축 누수 차단 (E2 중심)
### (a) 왜 필요한지
- 현재 **degenerate_folds: [1,2,3,8]**는 “학습/평가 스플릿이 깨졌거나 데이터 결측/정렬/라벨 누수” 가능성이 큼.
- degenerate 폴드가 있으면 OOS mean이 좋아 보여도 **신뢰 불가(과최적화/누수)**.

### (b) 위험/부작용
- 누수 차단/엠바고 적용 시 **지표가 단기적으로 하락**할 수 있음(하지만 그게 정상).
- 유효 샘플 수 감소로 변동성이 커질 수 있음.

### (c) 최소 실험 2~3개 (E2 단독으로 충분, 필요시 E1 결합)
- **E2-1 (패치)**: 시간기반 CV에 **purge + embargo**(예: lookback 기반 n일 엠바고) 강제 적용.
- **E2-2 (패치)**: 폴드 생성 후 각 폴드에 대해  
  `(#샘플, #유니크일자, #결측비율, 타깃분포)`를 체크하고 기준 미달 시 **degenerate로 분류 + 런 FAIL**.
- **E2-3 (검증 런)**: 동일 챔피언 설정에서 degenerate_folds가 **0**이 되는지 확인.

### (d) PASS 조건
- degenerate_folds = **[]**
- 폴드별 OOS가 “일부 폴드만 과도하게 좋음”이 줄고(분산 감소), 최소 성과(oos_min 등)가 합리화.
- (E1 결합 시) degenerate 판정 근거가 리포트에 자동 첨부.

## 3) [비용 미반영] 거래비용/슬리피지/턴오버를 “의사결정 게이트”로 승격 (E3 중심)
### (a) 왜 필요한지
- 현재 제공 지표에 **비용/슬리피지/체결 실패**가 핵심 KPI로 보이지 않음 → 실거래에서 성능 붕괴 가능.
- 노출 최대가 0.84까지 나오는 상황에서, 회전율이 높으면 비용이 PnL을 잠식.

### (b) 위험/부작용
- 비용을 넣으면 백테스트 성능이 하락해 “진전이 없어 보이는” 구간이 올 수 있음.
- 비용모델 파라미터가 임의적이면 또 다른 과최적화 축이 생김(따라서 **보수적 고정** 권장).

### (c) 최소 실험 2~3개 (E3 + E1 로깅 권장)
- **E3-1 (패치)**: 고정 비용모델 도입(예: 수수료 + 고정 bp 슬리피지 + 스프레드의 보수적 상수). 파라미터는 48시간 동안 고정.
- **E3-2 (패치)**: 리밸런스에서 **턴오버 상한(예: 일/리밸런스당)** 또는 **포지션 변경폭 제한** 추가.
- **E3-3 (A/B 런)**: 동일 신호로 비용 OFF vs ON 비교 리포트(“신호 알파”와 “비용 민감도” 분리).

### (d) PASS 조건
- 비용 ON에서도 OOS mean이 **유의미하게 양수 유지** + worst_mdd 산출/관리 가능.
- 비용 OFF 대비 ON에서 성능 감소폭이 **턴오버/리밸런스 빈도와 정합적**(이상치면 체결/가격정렬 버그 의심).
- 리포트에 **(gross PnL, cost, net PnL, turnover)**가 반드시 함께 출력.

## 4) [서바이버십/유니버스] 8~14개 Tech+Healthcare “고정 유니버스”를 데이터 스냅샷으로 동결 (E4 중심)
### (a) 왜 필요한지
- “미국주식 only + Tech/Healthcare 중심 8~14”에서 가장 흔한 함정은  
  **현재 살아남은 종목으로만 과거를 백테스트(서바이버십 바이어스)** 또는 룩어헤드(섹터 분류/시총 조건의 미래정보 혼입).
- 유니버스가 런마다 달라지면 성능 변화가 “전략 변화”가 아니라 “종목 바뀜”일 수 있음.

### (b) 위험/부작용
- 서바이버십 제거(상폐/인수 포함)하면 데이터 품질 문제가 드러나며, 초기에는 결측/매칭 이슈로 런 FAIL이 늘 수 있음.
- 8~14개로 너무 고정하면 특정 종목 편향이 생길 수 있어 “리밸런스/노출” 관리가 더 중요해짐.

### (c) 최소 실험 2~3개 (E4 + E2 일부 연계 가능)
- **E4-1 (패치)**: 유니버스 리스트를 **명시적으로 파일로 고정**(티커 + 섹터 태그 + 유효기간)하고, 각 런은 해당 스냅샷만 사용.
- **E4-2 (패치)**: 과거 시점 기준 섹터/산업 분류가 없으면, “현재 분류” 사용을 금지하거나 **룩어헤드 플래그**로 FAIL.
- **E4-3 (검증 런)**: 유니버스 스냅샷 A/B(예: 10종 vs 14종) 2개만 비교하여 성능 민감도 확인(케이스 확장 금지).

### (d) PASS 조건
- 모든 런에서 “사용 유니버스 티커 목록”이 리포트 상단에 고정 출력.
- 유니버스가 바뀌지 않았는데도 성능이 변하면(=전략 때문) 원인 추적 가능.
- 서바이버십/분류 룩어헤드 의심 플래그가 0.

## 5) [과최적화/레짐] 신호 단순화 + 노출 게이트 + ETF는 “레짐 관측”만 (E5 중심)
### (a) 왜 필요한지
- “No-Delta(성능이 안 움직임)” 구간에서 흔한 원인은  
  (i) 신호가 이미 포화(미세 튜닝만 반복) 또는 (ii) 시장 레짐이 바뀌었는데 노출이 동일.
- ETF 매매는 금지지만, **QQQ/XLK/XLV/SMH 등은 레짐 관측 지표로 유용**(리스크 온/오프, 섹터 상대강도).

### (b) 위험/부작용
- 레짐 필터가 또 하나의 과최적화 축이 될 수 있음 → **규칙은 단순/고정**, 실험 수 최소화 필요.
- 노출 게이트가 과도하면 기회 손실(수익 상단 제한).

### (c) 최소 실험 2~3개 (E5 단독 또는 E3와 결합)
- **E5-1 (패치)**: 레짐 관측지표 1~2개만 고정(예: `XLK/XLV 상대모멘텀`, `QQQ 200D 위/아래`)하고, 결과는 “리포트에만” 남겨라(매매 금지).
- **E5-2 (패치)**: 레짐이 불리할 때 **총 노출 상한 축소**(예: max exposure 0.85 → 0.55) 같은 단일 게이트 적용.
- **E5-3 (A/B 런)**: 레짐 게이트 OFF vs ON 2개만 비교(동일 신호/동일 비용모델).

### (d) PASS 조건
- 레짐이 “리스크오프”로 관측된 구간에서 worst_mdd/좌측 꼬리가 개선(손실 완화)되고,
- 리스크온 구간에서 OOS mean 훼손이 제한적.
- 레짐 규칙/파라미터가 48시간 내 변경되지 않고도 재현 가능.

# E1~E5 (48시간 자동 루프용) — 실험 정의/게이트/기대 관측치
아래 5개만 돌려라(추가 실험 생성 금지).

1) **E1: Logging & Artifact Integrity**
- (1) 실험 정의: rebalance 로그/메타(run_hash 등) 강제 + 파일입력 검증
- (2) 게이트: worst_mdd!=None, rebalance.* 존재, pinpoint 리포트 생성 성공
- (3) 기대 관측치: “원인 추적 불가” 상태 해소(디버깅 속도↑)

2) **E2: Purged/Embargo CV + Degenerate Fold Kill-switch**
- 게이트: degenerate_folds==0
- 기대 관측치: OOS가 과장되던 케이스 제거(초기 성능 하락 가능)

3) **E3: Cost/Turnover Model On**
- 게이트: net PnL/비용/턴오버가 리포트에 항상 출력 + 비용 ON에서도 전략 생존
- 기대 관측치: “알파 vs 비용 민감도” 분리

4) **E4: Survivorship-safe Fixed Universe Snapshot**
- 게이트: 유니버스 스냅샷 ID 고정 + 룩어헤드 플래그 0
- 기대 관측치: 전략 변화와 종목 변경 효과 분리

5) **E5: Regime Observe-only + Exposure Gate**
- 게이트: 레짐 지표가 리포트에 기록 + 게이트 적용 시 MDD 개선 여부 확인
- 기대 관측치: 좌측 꼬리 개선, 성능의 레짐 의존성 가시화

# “성능이 안 움직일 때(No-Delta)” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래를 **트리 형태로 고정 점검**하고, E1 로그가 갖춰진 뒤 자동 리포트로 붙여라.

## A. Trigger(신호 발생) 문제
- [ ] 신호가 대부분 0/클리핑/동일값인가? (종목별 신호 분산, 유니크 값 개수)
- [ ] 날짜 정렬/라벨 시프트가 맞는가? (t 신호로 t+1 수익 예측하는지)
- [ ] 결측 처리로 신호가 “평균값으로 평탄화”됐는가?

## B. Apply(주문/리밸런스 적용) 문제
- [ ] 리밸런스가 실제로 발생했나? (rebalance 로그에서 거래 0이 비정상적으로 많은지)
- [ ] 목표비중→체결비중 슬리피지/제약으로 “항상 못 따라가” 성능이 죽는가?
- [ ] 포지션 상한/하한이 신호를 다 눌러버리는가?

## C. Exposure(노출) 문제
- [ ] 노출이 지나치게 낮거나(항상 0 근처) 높아서(상한 근처) **변별력 없이 고정**됐는가?
- [ ] 섹터/단일종목 편중이 심해 “사실상 1~2종목 베팅”이 되었는가? (상위 1~3 종목 기여도)

## D. Cost(비용) 문제
- [ ] gross는 좋은데 net이 죽는가? → 턴오버/리밸런스 빈도 원인
- [ ] 비용 OFF/ON 차이가 비정상적으로 작거나 큰가? → 가격/체결/단위 버그 의심
- [ ] 거래단가(가격) 스케일/분할조정 오류로 비용이 왜곡되었는가?

## E. Regime(시장 국면) 문제
- [ ] 성능이 특정 국면(예: QQQ 하락, XLK<XLV)에서만 죽는가?
- [ ] 레짐별 조건부 성과표를 자동 출력하라:  
  (리스크온/오프 별 OOS mean, worst_mdd, hit rate, turnover)

## 실행 순서(48시간 우선순위)
- [ ] **1순위: E1**(로그/아티팩트 무결성) → 지금 상태에선 다른 개선이 “증명 불가”
- [ ] **2순위: E2**(degenerate_folds 제거/누수 차단)
- [ ] **3순위: E3**(비용/턴오버 게이트)
- [ ] **4순위: E4**(유니버스/서바이버십 스냅샷)
- [ ] **5순위: E5**(레짐 관측+노출 게이트)

이 순서를 지키면, “성능을 올리는 시도” 이전에 **성능이 진짜인지/어디서 깨지는지**가 24~48시간 내에 먼저 분해되고, 다음 사이클에서 전략 실험이 의미를 갖게 된다.
