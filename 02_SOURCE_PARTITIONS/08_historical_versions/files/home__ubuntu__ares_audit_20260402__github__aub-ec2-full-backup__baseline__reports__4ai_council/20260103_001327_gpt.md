# TOP5 제안 (코드/아키텍처/전략) + (a)(b)(c)(d)
아래 5개 제안은 **서로 다른 5개의 “공유 실험(총 5개만)”**으로 커버되도록 설계했다.  
각 제안마다 “최소 실험 2~3개”는 **E1~E5 중에서 재사용**해 충족(추가 실험 폭발 금지).

---

## 1) [누수/서바이버십] Point-in-Time + Purged CV 가드레일 (최우선)
### (a) 왜 필요한지
- OOS가 안 움직이거나 fold가 degenerate 되는 가장 흔한 원인:  
  **미래정보 혼입(리밸런스 시점/데이터 시점 불일치)** 또는 **서바이버십(현재 상장 종목 기준 샘플링)**.
- Tech/Healthcare 8~14 종목 소수 포트에서는 누수 1건이 성과를 “가짜로” 만들거나, 반대로 OOS를 “눌러” 델타가 사라지게 함.

### (b) 위험/부작용
- 누수 제거 후 **성과가 단기적으로 하락**할 수 있음(정상).
- Purged/embargo 적용 시 샘플 수가 줄어 **분산 증가** 가능.

### (c) 최소 실험(공유 실험 중 선택 2~3개)
- **E1** (필수): Purged Walk-Forward + Embargo + fold 유효성 강제
- **E4**: 메타데이터/리밸런스 로그 강화(누수 의심 트레이스 가능)
- **E5**: 레짐 분해(누수 제거 후 특정 레짐에서만 성과가 남는지 확인)

### (d) PASS 조건(게이트)
- [ ] `degenerate_folds == []`
- [ ] 각 fold당 **거래 횟수/리밸런스 횟수 > 0**, 노출 평균 > 0 (제로 전략 방지)
- [ ] “시점 유효성 테스트” 통과: 피처/라벨/체결시점이 **t 이전 데이터만 사용**(unit test)
- [ ] OOS가 떨어져도 OK. 단, **분해 가능(로그로 설명 가능)** 해야 PASS

---

## 2) [비용 미반영] 비용/슬리피지/지연 포함 “현실 백테스트” 패치
### (a) 왜 필요한지
- 지금 rebalance 로그가 깨져 있어 **턴오버/비용이 성과에 반영되지 않거나**, 반대로 비용이 과대/과소 반영될 수 있음.
- 8~14 종목 집중 포트는 리밸런스 빈도/턴오버에 따라 **비용 민감도**가 매우 큼 → 델타가 “비용 노이즈”에 묻힘.

### (b) 위험/부작용
- 비용 모델을 넣으면 OOS 평균이 하락할 수 있음(정상).
- 잘못된 슬리피지(특히 고정 bps)로 특정 가격대 종목에 편향 생길 수 있음.

### (c) 최소 실험(공유 실험 중 선택 2~3개)
- **E2** (필수): 비용 모델 v2 + 체결 지연(예: next-bar/next-open) + 슬리피지(bps, 변동성 연동 중 택1)
- **E4**: 리밸런스 로그/체결 로그 구조화(비용 기여도 추적)
- **E3**: 턴오버 캡(전략 제약)으로 비용 민감도 완화

### (d) PASS 조건(게이트)
- [ ] 비용 전/후 성과 차이가 **설명 가능**(턴오버↑면 비용 손실↑로 일관)
- [ ] **턴오버/비용/슬리피지 항목이 리밸런스 로그에 수치로 남음**
- [ ] OOS Mean이 하락해도, **OOS min/드로우다운이 개선**되면 PASS(현실화 성공)

---

## 3) [과최적화/노출 리스크] “8~14 Tech+Healthcare” 강제 + 노출/턴오버 제약
### (a) 왜 필요한지
- 현재 `exposure_max ~ 0.84` & exposure_min 0 → 시점별 **현금 비중/부분 노출**이 델타를 불안정하게 만들 수 있음.
- 종목 수가 적을수록 single-name 리스크가 커져서, 모델 변화가 성과로 “안 보이는” 구간이 자주 발생.

### (b) 위험/부작용
- 강제 제약은 성과 상한을 낮출 수 있음.
- 잘못된 섹터 분류/유니버스 고정은 레짐 변화에서 역효과.

### (c) 최소 실험(공유 실험 중 선택 2~3개)
- **E3** (필수):  
  - **보유 종목 수 8~14 고정**  
  - Tech+Healthcare만(미국주식)  
  - 단일 종목 max weight(예: 15~20%)  
  - 턴오버 상한(예: 일/주 리밸런스 시 최대 교체 비율)
- **E2**: 비용 모델과 결합해 “제약이 비용을 얼마나 줄이는지” 확인
- **E5**: 레짐별(변동성/금리) 성과 분해로 제약이 보호 역할 하는지 확인

### (d) PASS 조건(게이트)
- [ ] 매 리밸런스 시 **보유 종목 수가 8~14 범위 내**
- [ ] Tech/Healthcare 외 종목 편입 0
- [ ] **exposure_min을 >0로 끌어올리는 게 목표면**(예: 0.6 이상) 그 정책을 명시하고 준수
- [ ] single-name 기여도 상위 1종목이 PnL의 과반을 차지하는 구간이 감소하면 PASS

---

## 4) [운영 리스크] 리밸런스/체결/메타데이터 로깅 파이프 복구(재현성)
### (a) 왜 필요한지
- 지금 상태는 “성능이 왜 안 움직이는지”를 **증명/분해할 로그가 없음**.  
  `rebalance pinpoint`가 아예 실패 → 비용/턴오버/포지션 변화 비교가 불가능.
- `champion file empty`, `run_hash None`이면 autopilot이 **같은 실험을 다시 돌리거나** 결과를 덮어쓸 수 있음.

### (b) 위험/부작용
- 로그를 늘리면 저장공간/IO 증가(비용).
- 스키마 변경 시 기존 리포트 도구가 깨질 수 있음(마이그레이션 필요).

### (c) 최소 실험(공유 실험 중 선택 2~3개)
- **E4** (필수):  
  - run/lane hash 강제 생성  
  - champion file path 강제 기록  
  - `rebalance.jsonl` 스키마 고정(한 줄=한 리밸런스 이벤트)  
  - `rebalance.csv`는 선택, JSONL을 진실 원천으로
- **E1**: fold별 “거래/리밸런스 0”이면 즉시 실패시키는 검증도 함께 넣기
- **E2**: 비용 항목(commission/slippage/borrow)을 동일 스키마에 기록

### (d) PASS 조건(게이트)
- [ ] `rebalance_pinpoint`가 **base/cand 모두** 로드 성공
- [ ] run_hash/lane_hash/champion_file **항상 non-null**
- [ ] 리밸런스 이벤트마다: timestamp, holdings(8~14), weights, turnover, costs, exposure가 기록되면 PASS

## 5) [레짐/적용 리스크] “레짐 분해 + 게이트 트레이딩(관측지표 ETF)”로 델타가 사라지는 이유 찾기
*(ETF는 매매 금지, 관측지표로만 사용: 예 XLK/XLV/QQQ, Healthcare는 XLV/IHI 등 “상태 변수”로만)*

### (a) 왜 필요한지
- “성능이 안 움직임”은 종종 **모델이 변해도 실제 포지션이 거의 안 바뀌거나(적용 실패)**, 혹은 **레짐이 바뀌어 신호가 무력화**되는 현상.
- Tech/Healthcare는 금리/변동성/리스크온-오프에 민감 → 레짐 분해 없이는 개선이 누적되지 않음.

### (b) 위험/부작용
- 레짐 게이트는 **과최적화/데이터 스누핑** 위험이 큼(특히 조건이 많아질 때).
- 거래 기회 감소로 수익 기회도 감소.

### (c) 최소 실험(공유 실험 중 선택 2~3개)
- **E5** (필수): 레짐 라벨링 후 성과/노출/턴오버/비용을 구간별로 리포팅  
  (예: VIX 구간, 금리변화 구간, QQQ 추세/역추세 구간 등)
- **E3**: 제약(8~14, 턴오버 캡)이 레짐별로 방어적인지 확인
- **E2**: 레짐별로 비용 비중이 달라지는지 확인

### (d) PASS 조건(게이트)
- [ ] 레짐별로 **“델타가 안 나는 이유”가 수치로 드러남**  
  (예: 특정 레짐에서 turnover↑→cost↑로 알파 상쇄)
- [ ] 레짐 게이트를 넣더라도 **조건 수는 1~2개 이하**로 유지(과최적화 방지)
- [ ] 레짐별 리포트가 자동 생성되면 PASS

# 공유 실험(총 5개만) — 48시간 자동 루프 형태 (정의/게이트/기대 관측치)
아래 E1~E5만 돌리면 위 TOP5를 모두 커버.

## E1) LeakGuard + Purged Walk-Forward (Degenerate fold 제거)
- (1) 실험 정의  
  - Purged CV(리밸런스 주기 기준 embargo) 적용  
  - fold별 **거래/노출/샘플 유효성** 검증 실패 시 즉시 fail  
  - point-in-time 정렬 assert(피처 timestamp ≤ decision timestamp)
- (2) 게이트  
  - degenerate_folds=0, worst_mdd 산출됨, fold별 거래>0
- (3) 기대 관측치  
  - OOS mean이 내려갈 수 있으나, fold 분산/일관성이 개선되고 “가짜 알파” 제거 흔적이 보임

## E2) CostModel v2 + Execution Delay
- (1) 실험 정의  
  - next-open(또는 next-bar) 체결 지연  
  - slippage(고정 bps 또는 ATR/vol 연동 1개만 선택)  
  - 수수료/스프레드/borrow(공매도 있으면) 반영
- (2) 게이트  
  - 비용/슬리피지/턴오버가 rebalance 로그에 기록되고, 성과 차이가 방향성 일관
- (3) 기대 관측치  
  - gross→net 성과 하락, 대신 “턴오버 높은 설정”의 성과가 더 크게 깎이는 정상 패턴 관측

## E3) Universe & Constraints Patch (US Tech+Healthcare, 8~14, risk/turnover cap)
- (1) 실험 정의  
  - 유니버스: 미국주식, Tech+Healthcare만  
  - 보유 종목 수 8~14 강제, 단일 종목 max weight, 턴오버 상한
- (2) 게이트  
  - 종목 수/섹터 위반 0건, 단일 종목 비중 상한 준수
- (3) 기대 관측치  
  - 포지션 안정화, 비용 감소(턴오버 캡 덕분), OOS min/드로우다운 개선 가능

## E4) Observability/Logging Hardening (운영 리스크 제거)
- (1) 실험 정의  
  - run_hash/lane_hash/champion_file 강제 기록  
  - rebalance JSONL 스키마 고정 + 도구들이 그 스키마만 읽도록 통일  
  - “base-log 누락” 같은 경로 문제를 CI에서 실패 처리
- (2) 게이트  
  - rebalance pinpoint 도구가 base/cand 모두 로드 성공, 핵심 지표 자동 리포트 생성
- (3) 기대 관측치  
  - 성과 자체보다 “왜 성과가 안 움직이는지”를 다음 루프에서 즉시 원인 분해 가능

## E5) Regime Attribution Report (+ 1-rule gate option)
- (1) 실험 정의  
  - 관측지표(ETF는 매매 X): XLK/XLV/QQQ, VIX, 10Y 등으로 레짐 라벨 생성  
  - 레짐별 알파/비용/턴오버/노출/승률 리포트 자동 생성  
  - 옵션: 조건 1개짜리 게이트(예: 고변동 구간 노출 축소) 1회만 테스트
- (2) 게이트  
  - 레짐별 리포트가 매 루프 자동 산출, 특정 레짐에서의 “알파 상쇄 원인”이 수치로 특정됨
- (3) 기대 관측치  
  - “델타가 없는 이유”가 레짐별로 갈라져 보임(예: 리스크오프에서 신호 무력/비용 지배)

# 성능이 안 움직일 때 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 실행 순서 체크리스트
아래는 “델타 0” 상황에서 **자동 리포트로 바로 잡아낼** 분해 트리.

## A) 트리거(신호가 실제로 바뀌었나?)
- [ ] **신호 요약 통계**(mean/std, 상하위 분위수)를 base vs cand 비교
- [ ] 종목별 **rank correlation / sign flip rate** 계산(바뀐 척만 하는지 확인)
- [ ] 리밸런스 시점별 **신호→타깃 weight 매핑**이 단조인지(clip/softmax 포화 여부)

## B) 적용(바뀐 신호가 포지션으로 반영됐나?)
- [ ] 리밸런스 로그에서 **목표 weight vs 실제 체결 weight** 차이 추적(지연/체결 규칙 때문)
- [ ] **턴오버=0 구간** 탐지(제약/캐시/데이터 결측으로 리밸런스가 스킵되는 경우)
- [ ] “보유 종목 수 8~14 강제” 위반 여부 및 위반 시 처리(스킵/대체/현금화) 확인

## C) 노출(리스크 프로파일이 같아서 델타가 묻히나?)
- [ ] gross/net exposure, 섹터 비중(Tech vs Healthcare), 단일 종목 기여도 Top1 비중
- [ ] 베타(예: QQQ proxy), 변동성 타깃, 최대 손실 구간이 동일한지 비교
- [ ] exposure_min=0 구간이 잦으면 “사실상 현금 전략”이 되어 델타가 사라짐 → 정책으로 고정(예: min exposure)

## D) 비용(알파가 비용에 상쇄됐나?)
- [ ] PnL을 **alpha / slippage / commission / borrow**로 분해
- [ ] turnover↑인데 비용이 안 늘면 비용 모델 누락(누수) 의심
- [ ] 비용이 과대면(특히 고정 bps) 가격/유동성 구간별 과벌점 여부 확인

## E) 레짐(특정 구간에서만 먹히나?)
- [ ] 레짐별(고변동/저변동, 금리상승/하락, XLK>XLV/반대) 성과/노출/턴오버 리포트
- [ ] 델타가 “레짐 한 구간에서만” 존재하면: 그 구간만을 위한 조건 추가는 과최적화 위험 → **조건 1개 이하**로만 실험(E5 옵션)

## 24~48시간 실행 우선순위(명령형)
1) [ ] **E4 먼저 실행**: 로깅/메타데이터/리밸런스 파이프 복구(실패하면 다음 실험 금지)  
2) [ ] **E1 실행**: 누수/degenerate fold 제거(통과 전엔 성과 논의 금지)  
3) [ ] **E2 실행**: 비용+지연 포함한 현실 성과 확보  
4) [ ] **E3 실행**: 8~14 Tech+Healthcare 강제 + 노출/턴오버 제약으로 안정화  
5) [ ] **E5 실행**: 레짐 분해 리포트로 “왜 델타가 없는지”를 숫자로 특정

이 순서로 돌리면, “성능 개선” 이전에 **성능이 안 움직이는 구조적 이유(누수/비용/적용 실패/운영 결손/레짐)**가 먼저 고정되고, 그 다음 루프부터는 실험 델타가 정상적으로 관측된다.
