## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — **명령형 체크리스트**

### 1) **평가 무결성/아티팩트(리밸런스 로그·지표)부터 복구**
- **해야 할 일**
  - `aub_rebalance_pinpoint.py`가 **실제 존재하는 로그만** 읽도록 `--base-log/--cand-log` 인자 검증(문자열 `'--base-log'` 같은 오입력 즉시 fail-fast).
  - 실험 산출물에 **rebalance.csv + rebalance.jsonl을 “항상” 저장**(없으면 run을 실패 처리).
  - `worst_mdd: None`이 나오면 메트릭 계산 누락이므로 **MDD 계산 강제 + None 금지 어서션** 추가.
  - “Champion OOS Mean: 2.6276” vs “oos_mean: 1.8815” **불일치 원인**을 잡기 위해, 런마다 `dataset_hash / universe_hash / cost_model_hash / feature_hash`를 메타로 고정 출력.
- **(a) 왜 필요한지**
  - 지금은 **리밸런스 데이터가 로딩 실패**했고(`Expecting value…`), 핵심 위험지표(MDD)가 `None` → 성능이 “안 움직이는” 게 아니라 **측정이 깨졌을 가능성**이 큼.
- **(b) 위험/부작용**
  - fail-fast 도입으로 **실험 실패율 증가**(좋은 실패).  
  - 과거 런과 지표 정의가 달라져 **챔피언 교체 조건이 흔들릴 수 있음**(그래서 hash 고정이 필요).
- **(c) 최소 실험 2~3개** *(아래 공통 실험 풀 E1~E4 중 재사용)*  
  - **E1(필수)** + E3(센티널) 조합으로 “측정/누수”부터 제거.
- **(d) PASS 조건**
  - 모든 런에서 `rebalance.csv/jsonl` 생성, `worst_mdd != None`.
  - 동일 데이터/동일 설정 재실행 시 OOS 통계가 **±1% 이내 재현**.
  - oos_mean 불일치(2.6276 vs 1.8815)가 **hash 레벨에서 설명 가능**(데이터/코스트/유니버스 차이로 귀결).

---

### 2) **비용(슬리피지/스프레드/체결) 미반영을 즉시 반영 + 회전율 통제**
- **해야 할 일**
  - 백테스트 PnL에 **거래비용(고정 bps + 스프레드 프록시)**를 강제 반영.
  - 회전율이 높으면 OOS가 “무반응”처럼 보일 수 있으니, **turnover cap / min-hold(예: 2~5일)**를 옵션으로 추가.
  - 리밸런스가 48시간 루프라면, **시그널→다음 거래가능 시점**(예: next open/next close)을 명시적으로 고정(룩어헤드 방지).
- **(a) 왜 필요한지**
  - 비용이 빠지면 모델이 **미세 알파를 과대평가**하고, 실전에서는 성능이 “안 움직이는” 현상이 발생(비용에 먹힘).
- **(b) 위험/부작용**
  - 단기적으로 oos_mean 하락 가능(현실화).  
  - 회전율 제한이 알파를 “질식”시킬 수 있음 → 제한 강도는 실험으로.
- **(c) 최소 실험 2~3개**
  - **E2(필수)** + E1(로그로 회전율/비용 분해 확인).
- **(d) PASS 조건**
  - 비용 포함 후에도 oos_mean이 **치명적으로 붕괴하지 않음**(예: baseline 대비 ≥ 80% 유지 같은 내부 기준).
  - turnover, 평균 보유기간, 거래당 비용이 리포트에 **항상 노출**되고, 성능 변동의 원인이 비용으로 분해 가능.

---

### 3) **누수/과최적화 센티널을 “자동 게이트”로 승격**
- **해야 할 일**
  - **시간 시프트 센티널**을 CI 게이트로: feature를 +1일(미래) / -1일(과거) 시프트한 OOS를 자동 비교.
  - 학습/검증 폴드에서 **degenerate fold(정보량 0/상수 피처/거래 0)** 감지 시 런 실패 처리.
  - corporate action, 발표일(earnings) 등 이벤트 피처 사용 시 **타임스탬프 기준(발표 시각/거래 가능 시점)** 강제.
- **(a) 왜 필요한지**
  - “성능이 안 움직임”은 종종 **누수로 이미 포화(가짜 알파)** 상태이거나, 반대로 **누수 방지 패치로 알파가 사라진** 상태. 둘 다 센티널 없으면 구분 불가.
- **(b) 위험/부작용**
  - 센티널이 엄격하면 실험 통과율 감소.  
  - 일부 합법적 정보(전일 종가 기반)를 잘못 차단할 수 있음 → 게이트 정의를 명시해야 함.
- **(c) 최소 실험 2~3개**
  - **E3(필수)** + E1(메타 hash로 “왜 좋아졌는지” 설명 가능하게).
- **(d) PASS 조건**
  - **+1일 시프트 성능은 유의미하게 악화**, -1일 시프트가 원본보다 좋아지지 않음.
  - 센티널 실패 시 원인(피처/데이터열/정렬)이 로그에 pinpoint.

---

### 4) **서바이버십/유니버스 스냅샷(Tech+Healthcare 8~14종목) 고정**
- **해야 할 일**
  - 유니버스를 “현재 시점 종목 리스트”로 만들지 말고, **일자별 스냅샷(상장/상폐 포함) + 그날 거래 가능 종목만**으로 구성.
  - Tech+Healthcare 중심 제약을 지키되(8~14개), **선정 규칙을 날짜 기준으로 고정**(예: 해당일 섹터 분류/시총 상위/유동성 기준).
  - 결측/거래정지 발생 시 **대체 규칙(현금/동일 섹터 내 차선)**을 명시.
- **(a) 왜 필요한지**
  - 8~14 소수종목은 **서바이버십 편향/데이터 구멍**에 특히 취약. OOS가 “안 움직이는” 게 아니라 편향으로 “좋아 보이기만” 했을 수 있음.
- **(b) 위험/부작용**
  - 과거에 존재하지 않던 종목 제거로 백테스트 성능 하락 가능(현실화).  
  - 종목 교체 규칙이 복잡해지면 운영 리스크 증가 → 룰 단순화 필요.
- **(c) 최소 실험 2~3개**
  - E1(로그에 universe_hash/일자별 구성 기록) + E3(누수 센티널로 “유니버스 선택이 미래정보인지” 체크).
- **(d) PASS 조건**
  - 일자별 보유 가능 종목 수가 8~14를 만족 못 하는 날의 처리(현금/대체)가 **일관**.
  - universe_hash가 실험 간 의도치 않게 변하지 않음(변하면 사유가 로그에 남음).

---

### 5) **레짐/노출(Exposure 0.47~0.84) 제어를 “관측지표(ETF) 기반”으로 단순화**
- **해야 할 일**
  - ETF는 매매 금지(규칙 준수), 대신 **QQQ(Tech)·XLV(Healthcare)·SPY(시장)** 등을 **레짐 관측 지표**로만 사용.
  - 레짐에 따라 총 노출만 조절(예: risk-on 0.85 / risk-off 0.50), 종목 선택 로직은 그대로 두고 **노출 스케일링만** 적용.
  - tail-risk를 보려면 oos_min(현재 0.43) 개선에 집중: **최악 구간에서 노출 축소**가 목적.
- **(a) 왜 필요한지**
  - 지금 노출 범위가 넓고(0.47~0.84), 비용·레짐 불일치가 있으면 성능이 둔감해짐. **노출만 통제해도 “움직이는” 관측치**가 나옴.
- **(b) 위험/부작용**
  - 레짐 필터가 과하면 기회 손실(상승장 수익 희석).  
  - 관측 ETF 데이터 정렬이 잘못되면 누수 가능 → E3로 함께 게이트.
- **(c) 최소 실험 2~3개**
  - **E4(필수)** + E2(비용 포함에서도 tail 개선이 남는지 확인).
- **(d) PASS 조건**
  - oos_min 개선 또는 worst 구간 손실 감소(최소 기준을 내부 정책으로 고정).
  - 노출 변화가 리밸런스 로그에 명확히 기록(언제 risk-on/off였는지).

## 공통 “실행 가능한” 실험/패치 4개 (48시간 자동 루프용)
> **주의:** 아래 4개만 돌려도 위 TOP5의 검증 포인트를 대부분 커버하도록 설계(케이스 폭발 방지).

### E1) **리밸런스 로그/메트릭 완전성 패치 (관측 가능성 복구)**
1) **실험 정의**
   - 모든 런 산출물에 `rebalance.csv` + `rebalance.jsonl` + `metrics.json` 강제 저장.
   - `worst_mdd` 포함 핵심 메트릭 None 금지(계산 실패 시 런 실패).
   - `dataset_hash/universe_hash/cost_model_hash/feature_hash` 출력.
2) **게이트**
   - 파일 3종 존재, JSON 파싱 가능, 메트릭 None 없음.
   - 동일 seed/설정 재실행 시 OOS 통계 ±1% 이내.
3) **기대 관측치**
   - 현재 발생한 “rebalance data not found/JSON parse error” 소거.
   - “OOS Mean 불일치(2.6276 vs 1.8815)”가 hash 차이로 귀결(원인 위치가 명확해짐).

---

### E2) **비용+회전율 제약(현실화) 어블레이션**
1) **실험 정의**
   - 거래당 비용을 보수적으로 부과(예: 고정 bps + 스프레드 프록시).
   - turnover cap 또는 min-hold(짧게) 옵션 ON/OFF.
2) **게이트**
   - 비용 포함 후에도 OOS가 “완전 붕괴”하지 않음(내부 기준 유지).
   - turnover/거래횟수/비용 기여도가 리포트에 분해 출력.
3) **기대 관측치**
   - 성능이 비용에 민감하면: 평균은 떨어져도 **설명 가능성 증가**.
   - 회전율 제한이 tail(oos_min) 또는 변동성을 개선하면 운영 적합도 상승.

---

### E3) **누수 센티널(+1D/-1D 시프트) 자동 게이트**
1) **실험 정의**
   - 모든 피처(또는 핵심 피처 그룹)를 +1일 / -1일 시프트한 대조 실험을 자동 실행.
   - 시프트 결과를 원본과 같은 리포트에 나란히 기록.
2) **게이트**
   - +1D가 원본 대비 유의미하게 악화(“미래정보가 없으면 안 됨”이 정상).
   - -1D가 원본을 반복적으로 이기면 실패(정렬/라벨링 의심).
3) **기대 관측치**
   - “성능이 안 움직임”이 **누수 포화**인지, **정상/무알파**인지 1~2회전 내 판별.

---

### E4) **레짐 관측(ETF) 기반 노출 스케일링**
1) **실험 정의**
   - QQQ/XLV/SPY는 매매하지 않고, 단순 레짐 지표로 사용.
   - 레짐에 따라 총 노출만 2단(0.50/0.85 등)으로 스케일.
2) **게이트**
   - oos_min 또는 최악 구간 손실이 개선(평균이 조금 희생되어도 tail 개선이면 통과 가능하도록 정책화).
   - 레짐 판정이 룩어헤드 없이 동작(E3 통과).
3) **기대 관측치**
   - 평균 수익이 크게 변하지 않아도 **하방/변동성 지표가 “움직이는”** 형태로 관측될 확률이 높음.

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
> 아래는 “질문 없이” 바로 로그/리포트에 추가해서 48시간 루프에서 자동으로 판별하게 만드는 항목들.

### A) Trigger(신호 생성) 문제
- **체크**
  - 신호 분포가 상수에 가까운지(상위/하위 분위수 스프레드, 표준편차).
  - 일자별 신호 순위 상관(너무 높으면 변화 없음 → 리밸런스 무의미).
- **관측치**
  - `signal_std`, `rank_ic`, `top-bottom spread`를 매일 저장.

### B) Apply(리밸런스 적용/타이밍) 문제
- **체크**
  - 시그널 산출 시점과 체결 가격 시점이 뒤섞이지 않았는지(룩어헤드/지연).
  - 리밸런스가 실제로 포지션을 바꾸는지(변경 0이면 성능도 안 움직임).
- **관측치**
  - `#trades`, `position_delta_l1`, “신호 시각/체결 시각” 로그 필드.

### C) Exposure(노출/포지션) 문제
- **체크**
  - 총 노출이 좁은 범위로 고정되었는지(혹은 과도하게 출렁이는지).
  - 8~14 종목 제약에서 단일 종목 비중 상한이 제대로 걸렸는지.
- **관측치**
  - `gross_exposure`, `net_exposure`, `max_weight`, `HHI(집중도)`.

### D) Cost(비용) 문제
- **체크**
  - 총수익 대비 비용 비중(비용이 알파를 상쇄하면 “안 움직임”처럼 보임).
  - 거래가 몰리는 구간에서만 성능이 깨지는지(스프레드/임팩트 민감).
- **관측치**
  - `pnl_gross`, `pnl_net`, `cost_total`, `cost_per_trade`, `turnover`.

### E) Regime(시장 국면) 문제
- **체크**
  - 성능이 특정 변동성/금리/섹터 모멘텀 구간에서만 살아나는지.
  - Tech/Healthcare 간 상대강도 국면에 따라 편향이 생기는지.
- **관측치**
  - QQQ/XLV/SPY 기반의 레짐 라벨(관측지표), 레짐별 성과 테이블.

---

### 48시간 루프에서의 권장 실행 순서(명령형)
1) **E1 먼저 적용** → 로그/메트릭 완전성 없으면 이후 실험은 전부 무의미.
2) **E3 동시 적용** → 누수/정렬 문제를 먼저 배제.
3) **E2 적용** → 비용/회전율 현실화로 “실전 가능 알파”만 남기기.
4) **E4 적용** → 평균이 안 움직여도 tail/하방이 움직이는지 확인(운영 가치).

이 4개가 모두 통과하면, 그때부터(다음 사이클) 종목선정/팩터/모델링을 건드려도 “측정·운영·현실화” 기반 위에서 움직이게 됩니다.
