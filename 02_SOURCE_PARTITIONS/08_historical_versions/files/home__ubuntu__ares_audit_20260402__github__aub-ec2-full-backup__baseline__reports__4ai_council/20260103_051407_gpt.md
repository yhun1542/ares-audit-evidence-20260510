## 즉시 레드플래그(ONE TRUTH 기반)
- `degenerate_folds: [1,2,3,8]` → **검증셋 일부가 무거래/상수노출**일 가능성 큼(과최적화/데이터 분할 오류/필터 오류 우선).
- `worst_mdd: None` → **리스크 메트릭 계산 파이프라인 결손**(운영 리스크 + 평가 불능).
- `lane_hash/run_hash: None` → **재현성/추적성 결손**(48시간 자동 루프에서 원인분해가 막힘).
- Rebalance pinpoint가 **로그 포맷/경로 오류로 완전 실패** → 비용/턴오버/체결 리스크를 확인할 수 없음.

아래는 **24~48시간 우선순위 TOP5**. 단, “실행 가능한 patch/실험”은 **공통 실험 세트 E1~E5 (총 5개)**로 제한하고, 각 제안은 그중 **2~3개만 실행**하도록 구성함.

---

# 1) TOP5 우선순위 제안 (코드/아키텍처/전략)

## P1. (운영/재현성) Rebalance/Run 메타데이터 & 로그 파이프라인 “강제 정상화”
### (a) 왜 필요한지
- 현재 rebalance pinpoint가 실패하여 **턴오버/비용/체결**이 블랙박스.
- `lane_hash/run_hash None`이면 **같은 실험을 다시 못 만들고**, “성능이 안 움직이는 이유”를 분해할 수 없음.

### (b) 위험/부작용
- 로그 I/O 증가로 러ntime 증가, 디스크 사용량 증가.
- 기존 리포트 파서와 **호환성 깨질 수 있음**(버전 필드 필요).

### (c) 최소 실험(공통 E-세트에서 선택)
- **E1** 실행(로그 스키마 강제 + 샘플 리플레이).
- **E4** 실행(비용 스윕을 하려면 rebalance 이벤트가 필수).
- (옵션으로) **E5** 실행(제약이 rebalance에 반영되는지 확인).

### (d) PASS 조건
- 모든 run에서 `run_hash/lane_hash/data_hash/code_hash`가 **non-null**로 저장.
- rebalance 이벤트가 **JSONL/CSV 둘 중 하나로 100% 생성**, 파서가 에러 없이 ingest.
- 비용/턴오버 리포트가 자동 생성되고, 후보들 간 비교 가능.

---

## P2. (누수/과최적화 최우선) Degenerate fold 제거 + “폴드 유효성 게이트” 도입
### (a) 왜 필요한지
- degenerate folds는 **OOS 평균을 왜곡**하고, 작은 구간에 맞춘 파라미터가 “좋아 보이게” 만들 수 있음.
- fold가 무거래면 전략이 아니라 **데이터/필터/시그널 적용 경로** 문제일 가능성이 큼.

### (b) 위험/부작용
- 유효 폴드만 남기면 표본 수가 줄어 **분산 증가**.
- 게이트가 과도하면 실험이 자주 중단(하지만 자동 루프에는 오히려 유리).

### (c) 최소 실험
- **E2** 실행(폴드 유효성 assert + 재실행).
- **E1** 실행(폴드별 rebalance/노출 로그로 “왜 degeneracy인지” 확인).

### (d) PASS 조건
- `degenerate_folds`가 **빈 배열** 또는 전체 폴드의 5% 이하.
- 각 폴드에서 최소 조건 충족(예: `n_trades >= N`, `exposure_std > eps`, `turnover > 0`).
- 폴드별 성능 분포가 “한 폴드만 압도적으로 좋음” 형태가 완화.

---

## P3. (누수/서바이버십) “시간축 무결성 + 포인트인타임 유니버스” 감사(Audit) 실험
### (a) 왜 필요한지
- Tech/Healthcare 단일주(ETF 매매 제외)는 **서바이버십/상장폐지/인덱스 편입효과**에 취약.
- 성능이 정체(no-delta)인 경우, 실제로는 “개선이 무효”가 아니라 **누수 제거로 상쇄**되는 패턴이 흔함.

### (b) 위험/부작용
- 포인트인타임 유니버스/상장폐지 반영 시 성능이 크게 떨어질 수 있음(하지만 그게 “진실”).
- 데이터 소스/스키마 손대야 하면 단기 공수 증가.

### (c) 최소 실험
- **E3** 실행(시그널/피처 1일 지연 + 랜덤화/셔플 대조 + PIT 유니버스 토글).
- **E2** 실행(폴드 유효성까지 같이 통과시켜 “감사 실험이 무거래로 끝나는” 문제 제거).

### (d) PASS 조건
- 1일 지연/셔플에서 성능이 **유의미하게 붕괴**(= 누수 의심)하지 않거나, 붕괴 시 원인이 특정 피처/경로로 **좁혀짐**.
- PIT 유니버스 적용 전후 성능 차이가 납득 가능한 범위(예: 급격한 과대 성능이 제거되며 안정화).

---

## P4. (비용 미반영 최우선) 비용/슬리피지/차입비용을 “게이트로” 승격
### (a) 왜 필요한지
- 단일주 Tech/Healthcare는 이벤트/갭/스프레드 영향이 커서, 비용이 빠지면 **OOS mean이 움직여도 실전 PnL이 정체**될 수 있음.
- 현재 rebalance 로그가 불능이라 비용 검증 자체가 막혀 있음.

### (b) 위험/부작용
- 비용 모델이 과도하게 보수적이면 유망 전략을 조기 폐기할 수 있음 → **스윕(0x/1x/2x)**로 완화.
- 차입/공매도 제약 반영 시 노출이 줄어 성능 하락 가능.

### (c) 최소 실험
- **E4** 실행(비용 0x/1x/2x 스윕 + borrow fee 토글).
- **E1** 실행(비용 산출의 입력인 체결/리밸런스 이벤트 검증).

### (d) PASS 조건
- 1x 비용에서 OOS가 “양(+)의 기대값”을 유지(예: `oos_mean_cost1x > 0`).
- 2x 비용에서도 완전 붕괴가 아닌지 확인(비용 민감도 과도하면 turnover 문제로 판정).
- 비용 기여도가 리포트로 분해됨(슬리피지/수수료/차입 각각).

---

## P5. (노출/운영 리스크) 노출·턴오버·집중도 Governor 추가(전략은 유지, 실행만 안정화)
### (a) 왜 필요한지
- `exposure_max ~0.84`인데, 폴드 degeneracy와 결합하면 “어느 구간은 거의 풀노출, 어느 구간은 무노출” 같은 **불안정한 운용**이 발생 가능.
- 자동 루프에서는 “성능 개선”보다 먼저 **리스크/운용 가능성**을 잠그는 편이 수렴 속도가 빠름.

### (b) 위험/부작용
- 제약이 수익 기회를 깎아 OOS mean이 소폭 하락할 수 있음.
- 하지만 변동성/꼬리위험이 줄면 실전 적합도는 상승.

### (c) 최소 실험
- **E5** 실행(노출/턴오버/단일종목 집중도 제약 on/off).
- **E4** 실행(턴오버 감소가 비용 민감도를 실제로 줄이는지 확인).

### (d) PASS 조건
- `max_position_weight`, `sector_concentration`, `turnover`가 상한 내로 유지.
- 비용 1x에서 성능이 유지되거나, 성능 소폭 하락 대신 `worst_mdd`/tail loss 개선이 관측.

# 2) 48시간 자동 루프용 “공통 실험 세트” (E1~E5, 총 5개만 실행)

## E1) Rebalance/Trace Logging 강제 + 해시 메타데이터 삽입
1) **실험 정의**
- 모든 run 산출물에 `run_hash/lane_hash/code_hash/data_hash/config_hash` 기록.
- rebalance 이벤트를 **단일 표준(JSONL 권장)**로 기록(타임스탬프, 종목, 목표/실행 수량, 가격, 수수료, 슬리피지, 사유 코드).
2) **게이트**
- 로그 파일 0바이트/파싱 실패 시 즉시 FAIL.
- `worst_mdd`가 None이면 FAIL(리스크 리포트 생성 강제).
3) **기대 관측치**
- rebalance pinpoint가 정상 동작.
- “성능 정체”의 원인이 **무거래/비용/노출/신호 빈도** 중 어디인지 바로 분해 가능.

---

## E2) Fold Degeneracy Guardrail + 폴드별 최소 거래/노출 검증
1) **실험 정의**
- 폴드별로 `n_rebalance_events`, `n_trades`, `avg_exposure`, `exposure_std`, `turnover`를 계산하고 최소치 미달이면 폴드 자체를 FAIL 처리(또는 재분할).
2) **게이트**
- 전체 폴드 중 FAIL 비율이 임계치 초과(예: 10%↑)면 실험 FAIL.
3) **기대 관측치**
- degenerate_folds가 제거되고, OOS mean이 “허수”에서 “실거래 기반”으로 재정렬.
- 개선이 없더라도 원인이 **전략이 아니라 데이터/적용 경로**로 수렴.

---

## E3) Leakage/Survivorship Audit: 1일 지연 + 셔플 대조 + PIT 유니버스 토글
1) **실험 정의**
- 시그널/피처를 **t→t+1로 강제 지연**(미래정보 사용 차단).
- 라벨/시그널 셔플(또는 종목-일자 매칭 셔플)로 “우연 성능” 하한선 측정.
- 가능하면 유니버스/기업행동을 **포인트인타임**으로 토글.
2) **게이트**
- 지연/셔플에서 챔피언급 성능이 유지되면 FAIL(누수 강력 의심).
3) **기대 관측치**
- 누수 경로가 있으면 특정 모듈(정렬/리샘플/기업행동 반영/지표 계산)로 좁혀짐.
- PIT 적용 시 과대 성능이 줄고 분산이 안정화되는 패턴이 흔함.

---

## E4) 비용 모델 스윕(0x/1x/2x) + 차입비용/공매도 제약 토글
1) **실험 정의**
- 동일한 포지션 경로에 대해 비용을 0/1/2배로 재평가.
- 공매도 포함이면 borrow fee(보수적 상수라도)와 locate 실패(체결 불가) 옵션 토글.
2) **게이트**
- 1x 비용에서 기대값이 음(-)이면 FAIL(턴오버/미세엣지 문제로 분류).
3) **기대 관측치**
- “성능이 안 움직임”이 사실은 **비용에 의해 상쇄**되는지 즉시 확인.
- 비용 민감도가 높은 경우 해결책이 **신호 개선이 아니라 turnover 억제**로 바뀜.

---

## E5) Exposure/Turnover/Concentration Governor (실행 안정화 레이어)
1) **실험 정의**
- (예) 총 익스포저 상한, 단일 종목 비중 상한, 섹터(Tech/Healthcare 내) 집중 상한, 일/주간 turnover 상한을 소프트-클립(리노멀라이즈)로 적용.
2) **게이트**
- 제약 적용 후에도 `n_trades`가 급감(예: -70%↓)하면 FAIL(제약이 과도/신호가 약함).
3) **기대 관측치**
- MDD/꼬리손실이 감소하고, 비용 1x에서 성능이 더 “일관”되게 관측.
- 폴드별 노출 분산이 줄어들어 degenerate 재발 방지.

# 3) 성능이 안 움직일 때 “원인 분해” 아이디어(트리거/적용/노출/비용/레짐) — 명령형 체크리스트

## A) 트리거(Trigger) 계층: “신호가 실제로 발생하나?”
- 폴드/월별 `signal_fire_rate`(신호 발생일 비율), `avg_names_traded`를 기록하고 **0에 수렴 구간**을 플래그 처리.
- 신호 강도 분포(상위/하위 퍼센타일)와 체결 후 수익 기여를 함께 저장(“강한 신호가 돈을 버는지” 확인).
- (게이트) 신호 발생은 정상인데 거래가 없으면 **적용/제약 레이어** 문제로 이동.

## B) 적용(Application) 계층: “신호→주문 변환에서 죽나?”
- 신호 생성 시점/가격 기준(종가/시가/VWAP)과 주문 시점이 **미래를 참조하지 않는지**(E3로 동시 검증).
- 리밸런스 캘린더/휴장/반쪽장/기업행동(분할/병합) 적용 후 수량이 0으로 클립되는지 확인.
- (게이트) 리밸런스 이벤트가 없거나 파싱 불가면 **E1부터**.

## C) 노출(Exposure) 계층: “돈을 걸고 있나, 한쪽에 쏠리나?”
- 시간별 총익스포저, 롱/숏 익스포저, 상위 5개 종목 집중도, 섹터 집중도를 저장.
- 노출이 0↔0.8 사이를 불규칙하게 뛰면 **제약/필터/결측치 처리** 문제 가능.
- (해결 방향) 개선이 필요하면 전략 수정 전에 **E5 Governor**로 안정화.

## D) 비용(Cost) 계층: “엣지가 비용에 먹히나?”
- 총 비용을 슬리피지/수수료/차입/스프레드로 분해하고, **총 PnL 대비 비용 비율**을 상시 기록.
- (판정) 비용 0x에서만 개선되고 1x에서 상쇄되면 “신호 개선”이 아니라 **턴오버/홀딩기간/체결 기준가** 문제.

## E) 레짐(Regime) 계층: “특정 국면에서만 먹히나?” (ETF는 지표로만 사용)
- 관측지표로만 사용: `QQQ(나스닥)`, `XLV(헬스케어)`, `VIX 대용(예: VIX 지수 데이터)` 등으로
  - 추세(상승/하락), 변동성(고/저), 금리 민감(장단기 금리) 레짐을 태깅.
- 레짐별 성능을 분해해 “개선이 특정 레짐에서만 +, 다른 레짐에서 -로 상쇄”되는지 확인.
- (액션) 레짐 민감이 크면, 전략을 늘리기보다 **노출 스케일링(레짐별 risk scaler)**을 우선.

---

## 24~48시간 실행 순서(명령형)
1) **E1 실행**: 로그/해시/MDD 산출 강제 → rebalance pinpoint 복구.
2) **E2 실행**: degenerate fold 제거 게이트 추가 → OOS 수치의 신뢰도 확보.
3) **E3 실행**: 누수/서바이버십 감사로 “개선 무효화” 원인 제거/확정.
4) **E4 실행**: 비용 스윕으로 “정체=비용 상쇄” 여부 확정.
5) **E5 실행**: 노출/턴오버/집중도 안정화로 운영 리스크를 먼저 잠금.

이 5개가 통과하면, 그 다음부터는 “전략 아이디어 추가”가 아니라 **(i) 신호 품질 vs (ii) 비용/턴오버 vs (iii) 레짐 민감도** 중 어디를 더 깎아야 하는지 자동 루프가 스스로 가리키는 상태가 됨.
