## TOP1) **실험/리포트 신뢰성 복구(운영 리스크 + 과최적화 방지의 출발점)**
현재 로그에서 **OOS Mean 불일치(Champion 1.88 vs Diagnoser 2.63)**, **rebalance pinpoint가 입력 파일을 못 읽음(--base-log 경로/포맷 오류)**, **worst_mdd None**(리스크 지표 미계산 가능성) 징후가 있습니다. 이 상태에선 “성능이 안 움직임/움직임” 자체가 허상일 수 있습니다.

### 왜 필요한지
- **평가 지표/입력 아티팩트가 꼬이면** 어떤 패치도 검증 불가(운영 리스크 최상위).
- **MDD 미계산**이면 리스크 게이트가 작동하지 않아 과최적화/폭발을 못 막음.
- rebalance 로그 부재는 **“노출/비용/매매” 분해가 불가능**해져 원인 추적이 막힘.

### 위험/부작용
- 단기적으로 “실험이 느려짐(검증 단계 추가)”
- 기존 결과와 숫자가 달라져 **챔피언 재선정**이 발생할 수 있음(하지만 정상)

### 최소 검증(가벼운 체크; 풀백테스트 증식 방지)
- [ ] **단일 진실(ONE TRUTH) 경로를 강제**: `champion_v5_latest.json` 읽은 값과 diagnoser가 출력한 base OOS가 같은지 assert
- [ ] **리포트 I/O 스키마 고정**: rebalance 로그는 CSV/JSONL 중 하나로 통일하고, 파일 존재/JSON 파싱 실패 시 즉시 실패 처리
- [ ] **risk metric 강제 계산**: `worst_mdd`가 None이면 런 전체를 FAIL

### PASS 조건(게이트)
- [ ] 동일 base 파일 기준으로 **OOS Mean이 툴 간 오차 0.5% 이내**
- [ ] rebalance pinpoint가 “No rebalance data found” 없이 **최소 1회 리밸런스 이벤트를 로드**
- [ ] 모든 run 산출물에서 **worst_mdd가 숫자로 채워짐**

### 48시간 루프: (1)실험 (2)게이트 (3)기대관측치
- **실험 정의(패치)**: “Artifact Manifest + Metric Consistency Gate”  
- **게이트**: 위 PASS 조건 3개 전부  
- **기대 관측치**: 이후 실험들의 성능 변동/무변동이 “실제”가 됨(진단 가능 상태 확보)

## TOP2) **리밸런스/노-델타(성능 정체 핵심 후보) 계측 + 원인 귀속**
이미 “No-Delta Diagnoser”가 돌아가는데도, rebalance pinpoint는 입력을 못 읽고 있습니다. 즉, **‘트리거→주문→체결(가정)→포지션 변화’**가 제대로 추적되지 않는 상태일 가능성이 큽니다.

### 왜 필요한지
- 성능이 안 움직이는 흔한 이유:
  - 신호가 변해도 **리밸런스 임계값/라운딩/포지션 캡** 때문에 주문이 0
  - 반대로 주문은 나가는데 **비용/슬리피지**로 무효화
  - 스케일링/헤지 로직이 **항상 동일 노출**을 만들어 “전략이 달라져도 포트폴리오가 같음”
- 이건 전략보다 먼저 **계측/귀속(attribution)**으로 잡아야 합니다.

### 위험/부작용
- 로그량 증가(디스크/비용)
- 너무 촘촘한 리밸런스는 비용 폭증을 유발할 수 있어 **게이트 필수**

### 최소 실험(풀백테스트 1개 + 가벼운 체크 2개)
- [LIGHT] [ ] **리밸런스 이벤트 스키마 추가**: 날짜별 `target_w`, `prev_w`, `delta_w`, `reason(no_trade|threshold|cap|cash)` 기록
- [LIGHT] [ ] **No-Delta를 3단 분해**:  
  1) 신호 변화 없음 2) 신호는 변했으나 목표비중 동일 3) 목표비중은 변했으나 주문이 0
- [FULL RUN] [ ] **델타 임계값(예: L1 turnover threshold) 2수준**만 비교: `thr_low` vs `thr_high` (2-run)

### PASS 조건(게이트)
- [ ] OOS 구간에서 “주문 0”일 때 **reason이 95% 이상 분류됨(unknown <5%)**
- [ ] `thr_low` 대비 `thr_high`에서 **연간 턴오버/거래일 수가 의도대로 단조 감소**
- [ ] 델타 귀속 리포트에서 상위 원인 1~2개가 명확(“모름”이 1순위면 FAIL)

### 48시간 루프
- **실험 정의(패치)**: “Rebalance Event Logging + No-Delta Attribution + Threshold A/B(2-level)”  
- **게이트**: reason 분류율/턴오버 단조성  
- **기대 관측치**: 성능 정체가 “신호 문제”인지 “집행/제약 문제”인지 즉시 갈림

## TOP3) **비용(슬리피지/수수료/스프레드/대차) 모델을 목적함수에 강제 반영**
현재 출력만으로는 비용이 평가에 들어갔는지 불명확합니다. 특히 **8~14개 집중 포트**는 리밸런스/슬리피지에 민감하고, Tech/Healthcare는 이벤트(실적/임상)로 갭이 커서 **단순 고정 bps 비용은 과소추정**되기 쉽습니다.

### 왜 필요한지
- 비용 미반영은 **가짜 알파**의 1순위 원인.
- 성능이 “안 움직임”도 사실은 **비용이 전부 먹는 구조**일 수 있음(전략이 아니라 비용이 상쇄).

### 위험/부작용
- 단기 성능(OOS mean)이 낮아질 수 있음(정상)
- 너무 보수적으로 잡으면 매매가 과도하게 줄어 **신호 반영이 둔화**

### 최소 실험(풀백테스트 2개로 제한)
- [FULL RUN] [ ] **비용 On/Off** 비교(동일 시드/구간): 비용이 성능을 얼마나 먹는지 “차이”를 확보
- [FULL RUN] [ ] **슬리피지 단순 모델 2단**: `flat_bps` vs `spread+adv_proxy`(ADV/가격 기반; 보수적 캡 포함)

### PASS 조건(게이트)
- [ ] 비용 ON에서 **턴오버 상위 구간의 성능 붕괴**가 확인되면(예: 상위 20% turnover bucket Sharpe 급락) → 비용-민감 구조로 판정(다음 패치에서 턴오버 제약 강화)
- [ ] 비용 모델을 바꿔도 전략 순위가 완전 뒤집히면 → 기존 결과는 비용 누락/과소추정 가능성으로 FAIL 처리(챔피언 재검증)

### 48시간 루프
- **실험 정의(패치)**: “Cost-in-Objective + Slippage Model 2-level”  
- **게이트**: turnover bucket 붕괴 여부/모델 민감도  
- **기대 관측치**: ‘알파’와 ‘비용’이 분리되어 성능 정체 원인 규명 가능

## TOP4) **노출/집중/리스크 가드레일(8~14종목 집중 포트의 생존성)**
현재 노출 min/max가 0.47~0.84로 보이는데(현 챔피언 기준), 이 범위가 전략 의도인지/우연인지 불명확합니다. 또한 `worst_mdd None`이었던 점을 감안하면 리스크 통제가 약할 수 있습니다.

### 왜 필요한지
- 집중 포트는 작은 버그/레짐 변화에 **MDD가 급확대**될 수 있음(서바이버십/운영 리스크).
- 노출이 흔들리면 성능이 “안 움직이는 것처럼” 보여도 사실 **리스크 스케일만 변한 착시**가 생김.

### 위험/부작용
- 가드레일이 과하면 알파가 죽고 “항상 비슷한 포트”가 될 수 있음
- 변동성 타겟팅이 비용을 유발할 수 있음(리밸런스 증가)

### 최소 실험(풀백테스트 1개만; 나머지 체크)
- [LIGHT] [ ] **단일종목/섹터 캡**: 예) single-name ≤ 18%, Tech/Healthcare 각 ≤ 70% 등(미국주식/섹터 편향 완화)
- [LIGHT] [ ] **노출 하한/상한 하드 게이트**(예: 0.5~0.9) 및 위반 시 FAIL
- [FULL RUN] [ ] **변동성 타겟팅 On/Off**(또는 간단 리스크 패리티 스케일) 1회 비교

### PASS 조건(게이트)
- [ ] worst_mdd가 계산되며, 가드레일 적용 후 **worst_mdd 개선 또는 동일 수준 유지**(악화 시 FAIL)
- [ ] 평균 보유종목 수가 **8~14 유지**
- [ ] 노출 범위가 의도한 밴드 내에 **95% 이상** 들어옴

### 48시간 루프
- **실험 정의(패치)**: “Risk Guardrails + (Optional) Vol Targeting A/B”  
- **게이트**: MDD/종목수/노출 밴드  
- **기대 관측치**: 성능이 정체여도 “리스크 조정 성능”이 개선되며 생존성이 올라감

## TOP5) **레짐(ETF 관측지표) + 누수 방지 워크포워드 게이트(과최적화 차단)**
ETF는 매매하지 않고 **상태 관측용(레짐/리스크온·오프)**으로만 사용합니다. 예: QQQ(나스닥), XLK(Tech), XLV(Healthcare), IBB(Biotech) 등. 핵심은 **누수 없는 방식으로 “오늘 알 수 있는 값만” 쓰는 것**과, 성능이 안 움직일 때 레짐별로 분해가 가능해지는 것입니다.

### 왜 필요한지
- Tech/Healthcare는 레짐 의존(금리/리스크 선호/실적 시즌)에 따라 알파가 꺼졌다 켜질 수 있음.
- “성능이 안 움직임”이 실제론 **레짐 믹스 변화**일 가능성이 큼.
- 레짐 feature는 누수 위험이 커서 **purged/embargo** 없으면 과최적화가 즉시 발생.

### 위험/부작용
- 레짐 feature가 과하면 모델이 ETF에 과적합(간접 ETF 추종)
- 워크포워드/퍼지드 CV는 성능이 낮아 보일 수 있음(정상; 과대평가 제거)

### 최소 실험(풀백테스트 1개)
- [LIGHT] [ ] **레짐 라벨 산출**: (예) QQQ 20/60MA, VIX 대용지표(가능하면), XLK/XLV 상대강도 등 “t시점까지의 값만”
- [LIGHT] [ ] **Purged/Embargo CV 게이트**: 이벤트/중첩 구간 제거(lookahead 차단)
- [FULL RUN] [ ] 레짐 feature **On/Off 단일 비교**(feature 추가가 아니라 “게이팅 변수로만” 우선 사용)

### PASS 조건(게이트)
- [ ] 레짐 On에서 성능이 오르지 않더라도, **레짐별 성과 분산이 설명 가능**해짐(예: risk-on에서만 유효)  
- [ ] purged 적용 후 성능이 급락하면 → 기존에 누수/중첩 과대평가 가능성으로 FAIL 플래그

### 48시간 루프
- **실험 정의(패치)**: “Regime Observables (ETF) + Purged WF Gate”  
- **게이트**: 누수 차단 통과/레짐별 분해 가능성  
- **기대 관측치**: ‘왜 안 움직이는가’를 레짐으로 설명 가능(전략 수정 방향이 생김)

# 성능이 안 움직일 때: 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래 트리를 **매 런 자동 리포트**로 찍게 만들어 “어디서 막혔는지”를 한 번에 보이게 하십시오.

## A) Trigger(신호 생성) 레벨
- **Signal Delta 분포**: 날짜별 `||signal_t - signal_{t-1}||`  
  - 0에 몰림 → 피처/스케일/클리핑/결측 처리로 신호가 죽었을 가능성
- **상위 피처 기여도(간단 버전)**: 레짐/모멘텀/퀄리티 중 무엇이 움직였는지

## B) Apply(목표비중 변환/제약) 레벨
- **Signal→Target 변환 후 델타**: `||target_w_t - target_w_{t-1}||`  
  - 신호는 변했는데 타겟이 안 변하면: 캡/섹터제약/정규화가 모든 변화를 눌렀을 가능성
- **제약으로 잘린 비율**: cap hit rate(몇 % 날짜에서 cap에 걸렸나)

## C) Exposure(실현 노출) 레벨
- **실현 익스포저(베타/섹터/순노출/레버리지)** 타임시리즈  
  - 성능이 안 움직이고 노출도 안 움직이면 “항상 같은 포트” 문제  
  - 성능이 안 움직이는데 노출이 요동치면 “리스크 스케일 착시/비용” 문제

## D) Cost(매매/슬리피지) 레벨
- **턴오버 버킷별 성과**(0~20/…/80~100%)  
  - 고턴오버에서만 망가지면 비용·슬리피지·임계값 문제
- **거래일 비중**(얼마나 자주 리밸런스했나) vs 성과 상관

## E) Regime(시장 상태) 레벨 — ETF는 관측만
- 레짐 분할: 예) QQQ 추세(상/하), XLK/XLV 상대강도(Tech 주도/Healthcare 주도)  
- 레짐별 승률/평균 수익/최대낙폭  
  - 특정 레짐에서만 유효하면 “전략이 나쁜 게 아니라 적용 조건” 문제  
  - 모든 레짐에서 무효면 “신호/비용/누수” 재점검
