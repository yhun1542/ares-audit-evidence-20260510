### 1) **재현성/아티팩트/로그 무결성 복구(운영 리스크 최우선)**

  - `file: (빈값)`, `lane_hash/run_hash: None` → 챔피언이 “무엇인지” 재현 불가.
  - `rebalance_pinpoint`가 `--base-log` 파일 없음 + `rebalance.csv` 파싱 실패 → 리밸런스/체결/회전율/비용 분해가 막혀 “성능 안 움직임” 원인 진단 불가.
- **위험/부작용**
  - 로깅/아티팩트 스키마 변경으로 기존 리포트/툴 체인 일부 깨질 수 있음(단, 지금도 이미 깨져 있음).
- **최소 실험(공유 실험 풀에서 선택 2~3개)**  
  - **E1(필수)**, E3, E5
- **PASS 조건**
  - 모든 런에서 `run_hash/lane_hash/champion_file_path`가 채워지고, `rebalance_pinpoint`가 에러 없이 끝나며(Exit 0), 리밸런스 로그가 “빈 파일/빈 JSON”이 아님.

### 2) **Degenerate fold(누수/과최적화 신호) 제거 + CV 게이트 강화**
- **왜 필요한지**
  - `degenerate_folds: [1,2,3,8]`는 평가가 사실상 무효/왜곡될 수 있다는 강한 신호(데이터 부족, split 오류, 누수, 라벨 정렬 문제 등).
  - 누수/폴드 붕괴가 있으면 OOS Mean이 “좋아 보이는데” 실전에서 전혀 안 움직이는 패턴이 흔함.
- **위험/부작용**
  - 누수/폴드 붕괴를 제거하면 단기적으로 OOS Mean이 하락할 수 있음(하지만 이게 정상).
- **최소 실험**
  - **E2(필수)**, E4
- **PASS 조건**
  - `degenerate_folds`가 빈 배열.
  - Fold별 샘플 수/거래 수가 최소치 이상(게이트에서 강제)이고, OOS 분산이 과도하게 폭발하지 않음.

### 3) **비용(슬리피지/스프레드/회전율) 모델을 “학습/선정 단계”에 강제 반영**
- **왜 필요한지**
  - 현재 리밸런스 로그가 없어서 비용 기여/회전율이 미지수. 비용 미반영은 “백테스트는 좋아 보이는데 실전은 정체”의 대표 원인.
- **위험/부작용**
  - 비용을 넣는 순간 기존 챔피언 성능이 크게 꺾일 수 있음(특히 고회전이면).
- **최소 실험**
  - **E3(필수)**, E1
- **PASS 조건**
  - Net 성능(비용 차감)이 Gross 대비 비정상적으로 붕괴하지 않음(예: Net OOS Mean이 Gross의 70% 미만으로 떨어지면 FAIL로 간주).
  - Turnover/거래횟수 지표가 로그로 남고, 비용이 성능의 몇 %를 깎는지 분해 가능.

## 48시간 자동 루프용 “실행 가능한 Patch/실험” 5개 (각각: 실험 정의 → 게이트 → 기대 관측치)

### E1) **아티팩트/리밸런스 로그 표준화 패치**
1) **실험 정의**
   - 모든 런에서 다음을 강제 저장:
     - `champion_file_path`, `run_hash`, `lane_hash`, git commit hash, 데이터 스냅샷 id
     - `rebalance.jsonl`(각 리밸런스일: 목표비중/체결가정/거래량/비용/슬리피지/턴오버/노출)
   - `aub_rebalance_pinpoint`가 읽는 입력 경로/포맷을 단일화(CSV/JSON 혼용 금지).
2) **게이트**
   - 파이프라인 종료 전 “필수 파일 존재 + JSON 파싱 OK” 체크(없으면 런 FAIL).

3) **기대 관측치**
   - “성능 안 움직임”을 **거래 부재/게이트 과도/비용 폭발/리밸런스 누락** 중 무엇인지 1회전 내에 바로 분해 가능.

### E2) **Degenerate fold 제거(시계열 CV, 퍼지/엠바고 포함)**
1) **실험 정의**
   - 시계열 split에서 최소 학습길이/테스트길이, 최소 거래 발생 수를 강제.
   - 라벨 누수 방지용 purge+embargo(예: lookahead 창만큼 간격) 적용.
   - fold가 조건 미달이면 자동으로 fold 수를 줄이거나 기간을 재할당.
2) **게이트**
   - `degenerate_folds == []` 아니면 FAIL.
   - Fold별 “거래 수/표본 수/노출 평균” 최소치 미달 시 FAIL.
3) **기대 관측치**
   - OOS Mean이 다소 내려가도 **분산 감소 + 재현성 상승**.
   - “좋아 보이던 성능이 갑자기 평범해지는” 경우 → 이전에 과대평가(누수/붕괴)였다는 증거 확보.

### E3) **비용/슬리피지 내재화(선정 단계부터 net 기준)**
1) **실험 정의**
   - 종목별 ADV 기반 슬리피지(거래대금/변동성/스프레드 proxy) + 고정 커미션을 비용으로 반영.

2) **게이트**
   - `net_oos_mean`을 1급 지표로 저장, gross/net 괴리가 임계치 초과 시 FAIL(예: net가 gross의 70% 미만).
   - 평균 회전율/거래횟수 상한(예: 월 turnover > X면 FAIL)을 게이트로 추가.
3) **기대 관측치**
   - 거래가 과도한 전략이 자동 탈락 → “실전에선 정체” 케이스 감소.
   - 로그에서 비용이 성능을 얼마나 깎는지 상시 추적 가능.

### E5) **레짐/노출 게이트(ETF는 관측만) + MDD 산출 강제**
1) **실험 정의**

   - 관측지표로 노출 스케일링(예: 리스크오프면 총노출 0.3~0.5로 축소).

2) **게이트**

   - `exposure_max` 정책 초과 시 FAIL(예: 0.65 초과).
   - 단일 종목 비중 상한 초과 시 FAIL(예: 15%).
3) **기대 관측치**
   - `oos_min`(최악 구간) 개선 또는 tail 손실 완화.
   - “좋은데도 정체” 구간에서 노출이 자동으로 줄어드는지 확인 가능.

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐) — 명령형 체크리스트

### A) 트리거(신호 발생) 문제
- **신호가 실제로 변하는지**: feature/score 시계열 분산이 0에 수렴하면 즉시 경고.
- **리밸런스 이벤트 수**: 48시간/최근 N일 동안 “리밸런스 0회”면 전략이 멈춘 것.
- **결측/NaN 전파**: NaN이 스코어를 0으로 만들며 거래가 사라지는 패턴 탐지.

### B) 적용(게이팅/제약) 문제
- **게이트로 전부 컷되는지**: “게이트 FAIL 사유 상위 3개”를 매 런 저장.
- **제약 충돌**: 종목 상한/섹터 상한/총노출 상한이 동시에 걸려 포트가 현금화되는지 확인.
- **degenerate fold 재발**: fold 붕괴가 다시 나타나면 그 시점 데이터 구간을 우선 격리.

### C) 노출(포지션/리밸런스) 문제
- **총노출 타임라인**: exposure가 0 근처(현금)로 붙어 있으면 “신호 없음/게이트 과도/유니버스 결측” 중 하나.
- **단일 종목 쏠림**: 상위 1~2 종목 비중이 과도하면 성능이 특정 종목에 종속되어 정체처럼 보일 수 있음.
- **턴오버 급증/급감**: 비용/정체의 양쪽 원인이므로 항상 같이 본다.

### D) 비용(슬리피지/스프레드) 문제
- **Gross vs Net 괴리**를 고정 리포트로 저장:
  - `gross_return`, `cost`, `net_return`의 분해가 없으면 원인 규명 불가(지금 상태가 여기에 해당).
- **비용이 “상승장/하락장”에서 비대칭인지**(하락장에 스프레드 확대) 확인.

### E) 레짐(시장 상태) 문제
- **관측 ETF로 레짐 태깅**(매매는 금지):
  - SPY 드로우다운, XLK 상대강도, VHT/IBB 상대강도, 금리 민감(간접) 구간을 태그.
- **레짐별 성능 테이블**: 레짐 A에서만 수익이 나고 B에서 0이면 “정체”로 보임 → 노출 스케일링(E5)로 대응.

## 48시간 실행 순서(우선순위 그대로, 질문 없이 바로 실행)
1) **E1 먼저 적용** → 로그/아티팩트/핀포인트 도구가 돌아가는지 확인(돌아가지 않으면 나머지 실험 결과 해석 불가).  
2) **E2 적용** → degenerate fold 제거로 OOS 신뢰도 확보.  
3) **E3 적용** → Net 기준으로 챔피언 선정을 강제(비용 미반영 제거).  
4) **E4 적용** → point-in-time 유니버스 고정으로 서바이버십 제거.  
5) **E5 적용** → 노출/레짐 게이트 + MDD 산출 강제(테일리스크/정체 구간 대응).

원하면 위 5개를 “동시에 다” 돌리지 말고, **E1→E2→E3**까지만 24시간 내에 통과시키고(E4/E5는 다음 24시간) 파이프라인 안정성을 먼저 확보하는 구성이 48시간 루프에 가장 잘 맞습니다.
