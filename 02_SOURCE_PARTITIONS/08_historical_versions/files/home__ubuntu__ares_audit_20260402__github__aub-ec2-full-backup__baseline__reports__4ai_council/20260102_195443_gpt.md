# 1) 24~48시간 우선순위 TOP5 제안 (명령형 체크리스트)

## Priority 1) (운영 리스크 1순위) “리밸런스/메타데이터 로깅” 복구
**(a) 왜 필요한지**
- 현재 상태에선 **거래가 실제로 어떻게 발생했는지(리밸런스, 체결, 턴오버)**가 증명되지 않아 **비용/슬리피지/노출/리스크**를 전부 검증할 수 없음.
- 성능이 움직이지 않는 원인이 “전략”이 아니라 “실험/로그 파이프라인 불능”일 가능성이 큼.

**(b) 위험/부작용**
- 로그 스키마 변경 시 기존 리포트 도구가 깨질 수 있음.
- 리밸런스 기록이 늘어나면서 저장/IO 비용 증가.

**(c) 최소 실험(아래 공용 실험 E1/E2 사용)**
- E1(로그/리밸런스 산출 복구)
- E2(비용 모델 붙여서 net 성능 산출)

**(d) PASS 조건**
- 모든 런에서 **rebalance.jsonl(또는 csv) 생성 + 파싱 성공**
- 각 타임스텝의 **목표가중치/실행가중치/체결가/수량/턴오버**가 1:1로 추적 가능
- champion/candidate 모두에서 **worst_mdd가 None이 아니게** 산출

---

## Priority 2) (비용 미반영 최우선) “턴오버-슬리피지-수수료”를 Net 기준으로 강제
**(a) 왜 필요한지**
- Tech/Healthcare 개별주 8~14개로 운용하면 리밸런스가 잦을수록 **성과가 비용에 잠식**됨.
- 현재 리밸런스 로그가 없어서 “고수익처럼 보이지만 거래로 소진”되는 패턴을 걸러내기 어려움.

**(b) 위험/부작용**
- gross 성능이 좋아 보이던 전략이 net에서 급락할 수 있음(하지만 이게 현실).
- 비용 가정이 과보수적이면 과도하게 보수 전략으로 쏠릴 수 있음 → 민감도 실험으로 완화.

**(c) 최소 실험**
- E2(비용/슬리피지 on + 민감도 2레벨)

**(d) PASS 조건**
- Net OOS mean이 **gross 대비 합리적 감소폭**(예: 턴오버와 일관된 감소)으로 설명 가능
- Net 기준으로도 **oos_min 방어**(최악 구간이 더 악화되지 않음)
- 비용 민감도(낮음/높음)에서 전략 순위가 “완전 뒤집히지” 않을 것(강건성)

---

## Priority 3) (누수/과최적화/서바이버십) “Time-split/Leakage/CV 퇴행” 수리
**(a) 왜 필요한지**
- degenerate_folds는 **누수/빈 폴드/라벨-피처 시점 불일치** 또는 데이터 인덱싱 오류의 전형적인 전조.
- OOS가 정체될 때 가장 흔한 원인은 “전략이 약함”보다 **검증이 왜곡**된 경우.

**(b) 위험/부작용**
- 누수 제거/엠바고 적용 후 성능이 내려갈 수 있음(정상).
- 학습 데이터가 줄어 분산이 증가할 수 있음 → 폴드 설계로 완화.

**(c) 최소 실험**
- E3(워크포워드 + purge/embargo + degenerate fold 0 만들기)

**(d) PASS 조건**
- degenerate_folds가 **빈 리스트**가 됨
- 폴드별 OOS 분산이 과도하지 않음(특정 폴드만 “터지는” 현상 감소)
- 동일 실험을 시드/시작일 소폭 변화에도 성능 순위가 유지(과최적화 완화)

---

## Priority 4) (노출/리스크) “8~14종목 + 포지션 상한 + MDD 산출”을 강제
**(a) 왜 필요한지**
- exposure_max 0.84 수준이면 부분 현금/미노출 구간이 존재할 수 있는데, 이것이 “알파”인지 “게이트/클램프/버그”인지 구분 불가.
- worst_mdd None은 위험관리 파이프라인이 작동하지 않음을 의미.

**(b) 위험/부작용**
- 강제 제약(종목 수, 상한, 섹터 밴드)이 성능을 일부 깎을 수 있음.
- 너무 타이트하면 신호가 있어도 못 타서 OOS mean이 떨어질 수 있음 → 제약 강도 2단계만 실험.

**(c) 최소 실험**
- E4(포지션/노출/리스크 제약 패치 + 2레벨 강도)

**(d) PASS 조건**
- 매 리밸런스 시 **보유 종목 수 8~14 유지**
- 단일 종목/섹터 쏠림이 상한 내(예: single name cap, sector cap)
- worst_mdd 산출 + tail(최악 구간) 방어가 개선(또는 동일 성능에서 MDD 감소)

## Priority 5) (성능 정체 해부) “레짐/트리거/적용/노출/비용” 분해 모니터 고정
**(a) 왜 필요한지**
- “성능이 안 움직임”은 보통 아래 중 하나:
  - 트리거가 안 울림(신호 희소)
  - 울리는데 적용이 안 됨(클램프/제약/현금화)
  - 적용되는데 비용으로 상쇄
  - 레짐이 바뀜(Tech/Healthcare가 방어/공격 국면 전환)
- ETF는 매매 금지지만 **레짐 관측 지표**로는 가장 안정적.

**(b) 위험/부작용**
- 모니터가 많아져 운영이 복잡해질 수 있음 → “필수 6개 지표”만 고정.

**(c) 최소 실험**
- E1 로그가 복구되면 자동으로 파생 지표 산출(추가 실험으로 늘리지 않음)
- E3/E4 결과를 레짐별로 슬라이스(추가 실험 없이 리포팅만)

**(d) PASS 조건**
- 매 런마다 동일 포맷으로 “정체 원인 1순위”가 수치로 찍힘(예: trigger rate 0.2% / turnover 250% / cost drag -Xbp 등)
- 원인 카테고리가 매번 바뀌지 않고 일관되게 추적됨(재현성)

# 2) 48시간 자동 루프용 “실행 가능한 패치/실험” 4개 (3~5개 제한 준수)

아래 4개만 돌려도 TOP5의 대부분을 커버한다.

---

## E1) Rebalance/Run 아티팩트 표준화 패치 (로그 복구)
**(1) 실험 정의**
- 백테스트/실험 종료 시 아래를 **항상 생성**:
  - `run_meta.json` (run_hash, lane_hash, git_sha, 데이터 스냅샷 id, 시드, 시작/종료, 유니버스 버전)
  - `rebalance.jsonl` (timestamp, target_w, exec_w, price, shares, turnover, reason_code)
  - `risk.json` (gross/net exposure, concentration, MDD, VaR/ES 간단 버전)
- 기존 도구(`aub_rebalance_pinpoint.py`)가 읽을 스키마에 맞춰 **csv/jsonl 둘 중 하나로 고정**.

**(2) 게이트(실패 시 즉시 중단)**
- 파일 존재 + JSON 파싱 100% 성공
- 리밸런스 레코드 수가 타임스텝과 정합(0개/NaN/빈 파일이면 FAIL)
- worst_mdd가 None이면 FAIL

**(3) 기대 관측치**
- turnover/time, 거래 빈도, 현금비중, 이유코드(제약으로 못 삼/못 팜 등) 분포가 출력됨
- pinpoint 리포트가 “데이터 없음” 대신 실제 차이를 지목

---

## E2) 비용/슬리피지 Net 강제 + 민감도 2레벨
**(1) 실험 정의**
- 거래비용을 Net PnL에 반영:
  - 고정 수수료(주당 또는 bps) + 슬리피지(bps) + 스프레드 근사
- 민감도 2레벨만:
  - LOW: 5–10bps 수준
  - HIGH: 20–40bps 수준 (유동성 낮은 종목 대비)

**(2) 게이트**
- gross/net 리턴이 동시에 저장되고, cost_drag(bps/day)가 계산됨
- turnover가 0인데 cost가 발생하거나(버그), turnover가 큰데 cost가 0이면 FAIL

**(3) 기대 관측치**
- “성능 정체”가 비용 때문인지 즉시 판별:
  - gross는 괜찮은데 net이 눌리면 → 리밸런스/턴오버 문제
  - 둘 다 약하면 → 신호/레짐/누수 문제로 이동

---

## E3) Purge/Embargo 포함 Walk-forward 검증으로 degenerate_folds 제거
**(1) 실험 정의**
- 시간축 검증을 강제:
  - walk-forward(예: train N개월 / test 1개월 롤링)
  - 라벨-피처 시점이 겹치지 않도록 purge window + embargo 적용
- 폴드 생성 로직에 진단 로그를 추가(폴드 길이, 공통 인덱스 수, 결측률).

**(2) 게이트**
- degenerate_folds == [] 아니면 FAIL
- 각 폴드의 샘플 수가 최소 기준 미만이면 FAIL(“빈 폴드” 방지)

**(3) 기대 관측치**
- 폴드별 OOS mean 분산이 합리적으로 줄어듦
- 기존 OOS가 “좋았는데” 이 실험에서 급락하면 → 누수/정합성 문제가 원인이었을 확률 상승

---

## E4) 포지션/노출/리스크 제약 패치 (8~14종목 + 상한 + MDD)
**(1) 실험 정의**
- 종목 수를 항상 8~14로 유지(부족하면 신호 상위로 채우되 상한 유지)
- 단일 종목 상한, 섹터(Tech/Healthcare) 밴드, gross/net exposure 상한
- 리스크 타겟(간단): 변동성 타겟 또는 최대 익스포저 클램프 2레벨
  - Loose / Tight 두 단계만

**(2) 게이트**
- 모든 리밸런스에서 보유 종목 수 8~14 유지(위반 시 FAIL)
- worst_mdd 산출 + 노출 min/max가 정의 범위 내
- 극단 쏠림(단일 종목 비중 초과) 발생 시 FAIL

**(3) 기대 관측치**
- oos_min 및 tail 구간이 방어되거나, 최소한 동일 성능 대비 MDD 개선
- “성능이 안 움직임”이 사실은 클램프에 의한 미노출 때문인지(현금비중↑) 확인 가능

# 3) 성능이 안 움직일 때 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래는 **원인 트리(명령형 체크리스트)**로 고정해서 매 런마다 찍어라. (질문 금지 조건 준수: “확인/계산/출력”만 지시)

## A. Trigger(신호 발생) 문제
- **신호 발생률(trigger rate)** 출력: 전체 바 대비 포지션 변경 신호 비율
- 상위 신호(Top-K) 스코어 분포의 분산/왜도 출력: 스코어가 납작하면 알파 약화
- 피처 드리프트 지표 출력: 최근 1개월 vs 과거 학습구간의 Z-score 이동(간단 KS/PSI도 가능)

## B. Apply(적용/집행) 문제
- 제약으로 주문이 잘렸는지(reason_code) 비율 출력:
  - “max position cap”, “sector cap”, “min lot”, “cash clamp”
- target_w 대비 exec_w 괴리(슬리피지/부분체결 가정 포함) 평균/최댓값 출력
- 리밸런스가 0건인데 신호는 존재하면 → 스케줄러/게이트 버그로 분류

## C. Exposure(노출) 문제
- gross/net exposure 타임시리즈 출력 + 현금비중 출력
- 8~14 종목 규칙 위반 여부 카운트(0이 아니면 그 자체로 운영 장애)
- concentration(HHI)와 상위 1~3종목 기여도 출력(쏠림이면 레짐에 취약)

## D. Cost(비용) 문제
- turnover와 cost_drag(bps)를 같은 그래프/테이블로 출력
- gross alpha - cost = net alpha 분해표를 고정 출력
- 비용 민감도(LOW/HIGH)에서 결과가 급변하면 → “턴오버 기반 가짜 알파”로 분류

## E. Regime(레짐) 문제 — ETF는 관측 지표로만
- 관측 ETF(매매 금지): **XLK(Tech), XLV(Healthcare), IHI(의료기기), QQQ(대형 성장)**  
- 레짐 슬라이스 리포트 생성:
  - XLK 상대강도(예: XLK/SPY 모멘텀) 상/하 구간
  - 금리 민감(간단히 10Y proxy가 없으면 QQQ vs DIA 같은 대체도 가능)
- 레짐별로 “trigger rate / net exposure / net return / MDD”를 테이블로 고정 출력

---

## 24~48시간 실행 순서(권장)
1) **E1 먼저**(로그/리밸런스/메타데이터 복구) → 실패 시 나머지 실험 전부 중단  
2) **E2 즉시**(비용 반영) → net 기준으로 의미 있는지 확인  
3) **E3**(degenerate_folds 제거) → 누수/검증왜곡 제거  
4) **E4**(8~14 + 리스크 제약 2레벨) → 운영 가능한 형태로 수렴

이 4개가 돌아가면, 성능 정체의 원인이 **신호 부재(Trigger)**인지 **제약/집행(Apply)**인지 **미노출(Exposure)**인지 **비용(Cost)**인지 **레짐(Regime)**인지가 자동으로 분리된다.
