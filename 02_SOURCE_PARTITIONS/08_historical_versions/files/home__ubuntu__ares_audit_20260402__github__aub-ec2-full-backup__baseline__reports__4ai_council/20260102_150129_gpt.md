## 24~48시간 TOP5 우선순위 (코드/아키텍처/전략) — **명령형 체크리스트**
(누수/과최적화/서바이버십/비용 미반영/운영 리스크 우선)

# 1) **리밸런스/평가 로깅 복구 + 지표 “ONE TRUTH” 정합성 확보 (운영 리스크 최우선)**
### (a) 왜 필요한지
- 현재 `aub_rebalance_pinpoint`가 **입력 경로 오류 + JSON 파싱 실패**로 리밸런스 로그를 못 읽음 → “왜 성능이 안 움직이는지”를 **관측 불가**.
- `Current Champion oos_mean(1.88)` vs `No-Delta Diagnoser Champion OOS Mean(2.63)` **지표 불일치** → 다른 베이스 파일/스코어링 경로를 보고 있을 가능성(실험이 쌓여도 결론이 흔들림).

### (b) 위험/부작용
- 로깅 포맷 변경 시 기존 리포트 도구가 깨질 수 있음(역호환 필요).
- “정합성 체크”가 엄격하면 일부 실험이 실패로 중단될 수 있음(하지만 이게 안전한 실패).

### (c) 최소 실험 2~3개 (48시간 자동 루프 형태)
**Patch/Experiment 1 (로깅-정합성 패치)**  
1) **실험 정의**
   - E1-1: `rebalance.csv/jsonl` 생성 강제(없으면 실패) + 경로를 “실행 artifact 내부 상대경로”로 고정  
     - `--base-log`에 문자열 `--base-log` 자체가 들어간 현재 오류를 막기 위해 **argparse 기본값/호출부를 교정**  
   - E1-2: “스코어 계산” 단일화: backtest 결과 JSON에 `oos_mean`, `oos_min`, `mdd`, `turnover`, `cost`를 **동일 함수**로 계산/기록하고, diagnoser가 그 값을 읽도록 통일
   - E1-3: `worst_mdd: None` 금지 → MDD 계산 실패 시 예외 발생(조용히 None으로 통과 금지)

2) **게이트(실험 시작/중단 조건)**
   - G1: 실행 종료 시 `rebalance.jsonl`(또는 csv) **파일 존재 + 0바이트 아님** 아니면 FAIL
   - G2: `oos_mean`이 “champion json”과 “diagnoser 출력” 간 **절대오차 1e-6 이내** 아니면 FAIL
   - G3: `mdd`가 float로 기록되지 않으면 FAIL

3) **기대 관측치**
   - 리밸런스 이벤트 개수/일자/종목/수량/체결가/비용이 **핀포인트 리포트에서 확인 가능**
   - “No-Delta(성능 변화 없음)”의 원인이 **신호 미발생 vs 게이트/클램프 vs 비용** 중 어디인지 분해 가능

### (d) PASS 조건
- 핀포인트 리포트가 최소 1개 실험에 대해 **리밸런스 차이(diff)** 를 출력
- OOS 지표가 모든 툴에서 **동일 값으로 수렴**
- MDD/turnover/cost가 None 없이 기록

# 2) **누수/시간정렬/서바이버십 “하드 게이트” 추가 (과최적화·서바이버십 방지)**
### (a) 왜 필요한지
- Tech+Healthcare 소수(8~14) 포트는 작은 누수에도 성능이 “움직이는 척” 하다가 OOS에서 멈추는 패턴이 잦음.
- 특히 **데이터 시점 정렬(발표/체결/가격) + 생존 편향(현재 상장만)** 은 가장 흔한 “No-Delta/가짜 개선” 원인.

### (b) 위험/부작용
- 누수 제거 후 성능 하락이 발생할 수 있음(정상).
- 데이터 소스에 따라 “정확한 발표시각”이 없으면 보수적 딜레이로 알파가 줄 수 있음.

### (c) 최소 실험 2~3개
**Patch/Experiment 2 (Leakage/Survivorship 게이트)**  
1) **실험 정의**
   - E2-1: 모든 feature/라벨에 대해 **최소 1바(1 trading day) 딜레이 강제**(가격/지표/펀더멘털 구분 없이 일괄) 후 OOS 재평가
   - E2-2: **point-in-time 유니버스 스냅샷** 적용(해당 날짜에 거래 가능 종목만) + delisted 포함 가능하면 포함(불가하면 “상장폐지 발생 시 0원 청산” 보수 규칙)
   - E2-3: 폴드/윈도우에 대해 “미래 정보가 섞이는 경로”를 찾는 **assertion** 삽입  
     - 예: feature timestamp ≤ decision timestamp, decision ≤ execution

2) **게이트**
   - G2-1: “딜레이 강제” 모드에서 성능이 급락해도 OK, 대신 **성과가 좋아지면 누수 의심**으로 FAIL(=원인 규명 필요)
   - G2-2: 유니버스 스냅샷 적용 시 종목 수가 8~14를 충족 못하면 해당 구간 **현금 비중으로 처리**하고 로그에 남길 것(조용히 종목을 대체하지 말 것)

3) **기대 관측치**
   - “성능이 안 움직임”이 **누수 제거로 인해 원래부터 없던 알파였는지** 즉시 판별
   - 특정 기간에 유니버스 공백/거래불가가 얼마나 자주 발생하는지 노출

### (d) PASS 조건
- 모든 실행에서 “timestamp assertion” 0건 위반
- OOS 성능/턴오버/비용이 “딜레이/스냅샷” 변경에 대해 **해석 가능한 방향**으로 변함(무변화면 다른 원인으로 이동)

# 3) **비용(거래비용/슬리피지/숏 비용) 모델을 지표에 ‘강제 반영’ (비용 미반영 방지)**
### (a) 왜 필요한지
- 8~14 집중 포트는 리밸런스/교체가 조금만 늘어도 **실현 성과가 비용에 잠식**됨.
- 현재 로그/리포트가 깨진 상태에서는 비용이 실제로 반영되는지 확인도 불가.

### (b) 위험/부작용
- 비용 반영 후 성능 하락 가능(정상).
- 너무 보수적 비용은 전략 탐색을 조기에 죽일 수 있음(하지만 “현실성 게이트”가 우선).

### (c) 최소 실험 2~3개
**Patch/Experiment 3 (Cost-on, 비용 민감도 스윕)**  
1) **실험 정의**
   - E3-1: 기본 비용 모델 강제:  
     - 주식: `commission=0`(현실에 맞춰도 무방) + `slippage_bps`(고정) + `spread_bps`(고정)  
     - 숏/헤지 사용 시: `borrow_bps`(고정) 추가
   - E3-2: 비용 민감도 2포인트만 테스트(케이스 폭발 방지):  
     - Low: 5~10bps, High: 20~30bps (전략 특성에 맞게 설정)
   - E3-3: turnover 상한 게이트 추가(예: 일간/주간 회전율 제한) — 제한 걸리면 “trade skip” 로그

2) **게이트**
   - G3-1: 리포트에 `gross_return`, `net_return`, `total_cost`, `turnover`가 모두 기록되지 않으면 FAIL
   - G3-2: High-cost에서 성과가 gross 대비 과도하게 붕괴하면(예: net이 gross의 50% 미만) **“거래 구조 문제”로 분류**하고 전략 수정 우선순위 상승

3) **기대 관측치**
   - “성능이 안 움직임”이 사실은 **비용이 알파를 덮는 상황**인지 즉시 드러남
   - turnover가 특정 트리거/레짐에서 튀는지(리밸런스 핀포인트로) 확인 가능

### (d) PASS 조건
- net 지표가 항상 산출되고, 비용 스윕에 대해 net이 합리적으로 단조 감소(모델이 실제로 적용됨)
- turnover 상한이 작동해도 포트가 8~14 범위 내에서 안정 유지(현금 처리 포함)

# 4) **노출(Exposure)·포트 구성 제약을 “하드”로 고정 (과최적화/운영 리스크 완화)**
### (a) 왜 필요한지
- 현재 exposure min/max가 0.47~0.84로 **일관되지 않음** → 신호가 약한 구간에 현금이 쌓이거나(의도라면 OK) 혹은 제약 충돌로 주문이 막힐 수 있음.
- 8~14 종목 제약(Tech+Healthcare 중심)을 운영적으로 고정하지 않으면, 테스트/실거래 괴리가 커짐.

### (b) 위험/부작용
- 제약이 강해지면 백테스트 성능이 낮아질 수 있음(정상).
- 제약 충돌(예: 후보 종목 부족) 시 현금 비중이 증가 → 기회비용 발생.

### (c) 최소 실험 2~3개
**Patch/Experiment 4 (Exposure/Constituents 하드 제약 + 실패 로깅)**  
1) **실험 정의**
   - E4-1: “항상 8~14개” 강제: 후보 부족 시 **현금**으로 채우고 그 사유를 로그(“insufficient candidates”)
   - E4-2: 섹터 바스켓(Tech+Healthcare) 강제: 분류 불명/기타 섹터는 **0% 목표**(예외 허용 시 상한 5% 등)
   - E4-3: 노출 타겟 범위 고정(예: gross exposure 0.8~1.0) + 벗어나면 주문을 스케일링해서 맞춤

2) **게이트**
   - G4-1: 각 리밸런스 시점에 holdings count가 8~14 밖이면 FAIL(단, “현금 포함 count” 기준으로 통과하도록 정의)
   - G4-2: 섹터 위반 비중이 상한 초과하면 FAIL
   - G4-3: 노출 범위 이탈이 연속 N회 발생하면 FAIL(제약 충돌)

3) **기대 관측치**
   - 성능 정체가 “제약 때문에 신호가 표현이 안 되는 문제”인지 판별
   - 후보 부족/분류 문제/주문 스케일 문제를 로그로 즉시 확인

### (d) PASS 조건
- 모든 기간에 대해 포트 구성 제약이 자동으로 만족되며, 위반 시 **명시적 FAIL**로 멈춤(조용히 통과 금지)

# 5) **레짐(시장 상태) 기반 스케일링만 추가 (ETF는 ‘관측지표’로만)**
### (a) 왜 필요한지
- “No-Delta(성능이 안 움직임)”는 종종 **레짐 미스매치**(변동성/금리/리스크온오프)에서 발생.
- ETF는 매매 제외 규칙이므로, **XLK/XLV/QQQ/SPY, VIX(또는 VIX proxy)** 를 “스위치/스케일” 관측 지표로만 사용해 리스크를 조절하는 게 안전한 48시간 패치.

### (b) 위험/부작용
- 레짐 필터가 과하면 “거의 안 들어가는 전략”이 되어 OOS mean이 정체될 수 있음.
- 레짐 규칙이 임의적이면 또 다른 과최적화 축이 됨 → 규칙 수를 최소화해야 함.

### (c) 최소 실험 2~3개
**Patch/Experiment 5 (Regime scaling only, 2-rule max)**  
1) **실험 정의**
   - E5-1: 변동성 기반 노출 스케일: (예) VIX 높음 구간에는 exposure를 0.6으로, 낮음 구간에는 0.9로(정확한 수치는 고정, 최적화 금지)
   - E5-2: 섹터 상대강도 스케일: XLK vs XLV 상대 모멘텀(관측)으로 Tech/Healthcare 내 비중을 60/40 ↔ 40/60 정도로만 이동(종목 선택 로직은 그대로)
   - E5-3: “필터”가 아니라 “스케일”만 허용(거래 중단 X) — 중단하면 표본이 줄어 과최적화 위험 증가

2) **게이트**
   - G5-1: 레짐 규칙 수 2개 초과 시 FAIL(규칙 폭발 방지)
   - G5-2: 레짐 스케일링으로 인해 turnover가 증가하면 FAIL(리스크 완화 목적 위배)

3) **기대 관측치**
   - 레짐에 따라 성과 분산이 줄고, MDD/하방 tail이 개선되는지 확인
   - “성능이 안 움직임”이 레짐 때문인지(특정 구간에서만 죽는지) 분해 가능

### (d) PASS 조건
- net 기준 MDD 개선(또는 worst-week 손실 축소) + turnover 비증가
- 레짐별 성과가 “한쪽 레짐에만 몰빵”되지 않고 분산(극단적 편향이면 재검토)

# 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐)
아래는 **관측 지표(로그/리포트)로 바로 분해**하도록 설계된 체크 트리(질문 금지, 실행만).

## A) 트리거(신호 생성) 문제
- **실행:** 각 리밸런스 시점에 `signal_score 분포(평균/표준편차/상위-하위 스프레드)`를 저장
- **판정:** 스프레드가 거의 0이면 → “모델이 사실상 상수” 또는 데이터 정렬/결측 처리로 죽음

## B) 적용(주문/체결) 문제
- **실행:** 목표포지션 vs 실제포지션 괴리를 `tracking_error_notional`로 기록
- **판정:** 괴리가 지속되면 → 최소주문단위/가격누락/거래정지/제약 충돌/스케일링 버그

## C) 노출(제약/클램프) 문제
- **실행:** 매 시점 `exposure_before/after_clamp`, `clamp_reason` 로그
- **판정:** after_clamp가 항상 비슷하면 → 전략이 아니라 “클램프가 포트 결정”

## D) 비용(턴오버/슬리피지) 문제
- **실행:** `gross_pnl`, `cost`, `net_pnl`을 일별로 분해 + turnover와 함께 저장
- **판정:** gross는 괜찮은데 net이 정체면 → 거래빈도/리밸런스 규칙/체결 가정이 원인

## E) 레짐(시장 상태) 문제
- **실행:** 구간별(예: VIX 상/하, SPY 추세 상/하) 성과 테이블을 자동 생성(ETF는 관측만)
- **판정:** 특정 레짐에서만 급락이면 → 스케일링(패치5)로 완화 여지, 아니면 신호 자체를 레짐별로 분리해야 함(다음 사이클 과제로 넘김)

원칙 준수 확인(요약)
- 누수/과최적화/서바이버십/비용/운영리스크를 **1~3번에서 선제 봉쇄**
