## 다음 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — 명령형 체크리스트

### 1) **누수(lookahead)·정렬(as-of)·서바이버십을 최우선으로 “증명/차단”**
**(a) 왜 필요한지**
- “성능이 안 움직임”의 1순위 원인은 **누수/정렬 오류로 인한 가짜 안정성** 또는 **서바이버십으로 인한 과대추정**임.
- 현재 `degenerate_folds`가 존재 → 폴드가 실질적으로 학습/검증을 못하는 경우가 섞여 있을 가능성↑(데이터 누락/정렬/트레이드 수 부족/리밸런스 이벤트 부재).

**(b) 위험/부작용**
- 누수 차단 후 성능 급락 가능(정상 반응).
- PIT(포인트-인-타임) 재구축으로 데이터량 감소/공백 증가 → 포지션 8~14 유지가 더 어려워질 수 있음.

**(c) 최소 실험(아래 공용 실험 ID 재사용)**
- **E1 + E2** 실행(아래 “48시간 자동 루프 실험 5개” 참조)
- (선택적으로 동일 실험 내) **델리스팅 리턴/심볼 히스토리 반영 토글** 비교

**(d) PASS 조건**
- **E2(시프트 테스트)**에서: `features +1day` 성능이 **유의미하게 악화**되고, `-1day`에서 **개선이 발생하지 않을 것**(개선되면 누수 의심).
- **E1(서바이버십/PIT 토글)**에서: PIT 적용 시 성능이 일부 하락하더라도 **폴드 퇴화(degenerate) 감소 + 분포 안정화**가 동반될 것.


---

### 2) **과최적화/폴드 퇴화(degenerate folds) 제거: Purged/Embargo CV + “최소 트레이드 폴드 게이트”**
**(a) 왜 필요한지**
- 현재 `degenerate_folds: [1,2,3,8]` → OOS 평균이 의미 없거나 “무거래 폴드”가 섞여 있을 가능성.
- 과최적화는 **CV가 실제 운용 리밸런스/홀딩 구조를 반영하지 못할 때** 가장 심해짐.

**(b) 위험/부작용**
- 더 엄격한 CV 적용 시 실험 실패율↑(통과 모델 수↓).
- 성능 개선보다 “안정성 지표” 개선이 먼저 나타날 수 있음.

**(c) 최소 실험**
- **E3 + E5** 실행(특히 E5는 리밸런스 이벤트 로그가 있어야 E3 진단도 빨라짐)
- E3에서 **폴드별 최소 리밸런스 횟수/거래횟수 조건**을 강제

**(d) PASS 조건**
- `degenerate_folds`가 **0 또는 1 이하**로 감소.
- OOS 평균이 비슷하더라도 **폴드 간 분산 감소(안정화)** + **worst_mdd 산출 가능(누락 None 제거)**.


---

### 3) **비용(수수료/스프레드/슬리피지/임팩트) 미반영을 즉시 반영 + 회전율(턴오버) 상한**
**(a) 왜 필요한지**
- 비용 미반영은 “백테스트 성능은 유지되는데 실운용은 안 움직임/녹아내림”의 대표 원인.
- `exposure_max ~0.84`이면 리밸런스가 잦을 때 비용 충격이 커짐(특히 8~14개 집중 포트폴리오).

**(b) 위험/부작용**
- 비용을 넣으면 대부분의 실험이 급락 → 탐색 공간 재설계 필요.
- 지나친 턴오버 억제는 신호 반응성을 떨어뜨릴 수 있음.

**(c) 최소 실험**
- **E4 + E3** 실행(비용 포함 상태에서 CV 안정성까지 같이 확인)
- E4에서 비용 레벨 스윕(낮음/중간/높음)으로 “비용 민감도 곡선”을 얻기

**(d) PASS 조건**
- “중간 비용” 가정에서 **Net OOS가 플러스 유지** + 턴오버가 상한 이하(예: 일일/주간 리밸런스 기준 내부 정책치).
- 비용 레벨을 올려도 **성능 붕괴가 완만(민감도 완화)**할 것.


---

### 4) **운영 리스크(재현성/관측 불가) 제거: 리밸런스 로그·아티팩트 표준화**
**(a) 왜 필요한지**
- 현재 리밸런스 핀포인트가 `--base-log` 파일 미존재/CSV 파싱 실패 → **실험 간 차이가 어디서 났는지 추적 불가**.
- “성능이 안 움직임”도 **진단 불능(관측 불가)** 상태면 시간만 소모.

**(b) 위험/부작용**
- 로그 표준화 작업이 단기적으로 성능 개선을 직접 만들진 않음.
- 포맷 변경 시 기존 도구/리포트가 깨질 수 있음(마이그레이션 필요).

**(c) 최소 실험**
- **E5 + E3** 실행
- E5에서 “리밸런스 이벤트(타임스탬프/사유/목표비중/체결가정/비용/턴오버)”를 JSONL로 강제 출력

**(d) PASS 조건**
- `aub_rebalance_pinpoint`가 **base/cand 모두에서 데이터 로드 성공**.
- 실험 간 성능 차이가 날 때 **‘언제/무엇을/얼마나’ 바뀌었는지 1분 내 pinpoint** 가능.


---

### 5) **전략 제약(미국주식 Tech+Healthcare, 8~14종목, ETF 매매 제외) 하에서 노출/리스크 일관성 확보**
**(a) 왜 필요한지**
- 제약이 강할수록 모델이 “실제 운용 가능한 포트폴리오”로 수렴하지 않으면 OOS가 흔들림.
- 현 상태에서 `exposure_min/max: 0.0 / 0.84` → **노출이 들쭉날쭉**할 가능성(레짐 대응/신호 부재 시 캐시 비중 변동이 과대).

**(b) 위험/부작용**
- 종목수(8~14)·섹터(Tech/Healthcare) 강제는 신호 부족 시 품질 저하 가능.
- 노출 캡/단일종목 캡은 “잘 될 때의 상방”을 제한.

**(c) 최소 실험**
- **E4 + E3**로 (비용 포함 + 안정 CV) 상태에서
  - 포지션 수 강제(8~14), 단일 종목 상한, 섹터 바스켓 편중 상한을 적용한 포트폴리오 빌더 비교

**(d) PASS 조건**
- 항상 **8~14 유지(결측/거래불가 시 대체 규칙 포함)**.
- 노출/턴오버/단일종목 최대비중이 **정책 범위 내**에서 OOS가 유지/개선.
- (관측지표로만) XLK/XLV/QQQ/SPY 레짐 구간별 성능 편차가 과도하지 않을 것.


---

## 48시간 자동 루프용 “공용 실험 5개”(3~5개 제한 준수)  
각 실험은 **(1) 실험 정의 → (2) 게이트 → (3) 기대 관측치**로 구성.  
아래 5개를 돌리면 위 TOP5 우선순위에 모두 커버되도록 설계함.

---

### **E1) PIT/서바이버십 토글 실험(데이터 정합성)**
1) **실험 정의**
- Universe/가격/재무/이벤트(분할·배당)에서 **PIT(포인트-인-타임) 적용 ON/OFF** 2-런 비교.
- 델리스팅/심볼 변경/상장폐지 리턴 처리 토글 포함(가능하면).

2) **게이트**
- 폴드별 유효 리밸런스 수(또는 트레이드 수) 최소치 미달 시 FAIL.
- PIT ON에서 결측률 급증 시(정책 임계치 초과) FAIL → 데이터 파이프 보강 티켓 생성.

3) **기대 관측치**
- PIT ON에서 성능이 하락하더라도 **폴드 퇴화 감소**, 수익 분포가 더 현실적으로 변함.
- 특정 기간/섹터에서만 급변하면 해당 데이터 소스(재무 업데이트 시점 등) 누수 의심 포인트가 좁혀짐.

---

### **E2) 시프트(±1day)·라벨 랜덤화 누수 탐지**
1) **실험 정의**
- 동일 파이프라인에서 `features shift +1d`, `features shift -1d`, `label random` 3런(또는 2런으로 축소 가능).

2) **게이트**
- `shift +1d`가 원본 대비 성능이 비슷하거나 개선되면 **즉시 FAIL(누수 의심)**.
- `label random`에서 유의 성능이 나오면 **즉시 FAIL(파이프라인/평가 누수)**.

3) **기대 관측치**
- 정상이라면: 원본 > (+1d) 이고, 랜덤은 0 근처로 수렴.
- FAIL 시: 누수 위치를 “특징 생성 시점/리밸런스 가격/체결가정”으로 분해할 근거가 확보됨.

---

### **E3) Purged/Embargo CV + 폴드 최소거래 게이트**
1) **실험 정의**
- 시간순 CV를 **purge + embargo**(리밸런스 윈도우만큼)로 변경.
- 폴드별 “최소 리밸런스/최소 트레이드”를 강제하여 degenerate fold를 구조적으로 제거.

2) **게이트**
- `degenerate_folds == 0(권장) 또는 <=1` 아니면 FAIL.
- `worst_mdd`가 None이면 FAIL(리포트 산출 파이프 결함으로 간주).

3) **기대 관측치**
- OOS 평균이 약간 내려가도 **폴드 간 분산 감소**, 운영 가능한 모델만 남음.
- 진짜 개선은 E4(비용) 포함 후에도 유지되는지로 판단 가능.

---

### **E4) 비용+턴오버 패널티 스윕(운용 현실화)**
1) **실험 정의**
- 거래비용 모델(수수료+스프레드+슬리피지) 3레벨(예: Low/Med/High bps) 스윕.
- 포트폴리오 목적함수에 **턴오버 패널티**(또는 리밸런스 임계값/밴드) 1개만 추가(과도한 탐색 금지).
- 종목 8~14, Tech+Healthcare 필터를 강제(ETF 매매 없음).

2) **게이트**
- Med 비용에서 Net OOS < 0 이면 FAIL(또는 현 챔피언 대비 -X% 이상 하락 시 FAIL).
- 평균 종목 수가 8~14 밖으로 벗어나면 FAIL.

3) **기대 관측치**
- 비용 레벨 증가에 따라 성능이 선형/완만하게 감소(“붕괴”가 아니라 “감쇠”)하면 정상.
- 턴오버가 내려가면서도 OOS가 크게 훼손되지 않는 파라미터가 나타나야 함.

---

### **E5) 리밸런스 로그 표준화 + pinpoint 도구 복구**
1) **실험 정의**
- 모든 런에서 `rebalance.jsonl`(또는 csv) 강제 생성:
  - timestamp, target weights, prev weights, turnover, cost, fill assumption, reason(신호/리스크/제약), universe size, missing symbols
- `aub_rebalance_pinpoint`가 base/cand를 정상 비교하도록 경로/포맷 고정.

2) **게이트**
- 로그 파일 로드 실패 시 FAIL.
- 리밸런스 이벤트가 0이면 FAIL(전략이 “거래 안 함”으로 퇴화했는지 즉시 확인).

3) **기대 관측치**
- 성능이 안 움직일 때도 **원인이 “신호 무변화 vs 제약에 의한 무거래 vs 노출 캡” 중 어디인지** 로그만으로 1차 판별 가능.

---

## 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 명령형 트리

### A) 트리거(신호 발생) 단계
- **신호 발생률(일/주 리밸런스 기준)**을 집계하라: `#rebalance_events`, `#trade_signals`, `signal_strength 분포`.
- **상위/하위 신호 종목이 매번 동일한지** 확인하라(과도한 고정 → 과최적화/데이터 편향).
- **E2 시프트/랜덤 테스트 결과로 누수 여부를 먼저 확정**하라.

### B) 적용(포트폴리오 빌드/제약) 단계
- 제약으로 인해 “신호가 있어도 못 사는” 케이스를 로그로 남겨라:
  - `constraint_binding_rate`(종목수 8~14, 섹터 필터, 단일종목 상한, 노출 상한)
- **리밸런스 목표비중 vs 실제 적용비중(제약 후)** 괴리를 기록하라.

### C) 노출(Exposure) 단계
- `gross/net exposure`, `top1/top3 weight`, `sector weights(Tech/Healthcare 내 서브산업)`의 분포를 폴드별로 비교하라.
- `exposure_min=0` 구간이 잦으면: “신호 부재로 캐시화”인지 “제약/데이터 결측으로 포트 구성 실패”인지 분리하라(E5 로그로 즉시 가능).

### D) 비용/체결(현실 마찰) 단계
- **턴오버×비용의 손익 기여도를 분해**하라: `gross_pnl`, `cost_pnl`, `net_pnl`.
- 비용 미반영 상태에서만 좋은 모델은 버려라(E4로 즉시 선별).

### E) 레짐(시장 국면) 단계 — ETF는 관측지표로만 사용
- 레짐 라벨을 단순화해 먼저 관측하라(케이스 폭발 금지):
  - 예: `SPY 추세(상/하)`, `QQQ 변동성(상/하)`, `XLK-XLV 상대강도(Tech vs Health)`  
- 레짐별로 **신호 발생률/턴오버/성과**를 표 하나로 고정 출력하라(매 48시간 자동 리포트).

---

## 바로 실행 순서(48시간 내)
1) **E5 먼저** 돌려서 “관측 가능성”을 복구하라(리밸런스 로그/핀포인트 도구가 먼저 살아야 다음 디버깅이 빨라짐).
2) **E2 → E1** 순으로 누수/서바이버십을 확정하라(FAIL이면 전략 튜닝 금지, 파이프라인 수정으로 전환).
3) **E3**로 degenerate fold 제거 및 OOS 안정성 확보.
4) **E4**로 비용+턴오버 현실화 후에도 남는 후보만 챔피언 경쟁에 올려라.

위 5개 실험(E1~E5)만으로 누수/과최적화/서바이버십/비용/운영리스크를 우선 정리하면서, 미국주식 Tech+Healthcare 8~14종목 제약 하에서 “성능이 왜 안 움직이는지”를 48시간 루프 안에서 계속 분해 가능하게 만든다.
