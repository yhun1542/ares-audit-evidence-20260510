## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — **명령형 체크리스트**
(누수/과최적화/서바이버십/비용 미반영/운영 리스크 순으로 배치)

---

# 1) **평가 파이프라인 “무효 실험” 제거(degenerate folds, 로그/해시 누락)**
### (a) 왜 필요한지
- `degenerate_folds: [1,2,3,8]`는 **검증 구간이 깨졌거나(샘플 0/상수 타깃/정렬 실패)**, 폴드 분할·필터링·결측 처리에서 누수가 생겨 **OOS가 의미 없게** 나올 가능성이 큼.
- `worst_mdd: None`, `lane_hash/run_hash: None`, 리밸런스 pinpoint가 **로그 파일/포맷 불일치로 실패** → “성능이 안 움직임”의 1순위 원인은 **실제로는 같은 전략이 계속 돌아가거나(노델타), 측정이 실패**하는 케이스.

### (b) 위험/부작용
- 폴드/로그를 엄격히 하면 기존 챔피언 성능이 내려갈 수 있음(정상).
- 산출물이 강제되면서 실험 속도가 일시적으로 느려질 수 있음.

### (c) 최소 실험 2~3개  *(아래 공용 실험 E1~E5 중 매핑)*
- **E1(필수)**: Purged/Embargo Walk-Forward + degenerate fold hard-fail
- **E2(필수)**: Rebalance/Fill/Cost 로그 “스키마 고정” + 해시 강제

### (d) PASS 조건
- 모든 실험에서 `degenerate_folds == []` (또는 0개)이고, 각 폴드 샘플 수/분산이 임계치 이상.
- `run_hash/lane_hash`가 매 런 생성되고, 리밸런스 로그가 **항상** 생성되며 pinpoint 도구가 **에러 없이 비교 리포트 생성**.
- `worst_mdd`가 None이 아닌 숫자로 산출(백테스트 리포팅 결측 제거).

---

# 2) **서바이버십/룩어헤드/포인트-인-타임(PTI) 데이터 점검**
### (a) 왜 필요한지
- 미국 주식(Tech+Healthcare 8~14종목)은 **종목 교체/상폐/합병 영향이 큼**. PTI가 아니면 “살아남은 종목만”으로 학습해 OOS가 왜곡됨.
- 리밸런스 로그가 없어서 “실제 체결 가격/신호 시점”이 불명확 → 룩어헤드가 숨기 쉬움.

### (b) 위험/부작용
- PTI·delisting returns 반영 시 성능이 눈에 띄게 하락 가능(정상).
- 데이터 비용/구현 복잡도 증가.

### (c) 최소 실험 2~3개 *(공용 E3로 커버 + E1 일부와 연동)*
- **E3(필수)**: PTI/상폐수익률/기업행위(스플릿) 반영 토글 A/B (동일 전략, 데이터만 교체)
- (옵션) E1의 embargo 창을 “결산 발표/가이던스” 구간에 맞춰 확대해 룩어헤드 민감도 측정

### (d) PASS 조건
- PTI ON/OFF 간 성능 차이가 “상식 범위”로 축소되고(극단적 점프 제거), ON에서 OOS가 안정화.
- delisting/합병 이벤트가 포함된 기간에서 수익률 계산이 끊기지 않고 재현 가능.

---

# 3) **비용(수수료+슬리피지+임팩트) 미반영 제거 + 턴오버 게이트**
### (a) 왜 필요한지
- 8~14종목 집중 포트는 리밸런스 빈도/체결 슬리피지에 성과가 크게 좌우됨.
- 현재 “rebalance data may not be included” 상태라면, **비용이 사실상 0으로 평가**되고 있을 가능성이 큼 → 성능 “정체/허상”의 핵심 원인.

### (b) 위험/부작용
- 비용 반영 즉시 성능 하락 가능(정상).
- 턴오버 제한으로 기회 손실 가능.

### (c) 최소 실험 2~3개 *(공용 E4로 커버)*
- **E4(필수)**: 비용모델 3단(낙관/기준/보수) + 턴오버 상한(예: 일/주) 게이트 동시 적용
  - 낙관: 1bp+고정 슬리피지
  - 기준: 3~8bp + 스프레드 기반
  - 보수: 10~20bp + ADV 기반 임팩트(간단 선형)
- (옵션) 리밸런스 “부분 체결/체결 실패” 시나리오(유동성 부족) 1개 추가

### (d) PASS 조건
- 기준 비용에서 OOS mean이 **의미 있게 양수 유지**(팀 기준치) + 보수 비용에서도 “폭망”하지 않음(손실 tail 급증 금지).
- 턴오버 상한 적용 후에도 샤프/드로우다운이 개선 또는 유지되며, 거래 횟수·거래대금이 운영 가능 범위.

# 4) **노출/리스크(베타, 섹터, 단일종목) 게이트로 “운영 가능한” 포트 만들기**
### (a) 왜 필요한지
- `exposure_min/max: 0.0 / 0.8388`는 현금비중이 크게 출렁일 수 있음을 시사 → 전략이 “신호 없음/게이트 실패” 시 **현금화**로 성과가 멈추거나, 반대로 특정 구간에서 과도한 익스포저가 생길 수 있음.
- Tech+Healthcare만으로는 시장 레짐에 취약 → 최소한의 베타/변동성/단일종목 집중 제한이 필요.

### (b) 위험/부작용
- 리스크 제한이 과하면 수익 기회를 깎아 OOS 평균이 낮아질 수 있음.
- 제약이 많아지면 최적화가 제약 적합에 과최적화될 수 있음.

### (c) 최소 실험 2~3개 *(공용 E5로 커버)*
- **E5(필수)**: 익스포저/변동성 타깃/단일종목 캡 동시 적용(하나의 패치로)
  - 총 익스포저: [0.3, 0.9] 같은 “바닥” 포함(신호 부재로 0 되는 현상 방지)
  - 단일종목 최대 비중: 12~18% (8~14종목 기준)
  - 포트 변동성 타깃(rolling 20D)으로 레버/현금 자동 조절
- (옵션) 베타(대상: QQQ/XLK/XLV **관측만**)가 특정 임계 초과 시 포지션 축소(ETF는 거래하지 말고 “게이트 지표”로만)

### (d) PASS 조건
- 최대 낙폭(worst_mdd)이 산출되고, 이전 대비 악화되지 않음(또는 목표 개선).
- 단일종목 익스포저 위반 0회, 총 익스포저 하한 미만 구간이 전체의 일정 비율 이하로 감소.
- 레짐 급변 구간에서 손실 꼬리(왼쪽 tail)가 줄어듦.

# 5) **“노델타” 원인(신호가 적용되지 않음/주문이 안 나감) 제거 + 48시간 자동 루프 안정화**
### (a) 왜 필요한지
- No-Delta Diagnoser가 “9 experiments”를 봤는데도 성능 변화가 없으면,
  1) 실험 파라미터가 실제 전략에 주입되지 않거나  
  2) 게이트로 인해 거래가 거의 없거나  
  3) 리밸런스/체결이 기록되지 않아 측정이 동일해지는  
  케이스가 흔함.
- 48시간 루프에서는 “변경→적용→측정”의 연결이 끊기면 무한 제자리.

### (b) 위험/부작용
- 계측을 촘촘히 넣으면 로그/저장 비용 증가.
- 강제 실패(hard fail)로 자동 루프가 자주 멈출 수 있음(초기엔 의도된 현상).

### (c) 최소 실험 2~3개 *(E2를 중심으로 커버 + E1/E4/E5의 계측 연동)*
- **E2 확장**: “전략 입력 파라미터 덤프 + 주문생성 이벤트 카운터”를 리밸런스 로그에 포함
  - 예: `num_signals_generated`, `num_orders_submitted`, `num_fills`, `turnover`, `cash_pct`, `cap_violations`
- (옵션) “신호는 바뀌었는데 주문이 0”인 경우 자동 FAIL(게이트 원인 코드까지 출력)

### (d) PASS 조건
- 모든 런에서 “전략 파라미터 덤프(실험값)”가 로그에 남고, 챔피언/후보 간 값 차이가 확인됨.
- `num_orders_submitted==0`인 런이 발생하면 **원인 코드**(게이트/유동성/데이터 결측/거래시간 미스매치)와 함께 자동 중단 또는 격리됨.

## 공용 “실행 가능한 패치/실험” 5개만 운용 (48시간 루프 형태)
아래 5개만 돌리면서 위 TOP5를 커버하도록 설계(케이스 폭발 방지).

### E1) Purged Walk-Forward + Degenerate Fold Hard-Fail
- (1) **실험 정의**: 폴드 분할을 purged/embargo로 교체하고, 폴드 샘플 수/타깃 분산/결측률 임계 미달 시 즉시 FAIL.
- (2) **게이트**: `degenerate_folds==[]` AND 각 폴드 `n>=Nmin`, `var(y)>0`, 결측률 < X%.
- (3) **기대 관측치**: OOS mean이 과대에서 현실화되며, 실험 간 차이가 “진짜”로 나타나기 시작.

### E2) Rebalance/Fill/Cost 로그 스키마 고정 + run_hash 강제
- (1) **실험 정의**: CSV/JSONL 스키마를 고정(버전필드 포함), 파일 경로를 런 해시 기반으로 강제 생성. pinpoint 도구 입력도 동일 규약으로 통일.
- (2) **게이트**: 리밸런스 로그 생성 100% + JSON 파싱 에러 0 + run_hash 존재.
- (3) **기대 관측치**: “노델타”가 실제 전략 문제인지 파이프라인 문제인지 즉시 구분 가능.

### E3) PTI/Delisting/Corporate actions 토글 A/B
- (1) **실험 정의**: 동일 전략을 PTI OFF vs ON으로 1회씩만 비교(종목은 Tech+Healthcare 8~14 유지).
- (2) **게이트**: 두 런의 데이터 커버리지 리포트(상폐/결측/스플릿 처리) 자동 출력.
- (3) **기대 관측치**: OFF에서만 잘 나오던 성과가 ON에서 붕괴하면 원인이 서바이버십/룩어헤드임이 확정.

### E4) 비용 3단 + 턴오버 상한 게이트
- (1) **실험 정의**: 비용(낙관/기준/보수) 3개 시나리오를 동일 신호에 적용 + 턴오버 상한 적용.
- (2) **게이트**: 기준 비용에서 OOS mean/드로우다운 최소 기준 통과 + 보수 비용에서 tail 폭발 금지.
- (3) **기대 관측치**: “실거래 가능한” 성능만 남고, 전략 간 비교가 의미 있어짐.

### E5) 익스포저 하한/단일종목 캡/변동성 타깃(리스크 패치)
- (1) **실험 정의**: 총 익스포저 하한 도입(현금화 방지), 단일종목 최대비중, 포트 변동성 타깃을 한 번에 적용.
- (2) **게이트**: 제약 위반 0회 + worst_mdd 산출 및 목표 범위 통과.
- (3) **기대 관측치**: 레짐 급변에서 손실 꼬리 감소, “노출이 0으로 떨어져 성능이 멈추는” 현상 감소.

## 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐)
아래를 **로그로 숫자화해서** 한 번에 진단하도록 구성(질문 없이 실행 항목만).

### A) Trigger(신호 발생) 문제
- `num_signals_generated`가 거의 0인지 확인 → 0이면 **특징/라벨 정렬 실패, 결측 필터 과도, 임계치 과도** 가능성.
- 신호 분포(상위/하위 분위)와 “선택된 종목 수(8~14 내 유지)”를 매 리밸런스마다 저장.

### B) Apply(주문 생성/게이트) 문제
- `num_orders_submitted`, `cap_violations`, `gate_reject_reason_counts`를 저장.
- “신호는 있는데 주문 0”이면 게이트(유동성/리스크/거래시간)에서 막힌 것 → 성능 변화가 없어짐.

### C) Exposure(실현 익스포저/현금화) 문제
- 시간가중 평균 익스포저, 현금비중 히스토그램, 종목별 평균 비중을 기록.
- 익스포저가 자주 0 근처면 전략 비교가 무의미해짐 → E5의 익스포저 하한으로 교정.

### D) Cost(비용) 문제
- 총비용(bps), 슬리피지(bps), 턴오버, ADV 대비 거래비중을 저장.
- “Gross는 좋은데 Net이 정체”면 비용이 원인 → E4로 해결/상한 설정.

### E) Regime(시장 국면) 문제 — ETF는 **관측 지표로만**
- QQQ/XLK/XLV/IBB의 20D 모멘텀, 변동성, 상관(Tech vs Healthcare)만 기록.
- 국면별 성과를 버킷팅(예: QQQ 모멘텀 상/하, VIX 대용 변동성 상/하)하여 “어느 국면에서만 먹히는지” 확인.
- 특정 국면에서만 성과가 나오면 **게이트(진입 축소/중단)** 또는 **변동성 타깃**이 해법(E5).

## 즉시 실행 순서(48시간)
1) **E2 먼저** 적용해서 로그/해시/리밸런스 산출을 고정하라(지금 상태에선 비교가 깨져 있음).  
2) 동시에 **E1**로 degenerate fold를 0으로 만들고, 실패를 강제하라.  
3) 그 다음 **E3 → E4 → E5** 순서로 “데이터 현실화 → 비용 현실화 → 운영 리스크 제약”을 입혀라.  
4) 각 실험은 “OOS mean”만 보지 말고, 위 A~E 지표(트리거/적용/노출/비용/레짐)에서 **어디가 0/None/에러인지**를 1차 합격 기준으로 삼아라.
