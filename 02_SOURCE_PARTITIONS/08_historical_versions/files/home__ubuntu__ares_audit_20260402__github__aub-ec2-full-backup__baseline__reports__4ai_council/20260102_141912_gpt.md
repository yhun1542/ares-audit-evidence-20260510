## TOP5 우선순위(24~48h) — 명령형 체크리스트(누수/과최적화/서바이버십/비용/운영리스크 우선)

### 1) **리밸런스/로그 아티팩트 표준화(운영 리스크 0순위)**
- **왜 필요한가**
  - `aub_rebalance_pinpoint`가 `--base-log` 누락 + `rebalance.csv/jsonl` 파싱 실패로 **원인추적 불가** 상태.
  - “성능이 안 움직임”이 모델 문제인지, 리밸런스 생성/적용/평가 파이프 문제인지 구분이 안 됨.
- **위험/부작용**
  - 로그 포맷 변경 시 과거 리포트 도구 호환 깨짐.
  - 실험 간 결과 비교가 일시적으로 흔들릴 수 있음(메트릭 정의/집계 변경 때문).
- **실행 patch/실험 (E1: 1개로 수렴)**
  - **E1: Rebalance Trace Contract 도입**
    - (1) **실험 정의**
      - 매 런마다 아래 파일을 **반드시** 생성/저장(없으면 런 실패로 처리):
        - `rebalance.jsonl`(권장): 한 줄=한 리밸런스 이벤트 JSON (timestamp, universe, target_w, executed_w, px, qty, costs, slippage, reason, signal_snapshot_hash)
        - `metrics.json`: oos_mean/oos_min/worst_mdd/turnover/cost_bps/exposure_minmax 등 고정 스키마
        - `champion.json`에 `file`(모델/설정 경로) **필수 채움**(현재 champion에서 `file:` 비어있음)
      - `aub_rebalance_pinpoint.py` 입력을 `--base-log`가 아니라 **base/cand 모두 아티팩트 디렉토리**로 받도록 단일화.
    - (2) **게이트(FAIL FAST)**
      - `rebalance.jsonl` 1줄도 없으면 FAIL
      - 각 이벤트에서 `sum(target_w)`가 1±1e-6(또는 long-only면 ≤1) 만족 못하면 FAIL
      - `executed_w`가 존재할 때 `|executed_w-target_w|` 분포 리포트 출력(미출력 시 FAIL)
    - (3) **기대 관측치**
      - pinpoint 리포트가 “어느 날/어느 종목/어느 신호”에서 성능이 갈라지는지 즉시 표기
      - “성능 무변화” 상황에서 **리밸런스가 실제로 발생했는지**부터 1분 내 확인 가능
- **PASS 조건**
  - 다음 런에서 `rebalance_pinpoint.md`가 오류 없이 생성되고, 최소 1개 리밸런스 이벤트가 위치/비용/슬리피지 포함으로 재현 가능해야 함.

### 2) **거래비용/슬리피지/턴오버를 OOS 점수에 “강제 반영”(비용 미반영 제거)**
- **왜 필요한가**
  - OOS mean이 움직이지 않는 원인이 “신호 개선이 비용으로 상쇄” 또는 “비용이 아예 모델 선택에 미반영”일 수 있음.
  - Tech/Healthcare 8~14종목은 리밸런스 빈도/체결편차가 성과를 크게 좌우.
- **위험/부작용**
  - 비용을 넣으면 단기적으로 OOS가 하락(정상) → 기존 champion 교체가 늦어질 수 있음.
  - 지나친 비용 패널티는 “거의 안 움직이는 전략”으로 퇴화 위험.
- **실행 patch/실험 (E2)**
  - **E2: 비용 통합 스코어링(Score_net) + 비용 브래킷 민감도 동시 산출**
    - (1) **실험 정의**
      - 평가 메트릭을 `gross`와 `net`으로 분리하고, champion 선정은 **net 기준**으로 고정.
      - 비용모델(최소): `commission_bps + slippage_bps = a + b*vol + c*|Δw|` 형태(단순 선형으로 시작).
      - 같은 백테스트에서 비용 브래킷(예: 5/10/20 bps)을 **동일 리밸런스 로그로 재평가만**(추가 백테스트 없이) 출력.
    - (2) **게이트**
      - turnover, cost_bps(일/월), slippage_bps가 metrics.json에 **항상 존재**해야 PASS
      - `net <= gross` 위반 시 FAIL(부호/적용 오류)
    - (3) **기대 관측치**
      - “개선이 안 된다”가 **신호 한계**인지 **비용 상쇄**인지 즉시 분해
      - 비용 브래킷에 따라 순위가 뒤집히는 실험은 과최적화/미세차익 전략으로 분류 가능
- **PASS 조건**
  - champion 선택 기준이 net으로 고정되고, 리포트에 gross/net/turnover/cost가 항상 함께 출력되며, 비용 브래킷 민감도가 1회 런에서 동시에 제공될 것.

### 3) **누수/서바이버십 방지 “하드 테스트” 추가(데이터 리스크 우선 제거)**
- **왜 필요한가**
  - Tech/Healthcare 대형주는 서바이버십 영향이 작아 보이지만, **기업행동(스플릿/머지/심볼변경), 구성종목 고정 방식, 리밸런스 시점 정렬**에서 누수가 자주 생김.
  - “OOS 평균은 괜찮은데 새 실험이 안 움직임”은 누수 방지 로직이 이미 성과를 잡아먹고 있거나, 반대로 누수가 있어 챔피언만 과대평가됐을 수도 있음.
- **위험/부작용**
  - 엄격한 point-in-time 적용 시 과거 성과가 급락(정상일 수 있음).
  - 데이터 공급원 한계로 결측이 늘어 전략이 덜 거래될 수 있음.
- **실행 patch/실험 (E3)**
  - **E3: 누수 감지용 “시간 시프트/미래정보 센티널” 테스트**
    - (1) **실험 정의**
      - 동일 파이프에서 feature timestamp를 **의도적으로 +1 bar(미래) / -1 bar(과거)** 시프트한 “센티널 런”을 만들고, 성능 변화를 자동 비교.
      - 또한 **리밸런스 결정시각 vs 가격 적용시각**(close로 결정하면 next open 체결 등)을 명시적으로 분리해 로그에 기록.
    - (2) **게이트**
      - +1 bar(미래) 시프트에서 성능이 **유의미하게 급등**하면 누수 가능성으로 FAIL(경보 발령)
      - -1 bar 시프트에서 성능이 완만히 하락하는 정도는 정상 범주로 기록
    - (3) **기대 관측치**
      - “성능 무변화”가 진짜 신호 한계인지, 아니면 **정렬/적용 시점 문제**인지 빠르게 판별
- **PASS 조건**
  - 센티널 비교 리포트가 자동 생성되고, 미래 시프트 급등 시 파이프가 경보/차단(Fail)까지 수행.

### 4) **노출(Exposure)/리스크 제약의 명시화 + 변동성 타겟(운영 안정성)**
- **왜 필요한가**
  - 현재 exposure min/max가 0.47~0.84로 보이며, “안 움직임”은 실제로는 **노출이 제한에 걸려 신호가 눌린 것**일 수 있음.
  - worst_mdd가 `None`인 점은 리스크 산출/로그 누락 가능성(운영 리스크).
- **위험/부작용**
  - 제약 강화는 수익 잠재력을 깎을 수 있음.
  - 변동성 타겟은 급변장에 디레버리징으로 기회비용 발생.
- **실행 patch/실험 (E4)**
  - **E4: Exposure/Vol Target 모듈을 “리밸런스 후처리(post-optimizer)”로 고정**
    - (1) **실험 정의**
      - 신호→목표비중 생성 후, 항상 동일한 후처리:
        - (i) 총 익스포저 클립(예: 0.6~0.9)
        - (ii) 단일 종목 상한(예: 12~15%)
        - (iii) 포트폴리오 vol 타겟(예: 12~16% 연환산)으로 스케일
      - worst_mdd를 필수 산출(없으면 런 FAIL).
    - (2) **게이트**
      - 리밸런스 이벤트마다 제약 위반 0건이어야 PASS
      - `worst_mdd`가 None이면 FAIL
    - (3) **기대 관측치**
      - “성과 무변화”가 노출 클립 때문인지(클립 빈도/강도 로그로 확인) 드러남
      - 운영적으로 drawdown/리스크 리포팅이 항상 가능
- **PASS 조건**
  - 모든 런에서 worst_mdd/제약위반건수/클립비율이 metrics에 기록되고, 제약 위반이 자동 차단.

### 5) **전략 레벨: Tech+Healthcare 8~14종목 “고정 바스켓” + 레짐 관측지표(ETF는 관측만)**
- **왜 필요한가**
  - 실험이 많이 쌓였는데도 OOS가 안 움직이면, (a) 종목 구성/유니버스 변동이 노이즈를 만들거나 (b) 레짐(리스크온/오프)에 따라 신호가 상쇄될 수 있음.
  - ETF는 매매 금지이므로 **관측지표(QQQ/XLK/XLV/IEF 등)**로만 레짐을 판정해 필터링.
- **위험/부작용**
  - 바스켓 고정은 종목 교체 알파를 포기.
  - 레짐 필터는 타이밍 실패 시 거래 기회 감소.
- **실행 patch/실험 (E5)**
  - **E5: 바스켓 고정(8~14) + 레짐 플래그(관측용 ETF)로 “거래 빈도/방향”만 조정**
    - (1) **실험 정의**
      - Tech/Healthcare에서 유동성/대표성 높은 8~14개를 **명시적으로 고정**(심볼 리스트 버전관리).
      - 레짐은 ETF 수익률/스프레드로만 계산(매매 없음):
        - 예: `Regime = sign(20d(QLD?) 금지이므로 QQQ 사용)`, 혹은 `XLK-XLV 상대모멘텀`, `QQQ vs IEF` 등
      - 레짐에 따라 **리밸런스 강도(Δw 스케일)**만 조절(신호 자체 변경 최소화).
    - (2) **게이트**
      - universe 크기 항상 8~14 유지(벗어나면 FAIL)
      - 레짐 플래그가 NaN/결측이면 해당일 거래 금지(운영 안전)
    - (3) **기대 관측치**
      - 성능 정체가 “유니버스 흔들림” 때문인지 제거
      - 레짐별 성과 분해(리스크온/오프)로 ‘안 움직임’의 구조 확인
- **PASS 조건**
  - 레짐별(2~3구간) 성과/턴오버/비용 분해가 리포트에 자동 포함되고, universe 고정이 강제된다.

## 48시간 자동 루프 운영 형태(고정)
- **Cycle(매 48h)**
  1) E1→E2→E3→E4→E5 순서로 단일 파이프에서 실행(각 실험은 “게이트 실패 시 즉시 중단”).
  2) 모든 게이트 통과 시에만 champion 비교(oos_net 기준) 수행.
  3) 리포트는 다음 4종을 항상 생성:
     - `diagnosis.md`(누수/정렬/비용/노출 요약)
     - `rebalance_pinpoint.md`(종목/일자/사유 pinpoint)
     - `regime_breakdown.md`(레짐별 성과)
     - `artifact_index.json`(런 해시→파일 링크)

## 성능이 안 움직일 때 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 트리(명령형)

### A. Trigger(신호 발생) 문제
- 신호 분포(평균/표준편차/0비율)가 기간별로 붕괴했는지 확인하라.
- 상위/하위 신호 종목이 고정돼 “랭킹이 안 바뀌는지” 확인하라.
- 레짐별로 신호-수익 상관이 반전되는지 확인하라.

### B. Apply(적용/정렬/리밸런스) 문제
- **결정 시각 vs 체결 시각**을 분리해 기록하라(누수 최빈 지점).
- 리밸런스 이벤트 수(일/월)가 0에 수렴하는지 확인하라(‘안 움직임’의 가장 흔한 원인).
- target_w는 바뀌는데 executed_w가 안 바뀌는지(체결/제약/현금부족) 확인하라.

### C. Exposure(노출) 문제
- 익스포저 클립 발동률(%)과 평균 클립 강도를 로그로 남겨라.
- 단일 종목 상한 때문에 알파가 눌리는지(상한 hit 횟수) 확인하라.
- vol 타겟 스케일이 항상 0.5 이하로 눌려 있는지 확인하라(사실상 디레버 상태).

### D. Cost(비용) 문제
- gross→net 차이(=cost drag)가 개선분을 상쇄하는지 확인하라.
- turnover가 동일한데 성능만 안 움직이면 신호가 “사이즈만 바뀌고 방향은 동일”일 가능성이 큼(Δw 분포 확인).
- 슬리피지가 특정 종목에서만 과도한지 pinpoint하라(리밸런스 로그로 종목별 cost 랭킹).

### E. Regime(시장 국면) 문제
- 레짐별 성과 테이블(리스크온/오프/중립)로 “전체 평균이 상쇄”되는지 확인하라.
- Tech vs Healthcare 상대강도(예: XLK-XLV)를 관측지표로 두고, 해당 구간에서만 성과가 나오는지 확인하라.
- 레짐 전환 직후(±5~10일) 성과가 급격히 나빠지면 리밸런스 지연/체결가정 문제를 의심하라.

## 즉시 적용 메모(현재 상태 기반)
- `Champion file:` 비어있음 → **E1에서 필수 채움**(재현성/감사 가능성).
- `worst_mdd: None` → **E4 게이트로 런 차단**(리스크 지표 누락은 운영상 결격).
- `rebalance pinpoint`가 입력 파일을 못 읽음 → **E1로 도구 입력을 “아티팩트 디렉토리 기반”으로 단일화**해서 재발 방지.

위 5개(E1~E5)를 그대로 48시간 루프에 걸면, “성능이 안 움직임”이 **(1) 로그/적용 문제 (2) 비용 상쇄 (3) 누수/정렬 (4) 노출 제약 (5) 레짐 상쇄** 중 어디인지가 자동으로 갈라지게 된다.
