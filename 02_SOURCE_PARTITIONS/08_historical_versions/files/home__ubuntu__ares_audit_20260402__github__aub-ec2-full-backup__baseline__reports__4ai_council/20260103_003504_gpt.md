## TOP5 우선순위 (24~48h) — 명령형 체크리스트

### 1) **데이터/로그 무결성(누수·비용·리밸런스)부터 복구**
- [ ] `--base-log` / `rebalance.csv|jsonl` 로딩 실패를 **즉시 고정**(현재 pinpoint가 “비어있음” → 비용/턴오버/체결 가시성 0)
- [ ] 모든 실험 산출물에 `lane_hash/run_hash/champion_file_path`를 **강제 기록**(현재 `None` 다수 → 재현/비교 불가)
- [ ] “OOS mean 3.32” vs “Champion OOS Mean 2.6276” **불일치 원인 제거**(champion 참조 소스 단일화)

### 2) **Fold 퇴화(degenerate_folds) 제거(과최적화/서바이버십/스플릿 오류 의심)**
- [ ] degenerate folds [1,2,3,8] 원인을 **자동 진단 + hard fail**로 전환(빈 샘플/0거래/라벨 상수/누락 데이터)
- [ ] 워크포워드/퍼지드(purged) 스플릿으로 **미세 누수 차단**(특히 리밸런스-라벨 겹침)

### 3) **비용(수수료/슬리피지/임팩트) 상시 반영 + 게이트화**
- [ ] 비용이 리턴에 “사후 보고”가 아니라 **학습/선택/게이트에 직접 들어가게** 패치
- [ ] 턴오버·체결갭·슬리피지 민감도를 **48h 루프에서 자동 추적**

### 4) **운영 리스크(노출·집중·거래가능성) 게이트 강화**
- [ ] US 주식 only + Tech/Healthcare 중심 **8~14종** 강제(ETF 매매 금지, ETF는 관측지표만)
- [ ] `exposure_max≈0.84` 상태에서 “현금 비중”이 성능을 가리는지/리스크를 낮추는지 분리 측정
- [ ] 단일 종목/섹터 집중, 하방 tail, 이벤트(실적/임상) 리스크를 **제약조건으로 고정**

### 5) **“No-Delta(성능 정체)” 원인분해 계측 추가(트리거→적용→노출→비용→레짐)**
- [ ] 트리거 발생/필터 통과/실제 주문/체결/보유기간/청산 사유를 단계별로 로그
- [ ] 레짐(Tech/Healthcare 리스크온·오프)에서만 먹는 전략인지 **분리 리포트 자동 생성**(ETF는 지표로만 사용: QQQ/XLK/XLV 등)

## 48시간 자동 루프에 넣을 “실행 가능한 Patch/실험” 5개 (공용 풀)
아래 5개만 돌리고, TOP5 우선순위에는 이 5개를 조합해서 붙입니다(케이스 폭발 방지).

### **E1. Rebalance/Cost 로그 파이프라인 복구 Patch**
- (1) 실험 정의  
  - `aub_rebalance_pinpoint`가 **반드시** base/cand 리밸런스 로그를 읽도록 포맷 단일화(권장: `rebalance.jsonl` 고정)  
  - 런 종료 시 `rebalance_summary.json`(턴오버/거래횟수/평균 체결지연/총비용/bps) 생성
- (2) 게이트  
  - 로그 파일 0바이트/파싱 실패 시 **런 FAIL**  
  - `rebalance_summary` 누락 시 **런 FAIL**
- (3) 기대 관측치  
  - 모든 실험에 대해 턴오버/비용/체결 관련 지표가 OOS 리포트에 항상 동반됨  
  - “성능 정체”가 비용/턴오버 문제인지 즉시 분리 가능

### **E2. Degenerate Fold 하드 실패 + 원인코드 출력 Patch**
- (1) 실험 정의  
  - fold별 `n_trades`, `n_samples`, `label_var`, `non_nan_ratio` 산출  
  - 조건 미달 fold 발생 시 “skip”이 아니라 **FAIL + 원인코드 출력**
- (2) 게이트  
  - `degenerate_folds != []` 이면 **런 FAIL**
- (3) 기대 관측치  
  - 과최적화/누수/데이터 결측이 “조용히 성능을 만드는” 상태 제거  
  - 현재 [1,2,3,8] 문제의 정확한 원인이 1회 루프로 특정됨

### **E3. 비용 모델 on/off A/B (학습·선택·평가에 동일 반영)**
- (1) 실험 정의  
  - 동일 전략에서 비용모델을 `OFF` vs `ON(commission+spread+slippage)`로만 바꿔 2런 비교  
  - 결과는 **gross vs net**를 동시에 저장
- (2) 게이트  
  - `net_oos_mean`이 `gross_oos_mean` 대비 비정상적으로 과도하게 훼손(예: -50% 이상)되면 **턴오버 과다**로 판정하고 FAIL
- (3) 기대 관측치  
  - “OOS는 좋아 보이는데 실전은 안 되는” 전형적 비용 미반영 문제를 즉시 적발  
  - 실험 간 delta가 안 나는 이유가 비용상쇄인지 확인 가능

### **E4. Universe/Constraint 강제(US·Tech+HC 8~14종) + 노출 안정화**
- (1) 실험 정의  
  - 유니버스 고정(미국 상장, Tech+Healthcare 중심 단일주 8~14)  
  - 제약: 종목당 max weight, 섹터별 max, 최소 거래대금/스프레드 필터, `exposure_min` 하한(예: 0.3) 옵션
- (2) 게이트  
  - 종목 수가 8~14 밖이면 FAIL  
  - 거래대금/스프레드 기준 위반 체결이 발생하면 FAIL
- (3) 기대 관측치  
  - 서바이버십/거래불가 종목 혼입 감소  
  - `exposure_max`만 높고 실제론 현금비중이 성능을 좌우하는 상태를 정리

### **E5. 레짐 진단 리포트 Patch(ETF는 지표로만)**
- (1) 실험 정의  
  - OOS 구간을 레짐으로 분해(예: QQQ 추세/변동성, XLV 상대강도 등 “지표”)하여 성과/턴오버/드로우다운을 레짐별로 저장
- (2) 게이트  
  - 레짐별 성과 리포트 미생성 시 FAIL
- (3) 기대 관측치  
  - “한 레짐에서만 먹고 다른 구간에서 0” → no-delta의 구조적 이유를 즉시 노출  
  - 이후 게이트(거래 중지/포지션 축소) 설계 근거 확보

## TOP5 제안별 상세 (왜/위험/최소 실험/ PASS 조건)

### 1) 데이터/로그 무결성 복구
- (a) 왜 필요한지  
  - 현재 `rebalance_pinpoint`가 로그를 못 읽어 **비용/턴오버/리밸런스 품질을 비교 불가**. 이 상태에서 OOS mean 개선은 대부분 “착시”가 됩니다.  
  - `lane_hash/run_hash None`은 재현성·롤백 불가 → 운영 리스크.
- (b) 위험/부작용  
  - 하드 FAIL을 걸면 단기적으로 “성공 런 수”가 줄어 진행이 느려 보일 수 있음. (하지만 잘못된 성공을 제거하는 게 목적)
- (c) 최소 실험(공용 풀에서 선택)  
  - **E1**, **E5** (리밸런스/비용/레짐 로그가 모두 있어야 다음 단계 해석 가능)
- (d) PASS 조건  
  - 모든 런에서 `rebalance_summary.json` 생성 + pinpoint가 base/cand 비교를 수행  
  - OOS 리포트에 `gross/net`, turnover, 비용(bps), 레짐별 성과가 항상 포함

---

### 2) Degenerate folds 제거(과최적화/스플릿 결함 차단)
- (a) 왜 필요한지  
  - `degenerate_folds: [1,2,3,8]`는 “일부 fold가 사실상 무의미”하다는 신호입니다. 이 상태는 **과최적화/누수/결측**이 섞여도 평균 성과가 좋아 보일 수 있습니다.
- (b) 위험/부작용  
  - 데이터가 얇거나 필터가 과하면 연속 FAIL이 날 수 있음(그 자체가 설계 문제를 드러냄).
- (c) 최소 실험  
  - **E2**, (원인 분리 위해) **E4**
- (d) PASS 조건  
  - `degenerate_folds == []`  
  - fold별 `n_trades`/`label_var`가 최소 기준을 상회(0거래 fold 제거)

---

### 3) 비용 상시 반영(수익의 실전화)
- (a) 왜 필요한지  
  - 비용이 반영되지 않으면 Tech/HC의 변동성·이벤트로 인해 **턴오버가 수익을 상쇄**하는데도 OOS가 좋아 보일 수 있습니다.
- (b) 위험/부작용  
  - 단기적으로 OOS 평균이 하락할 가능성 큼(하지만 net 기준의 “진짜 전략”만 남습니다).
- (c) 최소 실험  
  - **E3**, (비용 원인 추적 위해) **E1**
- (d) PASS 조건  
  - `net_oos_mean`이 0 이상(또는 기존 챔피언 net 대비 개선)  
  - `net/gross` 훼손률이 합리적 범위(턴오버 과다로 인한 급락이면 FAIL)

---

### 4) 운영 리스크 게이트(노출/집중/거래가능성)
- (a) 왜 필요한지  
  - `exposure_max ~ 0.84`는 상한만 있고, 실제로는 현금비중/집중/유동성 문제가 성과를 좌우할 수 있습니다.  
  - 8~14 종목 강제는 “포트폴리오로서의 전략”을 고정해 비교 가능하게 만듭니다.
- (b) 위험/부작용  
  - 제약을 강하게 걸면 수익 기회가 줄어 OOS 평균이 떨어질 수 있음. 대신 tail/운영 리스크가 감소.
- (c) 최소 실험  
  - **E4**, (레짐별로 제약 효과 확인) **E5**
- (d) PASS 조건  
  - 종목 수 8~14 유지, 종목/섹터 집중 규칙 위반 0  
  - 실거래가능(거래대금/스프레드) 위반 0  
  - MDD 또는 하방 꼬리(레짐별) 악화 없이 net 성과 유지/개선

---

### 5) No-Delta(성능 정체) 원인분해 계측
- (a) 왜 필요한지  
  - “9 experiments 했는데 성능이 안 움직임”은 보통 전략의 문제가 아니라 **트리거가 안 걸리거나(적용 0), 노출이 제한되거나(현금), 비용이 상쇄하거나(턴오버), 특정 레짐에서만 먹는** 구조적 원인입니다.
- (b) 위험/부작용  
  - 계측이 늘어나 로그/스토리지 비용 증가. 하지만 48h 루프에서 디버깅 비용이 크게 감소.
- (c) 최소 실험  
  - **E5**, (단계별 실행 로그 기반을 위해) **E1**
- (d) PASS 조건  
  - 아래 분해 지표가 모든 런에서 채워짐(누락 시 FAIL):
    - trigger_rate, pass_rate(after filters), order_rate, fill_rate  
    - avg_holding_period, turnover, cost_bps  
    - exposure_time(노출된 시간 비율), cash_ratio  
    - regime_bucket별 net_return / mdd / turnover

## 성능이 안 움직일 때(“No-Delta”) 원인 분해 아이디어 — 트리거/적용/노출/비용/레짐
아래를 **순서대로** 확인하고, 각 단계가 “0 또는 포화”인지 찾으면 됩니다.

### A) Trigger(신호 발생) 문제
- [ ] 신호 발생 빈도(trigger_rate)가 너무 낮거나(거의 0) 너무 높아(항상 1) 구분력이 없는지
- [ ] 라벨이 상수/분산이 너무 작은지(label_var by fold)

### B) Apply(필터/제약 통과) 문제
- [ ] 유동성/스프레드/섹터/종목수 제약 때문에 pass_rate가 급락하는지
- [ ] 이벤트(실적/임상) 회피 규칙이 과도하게 거래를 막는지

### C) Exposure(실제 노출) 문제
- [ ] 현금비중(cash_ratio)이 높아 “리턴이 거의 현금+약간”이 되는지
- [ ] 포지션 상한/섹터 상한 때문에 항상 비슷한 포트가 나오는지(다양성 부족)

### D) Cost(비용 상쇄) 문제
- [ ] turnover가 증가한 만큼 net이 깎이는지(특히 Tech 변동구간)  
- [ ] 체결지연/슬리피지(갭)로 gross 대비 net 훼손이 커지는지

### E) Regime(레짐 편향) 문제
- [ ] QQQ/XLK/XLV 등의 지표 레짐에 따라 성과가 한쪽에만 몰리는지  
- [ ] “좋은 레짐”이 OOS에서 적어 개선이 안 보이는지(표본 문제)

### F) Survivorship/Leakage(구조적 오류) 빠른 체크
- [ ] 유니버스가 “현재 기준”으로 고정되어 과거에 존재하지 않던 종목이 포함되는지(서바이버십)  
- [ ] 재무/이벤트 데이터가 as-of timestamp 없이 미래값을 끌어오는지(누수)  
- [ ] 리밸런스 시점과 라벨 산출 구간이 겹치는지(미세 누수)

---

### 실행 순서(48h)
- [ ] 1회차 루프: **E1 + E2** (파이프라인/폴드 퇴화부터 하드 고정)
- [ ] 2회차 루프: **E3 + E4** (비용/제약을 net 기준으로 정렬)
- [ ] 상시: **E5** (레짐 분해 리포트 자동 생성)

이렇게 하면 “성능이 안 움직이는” 상황이더라도, 다음 루프에서 바꿔야 할 레버(트리거·필터·노출·비용·레짐)가 숫자로 특정됩니다.
