## 다음 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — **명령형 체크리스트**

### 1) **재현성/메타데이터 무결성부터 복구 (lane_hash/run_hash=None, 로그 파일 누락)**
- **왜 필요한지**
  - 현재 Champion에 `lane_hash=None`, `run_hash=None`, `worst_mdd=None`가 찍히고, rebalance pinpoint가 **입력 로그 누락/JSON 파싱 실패**로 멈춤.  
  - 이 상태에서는 “성능이 안 움직이는” 원인이 **모델 때문인지 / 파이프라인 결함인지** 분리가 불가능(운영 리스크 최우선).
- **위험/부작용**
  - 로그/해시 강제는 실험 속도 감소, 스토리지 증가.
  - run_id 고정으로 기존 비교 기준이 바뀔 수 있음(하지만 필수).
- **관련 최소 실험(아래 E1, E2 사용)**  
- **PASS 조건**
  - 모든 실험 산출물에 `lane_hash/run_hash/seed/git_sha/data_snapshot_id`가 **비어있지 않음**.
  - rebalance pinpoint가 **base/cand 모두에서** 정상 리포트 생성.
  - `worst_mdd`가 모든 런에서 계산/표기됨(Null 금지).

### 2) **누수/과최적화/폴드 퇴화(degenerate_folds) 차단 (degenerate_folds=[1,2,3,8])**
- **왜 필요한지**
  - degenerate fold는 보통 (a) 거래 수 0, (b) 라벨/피처 정렬 오류, (c) 시계열 CV 설정 오류(lookahead/embargo 미적용), (d) universe가 너무 빡빡해서 샘플 소실을 의미.  
  - 이게 남아있으면 OOS 평균이 좋아도 **우연/누수/빈 트레이드**일 수 있음.
- **위험/부작용**
  - 누수 방지(embargo, shift) 적용 시 단기 성능 하락 가능(정상).
  - 폴드 품질 게이트로 실험 실패율 증가(정상).
- **관련 최소 실험(아래 E3 사용 + E1의 게이트 강화)**  
- **PASS 조건**
  - `degenerate_folds == []` (0개) 또는 허용해도 **1개 이하**로 하락.
  - 각 폴드별 최소 거래/리밸런스 이벤트 수가 임계치 이상(예: fold당 트레이드 ≥ N).
  - OOS min이 “비정상적으로 0 근처 고정” 패턴이 사라짐(빈 포지션 의심 제거).

---

### 3) **거래비용/슬리피지/회전율(turnover) 미반영 여부를 강제 검증**
- **왜 필요한지**
  - 현재 rebalance 데이터 자체가 로딩 실패. 비용이 빠져 있거나, 체결 단가/수수료/슬리피지/시장충격이 0으로 들어가면 성능이 “안 움직이거나” 또는 “과대평가”될 수 있음.
- **위험/부작용**
  - 비용 모델을 넣으면 성능 급락 가능(정상).  
  - 비용 과대추정 시 유망 전략을 조기 폐기할 위험 → 범위(낙관/기준/보수) 3점으로만 확인.
- **관련 최소 실험(아래 E2, E4 사용)**  
- **PASS 조건**
  - 비용 3점(낙관/기준/보수)에서 **순위가 안정적**(상위 전략이 비용 민감도로 급전환하지 않음).
  - turnover 상한 게이트 통과(예: 일평균 turnover ≤ X, 리밸런스 빈도 제한).

### 4) **포트폴리오 구성 제약(미국주식 only, Tech+Healthcare, 8~14종목) 강제**
- **왜 필요한지**
  - 전략이 좋아도 운영 조건(8~14개 종목, 섹터 제한)을 만족 못하면 실제 배치 불가.  
  - 종목 수가 흔들리면 노출/변동성/거래비용이 불안정 → OOS가 “안 움직이는” 원인이 됨(구성 단계 문제).
- **위험/부작용**
  - 제약이 강하면 기회 손실로 성능 하락 가능.
  - 섹터 분류 데이터 품질(분류 변경/누락) 리스크 → 스냅샷 고정 필요.
- **관련 최소 실험(아래 E5 사용 + E4에서 포지션 수/섹터 게이트)**  
- **PASS 조건**
  - 항상 **8~14 종목 유지**(예외 0회 또는 극히 제한).
  - Tech+Healthcare 비중(종목 수 기준 또는 달러 기준)이 정책 범위 내 유지.
  - 미국주식 only(ADR/OTC/비미국 상장 혼입 0).

- **관련 최소 실험(아래 E1의 리스크 산출 강제 + E4의 노출/회전율 게이트)**  
- **PASS 조건**

## 48시간 자동 루프용 “실행 가능한 patch/실험” **5개만** (E1~E5)
아래 5개만 돌리면 위 TOP5의 대부분을 동시에 커버하도록 설계.

---

### E1) **Run Integrity Patch (해시/시드/스냅샷/리스크 산출 강제)**
1) **실험 정의**
   - 모든 런에서 다음 필드를 강제 생성/저장:  
     `run_hash, lane_hash, seed, git_sha, data_snapshot_id, config_hash`  
   - 리포트에 `worst_mdd` 산출 강제(Null이면 런 실패 처리).
2) **게이트**
   - (필수) 위 메타 필드가 하나라도 Null/빈값이면 FAIL.  
   - (필수) `worst_mdd` Null이면 FAIL.
3) **기대 관측치**
   - 챔피언/후보 비교가 “동일 데이터/동일 설정” 단위로 추적 가능.
   - “성능 정체”가 파이프라인 결함인지 전략 이슈인지 즉시 분리됨.

---

### E2) **Rebalance Logging Fix + Pinpoint 재가동**
1) **실험 정의**
   - rebalance 로그를 단일 포맷으로 표준화(예: JSONL)하고, 항상 아티팩트에 저장.  
   - `aub_rebalance_pinpoint.py` 입력 경로를 **실제 생성물 경로로 자동 연결**(현재 `--base-log`가 파일이 아닌 문자열로 들어가며 깨짐).
2) **게이트**
   - pinpoint 리포트 생성 성공 + 파싱 에러 0건.  
   - base/cand 모두 rebalance 이벤트가 0이 아니어야 함(0이면 “전략이 안 돈 것”으로 별도 FAIL).
3) **기대 관측치**
   - “언제/왜 리밸런스가 달라졌는지”가 바로 드러남(정체 원인 1순위 제거).

---

### E3) **Leakage/Overfit Guard (시계열 정렬 + Embargo + Fold 품질 게이트)**
1) **실험 정의**
   - 피처/라벨/실행시점 정렬을 강제(예: 예측은 t에서 만들고, 실행은 t+1 오픈/클로즈 등 명시).  
   - Walk-forward CV에 embargo(완충 구간) 적용.  
   - fold당 최소 거래수/표본수 미달이면 fold 자체를 “degenerate”로 기록하고 런을 FAIL 처리.
2) **게이트**
   - `degenerate_folds == []` (또는 1개 이하)  
   - fold별 trade_count ≥ N, sample_count ≥ M (N/M은 시스템 기본값으로 고정)
3) **기대 관측치**
   - OOS mean이 다소 내려가도 OOS min/폴드별 분산이 정상화.  
   - “좋아 보이는데 실제론 빈 포지션/누수” 패턴 제거.

---

### E4) **Cost & Turnover Sweep (비용 3점 + 회전율 상한)**
1) **실험 정의**
   - 거래비용을 3점으로 스윕:  
     - Low(낙관), Base(기준), High(보수)  
   - turnover 상한(일/주 기준)을 걸고, 초과 시 포지션 변경량을 스로틀(clip)하는 패치를 함께 비교.
2) **게이트**
   - High 비용에서도 OOS mean이 기준 대비 **과도한 붕괴(예: -X% 이상)** 없을 것.  
   - turnover가 상한 이하로 유지.
3) **기대 관측치**
   - 성능 정체가 “비용/회전율에 의해 상쇄”되는지 즉시 판별.
   - 리밸런스가 잦은 전략이 자동으로 걸러짐.

---

### E5) **Portfolio Constraint Patch (US only, Tech+Healthcare only, 8~14 names)**
1) **실험 정의**
   - 유니버스 필터를 고정(미국 상장 + 섹터 Tech/Healthcare).  
   - 포트폴리오 구성에서 항상 8~14개 종목 유지(스코어 상위 N, 동률 처리 규칙 고정).  
   - 섹터 분류 소스는 스냅샷 ID로 고정(서바이버십/리라벨링 리스크 완화).
2) **게이트**
   - 매 리밸런스 시점마다 종목 수 8~14 유지(위반 0회).  
   - 비대상 섹터/비미국 상장 혼입 0.
3) **기대 관측치**
   - 노출/변동성/비용이 안정 → OOS가 “안 움직이는” 원인이 구성 흔들림인지 제거.
   - 실운영 제약 만족하는 성능만 남음.

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐) — 명령형 트리
아래를 **위에서 아래로** 순서대로 확인(누수/과최적화/서바이버십/비용/운영 리스크 우선).

### A. 트리거(신호 발생) 레벨
- **신호가 거의 안 바뀌는지** 확인: 예측값 분산/엔트로피, 상위 랭크 교체율.
- **룩어헤드/정렬 오류** 징후 확인: 특정 날짜 이후 성능 급변, 폴드별 성능 비정상.
- **유니버스가 너무 좁아 샘플이 사라지는지** 확인: 날짜별 후보 종목 수 타임시리즈.

### B. 적용(실행/리밸런스) 레벨
- 리밸런스 이벤트가 실제로 찍히는지 확인(0이면 전략이 “돌지 않음”).  
- 주문이 포지션으로 반영되는지 확인(체결 가정/반영 시점 불일치 방지).  
- “리밸런스는 했는데 결과가 동일”이면:  
  - 포지션 스냅샷이 업데이트 안 되는 버그  
  - 슬리피지/비용이 과도해 net이 상쇄  
  - 노출 캡/포지션 수 캡에 걸려 변화가 무효화

### C. 노출(포지션 구성) 레벨
- **종목 수(8~14) 위반/진동** 확인.  
- 섹터 편향(Tech/Healthcare 밖으로 새는지) 확인.  
- 총 노출(min/max)과 현금 비중이 OOS 기간에 고정돼 있지 않은지 확인(고정이면 신호/실행 문제).

### D. 비용(현실성) 레벨
- turnover가 높은데 비용이 0이면 과대평가.  
- 비용을 넣었는데 성능이 안 움직이면:  
  - 실제로는 비용이 지배(회전율 스로틀 필요)  
  - 체결 단가 모델이 과보수(스프레드/슬리피지 상한 재검토)  
- **gross→net 브리지**(gross pnl, cost, net pnl)를 반드시 분리 리포트.

### E. 레짐(시장 국면) 레벨 (ETF는 “관측 지표”로만 사용)
- 관측용 지표로만: QQQ(Tech), XLV(Healthcare), VIX/금리(가능하면) 등. **매매는 금지**.
- 레짐별로 “신호가 작동하는 구간/죽는 구간”을 분리:  
  - 고변동 vs 저변동  
  - 금리 급등락 구간  
  - 섹터 로테이션 구간(Tech↔Healthcare 상대강도)

## 48시간 운영 순서(고정) — 명령형
1) **E1 → E2** 먼저 통과시켜 “측정/비교 가능한 상태”를 만든다.  
2) 그 다음 **E3**로 누수/폴드 퇴화를 제거한다.  
3) 그 다음 **E4**로 비용/회전율 민감도를 확정한다.  
4) 마지막으로 **E5**로 실운영 제약(US only, Tech+Healthcare, 8~14) 안에서 성능을 재측정한다.  
5) 위 게이트 하나라도 FAIL이면 챔피언 교체/승급을 금지하고, FAIL 원인만 패치한다.

이렇게 하면 “성능이 안 움직이는” 문제를 **측정 불가/로그 결함(운영)** → **누수/폴드 품질(과최적화)** → **비용/회전율(현실성)** → **구성 제약(배치 가능성)** → **레짐(구조적 한계)** 순서로 48시간 안에 거의 확실하게 분해할 수 있다.
