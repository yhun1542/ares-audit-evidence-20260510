## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — 명령형 체크리스트

### 1) **리밸런스/아티팩트 로깅 파이프라인 복구(운영 리스크 최우선)**
- **해야 할 일**
  - `--base-log`/`rebalance.csv|jsonl` 경로를 *하드코딩/가짜 인자* 없이 “런 아티팩트 표준 위치”로 강제.
  - 백테스트 실행 시 `rebalance.jsonl`(한 줄=한 이벤트) + `rebalance_summary.json`(집계) **항상 출력**.
  - `champion` JSON에 `file, lane_hash, run_hash, seed, universe_hash, cost_model_hash`를 **필수 필드**로 만들고 누락 시 런을 FAIL.
- **(a) 왜 필요한지**
  - 현재 `rebalance_pinpoint`가 입력 부재/파싱 실패로 무력화됨 → “성능이 안 움직임”의 원인이 **전략이 아니라 관측 불능(telemetry 부재)** 일 가능성이 큼.
  - `Champion file/lane_hash/run_hash None` 상태는 **재현/추적 불가**(운영 리스크).
- **(b) 위험/부작용**
  - 로깅 증가로 I/O 비용 상승(하지만 48시간 루프에서는 디버깅 가치가 훨씬 큼).
  - 스키마 강제 도입 시 기존 런들이 FAIL(단기 불편, 장기 안정).
- **(c) 최소 실험(아래 공용 실험 E1~E5 중 2~3개 사용)**
  - **E1**, **E5**
- **(d) PASS 조건**
  - `rebalance_pinpoint`가 **에러 없이 리포트 생성**.
  - 각 런에서 `rebalance.jsonl` 존재 + **rebalances>0** + `positions/cash` 합계 일관성 체크 PASS.
  - `champion` 메타데이터 필수 필드 누락 0건.

### 2) **Degenerate folds(현재 [1,2,3,8]) 제거: 누수/과최적화 사전 차단 게이트**
- **해야 할 일**
  - CV/워크포워드에서 폴드별 **거래수/노출/유효일수** 최소 기준 미달 시 “폴드 무효”가 아니라 **런 FAIL**로 바꿔 원인을 노출.
  - 피처/라벨에 **purge+embargo**(예: 이벤트 윈도우 기반 누수 차단) 기본 적용.
  - 데이터 조인(특히 펀더멘털/리비전/서프라이즈/가이던스)에서 **발표시각 기준 timestamp 정합성** 자동 검증.
- **(a) 왜 필요한지**
  - degenerate fold는 OOS 평균이 좋아 보여도 **실제로는 거래가 거의 없거나 0노출**일 수 있음 → “움직임 없음/재현 불가”의 대표 원인.
  - 누수/과최적화는 48시간 자동루프에서 **가장 빠르게 망가지는 지점**.
- **(b) 위험/부작용**
  - 단기적으로 OOS 수치 하락 가능(진짜 실력만 남음).
  - 런 FAIL이 늘어 파이프라인이 “빨리 빨갛게” 변함(정상).
- **(c) 최소 실험**
  - **E2**, **E5**
- **(d) PASS 조건**
  - `degenerate_folds == []`
  - 폴드별 `n_trades >= Nmin`, `exposure_mean >= Emin`, `valid_days >= Dmin` 모두 만족(기준은 코드 상수로 고정).
  - purge/embargo 적용 후에도 학습/검증이 정상 완료.

### 3) **비용(슬리피지/커미션/턴오버/대차) 미반영 여부를 “단조성 테스트”로 고정**
- **해야 할 일**
  - 비용 모델을 백테스트 엔진의 단일 모듈로 통합하고, 결과 리포트에 `gross->net bridge`를 고정 출력.
  - **비용을 올릴수록 성과가 떨어져야 한다**(단조성). 이 테스트가 깨지면 런 FAIL.
- **(a) 왜 필요한지**
  - “OOS가 안 움직임”이 아니라 **비용이 0으로 고정/미적용**이면 모든 실험이 무의미.
  - Tech/Healthcare 단일주식은 체결/갭/슬리피지 영향이 큼.
- **(b) 위험/부작용**
  - 성과 수치가 현실적으로 낮아짐(정상).
  - 비용 파라미터 민감도가 커지면 전략이 불안정해 보일 수 있음(실제 리스크를 드러내는 것).
- **(c) 최소 실험**
  - **E3**, **E1**
- **(d) PASS 조건**
  - slippage/비용을 0→5→15bps로 높일 때 `OOS_mean(net)`이 **단조 감소**(최소한 비단조/역전 현상 없음).
  - 리포트에 turnover, 비용총액, 평균 슬리피지, 거래대금 대비 비용 비율이 모두 출력.

### 4) **미국주식 단일종목(Tech+Healthcare) 8~14개 강제: 노출/제약이 실험을 “죽이는지” 확인**
- **해야 할 일**
  - 유니버스를 “US equities ∩ (Tech, Healthcare) ∩ 유동성/시총/가격 필터”로 고정.
  - 포트폴리오 제약을 명시적으로 강제:
    - 보유 종목수 **8~14**
    - 단일종목 max weight, 섹터 편중 제한(Tech/HC 내에서도 서브산업 편중 방지)
    - 현금 비중 상한/하한(0노출 방지)
  - ETF는 **매매 금지**, 단 **관측 지표(레짐/리스크온/오프)** 로만 사용.
- **(a) 왜 필요한지**
  - 현재 exposure max가 0.84인데 exposure min이 0.0 → **0노출 구간**이 길면 실험 변경이 성과로 나타나기 어려움(“no-delta” 착시).
  - 종목수/섹터 강제가 없으면 과최적화가 종목 선택에 숨어버림.
- **(b) 위험/부작용**
  - 강제 종목수로 인해 신호 품질이 낮을 때 성과 하락 가능.
  - 제약 충돌 시 리밸런스가 과도해져 turnover 증가(비용 악화).
- **(c) 최소 실험**
  - **E4**, **E3**
- **(d) PASS 조건**
  - 모든 리밸런스 시점에서 `8 <= n_holdings <= 14` 위반 0건.
  - exposure min이 구조적으로 0에 붙지 않음(예: `exposure_p10 > 0.15` 같은 분위수 기준으로 게이트).
  - ETF 주문/체결 이벤트 0건(“관측만”).

### 5) **트리거/적용/스케일 문제(“신호가 실제로 주문으로 이어지는가”)를 계측으로 고정**
- **해야 할 일**
  - 매일(또는 바 단위) 다음을 로깅:
    - raw score 분포(평균/표준편차/극값/NaN 비율)
    - 트리거 통과율(% days with trade signal)
    - 주문 생성 수, 주문 취소/거절 수, 제약으로 잘린 수(clip)
  - “신호가 존재하지만 주문이 0”이면 원인을 코드 레벨에서 분류(트리거/제약/유니버스/데이터결측).
- **(a) 왜 필요한지**
  - “OOS가 안 움직임”의 흔한 원인은 **스케일/임계값 불일치로 트레이드가 거의 없음** 또는 제약에 의해 주문이 상쇄됨.
- **(b) 위험/부작용**
  - 로깅/모니터링 복잡도 증가.
  - 트리거 조정으로 turnover 급증 위험(비용 게이트와 함께 써야 함).
- **(c) 최소 실험**
  - **E5**, **E2**
- **(d) PASS 조건**
  - 트리거 통과율이 극단적으로 낮지 않음(예: <1%면 FAIL).
  - “주문=0인데 신호≠0” 케이스 0건(있으면 원인 코드가 반드시 태깅되어야 함: `CAUSE=constraint|universe_empty|nan_features|threshold`).

## 공용 “48시간 자동 루프”용 Patch/실험 5개 (3~5개 제한 준수)

아래 **E1~E5만** 이번 사이클에서 돌려서 케이스 폭발을 막아라. (각 TOP5 제안은 이 E1~E5를 조합해 충족)

### E1) Rebalance/Artifact Telemetry Patch
- **(1) 실험 정의**: `rebalance.jsonl` + 메타데이터 필수필드 + 스키마 검증 + pinpoint 입력 경로 자동 연결.
- **(2) 게이트**: 파일 존재/파싱 성공/리밸런스 이벤트>0/메타필드 누락=0.
- **(3) 기대 관측치**: pinpoint 리포트가 생성되고, “언제/왜/무엇이 바뀌었는지” 이벤트 단위로 확인 가능.

### E2) Fold Health + Purge/Embargo + Leak Tripwires
- **(1) 실험 정의**: CV 폴드별 `n_trades/exposure/valid_days` 게이트 + purge/embargo 기본 적용 + 발표시각 정합성 체크.
- **(2) 게이트**: degenerate folds 0, 누수 트립와이어(미래 timestamp 참조) 0.
- **(3) 기대 관측치**: OOS 평균이 다소 내려가도 분산/재현성이 개선되고, 폴드별 성능이 “거래 존재” 조건에서 비교 가능.

### E3) Cost Monotonicity Sweep (0/5/15bps + turnover cap)
- **(1) 실험 정의**: 동일 전략에 비용만 바꿔 3런(또는 1런 내 3시나리오) 생성.
- **(2) 게이트**: 비용 증가 시 net 성과가 단조 감소(비단조면 FAIL).
- **(3) 기대 관측치**: 비용 민감도 곡선 확보 → 비용 미반영/이상 적용 여부 즉시 판별.

### E4) Universe/Constraint Enforcement (Tech+HC, 8~14 names)
- **(1) 실험 정의**: 유니버스 필터 고정 + 보유종목수 8~14 강제 + 단일종목 상한 + ETF 거래 금지.
- **(2) 게이트**: 보유종목수 위반 0, ETF 주문 0, exposure 하위 분위수 게이트 통과.
- **(3) 기대 관측치**: “노출 0 구간” 감소, 실험 간 성과 차이가 더 잘 드러남.

### E5) Signal→Order Coverage Instrumentation (No-Delta Breaker)
- **(1) 실험 정의**: score 분포/트리거율/주문생성/제약clip/결측 비율을 표준 리포트로 고정.
- **(2) 게이트**: 트리거율 최저치 미달 FAIL, `signal_present & order_zero` 케이스 자동 태깅.
- **(3) 기대 관측치**: 성능 무변화의 원인이 “신호 부재/적용 부재/제약 상쇄/비용 상쇄/레짐” 중 어디인지 즉시 분해.

## 성능이 안 움직일 때(“No-Delta”) 원인 분해 아이디어 — 트리거/적용/노출/비용/레짐

아래 트리를 **로그 기반으로 자동 판정**하게 만들어라(사람이 눈으로 추측 금지).

1) **트리거(Trigger)**
- 관측: `trigger_rate`, `days_with_nonzero_score`, `score_std`
- 판정:
  - score가 거의 0/상수 → 피처/스케일/정규화 문제
  - score는 있는데 trigger_rate가 0~1% → 임계값 과도/필터 과도

2) **적용(Application: 신호가 주문으로 변환되는가)**
- 관측: `orders_created`, `orders_rejected`, `orders_clipped_by_constraints`, `universe_empty_days`
- 판정:
  - `signal_present & orders_created==0` → 제약/유니버스/결측/리밸런스 스케줄 버그

3) **노출(Exposure)**
- 관측: `exposure_mean`, `exposure_p10`, `cash_mean`, `n_holdings_distribution`
- 판정:
  - exposure_p10이 0 근처 → 사실상 현금 전략(실험 변화가 성과로 안 보임)
  - holdings가 0 또는 1~2에 치우침 → 유니버스/필터/제약 충돌

4) **비용/턴오버(Cost & Turnover)**
- 관측: `gross_pnl`, `net_pnl`, `total_cost`, `turnover`, `avg_trade_size`
- 판정:
  - gross는 움직이는데 net이 고정/악화 → 비용/슬리피지 과다 또는 비용 모델 오류
  - 비용 바꿔도 결과 동일 → 비용 미적용 버그(=E3로 즉시 검출)

5) **레짐(Regime)**
- ETF는 관측지표로만 사용: 예) QQQ(Tech risk), XLV/IBB(Healthcare/biotech risk), VIX proxy(가능하면 지수로만)
- 관측: 레짐별(리스크온/오프) 성과/노출/트리거율
- 판정:
  - 특정 레짐에서만 트리거/노출이 발생 → 레짐 필터가 지나치게 강하거나, 학습기간 편향(서바이버십/기간편향)

## 즉시 실행 순서(48시간 루프에 그대로 투입)
1. **E1 먼저 적용**(관측/재현이 없으면 이후 모든 실험이 무의미)  
2. **E2 적용**(degenerate folds 제거 + 누수 차단)  
3. **E3 적용**(비용 단조성으로 비용/실행 계층 검증)  
4. **E4 적용**(US Tech+HC 8~14 단일주식 제약 고정)  
5. **E5 상시 켜기**(No-Delta 자동 분해 계측)

위 5개만으로도 현재 로그에서 드러난 핵심(리밸런스 로그 부재, 메타데이터 누락, degenerate folds, 비용/노출/적용 불명)을 24~48시간 내에 “원인-증거-수정” 루프로 묶어낼 수 있다.
