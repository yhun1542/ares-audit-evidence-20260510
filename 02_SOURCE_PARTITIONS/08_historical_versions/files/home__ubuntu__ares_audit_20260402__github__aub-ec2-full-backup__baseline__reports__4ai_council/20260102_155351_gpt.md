아래는 **24~48시간 내 우선순위 TOP5(코드/아키텍처/전략)**이며, 각 항목은 **(a) 필요성 (b) 위험/부작용 (c) 최소 실험 2~3개(단, 아래 5개 공용 Patch/Experiment 묶음 재사용) (d) PASS 조건**으로 정리했습니다.  
규칙 준수: **누수/과최적화/서바이버십/비용 미반영/운영 리스크를 최우선**, **미국주식 only**, **Tech+Healthcare 8~14종목**, **ETF는 거래 금지(관측지표만)**, **48시간 자동 루프 형태**, **실행 가능한 Patch/Experiment는 5개로 제한**.

## 0) 공용 Patch/Experiment 5개 (48시간 루프 기본 단위)
각 TOP5 제안은 아래 **E1~E5**를 **조합**해서 실행합니다(새 실험 폭발 금지).

### E1. (누수/서바이버십) “ASOF 강제 + 디리스트(상폐) 수익 반영 + 1-bar 지연” 패치
- **실험 정의**:  
  - 모든 feature/라벨/리밸런싱 의사결정에 대해 `asof_timestamp <= decision_time` 강제  
  - 가격/펀더/이벤트(실적발표 등) feature는 **최소 1 trading-day lag** 강제(“T에 결정이면 T-1 데이터까지만”)  
  - **상폐/합병/티커 변경** 케이스의 최종 수익(디리스트 리턴)을 backtest에 반영(서바이버십 제거)
- **게이트(자동 FAIL 조건)**:  
  - ASOF 위반 1건이라도 발생 시 FAIL  
  - “상폐 종목 수=0” 또는 “delist_return 컬럼 미존재”면 FAIL(데이터 파이프라인 결함으로 간주)
- **기대 관측치**:  
  - 단기적으로 OOS mean이 **하락할 수 있음(정상)**  
  - 대신 fold 간 분산/극단치가 감소하고, “이상하게 좋은 구간”이 줄어듦

### E2. (비용/현실성) “거래비용+슬리피지+차입비용(쇼트)” 패치
- **실험 정의**:  
  - 주식별 **스프레드 기반 슬리피지(예: half-spread)** + 고정 수수료(또는 bps) + 거래대금 비례 market impact(단순 sqrt 모델도 OK)  
  - 쇼트가 있으면 **borrow fee**(보수적으로) 반영, 불가 종목은 쇼트 금지 처리
- **게이트**:  
  - 비용 모델 적용 후도 **총 거래비용/일이 상한**(예: NAV 대비 X bps/day) 아래여야 PASS  
  - “비용 0” 혹은 “거래가 있는데 비용이 0”이면 FAIL(계산 누락)
- **기대 관측치**:  
  - turnover 높은 전략이 눈에 띄게 악화 → 현실성 확보  
  - 이후 최적화가 turnover/빈도 억제 쪽으로 유도됨

### E3. (노출/운영 리스크) “8~14종목 + 단일종목/섹터 캡 + 총노출 게이트” 패치
- **실험 정의**:  
  - **보유 종목 수 8~14 강제(Tech+Healthcare만)**  
  - 단일 종목 비중 상한(예: 12~15%), 섹터(Tech/Healthcare 내) 캡, 총 익스포저 상한(예: 0.75~0.85)  
  - 리밸런싱 시 “미세한 변동”은 무시하는 **min-trade threshold**로 churn 감소
- **게이트**:  
  - 종목수/상한/총노출 위반 1회라도 FAIL  
  - 챔피언 현재 exposure_max ~0.844로 이미 높음 → 상한 위반 시 즉시 차단
- **기대 관측치**:  
  - 샤프가 약간 감소할 수 있으나 MDD/운영 안정성 개선  
  - 리밸런스 빈도/거래량 감소

### E4. (운영/관측) “Rebalance 로그 복구 + worst_mdd 산출 + JSONL 정합성” 패치
- **실험 정의**:  
  - 현재 상태: `--base-log` 경로 오류 + rebalance.csv/JSON 파싱 실패 + `worst_mdd: None` → **관측 불능**  
  - backtest 실행 시 **표준 rebalance.jsonl**(결정시각, 목표비중, 체결비중, 가격, 슬리피지, 비용, 포지션 변화, turnover) 강제 저장  
  - 매 실행마다 `worst_mdd`, turnover, cost, exposure 타임시리즈를 산출/아카이빙
- **게이트**:  
  - 파일 경로 미존재/빈 파일/JSON 파싱 실패 시 FAIL  
  - `worst_mdd=None`이면 FAIL(리스크 지표 결측은 운영불가)
- **기대 관측치**:  
  - “왜 성능이 안 움직이는지”를 거래/리밸런스 단위로 쪼개 볼 수 있게 됨  
  - No-Delta(변화 없음) 원인을 로그로 특정 가능

### E5. (레짐/과최적화) “ETF 관측지표로 레짐 분해 + 구간별 OOS 안정성 게이트” 패치
- **실험 정의**(ETF는 거래 X, 관측만):  
  - 관측: QQQ(테크), XLV(헬스케어), SPY(시장), IWM(리스크온), VIX proxy(예: VIX 지수/선물 대체 데이터 가능 시)  
  - 레짐 라벨: (상승/하락, 고변동/저변동, Tech>Health / Health>Tech) 등 단순 규칙으로 분할  
  - 각 레짐별 OOS mean/min, MDD, 비용/turnover를 자동 리포트
- **게이트**:  
  - 특정 레짐에서만 성능이 과도하게 좋고 나머지가 붕괴하면 FAIL(과최적화 시그널)  
  - 레짐별 표본 수가 너무 작으면(예: 5% 미만) 해당 분해는 참고만 하고 PASS/FAIL에 과가중 금지
- **기대 관측치**:  
  - “안 움직임”이 레짐 한정 문제인지(예: 2022형 약세/고변동) 즉시 식별  
  - 개선 방향이 비용/노출/시그널 적용 타이밍 중 어디인지 좁혀짐

# 1) TOP5 우선순위 제안 (24~48h)

## TOP1) 누수/서바이버십 “선 제거” (신뢰 가능한 OOS 확보)
### (a) 왜 필요한지
- 현재 챔피언에서 `worst_mdd: None` 등 **기초 리스크 관측 결측**이 있고, 진단기 출력(Champion OOS Mean 2.6276)과 ONE TRUTH(1.88)가 **불일치**합니다. 이 상태는 “성능이 좋다/안 좋다” 자체가 흔들릴 수 있어 최우선으로 데이터/평가 신뢰도를 고정해야 합니다.
- Tech/Healthcare 개별주 8~14종목 전략은 **소수 종목/이벤트(실적, 규제, M&A)**에 민감 → 누수/서바이버십이 있으면 성능이 허수로 커집니다.

### (b) 위험/부작용
- 누수 제거 즉시 성능이 떨어질 수 있음(정상).  
- 단기적으로 “실험들이 전부 나빠지는 것처럼” 보여 개발 동력이 흔들릴 수 있음(그래서 게이트/로그가 필요).

### (c) 최소 실험(공용 묶음 재사용)
- **E1 실행**(ASOF/1-day lag/디리스트 반영)  
- **E4 실행**(로그 정합성/지표 결측 제거)  
- **E5 실행**(레짐별로 누수 의심 구간(특정 레짐에서만 폭발) 탐지)

### (d) PASS 조건
- ASOF 위반 0건, delist 반영 확인, `worst_mdd` 산출됨  
- ONE TRUTH의 OOS와 진단기 OOS가 **동일 정의로 재현**(동일 스냅샷/동일 집계 규칙)  
- 누수 제거 후에도 OOS min이 “0 근접 붕괴”로 급락하지 않음(급락하면 기존 성능이 누수 가능성 큼)

---

## TOP2) 비용/슬리피지/차입비용 반영으로 “현실성 고정”
### (a) 왜 필요한지
- Tech 대형주는 스프레드가 좁아 보이지만, **리밸런스 빈도/턴오버**가 높으면 비용이 성과를 먹습니다.
- “성능이 안 움직임”은 종종 **알파가 비용에 상쇄**되어 발생합니다(특히 미세한 신호/잦은 리밸런스).

### (b) 위험/부작용
- 백테스트 성능 악화(정상).  
- 비용 모델 파라미터가 과보수적이면 유망 전략까지 과소평가할 수 있음(하지만 48시간 루프에서는 보수적이 안전).

### (c) 최소 실험
- **E2 실행**(비용/슬리피지/borrow)  
- **E4 실행**(리밸런스 단위로 비용이 실제로 찍히는지 검증)  
- **E3 실행**(min-trade threshold로 churn 억제 → 비용 민감도 감소)

### (d) PASS 조건
- “거래가 있는데 비용이 0”이 사라짐  
- 비용 반영 후에도 OOS가 완전 붕괴하지 않고, **turnover/일**이 상한 아래로 안정화  
- 비용 반영 유무에 따른 성능 차이가 “설명 가능한 수준”으로 로그에 귀속됨(예: 특정 리밸런스에서 슬리피지 급증)

---

## TOP3) 리밸런스/지표 로깅 복구(운영 리스크 제거) + “No-Delta” 원인 추적 가능화
### (a) 왜 필요한지
- 현재 rebalance pinpoint가 **입력 로그 로딩 실패**로 아무 것도 못 보고 있습니다:  
  - `--base-log` 파일 경로 오류  
  - rebalance.csv/JSON 파싱 실패  
- 이 상태는 “전략이 변했는데 성능이 그대로” vs “아예 주문/리밸런스가 안 일어남”을 구분 불가 → 자동 루프 운영 리스크 최상급.

### (b) 위험/부작용
- 로그 스키마 변경으로 기존 도구들이 깨질 수 있음 → **표준 스키마(고정)**가 필요.
- IO 증가(저장용량/속도). 하지만 48시간 루프에서는 필수 비용.

### (c) 최소 실험
- **E4 실행**(표준 rebalance.jsonl 생성/파싱/지표 산출)  
- **E1 실행**(decision_time/feature_time 정합성도 함께 로그로 남겨 누수 추적)  
- **E2 실행**(리밸런스 로그에 비용 항목 강제 포함)

### (d) PASS 조건
- pinpoint 도구가 base/cand 모두에서 **정상 리밸런스 diff**를 출력  
- `worst_mdd`가 None이 아니고, 리밸런스별 turnover/cost가 시계열로 일관되게 존재  
- “No-Delta” 발생 시 로그로 원인이 분류됨(예: 신호 동일/게이트로 주문 차단/유니버스 부족/가격 결측)

---

## TOP4) 노출/종목수(8~14)/단일종목 캡을 게이트로 고정(과최적화/운영 리스크 동시 저감)
### (a) 왜 필요한지
- 현재 챔피언의 exposure_max가 **~0.844**로 높습니다. 소수 종목 전략에서 이 정도 총노출은 단일 이벤트에 취약합니다.
- “성능이 안 움직임”은 종종 **포지션이 사실상 고정(게이트/제약 미비)**이거나, 반대로 **너무 자주 흔들려 비용에 상쇄**되는 두 극단에서 발생합니다. 게이트로 중간을 강제해야 합니다.

### (b) 위험/부작용
- 상한/종목수 강제는 알파를 일부 깎을 수 있음.  
- 제약이 너무 타이트하면 “항상 비슷한 포트폴리오”가 되어 개선 여지가 줄어듦(그래도 운영 안정성이 우선).

### (c) 최소 실험
- **E3 실행**(8~14, 단일종목/섹터 캡, 총노출 상한, min-trade threshold)  
- **E2 실행**(제약이 비용을 얼마나 줄이는지 확인)  
- **E5 실행**(레짐별로 제약이 과도하게 방어적으로 작동하는지 확인)

### (d) PASS 조건
- 종목수 8~14 준수 + 단일종목 상한 위반 0  
- 노출 상한 내에서 OOS min이 바닥으로 꺼지지 않음  
- turnover가 의미 있게 감소하고, 비용 반영 성능이 개선 또는 안정화

## TOP5) 레짐 분해(ETF 관측만)로 “성능 정체” 원인을 구간별로 격리
### (a) 왜 필요한지
- Tech/Healthcare는 레짐 민감(금리, 리스크오프, AI/바이오 사이클). 성능이 안 움직이는 건 “전체 평균”에서 상쇄될 수 있습니다.
- ETF는 거래하지 않더라도, **전략이 어떤 시장 상태에서 작동/미작동인지**를 48시간 루프에서 빠르게 확인하는 관측지표로 최적.

### (b) 위험/부작용
- 레짐 라벨이 너무 세분되면 표본 부족으로 결론이 흔들림.  
- 레짐에 맞춘 과도한 분기/조건부 전략으로 가면 과최적화 위험(여기서는 “분해/관측”까지만).

### (c) 최소 실험
- **E5 실행**(레짐 분해 리포트 자동 생성)  
- **E4 실행**(레짐별로 리밸런스/비용/노출이 어떻게 달라지는지 결합 리포트)  
- **E1 실행**(레짐별로 누수 의심 패턴(특정 구간만 비정상적으로 좋음) 감시)

### (d) PASS 조건
- 레짐별 성능표가 자동 생성되고, “정체 원인”이 최소 1개 축에서 분리됨(예: 고변동 레짐에서만 비용 폭증, 하락 레짐에서만 노출 과다)  
- 레짐별 표본 부족 경고가 함께 출력(과해석 방지)

# 2) 48시간 자동 루프용 “명령형 체크리스트”(실행 순서)
1. **E4부터 적용하라**: rebalance 로그/지표 산출(특히 `worst_mdd`)이 없으면 나머지 실험은 해석 불가로 간주하고 중단하라.  
2. **E1을 즉시 켜라**: ASOF/lag/delist 강제 후, 기존 챔피언 OOS가 얼마나 변화하는지 기록하라(하락해도 정상).  
3. **E2를 켜라**: 비용 0/누락이 없는지 로그로 검증하고, turnover 상한을 초과하면 FAIL 처리하라.  
4. **E3를 켜라**: 8~14 종목 + 단일종목/총노출 캡 위반을 하드 FAIL로 만들고, min-trade threshold로 churn을 줄여라.  
5. **E5를 돌려라**: 레짐별로 성능/비용/노출을 분해해 “정체”가 어디서 오는지 구간을 확정하라.

# 3) 성능이 안 움직일 때 “원인 분해 아이디어”(트리거/적용/노출/비용/레짐)
아래 트리는 **로그(E4) 없이는 불가능**하므로, E4가 전제입니다.

## A. Trigger(신호 생성) 문제
- **증상**: 예측/스코어 분포가 매일 거의 동일, 상위 종목이 고정
- **점검/조치**
  - 스코어의 일별 분산/순위변동(켄달/스피어만) 추적
  - feature 업데이트 주기 확인(펀더멘털이 “미래값”이거나 반대로 “갱신이 안 됨”)
- **연결 실험**: E1(ASOF/lag), E4(스코어 로그 포함)

## B. Application(적용/주문) 문제 — “No-Delta”의 1순위 운영 원인
- **증상**: 스코어는 변하는데 포트폴리오는 그대로, 혹은 리밸런스가 거의 없음
- **점검/조치**
  - 게이트가 과도하게 차단하는지(종목수, 상한, 최소주문, 거래가능성) 리밸런스 로그로 확인
  - 유니버스가 비는지(Tech+Healthcare 필터 이후 8종목 미만이면 리밸런스 불능)
- **연결 실험**: E4, E3

## C. Exposure(노출/구성) 문제
- **증상**: 총노출이 상단에 붙어(현재 max~0.844) 사실상 “항상 비슷한 베타”가 됨 → 알파 변화가 희석
- **점검/조치**
  - (1) 총노출 타임시리즈 (2) 단일종목 비중 상위 집중도 (3) 섹터 내 편향 추적
- **연결 실험**: E3, E5

## D. Cost(비용) 문제 — 알파가 비용에 상쇄
- **증상**: gross 성과는 좋아 보이나 net이 정체/악화, 또는 특정 리밸런스에서만 성과가 사라짐
- **점검/조치**
  - 리밸런스별 turnover와 슬리피지/비용 기여를 분해(“비용 이벤트” 찾기)
  - min-trade threshold/리밸런스 주기 완화 효과 확인
- **연결 실험**: E2, E4, E3

## E. Regime(레짐) 문제 — 평균에서 상쇄
- **증상**: 어떤 기간에는 잘 되고 다른 기간에는 반대로 손실 → 전체 평균이 “안 움직임”
- **점검/조치**
  - QQQ/XLV/SPY 관측으로 레짐 라벨링 후 구간별 OOS, MDD, 비용/노출 비교
  - “테크 주도장 vs 헬스케어 방어장”에서 동일 포지셔닝을 하고 있지 않은지 확인
- **연결 실험**: E5, E4

---

## 최종 요약(우선순위)
- **1순위는 E4(관측 복구) + E1(누수/서바이버십 제거)**: 지금은 성능 논의 자체가 흔들릴 수 있는 상태.
- 그 다음 **E2(비용 현실화)**로 “알파가 비용에 상쇄되는 정체”를 배제.
- **E3(8~14/캡/노출 게이트)**로 운영 안정화.
- **E5(레짐 분해)**로 정체 원인을 구간 단위로 확정.

위 5개(E1~E5)는 48시간 자동 루프에 그대로 얹을 수 있게 **정의/게이트/기대 관측치**까지 고정해 둔 형태입니다.
