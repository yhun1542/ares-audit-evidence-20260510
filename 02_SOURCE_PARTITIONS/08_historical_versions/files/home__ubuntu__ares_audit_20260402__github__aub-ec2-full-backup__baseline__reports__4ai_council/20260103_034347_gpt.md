## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — 명령형 체크리스트
우선순위는 **누수 → 과최적화/검증붕괴 → 비용/체결 → 서바이버십 → 운영리스크** 순으로 배치.

---

# 1) (P0) “검증이 깨짐”부터 고치기: degenerate folds / run_hash·lane_hash / worst_mdd None
### (a) 왜 필요한지
- 현재 상태에서 **degenerate_folds=[1,2,3,8]**, **lane_hash/run_hash=None**, **worst_mdd=None**는 “성능이 안 움직이는” 게 아니라 **검증/리포팅 파이프라인이 정상 산출을 못 하는 상태**일 확률이 큼.
- 이 상태에서는 어떤 전략 patch도 “PASS/FAIL”을 신뢰할 수 없음(과최적화·누수 탐지 불가).

### (b) 위험/부작용
- 폴드 생성/시드 고정으로 과거 챔피언 대비 수치가 급변할 수 있음(정상).
- 리포트 포맷 변경으로 기존 도구가 추가로 깨질 수 있음(마이그레이션 필요).

### (c) 최소 실험(단일 패치 내 동시 실행 2~3개 “내장 검증”)
**PATCH-1: Validation/Artifact Hardening (1개 패치로 48h 루프 탑재)**
1) **Fold 생성 강제 규격화**: time-series split에서 각 fold 최소 샘플/거래일 수 미만이면 fold 폐기/재생성.  
2) **Hash 강제 부여**: (config + code git SHA + data snapshot id)로 lane_hash/run_hash 강제 생성, 리포트에 주입.  
3) **Metric 완결성 게이트**: worst_mdd, turnover, trade_count, cost_pnl이 None이면 “실패로 종료” 처리.

### (d) PASS 조건(게이트)
- degenerate_folds = 0
- lane_hash/run_hash 모두 non-null
- worst_mdd / turnover / trade_count / cost_pnl 모두 산출
- 동일 config 재실행 시 주요 OOS 메트릭 변동이 허용범위 내(예: OOS mean ±2~3%p 이내)로 재현

### 48h 자동 루프 형태
- **(1) 실험 정의**: “PATCH-1 적용 전/후 동일 챔피언 재실행(데이터 스냅샷 고정) + 리포트 산출”
- **(2) 게이트**: 위 PASS 조건 전부 충족 못 하면 이후 실험 전부 중단
- **(3) 기대 관측치**: 리포트/리밸런스 로그가 안정적으로 생성되고, “성능 변화 없음”이 진짜인지/파이프라인 문제인지 분리됨

# 2) (P0) 누수/정렬(lookahead) 자동 탐지: “No-Delta”가 실제인지 확인
### (a) 왜 필요한지
- “성능이 안 움직임”은 자주 **신호가 미래 데이터를 보고 있거나**, 반대로 **정렬이 어긋나 신호가 적용되지 않는** 두 극단에서 발생.
- Tech/Healthcare 단일 종목(8~14)일수록 작은 정렬 오류가 전체를 무력화.

### (b) 위험/부작용
- 엄격한 point-in-time 적용 후 과거 성능이 하락할 수 있음(정상: 누수 제거).
- 일부 피처/데이터 소스가 사용 불가 판정될 수 있음(대체 필요).

### (c) 최소 실험
**PATCH-2: Leakage/Alignment Sentinel (1개 패치)**
1) **Shift-1 강제 비교(내장 A/B)**: 모든 피처를 +1 bar shift한 “의도적 열화 버전”을 병렬 계산 → 원본과 성능이 비슷하거나 원본이 더 나쁘면 정렬/적용 문제 의심.  
2) **Label leakage test**: 목적변수/수익률 계산에 사용된 close/adjclose 시점이 신호 생성 시점보다 미래면 즉시 실패.  
3) **Apply-rate 계측**: “신호 생성됨 → 주문 생성됨 → 체결됨” 단계별 카운트/비율을 로그로 남김(0에 수렴하면 적용 문제).

### (d) PASS 조건
- Shift-1 열화 버전이 **일관되게 성능 저하**(예: OOS mean이 의미 있게 감소)해야 함  
- lookahead 규칙 위반 0건
- apply-rate(신호→주문)가 최소 임계치 이상(예: 신호 발생일의 90% 이상 주문 생성)

### 48h 자동 루프
- **(1) 실험 정의**: “원본 vs Shift-1 vs 강제 lookahead 차단” 3-arm을 한 번의 러너에서 병렬 산출
- **(2) 게이트**: lookahead 1건이라도 발견 시 즉시 실패 처리(다음 실험 중단)
- **(3) 기대 관측치**: “No-Delta”가 전략 무반응인지, 누수/정렬/적용 문제인지 즉시 분리

# 3) (P0) 비용/체결/리밸런스 로그 복구: 현재 rebalance pinpoint가 데이터 자체를 못 읽음
### (a) 왜 필요한지
- 로그 오류:
  - `Error loading --base-log: No such file or directory: '--base-log'`
  - `rebalance.csv ... Expecting value ...`
- 비용/리밸런스 데이터가 없으면 **거래비용 미반영** + **운영/체결 리스크 미계측** 상태로 과최적화 위험이 최상위.

### (b) 위험/부작용
- 비용/슬리피지 반영 후 성능이 떨어질 수 있음(정상).
- 회전율 높은 전략은 사실상 폐기될 수 있음.

### (c) 최소 실험
**PATCH-3: Rebalance Log Contract + Cost Model (1개 패치)**
1) **리밸런스 로그 스키마 고정(JSONL)**: timestamp, ticker, target_w, prev_w, delta_w, shares, price, notional, est_slippage_bps, commission, realized_cost를 강제 출력.  
2) **비용모델 최소 도입**:  
   - commission(고정 + bps)  
   - slippage = k * volatility * |delta_notional| (최소형)  
3) **turnover/impact 게이트**: turnover 상한 초과 시 포지션 변경량 클리핑(운영 안정화).

### (d) PASS 조건
- pinpoint 도구가 base/cand 둘 다에서 리밸런스 로그를 정상 로드
- cost_pnl 산출(0/None 금지)
- 비용 반영 후에도 OOS mean이 “완전 붕괴”하지 않음(예: 비용 전 대비 -X%p 이상 하락 시 FAIL; X는 내부 기준으로 고정)

### 48h 자동 루프
- **(1) 실험 정의**: 동일 전략을 “비용 0” vs “비용 on” 병렬 산출(단일 실행 내)
- **(2) 게이트**: 로그 로드 실패/비용 None이면 실패
- **(3) 기대 관측치**: “성능이 안 움직임”이 사실 비용/체결에서 상쇄되는지 즉시 확인 가능

# 4) (P1) 서바이버십/유니버스 고정(미국주식 Tech+Healthcare 8~14) + 상장폐지/행동 처리
### (a) 왜 필요한지

### (b) 위험/부작용
- 유니버스가 고정되면 과거 특정 구간 성능이 하락할 수 있음(정상).
- 상장폐지/합병 처리 로직이 추가되며 구현 복잡도 증가.

### (c) 최소 실험
**PATCH-4: Universe Contract (1개 패치)**
1) **거래 유니버스 하드락(8~14)**: 예시(미국, Tech+HC 중심, 대형/유동성):

   - Healthcare: UNH, JNJ, ABBV, LLY, MRK, TMO  *(총 12)*  
2) **데이터 품질 게이트**: 각 종목별 결측/거래정지/스플릿·배당 조정 여부 체크(Adj 기반 통일).  
3) **상장폐지/합병 이벤트 처리**: 가격 소실 시 “강제 청산 + 현금화” 규칙 고정(미반영 시 서바이버십/운영리스크).

### (d) PASS 조건
- 백테스트 전 구간에서 각 티커별 데이터 완결성 리포트 생성

- 유니버스가 실험 간 변하지 않음(재현성)

### 48h 자동 루프

- **(2) 게이트**: 데이터 결측 시 포지션 잔존하면 FAIL
- **(3) 기대 관측치**: 서바이버십/운영 이벤트에 대한 내성이 수치화됨

# 5) (P1) 노출/레짐/리스크 오버레이: “노출이 0~0.84”면 무반응 가능성 높음
### (a) 왜 필요한지
- exposure_min/max가 0.0 / 0.838… → 구간에 따라 **거의 미투자(0)**가 길면 “전략 개선”이 성능에 반영되지 않음.
- ETF는 매매 금지지만, 레짐 관측(예: QQQ/SPY, XLK, XLV, IBB)은 허용이므로 **리스크 게이트**로만 사용.

### (b) 위험/부작용
- 리스크 오버레이가 과도하면 수익 기회도 차단(언더익스포저).
- 레짐 지표가 지연/과적합될 수 있음(간단한 규칙부터).

### (c) 최소 실험
**PATCH-5: Exposure/Risk Overlay Minimal (1개 패치)**
1) **노출 하한 게이트**: “신호가 존재하면 최소 gross exposure ≥ E_min”을 강제(예: 0.3)하여 무반응 제거.  
2) **레짐 관측 기반 위험축소(관측만)**:  
   - 예: QQQ 50D<200D 이거나 SPY 변동성 상위 분위면 포지션 스케일 0.5  
3) **포지션 클리핑/턴오버 제한**: 종목당 max weight, 하루 변경량 cap으로 운영 리스크 감소.

### (d) PASS 조건
- 노출 분포가 “0에 쏠림”에서 벗어남(예: 투자일 비율, 평균 gross 증가)
- turnover가 상한 내 유지
- 비용 반영 OOS에서 성능/변동성/드로우다운이 동시에 악화되지 않음(최소 2개 지표 개선 또는 1개 개선+1개 유지)

### 48h 자동 루프
- **(1) 실험 정의**: (기존) vs (노출 하한) vs (노출 하한+레짐 축소) 3-arm 병렬(단일 실행)
- **(2) 게이트**: turnover/비용/드로우다운 임계치 초과 시 FAIL
- **(3) 기대 관측치**: “전략이 안 먹는 것처럼 보이는” 원인이 노출/리스크 레이어인지 분리

## 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐) — 트리 형태 체크리스트
아래는 **질문 없이** 바로 로그/리포트에 추가해서 자동 분해하도록 설계.

### A. 트리거(신호가 생성되나?)
- [ ] 날짜별 신호 발생률(% days with non-zero score) 로그화  
- [ ] score 분포(평균/표준편차/상하위 1% 클리핑 여부)  
- [ ] Shift-1 열화 테스트에서 성능 차이가 존재하는지(없으면 정렬/누수/무의미 신호 의심)

**관측 시나리오**
- 신호 발생률이 낮음 → 트리거 조건 과도/피처 결측  
- 분산이 거의 0 → 정규화/스케일링 버그 또는 상수 피처

### B. 적용(신호→주문→체결로 이어지나?)
- [ ] 신호 발생일 대비 주문 생성 비율  
- [ ] 주문 생성 대비 체결 비율(시뮬레이터라도 fill 가정 명시)  
- [ ] 리밸런스 로그에 delta_w가 0으로만 찍히는지

**관측 시나리오**
- 신호는 있는데 주문 0 → 리스크 오버레이가 전부 차단 / 포지션 제한이 0으로 수렴  
- 주문은 있는데 체결 0 → 체결 모델/가격 참조 시점 오류

### C. 노출(실제로 돈이 들어가 있나?)
- [ ] gross/net exposure 시계열 + 히스토그램  
- [ ] 투자일 비율(% exposure>0.1)  
- [ ] 종목별 평균 weight / 최대 weight

**관측 시나리오**
- 노출이 자주 0 → 무반응(개선이 성능에 반영 안 됨)  
- 노출이 높지만 성능 무변화 → 비용/레짐/신호 무효 가능성

### D. 비용(거래비용이 다 먹나?)
- [ ] 총 PnL = alpha_pnl + market_pnl - cost_pnl 로 분해  
- [ ] cost_pnl / gross_pnl 비율  
- [ ] turnover vs pnl 상관(회전만 높고 pnl 없으면 과최적화/노이즈)

**관측 시나리오**
- 비용 반영 후만 무너짐 → 슬리피지/턴오버 캡 필요  
- 비용이 0 또는 None → 리포팅 실패(즉시 P0)

### E. 레짐(시장 환경에서만 죽나?)
- [ ] 레짐 버킷별 성능: (예) QQQ 추세(50/200), SPY 변동성 분위, XLK-XLV 상대강도  
- [ ] 버킷별 노출 차이(레짐에서만 노출 0으로 떨어지는지)

**관측 시나리오**
- 특정 레짐에서만 노출 0 → 레짐 게이트 과도  
- 특정 레짐에서만 손실 집중 → 관측지표 기반 스케일링이 유효
