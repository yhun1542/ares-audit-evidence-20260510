## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — 명령형 체크리스트

### 1) **누수/서바이버십/평가 불일치(OOS mean 3.32 vs 2.63) 즉시 봉합**
**(a) 왜 필요한지**
- 현재 “Champion OOS Mean” 값이 리포트/러너에서 서로 다르게 보임(3.3249 vs 2.6276). 이 상태에선 어떤 개선도 신뢰 불가.
- degenerate_folds([1,2,3,8])는 CV가 실제로 학습/검증을 제대로 못 돌렸거나, 폴드 데이터가 비어/상수/정렬 깨짐 가능성이 큼(과최적화·누수·서바이버십의 전형적 전조).

**(b) 위험/부작용**
- 엄격한 무결성 체크를 추가하면 단기적으로 실험이 “실패”로 많이 떨어져 속도가 느려짐.
- 기존 성능이 “착시”였다면 성능이 하락해 보일 수 있음(정상).

**(c) 최소 실험 2~3개 (48시간 자동 루프형)**
1) **EX1: 단일 소스 OOS 스코어 정규화(평가 파이프라인 고정)**
   - (1) 실험 정의: `score_oos()` 계산을 단일 함수로 강제하고, 러너/diagnoser/리포트가 동일 JSON 필드를 읽도록 패치(예: `metrics/oos_mean`, `metrics/oos_min`, `metrics/mdd`).
   - (2) 게이트: 동일 run_hash에 대해 3개 도구 출력의 oos_mean 차이 `abs(diff) <= 1e-6`.
   - (3) 기대 관측치: “3.32 vs 2.63” 불일치 0으로 수렴, 원인(다른 기간/다른 비용/다른 리밸런스 규칙) 로그에 명시.

2) **EX2: 폴드 퇴화(degenerate_folds) 원인 격리용 정적 진단**
   - (1) 실험 정의: 각 fold별 (샘플 수, 유니크 날짜 수, 결측률, feature 분산, label 분산, 트레이드 수) 출력하는 `fold_health_report.json` 생성.
   - (2) 게이트: 모든 fold에서 `n_dates >= 최소 기준`, `label_std > 0`, `features_std_ratio`가 임계치 이상.
   - (3) 기대 관측치: degenerate_folds가 “데이터 공백/정렬/필터링 후 0샘플/상수 피처” 중 하나로 귀결.

3) **EX3: 서바이버십/룩어헤드 하드 체크(테크+헬스케어 8~14종목 universe 고정)**
   - (1) 실험 정의: 백테스트 시작 시점에 종목 리스트를 고정(IPO 이후 편입 금지), 각 피처의 timestamp가 t 시점 이전 데이터만 쓰는지 “최대 허용 지연(lag)” 검증.
   - (2) 게이트: 위반 건수 0, 위반 시 run 즉시 FAIL.
   - (3) 기대 관측치: 누수 가능성 제거, 성능이 바뀌면 “이전 성능은 누수/서바이버십 영향”으로 판정 가능.

**(d) PASS 조건**
- OOS 산출이 모든 도구에서 동일 + degenerate_folds 원인이 로그로 1차 판명 + 룩어헤드/서바이버십 위반 0.

### 2) **비용(수수료/슬리피지/스프레드) 미반영 가능성 차단 + 비용 민감도 계측**
**(a) 왜 필요한지**
- “성능이 안 움직임”의 1순위 가설: 개선분이 거래비용에 의해 상쇄.
- 비용이 파이프라인/리포트 어디에 적용되는지 불명확하면 최적화가 허공에 뜸.

**(b) 위험/부작용**
- 비용 적용 후 OOS 급락 가능(정상).
- 거래 빈도가 줄어 노출이 0에 가까워질 수 있음(현재 exposure_min=0.0과도 정합).

**(c) 최소 실험 2~3개**
1) **EX1: 비용 모델 “강제 온/오프” 2점 민감도(동일 신호, 동일 리밸런스)**
   - (1) 실험 정의: 동일 run 설정에서 `cost=0` vs `cost=prod(commission+slippage+half-spread)` 두 번 산출(학습 재사용 가능하면 재사용).
   - (2) 게이트: 두 결과의 차이를 `cost_drag = oos_mean_no_cost - oos_mean_with_cost`로 리포트에 고정 출력.
   - (3) 기대 관측치: cost_drag가 크면 “전략 개선은 트레이드 효율(Turnover)부터”로 방향 확정.

2) **EX2: Turnover/거래횟수/체결가정 로그 표준화**
   - (1) 실험 정의: 매 리밸런스마다 (target %, filled %, 예상 슬리피지, 추정 스프레드 비용, turnover) JSONL로 저장.
   - (2) 게이트: 리밸런스 로그 파일 존재 + 구간별 turnover 시계열 생성 성공.
   - (3) 기대 관측치: 성능 정체 구간이 “턴오버 스파이크” 혹은 “거래 0” 구간과 매칭되는지 즉시 확인 가능.

3) **EX3: 비용 내성 게이트(자동 루프에서 조기 중단)**
   - (1) 실험 정의: OOS에서 `turnover_p95`가 임계치 초과면 실험 FAIL(과거 대비 과도한 매매 전략 차단).
   - (2) 게이트: `turnover_p95 <= threshold` AND `avg_positions in [8,14]`.
   - (3) 기대 관측치: 비용에 취약한 후보가 자동으로 걸러져 “움직이는 개선”만 남음.

**(d) PASS 조건**
- cost_drag/turnover 로그가 항상 산출되고, 후보 비교가 “비용 반영 후” 기준으로 일관되게 가능.

### 3) **운영 리스크(리밸런스 로그 깨짐, MDD None) 관측 가능성(Observability) 복구**
**(a) 왜 필요한지**
- `aub_rebalance_pinpoint`가 입력 로그를 못 읽고 있음(파일 없음/JSON 파싱 실패).
- `worst_mdd: None`은 리스크 지표 미산출 또는 파이프라인 단절. 운영 단계에서 즉시 사고로 이어짐.

**(b) 위험/부작용**
- 로그/아티팩트 표준화로 디스크 사용량 증가.
- 스키마 변경 시 기존 리포트 도구와 호환성 이슈.

**(c) 최소 실험 2~3개**
1) **EX1: 리밸런스 출력 스키마 고정 + 경로 자동 주입**
   - (1) 실험 정의: 모든 run에 대해 `artifacts/<run_hash>/rebalance.jsonl` 강제 생성(한 줄=한 리밸런스, JSON schema 버전 포함).
   - (2) 게이트: 파일 존재 + 첫 10줄 JSON parse 성공 + schema_version 일치.
   - (3) 기대 관측치: pinpoint 도구가 “항상” 작동, 리밸런스 변화가 성능 변화로 연결되는지 바로 추적 가능.

2) **EX2: MDD/노출/현금비중 계산을 “트레이드 로그”가 아닌 “포트폴리오 가치 시계열”에서 직접 산출**
   - (1) 실험 정의: daily equity curve를 필수 아티팩트로 저장하고, 거기서 MDD/worst_mdd/exposure를 재계산.
   - (2) 게이트: `worst_mdd != None` AND exposure 시계열 길이 == OOS 일수.
   - (3) 기대 관측치: 리스크 지표 공백 제거, degenerate 전략(거래 없음/노출 0) 즉시 식별.

3) **EX3: 자동 루프 “아티팩트 무결성 게이트”**
   - (1) 실험 정의: (equity_curve.csv, rebalance.jsonl, metrics.json) 3종이 없으면 run FAIL.
   - (2) 게이트: 3종 존재 + parse OK.
   - (3) 기대 관측치: “성능이 안 움직이는 이유가 로그 부재”인 상태를 근절.

**(d) PASS 조건**
- pinpoint/MDD/노출이 매 run에서 자동 생성되고, 다음 실험이 이전 실험과 비교 가능.

### 4) **노출(0~0.84) 불안정/거래 0 구간 제거: 트리거→포지션 형성 파이프 점검**
**(a) 왜 필요한지**
- exposure_min=0.0은 “현금 대기”가 장기간 발생 가능성을 의미. 이러면 개선이 신호가 아니라 “시장 방향”에 묻혀 OOS가 정체되기 쉽다.
- 특히 8~14종목 제약(테크+헬스케어)에서는 포지션 수/리밸런스 주기/진입 임계값이 조금만 꼬여도 거래 자체가 사라짐.

**(b) 위험/부작용**
- 강제 노출 하한을 두면 하락장에서 MDD 악화 가능.
- 너무 자주 리밸런스하면 비용 증가.

**(c) 최소 실험 2~3개**
1) **EX1: “신호는 있는데 실행이 안 되는” 구간 분리 로깅**
   - (1) 실험 정의: 매일 (raw_signal 존재 여부, 통과한 필터 수, 최종 주문 수, 체결 수, 최종 보유 종목 수) 카운트 로그 저장.
   - (2) 게이트: OOS 기간 중 `days_with_signal>0`인데 `orders=0`인 날 비율이 임계치 이하.
   - (3) 기대 관측치: 정체 원인이 (트리거) vs (필터) vs (리밸런스/체결) 중 어디인지 하루 단위로 분해.

2) **EX2: 노출 하한/포지션 수 하한 게이트(전략 파라미터가 아닌 “안전장치”)**
   - (1) 실험 정의: `min_positions=8`, `max_positions=14`를 강제하고, 신호 부족 시 “상위 랭크 대체(tech+healthcare 내)”로 채움.
   - (2) 게이트: 평균 보유 종목 수가 [8,14] 유지 + exposure_p50이 최소 임계치 이상.
   - (3) 기대 관측치: 거래 0/노출 0 구간 축소 → 성능이 신호 변화에 반응할 가능성 상승.

3) **EX3: 리밸런스 주기 2점 테스트(동일 신호, 주기만 변경)**
   - (1) 실험 정의: (예) 1일 vs 5일 리밸런스만 바꿔 turnover/성능/비용 비교.
   - (2) 게이트: 비용 반영 후 oos_mean 개선 또는 turnover 유의미 감소.
   - (3) 기대 관측치: “성능 정체=과도한 리밸런스/비용”인지 빠르게 판정.

**(d) PASS 조건**
- 신호→주문→체결→보유로 이어지는 파이프가 끊기지 않고, 8~14종목 제약 하에서 노출이 안정화.

### 5) **과최적화/레짐 취약성 차단: 폴드/기간/레짐별 성능 분해와 게이트 도입**
**(a) 왜 필요한지**
- degenerate_folds가 이미 “검증체계 취약” 신호.
- Tech+Healthcare는 금리/리스크온오프/AI 테마 등 레짐 영향이 크고, 평균 OOS만 보면 개선이 “안 움직이는 것처럼” 보일 수 있음(레짐 상쇄).

**(b) 위험/부작용**
- 게이트가 빡세면 통과 모델 수가 감소(탐색 속도 저하).
- 레짐 분해가 과하면 판단 기준이 늘어나 오히려 혼란(그래서 2~3개 핵심 레짐만).

**(c) 최소 실험 2~3개**
1) **EX1: 레짐 태깅(ETF는 ‘관측 지표’로만) + 조건부 OOS 리포트**
   - (1) 실험 정의: OOS 일자를 2~3개 레짐으로 태그:
     - Risk-on/off: `QQQ` 모멘텀, `XLV` 상대강도(관측만)
     - 금리 민감: `TLT` 추세(관측만)
     성능을 레짐별로 분해 출력.
   - (2) 게이트: 레짐별 샘플 수 최소치 충족 + 레짐별 oos_mean/mdd 표 출력 자동 생성.
   - (3) 기대 관측치: “평균이 안 움직이는” 이유가 특정 레짐 손실로 상쇄되는지 확인.

2) **EX2: 폴드/기간별 안정성 게이트(서바이버십/누수 체크 통과 후에만)**
   - (1) 실험 정의: `oos_min`, `fold_worst`, `regime_worst`를 3개 핵심 지표로 고정하고 자동 PASS/FAIL.
   - (2) 게이트: `oos_min >= floor`, `regime_worst >= floor2` 등.
   - (3) 기대 관측치: 평균만 높은 “운 좋은” 후보 제거 → 진짜 개선만 남음.

3) **EX3: 간단한 “복잡도 상한” 패치(과최적화 억제)**
   - (1) 실험 정의: 피처 수/모델 depth/정규화 강도 등 복잡도 관련 한 가지 축을 상한으로 고정(나머지 동일).
   - (2) 게이트: OOS 평균은 유지하면서 fold 분산 감소(안정성 증가).
   - (3) 기대 관측치: OOS가 안 움직이는 원인이 “이미 과적합 한계”인지 확인.

**(d) PASS 조건**
- 평균 OOS 외에 “레짐/폴드 최악”이 개선되거나 최소한 악화하지 않음(안정성 기반의 개선).

## 48시간 자동 루프 운용 형태(권장 실행 순서) — “3~5개 패치/실험”로 묶어 운용
아래 4개를 **실제 실행 단위(패치/실험)** 로 잡고, 각 패치 안에서 위의 세부 EX를 “동일 run 내 로그/리포트로 동시 산출”하게 구성해 케이스 폭발을 막아라.

1) **PATCH-A (무결성/평가 단일화)**: Proposal 1의 EX1~EX3을 한 번에.
2) **PATCH-B (비용+턴오버 계측/게이트)**: Proposal 2의 EX1~EX3을 한 번에.
3) **PATCH-C (아티팩트/리밸런스/MDD 복구)**: Proposal 3의 EX1~EX3을 한 번에.
4) **PATCH-D (노출 안정화 + 레짐 리포트)**: Proposal 4의 EX1~EX3 + Proposal 5의 EX1을 한 번에(레짐 태깅은 관측만).

각 PATCH는 공통 게이트로:
- `artifacts complete`(equity_curve, rebalance.jsonl, metrics.json)
- `worst_mdd != None`
- `degenerate_folds == []`
- `avg_positions in [8,14]`
를 통과 못 하면 다음 탐색(전략 개선)으로 넘어가지 말고 즉시 FAIL 처리.

## “성능이 안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 명령형 트리

### A) 트리거(신호) 문제
- **RAW 신호 분포를 일자별로 저장**: 평균/표준편차/상위 quantile.
- **신호가 0/상수인 구간을 표시**: 해당 구간이 OOS 정체 구간과 겹치면 “데이터/피처 생성” 이슈로 분류.
- **(관측)** QQQ/XLV/TLT 레짐과 신호 강도의 상관을 리포트: 레짐 편향 여부 확인.

### B) 적용(필터/제약) 문제
- **필터 단계별 드랍률 계측**: “신호→유니버스 필터→리스크 필터→주문 생성” 각 단계 통과 수.
- **8~14종목 제약 위반/미달 일수 계측**: 미달이면 “필터가 과도” 또는 “랭킹 타이브레이크/결측” 문제.

### C) 노출(포지션 형성) 문제
- **exposure 시계열과 보유 종목 수 시계열을 함께 출력**.
- **노출=0인데 신호는 존재**하면: 주문 생성/체결/리밸런스 주기 버그 가능성으로 즉시 분류.

### D) 비용(거래비용) 문제
- **cost_drag를 항상 함께 표시**(cost=0 대비).
- **turnover p95와 성능의 관계를 스캐터로 저장**: 고턴오버 전략이 평균만 높고 실제는 비용에 눌리는 패턴 확인.
- **슬리피지 가정 2점(낮음/높음) 스트레스**로 순위 변동이 큰지 확인(운영 리스크).

### E) 레짐(시장 상태) 문제
- **레짐별 성능(평균/최악/MDD) 표준 출력**.
- **“평균이 안 움직임=레짐 상쇄”**면: 레짐 중립화(노출 스케일링/리밸런스 완화/헷지 *관측 기반* 의사결정) 방향으로만 다음 패치 설계.

### 마지막으로(현재 ONE TRUTH에서 즉시 잡아야 하는 결함 3개)
- `degenerate_folds` 다수 발생 → **폴드 건강 리포트 + FAIL 게이트**로 먼저 봉합.
- `worst_mdd: None` → **equity curve 기반 MDD 강제 산출**로 운영 리스크 제거.
- rebalance pinpoint 입력 파일 부재/파싱 실패 → **rebalance.jsonl 스키마/경로 표준화**로 관측 불능 상태 종료.

이 3개가 해결되기 전엔 “전략 개선”을 더 해도 성능이 안 움직이는 원인이 단지 “측정/로그/폴드 붕괴”일 수 있으니, 자동 루프의 최우선 게이트로 고정해라.
