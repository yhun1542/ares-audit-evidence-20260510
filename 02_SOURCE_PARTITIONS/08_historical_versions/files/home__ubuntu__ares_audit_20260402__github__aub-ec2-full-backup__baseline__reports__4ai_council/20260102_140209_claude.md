## 1. 우선순위 TOP-5 패치 (실행 가능)

### PATCH-1: MDD·비용 파이프라인 복구 (우선순위: 🔴 CRITICAL)

**(a) 왜 필요한지**
- `worst_mdd: None` → 드로우다운 제약 없이 OOS 평가 = 과최적화 리스크
- rebalance 로그 파싱 실패 → 거래비용·슬리피지 미반영

**(b) 위험/부작용**
- MDD 계산 추가 시 기존 champion 탈락 가능 (실제 성능 하락 아님, 정확한 평가)
- 파이프라인 수정 중 regression 가능

**(c) 최소 실험**

| ID | 실험 정의 | 게이트 조건 |
|----|-----------|-------------|
| P1-A | `backtest_engine.py`에 rolling MDD 계산 추가 | MDD 컬럼 non-null |
| P1-B | rebalance 로그 JSON→CSV 자동 변환 스크립트 | 파싱 성공률 100% |
| P1-C | 비용 반영 OOS 재계산 (10bps RT 가정) | OOS mean 재산출 |

**(d) PASS 조건**
```
worst_mdd IS NOT NULL AND worst_mdd > -0.25
AND cost_adjusted_oos_mean > 1.5
```

### PATCH-2: OOS 버전 불일치 해소 (우선순위: 🔴 CRITICAL)

**(a) 왜 필요한지**
- HANDOFF OOS=1.88 vs Diagnoser OOS=2.63 → **27% 괴리**
- 원인 후보: fold 정의 차이 / 날짜 범위 / 데이터 버전

**(b) 위험/부작용**
- 잘못된 baseline으로 A/B 비교 시 false positive

**(c) 최소 실험**

| ID | 실험 정의 | 게이트 조건 |
|----|-----------|-------------|
| P2-A | champion_v5 동일 config로 재실행, hash 비교 | lane_hash 일치 |
| P2-B | fold boundary 로깅 추가 (start/end date 명시) | 5-fold 날짜 출력 |
| P2-C | train/test 데이터 row count 검증 | expected count ±1% |

**(d) PASS 조건**
```
abs(oos_mean_rerun - oos_mean_diagnoser) < 0.05
AND fold_dates deterministic
```

### PATCH-3: Exposure 편향·Survivorship 점검 (우선순위: 🟡 HIGH)

**(a) 왜 필요한지**
- exposure_max=84% → 특정 섹터/종목 과집중 가능
- Tech+Healthcare 14종목 중 상장폐지/M&A 종목 포함 여부 미확인

**(b) 위험/부작용**
- 종목 제거 시 백테스트 기간 축소
- universe 변경 → 기존 실험 비교 불가

**(c) 최소 실험**

| ID | 실험 정의 | 게이트 조건 |
|----|-----------|-------------|
| P3-A | 종목별 exposure 분포 히스토그램 생성 | top1 종목 < 25% |
| P3-B | 2020~2024 상장폐지 종목 스크리닝 | survivor count 기록 |
| P3-C | sector weight 시계열 drift 체크 | tech:healthcare 비율 변동 < 20% |

**(d) PASS 조건**
```
max_single_stock_exposure < 0.25
AND survivorship_bias_flag = FALSE
```

### PATCH-4: 신호 트리거 빈도 분석 (우선순위: 🟡 HIGH)

**(a) 왜 필요한지**
- "성능이 안 움직인다" = 신호가 발생 안 하거나, 발생해도 필터링됨
- FSA scale/hedge 조정 효과 검증 필요

**(b) 위험/부작용**
- 트리거 완화 시 noise trade 증가
- 과거 regime에서만 유효한 신호일 수 있음

**(c) 최소 실험**

| ID | 실험 정의 | 게이트 조건 |
|----|-----------|-------------|
| P4-A | 월별 signal firing rate 집계 | rate > 5%/month |
| P4-B | signal→position 변환율 추적 | conversion > 30% |
| P4-C | regime별 (bull/bear/sideways) 신호 분포 | 3 regime 모두 존재 |

**(d) PASS 조건**
```
avg_monthly_signal_rate BETWEEN 0.05 AND 0.40
AND regime_coverage = 3
```

### PATCH-5: Degenerate Fold 조기 탐지 강화 (우선순위: 🟢 MEDIUM)

**(a) 왜 필요한지**
- 현재 `degenerate_folds: []` 이지만 탐지 로직 자체 검증 필요
- 특정 fold에서 극단적 성능 → 전체 평균 왜곡

**(b) 위험/부작용**
- 너무 엄격한 기준 → 대부분 fold 탈락
- fold 제거 시 OOS 샘플 축소

**(c) 최소 실험**

| ID | 실험 정의 | 게이트 조건 |
|----|-----------|-------------|
| P5-A | fold별 OOS 분포 (mean, std, min, max) 리포트 | std/mean < 0.5 |
| P5-B | worst fold 제거 후 OOS 재계산 | delta < 15% |
| P5-C | fold간 종목 overlap 비율 체크 | overlap > 60% |

**(d) PASS 조건**
```
oos_fold_std / oos_fold_mean < 0.5
AND worst_fold_impact < 0.15
```

## 2. 성능 불변 원인 분해 트리 (48H 자동 진단용)

```
[성능 안 움직임]
│
├─(1) 트리거 문제
│   ├─ signal firing rate < 5%? → 임계값 완화 실험
│   └─ signal 전부 같은 방향? → diversity 지표 추가
│
├─(2) 적용 문제  
│   ├─ position size 0으로 스케일? → min_position 강제
│   └─ hedge가 signal 상쇄? → net_exposure 추적
│
├─(3) 노출 문제
│   ├─ 특정 종목만 거래? → concentration index
│   └─ 레짐 필터가 전부 막음? → regime_active_ratio
│
├─(4) 비용 문제
│   ├─ 거래 빈도 과다? → turnover 체크
│   └─ 슬리피지 미반영? → PATCH-1 우선
│
└─(5) 레짐 문제
    ├─ 백테스트 기간이 단일 레짐? → 기간 확장
    └─ 현재 레짐과 불일치? → live 데이터 비교
```
