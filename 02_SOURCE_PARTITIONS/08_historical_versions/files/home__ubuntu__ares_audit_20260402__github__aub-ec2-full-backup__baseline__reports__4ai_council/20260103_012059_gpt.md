## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — **명령형 체크리스트**
(누수/과최적화/서바이버십/비용 미반영/운영 리스크 순으로)

---

# 1) **리밸런스/평가 로깅 복구 + 재현성 해시 고정 (운영 리스크 최우선)**
### (a) 왜 필요한지
- 현재 상태에서 **rebalance 로그 로딩 실패**, `worst_mdd: None`, `lane_hash/run_hash: None` → “성능이 안 움직임”이 **실제 무변화인지, 기록/평가 파이프라인 결함인지 구분 불가**.
- 자동 루프(48h)에서 **원인 추적 불가 = 운영 장애**로 직결.

### (b) 위험/부작용
- 로깅/평가 기준이 바뀌면서 **과거 챔피언 점수와 불연속** 발생 가능(정상).
- 저장 로그가 커져 디스크/IO 비용 증가.

### (c) 최소 실험(=1개 Job 안에서 2~3 variants 스윕)
**[PATCH/EXPERIMENT #1: “EvalTrace v1”]**
- Variant A: 리밸런스 산출물 **JSONL 표준 스키마**로 강제 저장(각 시점: weights, fills, turnover, costs, exposure, beta, sector, PnL 구성요소)
- Variant B: 동일 + `lane_hash/run_hash`를 (데이터 스냅샷 해시 + 코드 커밋 + 설정 해시)로 생성/저장
- Variant C: 동일 + `worst_mdd`, `oos_min`을 **반드시 계산 실패 시 런 자체 FAIL** 처리

### (d) PASS 조건 (게이트 포함)
- **Gate(즉시 실패 조건)**: rebalance 로그/스키마 검증 실패(필수 필드 누락) 시 실험 런을 FAIL.
- **PASS**:  
  - 모든 런에서 `rebalance.jsonl` 로딩 100% 성공  
  - `worst_mdd`가 None이 아닌 값으로 저장  
  - 동일 입력(데이터+설정) 재실행 시 `lane_hash` 동일(재현성 확보)

### 48시간 자동 루프 형태
- (1) 실험 정의: EvalTrace v1 (A/B/C 스윕)
- (2) 게이트: 로그 스키마/필수 metric 계산 실패 시 중단
- (3) 기대 관측치: “성능 무변화”가 **(i) 실제 전략 무변화** vs **(ii) 평가/리밸런스 누락**으로 분리되어 관측됨

---

# 2) **Degenerate folds 제거 + Purged/Embargo CV로 누수 차단 (누수/과최적화)**
### (a) 왜 필요한지
- `degenerate_folds: [1,2,3,8]` → CV가 **학습/검증 분할로서 기능하지 않는 구간**이 존재(샘플 부족/라벨 누락/동일기간 중복/정렬 오류 가능).
- 이런 상태에서는 OOS mean이 좋아도 **누수/우연 적중** 가능성이 매우 큼.

### (b) 위험/부작용
- CV가 엄격해지면서 **점수가 하락**할 가능성(정상적인 페널티).
- 학습 데이터 감소로 신호가 약해질 수 있음.

### (c) 최소 실험(=1개 Job 안에서 2~3 variants 스윕)
**[PATCH/EXPERIMENT #2: “CV Purge v1”]**
- Variant A: 현재 fold 생성 로직에 **정합성 assert** 추가(각 fold 샘플 수, 날짜 연속성, label/feature NaN 비율 상한)
- Variant B: **Purged K-fold(lookback/holding period만큼 purge)** 적용
- Variant C: Variant B + **Embargo(검증 직후 일정 기간 학습 제외)** 추가

### (d) PASS 조건
- **Gate**: degenerate fold가 0개가 아니면 FAIL.
- **PASS**:  
  - degenerate_folds = []  
  - OOS mean이 다소 하락해도 **OOS min 악화 폭 제한**(예: 기존 대비 -20% 이내)  
  - fold별 성능 분산(표준편차)이 감소(과최적화 완화 신호)

### 48시간 자동 루프 형태
- (1) 실험 정의: CV Purge v1 (A/B/C)
- (2) 게이트: degenerate fold 1개라도 발견되면 즉시 실패
- (3) 기대 관측치: “좋게 나오던 점수”가 **누수 제거 후 유지되는지**가 즉시 드러남

---

# 3) **거래비용/슬리피지/체결 제약을 PnL에 강제 반영 (비용 미반영 리스크)**
### (a) 왜 필요한지
- 현재 리밸런스 로그 자체가 불확실하고(로딩 실패), 비용 모델이 약하면 **OOS mean이 실거래에서 재현 불가**.
- Tech+Healthcare 8~14종목이라도 리밸런스가 잦으면 **turnover 비용이 알파를 잠식**.

### (b) 위험/부작용
- 비용 반영 시 성능 급락 가능(정상: “원래 없던 알파”일 수 있음).
- 과도한 비용 모델은 전략을 지나치게 보수적으로 만들 수 있음.

### (c) 최소 실험(=1개 Job 안에서 2~3 variants 스윕)
**[PATCH/EXPERIMENT #3: “CostModel v1”]**
- Variant A: 고정 수수료 + 고정 슬리피지(bps) 적용(최소 모델)
- Variant B: Variant A + **일일 거래대금(ADV) 기반 비선형 슬리피지**(거래량/유동성 페널티)
- Variant C: Variant B + **리밸런스 빈도 제한(최소 변경폭 임계치, 예: |Δw|<x면 미체결)**

### (d) PASS 조건
- **Gate**: 비용 반영 후에도 리밸런스 로그에서 “총비용/turnover/체결수”가 0 또는 NaN이면 FAIL(계산 누락).
- **PASS**:  
  - 비용 차감 후 OOS mean이 **양(+) 유지**  
  - turnover가 Variant A 대비 Variant C에서 의미 있게 감소  
  - 종목당 거래횟수/일이 과도하지 않음(운영 가능성)

### 48시간 자동 루프 형태
- (1) 실험 정의: CostModel v1 (A/B/C)
- (2) 게이트: 비용/turnover/체결 로그 누락 시 실패
- (3) 기대 관측치: “성능 무변화”가 비용 때문에 상쇄되는지, 혹은 원래부터 알파가 없는지 분해 가능

# 4) **노출(Exposure) 바닥/천장 + 포지션 수(8~14) 강제 + 리스크 스케일링 (노출/레짐/운영)**
### (a) 왜 필요한지
- 현재 `exposure_min/max: 0.0 / 0.8388` → 어떤 기간에는 **현금화(0 노출)**가 발생.  
  - 이게 의도된 리스크오프인지, 신호/게이트 오류인지 불명확.
- 종목 수 제한(8~14)과 Tech+Healthcare 중심 규칙을 **백테스트/리밸런서 레벨에서 강제**해야 운영 중 일탈 방지.

### (b) 위험/부작용
- 노출 하한을 두면 레짐 악화 시 손실 확대 가능.
- 리스크 스케일링이 잦으면 turnover 증가 가능(비용과 충돌).

### (c) 최소 실험(=1개 Job 안에서 2~3 variants 스윕)
**[PATCH/EXPERIMENT #4: “ExposureGuard v1”]**
- Variant A: 포지션 수를 **항상 8~14로 클립**(랭킹 상위 N만, 나머지 0)
- Variant B: Variant A + 총 익스포저를 **[0.6, 1.0]**로 클립(현금 과다 방지)
- Variant C: Variant B + **변동성 타게팅(예: 20d realized vol로 scale)** 적용(레짐 대응)

※ ETF는 매매 금지 준수: 변동성/레짐 지표로 **QQQ, XLV 관측만** 허용(트레이딩 금지).

### (d) PASS 조건
- **Gate**: 포지션 수가 8~14 범위를 벗어나는 리밸런스가 1회라도 있으면 FAIL.
- **PASS**:  
  - exposure_min이 0에서 상승(의도된 리스크오프가 아니라면)  
  - OOS min(최악 구간)이 개선되거나 MDD가 감소  
  - 비용(실험 #3 결과)과 함께 봤을 때 “실거래 가능한 turnover”로 유지

### 48시간 자동 루프 형태
- (1) 실험 정의: ExposureGuard v1 (A/B/C)
- (2) 게이트: 포지션 수/노출 제약 위반 시 실패
- (3) 기대 관측치: 성능이 안 움직일 때 “노출이 실제로 들어갔는지(베타/익스포저)”가 수치로 고정 관측됨

# 5) **서바이버십/기업행동(스플릿/머지/상장폐지) 및 데이터 스냅샷 고정 (서바이버십/운영)**
### (a) 왜 필요한지
- Tech+Healthcare 소수 종목일수록, **기업행동/티커 변경/상장폐지** 한 번이 전체 PnL을 왜곡.
- “ONE TRUTH”가 없으면 실험 간 데이터가 미묘하게 달라져 **no-delta(변화 없음) 또는 가짜 개선**이 발생.

### (b) 위험/부작용
- 포인트-인-타임 데이터 정합을 맞추면 과거 성능이 하락할 수 있음(정상).
- 데이터 스냅샷 보관으로 저장 비용 증가.

### (c) 최소 실험(=1개 Job 안에서 2~3 variants 스윕)
**[PATCH/EXPERIMENT #5: “DataIntegrity v1”]**
- Variant A: 가격/수정주가/거래정지/기업행동 이벤트를 한 테이블로 합쳐 **결측/불연속 탐지 리포트** 생성
- Variant B: Variant A + 실험 시작 시점에 **데이터 스냅샷 해시 고정**(스냅샷/버전이 다르면 런 FAIL)
- Variant C: Variant B + 종목 리스트(8~14)가 “현재 시점 임의 선택”이 되지 않게 **고정 규칙(예: 사전 정의된 티커 풀 + 필터 로그 저장)**

### (d) PASS 조건
- **Gate**: 데이터 스냅샷 해시 불일치(재현 불가)면 FAIL.
- **PASS**:  
  - 기업행동 발생 구간에서 비정상 수익률(극단치) 비율 감소  
  - 동일 기간 재실행 시 결과가 동일(또는 허용 오차 내)

### 48시간 자동 루프 형태
- (1) 실험 정의: DataIntegrity v1 (A/B/C)
- (2) 게이트: 스냅샷 불일치/결측률 임계 초과 시 실패
- (3) 기대 관측치: 성능 변화가 “데이터 변경” 때문인지 아닌지 즉시 분리됨

## 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐) — 명령형 트리
아래는 **질문 없이**, 자동 루프에서 바로 로그/대시보드로 박아 넣을 항목들.

### A. Trigger(트리거) 계층: “재학습/재리밸런스가 실제로 발생했나?”
- 각 런에서 `model_fit_timestamp`, `training_window`, `feature_set_hash`, `data_snapshot_hash`를 저장하라.
- **연속 2회 런에서** 위 4개가 모두 동일하면 “트리거 미발생(학습/데이터 고정)”으로 라벨링하라.
- 리밸런스 예정일인데 `orders_count==0`이면 “리밸런서/게이트가 막음”으로 라벨링하라.

### B. Apply(적용) 계층: “신호는 변했는데 포트가 안 바뀌나?”
- `pred_vector_cosine_similarity(t vs t-1)`(예측 벡터 코사인 유사도) 저장하라.  
  - 유사도 ~1이면 모델이 사실상 변화 없음.
- `target_weights`와 `filled_weights`를 분리 저장하라.  
  - target은 변하는데 filled가 고정이면 **체결/제약/라운딩 문제**다.

### C. Exposure(노출) 계층: “알파가 아니라 현금/베타가 성과를 좌우하나?”
- 매 리밸런스마다 아래를 강제 저장하라:
  - gross/net exposure, cash weight
  - SPY(또는 QQQ) 베타(관측용), 섹터 익스포저(Tech/Healthcare)
  - 포지션 수(8~14 준수 여부)
- 성능 무변화 + exposure가 0 근처면 **전략 문제가 아니라 ‘노출이 안 들어간 것’**이다.

### D. Cost(비용) 계층: “원시 알파는 있는데 비용이 다 먹나?”
- PnL을 **gross / after spread / after fee / after impact**로 분해 저장하라.
- `turnover`, `dollars_traded`, `impact_bps`를 함께 보라.
- gross는 좋은데 net이 0이면 **리밸런스/회전율을 줄이는 방향**(임계치, 빈도 제한)이 우선이다.

### E. Regime(레짐) 계층: “시장 국면에서만 먹고 있나?”
- 관측 지표(매매 금지): QQQ 20d trend, XLV/QQQ 상대강도, VIX(가능하면), 금리(가능하면)
- 성능을 레짐별로 자동 버킷팅하라(예: QQQ above/below 200d MA, vol 상/하).
- 특정 레짐에서만 알파가 나오면 “항상 노출” 대신 **레짐 게이트/스케일링**이 필요하다(실험 #4로 연결).

## 지금 주어진 ONE TRUTH에서 즉시 찍히는 “빨간불”
- `degenerate_folds` 존재 → **누수/검증 실패 가능성 최상위**
- `worst_mdd: None` → **리스크 측정 공백(운영 불가)**
- rebalance pinpoint가 파일/포맷 문제로 실패 → **실험 비교 불가**
- exposure가 0~0.84로 넓음 → “의도된 현금화”인지 “신호/제약 오류”인지 미분리

---

## 실행 순서(48h) 권장
1. **#1 EvalTrace v1**로 “측정/재현/로그”를 고정(이게 없으면 나머지 실험 해석 불가)
2. **#2 CV Purge v1**로 누수/degenerate fold를 먼저 제거
3. **#3 CostModel v1**로 실거래 가능성(비용 반영)을 확정
4. **#4 ExposureGuard v1**로 노출/포지션 규칙(8~14, Tech+Healthcare 중심)을 백테스트 레벨에서 강제
5. **#5 DataIntegrity v1**로 데이터/기업행동/스냅샷 고정

위 5개는 모두 “48시간 자동 루프에서 실패를 빨리 드러내는 게이트”가 포함되어, 성능이 안 움직일 때도 **원인을 강제로 드러내는 구조**로 설계되어 있음.
