## TOP5 제안 (24~48h 우선순위)

### 1) [운영/아키텍처] 리밸런스/런 아티팩트 “깨짐” 즉시 복구 (로그 스키마 고정 + 무결성 게이트)
**왜 필요한지**
- 현재 상태에서 `lane_hash/run_hash/file=None`, `worst_mdd=None`는 **런 산출물 누락/파싱 실패** 가능성이 큼.
- `aub_rebalance_pinpoint`가 **base-log 경로 오류 + rebalance.csv/jsonl 파싱 실패**로 “리밸런스 데이터 없음” → **전략이 실제로 뭘 했는지 추적 불가**. 성능 정체 시 원인 분해가 막힘(운영 리스크 최상위).

**위험/부작용**
- 로그/스키마 변경으로 과거 리포트 호환성 깨질 수 있음(단, 변환 스크립트로 완화).
- 게이트가 빡세지면 실험이 자주 중단될 수 있음(초기 1~2회는 의도된 중단).

**최소 실험(아래 “공통 실험 팩”에서 재사용)**
- **E1 + E3** 적용

**PASS 조건**
- 모든 실험 런에서 **rebalance 로그(표준 스키마)**가 생성/파싱 가능
- `run_hash/lane_hash/file/worst_mdd`가 **항상 채워짐**
- `rebalance_pinpoint`가 base/cand 모두에서 **0건이 아닌 리밸런스 이벤트**를 재구성(“전략이 실제로 거래했다”를 증명)

---

### 2) [누수 최우선] 시점 정렬/라벨-피처 누수(lookahead) 자동 차단 (특히 헬스케어 펀더멘털/리포트)
**왜 필요한지**
- Tech/Healthcare는 **실적/가이던스/임상 이벤트**로 갭이 커서, 보고일/발표시각 정렬이 틀리면 **미세 누수로 OOS가 ‘안 움직이거나’ 가짜로 좋아짐**.
- “degenerate_folds”가 있는 상태에서 누수까지 섞이면 **CV가 무의미**해짐.

**위험/부작용**
- 누수 차단하면 단기적으로 OOS 평균이 내려갈 수 있음(“진짜 성능”으로 정상화).
- 리밸런스 타이밍이 늦춰져 신호 반응이 둔해질 수 있음.

**최소 실험**
- **E2 + E3** 적용

**PASS 조건**
- 누수 진단(시점 검증)에서 **미래 데이터 참조 0건**
- OOS 평균이 하락하더라도 **fold 분산 감소 + oos_min 개선(꼬리 리스크 완화)**가 확인되면 PASS(장기적으로 이득)

---

### 3) [과최적화/서바이버십] Degenerate folds 제거 + Purged/Embargo Walk-forward로 CV 재정의
**왜 필요한지**
- `degenerate_folds: [1,2,3,8]`는 사실상 **검증 구조가 깨져 있다는 신호**(표본 부족/클래스 한쪽 쏠림/리밸런스 0회 등).
- 이 상태에서 파라미터 튜닝은 **과최적화 확정 루트**.

**위험/부작용**
- 유효 fold 수가 줄어 실험 통과율이 낮아질 수 있음(초기 정상).
- 성능 수치가 “덜 좋아 보이게” 재평가될 수 있음(정상).

**최소 실험**
- **E3 단독 + (필요시) E1** 연동

**PASS 조건**
- degenerate fold **0**
- fold별 거래 횟수/노출/비용이 **0이 아닌 값**으로 분포
- OOS mean이 크게 안 늘어도, **OOS min(하방)과 fold 간 변동성**이 개선되면 PASS

---

### 4) [비용 미반영] 슬리피지/수수료/공매도 비용 + 유동성(ADV) 기반 포지션 캡 강제
**왜 필요한지**
- 현재 exposure max가 0.84로 보이는데, **거래 회전(turnover)**이 높으면 비용 미반영 시 “성능이 안 움직이는” 게 아니라 **비용이 다 먹는 구조**일 수 있음.
- 8~14개 종목 집중(Tech+Healthcare)에서는 단일 종목 리밸런스가 크고, 실거래 슬리피지가 커짐.

**위험/부작용**
- 비용 모델을 넣으면 성능이 떨어질 수 있음(현실화).
- 유동성 캡으로 알파가 제한될 수 있음(대신 재현성↑).

**최소 실험**
- **E4 + E1** 적용(비용/체결 가정이 로그에 남아야 함)

**PASS 조건**
- 비용 포함 OOS에서 **oos_min(최악) 악화 없이** 유지 또는 개선
- turnover/일 거래대금 대비 비중이 **상한 내**로 들어옴
- “비용 전/후 성능 차이”가 로그로 항상 재현 가능

---

### 5) [전략/레짐] ETF는 “관측지표”로만: 레짐 기반 익스포저 게이트(리스크-온/오프)
**왜 필요한지**
- ETF 거래는 금지이지만, **XLK/XLV/QQQ/SPY/VIX(또는 VIX proxy)**로 레짐을 관측해 **익스포저/리밸런스 빈도**만 제어하면, OOS min(꼬리) 완화에 효과적.
- “성능이 안 움직임”이 레짐 미스매치(리스크오프 구간에서 Tech 롱 노출 유지 등)일 수 있음.

**위험/부작용**
- 게이트가 과하면 기회 손실(상승장 참여 감소).
- 레짐 지표 자체가 지연되면 “늦게 줄이고 늦게 늘리는” 현상.

**최소 실험**
- **E5 + E4 + (누수 방지로) E2** 중 2~3개 조합(권장: E5+E4)

**PASS 조건**
- 리스크오프 구간에서 **gross/net 노출이 자동 축소**되고, drawdown 꼬리가 줄어듦
- OOS mean이 그대로여도 **worst MDD / oos_min 개선**이면 PASS

---

## 공통 “실행 가능한 Patch/실험” 팩 (전체 5개만 운용, 각 제안에서 재사용)
아래 5개만 48시간 루프에 넣고, TOP5 제안들은 이 조합으로 커버합니다(케이스 폭발 방지).

---

### E1) 리밸런스/런 아티팩트 표준화 패치 (운영 무결성)
**(1) 실험 정의 (PATCH)**
- 런 종료 시 아래를 **항상 단일 JSONL/Parquet로 저장**:
  - `run_hash, lane_hash, universe_hash, code_version, data_version`
  - `orders`(timestamp, symbol, side, qty, price_assumption)
  - `fills`(가정 체결가/슬리피지/수수료)
  - `positions`(종목별 weight, gross/net, exposure clip 여부)
  - `metrics`(worst_mdd 포함)
- `aub_rebalance_pinpoint` 입력 경로를 **“아티팩트 디렉토리 기반 자동 탐색”**으로 통일(더 이상 `--base-log` 같은 깨지는 하드코딩 금지).

**(2) 게이트**
- 아티팩트 생성/파싱 실패 시 **즉시 실험 FAIL(점수 계산 금지)**  
- 필수 필드 누락(`worst_mdd=None`, run_hash None 등) 시 FAIL

**(3) 기대 관측치**
- “리밸런스 이벤트 수”, “실제 체결 가정”, “노출 clip 발생 횟수”가 매 런마다 출력
- pinpoint 리포트가 “No rebalance data”를 더 이상 내지 않음

---

### E2) 누수 차단 패치: 시점 정렬 + 발표일/거래일 Embargo
**(1) 실험 정의 (PATCH)**
- 모든 피처에 대해 **사용 가능 시점(availability timestamp)**을 강제:
  - 가격 기반: t-1 close까지만 사용, 거래는 t open(또는 t close 명시)로 고정
  - 펀더멘털/이벤트: 보고일 + 최소 1 trading day embargo(보수적으로)
- 레이블도 동일 기준으로 정렬(“예측 시점 이후 수익률”만)

**(2) 게이트**
- “피처 timestamp > trade timestamp” 케이스 1건이라도 발견 시 FAIL
- 임상/실적 이벤트 윈도우에서 누수 플래그 감지 시 FAIL

**(3) 기대 관측치**
- OOS mean이 당장 개선 안 되더라도:
  - fold 간 성능 분산 감소
  - 특정 이벤트 구간에서 과도한 승률/샤프가 정상화

---

### E3) CV 구조 패치: Purged Walk-forward + Degenerate fold 자동 차단
**(1) 실험 정의 (PATCH)**
- Walk-forward fold 구성 시:
  - 학습/검증 사이 **purge window + embargo** 적용
  - fold별 최소 거래 횟수/표본 수 기준 미달이면 **해당 fold 제외가 아니라 “실험 자체 FAIL”**(과최적화 방지)
- degenerate fold 원인(거래 0회/노출 0/라벨 상수 등) 자동 리포트.

**(2) 게이트**
- degenerate fold 1개라도 발생 시 FAIL
- fold별 거래 이벤트(리밸런스) 수가 임계치 미만이면 FAIL

**(3) 기대 관측치**
- “OOS가 안 움직이는” 현상 중, CV가 깨져서 생기는 가짜 정체가 제거됨
- oos_min(최악)과 fold 안정성이 개선되는 방향으로 수렴

---

### E4) 비용/유동성 패치: 슬리피지 + 수수료 + 공매도 비용 + ADV 캡
**(1) 실험 정의 (PATCH)**
- 슬리피지(예): `k * volatility * (order_notional / ADV)` 형태의 보수적 모델 고정
- 수수료/스프레드 포함, 공매도는 **borrow cost(보수적 고정치)** 반영
- 포지션 상한: `position_notional <= c * ADV` 및 일 회전율 상한

**(2) 게이트**
- 비용 포함 성능 산출이 불가하거나, ADV/vol 데이터 누락 시 FAIL
- ADV 캡 위반 주문 생성 시 FAIL

**(3) 기대 관측치**
- 비용 전/후 성능 차이가 정량화되어 “성능 정체=비용 탓”을 즉시 판별 가능
- 턴오버 하락, oos_min/드로우다운 꼬리 완화 기대

---

### E5) 레짐 기반 익스포저 게이트 (ETF는 관측만)
**(1) 실험 정의 (PATCH)**
- 관측 지표(거래 금지, 관측만): `SPY, QQQ, XLK, XLV, VIX(또는 proxy)`
- 규칙 예:
  - 리스크오프 조건: (SPY < 200D MA) AND (VIX 상승) → gross cap 0.3, net cap 0.1
  - 리스크온 조건: → gross cap 0.8 (현 수준 유지)
- 종목은 **미국주식 Tech+Healthcare 8~14개**로만 매매(ETF 주문 생성 금지 게이트 추가)

**(2) 게이트**
- ETF 주문 생성 1건이라도 있으면 FAIL(관측만)
- 리스크오프 조건인데 노출이 cap을 넘으면 FAIL

**(3) 기대 관측치**
- 큰 하락장에서 노출이 자동 축소되어 worst MDD/oos_min 개선
- 상승장에서 참여율이 줄어도 꼬리 개선이 확인되면 유효

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래를 **명령형 체크리스트**로 매 런마다 자동 리포트에 넣으세요(E1에 포함 권장).

### A) Trigger(신호 생성) 문제
- [ ] 상위 피처 값 분포가 최근 N일 동안 거의 고정인지 확인(분산/엔트로피)
- [ ] 예측 스코어 상위/하위 종목이 매일 동일하게 반복되는지(랭크 변동률)
- [ ] 이벤트(실적/임상) 구간에서 신호가 “미리” 움직이는 패턴이 있는지(누수 의심 → E2)

### B) Apply(적용/주문/리밸런스) 문제
- [ ] 리밸런스 이벤트 수가 0이거나 비정상적으로 낮은지(E1로 즉시 가시화)
- [ ] 주문이 생성돼도 ADV 캡/노출 캡에서 전부 컷되어 “실제 포지션 변화 0”인지
- [ ] 기준일/캘린더/휴장 처리로 리밸런스가 건너뛰는지(거래일 정렬)

### C) Exposure(노출) 문제
- [ ] gross/net/exposure clip 횟수(상한에 계속 걸리면 성능 변화가 둔화)
- [ ] 8~14개 종목 내에서 특정 1~2개로 쏠림(효과적 분산 실패)
- [ ] 섹터(Tech vs Healthcare) 비중이 레짐과 반대로 고정되어 있는지

### D) Cost(비용) 문제
- [ ] 비용 전/후 샤프/수익률 차이가 대부분을 설명하는지(E4)
- [ ] turnover가 높아 비용이 선형으로 누적되는 구조인지
- [ ] 공매도 borrow cost/스프레드가 손익의 큰 비중인지

### E) Regime(레짐) 문제
- [ ] “리스크오프” 구간에서 Tech 롱 노출이 유지되는지(→ E5)
- [ ] 헬스케어 이벤트 구간에서 변동성 급등 시 노출이 줄지 않는지
- [ ] 레짐 게이트가 너무 늦게 반응하는지(관측 지표 지연/MA 길이 문제)

---

## 24~48시간 실행 순서 (명령형)
1. [ ] **E1 적용 후 1회 런**: 리밸런스/체결/노출/비용(placeholder라도) 로그가 완전한지 확인(불완전하면 즉시 중단)
2. [ ] **E3 적용 런**: degenerate fold 0 만들기(여기서 FAIL이면 성능 논의 중지)
3. [ ] **E2 적용 런**: 누수 0 보장(여기서 FAIL이면 성능 개선 실험 금지)
4. [ ] **E4 적용 런**: 비용 포함 성능으로 재평가(“정체=비용”인지 판별)
5. [ ] **E5 적용 런**: 레짐에서 꼬리(oos_min/worst MDD) 개선 여부만 우선 확인

이 순서대로면, 지금 상태에서 가장 가능성이 큰 “성능 무반응” 원인(로그/리밸런스 부재, CV 붕괴, 누수, 비용, 레짐)을 48시간 내에 높은 확률로 분리해낼 수 있습니다.
