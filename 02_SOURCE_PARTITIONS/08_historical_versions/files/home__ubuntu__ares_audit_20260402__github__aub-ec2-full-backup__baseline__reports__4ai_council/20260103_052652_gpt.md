아래는 **24~48시간 내 자동 루프(48h)에서 바로 돌릴 수 있는 “명령형 체크리스트”**로만 정리. 우선순위는 **누수/과최적화/서바이버십/비용 미반영/운영 리스크** 순으로 배치. (미국주식 only, Tech+Healthcare 8~14종목 유지, ETF는 관측지표로만)

## 0) 공통 전제: “실험 템플릿 5개”만 만들고, 모든 제안은 이 5개를 재사용
케이스 폭발 방지용으로 **유니크 실험은 E1~E5 딱 5개**만 운용.

### E1. 아티팩트/로그 무결성 스모크 실험
1) **실험 정의**: 가장 짧은 기간(예: 6~12개월) 미니 백테스트 1회 실행 → champion JSON, run_hash/lane_hash, 리밸런스 로그 파일 생성까지 강제
2) **게이트(FAIL 즉시 중단)**  
   - champion 파일 경로가 공백/None 아님  
   - `run_hash`, `lane_hash`가 None 아님  
   - JSON 파싱 OK + 스키마 키 존재(메트릭/폴드/거래내역 메타)  
3) **기대 관측치**: `aub_rebalance_pinpoint`와 `no_delta_diagnoser`가 **파일 에러 없이** 끝남

### E2. 리밸런스 로그 재구성 + 비용 반영 파이프 실험
1) **실험 정의**: 백테스터가 매 리밸런스마다 `rebalance.jsonl`(행 단위) + `rebalance.csv`(요약) 동시 생성, 각 체결에 **추정비용/슬리피지** 기록
2) **게이트**  
   - 파일이 “항상” 생성(빈 파일 금지)  
   - 각 행에 `ts,ticker,prev_w,target_w,trade_w,px,notional,fee_bps,slip_bps,cost_$` 존재  
   - 비용 적용 전/후 PnL이 일관(비용≥0, 비용 반영시 PnL 감소)
3) **기대 관측치**: “비용으로 깎인 정도”, “턴오버”, “리밸 빈도”가 수치로 보임

### E3. 결정성(재현성) 회귀 실험
1) **실험 정의**: 동일 config로 2회 연속 실행 → 결과/로그/해시 비교
2) **게이트**  
   - 주요 메트릭(oos_mean, oos_min 등) 차이 < 1e-6  
   - 리밸런스 타임스탬프/종목/가중치가 동일  
3) **기대 관측치**: “안 움직이는 이유가 랜덤/비결정성 때문” 가능성 제거

### E4. Purged/Embargo CV + 비용 스트레스 + 레짐(ETF 관측) 동시 실험
1) **실험 정의**:  
   - Purged K-fold(라벨 구간 purge) + Embargo(예: 5거래일) 적용  
   - 비용 시나리오 0/10/25bps(수수료+슬립) 동시 산출  
   - ETF(예: QQQ, XLK, XLV, IBB)로 **레짐 태깅**만 수행(매매 X) → 성과를 레짐별로 분해 출력
2) **게이트**  
   - degenerate fold = 0  
   - 비용 25bps에서도 oos_mean이 “방향성 유지”(완전 붕괴 금지)  
   - 보유 종목수 8~14 유지, 섹터(Tech/HC) 범위 밖 가중치=0
3) **기대 관측치**: 누수/과최적화로 부풀린 성과라면 **purge+비용에서 급락**, 진짜면 **완만한 저하**

### E5. 누수/서바이버십/포인트인타임(PIT) 유니버스 단위테스트 실험
1) **실험 정의**: 데이터 로더/피처 생성/유니버스 선택에 대해 “미래 참조 금지”와 “PIT 멤버십”을 강제하는 테스트 실행
2) **게이트**  
   - (누수) t 시점 피처가 t+1 이후 데이터를 조회하면 테스트 FAIL  
   - (서바이버십) delist/merge 심볼이 특정 과거 구간에서 누락되면 FAIL  
   - (PIT) 유니버스가 “현재 구성”으로 과거를 덮어쓰면 FAIL
3) **기대 관측치**: “oos_mean이 안 움직이는/이상하게 높은” 원인이 바이어스인지 즉시 판별

# 1) 다음 24~48시간 우선순위 TOP5 제안 (코드/아키텍처/전략)

## TOP1) (운영 리스크) **아티팩트/로그 파이프라인 즉시 복구**
현재 ONE TRUTH에서 `file:` 공백, `lane_hash/run_hash None`, 리밸런스 pinpoint가 파일 에러로 무력화됨 → **자동 루프가 ‘진단 불능’ 상태**.

- (a) 왜 필요한지  
  - “성능 개선” 이전에 **실험 결과를 신뢰/비교/재현**할 수 있어야 함  
  - rebalance 로그가 없으면 **비용/턴오버/노출 변화**가 블랙박스
- (b) 위험/부작용  
  - 로깅/스키마 변경으로 기존 리포트 파서가 깨질 수 있음  
  - 디스크 사용량 증가(단, jsonl 압축/로테이션으로 완화)
- (c) 최소 실험(아래 템플릿 재사용)  
  - **E1** 실행(무결성 스모크)  
  - **E2** 실행(리밸런스 로그+비용 기록)  
  - **E3** 실행(결정성 회귀)
- (d) PASS 조건  
  - `aub_rebalance_pinpoint.py`가 **입력 파일 에러 없이** 리포트 생성  
  - champion JSON에 `file/run_hash/lane_hash`가 채워지고, 2회 실행 결과 동일(E3)

## TOP2) (누수/과최적화) **Degenerate folds 제거 + Purged/Embargo CV로 재검증**
현재 `degenerate_folds: [1,2,3,8]`은 거의 “검증 실패” 신호. 이 상태 OOS mean은 신뢰 불가 가능성이 큼.

- (a) 왜 필요한지  
  - degenerate fold는 보통 (i) 표본 수 부족 (ii) 라벨 누수 (iii) split 오류 (iv) 특정 기간 거래 없음 등으로 발생  
  - “성능이 안 움직임/이상하게 좋음”의 최빈 원인이 CV 누수/분할 오류
- (b) 위험/부작용  
  - purge/embargo 적용 시 성능이 하락(정상)  
  - 학습 가능 데이터 감소로 분산 증가
- (c) 최소 실험  
  - **E4** 실행(Purged/Embargo + 비용 스트레스 + 레짐 분해)  
  - **E5** 실행(누수 단위테스트로 원인 확정)  
  - (재현성까지 고정) **E3** 재확인
- (d) PASS 조건  
  - degenerate fold = 0  
  - 비용 25bps에서도 성과가 “완전 붕괴”하지 않음(방향성 유지)  
  - 레짐별 성과가 특정 1개 구간에만 몰리지 않음(서바이버십/누수 의심 완화)

## TOP3) (서바이버십/유니버스 바이어스) **PIT 유니버스 + 상장폐지/합병 처리 강제**
Tech+Healthcare 8~14 종목 전략은 유니버스가 좁아 **서바이버십/심볼 히스토리 오류**에 특히 취약.

- (a) 왜 필요한지  
  - “현재 살아남은 우량주”만 과거에 넣으면 OOS가 비정상적으로 좋아지거나, 반대로 특정 구간에서 거래가 0이 되어 성능이 안 움직일 수 있음  
  - 유니버스가 PIT가 아니면, 신호가 바뀌어도 실제 매매 종목이 고정/왜곡될 수 있음
- (b) 위험/부작용  
  - PIT 적용 후 성능 하락(정상)  
  - 데이터 소스/정합성 요구 증가(운영 복잡도 상승)
- (c) 최소 실험  
  - **E5** 실행(서바이버십/PIT 강제 테스트)  
  - **E4** 실행(PIT 적용 전/후 레짐별 성과 분해로 “어느 구간이 바뀌는지” 확인)
- (d) PASS 조건  
  - 과거 특정 구간에 delist/merge가 있었던 심볼이 테스트에서 누락되지 않음  
  - 유니버스 멤버십이 날짜에 따라 변하고(정상), 그 변경이 로그로 남음  
  - “거래 0 구간”이 비정상적으로 길지 않음(운영 가능성)

## TOP4) (비용 미반영) **턴오버/비용/슬리피지 모델을 1급 시민으로 승격**
현재 리밸런스 로그 자체가 깨져 있어 비용 반영이 사실상 불가. 비용이 빠지면 **개선 패치가 ‘허상 알파’**가 되기 쉬움.

- (a) 왜 필요한지  
  - 8~14 종목이라도 리밸 빈도가 높으면 비용이 성과를 지배  
  - “성능이 안 움직임”은 실제로는 “비용이 다 먹는” 현상일 수 있음(지금은 관측 불가)
- (b) 위험/부작용  
  - 비용 반영 즉시 성능 급락 가능(정상)  
  - 슬리피지 파라미터 튜닝이 과최적화 포인트가 될 수 있음 → **시나리오 스트레스**로만 관리
- (c) 최소 실험  
  - **E2** 실행(리밸/비용 로그 생성)  
  - **E4** 실행(0/10/25bps 비용 스트레스에서 안정성 확인)
- (d) PASS 조건  
  - 비용 25bps에서도 전략이 “살아있음”(oos_mean 방향 유지 + oos_min 극단적 붕괴 방지)  
  - 턴오버 상한이 설정되고(예: 일/주 단위), 초과 시 페널티/게이트가 작동

## TOP5) (노출/레짐) **노출 게이트와 레짐 관측(ETF) 기반 스케일링으로 “안 움직임” 제거**
현재 exposure max가 0.84까지 가지만, min이 0 → **필터/게이트가 자주 발동하면 ‘아예 안 타는’ 구간**이 생길 수 있음. 또한 레짐 불일치면 신호가 무력화.

- (a) 왜 필요한지  
  - “신호는 있는데 포지션이 안 생김” vs “포지션은 있는데 PnL이 안 남음”을 분리해야 함  
  - ETF는 매매하지 않고도 Tech/HC 레짐(리스크온/오프)을 관측하는 가장 간단한 센서
- (b) 위험/부작용  
  - 레짐 스케일링이 과도하면 상방을 놓침(언더익스포저)  
  - 노출 게이트가 타이트하면 거래가 줄어들어 학습/검증이 불안정
- (c) 최소 실험  
  - **E4** 실행(ETF 레짐 태깅 + 노출 스케일링 on/off 비교를 “동일 실험 내 출력”으로 포함)  
  - **E2** 실행(노출 변화가 실제 리밸 로그로 남는지 확인)
- (d) PASS 조건  
  - 보유 종목수 8~14를 유지하면서, “현금 100% 구간”이 비정상적으로 길지 않음  
  - 레짐별 성과가 한쪽 레짐에서만 0에 수렴하지 않음(스케일링이 ‘무력화’시키지 않음)

# 2) 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래 순서대로 **로그로 수치화**해서 원인을 한 번에 잘라냄. (질문 금지 조건이므로, 바로 구현/추가할 관측치만 명령형으로 제시)

## A) Trigger(신호 생성) 레벨
- 매일(또는 리밸 시점마다) 아래를 로그로 남겨라  
  - `signal_std`, `signal_rank_entropy`, `topk_names`, `bottomk_names`  
  - 신호가 상수/NaN/클리핑으로 죽으면 성능은 절대 안 움직임
- 트리거 판정
  - `signal_std ~ 0` 이면: 피처 업데이트/정렬/정규화/라벨 시프트 오류 가능성 → **E5**로 누수/시프트 테스트 강제

## B) Application(필터/게이트 적용) 레벨
- 게이트 카운터를 1급 메트릭으로 추가해라  
  - 예: `blocked_by_liquidity`, `blocked_by_sector_constraint`, `blocked_by_risk_cap`, `blocked_by_missing_px`
- 트리거 판정  
  - 특정 사유로 block 비율이 높으면 “전략이 아니라 운영규칙이 포지션을 죽임” → 노출 0 구간 증가

## C) Exposure(노출/포지션) 레벨
- 아래를 타임시리즈로 저장해라  
  - `gross_exposure`, `net_exposure`, `active_names_count(≠0 weight)`, `max_name_weight`  
- 트리거 판정  
  - `active_names_count < 8`가 잦으면: “8~14 유지 규칙” 자체가 깨지거나, 종목 선택/정렬 단계에서 누락 발생  
  - `gross_exposure`가 자주 0이면: 필터/데이터 결측/리밸 스케줄 오류

## D) Cost(비용) 레벨
- **E2**로 아래를 반드시 관측해라  
  - `turnover`, `trades_count`, `avg_trade_w`, `total_cost_$`, `cost_bps_of_notional`
- 트리거 판정  
  - “비용 전에는 움직이는데 비용 후에 0 근처로 눌림”이면: 개선 방향은 신호가 아니라 **거래 빈도/턴오버 제어**

## E) Regime(레짐) 레벨 (ETF는 관측만)
- QQQ(리스크온), XLK(테크), XLV(헬스케어), IBB(바이오)로 레짐 라벨링만 추가해라  
  - 예: (i) ETF 20d 모멘텀 부호 (ii) 20d 변동성 구간 (iii) drawdown 상태
- 트리거 판정  
  - 성과가 특정 레짐에서만 발생하면: “전략은 레짐 의존” → 레짐 스케일링/노출 게이트가 해법  
  - 모든 레짐에서 0이면: 트리거/적용/비용 쪽 문제 가능성이 더 큼

# 3) 48시간 자동 루프에 넣을 “다음 실행 순서”(명령형)
1) **E1 실행 → FAIL 시 즉시 종료(로그/아티팩트부터 고쳐라)**  
2) **E2 실행 → 비용/리밸 로그 생성 확인(핀포인트 도구가 먹게 만들어라)**  
3) **E5 실행 → 누수/서바이버십/PIT에서 FAIL 뜨면 그날은 전략 실험 금지**  
4) **E4 실행 → degenerate fold=0, 비용 스트레스/레짐 분해 출력 확보**  
5) **E3 실행 → 결과 재현성 잠그고 다음 패치로 넘어가라**

이 순서를 통과하면 그 다음부터의 “전략 아이디어”가 의미를 갖고, 통과 못 하면 지금 OOS mean은 방어 불가(운영/바이어스 리스크).
