## TOP5 우선순위 (24~48h)

### 1) (운영 리스크 최우선) **리밸런스/메트릭 로깅·재현성 깨짐을 먼저 수리**
**현재 징후(ONE TRUTH 기반)**  
- `lane_hash: None`, `run_hash: None` → 재현성/추적 불가  
- `worst_mdd: None` → 리스크 메트릭 파이프라인 누락/실패 가능  
- `aub_rebalance_pinpoint`가 **--base-log 경로 오류** + **rebalance.csv JSON 파싱 오류**로 실패  
  - `Error loading --base-log: '--base-log'` (문자열 그대로 파일명 처리)
  - `rebalance.csv: Expecting value` (CSV를 JSON으로 읽는 경로 가능성)

**(a) 왜 필요한지**
- “성능이 안 움직임(no-delta)”을 분석하려면 **리밸런스 이벤트/체결/비용/노출 변화** 로그가 필수.
- 현재 상태는 **진단 도구가 입력을 못 읽는 운영 장애**라서, 전략 개선을 해도 변화 원인을 확인할 수 없음.

**(b) 위험/부작용**
- 로깅 추가로 저장공간/IO 증가, 실행 시간 소폭 증가.
- 포맷 변경 시 기존 리포트 도구와 호환성 이슈 → **버전 태그 필요**.

**(c) 최소 실험 2~3개 (아래 공통 실험 E1로 묶어서 처리)**
- (E1-1) 리밸런스 로그를 **CSV/JSONL 둘 다** 내보내고, 도구가 자동 감지하게 만들기  
- (E1-2) `lane_hash/run_hash`를 커맨드라인+설정+데이터스냅샷으로 결정론적 생성  
- (E1-3) `worst_mdd` 계산을 파이프라인 필수 단계로 승격(없으면 런 FAIL)

**(d) PASS 조건**
- `aub_rebalance_pinpoint.py`가 **base/cand 모두**에서 rebalance 로그를 읽고 리포트를 생성한다.
- 모든 런 아티팩트에 `lane_hash`, `run_hash`, `data_hash`, `code_hash`가 채워진다.
- `worst_mdd != None` (NaN/None이면 런 실패 처리)

### 2) (과최적화/누수 경계) **degenerate_folds 제거 + 시계열 CV 강제**
**현재 징후**
- `degenerate_folds: [1, 2, 3, 8]` → 폴드 구성/샘플 부족/라벨 누락/필터링으로 폴드가 깨짐  
- 이런 경우 OOS 평균이 “그럴듯”해도 실제로는 **평가가 무의미**해질 확률이 큼.

**(a) 왜 필요한지**
- degenerate fold는 보통 아래를 의미:
  - 특정 기간 데이터 공백
  - 필터(유니버스/유동성/가격) 적용 후 표본 0
  - 미래정보(lookahead) 또는 정렬 문제로 레이블 생성 실패
- 이 상태에서 파라미터 튜닝하면 **과최적화 확률 급상승**.

**(b) 위험/부작용**
- 폴드를 엄격히 하면 OOS 성능이 하락할 수 있음(“진짜 성능”으로 수렴).
- 실험 수가 줄어들어 탐색이 느려질 수 있음.

**(c) 최소 실험 2~3개 (E2로 묶어서 처리)**
- (E2-1) **TimeSeriesSplit 고정**(미래 데이터 섞임 금지) + 폴드당 최소 표본/최소 거래일 게이트
- (E2-2) 폴드별 “거래 가능 종목 수(Tech+Healthcare 내)”가 기준치 미만이면 해당 폴드 무효가 아니라 **런 자체 FAIL**
- (E2-3) 폴드별 성능/노출/턴오버를 반드시 로그로 남겨 “어디가 비는지” 즉시 확인

**(d) PASS 조건**
- `degenerate_folds`가 빈 배열이 된다.
- 폴드별 “유효 거래일/유효 종목수/리밸런스 횟수”가 모두 기준 이상이며, 리포트에 출력된다.
- OOS mean이 바뀌어도(하락 포함) **fold-to-fold 분산이 줄거나** 원인(데이터 공백/필터)이 명확히 로그에 남는다.

### 3) (비용 미반영 최우선) **거래비용/슬리피지/턴오버 상한을 강제해서 “가짜 알파” 제거**
**(a) 왜 필요한지**
- Tech+Healthcare 8~14종목은 리밸런스가 잦으면 턴오버가 쉽게 커짐.
- 비용을 약하게 잡으면 OOS 평균이 높아도 실거래에선 즉시 죽음(특히 잦은 리밸런스/포지션 뒤집기).

**(b) 위험/부작용**
- 비용 모델 강화는 성능 하락을 유발(하지만 그게 정상).
- 너무 강한 턴오버 캡은 알파 구현 자체를 막을 수 있음(“안 움직임”처럼 보일 수 있음).

**(c) 최소 실험 2~3개 (E3 하나로 묶어서 처리)**
- (E3-1) 슬리피지 = `k * (spread + volatility * sqrt(volume_ratio))` 형태의 단순 모델 추가(최소한 spread 반영)
- (E3-2) **턴오버 캡**(리밸런스 시 총 거래대금 비율 상한) + 캡 발동 횟수 로깅
- (E3-3) 비용 민감도 스윕(저/중/고 3단) → “알파가 비용에 얼마나 취약한지” 즉시 확인

**(d) PASS 조건**
- 비용(중간 설정)에서 **OOS mean이 챔피언 대비 과도하게 붕괴하지 않거나**, 붕괴 시 원인이 “턴오버/리밸런스 빈도/스프레드”로 로그에서 분해된다.
- 평균 턴오버가 상한 내로 들어오고, 캡 발동이 잦다면 그 자체가 리포트에서 경고로 뜬다.

### 4) (노출/리스크) **exposure(0~0.84) 상태를 “의도된 설계”로 고정 + MDD 산출**
**현재 징후**
- exposure가 최소 0, 최대 0.84 → 현금 비중이 커질 수 있고, 신호가 “안 움직이는” 것처럼 보이기 쉬움.
- `worst_mdd: None`과 같이 리스크 지표가 비어 있으면 “노출 줄여서 성능 좋아보이기”가 발생해도 못 잡음.

**(a) 왜 필요한지**
- 8~14종목 집중 포트폴리오는 노출 정책(항상 투자/조건부 투자)이 핵심 설계 요소.
- 노출이 들쭉날쭉하면 성능 변화(no-delta)의 원인이 “알파”가 아니라 “현금 대기”일 수 있음.

**(b) 위험/부작용**
- 최소 노출을 강제하면 하락장에서 MDD가 커질 수 있음.
- 반대로 최대 노출을 강제하면 변동성이 커질 수 있음 → 그래서 MDD/Vol 게이트가 필수.

**(c) 최소 실험 2~3개 (E4로 묶어서 처리)**
- (E4-1) **min gross exposure**(예: 0.6) 게이트: 신호가 약하면 “동일 가중(Tech+Healthcare 내)”로 채워 넣는 fallback(ETF 매매 없음, 현금/종목만)
- (E4-2) **max gross exposure**(예: 1.0) + 포지션 상한(한 종목 최대 비중) 강제
- (E4-3) MDD/Vol 타게팅(단순 스케일링) 추가하고, 적용 여부/스케일 팩터를 리밸런스 로그에 남김

**(d) PASS 조건**
- `exposure_min`이 목표치 이상으로 올라가고(설계 의도 반영), `worst_mdd`가 정상 계산된다.
- 성능이 유지/개선되지 않더라도 “노출 정책 변경이 성능/변동성에 미친 영향”이 로그에서 분해된다.

### 5) (서바이버십/레짐/누수) **유니버스(Tech+Healthcare)·지표·적용시점(라그) 일관성 게이트**
**(a) 왜 필요한지**
- Tech/Healthcare 유니버스는 구성 변동(상장/상폐/분류 변경)이 잦음 → 서바이버십/룩어헤드 위험.
- “지표는 ETF로 관측만” 규칙이면, **관측 지표의 발표/가격 시점 라그**가 엄격해야 함(당일 종가로 당일 체결 같은 누수 방지).

**(b) 위험/부작용**
- 라그를 넣으면 성능이 감소할 수 있음(정상).
- 유니버스 재구성 규칙을 과도하게 엄격히 하면 거래 기회가 줄어듦.

**(c) 최소 실험 2~3개 (E5로 묶어서 처리)**
- (E5-1) **모든 입력 피처에 “사용 가능 시점” 타임스탬프 강제**(EOD 계산이면 next open 체결 등)
- (E5-2) 유니버스 구성은 **해당 시점 기준**(당시 분류/상장상태)으로 스냅샷 사용 + 스냅샷 해시 저장
- (E5-3) 레짐 태깅(관측용 ETF/지표: QQQ/XLK/XLV/VIX 등은 “매매 금지”, 단 조건분기/리포트 태그만) 후 성과를 레짐별로 자동 분해

**(d) PASS 조건**
- 피처/유니버스에 대한 “as-of 시점” 로그가 남고, 동일 run_hash에서 완전 재현된다.
- 레짐별 성과 리포트가 생성되고, 성능이 특정 레짐 한 구간에만 쏠리는지(서바이버십/과최적화 징후) 즉시 보인다.

# 48시간 자동 루프용 “실행 가능한 patch/실험” 5개 (각각: 정의 → 게이트 → 기대 관측치)

  - `worst_mdd` non-null
  - `pinpoint report` 생성 성공

  - 운영 장애(경로/포맷)로 인한 블라인드 제거

## E2) Fold Degeneracy Elimination (Time-series CV hardening)
- **실험 정의**
  - 순방향 시계열 분할 고정, 폴드당 최소 표본/최소 거래일/최소 유니버스 종목수 조건
  - 폴드가 비면 “무시”가 아니라 런 FAIL + 원인 로그

  - `degenerate_folds == []`
  - 폴드별 유효성 지표 리포팅
- **기대 관측치**
  - OOS 평균이 변하더라도 **평가 신뢰도 상승**, no-delta의 원인이 “평가 붕괴”인지 즉시 분리

## E3) Cost & Turnover Stress Test (3-level)
- **실험 정의**
  - 비용모델(저/중/고) 3단계로 동일 전략을 재평가
  - 턴오버 캡 + 캡 발동 횟수/미체결(스케일 다운) 로깅
- **게이트**
  - 중간 비용에서 OOS mean이 “비정상 붕괴”하면 FAIL(그리고 붕괴 원인 로그 필수)
  - 평균 턴오버/리밸런스 빈도 리포트 출력
- **기대 관측치**
  - 알파가 비용에 취약한지(가짜 알파) vs 비용에 견디는지(실제 알파) 구분

## E4) Exposure Policy Lock + Risk Metrics
- **실험 정의**
  - min/max gross exposure, 종목당 비중 상한, (선택) 단순 vol targeting 스케일 적용
  - 현금 대기(0 노출)가 “의도”인지 “신호 붕괴”인지 분리되게 로깅
- **게이트**
  - `exposure_min` 목표 이상
  - `worst_mdd` 정상 산출, 변동성/드로우다운 리포트 생성
- **기대 관측치**
  - 성과 변화가 알파가 아니라 노출정책 때문인지 즉시 분해

## E5) As-of Timing / Survivorship / Regime Attribution
- **실험 정의**
  - 모든 피처/유니버스를 “as-of” 기준으로 스냅샷화(미래 데이터 접근 차단)
  - 관측 지표(ETF 등)는 매매 금지, 레짐 라벨링/리포트 분해만 수행
- **게이트**
  - 피처별 사용 가능 시점 로그 존재(누수 검증 가능)
  - 레짐별 성과 테이블 생성
- **기대 관측치**
  - no-delta가 “레짐 비적합/한 구간 과최적화/서바이버십”인지 판별 가능

# 성능이 안 움직일 때(no-delta) 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)

아래 순서대로 “원인 후보를 빠르게 제거”하도록 로그/리포트를 맞추세요. (질문 없이 바로 실행하는 체크리스트)

## A) Trigger(신호 발생) 단계
- [ ] 리밸런스 시그널 값 분포(평균/표준편차/상위-하위 스프레드)가 기간별로 0에 수렴하는지 확인  
- [ ] “거래 후보 종목 수(Tech+Healthcare 내)”가 리밸런스마다 충분한지(8~14 구성 가능 여부)
- [ ] 신호가 임계값 조건에 막혀서(예: filter) **항상 HOLD**가 되는지 확인

## B) Apply(적용/정렬/라그) 단계 — 누수 최우선
- [ ] 피처 생성 시점(EOD)과 체결 시점(next open)이 일관적인지(당일 종가로 당일 체결 금지)
- [ ] 데이터 정렬(타임존/캘린더) 오류로 미래 행이 섞이지 않는지
- [ ] corporate actions(분할/배당) 반영이 일관적인지 (조정가/비조정가 혼용 금지)

## C) Exposure(노출/제약) 단계
- [ ] 제약조건(최대비중/섹터/리스크)이 너무 강해 **항상 같은 포트폴리오**가 되는지
- [ ] `exposure_min=0`처럼 현금 비중이 커져서 변동이 죽는지
- [ ] 포트폴리오가 8~14종목을 실제로 유지하는지(종목 수 타임라인 로그)

## D) Cost(비용/체결) 단계 — “가짜 알파” 제거
- [ ] 턴오버가 높은데 비용이 낮게 잡혀 성능이 과대평가되는지
- [ ] 슬리피지/스프레드 반영 후 성능이 급락한다면, 개선 방향은 “신호”가 아니라 “거래 빈도/리밸런스 규칙”일 가능성 큼
