## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — 명령형 체크리스트

### 1) **리밸런스/비용/노출 “관측 불능” 상태 제거 (운영 리스크 최우선)**
- [ ] `aub_rebalance_pinpoint`가 깨지는 입력 경로(`--base-log`)를 **실제 파일로 자동 탐색**하도록 패치하고, 실패 시 **즉시 하드 에러**로 전환(지금은 “No rebalance data found”로 조용히 통과).
- [ ] 백테스트/실거래 공통으로 **리밸런스 로그(JSONL/CSV) 표준 스키마**를 강제 저장: `timestamp, universe, weights_before/after, turnover, est_cost, realized_slip(가능시), exposure`.
- [ ] `worst_mdd: None` → MDD 계산/저장 파이프라인을 고정(누락은 PASS 불가).
- [ ] “Champion OOS Mean” 값이 서로 다르게 보이는(1.88 vs 2.63) **버전/산출물 불일치**를 감지하면 런을 FAIL 처리(같은 champion을 가리키는지 hash로 검증).

**(a) 왜 필요한지**
- 지금 상태는 “성능이 안 움직이는 이유”를 비용/턴오버/리밸런스 단에서 분해할 수 없고, 잘못된 비교(다른 베이스/다른 산출물)로 **가짜 no-delta**가 발생할 확률이 큼.
- 운영에서 로그 누락은 자동루프가 “조용히 망가지는” 전형적인 장애 패턴.

**(b) 위험/부작용**
- 로그 강제/하드 에러로 인해 단기적으로 실패 런이 늘어남(하지만 그게 정상).
- 저장 용량 증가(해결: 압축/샘플링 정책).

**(c) 최소 실험 2~3개 (아래 공용 실험 ID 재사용)**
- E1(관측 파이프라인 게이트) + E2(비용모델 주입) + E3(리밸런스 pinpoint 경로 자동탐색)

**(d) PASS 조건**
- `rebalance_pinpoint.md`가 **양쪽(Base/Cand) 모두**에서 리밸런스 이벤트를 ≥1개 이상 파싱.
- 모든 런에서 `worst_mdd`가 숫자로 기록.
- champion 산출물의 `lane_hash/run_hash` 및 “OOS mean” 산출 로직이 **단일 소스**로 일치(불일치 시 런 FAIL이 발생해야 함).

---

### 2) **비용(슬리피지/임팩트/수수료) 미반영/과소반영 즉시 차단**
- [ ] 거래비용을 “보고용”이 아니라 **최적화/평가에 직접 반영**(net metric을 기본으로).
- [ ] turnover 상한/비용 상한을 **게이트로 강제**(과최적화·서바이버십보다 먼저 깨지는 지점이 비용인 경우 많음).
- [ ] “리밸런스 빈도/유동성”이 Tech+Healthcare 8~14종 포트에 맞는지 점검(소수 종목일수록 turnover가 곧 성능을 잡아먹음).

**(a) 왜 필요한지**
- no-delta의 흔한 원인이 “gross에서만 미세 개선”인데 비용에서 상쇄되는 케이스.
- 자동루프에서는 비용이 반영되지 않으면 과최적화가 가장 먼저 생김.

**(b) 위험/부작용**
- 단기적으로 OOS mean 하락 가능(하지만 net 기준 신뢰도가 올라감).
- 비용 모델 파라미터 오설정 시 지나친 보수화 가능(게이트를 단계적으로).

**(c) 최소 실험 2~3개**
- E2(비용 모델 A/B) + E4(turnover/exposure 게이트 실험)

**(d) PASS 조건**
- `net_oos_mean`이 기준 대비 **유의미하게 개선**(예: +0.05 이상) 또는 gross 개선이 줄더라도 **net drawdown/변동성**이 동반 개선.
- `median_turnover`가 상한 내(예: 일/리밸런스당 25~35% 이내; 현재 시스템 기준에 맞춰 숫자는 일관되게 고정).

---

### 3) **누수/시간정렬/피처 스케일링 과최적화(“아예 움직이지 않는 성능”의 1순위 원인)**
- [ ] 모든 피처에 대해 `asof_timestamp`를 강제하고, 라벨/리턴과의 조인에서 **미래 데이터 접근 시 런 FAIL**.
- [ ] 표준화/스케일링이 “전체 기간 fit”으로 돌아가지 않게 fold 단위 fit을 강제(특히 의료/테크는 구조 변화가 커서 스케일 누수가 잦음).
- [ ] “FSA only scale / hedge” 같은 실험 플래그가 실제로 적용되는지(적용=노출 변화) 관측 지표로 검증.

**(a) 왜 필요한지**
- 성능이 “개선이 전혀 안 된다”는 증상은 (1) 실험이 적용 안 됨, (2) 누수 방지로 인해 원래 과대평가가 제거됨, (3) 스케일이 포화되어 노출이 안 바뀜 중 하나인 경우가 많음.

**(b) 위험/부작용**
- 누수 차단 후 성능 급락 가능(그러나 그게 진짜 성능).
- 엄격한 time alignment로 데이터 결측 증가 → 커버리지 저하 가능.

**(c) 최소 실험 2~3개**
- E1(적용/정렬 게이트) + E5(레짐 스트레스/시프트 감지)  

**(d) PASS 조건**
- 누수 탐지 테스트(미래 조인/스케일링 누수)가 0건.
- 실험 플래그 변경 시 **노출/턴오버/리밸런스 빈도** 중 최소 1개가 유의하게 변함(“성능은 그대로인데 포지션도 그대로”면 적용 실패로 FAIL).

---

### 4) **유니버스/서바이버십/코퍼레이트 액션(분할·상장폐지) 점검 + Tech/HC 8~14종 강제**
- [ ] 유니버스를 “현재 살아있는 종목”에서 뽑지 말고 **각 날짜 시점의 생존 집합**으로 구성(서바이버십 차단).
- [ ] Corporate actions 반영(스플릿/머지)으로 가격/리턴 불연속 제거.
- [ ] 미국주식 only + Tech/Healthcare 중심 + 8~14종 보유를 **하드 제약**으로 강제(ETF 매매 제외, ETF는 관측 지표로만).

**(a) 왜 필요한지**
- 서바이버십/CA 미반영은 OOS의 개선이 안 보이거나 특정 구간에서만 이상해지는 원인이 됨.
- 소수 종목(8~14) 포트는 데이터 품질 이슈가 성능을 지배.

**(b) 위험/부작용**
- 유니버스가 좁아져 분산이 줄고 변동성 증가 가능.
- 데이터 소스에 따라 delisted 데이터 확보가 어려울 수 있음(없으면 그 자체가 리스크로 보고).

**(c) 최소 실험 2~3개**
- E1(유니버스/CA 검증 게이트) + E5(레짐별 성능 분해)

**(d) PASS 조건**
- 랜덤 날짜 샘플에서 “그 날짜에 거래 불가/상장폐지/비정상 가격” 종목이 포트에 포함되는 비율 0%.
- 포트 종목 수(8~14) 및 섹터 비중(Tech+HC 중심)이 전 기간 유지(이탈 시 FAIL).

---

### 5) **노출(Exposure) 포화/헤지 비율로 인한 “변화 무력화(no-delta)” 방지**
- [ ] 현재 노출 범위(약 0.47~0.84)가 실험 변화(스케일/헤지) 대비 충분히 움직이는지 점검.
- [ ] 스케일/헤지가 “클리핑(상·하한)”에 막혀 포트가 거의 고정되는지 확인.
- [ ] 8~14종 소수 종목에서 헤지가 과하면 알파가 상쇄되므로, 헤지의 목적(변동성 완화 vs 수익)을 분리해 평가.

**(a) 왜 필요한지**
- 실험을 바꿔도 포트가 거의 동일하면 성능은 당연히 안 움직임(“전략이 나쁜” 게 아니라 “변경이 적용되지 않거나 제약에 막힘”).
- 특히 hedge 파라미터가 강하면 개선이 비용/노이즈에 묻힘.

**(b) 위험/부작용**
- 노출 확대로 MDD 확대 가능.
- 제약 완화가 과최적화로 이어질 수 있음(그래서 게이트가 필요).

**(c) 최소 실험 2~3개**
- E4(노출/턴오버 제약 A/B) + E2(비용 포함 net 평가)

**(d) PASS 조건**
- 실험 간 포지션 유사도(예: weight cosine similarity)가 일정 임계치 이하로 떨어져 “실제로 다른 포트”가 생성됨.
- net 기준 성과/리스크 중 최소 1개 축(Sharpe, MDD, net mean)이 개선.

## 공용 “Patch/실험” 5개만 돌리는 48시간 자동 루프 (각 제안에서 재사용)

아래 E1~E5를 **동일 프레임**으로 48시간 동안 반복 실행: (1) 실험 정의 → (2) 게이트 → (3) 기대 관측치.

---

### E1) **누수/정렬/적용 검증 게이트(하드 FAIL)**
1) **실험 정의**
- 데이터 조인/피처 생성 전 구간에 `asof_timestamp`를 강제.
- 스케일러/정규화는 fold-train에서만 fit, fold-val/oos에는 transform만.
- 실험 플래그(예: scale/hedge)가 포트에 반영되었는지 “포지션 변화”까지 함께 로깅.

2) **게이트**
- 미래 데이터 접근 탐지(리턴/라벨보다 이후 timestamp 사용) 1건이라도 발견 시 FAIL.
- 스케일러가 전체기간 fit 흔적 발견 시 FAIL.
- 실험 플래그 변경에도 weights/turnover/exposure가 거의 동일하면(예: 유사도 > 0.98) FAIL(적용 실패로 간주).

3) **기대 관측치**
- no-delta였던 런에서 “적용 실패”가 드러나거나, 누수 차단 후 gross는 내려가도 신뢰도 상승(변동성/드로우다운 패턴이 현실화).

---

### E2) **비용 모델 net 평가 주입(A/B 2단계)**
1) **실험 정의**
- A: 고정 bps(예: 5~15bps) + 스프레드 추정
- B: turnover × (bps + 유동성(ADV) 기반 임팩트) 형태로 확대
- 목표지표를 gross가 아니라 **net_oos_mean / net_MDD** 중심으로 전환.

2) **게이트**
- turnover 상한 초과 시 FAIL(예: 리밸런스당 35% 또는 주간 100% 등, 시스템 기준으로 고정).
- 비용 반영 전후로 성과 역전이 심하면(“gross만 좋음”) 해당 전략은 후보에서 제외.

3) **기대 관측치**
- gross 개선이 net에서 사라지는 케이스를 조기에 제거.
- “성능이 안 움직임”이 사실은 비용에 의해 상쇄됨을 수치로 확인.

---

### E3) **리밸런스 pinpoint 입력 자동탐색 + 산출물 일관성 검사**
1) **실험 정의**
- `--base-log/--cand-log`가 없으면 `run_hash/lane_hash`로 artifacts 아래에서 최신 리밸런스 로그를 자동탐색.
- 찾지 못하면 “No data”가 아니라 FAIL.
- champion 산출물의 지표(예: OOS mean) 계산 함수/버전을 단일화하고, 불일치 시 FAIL.

2) **게이트**
- 리밸런스 이벤트 0개 파싱이면 FAIL.
- `Champion OOS Mean`이 서로 다른 리포트에서 불일치하면 FAIL(동일 hash 기준).

3) **기대 관측치**
- 리밸런스가 “실제로 일어났는지/언제 바뀌었는지”가 즉시 보임.
- no-delta가 비교 오류(서로 다른 베이스/산출물) 때문인지 즉시 드러남.

---

### E4) **노출/헤지/턴오버 제약 A/B (포화 방지)**
1) **실험 정의**
- A: 현 제약 유지(베이스라인)
- B: 노출 클리핑 완화 또는 헤지 강도 한 단계 낮춤(단, 8~14종/섹터 제약은 유지)
- 포지션 유사도/노출분포/턴오버를 1차 지표로 기록.

2) **게이트**
- 종목 수 8~14 유지 실패 시 FAIL.
- Tech+Healthcare 중심 비중(정의된 임계치) 이탈 시 FAIL.
- MDD가 기준 대비 과도하게 악화(예: +X%p 이상)하면 FAIL(운영 안전장치).

3) **기대 관측치**
- 실험 간 포트가 실제로 달라지기 시작(유사도 하락).
- 성능이 안 움직이던 원인이 “제약 포화”였는지 판별 가능.

---

### E5) **레짐/구간별 성능 분해 + no-delta 원인 태깅**
1) **실험 정의**
- OOS를 고정된 레짐으로 분할: 금리 급등/급락, 변동성(VIX) 상/하, Tech 주도/비Tech 주도(ETF는 관측만).
- 각 레짐에서: hit-rate, avg return, MDD, turnover, 비용을 리포트.

2) **게이트**
- 특정 레짐에서만 성능이 폭발/붕괴하면 “레짐 편향” 태그를 붙이고, 전체 평균만으로 champion 승격 금지.
- 레짐별 표본이 너무 적으면 해당 레짐 결론은 “보류”로 표시(과확신 금지).

3) **기대 관측치**
- “전체 OOS mean은 그대로”여도 레짐별로 개선/악화가 교차하는지 확인 → no-delta의 구조적 원인(레짐 상쇄)을 식별.

---

## 성능이 안 움직일 때 원인 분해 아이디어 (트리거/적용/노출/비용/레짐) — 명령형 진단 트리

### A) 트리거(신호 발생) 문제
- [ ] 신호 발생 빈도(일별/주별)와 신호 강도 분포를 로그로 남겨 “항상 0 근처”인지 확인.
- [ ] 상위/하위 신호 종목이 매번 동일하면 데이터/정렬/유니버스 고착을 의심하고 E1/E5로 태깅.

### B) 적용(실험이 실제로 포트에 반영되는가) 문제
- [ ] 실험 플래그 변경 전후 **weights cosine similarity**, turnover, exposure 변화가 거의 없으면 “적용 실패”로 분류(E1 FAIL).
- [ ] 리밸런스 이벤트 수가 0 또는 비정상적으로 낮으면 “리밸런스 파이프라인/로그” 문제로 분류(E3 FAIL).

### C) 노출(제약 포화/클리핑) 문제
- [ ] exposure 분포가 상한/하한에 몰려 있으면 포화로 분류(E4로 완화 실험).
- [ ] 8~14종 제약에서 헤지가 과하면 알파 상쇄 가능 → E4에서 헤지 강도만 단독으로 움직여 영향 분리.

### D) 비용/거래(턴오버) 문제
- [ ] gross 개선이 net에서 사라지면 “비용 상쇄”로 분류(E2에서 비용모델 단계 상향).
- [ ] turnover가 줄지 않는데 성능이 개선 안 되면 “신호 품질” 문제(트리거로 되돌림).

### E) 레짐(시장 국면) 문제
- [ ] 레짐별로 (+)와 (-)가 상쇄되어 전체 평균이 no-delta면 “레짐 상쇄”로 분류(E5).
- [ ] 특정 레짐에서만 개선이면, 운영 게이트를 “레짐 조건부 배치”로 전환(단, 자동루프에서는 태깅까지만 하고 즉시 조건부 매매로 확장하지 않음).
