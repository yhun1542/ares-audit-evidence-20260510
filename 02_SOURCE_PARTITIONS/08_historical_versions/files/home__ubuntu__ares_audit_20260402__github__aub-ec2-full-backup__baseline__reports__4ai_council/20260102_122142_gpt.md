## 0) 24~48h 우선순위 TOP5 (명령형 체크리스트)

1) **리밸런스/메트릭 로깅 파이프라인 복구(운영 리스크 최우선)**
- `aub_rebalance_pinpoint`가 입력을 못 읽고 있음(경로/포맷 불일치) → “왜 성능이 안 움직이는지”를 계측할 수 없는 상태를 먼저 제거.

2) **누수/시점정합(Point-in-time) + 서바이버십(상폐/편입) 감사**
- OOS가 “안 움직이는” 가장 흔한 원인이 (a) 은닉 누수 (b) 시점정합 붕괴 (c) 생존편향 제거로 인한 실력 하락인데, 현재는 이를 확증/배제할 계측이 부족.

3) **비용(슬리피지/스프레드/충격) 모델을 OOS 게이트에 강제 반영**
- 현재 OOS는 “비용 미반영” 가능성이 높고(리밸런스 로그도 없음), Tech+Healthcare 8~14종목은 리밸 빈도/턴오버에 성과 민감.

4) **노출/리스크(DD, concentration, 단일종목/섹터) 게이트 추가**
- `worst_mdd: None`는 리스크 측정이 누락됐거나 저장이 안 되는 신호. 노출 min/max는 0.47~0.84로 애매하게 높은 편 → 방어 게이트 없으면 OOS “평균”만 좋아지고 운영에서 깨짐.

5) **레짐/드리프트(Tech/Healthcare 내부 순환, 금리/리스크온오프) 관측 지표 고정**
- ETF는 매매 제외지만 **관측 지표**로 QQQ/XLV/SMH/IHI, TLT, HYG 등을 고정해 “성능 정체 원인”을 레짐으로 분해할 수 있게 만들기.

## 1) 48시간 자동 루프용 “실행 가능한 patch/실험” 5개만 정의 (3~5개 제한 준수)

아래 **E1~E5만** 돌려서 다음 24~48시간을 닫힌 루프로 운영.

---

### E1) Rebalance/Run 로그 표준화 패치 (운영/계측 복구)
- **(1) 실험 정의**
  - 모든 run에서 아래 아티팩트를 **항상 생성/저장**:
    - `rebalance.csv` (timestamp, ticker, target_w, prev_w, trade_w, price, shares, notional)
    - `rebalance.jsonl` (주문/체결/슬리피지 포함 가능)
    - `metrics.json` (oos_mean, oos_min, worst_mdd, turnover, cost, exposure stats)
  - `aub_rebalance_pinpoint.py` 입력을 “파일 경로 or 디렉토리” 둘 다 받도록 어댑터 추가.
- **(2) 게이트(FAIL FAST)**
  - run 종료 시 파일 3종 존재 + 파싱 100% 성공 + 컬럼 스키마 검증 통과.
  - `Champion OOS Mean`이 handoff와 diagnoser에서 **±1% 이내**로 일치.
- **(3) 기대 관측치**
  - 현재처럼 “No rebalance data found”가 0회가 되고, 실험 간 차이가 “거래/비용/턴오버”로 분해 가능해짐.

---

### E2) 비용 모델 주입 + OOS 게이트 강제 (비용 미반영 제거)
- **(1) 실험 정의**
  - 보수적 비용을 OOS에 직접 차감:
    - 고정 커미션 0 가정하더라도 **bid-ask + impact**를 단순 모델로:  
      `cost_bps = spread_bps(ticker) + k * |trade_notional| / ADV`
    - 최소한 1차로는 단순 상수(예: 5~15bp) + 거래비례(ADV 기반) 두 버전만.
  - 결과 저장: `gross_return`, `cost`, `net_return`, `turnover`.
- **(2) 게이트**
  - **Net OOS Mean**이 Gross 대비 과도 붕괴(예: -30% 이상)면 “전략이 비용 민감”으로 분류하고 다음 실험은 turnover 억제로 강제.
- **(3) 기대 관측치**
  - 성능 정체가 “실력 문제”인지 “턴오버/비용로스”인지 즉시 분리됨.

---

### E3) 누수/시점정합/서바이버십 감사 실험 (데이터 리스크 제거)
- **(1) 실험 정의**
  - 아래 3종 “감사 모드”를 같은 전략에 붙여 OOS를 비교:
    1) **시점정합 강제**: 모든 피처/라벨 `asof` 엄격 적용(미래 데이터 접근 차단)
    2) **리밸 시차(1 bar lag) 강제**: 신호 생성 t에 거래는 t+1로 강제
    3) **상폐/티커 변경 처리**: delist return/last price, corporate action 정합 테스트(최소한 생존편향 제거 토글)
- **(2) 게이트**
  - 감사 모드 간 성과가 “급격히” 달라지면(예: OOS Mean ±20% 이상) 누수/시점문제로 판정 → 해당 파이프라인을 고정 수정 전까지 전략 튜닝 중단.
- **(3) 기대 관측치**
  - “OOS가 안 움직임”이 사실상 **평가가 잘못된 것**인지, **진짜 알파 부재**인지 분기 가능.

---

### E4) 노출/리스크 게이트(DD/집중/섹터) 추가 실험 (운영 리스크)
- **(1) 실험 정의**
  - Tech+Healthcare 8~14종목 제약 하에서 다음을 하드 게이트로:
    - 단일종목 max weight (예: 20~25%)
    - 섹터 편중(Tech/Healthcare 내에서도 산업군 편중) 상한
    - `worst_mdd` 산출 강제 + 저장
    - exposure(현금 비중) 목표 범위 고정(예: 0.55~0.85 중 하나로 명확히)
- **(2) 게이트**
  - `worst_mdd` 미산출/누락 시 즉시 FAIL.
  - concentration 위반 시 리밸런스 단계에서 강제 클리핑(사후 페널티 금지).
- **(3) 기대 관측치**
  - 평균 성능이 소폭 줄어도, **oos_min 개선** 또는 tail 안정화가 관측되어야 정상(운영 가능성 상승).

---

### E5) 레짐 관측 지표 고정 + 성능 분해 리포트 자동 생성 (정체 원인 분해)
- **(1) 실험 정의**
  - 매매는 개별주 only 유지, ETF는 “관측 지표”로만 고정:
    - QQQ(Tech), XLV(Healthcare), SMH(semis), IHI(med devices), TLT(rates), HYG(credit)
  - OOS를 레짐별로 자동 분해:
    - 금리상승/하락(TLT 모멘텀)
    - 리스크온/오프(HYG 스프레드 proxy)
    - 섹터 상대강도(QQQ vs XLV)
- **(2) 게이트**
  - 레짐별 표본 수가 너무 적으면(예: 각 bin 30일 미만) 레짐 결론을 “보류”로 태깅(과최적화 방지).
- **(3) 기대 관측치**
  - “왜 안 움직이는지”가 **레짐 미스매치**인지, **신호 붕괴**인지, **비용 문제**인지 자동 요약됨.

## 2) TOP5 제안별 상세 (a) 필요성 (b) 위험/부작용 (c) 최소 실험 2~3개 (d) PASS 조건

### 제안 1) 로깅/리밸런스 핀포인트 복구
- (a) 왜: 현재 에러로 리밸런스 데이터를 못 읽어 **원인 분석 자체가 불가**. 또한 handoff OOS(1.88) vs diagnoser OOS(2.63) 불일치는 **메트릭 드리프트/다른 샘플** 가능성.
- (b) 위험: 스키마 강제 도입으로 기존 런과 호환 깨짐(단기 중단).
- (c) 실험: **E1 + (E5 일부: 리포트 자동 생성 연결)**  
- (d) PASS:
  - 모든 런에서 `rebalance.*` + `metrics.json` 생성/파싱 100% 성공
  - 동일 run의 OOS 핵심 지표가 도구 간 ±1% 이내 일치

### 제안 2) 누수/시점정합/서바이버십 감사
- (a) 왜: OOS가 안 움직일 때 “튜닝 한계”보다 **평가 체계 문제**일 확률이 높음. Tech/Healthcare는 상폐는 적어도 티커변경/인수합병/스플릿 등 이벤트가 빈번.
- (b) 위험: 성과가 크게 떨어져 “나빠진 것처럼” 보일 수 있으나, 그게 정상(기존이 과대평가였던 것).
- (c) 실험: **E3 + (E1로 로그 확보)**  
- (d) PASS:
  - 감사 모드에서 성과가 과도 붕괴하지 않거나(±20% 이내), 붕괴 시 원인이 특정(시점/상폐/딜레이)되어 수정 액션이 명확

### 제안 3) 비용 모델 반영(턴오버 민감도 포함)
- (a) 왜: 8~14종목은 한 번의 큰 리밸이 PnL을 좌우. 비용 미반영이면 “정체”가 아니라 “환상”일 수 있음.
- (b) 위험: 비용을 과도하게 잡으면 유효 전략을 조기 폐기 가능(보수성 튜닝 필요).
- (c) 실험: **E2 + (E1로 trade_notional/ADV 로그 확보)**  
- (d) PASS:
  - net OOS가 gross 대비 납득 가능한 수준으로 유지(예: -5~20% 범위 내) 또는
  - 붕괴 시 turnover 제한/리밸 빈도 조정이 다음 패치 후보로 도출(원인 분리 성공)

### 제안 4) 리스크/노출 게이트(worst_mdd 포함) 강제
- (a) 왜: `worst_mdd: None`은 운영에서 가장 위험. 평균이 좋아도 tail이 무너지면 실전 불가.
- (b) 위험: 게이트가 과하면 알파를 잘라먹어 평균 수익이 감소.
- (c) 실험: **E4 + (E2로 비용 포함 성과 확인)**  
- (d) PASS:
  - `worst_mdd` 산출/저장 100%
  - oos_min 또는 tail(예: 5% quantile) 개선이 관측(평균은 소폭 하락 허용)

### 제안 5) 레짐/드리프트 관측 지표 고정(ETF는 지표만)
- (a) 왜: 성능 정체는 종종 레짐 미스매치. ETF를 거래하지 않더라도 “설명 변수”로 고정해야 과최적화 없이 원인 분해가 됨.
- (b) 위험: 레짐 binning을 너무 잘게 하면 데이터 스누핑/서바이버십 비슷한 착시.
- (c) 실험: **E5 + (E1로 자동 리포트 루프 연결)**  
- (d) PASS:
  - 레짐별로 유의미한 성과 차이가 “표본 충분 조건” 하에서만 보고됨
  - 레짐에 따라 노출/리밸 정책을 바꿀 근거가 생기거나(혹은 “레짐 무관”으로 결론)

## 3) 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)

아래를 **항상 동일 순서로** 자동 리포트에 포함(케이스 폭발 방지, 결정 트리 형태로 단순화).

### A. Trigger(신호 발생) 문제
- 신호 발생 빈도/강도 분포가 최근 구간에서 붕괴했는지 확인  
  - 지표: daily signal entropy, top-k 점수 스프레드, “선정 종목 교체율”
- “안 움직임”이 **신호가 거의 0**이라서인지(=트리거 부족) 분리

### B. Apply(집행/딜레이) 문제
- 생성 신호가 실제 포지션에 반영되는지 확인  
  - 지표: target_w vs realized_w 상관, 리밸 실패율, lag(신호-체결) 분포
- 특히 E3의 “t+1 강제”에서 성과가 크게 바뀌면 집행 시점이 핵심

### C. Exposure(노출/제약) 문제
- 제약(8~14종목, max weight, cash band)이 알파를 눌러버리는지 확인  
  - 지표: constraint binding ratio(클리핑 발생 비율), 유효 자유도(실제 비중 다양성)
- “정체”가 사실 **제약에 의한 포화**인지 분리

### D. Cost(비용/턴오버) 문제
- gross는 움직이는데 net이 정체면 비용 탓  
  - 지표: turnover, cost/net slippage, ADV 대비 체결 비중, 리밸 시점(개장/종가)별 비용 차
- 비용 민감이면 “리밸 빈도/임계값(트레이드 밴드)” 쪽으로만 다음 패치 제한

### E. Regime(시장 국면) 문제
- 같은 신호가 레짐에 따라 부호가 바뀌는지 확인  
  - 지표: (QQQ-XLV) 상대강도 국면, TLT 모멘텀, HYG 스트레스 구간에서의 조건부 성과
- 레짐 차이가 없으면 “신호 자체의 알파 부재/포화”로 결론을 좁힘

## 최종 실행 순서(48h 루프용, 질문 없이 실행)

1) **E1 실행**: 로깅/리밸런스 파이프라인 복구 → 파싱/스키마/메트릭 일치 게이트 통과시까지 반복  
2) **E3 실행**: 누수/시점정합/서바이버십 감사 → 급변 여부로 “평가 신뢰성” 확정  
3) **E2 실행**: 비용 모델 주입 → net 기준으로 전략 생존성 판단  
4) **E4 실행**: worst_mdd 포함 리스크 게이트 강제 → oos_min/tail 안정화 확인  
5) **E5 실행**: 레짐 관측/분해 리포트 자동 생성 → 정체 원인을 (Trigger/Apply/Exposure/Cost/Regime)로 자동 라벨링

이 5개만으로도 다음 24~48시간 내에 “성능이 왜 안 움직이는지”를 계측 불능(운영 문제) → 평가 오류(누수/시점) → 비용/노출 → 레짐 순서로 깔끔하게 좁힐 수 있음.
