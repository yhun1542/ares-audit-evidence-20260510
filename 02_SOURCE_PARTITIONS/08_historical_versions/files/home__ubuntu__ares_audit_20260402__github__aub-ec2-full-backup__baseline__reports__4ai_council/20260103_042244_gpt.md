## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — **명령형 체크리스트**
(누수/과최적화/서바이버십/비용 미반영/운영 리스크 순으로 먼저 막고, 그 다음에 전략을 건드려라)

### 1) **시간정합(누수) 하드-가드**를 파이프라인 레벨에 박아라
- **왜 필요한가**
  - 현재 `degenerate_folds: [1,2,3,8]`는 “학습/검증 구간이 실질적으로 무너짐(누수/결측/리밸런스 미발생/포지션 0 고정)” 시그널일 때가 많다.
  - OOS mean이 나오는데도 fold가 깨지는 건 “데이터/피처 availability time”이 불일치하거나 특정 구간에서 feature가 전부 NaN→대체값으로 누수처럼 동작하는 패턴을 의심해야 한다.
- **위험/부작용**
  - 누수 제거 후 성능이 크게 내려갈 수 있다(하지만 이게 정상).
  - 피처가 부족해져 포지션이 줄거나 0이 되는 구간이 늘 수 있다(이 또한 원인 진단에 도움).
- **실험(공유 실험 세트에서 2~3개 지정)**: **E1, E4**
- **PASS 조건**
  - degenerate_folds가 **0 또는 1 이하**로 감소.
  - OOS mean이 일시 하락하더라도 **OOS min/극단 손실이 더 “현실적으로” 악화되지 않거나(비정상 급락 제거), 분산이 안정화**.
  - “미래 데이터 접근” 의심 로그(미래 timestamp join, forward-fill crossing boundary) **0건**.

---

### 2) **서바이버십/상장폐지/코퍼레이트액션(분할/배당) 처리**를 “Point-in-Time”로 고정하라
- **왜 필요한가**
  - US 주식(Tech+Healthcare) 8~14개 집중이면, 종목 교체/합병/상장폐지 이벤트가 누적되면 백테스트가 은근히 “살아남은 애들만”로 과대평가되기 쉽다.
  - 조정주가/비조정주가 혼용, 분할 이벤트 처리 누락은 리밸런스 계산 자체를 깨뜨려 degenerate fold를 만들 수 있다.
- **위험/부작용**
  - 데이터 소스가 point-in-time를 지원하지 않으면 구현 난도가 올라가고, universe가 일시적으로 줄어 성능이 흔들릴 수 있다.
- **실험**: **E2, E4**
- **PASS 조건**
  - 과거 구간에서 “현재 시점에만 존재하는 종목/티커”가 끼어드는 케이스 **0건**(리포트로 증빙).
  - 분할/배당 이후 포지션 수량/평가액 불연속(터무니없는 점프) **0건**.
  - 동일 기간 재실행 시 결과가 재현됨(동일 seed/run_hash에서 동일 성적).

---

### 3) **비용(슬리피지/스프레드/임팩트) + 턴오버 게이트**를 성능 평가의 1급 시민으로 만들라
- **왜 필요한가**
  - 현재 OOS mean 수치가 “비용 미반영/낙관적 체결”이면, 실전에서는 0 근처로 수렴하는 경우가 매우 흔하다.
  - 8~14개 종목 집중일수록 리밸런스가 잦으면 비용이 실질 수익을 삼킨다.
- **위험/부작용**
  - 비용을 넣는 순간 champion이 교체되거나 성능이 무너질 수 있다(하지만 이게 현실).
  - 과도한 비용 가정은 전략을 불필요하게 죽일 수 있다 → 그래서 **범위 실험**이 필요.
- **실험**: **E3, E5**
- **PASS 조건**
  - “비용 포함 OOS mean”이 비용 0 대비 감소하더라도 **전략 순위가 안정적**(상대우위 유지).
  - 연환산 턴오버가 상한(예: 6~12x/yr 같은 내부 기준) 초과 시 자동 탈락.
  - 비용 민감도(낮음/중간/높음) 3단에서 **방향성이 일관**.

---

### 4) **운영 리스크(로그/재현성/리밸런스 데이터 누락)부터 고쳐라**
- **왜 필요한가**
  - `aub_rebalance_pinpoint`가 rebalance 로그를 못 읽고 있다:  
    - `--base-log`가 파일이 아니고 문자열로 들어갔고  
    - candidate csv/jsonl 파싱도 깨졌다.  
  - 이 상태에서 “성능이 안 움직임”은 전략 문제가 아니라 **관측 불능(telemetry fail)**일 확률이 높다.
- **위험/부작용**
  - 로깅 고치면 성능이 “변한 것처럼” 보일 수 있다(사실은 기존이 잘못 측정된 것).
  - 실험 저장 포맷 변경이 downstream 툴을 깨뜨릴 수 있다 → 버전 필드로 호환 처리해라.
- **실험**: **E4, E1**
- **PASS 조건**
  - 모든 run에서 `lane_hash/run_hash`가 생성되고, 재실행 시 동일 설정이면 동일 hash.
  - rebalance 로그가 항상 생성되며(빈 리스트라도), `pinpoint` 툴이 에러 없이 비교 리포트를 만든다.
  - “리밸런스 0회/주문 0회/포지션 0 고정” 구간이 있으면 원인 코드 위치가 로그로 특정된다.

---

### 5) **레짐(Tech/Healthcare) 노출 스케일링을 ‘ETF는 지표로만’ 써서 단순화하라**
- **왜 필요한가**
  - ETF 매매는 제외지만, QQQ/XLV 같은 지표로 “위험 온/오프”만 해도 과최적화 없이 MDD를 줄이는 경우가 많다.
  - 현재 exposure max가 ~0.84인데, 언제/왜 줄었는지(게이트/클램프/결측) 불명확하다 → 레짐 스케일 규칙으로 노출 변화를 “설명 가능”하게 만들어라.
- **위험/부작용**
  - 레짐 필터가 너무 공격적이면 기회 손실(상승장 참여 부족).
  - 지표가 누수되면 즉시 치명적 → E1의 시간정합 가드 선행 필수.
- **실험**: **E5, E3**
- **PASS 조건**
  - 비용 포함 기준으로 worst drawdown이 개선되거나, 최소한 tail risk가 완화(OOS min 개선/극단 손실 빈도 감소).
  - 레짐별(리스크온/오프) 성과 분해에서 “노출 스케일링이 손실 구간을 줄였다”는 관측이 나온다.

---

## 48시간 자동 루프용 “실행 가능한” Patch/실험 5개 (E1~E5)
아래 5개만 돌려라(케이스 폭발 금지). 각 실험은 **(1)정의 → (2)게이트 → (3)기대 관측치**로 고정.

### E1) **Leakage/시간정합 감사 + 피처 as-of 조인 강제**
1) **실험 정의**
   - 모든 피처에 `feature_timestamp <= decision_timestamp` 강제(assert+로그).
   - forward-fill이 학습/검증 경계를 넘지 못하게 차단.
   - “미래 바/미래 펀더멘털” 접근 시 해당 피처를 NaN 처리하고 카운트 로그 출력.
2) **게이트**
   - 누수 의심 카운트 > 0이면 그 run은 자동 FAIL 처리 + 상위 20개 피처명 출력.
3) **기대 관측치**
   - degenerate_folds 감소.
   - OOS mean이 내려가도 **분산/꼬리(극단)**가 정상화되는 패턴이 나옴.

---

### E2) **서바이버십/코퍼레이트액션 Point-in-Time 유니버스 고정**
1) **실험 정의**
   - 일자별 tradable universe를 point-in-time로 생성(상장/거래정지/상폐 반영).
   - 분할/배당 조정 일관화(조정주가 기준으로 주문/평가 통일).
   - 티커 변경/합병 이벤트 매핑(가능한 범위에서).
2) **게이트**
   - “미래에만 존재하는 티커”가 과거에 등장하면 FAIL.
   - 분할일 전후 포지션 평가액 불연속(예: ±30% 이상 jump) 감지 시 FAIL(리포트 저장).
3) **기대 관측치**
   - 특정 구간에서 발생하던 이상수익/이상손실이 제거되며, 전략이 더 “밋밋하지만 진짜”로 변함.
   - 리밸런스 계산 실패/결측이 줄어듦.

---

### E3) **비용 모델 삽입 + 턴오버 패널티(3단 비용 민감도)**
1) **실험 정의**
   - 체결가 = mid ± half-spread + impact(거래대금 기반 단순 모델)로 3단(LOW/MID/HIGH).
   - turnover 상한 초과 시 신호를 스케일다운(또는 주문 컷).
2) **게이트**
   - MID 비용에서 OOS mean이 0 이하로 붕괴하거나, turnover가 상한을 지속 초과하면 FAIL.
3) **기대 관측치**
   - 비용 0에서 잘 나오는 전략이 비용에서 무너지는지 즉시 판별.
   - “성능이 안 움직임”이 사실 비용에 의해 상쇄되는 건지 분리 가능.

---

### E4) **운영/관측(telemetry) 복구: rebalance 로그 포맷/경로/해시**
1) **실험 정의**
   - 모든 run에 `run_hash/lane_hash/config_hash/data_hash`를 저장.
   - rebalance 이벤트를 표준 JSONL로 강제 출력(주문 전/후 포지션, 체결, 비용, 노출).
   - `aub_rebalance_pinpoint` 입력 경로 검증(문자열 `--base-log` 같은 사고 방지) + 파일 존재 assert.
2) **게이트**
   - rebalance 로그 누락/파싱 실패 시 FAIL.
   - 포지션이 0인데 신호가 존재하거나, 신호가 0인데 주문이 발생하면 FAIL(불일치 탐지).
3) **기대 관측치**
   - “언제/왜 리밸런스가 안 됐는지”가 1회 루프로 바로 드러남.
   - degenerate_folds의 원인이 데이터인지 실행 흐름인지 분리됨.

---

### E5) **레짐 기반 노출 스케일링(ETF는 지표로만) + 8~14 Tech/Healthcare 집중 규칙**
1) **실험 정의**
   - 종목군을 Tech+Healthcare 8~14개로 고정(ETF 매매 없음).
   - QQQ/XLV(또는 VIX/UST10Y 등) **지표**로만 risk-on/off를 정의해 총 노출을 0.3~0.9 범위에서 스케일.
   - 종목 선택은 기존 스코어 유지하되, 레짐에 따라 포지션 사이징만 조절(과최적화 최소화).
2) **게이트**
   - 레짐 룰이 과도하게 잦은 토글을 만들면 FAIL(예: 주간 토글 > N회).
   - 비용 포함 MID에서 worst tail(OOS min) 악화 시 FAIL.
3) **기대 관측치**
   - 큰 하락 구간에서 노출이 줄며 MDD 또는 OOS min이 개선.
   - 성능이 레짐에 “설명 가능”하게 분해됨.

---

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐) — 실행 순서로
아래는 **질문 없이** 바로 로그/리포트로 갈라치기하는 트리거다.

1) **트리거(신호 발생)**
- 신호 분포가 대부분 0/상수인지 확인하라(피처 NaN→0 대체로 신호가 죽는 경우).
- 신호 상위/하위 종목이 기간 내 거의 고정이면 과최적화/서바이버십을 의심하라(E2로 분리).

2) **적용(주문 생성/리밸런스)**
- “신호 있음 + 주문 0”이면: 거래 제한(유니버스 비어있음/결측), 게이트 클램프, 리밸런스 스케줄 버그를 의심 → E4로 즉시 잡아라.
- “주문 있음 + 포지션 변화 없음”이면: 체결/현금/수량 반올림/최소 주문단위 문제를 의심 → E4 로그로 체결단을 찍어라.

3) **노출(포지션/리스크)**
- exposure가 특정 값(예: 0.84 부근)에서 클립되는 패턴이면: 레버리지/마진/현금비중 규칙이 하드코딩됐거나 결측 대응이 노출을 줄이고 있을 수 있다 → E4에서 “노출 산식”을 단계별 로깅하라.
- 노출이 0으로 자주 떨어지면: 유니버스 공백, 신호 NaN, 리밸런스 미발생, 비용/슬리피지로 주문 컷 등 원인을 분리하라(E1/E2/E3/E4).

4) **비용(현실성)**
- 비용 0에서는 개선되는데 비용 MID/HIGH에서 전부 평평해지면: 엣지가 비용보다 작거나, turnover가 과도하다 → E3로 turnover 상한/패널티를 걸고 “엣지 크기 vs 비용”을 수치로 확인하라.

5) **레짐(시장 국면)**
- 성능이 특정 국면에서만 나오면: 레짐 필터로 “망가지는 구간만” 노출을 줄이는 게 최소 변경으로 효과가 크다 → E5로 스케일링만 추가하라(신호 구조 변경 금지).

---

### 48시간 실행 우선순위(권장)
1) **E4 먼저**(관측/로그 복구 없으면 나머지는 전부 추측)
2) **E1**(누수 차단)
3) **E3**(비용/턴오버 현실화)
4) **E2**(서바이버십/코퍼레이트액션)
5) **E5**(레짐 스케일링으로 리스크 절감)

이 5개를 돌리면, “성능이 안 움직이는 이유”가 전략 문제가 아니라 **데이터/누수/리밸런스/비용/레짐** 중 어디에 있는지 48시간 내에 강제 분해된다.
