## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — **명령형 체크리스트**
아래는 **누수/과최적화/서바이버십/비용 미반영/운영 리스크**를 먼저 잡고, **48시간 자동 루프**에서 “(1) 실험 정의 → (2) 게이트 → (3) 기대 관측치”로 바로 돌아가게 만든 TOP5입니다.  
(제약 준수: **미국주식 only**, **Tech+Healthcare 중심 8~14개**, **ETF 매매 제외(관측지표만)**, **총 5개 patch/실험**만 제안)

---

# 1) (최우선) **평가/데이터 무결성: 누수·서바이버십·시간정렬(lookahead) 차단**
### (a) 왜 필요한지
- 현재 `degenerate_folds: [1,2,3,8]`가 보인다는 건 **학습/평가 구간이 실질적으로 비어있거나(트레이드 0), 라벨/피처 정렬이 깨졌거나, 필터링으로 표본이 사라진 상황**일 가능성이 큼.
- OOS가 “안 움직이는(no-delta)” 현상은 종종 **피처가 이미 미래정보를 먹고 있거나**, 반대로 **신호가 의사결정까지 도달하지 못하는(클리핑/게이트로 무력화)** 때 같이 나타남.
- 미국주식에서 **코퍼레이트 액션(분할/배당) 반영 시점 오류**는 가장 흔한 “가짜 알파” 원인.

### (b) 위험/부작용
- 누수 제거 후 성능 급락 가능(정상).  
- 피처 지연(shift)으로 신호 약화 및 turnover 변화.

### (c) 최소 실험(단일 patch 내 2~3 설정 스윕)
**PATCH/EXPERIMENT #1: `leakage_sentinel_sweep`**
- 설정 A: 현재 파이프라인 그대로(베이스라인 재현)
- 설정 B: **모든 피처/라벨을 1 trading day 지연(shift +1)** 강제(특히 종가 기반이면 다음날 체결 가정)
- 설정 C: (가능하면) **코퍼레이트 액션/어드저스트 방식 2종 비교**(raw vs adjusted 또는 vendor-adjusted vs custom-adjusted)

### (d) PASS 조건(게이트)
- **Fold별 트레이드 수/표본 수가 0인 fold = 0**  
- “shift +1”에서 성능이 **합리적으로 하락**하되, 완전 붕괴가 아니면(예: OOS mean이 50% 이상 증발 + 분산 폭증) 누수 가능성 낮아짐  
- 설정 A/B/C 간 결과가 “비정상적으로 동일(no-delta)”이면 → **의사결정이 신호와 무관하게 고정**되어 있을 확률 ↑ (3번/5번으로 즉시 이동)

# 2) (최우선) **리밸런스/로깅/재현성: rebalance pinpoint 실패 원인 제거**
현재 로그:
- `Error loading --base-log: ... '--base-log'`
- `rebalance.csv` / `rebalance.jsonl` 파싱 실패  
즉, **리밸런스 이벤트가 기록되지 않거나 포맷이 깨져서**, “성능이 왜 안 움직였는지(실제로 매매가 있었는지)”를 추적 불가.

### (a) 왜 필요한지
- 리밸런스 로그가 없으면 **트리거→주문→체결→포지션** 연결이 끊겨서, no-delta의 원인을 영원히 못 잡음.
- `lane_hash/run_hash: None`도 재현성/아키텍처 운영 리스크(실험 결과가 어디서 왔는지 추적 불가).

### (b) 위험/부작용
- 로그/메타데이터 추가로 I/O 증가(미미).  
- 포맷 변경 시 기존 툴 호환성 깨질 수 있으니 버전필드 필요.

### (c) 최소 실험(단일 patch 내 2~3 설정 스윕)
**PATCH/EXPERIMENT #2: `rebalance_telemetry_fix`**
- 설정 A: rebalance 이벤트를 **JSONL 한 포맷으로 고정**(schema 버전 포함), 파일 경로를 run artifact 폴더로 강제
- 설정 B: base/cand 로그 경로를 **명시적 실존 경로로만 받도록**(지금처럼 `--base-log` 문자열이 path로 들어가면 실패)
- 설정 C: `lane_hash/run_hash`를 **config hash + data hash + code git sha**로 항상 채움

### (d) PASS 조건(게이트)
- 각 run에서 다음 파일이 **항상 생성 + 파싱 성공**:
  - `rebalance.jsonl`(또는 csv 단일화)
  - `orders.jsonl`, `fills.jsonl`(최소한 rebalance→target weights는 필수)
- rebalance pinpoint 툴이 base/cand 모두에서 **“리밸런스 횟수/평균 turnover/상위 기여 종목”**을 출력

# 3) (상) **비용/슬리피지/체결 가정 미반영 제거 + 비용 민감도 체크**
### (a) 왜 필요한지
- 비용이 빠져 있으면 “좋아 보이는데 운영에서 죽는” 케이스가 1순위.
- no-delta는 반대로 **비용/슬리피지가 너무 강하게 들어가 매매가 사실상 0**이어서 성능이 고정될 수도 있음(특히 exposure가 0.0~0.84로 뜨는 점이 의심 포인트).

### (b) 위험/부작용
- 비용 현실화로 성능 하락(정상).
- 잘못된 비용모델(과도) 적용 시 과도한 보수화로 전략 붕괴.

### (c) 최소 실험(단일 patch 내 2~3 설정 스윕)
**PATCH/EXPERIMENT #3: `cost_model_sweep_us_equities`**
- 설정 A: 비용 OFF(진단용)
- 설정 B: 비용 ON(보수적 고정): 예) `commission=0`, `slippage_bps=5~15bps(유동성 기반)` 중 하나로 고정
- 설정 C: 비용 ON(동적): `slippage_bps = k * (order_dollar / ADV)` 형태(ADV는 과거 데이터, 미래누수 없이)

### (d) PASS 조건(게이트)
- 비용 OFF 대비 ON에서:
  - turnover가 비정상적으로 0으로 떨어지지 않을 것(“매매가 살아있음” 확인)
  - OOS mean이 합리적으로 감소하되 **전략 순위/특성(승률, 분산 구조)**가 유지될 것
- 비용 ON에서 **실현가능한 turnover 상한(예: 일 20~40% 이내)**을 넘지 않을 것(전략 성격에 맞게)

# 4) (상) **포트폴리오 제약(8~14종, Tech+Healthcare 중심)과 노출/집중 리스크 하드가드레일**
### (a) 왜 필요한지
- 현재 exposure max가 0.838…로 보이고, min이 0.0이라 **현금 비중/노출 변동이 큰 구조**일 수 있음.  
- 운영 관점에서 8~14종 강제, 섹터 편향 관리(Tech+Healthcare 중심), 단일종목 과집중 방지가 필수.
- “성능이 안 움직이는” 원인이 **제약/클리핑이 너무 강해 신호가 죽는 것**일 수도 있으니, 제약이 실제로 어떻게 작동하는지 로그로 확인해야 함.

### (b) 위험/부작용
- 제약 강화로 알파 일부 희생.
- 강제 종목수로 인해 불리한 종목을 억지 편입 가능(특히 신호 약할 때).

### (c) 최소 실험(단일 patch 내 2~3 설정 스윕)
**PATCH/EXPERIMENT #4: `constraint_pack_8_14_names`**
- 설정 A: 종목수 hard constraint: **항상 8~14개**(미만이면 현금, 초과면 신호 상위만)
- 설정 B: 단일종목 cap: 예) **max 12~15%**
- 설정 C: 섹터 밴드(Tech/Healthcare 합산 중심): 예) **Tech+HC ≥ 70%**(단, ETF 매매 없음. 섹터 분류는 GICS/NAICS 등 과거시점 기준)

### (d) PASS 조건(게이트)
- 모든 리밸런스에서:
  - 보유 종목 수가 8~14 유지
  - 단일 종목 cap 위반 0
  - 섹터 밴드 위반 0
- OOS에서 degenerate fold가 늘지 않을 것(제약으로 매매 0이 되면 실패)

# 5) (중) **No-delta 원인 직접 타격: “신호→의사결정 영향도” 계측 + 트리거 민감도 스윕**
### (a) 왜 필요한지
- “9 experiments, no delta”는 보통 아래 중 하나:
  1) 실험 변경이 실제 주문/weights에 반영되지 않음(코드 경로 무시)
  2) 트리거/게이트가 너무 강해 매매가 동일(또는 0)
  3) 포지션/제약/정규화가 결과를 거의 고정
- 따라서 성능지표가 아니라 **의사결정 레벨의 변화량**(weights delta, turnover delta, rank correlation)을 먼저 봐야 함.

### (b) 위험/부작용
- 트리거 민감도 올리면 turnover 급증/비용 악화.
- 계측 추가로 로그량 증가.

### (c) 최소 실험(단일 patch 내 2~3 설정 스윕)
**PATCH/EXPERIMENT #5: `decision_impact_probe`**
- 공통 계측(필수):
  - 리밸런스 시점마다 `pre_weights`, `post_weights`, `target_weights`, `delta_L1`, `turnover`, `topK 변경 수`, `signal_rank_corr(base vs cand)` 저장
- 설정 A: 현재 트리거 그대로 + 계측만 추가
- 설정 B: 트리거 완화(예: rebalance threshold 50%로 낮춤)
- 설정 C: 트리거 강화(예: threshold 150%로 높임) → 매매 0 여부 확인

### (d) PASS 조건(게이트)
- 설정 A/B/C 간에 **delta_L1/turnover 분포가 유의하게 달라질 것**(달라지지 않으면 “전략이 실제로 고정/무시”)
- B에서 turnover가 늘어도 비용 ON(#3)에서 완전 붕괴하지 않을 것(운영 가능성)

# 성능이 안 움직일 때 “원인 분해” 아이디어(트리거/적용/노출/비용/레짐)
아래 트리를 **로그/계측으로 기계적으로 판정**하라(추측 금지).

## A. 트리거/적용(코드 경로) 레벨
- **체크 1:** 실험 config 변경이 `lane_hash/run_hash`에 반영되는지 확인(미반영이면 실험이 같은 런으로 취급될 수 있음)
- **체크 2:** cand vs base의 `target_weights`가 다른가?
  - 같으면 → **신호가 주문 생성 단계에 반영 안 됨**(코드 경로, flag, 캐시, 잘못된 파라미터 key)
- **체크 3:** `target_weights`는 다른데 `post_weights`가 같은가?
  - 같으면 → **트리거/게이트/리스크 제약이 다 씹어먹음**(클리핑/종목수 강제/노출 상한)

## B. 노출/제약(Portfolio) 레벨
- **체크 4:** exposure(min/max)와 현금비중이 실험 간 동일한가?
  - 동일하면 → 노출 결정이 고정(예: 항상 risk-off)
- **체크 5:** 종목 수(8~14) 강제 시, 신호 약한 구간에서 “현금으로 빠지는” 빈도가 과도한가?

## C. 비용/체결 레벨
- **체크 6:** 비용 ON에서 turnover가 0으로 수렴하는가?
  - 그렇다면 → 비용모델이 과도하거나, “비용>알파”로 트리거가 무력화
- **체크 7:** 슬리피지 계산에 미래 ADV/volume 사용 여부(누수) 점검

## D. 레짐(시장 국면) 레벨 — ETF는 “관측지표”로만 사용
- QQQ(Tech), XLV(Healthcare), SPY를 **레짐 태그용**으로만 사용:
  - 예: `trend(200d)`, `vol(20d)`, `drawdown`으로 기간을 태깅하고 OOS를 구간별 분해
- **체크 8:** 성능이 특정 레짐에서만 나오면 → 전 구간 평균이 “안 움직이는” 것처럼 보일 수 있음(레짐 분해 필수)

## E. 과최적화/서바이버십
- **체크 9:** 유니버스가 “현재 살아남은 대형주”만 포함되었는지(서바이버십)  
- **체크 10:** 하이퍼파라미터가 너무 촘촘한 탐색으로 OOS가 평평해졌는지(선택 편향) → 워크포워드/시드 고정/탐색 예산 제한
