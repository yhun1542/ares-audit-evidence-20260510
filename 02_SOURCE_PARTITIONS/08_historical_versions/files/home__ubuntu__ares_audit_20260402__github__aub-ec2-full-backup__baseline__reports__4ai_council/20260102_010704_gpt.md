## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — 명령형 체크리스트
(우선순위는 **누수 → 과최적화 → 서바이버십 → 비용 → 운영 리스크** 순으로 배치)

---

# 1) (P1) **누수/룩어헤드 하드닝**: “시간정렬 불변성”을 강제
### (a) 왜 필요한지
- tuning 대비 lockbox가 좋더라도, **미세 룩어헤드(가격/기업행동/피처 타이밍 1일 오차)**가 있으면 이후 실거래에서 급락.
- 특히 **close 기준 피처로 same-day 체결** 같은 형태가 가장 흔한 누수.

### (b) 위험/부작용
- 성능이 단기 급락할 수 있음(정상 반응).  
- 파이프라인 전반(피처 캐시/라벨 생성/리밸런싱 타이밍) 수정 필요로 개발비 증가.

### (c) 최소 실험(2~3개, 단 48h 루프에서는 1개만 실행)
- **E1-A (우선 실행)**: *피처 전체를 +1 trading day shift* 후 재학습/백테스트  
  - 목적: “룩어헤드면 성능이 과도하게 유지되는” 이상징후 탐지
- E1-B: *라벨/체결 타이밍 고정*: `signal@t` → **next open** 또는 **t+1 close** 체결로 강제
- E1-C: *purged/embargo 검증* (fold 경계에서 인접 샘플 제거)

### (d) PASS 조건(게이트)
- **누수 부재 쪽으로 수렴**:  
  - shift(+1) 적용 시 성능이 **합리적으로 하락**(예: lockbox_mean이 소폭~중간 하락)하되,  
  - *하락 폭이 “전략 붕괴급”이 아니고*,  
  - tuning-lockbox 괴리가 감소(과최적화 징후 완화).
- 최소 기준(권장):  
  - `worst_mdd <= 0.09` 유지  
  - `lockbox_min >= 0` 유지(또는 기존 대비 악화 제한)

**48h 자동 루프 형태**
1) 실험 정의: `feature_shift=+1d` 또는 `execution_lag=1`을 시스템 레벨 옵션으로 추가  
2) 게이트: lockbox_mean, lockbox_min, worst_mdd, tuning-lockbox gap  
3) 기대 관측치: “살짝 약해지지만 더 현실적” + gap 축소

# 2) (P2) **비용/슬리피지/임팩트 모델을 보수적으로 통합** (비용 미반영 리스크 우선 제거)
### (a) 왜 필요한지
- 8~14종목 집중 포트는 **회전율/스프레드/체결 실패**에 성능이 민감.
- lockbox가 좋아도 **비용을 현실화하면 순식간에 챔피언이 뒤집힘**.

### (b) 위험/부작용
- 성능 하락 가능(정상).  
- 과도하게 보수적이면 좋은 알파까지 제거.

### (c) 최소 실험(2~3개, 48h에서는 1개만 실행)
- **E2-A (우선 실행)**: 비용 모델 “보수 패치”  
  - 예: `commission + half_spread + k * (|trade|/ADV)` 형태 임팩트 추가  
  - ADV/스프레드는 가능하면 일별로(불가하면 고정 상수라도 보수적으로)
- E2-B: *턴오버 페널티를 목적함수에 직접 반영* (예: utility = return - λ*turnover - cost)
- E2-C: *포지션 사이즈 상한 + 거래량 대비 상한* (|trade| <= α*ADV)

### (d) PASS 조건
- 비용 반영 후에도:
  - `lockbox_mean >= current_champion.lockbox_mean` **또는** (조금 낮아져도) `worst_mdd`가 유의미하게 개선
  - **턴오버 지표 하락**(예: 일/주 turnover 15~30% 감소) + 성능 유지
- 운영 게이트:
  - 일별 예상 거래대금/ADV 비율이 임계값 이하(예: 1~3% 수준)

**48h 자동 루프**
1) 실험 정의: cost_model을 시스템 공통 모듈로 승격(백테스트/실행 동일)  
2) 게이트: 비용 전/후 성능 차이, turnover, trade/ADV  
3) 기대 관측치: “수익 감소 폭 제한 + MDD/변동성 감소”

# 3) (P3) **서바이버십 바이어스/유니버스 고정 규칙** (미국주식, Tech+Healthcare, 8~14개 유지)
### (a) 왜 필요한지
- “현재 살아남은 대형 테크/헬스케어”로만 과거를 백테스트하면 **서바이버십으로 과대평가**.
- 특히 개별주 8~14개면, 유니버스 정의가 성과를 좌우.

### (b) 위험/부작용
- 과거에 없던/상장폐지 종목 반영 시 데이터 결측/심볼 변경 처리 필요.
- 유니버스가 바뀌면 전략 성격이 달라져 비교가 어려워짐.

### (c) 최소 실험(2~3개, 48h에서는 1개만 실행)
- **E3-A (우선 실행)**: 유니버스 “시점 고정(frozen list)” 룰 적용  
  - 예: 기준일(백테스트 시작일)에서 Tech+Healthcare 대형주 후보를 선정하고 **끝까지 고정**  
  - (ETF 매매는 금지, QQQ/XLV는 관측지표만)
- E3-B: “IPO/상폐 필터”를 시점 기반으로 강제(데이터 존재 시작일부터만 편입)
- E3-C: 심볼 변경/합병(티커 변경) 맵핑을 강제하여 연속성 검증

### (d) PASS 조건
- 유니버스 고정 후에도:
  - `lockbox_mean`이 과도하게 붕괴하지 않고,
  - `lockbox_min` 및 `worst_mdd`가 안정적으로 유지/개선
- 추가로: “특정 1~2 종목이 성과 대부분을 설명”하는 집중도가 감소(서바이버십/행운 의심 완화)

**48h 자동 루프**
1) 실험 정의: universe_builder를 “시점 고정 모드” 옵션 추가  
2) 게이트: 성과 붕괴 여부 + 종목별 성과 기여도 집중도  
3) 기대 관측치: 성능 일부 감소 가능하지만 더 재현가능한 분포

---

# 4) (P4) **과최적화 억제: Purged Walk-Forward + 단순 앙상블(2~3개)**  
### (a) 왜 필요한지
- tuning_mean이 높아도, 운영에서 죽는 원인의 상당수는 **검증 구조 미흡(정보 누수/중복 샘플) + 하이퍼파라미터 과다**.
- 현재 candidate가 좋으므로, “더 올리기”보다 **견고화(variance 축소)**가 우선.

### (b) 위험/부작용
- 단기 최고점 성능(평균)은 내려갈 수 있음.
- 훈련 시간이 늘어날 수 있음(48h 루프에서 자원 관리 필요).

### (c) 최소 실험(2~3개, 48h에서는 1개만 실행)
- **E4-A (우선 실행)**: Purged K-Fold + embargo(예: 5~20일)로 재평가  
- E4-B: 모델/시그널 2개만 앙상블(예: mean rank)로 단순화  
- E4-C: 하이퍼파라미터 탐색 범위 축소(탐색 비용↓ + 과최적화↓)

### (d) PASS 조건
- “좋은데 불안정”이 아니라 “조금 덜 좋아도 꾸준”이 목표:
  - tuning-lockbox gap 축소
  - `worst_mdd` 개선 또는 tail(최악 fold) 개선
  - 성과가 특정 fold에 과도 의존하지 않음

**48h 자동 루프**
1) 실험 정의: validator를 purged/embargo 모드로 교체  
2) 게이트: gap, worst-fold 성능, MDD  
3) 기대 관측치: 평균 약간↓, 최악 구간↑(개선), 분산↓

---

# 5) (P5) **운영 리스크 패치: 48시간 자동루프 “실행 안전장치(가드레일)” 추가**
### (a) 왜 필요한지
- 실거래에서 망하는 케이스의 다수가 “전략”이 아니라 **배치/데이터/심볼/체결/리밸런싱 실패**.
- 자동 루프면 특히 **데이터 지연/부분 결측/이상치**에 취약.

### (b) 위험/부작용
- 과도한 가드레일은 거래 빈도를 줄여 성능 저하 가능.
- 경보/중단 로직이 너무 민감하면 “항상 멈춤” 상태가 될 수 있음.

### (c) 최소 실험(2~3개, 48h에서는 1개만 실행)
- **E5-A (우선 실행)**: “데이터 완결성 게이트”  
  - 당일 bar 개수/결측률/이상 갭(예: ±20% 급변) 탐지 시 **거래 중단 + 현금 유지**
- E5-B: “포지션/주문 상한” (8~14종목 강제, 단일 종목 최대 비중, 섹터 편중 제한)
- E5-C: “체결 실패/부분 체결” 시 다음 사이클 재시도 규칙 + 로그/스냅샷 저장

### (d) PASS 조건
- 백테스트 성과보다 **운영 안정성 지표** 통과가 목표:
  - 에러율 0, 결측 탐지율 정상, 중단 후 재개가 일관
  - 포트폴리오가 항상 8~14개 범위 유지(예외는 명시적으로 현금 처리)

**48h 자동 루프**
1) 실험 정의: pre-trade gate + fail-safe를 실행 파이프라인에 삽입  
2) 게이트: “거래 실행 성공률/에러 0/결측시 중단”  
3) 기대 관측치: 성능 변화 작거나 소폭↓, 대신 실운영 사고 확률 급감

## 48시간 실행 순서(5개만 돌리는 형태) — 명령형 체크리스트
1. **P1-E1A** 실행: 피처 +1d shift 실험을 candidate 기준으로 1회 러닝  
2. **P2-E2A** 실행: 보수 비용모델(스프레드+임팩트) on  
3. **P3-E3A** 실행: 유니버스 frozen-list 모드 on (Tech+Healthcare, 8~14 유지)  
4. **P4-E4A** 실행: purged+embargo 검증으로 재스코어링  
5. **P5-E5A** 실행: 데이터 완결성 게이트 삽입(결측/이상치 시 거래 중단)

(각 단계는 “성능 최대화”가 아니라 **리얼월드 붕괴 요인 제거**가 목적)

# 성능이 안 움직일 때: 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래 순서대로 “어디서 알파가 죽는지”를 분해하고, 로그/리포트에 강제 출력하라.

## A) Trigger(시그널 생성 품질) 분해
- **IC/RankIC 시계열**을 저장하고 “0 근처로 수렴했는지” 확인하라.
- 예측이 맞아도 수익이 안 나면:  
  - **정답 방향은 맞는데 크기가 작음**, 또는 **신호가 너무 드묾/너무 잦음**.
- 조치 패치 후보: 신호 임계값/홀드기간을 고정 2~3개로만 스윕(케이스 폭발 금지).

## B) Application(적용/체결 타이밍) 분해
- `signal@t` → 실제 주문이 `t open`인지 `t+1 open`인지 **명시적으로 로그**로 남겨라.
- 성능 정체의 흔한 원인:  
  - “close 기준으로 신호 생성 + same close 체결(불가능)”  
  - 혹은 “주문이 하루 밀려서 알파 소멸”
- 진단 출력: **signal_time, order_time, fill_time** 3타임스탬프 표준화.

## C) Exposure(포트폴리오 노출) 분해
- 매일 다음을 기록하라:
  - 종목 수(항상 8~14인지), 단일종목 최대비중, 섹터 비중(Tech vs Healthcare)
  - 시장 베타(관측지표로 SPY/QQQ), 스타일 노출(대형주 쏠림 등)
- 성능 정체 원인: “알파는 있는데 **베타/섹터 노출이 잡아먹음**” 또는 “포지션 상한 때문에 알파를 못 담음”.

## D) Cost(비용/회전율) 분해
- “총 PnL = gross alpha - cost”를 **일별로 분해** 저장하라.
- 성능 정체 원인: gross는 증가하는데 cost가 같이 증가(회전율 폭증).
- 필수 지표:
  - turnover(일/주), 평균 스프레드, trade/ADV, 비용이익비(cost / gross)

## E) Regime(레짐) 분해 — ETF는 관측지표로만 사용
- 레짐 버킷을 2~4개로만 단순화해라(케이스 폭발 금지):
  - 예: QQQ 추세 상/하, VIX 대용 변동성 상/하(가능하면), XLV 상대강도(헬스케어 vs 테크)
- 각 버킷에서:
  - 평균 수익, 최악 손실, hit-rate, turnover를 따로 리포트하라.
- 성능 정체 원인: 특정 레짐에서만 벌고 나머지에서 다 토함 → **레짐 필터/리스크 오버레이** 후보.

## PASS 판정의 “단일 문장” 표준(권장)
- **lockbox_mean 개선 또는 유지 + lockbox_min 비음 방지 + worst_mdd 개선 + 비용/턴오버/운영게이트 통과**면 PASS로 승격하라.

원하는 형식으로 `baseline/reports/next_fix.md`에 위 5개 패치를 그대로 “실험 스펙 템플릿(옵션/게이트/기대관측치)”로 내려쓰고, `--select-best`가 성능만 보지 않도록 **게이트(비용/누수/운영)**를 합격 조건에 포함시키는 쪽으로 고정하라.
