# TOP1) 데이터 누수/룩어헤드 “하드 차단” 패치 (가장 우선)
### (a) 왜 필요한지
- 현재 성능이 충분히 좋아 보일수록, **미세한 룩어헤드/정렬 오류**가 `lockbox_mean`을 과대평가했을 위험이 큼.
- 특히 기술적/의료 종목은 **어닝/갭**이 커서, “당일 종가로 신호 만들고 당일 체결” 같은 누수가 쉽게 숨어듦.

### (b) 위험/부작용
- 단기적으로 성능 하락 가능(“진짜 성능”이 드러남).
- 코드 경로가 늘어 운영 복잡도 증가.

### (c) 최소 실험(2~3)
**실험 1: Feature/Label 시간정렬 강제(1-bar shift)**
- [ ] 모든 feature 생성 후 **일괄 `shift(1)`**(또는 “신호는 T에 만들고 체결은 T+1 시가/종가”로 강제)
- [ ] 리샘플/머지 후 인덱스 정렬 검증(assert)

**실험 2: “체결가 기준”을 명시적으로 분리**
- [ ] 신호 생성용 가격(예: Close[T])과 체결가(예: Open[T+1])를 코드 상 **서로 다른 필드**로 강제
- [ ] “동일 timestamp에서 생성된 값으로 체결” 경로 제거

**실험 3: 누수 감지용 셔플 테스트(가짜 알파 검증)**
- [ ] 라벨(수익률) 시계열을 블록 단위로 섞거나, feature를 하루씩 랜덤 시프트 → 성능이 **유의미하게 붕괴**해야 정상

### (d) PASS 조건
- [ ] 누수 차단 후에도 `lockbox_mean`이 **챔피언 대비 -1~2%p 이내**로 유지하거나, 손실이 있더라도 **worst_mdd 개선**이 동반되면 PASS
- [ ] 셔플 테스트에서 성능이 **0 근처로 붕괴**(“가짜 알파 없음”)하면 PASS

### 48시간 루프 형태
- (1) 실험 정의: `leakage_hardening_v1` (shift+체결가 분리+셔플)
- (2) 게이트: 공통 게이트 + 셔플 성능 붕괴 확인
- (3) 기대 관측치: tuning 성능 소폭 하락 가능, lockbox가 “덜 과대평가”되며 MDD가 더 현실적으로 정리

# TOP2) 서바이버십/유니버스 고정 “스냅샷” 패치 (Tech+Healthcare 8~14 강제)
### (a) 왜 필요한지
- **서바이버십 바이어스**는 lockbox에서도 그럴듯한 성능을 만들 수 있음(특히 Mega-cap 중심).
- “당시 존재했던 종목/당시 상장 상태”가 코드에서 제대로 반영되지 않으면 **전략이 존재하지 않았던 종목을 거래**하게 됨.

### (b) 위험/부작용
- 유니버스가 줄어들면 분산이 낮아져 변동성이 커질 수 있음.
- 과도한 필터링은 샘플 수 감소로 과최적화 위험 증가.

### (c) 최소 실험(2~3)
**실험 1: 유니버스 스냅샷 파일화 + 해시 고정**
- [ ] Tech+Healthcare 후보 풀(예: 8~14개) **정적 리스트/룰 기반**으로 만들고, 백테스트 기간 전 구간에 대해 동일하게 적용
- [ ] 유니버스 구성 결과를 날짜별로 저장 + 해시(재현성) 기록

**실험 2: 상장폐지/티커변경 처리 검증**
- [ ] delisted/merged/renamed 티커가 데이터에서 어떻게 처리되는지 로그 출력
- [ ] “거래 가능 여부(tradable flag)” 없으면 거래 금지

**실험 3: Universe drift 감시(월별 구성 변화율 제한)**
- [ ] 룰 기반 유니버스일 경우 월별/분기별 변경률 상한(예: 20%) 두고 초과 시 경고/중단

### (d) PASS 조건
- [ ] 유니버스 스냅샷 적용 후에도 `lockbox_min` 비악화 + `worst_mdd` 동등 이상
- [ ] “비정상 티커/상장폐지 거래”가 **0건**으로 확인되면 PASS

### 48시간 루프 형태
- (1) 실험 정의: `universe_snapshot_v1`
- (2) 게이트: 공통 게이트 + “비정상 거래 0”
- (3) 기대 관측치: 성능이 약간 낮아져도 MDD/재현성/신뢰도가 크게 개선

# TOP3) 비용(슬리피지/스프레드/수수료) “보수적” 내재화 + Turnover 게이트
### (a) 왜 필요한지
- 지금의 개선폭(챔피언 대비 미세 개선)은 **비용 한 번에 상쇄**될 가능성이 큼.
- 특히 8~14 종목 집중은 거래 빈도가 늘면 비용 충격이 큼.

### (b) 위험/부작용
- 비용을 보수적으로 넣으면 성능이 눈에 띄게 떨어질 수 있음(하지만 그게 현실).
- 비용 모델이 잘못되면 오히려 왜곡 가능.

### (c) 최소 실험(2~3)
**실험 1: 고정 bps + 변동 스프레드(가격/변동성 연동)**
- [ ] 기본: 거래당 `commission_bps + slippage_bps`
- [ ] 변동: ATR 또는 일중 변동성 기반으로 슬리피지 bps 가중

**실험 2: Turnover 상한 게이트(전략 레벨)**
- [ ] 2일/5일/20일 평균 turnover를 계산하고 상한 초과 시 포지션 변경을 **부분 체결/지연**(rebalance throttle)

**실험 3: 비용 민감도 스윕(±50%)**
- [ ] 비용을 0.5x / 1.0x / 1.5x로 돌려서 성능이 “부드럽게” 변해야 정상(민감도가 비정상적으로 크면 구조 문제)

### (d) PASS 조건
- [ ] 비용 1.0x에서 `lockbox_mean`이 챔피언 대비 **-1%p 이내** 또는 `worst_mdd` 개선 시 PASS
- [ ] 비용 1.5x에서도 성능이 급사하지 않고(예: lockbox_mean의 급락/lockbox_min 악화가 과도하지 않음) **완만한 저하**면 PASS
- [ ] turnover 게이트 적용 후 `worst_mdd` 또는 `lockbox_min` 개선 확인 시 PASS

### 48시간 루프 형태
- (1) 실험 정의: `cost_model_conservative_v1 + turnover_throttle_v1`
- (2) 게이트: 공통 게이트 + “비용 1.5x 급사 금지”
- (3) 기대 관측치: 평균 수익 약간 하락, 대신 바닥(lockbox_min)과 MDD가 안정화

# TOP4) 과최적화 방지: “단순화/정규화/검증 강화” 패치
### (a) 왜 필요한지
- 후보가 챔피언을 근소하게 이길 때는, 대개 **자유도(파라미터/피처/규칙)가 너무 커서** 튜닝셋에만 맞춘 신호일 위험.
- 지금 숫자는 lockbox도 좋지만, 더 올리려면 “더 복잡하게” 가기보다 **더 단단하게** 가는 쪽이 기대값이 큼.

### (b) 위험/부작용
- 단순화로 단기 성능이 줄 수 있음.
- 지나친 정규화는 알파를 눌러버릴 수 있음.

### (c) 최소 실험(2~3)
**실험 1: 파라미터 동결(Freeze) + 민감도 확인**
- [ ] 가장 영향 큰 2~3개 하이퍼파라미터를 고정하고, 나머지 탐색 폭 축소
- [ ] 성능이 유지되면 “진짜” 신호일 확률 증가

**실험 2: Feature 드롭(상관 높은 피처 제거)**
- [ ] 피처 상관/중복(예: 상관 0.95+) 제거
- [ ] 피처 수를 줄인 버전이 lockbox에서 유지되면 과최적화 감소

**실험 3: Fold별 성능 분산(variance) 게이트 추가**
- [ ] mean만 보지 말고 fold 성능의 표준편차/최악 fold를 게이트로 사용(지금도 min을 보지만 분산까지 추가)

### (d) PASS 조건
- [ ] 단순화 후 `lockbox_mean`이 -1~2%p 이내로 유지하면서 **lockbox_min 또는 worst_mdd 개선**이면 PASS
- [ ] fold 분산 감소(예: 성능 표준편차 하락) 확인 시 PASS

### 48시간 루프 형태
- (1) 실험 정의: `regularize_simplify_v1`
- (2) 게이트: 공통 게이트 + fold 분산 상한
- (3) 기대 관측치: 평균은 비슷/소폭 하락, 대신 최악구간 방어력 개선

# TOP5) 노출(Exposure) 리스크/레짐 붕괴 방지: “볼 타게팅 + 섹터 밸런스” 패치
### (a) 왜 필요한지
- Tech/Healthcare 집중(8~14)에서는 **레짐(금리/리스크온오프)**에 의해 한 방향으로 쏠리면 MDD가 커짐.
- 성능이 정체될 때는 “알파 부족”이 아니라 **베타/변동성 노출이 성과를 덮는** 경우가 많음.

### (b) 위험/부작용
- 리스크 제어가 알파도 함께 줄여 평균 성과가 감소할 수 있음.
- 제약이 많아지면 체결 빈도/구현 복잡도 증가.

### (c) 최소 실험(2~3)
**실험 1: 변동성 타게팅(포트폴리오 레벨)**
- [ ] 최근 N일(예: 20) realized vol로 목표 변동성에 맞춰 포지션 스케일  
- [ ] 급변 구간에서 자동 디레버리지

**실험 2: 섹터 중립/밸런스(Tech vs Healthcare)**
- [ ] Tech/Healthcare의 총 노출을 50/50 또는 범위(예: 40~60%)로 제한  
- [ ] 8~14 종목 중 섹터 편중 발생 시 리밸런싱

**실험 3: ETF 관측지표 기반 “리스크 컷” (매매는 개별주만)**
- [ ] 관측: QQQ(Tech), XLV(Healthcare), VIX, TLT 같은 지표로 risk-off 감지  
- [ ] 트리거 시: 신규 진입 중단/포지션 축소(개별주만 조정)

### (d) PASS 조건
- [ ] `worst_mdd`와 `lockbox_min`이 개선되고, `lockbox_mean`이 챔피언 대비 -1~2%p 이내면 PASS
- [ ] 레짐 스트레스 구간(급락)에서 손실 꼬리(tail)가 줄어들면 PASS

### 48시간 루프 형태
- (1) 실험 정의: `risk_overlay_vol_target_v1 + sector_balance_v1 + regime_cut_v1`
- (2) 게이트: 공통 게이트 + tail 손실(최악구간) 개선
- (3) 기대 관측치: 평균은 약간 감소할 수 있으나 최악 MDD/바닥이 개선

# 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐)
아래는 “안 움직임”을 **어디서 막히는지** 빠르게 쪼개는 진단 축입니다(질문 없이 바로 추가 로그/리포트로 구현 가능).

## A) Trigger(신호 발생) 문제
- [ ] 신호 발생 빈도(일별/주별)와 “제로 포지션 비율” 출력  
- [ ] 신호 강도 분포(상위/하위 분위수)와 시간에 따른 드리프트 확인  
- [ ] 히트레이트/평균이익/평균손실(분해: hit rate vs payoff) 리포트

## B) Apply(적용/체결) 문제
- [ ] 신호→주문→체결까지의 **1-bar 지연**이 정확히 반영되는지 점검(룩어헤드와도 연결)
- [ ] 리밸런싱 규칙이 실제로 포지션을 얼마나 바꾸는지(의도 대비) 확인
- [ ] “같은 날 과도한 뒤집기” 발생 여부(플립 카운트) 출력

## C) Exposure(노출) 문제
- [ ] 포트의 순노출/총노출(gross), 종목별 비중 상한 위반 여부
- [ ] Tech vs Healthcare 노출 시계열(편중이 성과를 지배하는지)
- [ ] 스타일 노출(대형주 쏠림, 모멘텀/밸류 유사) 간이 팩터 회귀(정보만)

## D) Cost(비용) 문제
- [ ] 비용 전/후 성과 차이를 “일별 PnL 브리지”로 분해(슬리피지 vs 스프레드 vs 수수료)
- [ ] turnover가 특정 구간에서 폭증하는지(레짐과 결합) 확인
- [ ] 비용 민감도(0.5x/1.0x/1.5x)에서 곡선이 비정상적으로 꺾이면 구조 문제

## E) Regime(레짐) 문제
- [ ] ETF 관측지표(QQQ/XLV/VIX/TLT)로 구간을 2~3개 레짐으로 나눠 성과 테이블 출력(거래는 개별주만)
- [ ] 급락/급등/횡보 구간에서 성과가 어디서 깨지는지 확인(특히 worst_mdd 구간)
- [ ] 레짐별로 “신호 강도는 좋은데 체결이 손해”인지(갭/변동성) 분리

- [ ] 그 다음 TOP4(단순화/정규화)로 과최적화 제거
- [ ] 마지막 TOP5(리스크 오버레이)로 꼬리/MDD를 다듬어 lockbox_min과 worst_mdd를 개선

위 5개만으로도 48시간 루프에서 “성능 개선”보다 더 중요한 **성능의 진짜성/견고성**을 먼저 확정할 수 있고, 그 다음에야 lockbox_mean의 미세 개선이 의미 있게 누적됩니다.
