## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — 명령형 체크리스트

### 1) **아티팩트/로그 무결성 복구 (운영 리스크 최우선)**
- [ ] Champion JSON에 `file/lane_hash/run_hash/worst_mdd`가 **항상 채워지도록** 스키마 강제
- [ ] `rebalance` 로그 포맷을 **단일 표준(jsonl)** 로 고정하고, 툴이 기대하는 경로/확장자 자동 생성
- [ ] 실험 종료 시 **필수 산출물 존재 검증**(없으면 실패 처리) + “왜 실패했는지” 원인 코드 반환

**(a) 왜 필요한지**
- 현재 ONE TRUTH에서 `file: (blank)`, `lane_hash/run_hash: None`, `worst_mdd: None` → 재현/감사/디버그 불가(서바이버십·누수·비용 이슈를 검증할 기반 자체가 없음)
- `rebalance` 로딩이 깨져서 비용/턴오버/체결 가정을 점검할 수 없음

**(b) 위험/부작용**
- 실험이 “더 자주 실패”해 보일 수 있음(사실은 기존에 조용히 망가진 결과가 통과하던 것)
- 로그 저장량 증가(하지만 48시간 루프에선 필수 비용)

**(c) 최소 실험(2~3개)**
- E1 + E4(비용/리밸런스 로그가 있어야 성립) 를 **동시에** 굴려서 파이프라인 end-to-end 검증
- E1 + E2(폴드/누수 체크) 를 **동시에** 굴려서 재현성 확보

**(d) PASS 조건**
- 모든 러닝에서 `champion.json` 필수 필드 100% 채움 + 재실행 시 동일 seed면 동일 결과(허용 오차 내)
- `rebalance.jsonl` 생성 및 툴 로딩 성공(에러 0회)
- `worst_mdd` 산출(Null 금지) 및 계산 구간 명시


---

### 2) **누수/과최적화 방지: 폴드 퇴행(degenerate_folds) 제거 + Purged/Embargo CV**
- [ ] `degenerate_folds: [1,2,3,8]` 원인(샘플 부족/필터링/리밸런스 빈도/결측 처리) 추적 로그 추가
- [ ] 시계열 CV를 **Purged KFold + Embargo**(예: 5~20 trading days)로 고정
- [ ] 폴드별 “유효 거래일 수/포지션 발생률/노출 평균”을 저장하고 게이트로 사용

**(a) 왜 필요한지**
- 폴드가 퇴행하면 OOS 평균이 의미 없고, “안 움직이는 성능”의 1순위 원인이 됨(모델이 실제로는 거래를 안 하거나 학습/평가가 비정상)

**(b) 위험/부작용**
- OOS 성능이 일시적으로 하락할 수 있음(누수 제거의 정상 신호)
- 학습 데이터가 줄어 분산 증가 → 통계적 유의성 게이트 필요

**(c) 최소 실험(2~3개)**
- E2(새 CV/폴드 헬스 게이트) + E5(레짐별 노출 안정성 함께 체크)
- E2 단독으로 “기존 vs purged+embargo” A/B

**(d) PASS 조건**
- `degenerate_folds`가 **빈 리스트**(0개)
- 각 폴드에서 (i) 거래일 수, (ii) 포지션 발생률, (iii) 평균 노출이 **사전 하한** 충족
- OOS 성능이 떨어져도 “누수 지표(미래정보 의심)”가 제거되었음을 로그로 입증


---

### 3) **서바이버십/유니버스(미국 Tech+Healthcare 8~14종목) ‘Point-in-time’ 고정**
- [ ] 유니버스를 **포인트-인-타임 구성**(당시 상장/거래 가능 종목만)으로 만들고, delist/merge/spinoff를 반영
- [ ] “종목 선택 로직”이 미래 시가총액/현재 지수편입/현재 GICS를 참조하지 않도록 차단
- [ ] 결과 산출물에 “해당 기간 실제 거래된 종목 리스트(8~14)”를 스냅샷으로 저장

**(a) 왜 필요한지**
- Tech+Healthcare 집중 전략은 종목 바스켓이 핵심인데, survivorship가 섞이면 OOS가 “안 움직이거나” “과대평가”로 고정되는 경우가 많음
- 현재 로그 체계가 약해 실제로 8~14가 유지되는지 확인 불가

**(b) 위험/부작용**
- 데이터 소스/매핑(티커 변경 등) 정합성 작업이 필요
- 과거에 “있던 성과”가 줄어들 수 있음(정상)

**(c) 최소 실험(2~3개)**
- E3(포인트-인-타임 유니버스) + E4(비용 포함 시 생존 여부) 결합
- E3 + E2(폴드별 유니버스 변동이 폴드 퇴행 유발 여부 확인)

**(d) PASS 조건**
- 모든 평가 구간에서 “실제 거래 가능 종목 8~14 유지” (예외 발생 시 명시적 fallback 규칙 작동)
- delist 이벤트가 있으면 PnL/포지션 청산이 룰대로 처리되며, 누락 데이터로 조용히 0이 되지 않음


---

### 4) **비용/체결 현실화(턴오버/슬리피지/스프레드) + 비용 미반영 차단**
- [ ] 비용 모델을 “0”으로 두는 실험을 금지(최소 수수료+슬리피지 하한)
- [ ] `rebalance` 단위로 **턴오버, 체결가격, ADV 대비 주문비율, 슬리피지**를 기록
- [ ] 비용 포함/제외 성과를 반드시 동시에 출력(차이가 지나치게 크면 경고)

**(a) 왜 필요한지**
- “성능이 안 움직임”의 또 다른 흔한 원인: 실제로는 턴오버가 과도하거나(비용으로 상쇄) 혹은 거래가 거의 없어(비용도 영향 없음) 신호가 무력
- 현재 `rebalance` 로그 로딩 실패로 비용/턴오버를 검증 불가

**(b) 위험/부작용**
- 성과 급락 가능(정상적으로 현실화된 결과)
- 과도한 비용 가정은 전략을 불필요하게 죽일 수 있어 **스윕 실험**이 필요

**(c) 최소 실험(2~3개)**
- E4(비용 모델 스윕: low/base/high) + E1(리밸런스 로그 표준화)
- E4 + E5(레짐별로 거래 빈도/비용 민감도 다른지 분해)

**(d) PASS 조건**
- Net 성과가 Gross 대비 과도하게 붕괴하지 않고(사전 정의한 손실 한도 내), 턴오버가 상한 이내
- 리밸런스 로그로 “비용이 어디서 발생했는지” 설명 가능(거래 횟수/사이즈/슬리피지 분해)


---

### 5) **노출/리스크 게이팅(레짐 기반)으로 ‘노출 0~0.84’ 비정상/불안정 제어**
- [ ] 포지션 수(8~14), 단일 종목 비중, 섹터(Tech/HC) 내부 비중 상한을 하드코딩 게이트로 추가
- [ ] ETF는 매매 금지(관측만): `XLK/SMH`(Tech/반도체), `XLV/IBB/XBI`(Healthcare/바이오)로 레짐을 태깅
- [ ] 레짐별(리스크온/오프, 변동성 급등) 기대 노출 범위를 정의하고 벗어나면 자동 감산/중지

**(a) 왜 필요한지**
- exposure가 0까지 떨어지는 구간이 많으면 “전략이 사실상 꺼져서 성능이 안 움직이는” 상태가 발생
- 반대로 0.84까지 치솟는 구간은 비용/드로우다운을 악화시키며, MDD가 None인 현 상태에선 특히 위험

**(b) 위험/부작용**
- 너무 강한 게이트는 수익 기회를 제거
- 레짐 지표가 과적합 신호가 되지 않도록 “관측용”으로 제한하고 단순 규칙으로만 사용

**(c) 최소 실험(2~3개)**
- E5(레짐 태그 + 노출 클램프/감산) + E2(폴드 안정성)
- E5 + E4(레짐별 비용/턴오버 민감도 체크)

**(d) PASS 조건**
- 레짐별 노출이 목표 범위에 들어오고(예: risk-off에서 자동 감산), 급격한 노출 스파이크 감소
- OOS 분포에서 `oos_min` 악화가 완화되거나, 최소한 tail-risk 지표(최악 구간)가 개선

## 48시간 자동 루프용 “실행 가능한 Patch/실험” 패키지 (총 5개로 제한)

아래 5개만 돌리고, 각 TOP5 우선순위는 이 5개를 조합해 커버하도록 고정.

### **E1) 아티팩트/로그 스키마 강제 + 종료 검증 게이트**
1) **실험 정의**
- 출력 스키마: `champion.json`에 `file, lane_hash, run_hash, worst_mdd, exposure_min/max, fold_health, universe_snapshot_path, rebalance_log_path` 필수
- `rebalance.jsonl` 표준 생성(각 리밸런스 시점: weights, trades, turnover, est_cost, fill_px)
2) **게이트**
- 필수 파일/필드 누락 시 즉시 FAIL
- 동일 seed 재실행 시 핵심 지표 변동이 허용 오차 초과 시 FAIL
3) **기대 관측치**
- “무델타” 원인이 로그 결손인지/전략 문제인지 즉시 분리 가능
- `rebalance_pinpoint` 툴이 에러 없이 동작

---

### **E2) Purged+Embargo 시계열 CV + 폴드 헬스체크(퇴행 폴드 제거)**
1) **실험 정의**
- Purged KFold + Embargo(고정값) 적용
- 폴드별: 샘플 수, 거래일 수, 포지션 발생률, 평균/분산 노출 기록
2) **게이트**
- 퇴행 폴드 존재 시 FAIL
- 폴드별 거래일/포지션 발생률 하한 미달 시 FAIL
3) **기대 관측치**
- 누수 제거 시 OOS 평균이 내려가도 분산/안정성이 개선
- “성능이 안 움직임”이 폴드 퇴행 때문인지 즉시 확인

---

### **E3) Point-in-time 유니버스(Tech+Healthcare 8~14) + delist/CA 처리**
1) **실험 정의**
- 유니버스 생성에 미래 정보 금지(현재 편입/현재 GICS/현재 시총 참조 차단)
- delist/merge/spinoff 발생 시 포지션 처리 규칙 명시
2) **게이트**
- 기간 전체에서 실제 거래 가능 종목 수 8~14 유지(예외는 룰 기반 fallback만 허용)
- 유니버스가 평가 구간 도중 “조용히 비거나 고정”되면 FAIL
3) **기대 관측치**
- 성과가 현실적으로 재조정(대개 하방), 대신 신뢰도 상승
- 종목 바스켓이 레짐/기간에 따라 어떻게 바뀌는지 투명화

---

### **E4) 비용/체결 모델 스윕(LOW/BASE/HIGH) + 턴오버 상한**
1) **실험 정의**
- 수수료+슬리피지(스프레드/ADV 기반) 3단계 스윕
- 턴오버 상한(예: 일/주 단위)을 두고 초과 시 페널티 또는 거래 축소
2) **게이트**
- Net/Gross 괴리가 비정상적으로 크면 FAIL(비용 민감도 과도)
- 턴오버 상한 초과 빈도 임계 초과 시 FAIL
3) **기대 관측치**
- “원래 성과가 비용으로 소멸인지” vs “거래 자체가 거의 없는지” 분해 가능
- 비용 현실화 후에도 살아남는 설정을 빠르게 선별

---

### **E5) 레짐 태깅(ETF 관측만) + 노출 클램프/리스크 감산**
1) **실험 정의**
- 관측 ETF: XLK/SMH, XLV/IBB/XBI (매매 금지, 지표만)
- 레짐(예: 추세/변동성 급등/드로우다운)별로 목표 노출 범위 정의 후 클램프
- 단일 종목 최대 비중, 포지션 수 8~14 강제
2) **게이트**
- 레짐별 노출이 정의 범위를 지속 위반하면 FAIL
- 노출 0 구간이 과도(전략 “꺼짐”)하면 FAIL
3) **기대 관측치**
- tail-risk 완화(oos_min/최악 구간 개선) 또는 변동성 감소
- “노출이 요동쳐서 성능이 고정”되는 현상 감소

## 성능이 안 움직일 때(무델타) 원인 분해 아이디어 — 트리거/적용/노출/비용/레짐

아래 순서대로 **로그로 증명**하면서 원인을 한 단계씩 제거(48시간 루프에 맞춘 고정 디버그 루틴).

### A. Trigger(신호 발생) 문제
- [ ] 신호 발생률(일자 대비 신호 발생 일수) 기록
- [ ] 상위/하위 신호 값 분포가 기간별로 붕괴(거의 상수)했는지 점검
- [ ] 입력 피처의 결측/클리핑/정규화가 신호를 0으로 만들었는지 확인  
**관측 포인트:** “신호는 움직이는데 성과가 고정” vs “신호 자체가 안 움직임”

### B. Apply(룰 적용/필터) 문제
- [ ] 리스크 필터/거래 제한이 **대부분의 거래를 차단**하는지(차단 사유 카운트) 기록
- [ ] 리밸런스 일정/거래 가능 조건(가격, ADV, 거래정지)이 신호를 무력화하는지 점검  
**관측 포인트:** 차단 사유 TOP3가 전체의 80% 이상이면 룰이 과도하거나 데이터가 깨진 것

### C. Exposure(노출/포지션 구성) 문제
- [ ] 일별 총 노출, 종목 수(항상 8~14인지), 단일 종목 최대 비중, 섹터 내부 편중 기록
- [ ] 노출이 0에 붙어있는 기간(전략 OFF)이 긴지 확인  
**관측 포인트:** OOS가 “안 움직이는” 가장 흔한 형태가 “노출 0 장기화”

### D. Cost(비용/턴오버) 문제
- [ ] Gross vs Net, 비용 구성(수수료/슬리피지)과 턴오버의 상관 기록
- [ ] 특정 이벤트(리밸런스 직후)에서만 비용이 폭발하는지 pinpoint  
**관측 포인트:** Net이 고정/악화인데 Gross는 괜찮으면 비용/체결 모델 또는 턴오버가 원인

### E. Regime(시장 레짐 불일치) 문제
- [ ] 관측 ETF로 레짐 태깅 후, 레짐별 성과/노출/거래빈도 분해
- [ ] Tech(예: XLK/SMH)와 Healthcare(예: XLV/IBB/XBI) 레짐이 엇갈릴 때 바스켓이 흔들리는지 확인  
**관측 포인트:** 특정 레짐에서만 성과가 0 근처로 수렴하면 “조건부 전략”인데 조건 인식/게이트가 없음

### 즉시 적용할 “무델타 전용 게이트”(권장)
- [ ] **거래 발생률 게이트**: 폴드/전체 기간에서 거래일 비중 하한
- [ ] **노출 하한 게이트**: 평균 노출이 너무 낮으면 FAIL(전략 꺼짐 방지)
- [ ] **비용 민감도 게이트**: low/base/high 비용에서 결과 순서가 비상식이면 FAIL(모델/로그 오류 가능)
- [ ] **폴드 퇴행 게이트**: degenerate fold 1개라도 있으면 FAIL

이 TOP5 + E1~E5만 48시간 루프에 올리면, 현재 상태에서 가장 위험한 순서(운영/누수/서바이버십/비용/노출)를 먼저 닫으면서 “왜 성능이 안 움직이는지”를 로그 기반으로 강제 분해할 수 있음.
