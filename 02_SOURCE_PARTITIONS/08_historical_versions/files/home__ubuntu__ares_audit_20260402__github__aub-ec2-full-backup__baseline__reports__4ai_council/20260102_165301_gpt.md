## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — 명령형 체크리스트

### 1) **누수·서바이버십·PIT(Point-in-time) 데이터 무결성 가드레일 우선 구축**
- **왜 필요한지**
  - OOS가 “안 움직이거나” 비정상적으로 유지되는 가장 흔한 원인이 **룩어헤드/리밸런싱 시점 불일치/서바이버십/분할·배당 조정 누락**임.
  - Tech+Healthcare(US) 소수 종목(8~14)일수록 **단일 이벤트/상장폐지/인덱스 편입 효과**에 과적합되기 쉬움.
- **위험/부작용**
  - PIT/상장폐지 반영 후 성능이 크게 하락(“진실의 성능”)할 수 있음.
  - 데이터 재구축으로 실험 재현성이 일시적으로 흔들릴 수 있음(해시/캐시 무효화 필요).
- **연결 최소 실험(공유 실험 사용)**
  - **E1 (PIT+서바이버십 재구축 감사 런)**  
  - **E2 (누수 센티넬: 시프트/퍼뮤테이션 테스트)**
- **PASS 조건**
  - (필수) **E2에서**: `feature +1 bar shift` 또는 `label permutation` 시 OOS가 **0 근처(또는 통계적으로 무의미)**로 붕괴.
  - (필수) **E1에서**: 상장폐지/합병/심볼변경/분할·배당 조정/거래정지 구간이 **명시적으로 처리**되었고, 학습·거래 시점 `asof` 정렬이 로그로 증명.
  - (권장) PIT 적용 후 성능 하락이 있더라도 **폴드별 분산/극단치가 감소**.

---

### 2) **운영 리스크 제거: 리밸런스/트레이드 로그·메타데이터 파이프라인 즉시 복구**
- **왜 필요한지**
  - 현재 `rebalance_pinpoint`가 **입력 로그를 못 읽고 종료**(base-log path 오류 + csv/json 파싱 실패).  
  - `lane_hash/run_hash`가 None → **재현/원인추적/회귀방지 불가**.  
  - “성능이 안 움직임”을 진단하려면 **언제/무엇을/얼마나 거래했는지**가 1순위 증거.
- **위험/부작용**
  - 로깅 추가로 I/O 비용 증가(하지만 48시간 루프 운영 안정성이 이득).
  - 스키마 변경 시 기존 리포트 도구가 깨질 수 있음(버전 필드로 완충 필요).
- **연결 최소 실험(공유 실험 사용)**
  - **E5 (로깅/메타데이터 패치 + 재실행)**
  - **E4 (비용 포함 백테스트)** — 로깅이 있어야 비용/턴오버 검증 가능
- **PASS 조건**
  - (필수) 모든 실행이 `run_hash/lane_hash/data_hash/code_git_sha/config_hash`를 남김.
  - (필수) `rebalance.csv` 또는 표준 `rebalance.jsonl`이 생성되고 `aub_rebalance_pinpoint.py`가 **에러 없이 리포트 생성**.
  - (필수) 각 리밸런스에 대해 `target_weights / filled_weights / fills / turnover / est_slippage / fees`가 기록됨.

---

### 3) **과최적화/분할 붕괴(=degenerate folds) 제거: CV·폴드 생성 로직 교정**
- **왜 필요한지**
  - `degenerate_folds: [1, 2, 3, 8]`는 **폴드 데이터 부족/클래스 단일화/노출 0/리밸런스 없음** 등 구조적 문제 신호.
  - 폴드가 붕괴하면 평균 OOS가 “안 움직이거나” 허상으로 고정됨.
- **위험/부작용**
  - 더 엄격한 워크포워드·퍼지드 CV 적용 시 성능 하락 가능(하지만 과최적화 제거가 목적).
  - 실험 시간이 증가할 수 있음(48시간 루프에서 폴드 수/기간 최적화 필요).
- **연결 최소 실험(공유 실험 사용)**
  - **E3 (Purged walk-forward CV + embargo + min-fold-size)**
  - **E2 (누수 센티넬)** — CV가 고쳐졌는지 간접 검증
- **PASS 조건**
  - (필수) `degenerate_folds == []` (최소 폴드 기준 충족, 폴드별 샘플/거래 수가 0이 아님)
  - (필수) 폴드별 OOS 분포가 극단값에 끌리지 않고 **중앙값/사분위**가 안정화.
  - (권장) 워크포워드 구간에서 **턴오버/노출/수익이 동시에 기록**되고 재현 가능.

---

### 4) **비용 미반영 제거: 슬리피지/스프레드/임팩트/수수료/차입(필요시) 포함**
- **왜 필요한지**
  - Tech/Healthcare는 이벤트 드리븐 갭·볼 급등이 잦아 **비용/임팩트 미반영 시 성능이 “멈춘 듯” 보이거나 허상**이 됨.
  - `exposure_max ~0.84`인데도 성능이 정체라면 **실거래 비용/리밸런스 빈도/포지션 캡**이 원인일 수 있음.
- **위험/부작용**
  - 비용 모델이 과도하면 거래가 지나치게 줄어 “0 노출 전략”이 될 수 있음(게이트로 방지).
  - 데이터(스프레드/ADV) 품질이 낮으면 비용이 과대/과소 추정될 수 있음.
- **연결 최소 실험(공유 실험 사용)**
  - **E4 (비용 포함 백테스트 + 유동성 캡 + turnover 리포트)**
  - **E5 (로깅 패치)** — 비용 분해 로그가 필요
- **PASS 조건**
  - (필수) 총 PnL이 `gross`와 `net`으로 분리되고, `net = gross - slippage - fees - borrow`가 로그로 검증.
  - (필수) 포지션 사이징이 **ADV 기반 캡(예: 일 거래량의 x% 이하)**을 준수.
  - (권장) 비용 포함 후에도 OOS가 완전 붕괴하지 않고, **거래 빈도/턴오버가 합리 범위**(전략 의도와 일치).

---

### 5) **전략 운영형 제약 고정: US Tech+Healthcare 8~14 종목, 노출·리밸런스·리스크 게이트 명문화**
- **왜 필요한지**
  - “미국주식 only, Tech+Healthcare 중심, 8~14 종목”을 **코드로 강제**하지 않으면 실험마다 유니버스가 흔들려 비교 불가.
  - 노출이 0~0.84로 널뛰면 “성능이 안 움직임”의 원인이 **신호가 아니라 포트폴리오 게이트/리밸런스 조건**일 수 있음.
- **위험/부작용**
  - 제약이 과하면 알파를 못 쓰고 성능 저하 가능(하지만 48시간 자동 루프에선 일관성이 우선).
  - 특정 8~14 종목 고정은 집중 리스크(단, 섹터 내 분산/상한으로 완화).
- **연결 최소 실험(공유 실험 사용)**
  - **E4 (비용 포함 + 제약 포함 시뮬)** — 제약으로 인한 net 성능/턴오버 확인
  - **E5 (로깅 패치)** — “왜 노출이 0이 됐는지” 설명 가능해야 함
- **PASS 조건**
  - (필수) 유니버스가 **항상 8~14**로 유지되고, 모든 티커가 US 상장 + Tech/Healthcare로 필터링됨(하드 체크).
  - (필수) 노출 게이트(예: 신호 약함/비용 과다/리밸런스 불가)는 **사유 코드(reason code)**로 로깅.
  - (권장) 최대 단일 종목 비중/섹터 비중/일간 리밸런스 한도(턴오버 상한)가 일관 적용.

## 48시간 자동 루프용 “실행 가능한” Patch/실험 5개 (3~5 제한 준수)

아래 5개만 돌리고, 나머지는 **이 5개의 로그/결과로** 원인 분해까지 끝내도록 구성.

### **E1 — PIT+서바이버십 재구축 감사 런**
1) **실험 정의**
   - 데이터 로더에 `asof join` 강제, corporate actions(분할/배당) 반영, delisting/merge 처리.
   - 유니버스 필터(US + Tech/Healthcare)와 8~14 구성 규칙을 데이터 단계에서 고정.
2) **게이트**
   - 학습/예측 시각별 “사용 가능 데이터 타임스탬프” 감사 로그 출력(샘플 100건).
   - delisted 심볼이 학습엔 존재해도 미래 가격 참조가 없도록 차단.
3) **기대 관측치**
   - 과거 대비 OOS가 하락할 수 있으나, 폴드 편차가 줄고 극단 폴드가 정상화될 가능성.

---

### **E2 — 누수 센티넬(Leakage Sentinel)**
1) **실험 정의**
   - (a) 모든 feature를 **+1 bar 시프트**한 모델 성능 측정  
   - (b) 라벨 **퍼뮤테이션** 성능 측정
2) **게이트**
   - (a)(b) 중 하나라도 OOS가 유의미하게 높으면 즉시 실패로 처리하고 배포 금지.
3) **기대 관측치**
   - 정상이라면 OOS ~ 0(또는 샤프/수익률이 무의미), 거래도 랜덤 수준.

---

### **E3 — Purged Walk-forward CV(+embargo)로 폴드 붕괴 제거**
1) **실험 정의**
   - 시간 누수 방지: purge window + embargo 적용.
   - 폴드별 최소 샘플/최소 거래 수 조건(min-fold-size, min-trades) 강제.
2) **게이트**
   - `degenerate_folds == []`
   - 폴드별 거래 수가 0인 폴드가 없을 것.
3) **기대 관측치**
   - 평균 OOS는 낮아질 수 있으나, 폴드 안정성/재현성이 증가.

---

### **E4 — 비용 포함(Net) 백테스트 + 유동성/턴오버 캡**
1) **실험 정의**
   - slippage(스프레드/변동성/ADV 기반), 수수료, (필요 시) 차입비용을 net에 반영.
   - 포지션/주문 크기: ADV 대비 상한, 일일 turnover 상한.
2) **게이트**
   - `net` 성능/리스크 지표 생성 + 비용 항목 분해 로그 필수.
   - 제약으로 인해 노출이 장기간 0이면 실패(“전략이 아니라 필터”가 됨).
3) **기대 관측치**
   - gross→net 감소가 관측되며, 감소의 대부분이 turnover/슬리피지에서 발생하는지 확인 가능.

---

### **E5 — 로깅/메타데이터 패치(리밸런스 핀포인트 복구)**
1) **실험 정의**
   - `--base-log` 경로를 실제 파일로 교정(문자열 그대로 들어가는 버그 제거).
   - `rebalance.jsonl` 표준 스키마 고정 + `run_hash/lane_hash` 필수 기록.
2) **게이트**
   - `aub_rebalance_pinpoint.py`가 base/cand 모두 리포트 생성 성공.
   - 실행 1회만으로 “언제/왜/얼마나 거래했는지”가 재구성 가능.
3) **기대 관측치**
   - “성능 정체”의 원인이 **거래 미발생/노출 0/수수료 과다/리밸런스 조건 불일치** 중 무엇인지 1회 실행으로 좁혀짐.

## 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 실행 체크리스트

### A) 트리거(신호 생성) 문제
- **체크**: 신호 분포가 시간에 따라 붕괴(표준편차 0에 수렴) / 특정 구간 NaN 급증
- **증거 로그**: 날짜별 signal mean/std, NaN rate, 상위/하위 분위 포지션 수
- **즉시 판정**: 신호 분산이 폴드/기간별로 “거의 0”이면 전략이 아니라 상수 모델

### B) 적용(포트 구성/리밸런스 규칙) 문제
- **체크**: 신호는 있는데 주문이 안 나감(리밸런스 조건/최소변경폭/정수주 제약)
- **증거 로그**: “주문 스킵 reason code” 집계(예: min_trade_notional, turnover_cap, liquidity_cap, embargo)
- **즉시 판정**: 스킵 이유 상위 1~2개가 전체의 80%면 규칙이 과도하거나 버그

### C) 노출(Exposure) 문제
- **체크**: `exposure_min=0` 구간이 길어지거나, max가 특정 상한에 계속 붙음
- **증거 로그**: 일자별 gross/net exposure, 포지션 수, 상위 비중 종목
- **즉시 판정**: 노출이 대부분 0이면 “모델 성능”이 아니라 “필터 통과율” 문제

### D) 비용(슬리피지/수수료/임팩트) 문제
- **체크**: gross는 괜찮은데 net이 0 근처로 고정
- **증거 로그**: turnover, slippage, spread proxy, ADV 대비 주문비율
- **즉시 판정**: net 손실의 대부분이 slippage/turnover면 리밸런스 빈도/캡 조정이 핵심

### E) 레짐(시장 국면) 문제
- **체크**: Tech/Healthcare 레짐(금리·리스크온/오프)에서만 동작
- **증거 로그(ETF는 관측지표만)**: QQQ/XLK/XLV/IEF(또는 10Y proxy) 구간별 성능 태깅, VIX 구간 태깅
- **즉시 판정**: 특정 레짐에서만 일관되게 성능이 나오면, 레짐 게이트(거래 축소/헤지)는 “전략”이 아니라 “운영 안전장치”로 분리 구현

---

### 즉시 실행 순서(48시간 루프)
1) **E5 먼저 실행**(로그/리밸런스 핀포인트 복구 없이는 나머지 결과 해석 불가)  
2) **E2 실행**(누수면 즉시 중단하고 데이터/시점부터 다시)  
3) **E1 실행**(PIT/서바이버십 고정)  
4) **E3 실행**(degenerate folds 제거)  
5) **E4 실행**(net 성능/비용 분해로 운영 가능성 판정)

이 5개 결과로 “정체”의 원인을 **누수 → 폴드 → 거래 미발생/노출 → 비용 → 레짐** 순서로 단일 경로로 좁혀서, 다음 사이클에 불필요한 케이스 확장을 막도록 설계하면 됨.
