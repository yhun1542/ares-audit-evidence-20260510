## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — “명령형 체크리스트”
우선순위 기준: **누수 → 과최적화 → 서바이버십 → 비용 미반영 → 운영 리스크** 순으로 먼저 깨고, 그 다음에 성능 개선.

---

# 1) (최우선) 백테스트 무결성: 누수/라벨 정렬/재현성 하드 게이트 추가
### (a) 왜 필요한지
- 현재 Champion에 **`worst_mdd: None`**, **`file:` 비어있음**, **Next Commands 공백** → 지표/아티팩트가 “완주”하지 않아도 챔피언이 될 수 있는 상태(운영 리스크 + 평가 누락).
- OOS 평균이 높아도(1.88) **OOS min 0.43**이면 누수/정렬 오류가 숨겨진 채 통과했을 가능성을 먼저 배제해야 함.

### (b) 위험/부작용
- 엄격 게이트로 인해 당장 통과 모델이 줄어들고 “성능이 떨어져 보이는” 구간이 발생할 수 있음(정상).
- 런타임 증가(추가 검증/리포트 생성).

### (c) 최소 실험 2~3개 (48시간 자동 루프)
**실험 1: Purged/Embargo Walk-Forward 강제**
- (1) 실험 정의: 모든 CV/OOS 분할에 **purge window + embargo**(예: 5~20 거래일 grid 중 1개 고정) 강제, fold 간 feature/label overlap 차단.
- (2) 게이트:  
  - fold별 샘플 타임스탬프 중복 0  
  - embargo 위반 0  
  - degenerate_folds 발생 시 즉시 FAIL
- (3) 기대 관측치:  
  - 누수가 있었다면 OOS가 급락(“나쁜 소식”이 좋은 신호)  
  - 누수가 없으면 OOS 평균은 일부 하락하더라도 분산/최저치(OOS min)가 안정화

**실험 2: “Shift-1/Shift+1” 라벨/피처 정렬 스모크 테스트**
- (1) 실험 정의: 동일 파이프라인에서 **feature를 1일 미래로 당기기(의도적 누수)** / **1일 과거로 밀기** 2버전 실행.
- (2) 게이트:  
  - 의도적 누수(Shift 미래) 성능이 **비정상적으로 급등**하면 현재도 누수 가능성↑ → FAIL 처리(원인 찾기 전까지 배포/챔피언 금지)  
  - 과거로 밀기 성능은 급락이 정상(예측력 상실)
- (3) 기대 관측치:  
  - “누수 버전만 급등” 패턴이면, 현재 파이프라인의 timestamp alignment/리밸런싱 cut-off를 바로 조사 타겟으로 확정

**실험 3: 결과 아티팩트 필수화(메트릭 Null 금지)**
- (1) 실험 정의: run 종료 시 **worst_mdd, turnover, cost, slippage, exposure bounds, universe snapshot hash** 필수 산출/저장. 하나라도 None이면 run 전체 FAIL.
- (2) 게이트: `None` 메트릭 0, file path 비어있음 0
- (3) 기대 관측치:  
  - “챔피언이 되려면 최소한의 평가가 끝나야 함”이 보장되어 운영 사고/착시 제거

**(d) PASS 조건**
- purge/embargo 통과 + 정렬 스모크 테스트에서 누수 의심 없음 + 핵심 메트릭 None=0  
- 그리고 **OOS min이 구조적으로 개선(예: 기존 0.43 대비 상향/변동성 축소)** 되는 방향이면 우선 통과

# 2) 서바이버십/유니버스 고정: “Tech+Healthcare 8~14”를 OOS에서 동일하게 재구성
### (a) 왜 필요한지
- “미국주식 only, Tech+Healthcare, 8~14개” 제약에서 **유니버스 선정 자체가 누수/서바이버십의 가장 흔한 진입점**.
- 예: 현재 시점의 시총/섹터 분류로 과거를 재구성하면 서바이버십 발생.

### (b) 위험/부작용
- 유니버스가 더 거칠어져 단기 성능 하락 가능.
- 데이터 소스(섹터/상장폐지/합병) 보강 필요 시 구현 비용 증가.

### (c) 최소 실험 2~3개 (48시간 자동 루프)
**실험 1: “As-of Date” 유니버스 스냅샷**
- (1) 실험 정의: 매 리밸런스 날짜 t에 대해, **t 시점에 존재/거래가능**한 종목만으로 유니버스를 구성(상장폐지/합병 제거 포함). 스냅샷 hash 저장.
- (2) 게이트:  
  - OOS 구간 유니버스가 미래정보(현재 구성)를 참조한 흔적(일치율 과도) 탐지 시 FAIL  
  - 스냅샷 hash 미저장 시 FAIL
- (3) 기대 관측치:  
  - 서바이버십이 있었으면 OOS가 악화되나, min/드로우다운 프로파일이 현실적으로 변함

**실험 2: 섹터 분류 “as-of” 강제 + Tech/Healthcare 고정 바스켓**
- (1) 실험 정의: GICS/ICS 등 섹터 분류도 as-of로 동기화. 유니버스는 **Tech+Healthcare 내 상위 유동성/시총 규칙**으로 8~14 종목 고정(리밸런스 시에만 변경).
- (2) 게이트:  
  - 리밸런스 외 날짜에 구성 변경 0  
  - 8~14 범위 위반 0
- (3) 기대 관측치:  
  - “구성 흔들림(우발적 종목 교체)”이 줄면서 turnover/비용 추정이 안정화

**(d) PASS 조건**
- OOS에서 유니버스 스냅샷 기반으로도 성능이 유지(혹은 소폭 하락하더라도) + 성능 분산/최저치 개선 + 규칙 위반 0

# 3) 비용/슬리피지/회전율을 “하드 페널티”로 모델 선택에 반영
### (a) 왜 필요한지
- exposure가 **0.47~0.84**로 높고, 8~14개 운용이면 **회전율 증가 시 비용이 성과를 쉽게 잠식**.
- 비용을 나중에 “리포트로만” 보면 과최적화가 그대로 배포됨.

### (b) 위험/부작용
- 비용 모델이 과도하면 유의미한 알파까지 제거(보수 과대).
- 슬리피지 파라미터 튜닝이 필요.

### (c) 최소 실험 2~3개 (48시간 자동 루프)
**실험 1: 비용 포함 목적함수로 챔피언 재선정**
- (1) 실험 정의: 스코어를 `net_metric = gross_metric - λ*turnover - cost_bps` 형태로 고정(λ는 1개 값만 먼저). 거래비용(커미션+스프레드+슬리피지)을 bps로 반영.
- (2) 게이트:  
  - net 기준으로만 챔피언 선정  
  - turnover/거래횟수/체결가정 누락 시 FAIL
- (3) 기대 관측치:  
  - gross는 떨어져도 net이 안정적이면 “실전 적합” 방향  
  - OOS min이 특히 개선되는 경향(비용이 tail을 깎는 경우 많음)

**실험 2: 슬리피지 스트레스(2배/3배) 내성 테스트**
- (1) 실험 정의: 슬리피지 bps를 기본/2배/3배 3점만 테스트(케이스 폭발 금지).
- (2) 게이트: 3배에서도 net 성과가 임계치 아래로 붕괴하면 FAIL
- (3) 기대 관측치:  
  - 취약 전략은 슬리피지에 선형 이상으로 무너짐 → 즉시 배제 가능

**(d) PASS 조건**
- 비용 포함 net 기준 OOS가 유지되고, 슬리피지 2~3배에서도 “형태가 유지”(붕괴/부호전환 없음)

# 4) 노출(Exposure)·리스크 컨트롤: “최저치(OOS min) 방어” 우선
### (a) 왜 필요한지
- 현재 exposure 최대가 0.84로 꽤 높고, OOS min이 낮음 → 레짐/하락장에 취약할 수 있음.
- 8~14개 집중 포트폴리오는 한두 종목 이벤트 리스크에 크게 흔들림(헬스케어 특히).

### (b) 위험/부작용
- 과도한 리스크 컷은 알파를 눌러 평균 수익 감소.
- 규칙이 복잡해지면 디버깅/운영 리스크 증가(그래서 단순 규칙만).

### (c) 최소 실험 2~3개 (48시간 자동 루프)
**실험 1: 변동성 타게팅(간단형)**
- (1) 실험 정의: 포트 변동성(예: 20D realized vol)이 목표치를 초과하면 총 노출을 선형 축소. (예: 0.85 cap → vol 높으면 0.55까지)
- (2) 게이트:  
  - 노출 상한/하한 위반 0  
  - 레버리지/마진 사용 0(미국주식 현물 가정이면)
- (3) 기대 관측치:  
  - OOS min 및 드로우다운 지표 개선(특히 이벤트 구간)  
  - 평균은 일부 하락 가능(정상)

**실험 2: 단일 종목 최대비중/섹터 내 상관 방어**
- (1) 실험 정의: 종목별 weight cap(예: 12~15%)과, 상관 급등 시(최근 20D 상관 상위) 동시 보유 제한(아주 단순 룰 1개).
- (2) 게이트: weight cap 위반 0
- (3) 기대 관측치:  
  - “한 종목 악재로 포트 붕괴” 빈도 감소 → OOS min 개선

**(d) PASS 조건**
- OOS min 상승(또는 최소한 하방꼬리 축소) + 비용/turnover 급증 없이 유지

# 5) 운영/자동 루프 안정화: “48시간 무인” 기준의 실패-안전 설계
### (a) 왜 필요한지
- 현재 상태에서 **Next Commands가 비어있고**, 챔피언 아티팩트 경로도 비어있음 → 자동 루프가 멈추거나 “반쪽 결과”로 진행될 위험이 큼.
- 운영 안정화는 성능 개선보다 선행(잘못된 결과를 빠르게 반복하면 손실만 확대).

### (b) 위험/부작용
- 초기엔 로그/아티팩트 저장으로 디스크/비용 증가.
- 실패 조건이 많아져 러닝이 자주 중단될 수 있음(초기에 정상).

### (c) 최소 실험 2~3개 (48시간 자동 루프)
**실험 1: 3단계 파이프라인 상태머신 도입**
- (1) 실험 정의: `DATA_OK → BACKTEST_OK → REPORT_OK → PROMOTE_OK` 상태 전이. 각 단계 산출물(파일/메트릭) 없으면 다음 단계 금지.
- (2) 게이트: 단계별 필수 산출물 누락 시 FAIL + 자동 재시도(1회) 후 중단.
- (3) 기대 관측치:  
  - “왜 멈췄는지”가 로그로 즉시 귀결되고, 잘못된 챔피언 승격 방지

**실험 2: 결정적 재현성(Seed/버전/데이터 hash) 고정**
- (1) 실험 정의: run마다 `code git hash + data snapshot hash + random seed + env`를 리포트 헤더에 강제 기록.
- (2) 게이트: 동일 hash 조합에서 성과가 유의미하게 달라지면 FAIL(비결정성 버그로 분류)
- (3) 기대 관측치:  
  - “성능이 안 움직이는 문제”와 “재현 불가 문제”를 분리 가능

**(d) PASS 조건**
- 48시간 동안 무인 실행에서 FAIL이 나면 원인이 로그로 단번에 분류되고, 반쪽 결과로 승격되는 케이스 0

## 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐)
아래는 **질문 없이** 바로 넣을 수 있는 분해 로깅/리포트 축입니다. 각 축은 “원인이 어디인지”를 1~2번 루프에 좁혀줍니다.

### A) 트리거(리밸런스/신호 발생) 문제
- **리밸런스 발생 횟수**, 신호 발생일 수, 신호가 0인 비율을 일자별로 기록
- “신호는 좋아 보이는데 성능 정체”면: 신호가 실제로는 거의 발동하지 않거나(희소), 발동 시점이 뒤로 밀린 것(컷오프 오류) 가능

### B) 적용(시그널→주문) 문제
- `target_weight` vs `filled_weight` 차이(절대값/분포) 저장  
- 주문이 **항상 cap에 걸리는지**, 라운딩으로 0이 되는지, 체결가가 미래를 쓰는지(OHLC 선택) 점검
- 체결/가격 소스가 바뀌면 성능이 “안 움직이거나” 갑자기 변함

### C) 노출(Exposure) 문제
- 노출이 **항상 비슷한 범위(0.47~0.84)에 고정**이면, 모델 변화가 있어도 포트가 비슷하게 나가서 성능이 정체될 수 있음
- `gross exposure`, `net exposure`, `single-name max weight`, `effective N(분산)`를 리포트에 고정 포함

### D) 비용(거래비용/슬리피지) 문제
- gross 성과는 움직이는데 net이 안 움직이면 비용/회전율이 원인
- turnover와 비용의 곱이 성과를 상쇄하는지 “기여도”로 분해:  
  - `PnL_gross`, `PnL_after_spread`, `PnL_after_slip`, `PnL_net` 단계별 브릿지

### E) 레짐(시장 국면) 문제 — ETF는 “관측지표”로만 사용
- 매일 레짐 태그를 붙여 성과를 분해:  
  - QQQ(Tech), XLV(Healthcare), SPY(시장) **수익률/변동성/추세** 기반으로 3~4개 레짐(상승/하락/고변동/횡보)만
- “평균은 정체인데 min이 나쁨”이면 특정 레짐(예: QQQ 급락+고변동)에서만 깨질 가능성이 큼

## 실행 순서(48시간 루프에 바로 넣기)
1) **Patch 1(누수/무결성 게이트)** 먼저 적용 → 통과하지 못하면 나머지 성능 논의 중단  
2) **Patch 2(유니버스 as-of/서바이버십 제거)** 적용  
3) **Patch 3(비용 포함 목적함수 + 슬리피지 스트레스)** 적용  
4) **Patch 4(노출/리스크 컨트롤 1~2개만)** 적용  
5) **Patch 5(운영 상태머신/아티팩트 필수화)**로 48시간 무인 루프 완결

원칙: 평균 OOS를 더 끌어올리기 전에 **OOS min, MDD, 비용 내성, 재현성**부터 “깨지지 않게” 만드는 게 우선입니다.
