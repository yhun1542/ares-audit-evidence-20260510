# TOP5 제안 (각 제안: 왜/위험/최소 실험/Pass)

아래 5개 제안은 **서로 겹치는 실험을 재사용**해서 “케이스 폭발”을 막습니다.  
총 **유니크 실험 5개(실험팩 E1~E5)** 만 정의하고, 각 제안에서 **2~3개씩 연결**합니다.

---

## 1) (최우선) 데이터 누수/타임스탬프 정합성 “하드 게이트” 추가
### (a) 왜 필요한지
- 성능이 “안 움직이거나(노델타)” 혹은 “과도하게 잘 나오고” 이후 재현이 안 되는 대부분이 **누수/시점 정합성**에서 시작합니다.
- Tech/Healthcare 8~14종 집중 포트폴리오는 **한두 개 피처 누수**만 있어도 OOS가 왜곡됩니다.
- ETF는 매매 제외지만 “관측 지표”로 쓰는 순간 **리드(미래값) 혼입**이 자주 발생합니다(예: 당일 종가로 당일 신호).

### (b) 위험/부작용
- 누수 제거 시 **OOS 평균이 하락**할 수 있습니다(정상).
- 신호 지연(예: 1D lag)으로 **트리거 빈도 감소** → 노출/턴오버 변화.

### (c) 최소 실험 2~3개 (공유 실험팩 사용)
- **E1. 누수 스캐너 + 강제 lag A/B**
  - (실험 정의) 모든 피처를 `asof_ts` 기준으로 재구성하고, ETF 지표/팩터를 **+1D lag** 강제한 버전과 기존 버전을 동일 조건으로 OOS 비교
  - (게이트) `leakage_violations == 0` AND “당일 종가 사용/미래 재무/리밸 당일 종가 체결” 탐지 시 FAIL
  - (기대 관측치) 성능이 큰 폭으로 떨어지면 기존에 누수 가능성↑ / 거의 동일하면 누수 가능성↓
- **E4. Purged/Embargoed Walk-forward CV로 재측정**(아래 4번 제안과 공유)
- **E5. 신호 적용 시점 테스트(트리거-실행 분리)**(아래 5번 제안과 공유)

### (d) PASS 조건
- 누수 위반 0건 + “lag 버전”에서도 성능이 **방향성 유지(순위/샤프가 붕괴하지 않음)**  
- OOS가 낮아져도 OK, 대신 **재현성(폴드 간 분산 감소)**이 개선되면 PASS

---

## 2) (동급 우선) 비용/체결/턴오버를 “실거래급”으로 반영 + 리밸런스 로그 복구
### (a) 왜 필요한지
- 현재 리밸런스 pinpoint가 **로그 로드 실패**(경로에 `'--base-log'` 리터럴이 들어가고, csv/jsonl 파싱도 실패).  
  ⇒ 비용/체결/턴오버가 “보이지 않는 상태”면, 노델타/성능정체의 원인이 **비용인지 신호인지 분해 불가**.
- 집중(8~14종)이라도 리밸이 잦으면 비용이 성과를 먹습니다.

### (b) 위험/부작용
- 비용 반영 후 성능 하락(정상).
- 비용 모델이 과도하면 과소매매로 성능 악화.

### (c) 최소 실험 2~3개 (공유 실험팩 사용)
- **E2. 리밸런스 로깅/핀포인트 파이프라인 패치**
  - (실험 정의) 백테스트 실행 시 `rebalance.jsonl`(원시 체결/주문)과 `rebalance.csv`(일자별 turnover/cost) 강제 생성. `aub_rebalance_pinpoint.py`는 파일 존재/확장자에 따라 자동 선택하도록 수정(잘못된 `'--base-log'` 입력 시 즉시 에러)
  - (게이트) pinpoint 리포트가 “No rebalance data found” 없이 생성되고, turnover/cost가 0이 아니어야 함
  - (기대 관측치) 비용/턴오버가 어느 구간에서 성능을 잠식하는지 “구간별”로 보임
- **E3. 비용 민감도 3점 스윕(낮음/기본/높음)**
  - (실험 정의) 슬리피지/스프레드/임팩트 계수를 3단계로 고정 스윕(예: 0.5x/1x/2x)
  - (게이트) 비용 2x에서도 전략이 **완전 붕괴하지 않으면** 견고성↑
  - (기대 관측치) 노델타 원인이 “비용/턴오버”면 비용↑에서 급격히 악화
- **E5. 턴오버 상한 게이트 + 포지션 유지기간(min hold) 실험**(아래 5번과 공유)

### (d) PASS 조건
- 리밸런스 로그/핀포인트가 정상 생성 + 비용 반영 후에도 **oos_mean이 의미 있게 양(+) 유지** 또는 최소한 **폴드 붕괴/과최적화 징후 감소**

---

## 3) (우선) 서바이버십/유니버스 편향 제거 (Tech+Healthcare 8~14종 제약을 “PIT”로)
### (a) 왜 필요한지
- “미국주식 only, Tech+Healthcare 중심 8~14개”는 유니버스가 좁아서 **서바이버십(상장폐지/편입편출) 편향**이 성과에 직격탄입니다.
- 지금 Champion에서 worst_mdd가 None인 것도, 메트릭 파이프라인 결함 + 데이터 공백 가능성을 시사.

### (b) 위험/부작용
- PIT(시점정합) 유니버스 적용 시 과거 성과가 내려갈 수 있음(정상).
- 데이터 소스에 따라 구현 비용 증가.

### (c) 최소 실험 2~3개 (공유 실험팩 사용)
- **E1. PIT 유니버스 스냅샷 적용 + delisted 포함 여부 A/B**
  - (실험 정의) 각 리밸 날짜에 “그 시점에 거래 가능했던” Tech/Healthcare 유니버스(유동성/시총 하한 포함)를 구성하고, delisted 리턴 처리 포함 버전과 비교
  - (게이트) 리밸 날짜마다 유니버스 크기/섹터 분포가 기록되고, 미래 편입 종목이 과거에 등장하면 FAIL
  - (기대 관측치) 서바이버십 제거 시 성능이 과장되어 있던 구간이 드러남
- **E4. 폴드별 유니버스 안정성 검사(종목 수/결측률/리턴 분포)**
  - (게이트) fold 내 결측률/거래정지 비율이 임계치 초과 시 FAIL

### (d) PASS 조건
- PIT 기반에서 성능이 다소 낮아져도 **폴드 퇴화(degenerate_folds) 감소**, 극단적 outlier 수익 감소, 그리고 worst_mdd가 정상 산출되면 PASS

---

## 4) (필수) 과최적화/폴드 붕괴(degenerate_folds) 제거: Purged Walk-forward + 최소 샘플 게이트
### (a) 왜 필요한지
- 현재 `degenerate_folds: [1,2,3,8]`은 **검증 불능 상태**에 가깝습니다(거래가 거의 없거나 분산 0, 레이블 편향 등).
- 노델타(성능이 안 움직임)는 “개선이 없어서”가 아니라 **평가계가 무너져서** 구분력이 없는 경우가 많습니다.

### (b) 위험/부작용
- 더 엄격한 CV는 성능을 낮출 수 있음(정상).
- 샘플 부족 시 전략 자체가 “거래를 못 하는 전략”으로 판명될 수 있음(그게 목적).

### (c) 최소 실험 2~3개 (공유 실험팩 사용)
- **E4. Purged/Embargoed Walk-forward CV + 최소 거래수 게이트**
  - (실험 정의) 트레이닝/검증 사이에 embargo(예: 5~20영업일)를 두고, fold마다 `min_trades`, `min_days_in_market`, `min_return_variance` 게이트 적용
  - (게이트) degenerate_folds=0 AND 각 fold 거래수/노출일수 임계치 충족 못 하면 FAIL
  - (기대 관측치) 진짜 개선은 fold 전반에 분산되어 나타남. 특정 fold만 급등하면 과최적화 가능성↑
- **E2. 메트릭 산출 강제(worst_mdd None 금지)**
  - (게이트) worst_mdd가 None이면 즉시 FAIL(리포트 생성도 중단)

### (d) PASS 조건
- degenerate_folds=0 + oos_mean이 약간 낮아져도 **fold 분산 감소/재현성 상승**이면 PASS

## 5) (전략/운영 동시) 노출/포지션 제약을 “명시적”으로: 8~14종 유지 + 리스크 게이트 + 레짐(ETF 지표) 관측 기반
### (a) 왜 필요한지
- 현재 노출이 `0.0 ~ 0.8388`로 보이는데, **언제 0이 되는지/왜 0인지**(트리거, 게이트, 데이터 결측) 분해가 안 되면 성능 정체의 원인이 숨습니다.
- 8~14종 제약이 “의도”인데 실제로는 신호 부족/게이트로 인해 3종만 들거나 현금화되면, 전략 정의가 흔들립니다.
- ETF는 매매 금지이므로 **레짐 ‘관측’**으로만 사용: QQQ(테크), XLV(헬스케어), SPY, VIX(가능하면 지수) 같은 지표로 “리스크 온/오프”를 관측.

### (b) 위험/부작용
- 제약이 과하면 알파를 죽임(특히 8~14 강제 충족).
- 레짐 필터가 늦게 반응하면 상승장 수익을 놓칠 수 있음.

### (c) 최소 실험 2~3개 (공유 실험팩 사용)
- **E5. 포지션/노출 게이트 + min hold + 턴오버 상한**
  - (실험 정의)  
    - 보유 종목수: **항상 8~14** (부족하면 현금 비중이 아니라 “대체 후보(동 섹터/동 팩터)”로 채움)  
    - 단일 종목 max weight(예: 12~18%)  
    - min hold(예: 2~5일) 또는 거래 히스테리시스(진입/청산 임계치 분리)  
    - 일/주간 turnover 상한
  - (게이트) 종목수 위반/단일비중 위반/turnover 상한 초과 시 FAIL
  - (기대 관측치) 비용 감소 + 노출의 “0 구간”이 줄어들거나(혹은 0이 되는 명확한 이유가 로그로 남음)
- **E1. ETF 레짐 지표는 반드시 lag 적용 + “관측만” 로그화**
  - (게이트) ETF 데이터가 주문/체결 대상으로 들어가면 FAIL(매매 제외)
  - (기대 관측치) 레짐 구간별 성과 분해가 가능해짐(온/오프에서 히트율 차이 등)

### (d) PASS 조건
- 8~14종 유지가 실제로 지켜지고(로그로 검증), 비용/턴오버가 감소하며, OOS가 “큰 하락 없이” 안정화되면 PASS  
- 특히 **노출 0 구간의 원인이 트리거/게이트/데이터 중 어디인지**가 리포트로 분리되면 PASS

# 성능이 “안 움직일 때(No-Delta)” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래는 **질문 없이 바로 로그/리포트로 뽑아야 하는 분해 축**입니다.

## A) Trigger(신호 발생) 문제
- [ ] **신호 발생률(hit rate)**: 날짜당 “진입 후보 수/스코어 분산/상위-하위 스프레드”를 저장
- [ ] 신호가 대부분 0/상수면 → **피처 정규화/클리핑** 또는 데이터 결측으로 신호가 죽은 것
- [ ] “lag 적용 후” 신호가 사라지면 → 누수 기반 신호였을 가능성

## B) Apply(주문 반영) 문제
- [ ] “리밸런스 결정”과 “체결/포트 반영”을 분리 로그로 저장(결정은 났는데 체결이 0이면 운영 버그)
- [ ] 리밸런스가 생성되는데 포지션이 안 바뀌면 → **게이트(최소 거래단위/제약)**가 막고 있을 확률↑

## C) Exposure(노출/보유종목수) 문제
- [ ] **노출 히스토그램**(exposure=0 빈도, 0.2~0.8 구간 체류)을 리포트에 고정
- [ ] “8~14 보유 강제”인데 실제 보유가 3~5면 → 후보 풀 부족/게이트 과다/유니버스 오류
- [ ] 특정 구간에서만 0 노출이면 → 레짐 필터/리스크오프가 과도하게 작동

## D) Cost(비용/턴오버) 문제
- [ ] turnover 상위 10일과 비용 상위 10일을 찍고 그 날의 신호/레짐/변동성 동시 기록
- [ ] 비용 0.5x~2x에서 성능 기울기가 급하면 → “알파”가 아니라 “마찰”에 지배

## E) Regime(레짐) 문제
- [ ] 레짐별(예: QQQ 모멘텀 상/하, XLV 상대강도 상/하, VIX 상/하)로 **승률/평균수익/드로우다운** 분해
- [ ] 특정 레짐에서만 이기면 → 레짐 필터를 “진입 조건”이 아니라 **노출 스케일링(위험예산)**으로 바꾸는 실험(E5로 흡수)
