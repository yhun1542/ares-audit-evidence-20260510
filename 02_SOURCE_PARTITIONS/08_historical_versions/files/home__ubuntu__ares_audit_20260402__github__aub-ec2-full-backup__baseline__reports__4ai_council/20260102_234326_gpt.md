## 24~48시간 TOP5 우선순위 (코드/아키텍처/전략) — **명령형 체크리스트**
우선순위 기준: **누수/과최적화/서바이버십/비용 미반영/운영 리스크** → 그 다음 성능.

---

# 1) “No-Delta” 근본 원인 제거: **실험 파라미터가 실제로 적용되는지 증명하는 Provenance/Hash 레이어 추가**
### (a) 왜 필요한지
- 현재 상태에 **lane_hash/run_hash=None**, “No-Delta Diagnoser”에서 **9개 실험이 성능 변화 없음** → 가장 흔한 원인:
  - 실험 JSON이 로딩되지만 **실제 모델/시그널에 반영되지 않음**(config merge 무시, 키 이름 불일치, 디폴트로 덮어쓰기)
  - 파라미터가 반영돼도 **학습/리밸런스 단계에서 캐시/아티팩트 재사용**으로 결과가 동일
- 이 상태에서 전략 실험을 계속하면 48시간을 “0변화”로 소모.

### (b) 위험/부작용
- 해시/로그가 늘어 **아티팩트 용량 증가**, 파이프라인이 엄격해져 일시적으로 실패율 증가.
- 기존 “우연히 돌아가던” 실험이 깨질 수 있음(좋은 신호).

### (c) 최소 실험(2~3개 중 **하나만** 우선 실행)
- **E1-1 (권장, 2시간 내): Config Diff + Effective Config Dump**
  - 실행 시점에 “입력 JSON”이 아니라 **실제 런타임에 쓰인 effective_config**를 직렬화 저장.
  - `effective_config_hash`, `data_hash`, `universe_hash`, `signal_hash`를 아티팩트로 남김.
- **E1-2: 강제 파라미터 스윙(Shock Test)**
  - 일부 파라미터를 극단값으로 변경(예: 리밸런스 주기/스케일/헤지비율을 0↔1 수준)했을 때 **트레이드/노출이 바뀌는지** 확인.
- **E1-3: 캐시 무효화 실험**
  - 동일 설정으로 `--no-cache` 또는 run_id salt를 바꿔 **결과 동일성**이 캐시 때문인지 확인.

### (d) PASS 조건 (게이트)
- **게이트 G1**: “실험 파라미터 변경” 시 `effective_config_hash`가 반드시 변경됨.
- **게이트 G2**: Shock Test에서 최소 1개 이상이 변해야 함  
  - (i) 일별 포지션 벡터, (ii) turnover, (iii) exposure_min/max 중 하나라도 유의미하게 변화
- **기대 관측치**: 지금처럼 “OOS 동일”이 아니라, **노출/리밸런스 로그에서 즉시 차이**가 발생.

# 2) 리밸런스/트레이드 로그 복구: **비용·턴오버·MDD를 “관측 가능”하게 만들어 운영 리스크 차단**
### (a) 왜 필요한지
- `aub_rebalance_pinpoint`가 **base-log/cand-log 로딩 실패** → 리밸런스 데이터가 관측되지 않으면:
  - 비용 미반영(슬리피지/수수료)로 과대평가
  - 운영 리스크(거래 폭증, 특정 일자 집중) 탐지가 불가
  - “왜 성능이 안 움직이는지” 분해 불가
- 현재 `worst_mdd=None`도 **계산/로그 파이프라인 결손 가능성** 신호.

### (b) 위험/부작용
- 로그 포맷 표준화 과정에서 기존 리포트/도구 일부가 일시적으로 깨질 수 있음.
- 비용 모델 적용 후 성과가 하락할 수 있음(정상).

### (c) 최소 실험(2~3개 중 **하나만** 우선 실행)
- **E2-1 (권장): Rebalance Log 포맷 단일화 + 파서 폴백**
  - 출력: `rebalance.jsonl` (한 줄=한 이벤트) + `rebalance.parquet`(집계용)
  - 파서 입력: csv/jsonl 둘 다 수용, 파일 미존재 시 “명시적 실패”로 전환(지금처럼 조용히 None 금지)
- **E2-2: 비용 컴포넌트 필드 추가**
  - 이벤트별 `notional`, `shares`, `mid`, `slippage_bps`, `fee`, `borrow`, `impact_proxy` 기록.
- **E2-3: MDD/턴오버/거래일수 자동 산출**
  - `worst_mdd`, `avg_turnover`, `max_single_day_turnover`, `days_traded`를 챔피언 JSON에 고정 필드로 저장.

### (d) PASS 조건 (게이트)
- **게이트 G1**: `aub_rebalance_pinpoint`가 base/cand 모두에서 **0 errors**로 동작.
- **게이트 G2**: 모든 런에서 `worst_mdd`가 None이 아니어야 함.
- **기대 관측치**: “성과는 같은데” **턴오버/비용/리밸런스 빈도 차이**가 명확히 드러남(원인 분해 가능).

# 3) Degenerate folds 제거(누수/검증 붕괴 방지): **Time-series CV 게이트 강제 + 폴드 품질 메트릭**
### (a) 왜 필요한지
- `degenerate_folds: [1,2,3,8]`는 **검증 체계가 붕괴**했음을 의미(데이터 부족/라벨 NaN/동일 구간 반복/누수 등).
- OOS mean이 좋아도 폴드가 무너지면 **과최적화/서바이버십/누수** 가능성이 급상승.

### (b) 위험/부작용
- 데이터/기간 조건을 강화하면 학습 가능한 샘플이 줄어 **단기 성과 하락** 가능.
- 일부 전략은 더 이상 통과 못할 수 있음(오히려 바람직).

### (c) 최소 실험(2~3개 중 **하나만** 우선 실행)
- **E3-1 (권장): Fold 품질 게이트 추가**
  - 폴드별 `n_train`, `n_test`, `label_nonnull_ratio`, `unique_days`, `feature_nan_ratio` 저장.
  - “degenerate” 정의를 명시하고 런을 FAIL 처리.
- **E3-2: Purged/Embargoed CV 적용**
  - 리밸런스/홀딩 기간에 맞춰 **purge + embargo**로 인접 누수 차단.
- **E3-3: 서바이버십 차단 스냅샷**
  - 유니버스/가격/기업행동 데이터가 “현재 구성”을 누수하지 않도록 **시점 스냅샷 해시**를 기록(최소는 universe_hash).

### (d) PASS 조건 (게이트)
- **게이트 G1**: degenerate_folds가 빈 배열([])이거나, 폴드 FAIL 시 런이 중단되어 챔피언 갱신 금지.
- **게이트 G2**: 폴드별 최소 샘플/일수/라벨 비율 기준을 충족.
- **기대 관측치**: OOS 평균이 일시 하락해도 **폴드 분산/최악 성과(oos_min) 안정화**가 나타남.

# 4) 비용/노출/포지션 규율(운영 리스크 우선): **8~14개(Tech+Healthcare) 집중 + 비용 포함 + 노출 상한 고정**
### (a) 왜 필요한지
- 현재 `exposure_max ≈ 0.84`로 들쭉날쭉할 여지가 있고, 비용/턴오버가 관측 불가 상태면 **실전에서 성과 붕괴** 가능.
- 요구 조건: **미국주식 only**, **Tech+Healthcare 중심**, **8~14개 내외**, **ETF 매매 제외** → 이를 “전략 선언”이 아니라 **엔진 규칙**으로 강제해야 함.

### (b) 위험/부작용
- 종목수 제한/섹터 강제 시 분산 감소로 단기 변동성 증가 가능.
- 거래비용 반영 후 성과 하락 가능(정상적인 정직화).

### (c) 최소 실험(2~3개 중 **하나만** 우선 실행)
- **E4-1 (권장): Universe/섹터/종목수 하드 게이트**
  - 거래 가능: US common stock만.
  - 매수/보유 종목수: 8~14 강제.
  - 섹터: Tech+Healthcare 비중 하한(예: 70% 이상)을 규칙으로 강제(분류는 GICS/대체분류).
- **E4-2: 비용 모델 ON(보수적)**
  - 고정 수수료 + 슬리피지(bps) + (숏이면) borrow를 기본으로.
  - 백테스트 리포트에 “gross vs net” 둘 다 출력 강제.
- **E4-3: 노출/레버리지 상한**
  - `gross_exposure_cap`, `net_exposure_cap`을 하드 제한.
  - 상한 위반 시 리밸런스에서 자동 스케일다운.

### (d) PASS 조건 (게이트)
- **게이트 G1**: 어떤 날짜에도 보유 종목수가 8~14를 벗어나지 않음.
- **게이트 G2**: ETF 포지션이 0(관측지표로만 허용).
- **게이트 G3**: net 성과 리포트가 항상 생성되고, `turnover`와 비용이 0/None이 아님.
- **기대 관측치**: gross 성과는 비슷해도 **net 성과/턴오버가 합리적 범위**로 내려오거나, 문제 전략이 즉시 드러남.

# 5) 48시간 자동 루프용 “원인분해 관측 패널” 추가: 트리거/적용/노출/비용/레짐을 매 런 자동 리포트
### (a) 왜 필요한지
- 지금은 “OOS 안 움직임”의 원인이 **(i) 신호 무변화 (ii) 주문/리밸런스 미적용 (iii) 노출 스케일/캡 (iv) 비용 (v) 레짐 미스매치** 중 어디인지 즉시 알 수 없음.
- 48시간 자동 루프에서는 “성능”보다 **진단 가능한 관측치**가 먼저.

### (b) 위험/부작용
- 리포트 생성으로 런타임 증가(대개 경미).
- 지표가 늘어나면 잘못된 최적화 유혹(지표를 목표로 삼는 부작용).

### (c) 최소 실험(2~3개 중 **하나만** 우선 실행)
- **E5-1 (권장): 1페이지 진단 리포트 자동 생성**
  - 매 런마다 아래를 저장(시계열 + 요약):
    - Trigger hit rate(신호 발생 비율)
    - 포지션 변경률/턴오버
    - gross/net 수익 분해(비용 drag)
    - exposure 분포(평균/최대/상한 도달 빈도)
    - 섹터/종목 수 준수 여부
- **E5-2: 레짐 관측(ETF는 지표로만)**
  - QQQ(Tech), XLV(Healthcare), IWM(리스크), TLT(금리), VIX 대용지표(가능하면) 등을 “시장 상태 태그”로만 사용.
  - 태그별 성과/턴오버/히트율을 분해 출력.
- **E5-3: 알람 게이트**
  - “성과 악화”가 아니라 **운영 위험** 알람을 먼저(예: 단일일 turnover 폭발, 상한 반복 도달, 종목수 규칙 위반).

### (d) PASS 조건 (게이트)
- **게이트 G1**: 모든 런에서 진단 리포트가 생성되고, 핵심 필드가 None이 아님.
- **게이트 G2**: “성능 무변화” 상황에서도 최소 1개 이상의 원인 축(트리거/노출/비용/레짐)에서 변동이 관측되거나, 반대로 “완전 무변화=적용 실패”로 자동 판정 가능.
- **기대 관측치**: 다음 번 “No-Delta”가 나오면 즉시 **어느 단계가 고정(frozen)**인지 표시됨.

## 48시간 자동 루프 형태로 묶은 “실행 패치/실험” (3~5개로 제한)
아래 5개를 **그대로 백로그/크론에 태워** 순차 실행(각각 실패 시 다음으로 진행하지 말고 원인 고정).

1. **E1-1 Effective Config Dump + Hash**  
   - 게이트: 해시 변화/노출 변화 확인
2. **E2-1 Rebalance Log 포맷 단일화 + 파서 폴백**  
   - 게이트: pinpoint 0 errors, worst_mdd not None
3. **E3-1 Fold 품질 게이트**  
   - 게이트: degenerate_folds=[] 또는 런 FAIL
4. **E4-1 Universe/섹터/종목수 하드 게이트** (+ ETF 금지)  
   - 게이트: 8~14 유지, ETF 포지션 0
5. **E5-1 1페이지 진단 리포트 자동 생성**  
   - 게이트: 원인축 지표 None 금지

# 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐)
아래 트리는 **질문 없이도** 로그만으로 판정되게 만들어라.

## A. 트리거(신호가 발생했는가?)
- **Trigger hit rate가 거의 0%** → 신호 조건이 너무 빡셈/데이터 결측/필터가 과도
- **항상 100%** → 신호가 상수/버그(정규화 실패, 클리핑, 랭크가 전부 동일)

## B. 적용(신호가 주문으로 반영됐는가?)
- 신호는 변하는데 **포지션 벡터가 동일** → 주문 생성/리밸런스 로직에서 컷(최소 주문단위, 캡, 종목수 규칙, 거래가능 필터)
- 포지션은 변하는데 **체결/비용 로그가 없음** → 로깅 파이프라인 결손(지금 상태와 유사)

## C. 노출(스케일/캡이 성능을 눌렀는가?)
- `exposure_max`가 자주 캡에 붙음 → 예측이 좋아도 상한 때문에 알파가 제한
- 반대로 노출이 계속 낮음(예: 평균 0.1 이하) → 신호 약함/리스크 모델이 과도하게 축소

## D. 비용(거래가 알파를 먹는가?)
- gross는 개선인데 net이 개선 없음 → turnover 과다/슬리피지 과소추정/리밸런스 빈도 과다
- 특정 날짜에 비용 급증 → 리밸런스 집중, 유동성 낮은 종목(US large 위주로 제한 필요)

## E. 레짐(시장 상태에서만 먹히는가?)
- QQQ↑/금리↓/변동성↓ 같은 특정 상태에서만 성과가 남 → 레짐 태그별 성과 테이블 필요
- 레짐이 바뀌면 즉시 무력화 → 트리거를 레짐-조건부로 분기하거나, 노출을 레짐에 따라 조절(단, 먼저 관측부터)

## 즉시 반영(운영 리스크) 고정 규칙 요약
- **ETF는 매매 금지(관측지표로만)**  
- **US stocks only**, **Tech+Healthcare 중심**, **동시 보유 8~14개 강제**  
- **비용/턴오버/MDD 지표가 None이면 런 FAIL**  
- **degenerate fold 발생 시 챔피언 갱신 금지**

위 5개 패치를 48시간 루프로 돌리면, “성능이 안 움직이는 이유”가 **모델 문제가 아니라 파이프라인/적용/로그 문제인지**부터 확정되고, 그 다음에야 전략 실험이 의미를 갖게 된다.
