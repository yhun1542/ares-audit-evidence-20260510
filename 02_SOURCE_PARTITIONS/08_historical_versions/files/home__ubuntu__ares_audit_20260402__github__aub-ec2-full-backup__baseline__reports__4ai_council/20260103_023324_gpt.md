## 0) 즉시 우선 점검(누수/과최적화/서바이버십/비용/운영 리스크) — 명령형 체크리스트
- **(누수) 라벨 시프트/특징 생성/리밸런스 타이밍을 강제 검증하라**
  - 모든 feature에 대해 `max(feature_timestamp) <= decision_timestamp` 자동 어서션을 추가하라.
  - “체결/종가/다음날 시가” 기준이 코드 전역에서 **단일 규약**인지 검사하라(혼재 시 누수/가짜 알파).
- **(과최적화) degenerate fold 원인을 제거하라**
  - `degenerate_folds: [1,2,3,8]`는 평가 파이프라인 신뢰도를 깨는 신호다. 폴드별 표본수/거래수/노출분포/결측률을 리포트로 고정 출력하라.
- **(서바이버십) 유니버스가 포인트-인-타임인지 보증하라**
  - 백테스트 구간에 상장폐지/인수합병/티커변경 포함 여부를 자동 체크하고, 제외 시 실패 처리하라.
- **(비용) 거래비용/슬리피지를 “게이트”로 승격하라**
  - turnover×(bps cost) 민감도(예: 5/10/20bps)에서 OOS가 유지되는지 자동 산출하라.
- **(운영) 리밸런스 로그/런 해시를 반드시 남겨 재현성을 확보하라**
  - 현재 `lane_hash/run_hash: None`, 리밸런스 pinpoint가 “입력 파일 파싱 실패”로 깨져 있다. **실험 자동 루프의 관측 자체가 불능** 상태다.

## 1) TOP5 우선순위 제안(24~48h) — 코드/아키텍처/전략
아래 5개만 먼저 처리하라(케이스 확장 금지). 각 항목은 **실행 가능한 patch + 최소 실험(2~3)** + **PASS 게이트**로 구성했다.

# TOP1) (운영/재현성) Rebalance 로그 포맷 정규화 + run/lane hash 강제 기록
### (a) 왜 필요한지
- `aub_rebalance_pinpoint`가 **CSV/JSONL 파싱 실패** → “성능이 안 움직이는 이유”를 거래 단위로 분해할 수 없다.
- `lane_hash/run_hash None` → 동일 설정 재현/비교 불가. 자동 루프에서 “관측 불가능 = 최적화 불가능”.

### (b) 위험/부작용
- 로그 I/O 증가로 런타임/디스크 사용 증가.
- 포맷 마이그레이션 과정에서 기존 리포트/도구가 깨질 수 있음(버전 태깅 필요).

### (c) 최소 실험 2~3개 (48h 루프용: 실험 정의 / 게이트 / 기대 관측치)
**E1. Rebalance 이벤트 JSONL 표준화**
- 실험 정의: 모든 리밸런스 이벤트를 JSONL로 강제 출력 (`timestamp, universe, target_weights, exec_prices, fills, turnover, costs_bps, pnl_attrib`).
- 게이트: `aub_rebalance_pinpoint.py`가 base/cand 모두에서 **0 에러**, “No rebalance data found” 미발생.
- 기대 관측치: base vs cand 거래 차이가 “종목/시점/비중”으로 diff 가능해짐.

**E2. run_hash/lane_hash 강제 주입 + 설정 스냅샷**
- 실험 정의: config+data_version+code_git_sha를 합쳐 해시 생성 후 결과물/로그 파일명에 포함.
- 게이트: 모든 artifact에 `run_hash` 존재, 동일 입력이면 해시 동일.
- 기대 관측치: “No-delta(성능 변화 없음)”이 실제로 동일 실행인지/관측 누락인지 구분 가능.

**E3. 리포트 파이프라인 계약 테스트(contract test)**
- 실험 정의: 더미 2회 런을 돌려 보고서 생성/파싱이 모두 성공하는지 CI에서 자동 확인.
- 게이트: 리포트 생성 파일(진단/핀포인트) 100% 생성, 파싱 실패 0건.
- 기대 관측치: 다음 48h부터 “관측이 없는 실험”이 사라짐.

**PASS 조건**
- pinpoint 리포트에 최소 `Top trade diffs`, `turnover/cost diffs`, `exposure diffs` 섹션이 채워지고, base/cand 비교가 1회 이상 자동 생성되면 PASS.

# TOP2) (누수/타이밍) Feature/Label 타임라인 어서션 + “결정→체결→평가” 단일 규약 고정
### (a) 왜 필요한지
- OOS min이 음수로 내려가고, fold가 degenerate인 상황에서 **누수는 최우선 배제 대상**.
- 특히 일봉/분봉 혼재, 종가 기반 시그널이 같은 날 체결로 처리되면 쉽게 미래정보가 섞인다.

### (b) 위험/부작용
- 누수 제거 후 성능 급락 가능(하지만 이게 정상).
- 데이터 결측/지연으로 거래 빈도 감소.

### (c) 최소 실험 2~3개
**E1. 타임라인 어서션 모드(Strict)**
- 실험 정의: feature 생성 시점과 decision 시점 비교 어서션을 켜고, 위반 시 런 실패.
- 게이트: 위반 0건(또는 위반 목록이 리포트로 출력되어 수정 루프 진입).
- 기대 관측치: “의심 구간/피처”가 정확히 지목됨.

**E2. 체결 규약 고정: D일 종가로 신호 → D+1 시가 체결**
- 실험 정의: 전체 전략을 “EOD 신호, next-open fill”로 통일.
- 게이트: 룰 변경 전후로 거래 시점이 일관되게 이동(리밸런스 로그에서 확인).
- 기대 관측치: 과도한 당일 승률/급격한 알파가 사라지고, 대신 안정적 분포로 바뀜(정상화).

**E3. 라벨 시프트 감사(audit)**
- 실험 정의: 학습 라벨(예: next-day return)의 시프트가 코드 1곳에서만 정의되도록 통합.
- 게이트: 라벨 정의 함수가 단일 진입점, 중복 정의 0.
- 기대 관측치: 폴드 간 성능 분산 감소(특히 degenerate fold 감소).

**PASS 조건**
- “Strict 어서션 0위반 + next-open 통일” 후에도 OOS mean이 **통계적으로 의미 있게 붕괴하지 않고**(예: 30% 이내 감소) 유지되면 PASS. 붕괴하면 누수 가능성이 컸던 것으로 판단하고 다음 실험은 그 상태를 기준선으로 삼아라.

# TOP3) (서바이버십/유니버스) 포인트-인-타임 Tech+Healthcare 8~14종목 “고정 룰”로 구성
### (a) 왜 필요한지
- “미국주식 only, Tech+Healthcare, 8~14” 제약에서 가장 흔한 함정은 **현재 구성 종목을 과거에도 존재한 것으로 간주**하는 서바이버십.
- 유니버스 변화(상장/편출)와 스플릿/인수 이벤트가 거래 가능성/슬리피지/가격계열을 왜곡한다.

### (b) 위험/부작용
- 사용 가능한 종목 수 감소 → 분산/거래 기회 감소.
- 데이터 소스에 따라 delisted 데이터 비용/접근성 증가.

### (c) 최소 실험 2~3개
**E1. PIT 유니버스 빌더 patch**
- 실험 정의: 각 리밸런스 날짜에 “그 날짜에 실제 거래 가능(상장 상태, 유동성 기준 충족)”인 Tech+Healthcare만 후보로 생성.
- 게이트: 모든 날짜에서 후보 수 ≥ 14(또는 부족 시 그 이유가 로그로 남고 런이 실패/경고로 전환).
- 기대 관측치: 특정 기간(예: 2020~2021)에서만 과도하게 잘 되던 현상이 완화.

**E2. Delist/Corp action 처리 테스트**
- 실험 정의: 상장폐지/합병/티커변경 케이스를 5~10개 샘플로 회귀 테스트(가격 공백/급등락 처리).
- 게이트: 가격 공백 시 비정상 수익률(수백 %)이 발생하면 실패.
- 기대 관측치: tail return이 현실화(극단치 감소), MDD/분산이 더 현실적인 값으로 이동.

**E3. “8~14 종목 유지” 강제 리밸런스 룰**
- 실험 정의: 매 리밸런스마다 상위 N(8~14)만 보유, 나머지는 0; N은 고정(예: 10 또는 12)으로 먼저 실험.
- 게이트: 포트폴리오 종목 수 분포가 목표 범위 내(예: 95% 이상이 10±0).
- 기대 관측치: 노출/집중 리스크가 통제되어 OOS min 개선.

**PASS 조건**
- PIT 적용 후에도 OOS mean이 유지되고, OOS min이 **개선 또는 동일**이면 PASS(서바이버십 제거가 성능을 “현실화”시키는 게 목적).

# TOP4) (비용/현실성) 거래비용·슬리피지·체결제약을 스코어가 아닌 “게이트”로 적용
### (a) 왜 필요한지
- 현재 worst_mdd가 None인 점은 **리스크/비용 계산 경로가 누락**됐을 가능성이 있다.
- Tech+Healthcare라도 8~14 집중 포트는 리밸런스/슬리피지 영향이 크다. 비용 미반영은 가장 흔한 “가짜 알파” 원인.

### (b) 위험/부작용
- 단기 성능이 크게 낮아질 수 있음(정상).
- 비용 모델이 과보수적이면 알파를 과소평가할 위험.

### (c) 최소 실험 2~3개
**E1. 비용 민감도 스윕(고정 3점)**
- 실험 정의: 동일 전략에 대해 5/10/20 bps(왕복 또는 편도 명시) 비용을 적용해 OOS 재평가.
- 게이트: 10 bps에서 OOS mean이 양수 유지, 20 bps에서도 완전 붕괴(음수 고착)하지 않음.
- 기대 관측치: 성능이 비용에 얼마나 민감한지 곡선으로 확인(거래 빈도 문제 즉시 노출).

**E2. 체결 모델 단순화: next-open + participation cap**
- 실험 정의: 체결가격을 next-open로 고정하고, 일일 거래대금 대비 참여율 캡(예: 5%)을 적용해 슬리피지/미체결을 모델링.
- 게이트: 미체결/부분체결 로그가 남고, 총 turnover가 급증하는 시점이 식별됨.
- 기대 관측치: “잘 되던 시기”가 사실은 유동성으로 불가능했던 구간인지 드러남.

**E3. turnover 게이트(운영 리스크)**
- 실험 정의: 리밸런스당 turnover 상한(예: 30~50%)을 두고 초과 시 신호를 스케일 다운.
- 게이트: turnover 상한 위반 0 또는 자동 스케일로 해결.
- 기대 관측치: 비용 반영 후에도 OOS 안정성(특히 min)이 개선.

**PASS 조건**
- 비용/체결 제약을 넣은 뒤에도 OOS mean이 의미 있게 남고, OOS min(최악 성과)이 개선되면 PASS.

# TOP5) (과최적화/레짐) Degenerate fold 제거 + 레짐 분해 리포트(Tech/Healthcare 전용)로 “No-Delta” 원인을 구조적으로 찾기
### (a) 왜 필요한지
- degenerate fold는 학습/검증 분할이 깨졌거나 거래가 거의 없거나, 노출이 0에 수렴하는 구간이 있다는 뜻.
- “성능이 안 움직임”은 종종 **실험이 신호를 바꿨지만 실행/노출/비용/게이트에서 동일 결과로 클램핑**될 때 발생.

### (b) 위험/부작용
- 폴드 재정의로 과거 챔피언과 직접 비교가 어려워질 수 있음(하지만 지금은 비교 자체가 불완전).
- 레짐 리포트는 계산량 증가.

### (c) 최소 실험 2~3개
**E1. Fold 건강도(health) 게이트 추가**
- 실험 정의: 폴드별 (거래 수, 평균 노출, 결측률, 포지션 수 분포, turnover 분포) 산출 후 기준 미달이면 런 실패.
- 게이트: degenerate_folds=0을 목표로, 최소 “거래 수 하한 + 평균 노출 하한” 충족.
- 기대 관측치: OOS mean이 과대평가되던 문제가 줄고, 실험 간 비교가 유의미해짐.

**E2. 레짐 분해 리포트(트리거/적용/노출/비용) 자동 생성**
- 실험 정의: 월별/분기별로
  - 신호 강도 분포(트리거),
  - 실제 주문/체결(적용),
  - 평균/최대 노출(노출),
  - 비용 차감 전후 PnL(비용),
  - 섹터(Tech/Healthcare) 비중
  을 한 리포트에 고정 출력.
- 게이트: 모든 실험에서 동일 포맷으로 생성.
- 기대 관측치: “성능 무변화”가 어느 레이어에서 막히는지 즉시 보임.

**E3. 노출 클램핑/스케일링 영향 테스트**
- 실험 정의: 현재 노출 max가 0.838…로 보이는데, 스케일/헤지/캡이 결과를 고정시키는지 확인하기 위해 (a) 스케일 0.8, (b) 1.0, (c) 1.2 3점만 테스트(전략 구조는 동일).
- 게이트: 노출/turnover/비용이 스케일에 따라 단조 변화해야 함(단조가 아니면 클램핑/버그 의심).
- 기대 관측치: 성능이 “안 움직이는” 원인이 스케일러/캡에 있으면 여기서 바로 드러남.

**PASS 조건**
- degenerate fold 0, 레짐 리포트 생성 100%, 스케일 테스트에서 노출이 정상적으로 변하면 PASS.

## 2) 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 실행 체크리스트
아래 순서대로 **원인 레이어를 고정적으로 분해**하라(각 레이어는 로그로 수치화).

### A. 트리거(신호 생성) 레이어
- 신호 분포(평균/표준편차/상위1%/0 비율)를 base vs cand로 비교하라.
- 신호 상관(스피어만)과 순위 변동률을 계산하라.
- **관측 포인트**
  - cand가 base와 신호가 거의 동일하면: 실험이 실제로 신호를 바꾸지 못했거나, 파라미터가 무시됨.
  - 신호는 바뀌는데 성능이 동일하면: 다음 레이어(적용/노출)에서 막힘.

### B. 적용(주문/체결/리밸런스) 레이어
- 리밸런스 이벤트 수, 주문 수, 미체결률, 리밸런스 날짜 분포를 비교하라.
- “리밸런스가 아예 없거나 동일”이면: 캘린더/스케줄러/게이트(거래가능 필터)가 신호를 무력화.
- **지금 즉시 필요한 이유**: 현재 pinpoint가 깨져 있어 이 레이어가 사실상 블랙박스다(TOP1이 먼저).

### C. 노출(포트폴리오 구성) 레이어
- 평균/최대/최소 노출, 종목수(8~14 유지 여부), 섹터 비중, 단일 종목 최대 비중을 비교하라.
- cand의 노출이 base와 동일하면:
  - weight optimizer가 클램핑하고 있거나,
  - 리스크모델/캡 때문에 목표 비중이 동일하게 투영(projection)되고 있거나,
  - 거래비용/turnover 캡이 신호를 죽이고 있을 가능성.

### D. 비용(거래비용 차감 전/후) 레이어
- **비용 차감 전 PnL**과 **차감 후 PnL**을 분리해 비교하라.
- 차감 전은 개선인데 차감 후가 동일/악화면: 알파가 turnover 기반(비용 민감) → TOP4로 해결.

### E. 레짐(시장 국면/섹터 국면) 레이어
- 관측 지표(ETF는 매매 제외, 지표로만 사용):
  - QQQ(Tech), XLV(Healthcare), SPY(시장) 수익률/변동성,
  - 금리(예: 10Y), VIX 같은 변동성 지표(가능하면),
  - 섹터 상대강도(QQQ/XLV 비율).
- 월별/분기별 성과 테이블에서 “특정 레짐에서만 동작”하는지 확인하라.
- 레짐 의존성이 크면: 신호를 “레짐-조건부 스케일링”으로 줄이는 실험 1~2개만 추가(케이스 폭발 금지).

## 3) 48시간 자동 루프 형태로 정리 — 다음 액션(명령형 체크리스트)
- [ ] **TOP1(E1~E3)** 를 먼저 머지하고, 다음 런부터 모든 실험에 rebalance JSONL + run_hash/lane_hash를 강제하라.
- [ ] **TOP2(E1~E3)** 로 타임라인 어서션을 켠 “Strict 기준선”을 새로 만들고, 이후 모든 실험은 그 기준선 위에서만 비교하라.
- [ ] **TOP3(E1~E3)** 로 PIT 유니버스와 8~14 종목 유지 규칙을 고정하라(Tech+Healthcare only).
- [ ] **TOP4(E1~E3)** 로 비용/체결/turnover 게이트를 추가하고, OOS를 비용 민감도 3점으로 항상 함께 리포트하라.
- [ ] **TOP5(E1~E3)** 로 degenerate fold를 0으로 만들고, 레짐 분해 리포트를 모든 실험에 자동 첨부하라.

이 5개를 끝내면 “성능이 안 움직임”은 대부분 **(1) 신호가 안 바뀜 (2) 신호는 바뀌나 적용/노출에서 클램핑 (3) 비용에서 상쇄 (4) 레짐 의존 (5) 평가가 깨짐(폴드/서바이버십)** 중 하나로 강제 분류된다.
