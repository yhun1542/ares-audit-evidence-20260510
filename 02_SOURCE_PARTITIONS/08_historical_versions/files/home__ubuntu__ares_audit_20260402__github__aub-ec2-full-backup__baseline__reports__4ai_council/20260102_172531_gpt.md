## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — 명령형 체크리스트

### 1) **재현성/관측(telemetry) 복구: run_hash/lane_hash, 리밸런스 로그, MDD 산출**
**(a) 왜 필요한지**
- 현재 `lane_hash=None, run_hash=None`, `worst_mdd=None` → “성능이 안 움직이는” 원인이 **전략**인지 **파이프라인/로그 결손**인지 분리 불가.
- `aub_rebalance_pinpoint`가 `--base-log` 파일 미존재 + JSON 파싱 실패 → 리밸런스/턴오버/비용 기여도를 못 봄(운영 리스크 최상).

**(b) 위험/부작용**
- 로그/메트릭 추가로 실행시간/디스크 증가.
- 스키마 변경 시 기존 리포트 도구가 깨질 수 있음(버전 태그 필요).

**(c) 최소 실험 2~3개 (아래 공용 실험 E1~E5 중 선택)**
- **E1(필수)**: Telemetry 패치 적용 후 “동일 시드 2회 반복” 재현성 검증
- **E3**: 비용/슬리피지 로깅까지 포함해 리밸런스 로그 생성 확인
- **E5**: 익스포저/헤지 변화가 로그에 제대로 찍히는지(분포/턴오버) 검증

**(d) PASS 조건**
- `run_hash/lane_hash`가 모든 산출물에 기록되고, 동일 시드 재실행 시 **결과가 비트-레벨 또는 허용 오차 내 동일**.
- `rebalance.csv` 또는 `rebalance.jsonl`이 **항상 생성**되고 도구가 에러 없이 로딩.
- `worst_mdd`가 모든 run summary에 포함.

---

### 2) **누수/과최적화 1차 차단: degenerate folds 제거 + purged time-split 고정**
**(a) 왜 필요한지**
- `degenerate_folds: [1,2,3,8]`는 **검증이 무효화**됐을 확률이 높음(표본 부족/동일 구간 반복/라벨 누수).
- OOS mean이 높아도 **누수/접합 오류**면 “안 움직임”이 아니라 “가짜로 움직였던 것”.

**(b) 위험/부작용**
- 제대로 나누면 OOS가 급락할 수 있음(정상 반응).
- 표본이 적으면 변동성 증가 → 더 강한 게이트 필요.

**(c) 최소 실험 2~3개**
- **E2(필수)**: Purged time-series CV(embargo 포함)로 교체 + degenerate fold 자동 fail-fast
- **E1**: 동일 설정 반복 실행 시 fold별 점수 분산이 안정적인지 확인
- **E4**: 유니버스 고정(8~14 Tech+Healthcare) 시 fold 퇴화가 완화되는지 확인

**(d) PASS 조건**
- degenerate fold가 **0개**(또는 전체 fold의 5% 미만)로 감소.
- OOS mean이 변하더라도 **fold별 성능 분산(표준편차)과 oos_min이 개선/안정**.
- embargo/purge 적용 후에도 최소한의 유의미한 OOS가 유지(“좋아야 통과”가 아니라 “검증이 유효하면 통과”).

---

### 3) **비용/슬리피지/턴오버 반영: ‘수익은 있는데 안 움직이는’ 착시 제거**
**(a) 왜 필요한지**
- 지금 리밸런스 데이터가 비어 있어 **턴오버 폭증/슬리피지로 수익이 상쇄**되는지 판단 불가.
- Tech/Healthcare 단일주 중심(8~14)일수록 리밸런스가 성능을 지배하기 쉬움.

**(b) 위험/부작용**
- 비용을 반영하면 수익이 감소(정상).
- 비용 모델이 과도하면 “아무것도 못하는 전략”이 될 수 있음(스트레스/베이스 분리 필요).

**(c) 최소 실험 2~3개**
- **E3(필수)**: 비용 3단계(0 / base / stress) 민감도 실험(같은 신호, 비용만 변경)
- **E1**: 비용 포함 결과가 재현되는지 확인(로그 스키마 고정)
- **E5**: 익스포저 클램프/리밸런스 빈도 제한이 비용 민감도를 줄이는지 확인

**(d) PASS 조건**
- `net_after_cost`가 `gross_before_cost` 대비 **손실 기여가 설명 가능(턴오버/스프레드로 분해)**.
- base→stress로 바꿨을 때 성과가 “완전 붕괴”하지 않고 **연속적으로 악화**(모델이 비용에 과민/턴오버 과다이면 fail).
- 비용 반영 후에도 최소한의 oos_min이 유지(꼬리 리스크 점검).

---

### 4) **서바이버십/유니버스 운영 리스크 차단: Tech+Healthcare 8~14 종목 ‘고정 리스트’로 잠금**
**(a) 왜 필요한지**
- 유니버스가 시점에 따라 변하면(특히 현재 생존 종목 기반) 서바이버십 편향 가능.
- “미국주식 only + Tech/Healthcare 중심 8~14” 제약은 오히려 **검증/운영 단순화**에 도움.

**(b) 위험/부작용**
- 종목 고정은 분산 저하로 변동성/드로우다운 증가 가능.
- 특정 종목 이벤트(인수/상장폐지/거래정지) 시 운영 리스크 상승 → 대체 규칙 필요.

**(c) 최소 실험 2~3개**
- **E4(필수)**: 고정 유니버스(8~14) vs 기존 유니버스 비교(동일 신호/동일 CV)
- **E2**: 유니버스 고정 후 degenerate fold 감소 여부 확인
- **E3**: 유니버스 고정이 비용(스프레드/턴오버)에 미치는 영향 확인

**(d) PASS 조건**
- 유니버스 고정 후에도 OOS가 “완전 붕괴”하지 않으며, fold 퇴화/재현성/로그 품질이 개선.
- 종목별 최대 비중/유동성 게이트를 통과(아래 E5 게이트와 연동).

---

### 5) **노출/헤지/레짐 게이팅: 익스포저 상단(현재 max≈0.84)과 꼬리 위험을 규칙으로 제어**
**(a) 왜 필요한지**
- 노출이 높고(oos_min 음수), worst_mdd가 비어 있음 → 꼬리 위험이 “숫자로 관리되지 않는 상태”.
- ETF는 매매 금지지만 **관측 지표**로 레짐(리스크-온/오프) 판단은 가능(SPY/QQQ/XLV/XLK, VIX 등).

**(b) 위험/부작용**
- 과도한 게이팅은 기회 손실(수익률 상단을 깎음).
- 레짐 지표가 신호를 지연시키면 성과 둔화.

**(c) 최소 실험 2~3개**
- **E5(필수)**: 레짐 기반 익스포저 클램프(예: 변동성↑ 시 gross 축소, 추세↓ 시 net 축소) on/off
- **E3**: 비용 포함 상태에서 게이팅이 “순익”을 개선하는지 확인
- **E2**: 레짐 게이팅이 fold별 안정성을 개선하는지 확인

**(d) PASS 조건**
- 노출 분포가 목표 범위로 들어옴(예: gross 상한/일간 변화 상한 준수) + oos_min 개선.
- 비용 포함 기준에서 net 성과가 개선되거나 최소한 tail이 완화(드로우다운/하방분위수 개선).

## 공용 “48시간 자동 루프”용 실행 가능한 실험(총 5개로 제한)
아래 5개만 돌리고, TOP5 항목은 이 5개를 재사용해 판정합니다.

### **E1) Telemetry/재현성 골든런**
1) **실험 정의**
- 모든 산출물에 `run_hash, lane_hash, git_sha(or code_hash), data_version, seed` 기록
- 리밸런스 이벤트를 `rebalance.jsonl`(한 줄=한 이벤트)로 강제 저장
- `worst_mdd`, `turnover`, `gross/net exposure`를 summary에 강제 포함
2) **게이트**
- 동일 설정/동일 시드 2회 결과 diff가 허용오차 이내 아니면 FAIL
- 리밸런스 로그가 비어 있거나 파싱 실패 시 FAIL
3) **기대 관측치**
- “안 움직임”이 전략 문제가 아니라 관측 불능 문제였는지 즉시 분리됨

### **E2) Purged Time-Series CV + Degenerate Fold Fail-fast**
1) **실험 정의**
- time-split 고정 + purge/embargo 적용
- fold 크기/유효표본/결측률 기준을 만족 못하면 그 run 자체를 FAIL 처리
2) **게이트**
- degenerate folds > 0 이면 FAIL(또는 5% 초과 시 FAIL)
- 각 fold 최소 거래 수/최소 유효일수 미달 시 FAIL
3) **기대 관측치**
- OOS mean이 내려가더라도 신뢰도 상승, oos_min과 분산이 “설명 가능한 형태”로 변함

### **E3) 비용 민감도(0/base/stress)**
1) **실험 정의**
- 동일 포지션/리밸런스에서 비용만 3단계로 변경
- 비용 분해(스프레드/슬리피지/수수료/차입비용 가능 시)를 로그로 출력
2) **게이트**
- 비용을 0→base로 넣었을 때 성과가 비정상적으로 반전(예: 오히려 상승)하면 FAIL(부호/적용시점 버그 의심)
- stress에서 성과가 완전 붕괴하면(예: net이 gross의 대부분 상쇄) FAIL(턴오버/체결가정 과다)
3) **기대 관측치**
- “성과가 안 움직임”이 비용/턴오버 때문인지 즉시 드러남

### **E4) 유니버스 잠금(US, Tech+Healthcare, 8~14)**
1) **실험 정의**
- 거래 유니버스를 고정 리스트로 잠금(8~14)
- 종목별 최대 비중/최소 달러볼륨 게이트 추가(운영성)
2) **게이트**
- 일별 가격/거래정지/상폐 이벤트 발생 시 대체 규칙(현금화/동일섹터 대체) 없으면 FAIL
- 종목별 비중 상한 위반 시 FAIL
3) **기대 관측치**
- 서바이버십/유니버스 변동 노이즈 제거, fold 퇴화 감소 가능

### **E5) 레짐 관측(ETF는 지표만) 기반 익스포저 클램프**
1) **실험 정의**
- ETF는 매매하지 않고(SPY/QQQ/XLV/XLK/VIX 등) “관측 지표”로만 사용
- 예: (a) 변동성↑면 gross 축소 (b) 시장 추세↓면 net 축소 (c) 섹터 상대강도에 따라 Tech/Health 비중 한도 조정
2) **게이트**
- gross/net/exposure 변화율(일간) 상한 위반 시 FAIL
- 게이팅으로 거래 수가 급감해 표본이 무너질 경우 FAIL
3) **기대 관측치**
- oos_min/꼬리 개선, 비용 포함 성과의 안정화

## 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 실행 체크리스트

### A. 트리거(신호 생성) 단계
- **누수 점검**: 피처가 t시점 이후 정보를 포함하는지(리포트에 “피처 최신 타임스탬프 vs 체결 시점” 자동 출력).
- **신호 분포 점검**: 신호가 상수/포화(클리핑)되어 매일 동일 포지션이 되는지(신호 엔트로피/유니크 값 카운트).
- **라벨/정렬 점검**: 리턴 계산이 close-to-close인지, 체결가와 수익 계산 시점이 엇갈리지 않는지.

### B. 적용(포지션/리밸런스) 단계
- **리밸런스 로그 필수화**: “언제/왜/얼마나 바뀌었는지” 이벤트 단위로 남김.
- **제약이 신호를 죽이는지**: 최대 비중/현금비중/리스크 패리티 등이 항상 발동해 동일 포트폴리오가 되는지(제약 발동률).
- **degenerate fold의 실전 버전**: 백테스트에선 거래가 많지만 OOS에선 거래가 0이 되는지(기간별 거래수).

### C. 노출(Exposure) 단계
- **gross/net 분리**: 성과가 “시장 베타”인지 “알파”인지(시장 수익과의 상관, beta 추정).
- **익스포저 상단(현재 ~0.84) 원인**: (1) 신호 스케일 (2) 헤지 규칙 (3) 현금 제약 중 무엇 때문인지 분해.
- **포지션 집중도**: 8~14 종목에서 상위 2~3개가 성과를 지배하면 “움직임”이 둔해질 수 있음(HHI/상위비중).

### D. 비용(거래 마찰) 단계
- **턴오버-성과 관계**: 턴오버가 늘수록 성과가 선형으로 깎이는지(회귀/상관).
- **슬리피지 적용시점 버그**: 매수/매도 부호가 뒤집히면 성과가 이상해짐(E3에서 0→base가 좋아지면 즉시 의심).
- **유동성 게이트**: 달러볼륨/스프레드로 거래 가능성 필터(운영 리스크).

### E. 레짐(Regime) 단계
- **레짐별 분해 리포트**: (1) 변동성 상/하 (2) 시장 추세 상/하 (3) 섹터 상대강도 상/하로 OOS를 쪼개서 “언제만 되는지/언제 망하는지” 고정 표로 출력.
- **관측 ETF는 지표만**: 매매 금지 유지하면서도 레짐 라벨링은 가능.
- **게이트의 목적을 명확화**: “수익 극대화”가 아니라 “oos_min/꼬리 안정화”를 1차 목표로 둠.

## 바로 실행 순서(48시간 루프용)
1) **E1 먼저 실행** → 로그/해시/MDD/리밸런스 파싱이 깨지면 나머지 실험 중단  
2) **E2 실행** → degenerate fold 제거 및 검증 체계 확정(누수/과최적화 1차 차단)  
3) **E3 실행** → 비용이 성과를 먹는지 수치로 확정  
4) **E4 실행** → 유니버스 잠금으로 서바이버십/운영 단순화 + 안정성 확인  
5) **E5 실행** → 레짐 기반 익스포저 클램프로 oos_min/꼬리 개선 여부 확인  

이 5개만으로도 “성능이 안 움직이는” 원인이 **관측 불능(로그/재현성)**인지, **검증 무효(폴드 퇴화/누수)**인지, **비용/턴오버 착시**인지, **유니버스 편향**인지, **노출/레짐 미제어**인지가 24~48시간 내에 대부분 분리됩니다.
