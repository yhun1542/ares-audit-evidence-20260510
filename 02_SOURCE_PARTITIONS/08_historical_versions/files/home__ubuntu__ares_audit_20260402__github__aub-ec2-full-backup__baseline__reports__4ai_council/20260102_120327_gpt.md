## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — 명령형 체크리스트

### 1) **지표/아티팩트 무결성 + 리밸런스 로그 파이프라인 복구(운영 리스크 1순위)**
- [ ] Champion 메타의 `file:` 공란 원인 제거(실험/챔피언 JSON에 source artifact 경로 강제 기록)
- [ ] `worst_mdd: None`가 나오지 않도록 MDD 계산을 “항상” 수행(데이터 부족/NaN 시 명시적 에러)
- [ ] `aub_rebalance_pinpoint`가 실패한 원인(잘못된 `--base-log` 문자열/CSV 아닌 파일) 제거: **리밸런스 로그를 단일 포맷(jsonl)** 로 강제 생성
- [ ] “Champion OOS Mean: 2.6276” vs 현재 “oos_mean: 1.88” 불일치 해소(같은 기간/같은 스플릿/같은 비용모델인지 자동 검증)

**(a) 왜 필요한지**
- 지금 상태는 **리밸런스 로그가 없고**, 핵심 리스크 지표(MDD)가 **None**이며, OOS 평균이 도구마다 달라 **비교/자동선택 루프가 붕괴**할 가능성이 큼(서바이버십/과최적화 이전에 운영 리스크).

**(b) 위험/부작용**
- 로그 강제/검증 추가로 실행 시간이 증가, 실패가 “조기 에러”로 바뀌어 단기적으로 실험 통과율이 떨어질 수 있음(정상).

**(c) 최소 실험(공유 실험 E1, E4 사용)**
- 관련 실험: **E1(무결성+로그)**, **E4(비용 포함 재계산 시 지표 일치 검증)**

**(d) PASS 조건**
- `rebalance.jsonl` 생성 100% (base/cand 모두)
- `worst_mdd`가 항상 수치로 채워짐(None 금지)
- 동일 run에 대해 “진단기 OOS mean” vs “챔피언 JSON oos_mean” 차이 절대값 ≤ **0.5%**
- 파일 경로(`file:`)가 항상 비어있지 않음

### 2) **누수(Leakage) 최우선 차단: 시점정렬/피처 쉬프트/스플릿(과최적화보다 먼저)**
- [ ] 모든 피처를 **T 시점 예측에 T-1까지**만 사용하도록 강제(룰 기반 assert)
- [ ] “쉬프트 테스트(Shift test)”로 한 칸이라도 미래를 보면 성능이 폭발하는 피처를 자동 검출/차단
- [ ] Purged/Embargo CV(또는 최소한 gap 있는 split)로 학습-검증 경계 누수 제거
- [ ] `degenerate_folds`가 생기는 조건(표본 부족/동일 라벨/결측 폭증) 자동 fail-fast

**(a) 왜 필요한지**
- Tech/Healthcare는 이벤트(실적/임상/규제) 점프가 많아 **미세 누수도 OOS 평균을 가짜로 끌어올림**. 지금처럼 OOS가 도구마다 다르게 나오면 누수/정렬 문제가 섞였을 확률이 큼.

**(b) 위험/부작용**
- 누수 제거 후 성능이 내려갈 수 있음(정상). 대신 “재현 가능한” 개선이 가능해짐.

**(c) 최소 실험(공유 실험 E2 중심)**
- 관련 실험: **E2(Leakage audit + Purged CV)**, **E1(검증 assert로 운영화)**

**(d) PASS 조건**
- 쉬프트 테스트에서 “미래 쉬프트(+1)” 성능이 기준 대비 유의미하게 좋아지지 않음(예: OOS mean 개선이 **+3%p 이내**)
- Purged/Embargo 적용 후에도 OOS가 무너져서 `oos_min`이 급락하지 않음(예: 현재 0.43 → **0.35 미만으로 붕괴 금지**)
- 누수 의심 피처 자동 차단 목록이 로그로 남음

### 3) **서바이버십/유니버스 정의 고정(US Tech+Healthcare 8~14 종목) + PIT(시점정합)**
- [ ] 백테스트 유니버스를 “현재 구성 종목”이 아니라 **해당 시점에 거래 가능했던 종목**으로 구성(PIT)
- [ ] 8~14개 종목 규칙을 코드로 고정(Tech+Healthcare만) + delist/merge 처리(데이터 끊김 시 청산 규칙)
- [ ] 코퍼레이트 액션(분할/합병/티커 변경) 처리 누락 시 즉시 fail

**(a) 왜 필요한지**
- 소수 종목(8~14)에서 서바이버십이 섞이면 성능이 가장 크게 왜곡됨. 특히 헬스케어는 상폐/인수/임상 실패가 잦아 **PIT 부재 = 과거 손실 구간이 증발**할 수 있음.

**(b) 위험/부작용**
- PIT 적용 후 성능 하락 가능. 종목 수가 줄거나 공백 구간이 생겨 노출이 낮아질 수 있음(그 자체가 리스크 신호).

**(c) 최소 실험(공유 실험 E3 중심)**
- 관련 실험: **E3(PIT 유니버스 재구성)**, **E4(비용 포함 시 유니버스 영향 재평가)**

**(d) PASS 조건**
- 유니버스가 모든 날짜에 대해 재현 가능(같은 seed/run이면 동일)
- 상폐/거래정지 이벤트가 발생해도 백테스트가 중단되지 않고 “정의된 청산/대체 규칙”으로 처리
- PIT 적용 후에도 `exposure_min`이 과도하게 붕괴하지 않음(예: 0.47 → **0.30 미만으로 하락 지속** 시 FAIL)

### 4) **비용(수수료/슬리피지/스프레드/시장충격) 미반영 제거 + 턴오버 제어**
- [ ] 거래비용 모델을 OOS 산출에 **강제 포함**(미포함 결과는 리포트에 “invalid” 표시)
- [ ] 턴오버 상한(예: 일간/리밸런스당) + 최소 주문 단위(체결 불가/부분 체결 가정) 반영
- [ ] 소수 종목일수록 과도한 리밸런스로 성능이 환상화되므로 **거래 빈도/리밸런스 규칙을 로그로 고정**

**(a) 왜 필요한지**
- 8~14 종목 집중 + 높은 노출(최대 0.84)에서 비용이 빠지면 OOS가 “안 움직이는” 게 아니라 “가짜로 높거나 실험 간 구분이 안 되는” 상황이 흔함.

**(b) 위험/부작용**
- 비용을 넣으면 성능 하락/실험 탈락 증가. 대신 실거래에 가까워짐.

**(c) 최소 실험(공유 실험 E4 중심)**
- 관련 실험: **E4(비용+턴오버 캡)**, **E1(리밸런스 로그로 비용 근거 추적)**

**(d) PASS 조건**
- 비용 포함 OOS mean이 비용 미포함 대비 과도하게 붕괴하지 않음(예: **-30% 이내**; 초과 시 전략이 비용 민감 → 구조 변경 필요)
- `rebalance.jsonl`에서 평균 턴오버가 상한을 준수
- “비용 포함/미포함” 2개 지표가 같은 리포트에 동시에 기록됨(숨김 금지)

### 5) **레짐(시장 국면) 게이트 + 노출 스케일링(ETF는 관측만)**
- [ ] ETF(QQQ/XLV/SMH/IBB 등)는 **매매 금지**, 관측 지표로만 사용해 레짐을 정의
- [ ] 레짐에 따라 노출(0.47~0.84 범위)을 자동 스케일: 변동성/추세 악화 시 노출 축소
- [ ] 레짐 게이트가 “항상 켜짐/항상 꺼짐”이 되지 않도록, 발동률/지속시간을 로그로 검증

**(a) 왜 필요한지**
- 성능이 “안 움직이는” 원인이 모델이 아니라 **항상 비슷한 노출로만 움직이는 운영**일 수 있음. 레짐 게이트는 특히 Tech/Healthcare의 급락 국면에서 MDD를 줄이는 쪽으로 작동해야 함.

**(b) 위험/부작용**
- 레짐 필터가 과하면 기회를 놓쳐 OOS mean 하락 가능. 필터가 약하면 의미 없음(발동률로 판정).

**(c) 최소 실험(공유 실험 E5 중심)**
- 관련 실험: **E5(레짐 게이트+노출 스케일)**, **E1(관측 지표/발동률 로깅)**

**(d) PASS 조건**
- 레짐 게이트 발동률이 극단값이 아님(예: 0% 또는 100%면 FAIL)
- `worst_mdd`가 기준 챔피언 대비 악화되지 않음(또는 개선)
- 노출 분포가 레짐에 따라 유의미하게 달라짐(평균/분산 차이가 로그에 표시)

## 48시간 자동 루프용 “실행 가능한 Patch/실험” 5개 (정의/게이트/기대 관측치)
아래 **E1~E5만 돌리면** 위 TOP5를 전부 커버하도록 묶었습니다(케이스 폭발 방지).

### E1) Artifact/Metric/Log 무결성 패치
1) **실험 정의**
- 실험 러너가 종료 시 아래를 “항상” 생성/검증:
  - `run_meta.json`에 `artifact_path`, `data_hash`, `code_hash`, `split_hash`
  - `metrics.json`에 `oos_mean/oos_min/worst_mdd/exposure_min/max`
  - `rebalance.jsonl`(각 리밸런스의 timestamp, weights, turnover, est_cost)
- `aub_rebalance_pinpoint.py` 입력을 `--base-log path/to/rebalance.jsonl --cand-log ...`로 단일화

2) **게이트(FAIL-FAST)**
- `file:` 공란이면 FAIL
- `worst_mdd is None`이면 FAIL
- `rebalance.jsonl` 없으면 FAIL
- “진단기 산출 OOS mean” vs “metrics.json oos_mean” 차이 > 0.5%면 FAIL

3) **기대 관측치**
- pinpoint 리포트가 “No rebalance data found” 없이 생성
- OOS 지표 불일치가 사라짐(성능이 안 움직여도 원인 추적 가능)


### E2) Leakage Audit + Purged/Embargo CV
1) **실험 정의**
- 모든 피처에 대해 `shift = {-2,-1,0,+1}` 성능 민감도 테스트(+1은 미래 사용)
- CV를 purged(또는 최소 gap)로 교체하고 fold별 샘플 수/결측률 로깅

2) **게이트**
- `shift=+1`이 `shift=0` 대비 OOS mean이 +3%p 초과 개선하면 해당 피처군/파이프라인 FAIL(누수 의심)
- `degenerate_folds` 발생 시 FAIL

3) **기대 관측치**
- 성능이 단기 하락하더라도 fold 간 분산이 줄고(안정화), oos_min이 “의미 있는” 값으로 유지


### E3) PIT 유니버스(US Tech+Healthcare 8~14) 재구성 실험
1) **실험 정의**
- 8~14 종목을 “섹터(Tech/Healthcare) + 유동성 + PIT 가용성” 규칙으로 일관 생성
- delist/merge 시나리오를 데이터로 재현(가격 0/거래정지 구간 처리)

2) **게이트**
- 어떤 날짜에도 유니버스가 규칙을 위반(종목수 <8 또는 >14, 섹터 외 포함)하면 FAIL
- 상폐/티커변경 이벤트에서 백테스트 중단 발생 시 FAIL

3) **기대 관측치**
- 서바이버십 제거로 과거 급락 구간이 복원되고, 성능이 “안 움직이는” 원인이 데이터 왜곡인지 판별 가능


### E4) 비용 포함 + 턴오버 캡 실험
1) **실험 정의**
- 고정 비용모델(수수료+스프레드+슬리피지)을 적용한 net 성과를 기본 지표로 승격
- 리밸런스당 턴오버 캡(예: 20~30%) 적용 버전 동시 산출

2) **게이트**
- 비용 포함 성과 리포트가 없으면 FAIL
- 평균 턴오버가 캡을 초과하면 FAIL(또는 패널티)

3) **기대 관측치**
- “성과가 안 움직임”이 사실상 턴오버/비용이 지배하는 구간인지 드러남
- 전략이 비용 민감하면 리밸런스 빈도/신호 스무딩이 필요하다는 근거 확보


### E5) 레짐 게이트(ETF 관측만) + 노출 스케일
1) **실험 정의**
- ETF(예: QQQ, XLV, IBB)는 관측만: 추세/변동성/크레딧 스프레드 유사 지표로 레짐 스코어 생성
- 레짐 스코어로 목표 노출을 0.47~0.84 사이에서 스케일(리스크 오프 시 하향)

2) **게이트**
- 게이트 발동률이 0% 또는 100%면 FAIL
- 게이트 적용 후 worst_mdd가 악화(예: +20% 이상)하면 FAIL

3) **기대 관측치**
- 동일 알파라도 국면에 따라 노출이 달라지며, MDD/하방 꼬리가 줄어드는 방향의 변화 관측

## 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 즉시 적용 체크리스트

### A) 트리거(신호가 실제로 변하나?)
- [ ] 예측 스코어/랭킹의 일간 변화율(또는 리밸런스 시점 변화율) 분포를 기록: **거의 0이면 신호가 죽어있음**
- [ ] 상위/하위 종목이 고정되는 “스틱니스(stickiness)” 지표 로그화(상위 3개가 며칠 연속 동일인지)

### B) 적용(신호→포지션 변환이 막히나?)
- [ ] 포지션 생성 후 **제약조건(종목수 8~14, 섹터, 리스크)** 때문에 클리핑이 얼마나 발생하는지 로그화(클리핑률 높으면 전략이 무력화)
- [ ] 리밸런스 빈도/임계치 때문에 주문이 거의 안 나가는지 확인(주문 이벤트 수/일)

### C) 노출(리스크 버짓이 실질적으로 고정됐나?)
- [ ] `exposure_min/max` 외에 “실현 변동성 대비 목표 변동성”을 기록: 목표가 항상 cap에 걸리면 노출이 사실상 고정
- [ ] 현금 비중/미집행 비중(제약으로 못 산 비중)을 기록

### D) 비용(성과를 눌러서 실험 간 차이를 지우나?)
- [ ] gross vs net 차이를 리밸런스별로 분해(비용이 알파보다 크면 실험을 바꿔도 안 움직임)
- [ ] 턴오버와 성과의 상관(높으면 비용이 지배)

### E) 레짐(한 국면만 학습/평가하고 있나?)
