## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — 명령형 체크리스트

### 1) **누수/폴드 퇴화(degenerate_folds)부터 즉시 봉합**
**(a) 왜 필요한지**
- Champion에 `degenerate_folds: [1,2,3,8]`가 떠 있는 상태는 **검증 자체가 무효**이거나(표본 0/극소), **시간축 누수/정렬 오류/라벨 정렬 실패** 가능성이 최우선입니다.
- `worst_mdd: None`, `lane_hash/run_hash: None`도 함께 보면 **평가 파이프라인/로깅이 끊겨 “좋아 보이는 수치만 남는” 서바이버십형 착시** 위험이 큽니다.

**(b) 위험/부작용**
- 폴드 정리 후 성능이 “급락”할 수 있음(정상적인 현상일 수 있음).
- 테스트 기간이 줄어 OOS 분산이 커질 수 있음.

**(c) 최소 실험(공유 실험 세트 참조) 2~3개**
- **[E1] Purged Walk-Forward + Embargo 적용** (시간 누수 차단)
- **[E3] 평가 산출물(폴드별 샘플 수/수익시계열) 강제 로깅** (퇴화 즉시 탐지)
- **[E4] 포인트-인-타임(PIT) 데이터 스냅샷 강제** (특히 헬스케어/바이오 이벤트에서 누수 빈발)

**(d) PASS 조건**
- `degenerate_folds == []` (0개)
- 각 fold에 대해 `n_samples >= 최소치(예: 200 trading days equivalent)`를 로그로 확인
- OOS가 “좋아 보이기만” 하지 않도록: `oos_min`이 **비정상적으로 0 근처로 고정되지 않고**(현재 -0.025) fold별 분포가 정상(극단치/0 고정 제거)

---

### 2) **비용(수수료/슬리피지) 미반영 + 과최적화(턴오버) 즉시 점검**
**(a) 왜 필요한지**
- 미국 개별주 8~14종 포트는 리밸런스/체결 비용이 **수익을 쉽게 먹는 구조**입니다.
- “성능이 안 움직임”의 흔한 원인은 모델이 바뀌어도 **실제 PnL은 비용/턴오버에서 상쇄**되는 경우입니다(특히 테크/헬스 변동성 구간).

**(b) 위험/부작용**
- 비용을 넣으면 성능 하락 가능(하지만 운영 가능성은 상승).
- 턴오버 억제는 급변 레짐에서 반응이 늦어질 수 있음.

**(c) 최소 실험 2~3개**
- **[E2] 비용모델 + 턴오버 패널티(또는 min-hold) 도입**  
- **[E5] 포지션 상한/리밸런스 빈도(48h 루프 기준) 고정 + 거래 임계값(Δw threshold)**  
- **[E3] 리밸런스 로그(주문→체결 가정→비용) 단일 스키마로 기록**

**(d) PASS 조건**
- 비용 포함 후에도 `oos_mean`이 기준 대비 **유지(또는 소폭 - 이내)**하며,
- `turnover`가 목표 구간(예: 일간 0.5 이하 또는 주간 1.5 이하 등)으로 내려가고,
- `oos_min`이 악화되지 않거나(또는 악화 폭 제한) **PnL 변동의 원인이 비용 로그로 설명 가능**해야 함

### 3) **운영 리스크(로깅/리플레이/재현성) 복구 — rebalance pinpoint가 이미 실패**
**(a) 왜 필요한지**
- 현재 `aub_rebalance_pinpoint`가 `--base-log` 파일 미존재/CSV 파싱 실패로 **리밸런스 비교가 불가**합니다.  
  → “왜 성능이 안 움직였는지”를 **절대 분해할 수 없는 상태**.
- `lane_hash/run_hash: None`은 **재현 불가(실험-결과 연결 끊김)** 신호입니다.

**(b) 위험/부작용**
- 기능 추가로 파이프라인이 일시적으로 느려질 수 있음.
- 로깅이 늘며 스토리지 증가.

**(c) 최소 실험 2~3개**
- **[E3] 리밸런스 로그 포맷을 JSONL 단일화 + 스키마 버전 필드 추가**  
  - 최소 필드: `ts, universe, target_w, prev_w, trade_w, price_ref, cost_bps, realized_cost, exposure, signals_hash, data_hash, code_hash`
- **[E1] 폴드/백테스트 러너에 run_hash 강제 삽입(코드해시+데이터해시)**  
- **[E2] 비용 산출을 로그에서 “재계산 가능”하게 분리(비용함수 버전 고정)**

**(d) PASS 조건**
- `aub_rebalance_pinpoint.py`가 base/cand 모두에 대해 **에러 없이 리포트 생성**
- 동일 입력(데이터해시/코드해시)에서 결과가 **완전 재현**
- “성능 무변화” 케이스에서 **리밸런스/비용/노출 변화가 수치로 설명**됨

### 4) **서바이버십/코퍼레이트 액션(특히 헬스케어) 리스크 봉합 + US Tech/Healthcare 8~14 제약 고정**
**(a) 왜 필요한지**
- 헬스케어(바이오)에서 상장폐지/합병/스플릿/티커 변경이 잦아 **서바이버십 편향**이 생기기 쉽습니다.
- “US only + Tech/Healthcare 중심 + 8~14종” 제약을 코드로 고정하지 않으면 실험마다 유니버스가 달라져 **비교 불능/과최적화**가 발생합니다.

**(b) 위험/부작용**
- 유니버스가 줄어 성능이 하락할 수 있음(정상).
- PIT 데이터 구축 비용/시간 증가.

**(c) 최소 실험 2~3개**
- **[E4] PIT 유니버스 스냅샷 + 상폐/합병 이벤트 포함 백테스트**  
- **[E3] 유니버스 결정 로그(선정 사유/필터 결과/섹터 태그) 저장**  
- **[E5] 종목수 8~14 강제 + 섹터(Tech/Healthcare) 비중 하한/상한 게이트**

**(d) PASS 조건**
- 어떤 실험에서도 보유 종목 수가 **항상 8~14**로 유지
- 섹터 태그 기준으로 Tech+Healthcare 합산 비중이 **사전에 정의한 범위**를 유지
- 상폐/티커변경 이벤트가 포함된 구간에서도 백테스트가 **중단 없이 완주**, 그리고 결과가 “상폐 제거 버전” 대비 과도하게 괴리 나지 않음(서바이버십 의심 제거)

### 5) **노출/리스크(과도한 익스포저, MDD 미산출) 우선 봉합 — 운영 가능한 위험 한도 설정**
**(a) 왜 필요한지**
- 현재 노출이 `max ~0.84`까지 올라가는데, `worst_mdd: None`이면 **리스크 평가가 누락**된 상태입니다.
- “성능이 안 움직임”이 아니라 “리스크가 안 보임”일 수 있습니다(리스크 지표 미산출/미로깅).

**(b) 위험/부작용**
- 리스크 제한을 걸면 수익 상단이 줄 수 있음.
- 변동성 타겟팅은 급변장에선 잦은 리밸런스로 비용 증가 가능(→ [E2]와 같이 봐야 함).

**(c) 최소 실험 2~3개**
- **[E5] 노출 상한(예: gross/net), 단일종목 캡, 섹터 캡, 베타 타겟(관측지표로 QQQ/XLV 사용) 추가**  
- **[E3] MDD/VAR/ES를 fold별로 강제 산출 및 리포팅**  
- **[E2] 리스크 제약 도입 후 턴오버/비용 동시 최적(패널티)**

**(d) PASS 조건**
- `worst_mdd`가 **항상 산출(Null 금지)**되고, fold별 MDD가 리포트에 존재
- gross/net/exposure가 사전 정의한 한도 내 유지
- 제약 도입 후에도 OOS 핵심 지표가 **비정상(갑자기 0 근처 고정, 특정 fold만 폭주)**이 아니어야 함

## 공유 “실행 가능한 패치/실험” 5개 (48시간 자동 루프 형태)
아래 5개만 실제로 돌리고, 위 TOP5 항목은 이 5개를 조합해 해결합니다(케이스 폭발 방지).

### [E1] Purged Walk-Forward + Embargo + 퇴화폴드 하드-게이트
- **(1) 실험 정의**: 시계열 CV를 purging/embargo(예: 예측호라이즌만큼 purge + embargo k일)로 교체. fold 생성 시 최소 표본 미달 fold는 실패 처리.
- **(2) 게이트**: `degenerate_folds == []` AND fold별 샘플수/기간 최소치 충족 AND run_hash 기록.
- **(3) 기대 관측치**: OOS 평균은 일부 하락 가능하나 fold 간 분산/비정상 패턴(0 고정, 특정 fold만 폭주)이 감소.

### [E2] 비용모델 + 턴오버 제어(min-hold 또는 Δw threshold 또는 L1 turnover penalty)
- **(1) 실험 정의**: 고정 커미션+슬리피지(bps) 비용모델 적용, 목적함수에 turnover penalty 추가 또는 “최소 보유기간/최소 변경폭” 룰 적용.
- **(2) 게이트**: 비용 포함 성과를 별도 컬럼으로 강제 산출, turnover 로그 필수.
- **(3) 기대 관측치**: 거래 횟수/턴오버 하락, 비용 차감 후 PnL의 안정성 상승.

### [E3] 리밸런스/평가 로깅 스키마 단일화(JSONL) + pinpoint 복구
- **(1) 실험 정의**: 리밸런스 로그/백테스트 요약을 단일 JSONL로 저장(스키마 버전 포함). `aub_rebalance_pinpoint`가 읽는 경로/포맷을 표준화.
- **(2) 게이트**: pinpoint 리포트가 base/cand 모두에서 생성 성공, 에러 0.
- **(3) 기대 관측치**: “왜 성능이 안 움직였는지”를 리밸런스 차이(신호→타겟w→거래w→비용)로 설명 가능.

### [E4] PIT 유니버스 + 상폐/합병/스플릿 이벤트 포함(서바이버십 차단)
- **(1) 실험 정의**: 날짜 t에서 사용 가능한 정보만으로 유니버스 구성(Tech/Healthcare 태그 포함), corporate action 처리 강제.
- **(2) 게이트**: 상폐 이벤트 포함 구간에서도 백테스트 중단 0, 유니버스 로그 저장.
- **(3) 기대 관측치**: 과거 특정 구간 “너무 좋은” 성과가 완화될 수 있으나, 재현성과 현실성이 상승.

### [E5] 포트폴리오 제약(8~14종, 섹터/단일종목 캡, 노출 상한, 관측지표 베타) + 리스크 리포팅
- **(1) 실험 정의**: 종목수 8~14 강제, Tech/Healthcare 중심 비중 제약, 단일종목/섹터/노출 상한. QQQ/XLV는 **거래 금지**, 베타/레짐 관측용으로만 사용.
- **(2) 게이트**: 제약 위반 0, `worst_mdd`/exposure 지표 Null 금지.
- **(3) 기대 관측치**: 익스포저 폭주 감소, MDD가 “보이기” 시작, 운영 리스크 감소.

## 성능이 안 움직일 때 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래 순서로 “원인 분해 로그”를 자동 생성하도록 고정(질문 없이 실행).

1) **Trigger(신호 발생) 문제**
- 체크: 신호 분포(평균/표준편차/스파스성), 상위 신호 종목이 매일 동일한지, NaN/clip 빈도
- 증상: 신호가 거의 0이거나 상수 → 리밸런스가 안 움직임

2) **Apply(제약/정규화/리밸런스 규칙)에서 죽는 문제**
- 체크: 제약 적용 전 target_w vs 적용 후 final_w 차이(프로젝션 손실), min-hold/threshold로 trade가 0 되는 빈도
- 증상: 신호는 변하는데 최종 포트가 고정 → “전략이 안 움직임”

3) **Exposure(리스크/상관/베타)에서 상쇄되는 문제**
- 체크: 섹터/팩터 노출(관측용 ETF QQQ/XLV, 또는 시장 SPY 베타), gross/net, 상위 1~3 종목 기여도
- 증상: 포지션은 바뀌는데 순노출/팩터가 상쇄 → PnL 정체

4) **Cost(비용/슬리피지)에서 상쇄되는 문제**
- 체크: 거래비용 기여도(총 PnL vs 비용 차감 후 PnL), turnover와 PnL의 상관
- 증상: 그로스 PnL은 개선되나 네트 PnL 정체/악화

5) **Regime(레짐) 불일치 문제**
- 체크: 변동성 구간(예: VIX 대용 지표), 금리/헬스 이벤트 구간, Tech vs Healthcare 상대강도(관측용 지표로 QQQ/XLV 비율)
- 증상: 특정 레짐에서만 유효 → 전체 OOS 평균은 정체, fold 퇴화가 있으면 더 심하게 왜곡

## 24~48시간 실행 순서(고정)
1. **E3 먼저 적용**: 로그/재현성/핀포인트 복구 없이는 어떤 개선도 “원인 설명 불가”
2. **E1 적용**: degenerate fold 제거 + 누수 차단 게이트 통과시키기
3. **E2 적용**: 비용 포함 지표를 챔피언 선정의 필수 조건으로 승격
4. **E4/E5는 병렬**: 유니버스(PIT/서바이버십)와 리스크 제약(8~14, 섹터, 노출, MDD)을 운영 가능 형태로 고정

이렇게 하면 48시간 자동 루프에서 “성능이 안 움직임”이 발생해도, 최소한 **트리거→적용→노출→비용→레짐** 중 어디에서 막혔는지 로그로 단일 원인(또는 상위 2개 원인)까지는 자동으로 떨어지게 됩니다.
