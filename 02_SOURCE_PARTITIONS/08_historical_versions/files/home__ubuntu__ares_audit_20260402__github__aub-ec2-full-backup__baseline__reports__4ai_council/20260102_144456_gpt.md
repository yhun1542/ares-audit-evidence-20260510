## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — **명령형 체크리스트**
(우선순위는 **누수 → 과최적화 → 서바이버십 → 비용 미반영 → 운영 리스크** 순으로 고정)

---

# 1) **리밸런스/체결 로그 파이프라인 복구 (운영 리스크 + 비용/노출 분석 불능 해소)**
### (a) 왜 필요한지
- 현재 `aub_rebalance_pinpoint`가 **base-log/cand-log를 못 읽어 리밸런스 데이터 “없음”** 상태 →  
  **턴오버/비용/슬리피지/노출 변화**가 “성능이 안 움직이는 원인”인지 판단 자체가 불가.
- 48시간 자동 루프에서 “성능 정체”는 대부분 **리밸런스/비용/노출 레이어**에서 발생하는데, 지금은 관측이 막혀 있음.

### (b) 위험/부작용
- 로그 스키마 변경 시 기존 리포트/대시보드 파손.
- 로그량 증가로 IO 병목(특히 jsonl 과다 기록).

### (c) 최소 실험(1개 잡에 3-arm로 처리)
**[실험 E1: Rebalance Telemetry Patch]**
- Arm A: 현행 유지(컨트롤)
- Arm B: `rebalance.jsonl`을 **강제 생성**(각 리밸런스 이벤트: timestamp, ticker, target_w, prev_w, delta_w, price, est_slippage_bps, est_fee, realized_cost, turnover)
- Arm C: B + **base-log 경로 자동해결**(최근 champion run artifact에서 base rebalance log를 심볼릭 링크로 노출)

### (d) PASS 조건 (게이트)
- **게이트(필수)**: 각 run에 대해 `rebalance.jsonl`이 1) 존재 2) JSONL 파싱 성공 3) 이벤트 수>0 4) ticker/weight 합계 검증(∑w≈1 또는 현행 규칙 충족).
- **관측 기대치(48h)**:  
  - “성능 무변화” 상황에서도 **턴오버/비용/노출의 변화량**이 숫자로 드러나야 함(=원인 분해 가능 상태).

# 2) **데이터 누수(lookahead/리밸런스 타이밍) 자동 감사 게이트 추가**
### (a) 왜 필요한지
- Tech/Healthcare 단일주 포트폴리오는 신호가 강해 보일 때 **리밸런스 타이밍/가격 사용 방식** 하나로 OOS가 “잘 나오는 착시”가 생김.
- `oos_mean`이 과거 보고(2.62) vs 현재 챔피언(1.88)로 흔들리는 건 **스플릿/라벨/체결가 타이밍** 이슈일 가능성이 큼.

### (b) 위험/부작용
- 게이트가 너무 엄격하면 실험이 대량 FAIL → 탐색 속도 저하.
- 일부 “합법적” 피처까지 오탐으로 막힐 수 있음(예: EOD 기반 전략에서 close 사용).

### (c) 최소 실험(1개 잡에 3-arm)
**[실험 E2: Anti-Leakage Gate + Timing Shift]**
- Arm A: 현행 타이밍(컨트롤)
- Arm B: **가격/피처 1-bar 지연 강제**(모든 의사결정 입력을 t-1로 shift) + 체결가를 next open(또는 vwap 근사)로 고정
- Arm C: B + **리밸런스 캘린더 고정**(예: 월/주 1회 같은 deterministic schedule)하여 “미세 타이밍 튜닝” 제거

### (d) PASS 조건 (게이트)
- **게이트(필수)**:  
  - 모든 피처 timestamp ≤ decision cutoff(t-1) 검증 통과  
  - “당일 종가를 보고 당일 종가에 체결” 같은 패턴이 0건
- **관측 기대치(48h)**:  
  - Arm B/C에서 성능이 급락하면 → 기존이 **타이밍/누수 의존** 가능성  
  - 성능이 유사하면 → “누수 아닌 다른 원인(비용/노출/레짐)”로 다음 단계 진행

# 3) **비용(슬리피지/수수료/임팩트) 모델을 ‘하드 게이트’로 승격**
### (a) 왜 필요한지
- 단일주(특히 NVDA/AMD 같은 고변동)에서 리밸런스 잦으면, 백테스트 알파의 상당 부분이 **거래비용에 잠식**됨.
- 지금은 리밸런스 로그도 깨져 있어 “비용이 안 반영/과소평가”일 위험이 높음.

### (b) 위험/부작용
- 비용 모델을 과도하게 잡으면 “아무것도 안 하는 전략”이 유리해지는 부작용.
- 티커별 유동성 차이를 무시하면 왜곡.

### (c) 최소 실험(1개 잡에 3-arm)
**[실험 E3: Cost Model Hardening]**
- Arm A: 현행 비용(컨트롤)
- Arm B: **보수적 bps 슬리피지**(예: 8~15bps) + 고정 수수료 + turnover 기반 임팩트(선형) 추가
- Arm C: B + **턴오버 상한 게이트**(예: 20거래일 롤링 turnover ≤ X) 위반 시 신호 스케일 다운/리밸런스 스킵

### (d) PASS 조건 (게이트)
- **게이트(필수)**: 비용 반영 후에도  
  - `oos_mean` 하락폭이 “설명 가능한 수준”인지(비용=alpha의 과반 이상이면 FAIL로 간주)  
  - 평균 turnover가 상한 이내(또는 스케일링이 실제로 작동)
- **관측 기대치(48h)**:  
  - “성능 정체”가 비용 때문이면 B/C에서 성능이 **안 움직이는 이유가 수치로 확정**되고, 이후 신호/리밸런스 개선 방향이 명확해짐.

# 4) **과최적화/서바이버십 방지: ‘고정 유니버스(8~14) + 워크포워드 단순화’**
### (a) 왜 필요한지
- Tech+Healthcare 집중 포트에서 유니버스가 run마다 바뀌면 **서바이버십/리밸런스 편향**이 쉽게 들어감.
- “9 experiments 발견”인데도 no-delta라면, 탐색이 사실상 **노이즈/중복**일 확률이 큼 → 평가 프레임을 단순화해야 함.

### (b) 위험/부작용
- 고정 유니버스가 특정 기간에 불리할 수 있음(레짐 편향).
- 종목 수가 적어 분산 부족 → MDD 커질 수 있음(그래서 다음 항목의 노출 게이트와 함께 가야 함).

### (c) 최소 실험(1개 잡에 2~3-arm)
**[실험 E4: Fixed Universe + WF Split Freeze]**  
- 유니버스 고정(ETF 매매 금지, 관측 지표만):  
  - **Tech**: MSFT, AAPL, NVDA, GOOGL, AMZN, META, AVGO, AMD  
  - **Healthcare**: LLY, UNH, ABBV, MRK  *(총 12)*
- Arm A: 현행(컨트롤)
- Arm B: 위 고정 유니버스 + 워크포워드 split(기간/폴드) 완전 고정 + 하이퍼파라미터 탐색 폭 축소(탐색공간 1/3)
- Arm C(옵션): B + “피처 셋 동결(상위 N개만)”

### (d) PASS 조건 (게이트)
- **게이트(필수)**: 폴드별 성능 분산(예: fold 간 성능 표준편차) 급증 시 FAIL.  
- **관측 기대치(48h)**:  
  - 성능이 비슷하거나 개선되면 → 이전 개선 시도들이 **탐색 중복/과최적화**였던 정황  
  - 성능이 감소해도 분산이 줄면 → “신호는 약하지만 평가가 정직해졌다”로 다음 개선(레짐/노출) 단계 진행

# 5) **노출/레짐(ETF는 지표만) 기반 ‘리스크 게이트’ 추가**
### (a) 왜 필요한지
- 현재 exposure min/max가 0.47~0.84로 보이는데, 레짐 변화(금리/리스크오프)에서 **동일 신호라도 노출을 줄여야** OOS가 안정화됨.
- ETF는 매매하지 않되 **상태 관측(레짐 분류)**에는 최적.

### (b) 위험/부작용
- 레짐 필터가 과하면 기회 손실(under-exposure).
- 레짐 정의가 불안정하면 “필터가 신호를 랜덤하게 자르는” 형태가 됨.

### (c) 최소 실험(1개 잡에 3-arm)
**[실험 E5: Regime Risk Gate (ETF-as-indicator only)]**
- 관측 ETF(매매 금지): QQQ(성장), XLK(Tech), XLV(Healthcare), IWM(리스크), TLT(금리), HYG(크레딧)
- Arm A: 현행(컨트롤)
- Arm B: 레짐=RiskOff(예: QQQ<MA, HYG 약세, TLT 강세 등 단순 규칙) 시 **총 노출 cap**(예: max gross 0.5)
- Arm C: B + 섹터 바이어스(예: RiskOff 시 Healthcare 비중 상한 완화/Tech 상한 축소)

### (d) PASS 조건 (게이트)
- **게이트(필수)**:  
  - worst-case MDD(또는 95% MDD proxy) 개선이 없으면 FAIL  
  - 평균 노출이 “의도한 범위”로 실제 조절되는지(노출 로그 검증)
- **관측 기대치(48h)**:  
  - 수익률이 크게 안 늘어도 **oos_min, tail**이 개선되면 성공(자동 루프에서 “살아남는 전략” 쪽으로 진전)

## 48시간 자동 루프 형태로 정리 (실험 정의 → 게이트 → 기대 관측치)
- **E1 로그 복구**: 리밸런스 로그 생성/파싱 게이트 → 턴오버/비용/노출 원인 분해 가능해짐  
- **E2 누수/타이밍 쉬프트**: t-1 강제 게이트 → 성능 급락 여부로 누수 의존성 판별  
- **E3 비용 하드닝**: 비용+턴오버 상한 게이트 → “비용 때문에 안 움직임” 확정/반박  
- **E4 고정 유니버스/WF 동결**: 폴드 분산 게이트 → 과최적화/서바이버십 억제  
- **E5 레짐 노출 게이트**: MDD/노출 검증 게이트 → tail 안정화 중심 개선

# 성능이 안 움직일 때: 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래를 **순서대로** 분해(앞 단계가 불확실하면 뒤 단계로 가지 말기).

## A) 트리거(신호 발생 자체가 줄었나?)
- (체크) 신호 score 분포(평균/분산), 상위 quantile 빈도, “tradeable day 비율”
- (증상) score가 0 근처로 붕괴 → 피처 스케일/정규화/결측 처리 변화 가능성

## B) 적용(신호는 있는데 포지션에 반영이 안 되나?)
- (체크) target_w vs realized_w 괴리, 리밸런스 스킵 사유(게이트/캡/결측)
- (증상) target은 변하는데 realized가 고정 → 리밸런스 엔진/제약조건 버그 가능성(E1이 먼저)

## C) 노출(총 노출/섹터 노출이 의도와 다른가?)
- (체크) gross/net, Tech vs Healthcare 비중, 단일 종목 상한 hit 빈도
- (증상) 노출이 항상 0.5~0.8에 갇힘 → 캡/스케일링이 성능을 “평평하게” 만들 수 있음

## D) 비용(비용이 알파를 상쇄하나?)
- (체크) (턴오버 × bps)로 근사 비용을 먼저 산출해 OOS alpha 대비 비율 확인
- (증상) 비용/알파 비율이 50%↑이면, 전략 개선은 “신호”가 아니라 **리밸런스 빈도/포지션 관성**에서 나옴

## E) 레짐(같은 신호가 레짐에 따라 부호가 바뀌나?)
- (체크) ETF 지표 기반으로 RiskOn/Off를 나누고, 각 구간의 hit-rate/returns를 분리 집계
- (증상) 레짐별 성과 부호가 반대면 → 신호를 바꾸기보다 **노출 게이트(E5)**가 최단거리

## 오늘 바로 실행 순서 (명령형)
1) **E1 먼저**: 리밸런스 로그 생성/파싱 100% 통과시키기(원인분해 인프라)  
2) **E2**: t-1 쉬프트 + 체결가 규칙 고정으로 누수 여부 판정  
3) **E3**: 비용 보수화 + 턴오버 상한으로 “비용 탓 정체” 확정/배제  
4) **E4**: 12종 고정 유니버스 + WF split 동결로 과최적화/서바이버십 제거  
5) **E5**: ETF 지표로 레짐 노출 게이트 추가(수익률보다 tail 안정 우선)

(위 5개만으로 48시간 루프에서 “성능 무변화”의 대부분을 **관측 가능 + 원인 확정** 상태로 만들 수 있음.)
