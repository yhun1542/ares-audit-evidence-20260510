# 실험/패치 카탈로그 (총 5개만 운용)

## E1) 누수(Leakage)·평가 과최적화 차단 패치
**(1) 실험 정의**
- [ ] CV를 **Purged walk-forward + Embargo**로 강제(이웃 기간 정보 누수 차단)
- [ ] 모든 피처에 대해 **“as-of timestamp”/lag 규칙**을 단일 함수로 강제(미래값 접근 방지)
- [ ] 리밸런싱 시점 기준으로 **가격/재무/뉴스 등 데이터 소스별 lag 정책**을 명시적으로 분리

**(2) 게이트**
- [ ] “누수 탐지 테스트”에서 위반 0건(아래 중 최소 2개 자동 실행)
  - [ ] **feature lag 검사**(피처가 t 시점 이후 데이터를 참조하면 fail)
  - [ ] **shuffle test**(시간축 섞으면 성능이 1 근처로 붕괴해야 정상)
  - [ ] **label shift test**(레이블 +k shift 시 성능 급락해야 정상)
- [ ] lockbox_mean이 champion 대비 **유지 이상(하락폭 ≤ 0.5%)**이면 통과(누수 제거 시 단기 하락 허용)

**(3) 기대 관측치**
- [ ] 튜닝-락박스 괴리가 줄고(과최적화 감소) 성능 분산이 안정
- [ ] “특정 fold에서만 과하게 좋던” 패턴 완화

---

## E2) 서바이버십/상장폐지/심볼 변경(운영) 리스크 제거 패치
**(1) 실험 정의**
- [ ] 유니버스 생성 단계에서 **상장폐지/합병/심볼 변경**을 시간축대로 재현
- [ ] 백테스트에서 **delisting return / 마지막 거래일 처리**를 명시(0으로 고정 금지)
- [ ] “Tech+Healthcare 8~14”를 만족하는 **당시점 기준** 유니버스만 선택(미래의 생존 종목으로 고정 금지)

**(2) 게이트**
- [ ] 과거 임의 시점 N개를 뽑아 **“그 시점에 실제로 거래 가능했던 티커만 포함”** 자동 검증
- [ ] lockbox_min이 **악화되지 않을 것(≤ 0.00x 악화 금지)** 또는 worst_mdd가 **+1%p 이상 악화되면 fail**

**(3) 기대 관측치**
- [ ] 장기 성과 과대평가가 줄고, 실운영 재현성이 올라감
- [ ] 특정 티커/기간에서 발생하던 비정상 급등(데이터 오류성) 제거

---

## E3) 비용(수수료·슬리피지·스프레드) 반영 + 턴오버 제약 패치
**(1) 실험 정의**
- [ ] 거래비용 모델을 **고정 bps + 변동(유동성/변동성 기반) 슬리피지**로 2단 구성
- [ ] 리밸런싱마다 **turnover 상한** 또는 **거래비용 페널티(목적함수)** 추가
- [ ] 비용 민감도 스윕(예: 2/5/10/20 bps)을 자동 리포트로 저장

**(2) 게이트**
- [ ] lockbox에서 비용 3수준(예: 5/10/20bps) 모두 **성능 곡선이 단조 감소**하며, 10bps에서도 champion 대비 **손실이 과도하지 않을 것(예: -1% 이내)**  
- [ ] turnover가 **상한 이내**(예: 일/주 리밸런스 기준 사전 정의된 임계치)로 유지

**(3) 기대 관측치**
- [ ] “락박스에서 미세하게만 좋은” 후보들이 비용 반영 후 정리되고, 실운영 가능 후보만 남음
- [ ] 성능이 크게 안 움직이더라도 **리스크(실현가능성) 지표가 개선**됨

---

## E4) 레짐(Tech/Healthcare 리스크온·오프) 관측 지표(ETF) 기반 게이팅/리스크 오버레이
> ETF는 매매하지 않고 **관측용 지표로만 사용**  
**(1) 실험 정의**
- [ ] 관측 ETF 예: **XLK(tech), XLV(healthcare), QQQ(tech beta), IWM(리스크), TLT(금리), VIX 대용 지표(가능한 데이터 소스 내)**  
- [ ] 레짐을 2~3개로 단순화:
  - [ ] Risk-on: (XLK, QQQ 모멘텀 양호 & 변동성 낮음)
  - [ ] Risk-off: (모멘텀 약화 or 변동성 상승)
- [ ] Risk-off에서만 **포지션 수 축소(8→최소), 현금 비중 증가, 동일가중→리스크패리티** 같은 “방어 모드” 적용

**(2) 게이트**
- [ ] lockbox worst_mdd가 champion 대비 **개선(더 작아짐)** 또는 최소 **악화 ≤ 0.5%p**
- [ ] 레짐 전환 빈도 과다 금지(예: 월 X회 초과 시 fail → 운영리스크/채터링 방지)

**(3) 기대 관측치**
- [ ] 성과 평균이 크게 안 오르더라도 **tail risk/최악 구간 손실이 줄어드는 형태**가 나와야 정상

## E5) 노출(Exposure)·제약(8~14종목, 섹터 편중, 단일종목) 강제 + 포지션 구성 알고리즘 정리
**(1) 실험 정의**
- [ ] 포지션 구성 단계에서 하드룰:
  - [ ] 보유 종목 수 **8~14 고정**
  - [ ] 단일 종목 max weight (예: 15~20%)
  - [ ] Tech/Healthcare 내부에서도 **서브산업 편중 완화(가능하면)**  
- [ ] 동일 신호라도 “상위 N” 단순선정 vs “제약 최적화(간단한 greedy/QP)” 1개만 선택해 비교

**(2) 게이트**
- [ ] lockbox_min(최저 성과) 또는 worst_mdd가 **악화되면 fail**(노출 제약은 평균보다 하방 방어가 목적)
- [ ] 제약 위반 0건(리포트에 자동 표기)

**(3) 기대 관측치**
- [ ] 후보들 간 차이가 크지 않더라도 **운영 제약 준수 + 리스크 지표 개선**으로 “실전형”이 남음

# 1) 우선순위 TOP5 제안 (각: 왜/위험/적용 실험/ PASS)

## TOP1) 누수·평가 과최적화부터 “차단”
**(a) 왜 필요한지**
- 현재 champion/candidate가 **튜닝 대비 lockbox 개선 폭이 작고**(미세 개선), 이런 상황에서 제일 먼저 의심해야 하는 게 **미세 누수/평가 루프 과적합**입니다. 미세 누수는 “조금 좋아보이게” 만들고, 실전에서 가장 빨리 무너집니다.

**(b) 위험/부작용**
- 누수 제거는 단기적으로 성능 하락을 유발(“원래 없던 알파”가 빠짐)
- CV가 보수적으로 바뀌면 후보 PASS가 잘 안 나올 수 있음(정상)

**(c) 최소 실험(2~3개)**
- [ ] **E1** 적용(필수)
- [ ] **E3** 같이 적용해 “평가가 현실적일 때도” 유지되는지 확인
- [ ] **E5**로 노출 제약을 추가해 누수 제거 후에도 tail이 터지지 않는지 확인

**(d) PASS 조건**
- [ ] E1 게이트 통과(누수 테스트 위반 0)
- [ ] lockbox_mean이 champion 대비 **유지(하락폭 ≤ 0.5%)**면 PASS(이 단계는 ‘정화’가 목적)

---

## TOP2) 서바이버십/상장폐지 처리로 “실재현성” 확보
**(a) 왜 필요한지**
- Tech/Healthcare는 인수합병, 임상 실패, 상장폐지 등 이벤트가 잦아 **서바이버십 편향**이 백테스트를 쉽게 오염시킵니다.

**(b) 위험/부작용**
- 성과 하락 가능(특히 과거에 “결과적으로 살아남은 우량주”에 치우쳤다면)
- 데이터 파이프라인 복잡도 상승(운영 리스크도 같이 관리 필요)

**(c) 최소 실험(2~3개)**
- [ ] **E2** 적용(필수)
- [ ] **E1**과 조합(평가 프레임워크 정화)
- [ ] **E5**와 조합(유니버스가 더 현실적이면 노출이 치우치기 쉬움)

**(d) PASS 조건**
- [ ] E2 게이트(당시점 거래가능 티커 검증) 통과
- [ ] worst_mdd가 **+1%p 이상 악화 시 FAIL**, 그 외 유지/개선이면 PASS

---

## TOP3) 비용/턴오버 반영으로 “가짜 알파 제거”
**(a) 왜 필요한지**
- 성과가 미세하게만 개선되는 구간에서는 **거래비용 가정 하나**로 순위가 뒤집힙니다.
- 8~14 종목 전략은 리밸런스가 잦으면 비용 충격이 커집니다.

**(b) 위험/부작용**
- 비용 모델이 과보수면 좋은 전략도 죽일 수 있음 → 그래서 **민감도 스윕**이 필수
- 턴오버 억제로 신호 반응성이 떨어질 수 있음

**(c) 최소 실험(2~3개)**
- [ ] **E3** 적용(필수)
- [ ] **E5**로 포지션 제약(상한 weight/종목수 고정)까지 같이 걸어 운영형으로 정리
- [ ] **E4**로 리스크오프 구간 거래를 줄이는 게이팅(비용 절감 효과)

**(d) PASS 조건**
- [ ] 10bps 가정에서도 lockbox_mean이 champion 대비 **-1% 이내**(또는 유지/개선이면 더 좋음)
- [ ] turnover 상한 준수 + 비용 스윕에서 “비용↑ → 성과↓” 단조성 확보

---

## TOP4) 레짐 기반 방어 오버레이(ETF 관측만)로 tail 리스크를 먼저 줄이기
**(a) 왜 필요한지**
- Tech/Healthcare는 레짐(금리/리스크온오프)에 성과가 크게 갈립니다. 평균을 조금 올리기보다 **최악 구간(worst_mdd, lockbox_min)**부터 줄이는 게 “지속 운용”에 더 직접적입니다.

**(b) 위험/부작용**
- 레짐 분류가 채터링(자주 바뀜)하면 오히려 비용/성과 악화
- 잘못된 레짐 정의는 방어 모드가 수익 구간을 깎음

**(c) 최소 실험(2~3개)**
- [ ] **E4** 적용(필수)
- [ ] **E3** 비용 모델과 함께(게이팅이 실제로 비용/리스크를 줄이는지)
- [ ] **E1**과 함께(레짐 피처가 누수 경로가 되지 않게)

**(d) PASS 조건**
- [ ] worst_mdd **개선 또는 악화 ≤ 0.5%p**
- [ ] 레짐 전환 횟수 상한 준수(채터링 FAIL)

---

## TOP5) 포지션 구성(노출) 규칙을 하드코딩해 운영 리스크를 제거
**(a) 왜 필요한지**
- 같은 신호라도 “구성(최적화/정렬/제약)”이 바뀌면 결과가 크게 달라집니다.  
- 특히 8~14 종목 제한에서는 단일 종목/서브산업 쏠림이 곧 tail risk입니다.

**(b) 위험/부작용**
- 제약이 강하면 평균 수익이 줄 수 있음(정상)
- 구현 실수 시 제약 위반/리밸런스 오류가 운영 장애로 직결

**(c) 최소 실험(2~3개)**
- [ ] **E5** 적용(필수)
- [ ] **E3**와 결합(제약이 비용/턴오버를 줄이는지 확인)
- [ ] **E4**와 결합(리스크오프에서 포지션 수 축소 등)

**(d) PASS 조건**
- [ ] 제약 위반 0건
- [ ] lockbox_min 또는 worst_mdd가 **개선/유지**면 PASS(평균 소폭 하락은 허용)

# 2) “성능이 안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래는 **질문 없이 바로 추가**할 수 있는 진단 체크리스트입니다(리포트/로그로 자동 생성 권장).

## A. Trigger(신호 생성) 문제
- [ ] **신호 분포 붕괴 검사**: 점수의 평균/표준편차/상하위 분위수 time-series
- [ ] **rank stability**: 상위 14개 종목의 교집합 비율(리밸런스 간)
- [ ] **IC(Information Coefficient)**: 다음 기간 수익과의 상관(기간별/레짐별)

## B. Apply(적용/체결/리밸런싱) 문제
- [ ] 리밸런싱 캘린더가 의도대로인지(휴장/반쪽장/월말 등)
- [ ] “신호 계산 시점”과 “주문 가격(체결 가격)” 사이에 미래값이 끼지 않는지(E1과 연동)
- [ ] 주문이 포지션 제한(8~14, max weight)을 깨지 않는지(E5 리포트)

## C. Exposure(노출) 문제
- [ ] **Beta/Duration proxy**: QQQ/XLK/XLV/TLT에 대한 회귀 베타(관측만)
- [ ] **단일종목 기여도**: 상위 기여 1~2개 종목이 성과를 지배하는지
- [ ] Tech vs Healthcare 비중이 한쪽으로 고정되는지(레짐마다 달라져야 정상)

## D. Cost(비용) 문제
- [ ] turnover와 성과의 관계(턴오버↑인데 성과↑가 아니면 비용이 알파를 먹는 중)
- [ ] 비용 스윕 민감도 곡선(E3): 작은 bps 변화에 성과가 급변하면 “가짜 알파” 가능성

## E. Regime(시장 국면) 문제
- [ ] 레짐별 성과 분해: Risk-on/off에서 평균/최저/드로우다운 비교(E4 리포트)
- [ ] 레짐 전환 시점의 손익 기여(전환 직후 손실이 반복되면 게이팅/임계값 재조정)

# 3) 24~48시간 실행 순서(명령형)
- [ ] **T+0~6h:** E1(누수 차단) PR 1개로 구현 → 단위테스트/누수테스트 추가 → autopilot 1회
- [ ] **T+6~18h:** E3(비용/턴오버) PR 1개 → 비용 스윕 리포트 자동화 → autopilot 1회
- [ ] **T+18~30h:** E2(서바이버십/상폐) PR 1개 → 유니버스 검증 리포트 → autopilot 1회
- [ ] **T+30~42h:** E4(레짐 관측/방어) PR 1개 → 채터링 게이트 포함 → autopilot 1회
- [ ] **T+42~48h:** E5(노출/제약) PR 1개 → 제약 위반 0 리포트 → `--select-best`로 정리

실행 커맨드는 현재 handoff의 3줄을 그대로 사용(각 PR마다 1회씩 반복):
```bash
python3 experiment_system/tools/aub_autopilot.py --registry experiment_system/config/module_registry.yaml --run --select-best
python3 experiment_system/tools/system_autopilot.py --spec experiment_system/config/system_candidates.yaml --run
python3 experiment_system/tools/aub_next_fix.py --registry experiment_system/config/module_registry.yaml --output baseline/reports/next_fix.md
```

--- 

원칙적으로 **E1→E3→E2**까지가 “성능을 올리기 위한 준비(정화)”이고, **E4/E5**가 “락박스 tail 안정화”에 직접 기여하는 축입니다. 위 순서대로면 48시간 루프에서 “좋아진 것처럼 보이는 착시”를 먼저 제거하고, 그 다음에 진짜로 남는 개선만 챔피언으로 올릴 수 있습니다.
