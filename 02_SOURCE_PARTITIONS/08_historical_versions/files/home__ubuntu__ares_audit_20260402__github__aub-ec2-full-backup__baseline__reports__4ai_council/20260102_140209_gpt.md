## TOP5 우선순위 (24~48h)

### 1) (CODE) 평가/리포팅 파이프라인 “동일성” 복구 (지금 당장 최우선)
**(a) 왜 필요한지**  
- 현재 ONE TRUTH의 Champion `oos_mean=1.88`인데, No-Delta Diagnoser 출력에 **Champion OOS Mean=2.6276**로 **지표 불일치**가 이미 발생.  
- Rebalance pinpoint도 `--base-log` 파일 미존재 + CSV/JSON 파싱 실패로 **리밸런스/체결 로그가 사실상 “없음”** 상태.  
→ 성능이 “안 움직이는” 게 아니라 **측정이 깨졌을 가능성**이 높음(최악: 잘못된 지표로 오토파일럿이 최적화).

**(b) 위험/부작용**  
- 기존 결과와 “숫자”가 달라져 단기 혼란 발생(하지만 이게 정상이면 반드시 겪어야 함).  
- 실험/아티팩트 스키마를 강제하면 일부 legacy run이 로드 실패할 수 있음.

**(c) 최소 실험(공유 실험 사용): E1**
- E1에서 **metric parity + 로그 스키마 강제**를 동시에 검증.

**(d) PASS 조건(공유): E1 PASS**

### 2) (STRATEGY+CODE) 비용/슬리피지/턴오버를 “목적함수에 강제 반영”
**(a) 왜 필요한지**  
- 비용이 목적함수/게이트에 없으면, OOS가 “멈춘” 게 아니라 **실전형 성능이 숨겨진 채 과거구간 최적화**로 고착될 수 있음.  
- Tech/HC 8~14종목은 유동성은 좋지만, **리밸런스 빈도/시장충격/스프레드**가 누적되면 net이 쉽게 역전.

**(b) 위험/부작용**  
- net 성능은 단기 하락할 수 있음(현실화).  
- 비용이 과보수면 과도하게 거래를 줄여 신호가 죽을 수 있음(게이트로 제어).

**(c) 최소 실험: E2**
- E2에서 비용 모델(보수/완화 2단계)을 단일 실험 내에서 스위치 파라미터로 처리(실험 수 추가 없이).

**(d) PASS 조건: E2 PASS**

### 3) (ARCH+STRATEGY) 누수/과최적화 방지: Purged Walk-Forward + Embargo + “Shift/Shuffle” 센티널
**(a) 왜 필요한지**  
- “No-Delta”류에서 성능이 고착되면, 종종 원인은 모델이 아니라 **검증 설계(시간 인접 누수, 리밸런스 룩어헤드, 피처 정렬)**에 있음.  
- `degenerate_folds=[]`는 좋아 보이지만, **fold가 정상이어도 lookahead가 있으면 OOS가 과대**.

**(b) 위험/부작용**  
- 제대로 막으면 성능이 떨어지는 것이 정상(진짜 실력만 남음).  
- 데이터 길이가 짧으면 표본 손실로 분산 증가.

**(c) 최소 실험: E3**
- E3에서 purge/embargo + 타깃 시프트(+1D) + 라벨 셔플(무작위) 센티널을 함께 돌려 “누수 신호”를 판정.

**(d) PASS 조건: E3 PASS**

### 4) (DATA) 서바이버십/기업행위(Point-in-time) 강제 + 유니버스 재현성 고정(Tech/HC 8~14)
**(a) 왜 필요한지**  
- US 주식에서 백테스트가 안 움직일 때, 실제로는 **유니버스/티커 히스토리/스플릿/합병/상폐** 처리 문제로 학습/검증이 미묘하게 바뀌어 “성능이 둔감”해지는 케이스가 많음.  
- 특히 “현재 살아남은 티커만”으로 과거를 구성하면 OOS가 왜곡되고, 실험 간 비교가 무의미해짐.

**(b) 위험/부작용**  
- PIT 적용 시 과거 성능 하락이 정상.  
- 데이터 소스 비용/구현 복잡도 증가.

**(c) 최소 실험: E4**
- E4에서 PIT on/off를 비교(동일 코드/동일 시드/동일 리밸런스 규칙)하여 왜곡 크기 측정.

**(d) PASS 조건: E4 PASS**

### 5) (OPS+RISK) 운영 리스크 게이트(노출/드로다운/데이터 결측/거래 불능) + worst_mdd 산출 누락 제거
**(a) 왜 필요한지**  
- ONE TRUTH에 `worst_mdd: None` → **핵심 리스크 지표가 계산/로깅되지 않음**. 이 상태에서 오토루프는 “수익률만” 보고 잘못된 챔피언을 유지할 수 있음.  
- 노출이 `0.47~0.84`로 상단이 높고, 리스크 게이트 없으면 레짐 변화에서 급락 가능.

**(b) 위험/부작용**  
- 게이트를 강하게 걸면 거래가 줄어 성능이 떨어질 수 있음.  
- 하지만 운영 안정성(중단/오류/비정상 포지션)을 막는 효과가 더 큼.

**(c) 최소 실험: E5**
- E5에서 “하드 게이트 + 킬스위치 + mdd 산출 강제”를 적용해 정상 운용 가능성 확인.

**(d) PASS 조건: E5 PASS**

# 48시간 자동 루프용: 실행 가능한 실험 5개 (정의/게이트/기대 관측치)

## E1) Metric Parity & Logging Contract (평가 동일성/리밸 로그 복구)
**(1) 실험 정의 (명령형 체크리스트)**  
- 동일 데이터 스냅샷(날짜/소스 해시) + 동일 시드로 **Champion과 Candidate를 “같은 평가 함수”로 재평가**하라.  
- 평가 결과물에 아래 “계약 스키마”를 강제하라(없으면 실패 처리):  
  - `metrics.json`(oos_mean/oos_min/worst_mdd/exposure_minmax/turnover/cost_net)  
  - `trades.parquet`(timestamp, ticker, qty, price, side, slippage_bps, fee_bps)  
  - `rebalance.jsonl`(rebalance_id, target_weights, realized_weights, reason_codes)  
- `aub_rebalance_pinpoint.py`가 **파일 미존재/파싱 실패 없이** 끝나도록 I/O를 수정하라(경로 기본값 제거, 아티팩트 경로를 run manifest에서 resolve).

**(2) 게이트 (PASS 조건)**  
- Diagnoser의 Champion OOS Mean vs ONE TRUTH oos_mean이 **|Δ| ≤ 1%** 이내로 수렴하라(동일 평가면 거의 같아야 함).  
- rebalance pinpoint가 “No rebalance data found” 없이 완료되며, 최소 1개 이상의 리밸 이벤트를 로드하라.  
- `worst_mdd`가 None이 아니어야 한다.

**(3) 기대 관측치**  
- 2.6276 vs 1.8815 불일치가 “평가 함수/기간/비용/노출 정의 차이” 중 하나로 귀결되고, 차이 원인이 리포트로 남는다.  
- 이후 실험에서 “성능이 안 움직임”이 측정 문제인지 실제 문제인지 분리된다.

## E2) 비용 모델 주입(슬리피지/수수료/턴오버 패널티) + net 기준으로 챔피언 선정
**(1) 실험 정의 (명령형 체크리스트)**  
- 모든 체결에 대해 비용을 적용하라:  
  - 슬리피지: `max(spread_proxy, k * daily_vol / adv_proxy)` 형태의 보수적 bps(간단히 고정 bps도 가능)  
  - 수수료: 고정 bps  
  - (쇼트가 있으면) borrow bps(없으면 0으로 명시)  
- 목적함수/랭킹을 **gross → net**으로 전환하라.  
- 동일 run에서 비용 수준 2단계만 비교하라(“보수/완화” 플래그) — 실험 수 추가 금지.

**(2) 게이트 (PASS 조건)**  
- net oos_mean이 gross 대비 하락하더라도,  
  - (a) net oos_min이 0 아래로 붕괴하지 말 것(전략이 비용에 즉시 죽으면 실패)  
  - (b) turnover(또는 거래 횟수)가 이전 대비 의미 있게 낮아질 것(예: -15% 이상)  
- 비용 수준(보수/완화) 간 순위가 뒤집히면, “비용 민감”으로 라벨링하고 다음 실험에서 거래 제약을 강화하라.

**(3) 기대 관측치**  
- 성능이 “안 움직이는” 이유가 사실 **gross 기준 최적화 고착**인지 드러난다.  
- 거래가 많은 전략이 자동으로 배제되어 OOS 분산이 줄어든다.

---

## E3) 누수 센티널: Purged Walk-Forward + Embargo + Shift/Shuffle 테스트
**(1) 실험 정의 (명령형 체크리스트)**  
- Walk-forward를 **purge window + embargo**로 재구성하라(리밸 주기/피처 윈도우 길이를 반영).  
- 센티널 2개를 같은 파이프에서 수행하라:  
  - Label shift(+1D): 예측 타깃을 1일 뒤로 밀어서 성능이 유지되면 누수 의심  
  - Label shuffle: 라벨 무작위에서 성능이 유의미하면 누수/버그 확정  
- 결과를 `leakage_report.md`로 자동 요약하라(shift/shuffle 대비 본 실험의 상대 성능).

**(2) 게이트 (PASS 조건)**  
- Shuffle 성능은 0 근처로 수렴해야 한다(예: oos_mean이 본 실험의 20% 미만).  
- Shift(+1D) 성능은 본 실험 대비 **유의미하게 하락**해야 한다(유지되면 룩어헤드 가능성).  
- Purge/embargo 적용 후에도 본 실험이 여전히 양(+)의 net 성능을 유지해야 한다(완전 붕괴 시 과최적화로 판정).

**(3) 기대 관측치**  
- “성능 고착”이 데이터 정렬/룩어헤드/인접 누수 때문인지 즉시 판별된다.  
- 참이면 이후 전략 튜닝이 아니라 **데이터/검증 수리**가 우선이 된다.

---

## E4) PIT(서바이버십/기업행위) on/off 비교 + 유니버스 고정(Tech/HC 8~14)
**(1) 실험 정의 (명령형 체크리스트)**  
- 유니버스를 **고정 리스트(Tech+HC 8~14)**로 선언하고, 실험 동안 종목 수가 변하면 실패 처리하라(상폐/합병은 PIT 이벤트로 반영).  
- PIT off(현재 티커 기준 히스토리) vs PIT on(당시 기준 존재/상폐 포함, 스플릿/심볼변경 반영) **동일 조건 비교**를 수행하라.  
- corporate action 처리(스플릿/배당 조정)의 on/off 상태를 명시적으로 로깅하라.

**(2) 게이트 (PASS 조건)**  
- PIT on에서 결과가 악화되더라도,  
  - 성능 방향이 완전히 붕괴(예: oos_mean < 0 또는 oos_min 급락)하면 기존 백테스트가 편향 가능성이 높으므로 **PIT on을 기본으로 승격**하라.  
- 종목 수가 8~14 범위를 벗어나면 run을 실패로 처리하라(유니버스 재현성 깨짐).

**(3) 기대 관측치**  
- 과거 성능이 “너무 안정적”이었던 이유가 서바이버십일 수 있음을 정량화한다.  
- 이후 실험 비교가 “동일 유니버스”에서 일어나 실험 간 델타가 의미를 갖는다.

## E5) 운영/리스크 하드 게이트 + worst_mdd 산출 강제(노출/데이터/거래 불능)
**(1) 실험 정의 (명령형 체크리스트)**  
- 아래 하드 게이트를 백테스트/페이퍼 모두에 동일 적용하라:  
  - `worst_mdd` 계산 누락 시 즉시 실패  
  - 노출(exposure) 상한/하한 강제(예: 0.2~0.85) + 위반 시 포지션 스케일다운  
  - 단일 종목 비중 상한(예: 20~25%)  
  - 데이터 결측/가격 0/거래정지 감지 시 해당 종목 비중 0 + reason_code 로깅  
- “킬스위치”: 연속 N회(예: 3회) 게이트 실패 시 다음 48h 루프에서 **전략 탐색 중단하고 파이프라인 수리 모드**로 전환하라.

**(2) 게이트 (PASS 조건)**  
- `worst_mdd`가 항상 수치로 산출되어야 한다(None 금지).  
- 게이트 위반(reason_code)이 발생해도 run이 조용히 진행되지 말고, 리포트에 집계되어야 한다.  
- 노출이 관측된 범위 내에서 안정화되고(현재 0.47~0.84), 상단이 규정치를 넘지 않아야 한다.

**(3) 기대 관측치**  
- “성능이 안 움직임”이 실제로는 **게이트에 의해 트레이드가 억제**되거나, 반대로 **리스크 지표 누락으로 잘못된 챔피언 유지**였는지 드러난다.  
- 운영 중 갑작스런 데이터 사고/체결 불능이 손실로 이어지는 경로가 차단된다.

# 성능이 안 움직일 때: 원인 분해(트리거/적용/노출/비용/레짐) 체크 트리 (질문 없이 실행 지시)

## A) Trigger(신호 생성) 문제
- 피처/라벨 타임스탬프 정렬을 덤프하여 “피처 최대 시점 ≤ 의사결정 시점”을 강제 검증하라.  
- E3의 shift/shuffle 센티널 결과를 상시 저장하고, shift가 유지되면 룩어헤드로 즉시 분류하라.  

## B) Apply(신호 적용/리밸런스) 문제
- `rebalance.jsonl`에서 **target_weights vs realized_weights** 괴리를 집계하라(체결 불능/제약/라운딩).  
- “신호는 변하는데 포지션이 안 변함”이면: 최소 주문 단위/라운딩/거래 제한/게이트가 원인이다(Reason code로 분류).

## C) Exposure(노출/포지션 스케일링) 문제
- 노출이 0.47~0.84로 좁게 고정이면, 스케일러/리스크 패리티/헤지 파라미터가 사실상 클리핑 중일 수 있다.  
- 포지션 스케일링 함수 입력(변동성, 상관, 목표 리스크)을 로깅하고 “클리핑 발생률”을 지표화하라.

## D) Cost(비용) 문제
- gross/net을 항상 함께 리포팅하고, `net = gross - cost`에서 cost 기여도를 분해하라(슬리피지/수수료/borrow).  
- turnover와 성과의 상관을 리포트로 찍어 “거래가 많을수록 손해” 구간을 레짐 태그로 남겨라.

## E) Regime(시장 국면) 문제
- ETF는 매매 금지이므로 **관측 지표로만** 사용하라:  
  - QQQ(Tech), XLV(Health), VIX(변동성) 등으로 “고변동/저변동, Tech 우세/Health 우세” 레짐 태깅만 하라.  
- 레짐별 성과를 분해해 “전체 평균이 고착”인지 “레짐 상쇄”인지 판정하라(예: Tech 강세에서만 수익, 그 외 손실).

## 24~48시간 실행 순서(명령형 체크리스트)
1. **E1 먼저 실행**해서 지표 불일치(2.6276 vs 1.8815)와 리밸 로그 로딩 실패를 제거하라.  
2. E1 PASS 후 **E5를 즉시 적용**해 worst_mdd 산출/운영 게이트를 강제하라(루프 안전장치).  
3. 그 다음 **E3(누수 센티널)**로 “튜닝해도 안 오르는” 원인이 데이터/검증인지 확정하라.  
4. **E2(비용)**로 net 기준 최적화로 전환하라(실전형 선택 압력 부여).  
5. **E4(PIT)**로 서바이버십 왜곡 여부를 정량화하고, PIT on을 기본값으로 승격 여부 결정하라.

이 5개를 통과하면, 그 다음 단계(전략 신호 자체 개선/레짐 적응형 가중/리밸 주기 최적화)를 “측정/운영이 정상인 상태”에서 진행할 수 있다.
