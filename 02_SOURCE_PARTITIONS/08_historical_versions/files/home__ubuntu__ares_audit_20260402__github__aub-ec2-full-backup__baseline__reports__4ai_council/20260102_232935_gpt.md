## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — 명령형 체크리스트

### 1) **평가/로깅 파이프라인 복구(재현성 + 리밸런스 로그)**
(a) **왜 필요한지**
- `lane_hash/run_hash None`, `worst_mdd None`, `rebalance_pinpoint`가 입력을 못 읽음(파일/JSON 깨짐) → **“성능이 안 움직이는” 1순위 원인이 ‘전략’이 아니라 ‘측정 불능’일 가능성**이 큼.
- No-Delta diagnoser가 “실험 9개”를 찾았는데도 delta가 안 보이면, **실제로는 리밸런스/노출/비용 로그가 누락되어 변화가 관측되지 않거나 동일 run을 반복** 중일 수 있음.

(b) **위험/부작용**
- 스키마 통일 과정에서 과거 아티팩트 호환 깨짐.
- “지표가 바뀌는 것”이 “전략이 바뀐 것”처럼 보이는 착시 발생(초기 1~2회는 기준선 재설정 필요).

(c) **최소 실험(1개 패치 안에 2~3 변형으로 묶어서 실행)**
- **PATCH-LOG-1**: 리밸런스 로그를 *항상* `rebalance.jsonl`로 남기고, `rebalance.csv`는 선택 생성으로 강제
  - 변형 A: 현행 JSON 포맷 유지 + jsonl writer 추가(append)
  - 변형 B: base-log 경로 자동 탐색(최근 champion run의 artifacts에서 자동 탐색)
  - 변형 C: `pinpoint` 입력이 없을 때 “0 trades/0 turnover”를 명시적으로 출력(침묵 실패 금지)

(d) **PASS 조건(게이트)**
- 최근 3회 연속 run에서:
  - `rebalance.jsonl` 생성됨(파일 크기 > 0)
  - `pinpoint report`가 **trade count / turnover / avg holding**을 출력
  - `oos_mean` 재계산이 동일 seed에서 ±1% 이내 재현

**48시간 자동 루프 형태**
- (1) 실험 정의: PATCH-LOG-1 적용 후 동일 챔피언 설정 2회 재실행 + 후보 1회 실행  
- (2) 게이트: 위 PASS 충족 시에만 다음 패치 진행  
- (3) 기대 관측치: “전략이 움직였는지/안 움직였는지”가 **리밸런스·노출·비용 분해로 보임**

### 2) **누수(lookahead)·서바이버십·타임스탬프 정렬 우선 감사(US Tech+Healthcare 8~14 고정)**
(a) **왜 필요한지**
- OOS 평균이 보고마다 다름(예: 3.32 vs 2.63) + degenerate_folds 존재 → **데이터 분할/라벨 정렬/유니버스 정의가 흔들리면 “개선”이 무의미**.
- Tech/Healthcare 소수 종목(8~14) 구성에서 **서바이버십(현재 살아남은 종목만 포함)**은 성능을 과대평가하는 대표 원인.

(b) **위험/부작용**
- 누수 제거하면 단기적으로 OOS가 떨어질 수 있음(정상).
- PIT(point-in-time) 데이터로 바꾸면 데이터 결측이 늘어 모델이 “거의 거래 안 함”으로 수렴할 수 있음.

(c) **최소 실험**
- **PATCH-DATA-1**: “as-of” 강제 + 발표시점 이후만 사용(특히 헬스케어: 임상/실적/가이던스 반영 타이밍)
  - 변형 A: 모든 feature를 `t-1 close 기준`으로만 생성(당일 종가/당일 발표 혼입 방지)
  - 변형 B: 유니버스 고정 파일(8~14 tickers) + **기간 내 상장폐지/합병 이벤트 처리 규칙** 명시(가격 0 처리 금지, 마지막 거래일까지만)
  - 변형 C: “라벨 1일 shift 테스트” 자동화(특징을 +1일 밀었을 때 성능 급락하면 누수 의심 플래그)

(d) **PASS 조건**
- 누수 체크:
  - Feature +1일 shift 시 OOS가 “그럴듯한 수준으로” 하락(예: 30~70% 감소)하고, **오히려 상승하면 FAIL**
- 서바이버십 체크:
  - 유니버스 구성 파일이 run artifact에 고정 저장되고 hash가 기록됨
- degenerate_folds가 0 또는 1 이하로 감소(현재 [1,2,3,8] → 구조적 문제 가능)

**48시간 자동 루프**
- (1) 실험 정의: PATCH-DATA-1 적용 후 1회 전체 백테스트 + 1회 shift 테스트  
- (2) 게이트: shift 테스트/유니버스 hash 기록 통과 시만 다음 진행  
- (3) 기대 관측치: “성능 하락하더라도” 분산/안정성↑, fold 붕괴↓

### 3) **비용(수수료/스프레드/슬리피지) 미반영 가능성 제거 + 턴오버 상한**
(a) **왜 필요한지**
- 리밸런스 로그가 없어서 비용이 실제로 적용되는지 불명.
- 소수 종목 전략은 리밸런스가 잦아지면 **OOS가 ‘알파’가 아니라 ‘마찰비용 미반영’으로 보이는** 케이스가 많음.

(b) **위험/부작용**
- 비용을 넣는 순간 성능이 급락할 수 있음(정상).
- 과도한 턴오버 제한은 신호를 “항상 홀드”로 만들어 무의미해질 수 있음.

(c) **최소 실험**
- **PATCH-COST-1**: 3단 비용 티어를 *동일 코드 경로*로 스윕(실험 1개로 묶기)
  - 변형 A(낙관): 1bp 수수료 + 2bp 슬리피지
  - 변형 B(기준): 1bp + (half-spread 5~10bp, 거래대금/변동성 기반)
  - 변형 C(보수): 2bp + 15bp + 시장충격(거래비중 기반 간단함수)
  - 동시에: turnover cap(예: 일 50% 또는 주 150% 중 하나) 걸고 위반 시 주문 스케일링

(d) **PASS 조건**
- 비용 티어 B에서:
  - 거래가 “0으로 붕괴”하지 않을 것(trade count 최소치 설정)
  - OOS mean이 과도하게 무너지면(예: 50%+ 하락) → **기존 알파가 비용 의존**으로 판정(그 자체로 유의미한 결론)
- 티어 간 성능 민감도가 합리적(보수 티어가 항상 더 나쁘게)

**48시간 자동 루프**
- (1) 실험 정의: PATCH-COST-1 1회 실행(티어 스윕 포함)  
- (2) 게이트: trade count/turnover/cost attribution 출력 필수  
- (3) 기대 관측치: “알파 vs 비용” 분해표가 생기고, 개선 방향이 ‘신호’인지 ‘집행’인지 결정 가능

### 4) **노출(Exposure)·폴드 붕괴(degenerate_folds) 방지: 포트폴리오 제약/리스크 타기팅**
(a) **왜 필요한지**
- 현재 `exposure min/max: 0.0 / 0.8388` → 상당 기간 **현금화** 가능성.  
  “성능이 안 움직임”이 **실제로는 거의 포지션이 없어서**일 수 있음.
- degenerate_folds는 “학습/검증 구간에서 거래가 없거나 라벨이 단일” 같은 구조적 문제 신호.

(b) **위험/부작용**
- 최소 투자비중 강제 시, 약세 구간 손실이 커질 수 있음.
- 제약이 너무 빡세면 신호가 무시되고 동일 포지션으로 고착(또 다른 no-delta).

(c) **최소 실험**
- **PATCH-RISK-1**: “항상 투자”가 아니라 “조건부 최소 노출 + 변동성 타기팅”으로 강제
  - 변형 A: net exposure 바닥 40~60% (신호가 약하면 균등분산으로 채움)
  - 변형 B: 종목별 max weight(예: 20~25%), 섹터(Tech/HC) 비중 범위 강제
  - 변형 C: realized vol 타기팅으로 포지션 스케일(포지션 크기만 조절, 종목 선택은 유지)

(d) **PASS 조건**
- exposure가 0에 붙어 있는 구간 비율이 크게 감소(예: 전체 일수의 5% 이하)
- fold별 trade count가 최소치 이상(모든 fold에서 최소 N회 이상) → degenerate_folds 감소

**48시간 자동 루프**
- (1) 실험 정의: PATCH-RISK-1 1회 실행  
- (2) 게이트: exposure histogram + fold별 거래수 출력  
- (3) 기대 관측치: “거래/노출이 실제로 존재”하게 되며 no-delta가 ‘측정 문제’인지 ‘신호 문제’인지 분리됨

### 5) **레짐/헤지(ETF는 관측지표만) 게이트 재정의: Tail-risk 감소 확인**
(a) **왜 필요한지**
- 로그에 `...hedge_025`가 보이는데, 실제로 헤지/레짐이 동작했는지 관측 불가.  
- ETF 매매는 금지이므로, **QQQ/XLV 등은 “시장 상태 지표”로만** 써서 위험구간에서 노출을 줄이는 게 현실적.

(b) **위험/부작용**
- 레짐 필터가 과도하면 “항상 OFF”가 되어 또 no-delta.
- 잘못된 지표(과최적화된 임계값)는 OOS에서 효과 상실.

(c) **최소 실험**
- **PATCH-REGIME-1**: 단순·강건 레짐 2개를 고정하고, 임계값을 학습하지 말 것(하드코드)
  - 변형 A: QQQ(Tech proxy) 50DMA 하회 + VIX proxy 상승(또는 QQQ realized vol 상위 분위) → 노출 50%로 컷
  - 변형 B: XLV(Healthcare proxy) 상대강도( XLV/QQQ ) 하락 시 헬스케어 비중 상한 축소
  - 변형 C: 레짐 상태를 매일 로그(STATE=RISK_ON/OFF)로 남겨 “항상 동일 상태”인지 감시

(d) **PASS 조건**
- 레짐 상태가 기간 내 최소 5~10회 이상 전환(항상 ON/OFF면 FAIL)
- downside tail(최악 5% 일수익률 또는 CVaR)가 개선되거나, 비용 반영 후 MDD가 유의미하게 감소

**48시간 자동 루프**
- (1) 실험 정의: PATCH-REGIME-1 1회 실행  
- (2) 게이트: 레짐 state 전환 횟수 + tail 지표 출력  
- (3) 기대 관측치: 평균수익 변화가 작아도 “꼬리 위험”에서 차이가 나타남(전략 가치 확인)

## “성능이 안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 실행 순서 트리

아래를 **매 실행(48시간 루프)마다 자동 출력**하도록 고정(질문 없이 진단되게):

### A. 트리거(신호 생성) 레벨
- **Signal coverage**: (종목×일자) 중 신호가 NaN/0인 비율
- **Signal variance**: 신호 분산이 0에 가까우면 “항상 같은 점수” → 파라미터가 죽었거나 데이터 정렬 실패
- **Shift test**: feature를 +1일 밀어도 성능이 유지/개선되면 누수 의심

### B. 적용(리밸런스/주문 생성) 레벨
- **Trade count = 0?** → 리밸런스 조건/캘린더/휴장 처리/최소 주문단위 때문에 미체결 가능
- **Turnover = 0?** → 주문이 스케일링에 의해 0으로 잘렸는지(제약/슬리피지/현금부족)
- **Constraint binding report**: “어떤 제약이 몇 %의 날짜에서 바인딩 되었는지” (max weight, exposure cap 등)

### C. 노출(포지션) 레벨
- **Exposure time series**: 0에 붙는 구간 비율, 평균 gross/net
- **Concentration**: 상위 1~2종목 비중이 지나치면 성능이 한두 이벤트에 종속(서바이버십 착시와 결합)

### D. 비용(마찰) 레벨
- **Cost attribution**: 총 PnL = gross alpha − (commission + spread + impact)
- **Sensitivity**: 비용 티어 A/B/C에서 순위가 바뀌면 “고빈도/고턴오버 알파” 가능성

### E. 레짐(시장 상태) 레벨
- **Regime state occupancy**: ON/OFF 점유율과 전환 횟수
- **Conditional performance**: RISK_ON과 RISK_OFF에서 성능/노출이 어떻게 달라지는지(달라지지 않으면 레짐 로직이 무의미)

### F. 폴드/검증 붕괴 레벨(degenerate_folds)
- fold별로
  - 거래수/노출 평균/라벨 분포(상승일만 존재 등)
  - “한 fold라도 거래 0이면” 그 fold는 평가 불가 → 전체 OOS 비교가 무의미

## 24~48시간 실행 우선순위(권장 실행 순서)
1) **PATCH-LOG-1** 통과(측정 가능하게 만들기)  
2) **PATCH-DATA-1** 통과(누수/서바이버십 제거)  
3) **PATCH-COST-1**로 알파-비용 분해  
4) **PATCH-RISK-1**로 노출/degenerate_folds 교정  
5) **PATCH-REGIME-1**로 tail 개선 확인

이 순서로 돌리면 “전략을 바꿔도 성능이 안 움직이는” 상황을 **측정/데이터/집행/노출/레짐 중 어디에서 막히는지** 48시간 내에 강제 분리할 수 있음.
