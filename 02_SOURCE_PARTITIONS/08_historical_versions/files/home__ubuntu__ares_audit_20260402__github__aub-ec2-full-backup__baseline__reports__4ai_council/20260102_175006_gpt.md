## 0) 24~48시간 “우선 점검(리스크 우선)” 명령형 체크리스트
- **[누수]** 학습/검증/실거래 시점 기준으로 *feature/label/필터*가 미래정보를 참조하지 않는지 **point-in-time(PTI) 감사**를 먼저 돌려라.
- **[과최적화]** `degenerate_folds: [1,2,3,8]` 원인을 즉시 제거하라(폴드 무효/거래 0/노출 0 등). 폴드가 무너지면 OOS 평균은 의미가 없다.
- **[서바이버십]** 유니버스가 “현재 생존 종목 목록”을 참조하지 않도록, **해당 날짜에 존재했던 종목/상장상태/분할/합병**을 반영하라.
- **[비용 미반영]** 리밸런스 로그가 깨져 비용/회전율 검증이 불가하다(현재 `aub_rebalance_pinpoint`가 입력을 못 읽음). **거래 로그를 표준 포맷으로 강제 출력**하라.
- **[운영 리스크]** `lane_hash/run_hash None`, 챔피언 파일 경로 공란은 재현성/감사 불능 상태다. **실험 아티팩트/메타데이터 강제 저장을 “실패 시 런 중단”으로 바꿔라.**

# TOP1) 데이터/라벨 누수 + 서바이버십 “PTI 감사”를 자동 게이트로 만들기
### (a) 왜 필요한지
- OOS가 움직이지 않거나 과대평가되는 가장 흔한 원인은 **미세 누수/서바이버십**이다.
- Tech/Healthcare는 **리밸런스 빈도↑, 이벤트(실적/임상) 민감↑**이라 누수에 특히 취약하다.

### (b) 위험/부작용
- 누수 제거 시 **성능이 급락**할 수 있다(정상).
- PTI 데이터가 부족하면 일부 feature가 제거되어 **신호 약화** 가능.

### (c) 최소 실험 2~3개 (E1~E5 재사용)
- **E2 (CV/폴드 정상화)**: purge/embargo 포함한 워크포워드로 폴드를 재정의(폴드 붕괴 제거).
- **E4 (유니버스 고정+PTI)**: 8~14개 종목 고정 + 종목/상장상태/Corporate action을 날짜 기준으로 스냅샷.
- **E1 (프로비넌스/로그 강제)**: 어떤 데이터 버전/캘린더/조정가격을 썼는지 메타데이터 저장 강제.

### (d) PASS 조건
- 모든 폴드에서 **거래 수/노출/분산이 0이 아닌** 정상 상태(=degenerate fold 0).
- PTI 감사 리포트에서 **미래 참조 feature 0건**.
- 누수 제거 후에도 **after-cost OOS mean이 “0 이상” 유지 + oos_min이 안정적(급락 완화)**.

# TOP2) “degenerate folds” 제거: 평가 프레임 자체를 복구하기
### (a) 왜 필요한지
- 현재 `degenerate_folds`가 존재 → OOS 평균/최저치가 **의미 없는 숫자**일 가능성이 높다.
- 챔피언 OOS mean이 3.32 vs 2.63으로 서로 다른 값이 노출 → **리포팅 정의/집계 불일치** 가능.

### (b) 위험/부작용
- 평가가 엄격해져 **숫자가 낮아짐**(정상).
- 워크포워드/엠바고 적용 시 데이터 효율이 떨어져 **분산 증가**.

### (c) 최소 실험 2~3개
- **E2 (폴드 재정의 + 폴드 게이트)**: 폴드별 최소 거래수/최소 분산/최소 노출을 만족 못하면 런 실패 처리.
- **E1 (메트릭 정의 단일화)**: OOS mean 산식/구간/연환산 방식/after-cost 여부를 `run_hash`에 고정 기록.
- **E4 (유니버스 고정)**: 폴드마다 종목 구성이 달라져 퇴화하는 경우를 차단.

### (d) PASS 조건
- `degenerate_folds == []`
- 동일 `run_hash` 기준으로 리포트 간 **OOS mean 불일치 0**
- 폴드별 성능 분산이 “이상치(특정 폴드만 폭발)” 형태가 아닌지 통계적으로 확인(예: 폴드별 샤프 편차 상한).

# TOP3) 비용/회전율/리밸런스 로그를 “자동 루프 필수 산출물”로 만들기 (현재 도구가 실패함)
### (a) 왜 필요한지
- 지금 상태는 리밸런스 데이터 로딩이 실패 → **비용 미반영/운영 검증 불가**.
- Tech 대형주라도 **회전율이 높으면 슬리피지로 엣지가 사라진다**.

### (b) 위험/부작용
- 비용을 넣으면 성능이 하락할 수 있다(정상).
- 슬리피지 모델을 과하게 잡으면 **거래가 과도하게 억제**될 수 있다.

### (c) 최소 실험 2~3개
- **E1 (로그 포맷 고정 출력)**: `rebalance.csv` + `rebalance.jsonl`을 항상 생성(없으면 런 실패).
- **E3 (비용 모델 삽입)**: 스프레드/임팩트(ADV 기반) + 수수료를 after-cost에 반영.
- **E2 (최소 거래 단위/턴오버 게이트)**: 폴드별 턴오버 상한/거래 횟수 상한을 게이트로 둬 과회전을 차단.

### (d) PASS 조건
- `aub_rebalance_pinpoint`가 **에러 없이 리포트 생성**.
- after-cost 기준으로도 **OOS mean이 baseline 대비 악화 폭이 제한(예: -X% 이내)** 또는 개선.
- 턴오버/슬리피지가 **특정 일자(실적 주간 등)에 폭증하지 않음**(상한 위반 0).

# TOP4) 노출/리스크(드로우다운, 집중도) 운영 게이트 추가: “실전 운영 가능 형태”로 제한
### (a) 왜 필요한지
- 현재 노출 `max ~0.84`는 가능하지만, **worst_mdd None**은 계산/로그 결함 가능성이 높다.
- 8~14 종목 집중 포트는 **단일 종목 이벤트 리스크**가 크다(Tech/HC 특히).

### (b) 위험/부작용
- 리스크 제한이 신호를 “눌러” 성능이 감소할 수 있다.
- 게이트가 너무 타이트하면 **거래가 거의 없어** 다시 폴드 퇴화로 이어질 수 있다.

### (c) 최소 실험 2~3개
- **E4 (유니버스 8~14 고정 + 종목당 상한)**: 예) 종목당 12~15% 상한, 섹터별 상한.
- **E5 (레짐 게이트로 gross exposure 조절)**: QQQ/XLV/IEF(관측지표)로 위험 국면에서 노출 축소.
- **E1 (MDD/리스크 메트릭 강제 산출)**: worst_mdd/VAR/노출 히스토그램을 런 산출물로 강제.

### (d) PASS 조건
- `worst_mdd`가 None이 아니라 **항상 수치로 산출**.
- 종목/섹터 상한 위반 0, 노출 상한 위반 0
- OOS min(최악 구간)이 **명확히 개선**(tail 완화) 또는 비용 반영 후에도 생존.

# TOP5) “성능이 안 움직이는” 원인(트리거/적용/노출/비용/레짐)을 분해하는 관측체계 구축
### (a) 왜 필요한지
- 이미 `No-Delta Diagnoser`가 “9 experiments”를 찾았는데도 성능 변화가 제한적이면,
  - 신호가 실제로 포지션에 반영되지 않거나,
  - 반영돼도 비용/레짐으로 상쇄되거나,
  - 평가/폴드 문제로 가려졌을 가능성이 높다.

### (b) 위험/부작용
- 로깅/관측 지표가 늘어나며 실행 시간이 증가.
- 잘못된 분해 지표는 오히려 혼란을 만든다(지표 정의 단일화 필요).

### (c) 최소 실험 2~3개
- **E1 (관측 로그 확장)**: “트리거→시그널→스케일→주문→체결(가정)→비용→PnL” 단계별 테이블 저장.
- **E3 (비용 분해)**: 총 PnL을 **gross / slippage / spread / commission**으로 분해 저장.
- **E5 (레짐 태깅)**: 레짐(리스크온/오프, 금리상승, 헬스케어 방어)을 날짜별 태그로 저장.

### (d) PASS 조건
- “왜 안 움직였는지”가 **하나의 런 리포트에서** 단계별로 설명 가능(예: 시그널 변화는 있었지만 적용 스케일=0이었다).
- 레짐별 성능 테이블에서 **최소 2개 레짐 간 통계적 차이**가 관측(없으면 레짐 특징이 무의미).

## 2) 실행 가능한 “패치/실험” 5개 (48시간 자동 루프용: 정의→게이트→기대 관측치)
아래 5개만 돌려라(이 이상 확장 금지).

### E1) 메타데이터/리밸런스 로그/리스크 지표 “강제 산출” 패치
- **(1) 실험 정의**: 모든 런에서 아래 파일/필드 없으면 실패 처리  
  - `run_hash`, `lane_hash`, 데이터 버전, 캘린더, 조정가격 타입  
  - `rebalance.csv` + `rebalance.jsonl` (최소: timestamp, ticker, target_w, delta_w, price, shares, notional)  
  - 리스크: worst_mdd, turnover, exposure stats
- **(2) 게이트**: 산출물 누락/파싱 실패 시 **즉시 FAIL**
- **(3) 기대 관측치**:  
  - `aub_rebalance_pinpoint` 에러 0  
  - 챔피언/후보 리포트 간 OOS mean 불일치 감소(정의 고정)

### E2) 폴드/워크포워드 재정의 + purge/embargo + 폴드 퇴화 차단
- **(1) 실험 정의**: 시간순 워크포워드, 라벨 룩어헤드에 맞춘 embargo 적용, 폴드별 최소 거래수/노출/분산 조건 추가
- **(2) 게이트**: `degenerate_folds != []`면 FAIL
- **(3) 기대 관측치**: OOS 변동이 “평가 인공물”이 아니라 실제 변화로 해석 가능

### E3) 비용 모델 삽입(After-cost를 기본 메트릭으로)
- **(1) 실험 정의**: 스프레드+슬리피지(ADV/변동성 기반 단순모형)+수수료를 PnL에 반영, PnL 분해 로그 저장
- **(2) 게이트**: after-cost OOS가 gross 대비 “비용 상식 범위”를 벗어나면 FAIL(예: 비용이 음수로 PnL을 올리는 경우)
- **(3) 기대 관측치**: 고회전 전략의 성능이 합리적으로 감소하거나, 회전 억제의 필요성이 수치로 드러남

### E4) 유니버스 8~14 (US Tech+Healthcare) 고정 + 집중도 상한
- **(1) 실험 정의**: 8~14 종목만 사용(예: Tech/HC 대형주 중심), 종목/섹터 상한 도입, PTI membership 적용
- **(2) 게이트**: 종목 수/상한 위반 0, PTI 위반 0
- **(3) 기대 관측치**: 결과의 재현성↑, 서바이버십/유니버스 변동으로 인한 폴드 붕괴↓, tail 리스크 관리 가능

### E5) 레짐 관측(ETF는 지표로만) + 노출 스케일 게이트
- **(1) 실험 정의**: QQQ/XLV/IEF(or TLT)/VIX proxy를 “관측 지표”로 레짐 태깅, 레짐에 따라 gross exposure를 스케일(예: 리스크오프면 0.3x)
- **(2) 게이트**: 레짐 전환 시 노출 급변(갭) 상한 위반 0, 거래 정지로 인한 폴드 퇴화 0
- **(3) 기대 관측치**: OOS min 개선(꼬리 손실 완화), 레짐별 성능 차이가 리포트로 분리됨

## 3) “성능이 안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래 트리를 그대로 로그/리포트 구조로 구현해 원인을 고정 위치에서 찾아라.

### A. 트리거(Trigger): “신호가 실제로 변했나?”
- 점검: feature/alpha 값의 분산, 상관, 유효 표본 수, 결측률
- 증상: 알파 분산≈0 → 파라미터가 죽었거나 데이터가 평탄화됨

### B. 적용(Apply): “신호가 포지션으로 변환됐나?”
- 점검: signal→target_w 매핑 후 **클리핑/중립화/정규화**로 인해 target이 0으로 수렴했는지
- 증상: 신호는 있는데 target_w가 항상 0 근처 → 스케일/게이트가 과도하거나 버그

### C. 노출(Exposure): “노출이 성과를 낼 만큼 존재했나?”
- 점검: gross/net, 종목별 평균/최대 비중, 현금비중, 리밸런스 주기별 실제 변경량
- 증상: 노출 min/max가 정책 의도와 다름(현재 min 0.0은 정상일 수 있으나 ‘왜 0이 되었나’ 로그 필요)

### D. 비용(Cost): “엣지가 비용으로 상쇄됐나?”
- 점검: 비용 분해(commission/spread/slippage), turnover 기여도, 이벤트 데이 비용 폭증
- 증상: gross는 개선인데 after-cost가 정체 → 회전율/슬리피지 병목

### E. 레짐(Regime): “특정 국면에서만 먹히는가?”
- 점검: 레짐 태그별 성능(평균/하방), Tech vs Healthcare 기여도 분리
- 증상: 전체 평균은 정체인데 레짐별로 극단 → 레짐 게이트/스위칭이 필요

## 48시간 루프 운영 순서(명령형)
1. **E1 먼저 적용**해서 로그/메트릭/리밸런스 파일 강제 산출 → 도구 에러 0 만들기  
2. **E2 적용**해서 degenerate fold 0 만들기(평가 프레임 복구)  
3. **E3 적용**해서 after-cost를 기본 KPI로 전환  
4. **E4/E5는 “리스크/레짐” 축으로만 1회씩** 붙여 tail과 노출 안정성 확인  
5. 위 5개 외 추가 분기 금지(성능이 아니라 “진단 가능성”을 먼저 고정)

이 순서로 돌리면, “성능이 안 움직임”이 **(평가 붕괴) / (신호 미적용) / (비용 상쇄) / (레짐 미스)** 중 어디인지 48시간 내에 강제로 갈라진다.
