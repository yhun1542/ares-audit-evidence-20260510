## TOP5 우선순위(24~48h) — “명령형 체크리스트” (누수/과최적화/서바이버십/비용/운영 리스크 우선)

---

# 1) **운영/아키텍처: “No-Delta(성능/포지션이 안 움직임)” 원인 제거 + 메타데이터/리밸런스 로그 복구**
### (a) 왜 필요한지
- 현재 ONE TRUTH에서 **file/lane_hash/run_hash 비어있음**, **worst_mdd=None**, **rebalance pinpoint가 로그 포맷/경로 오류로 실패** → 실험이 실제로 “다른 포트폴리오”를 만들었는지조차 추적 불가.
- “성능이 안 움직임”의 1순위는 모델이 아니라 **적용/리밸런스/로그/캐시**에서 실험이 무력화되는 케이스.

### (b) 위험/부작용
- 로깅/아티팩트 강제는 단기적으로 **실험 속도 저하**, 저장공간 증가.
- “강제 실패(fail-fast)” 도입 시, 당분간 파이프라인이 자주 멈출 수 있음(하지만 이게 정상).

### (c) 최소 실험(단일 실험 내 2~3 arms)  
**[실험 #1: Auditability & Rebalance Logging Patch]**
- Arm A: 현재 로직 그대로 + **필수 메타(run_hash, lane_hash, champion file path) 주입/검증만 추가**
- Arm B: A + **리밸런스 로그를 CSV+JSONL 동시 출력(스키마 고정)**  
  - 필수 필드 예: `ts, symbol, target_w, prev_w, delta_w, price, dollar_vol, est_cost, reason_code`
- Arm C: B + **“no-trade day”도 로그 생성(0 deltas) + diff-friendly 정렬**(symbol sort)

### (d) PASS 조건(게이트)
- Gate-1: 모든 런에서 `run_hash/lane_hash/file`이 **비어있으면 즉시 실패**
- Gate-2: `rebalance.csv` 또는 `rebalance.jsonl`이 **항상 생성**되고, `aub_rebalance_pinpoint.py`가 **에러 없이 리포트 생성**
- Gate-3: Champion vs Candidate 비교 시, 최소 1일 이상에서 **(weights 또는 trades) diff가 탐지**(“no-delta”가 계속이면 원인 확정 가능)

### (3) 기대 관측치(48h 루프에서 볼 것)
- 리포트에서 “어느 날짜/어떤 게이트 때문에 주문이 0이었는지”가 reason_code로 남음.
- 이후 실험들이 “진짜로 적용되는지” 즉시 확인 가능.

# 2) **누수/과최적화: Degenerate folds 제거 + 시간축 CV(embargo/purge) 강제**
### (a) 왜 필요한지
- `degenerate_folds: [1,2,3,8]`은 **교차검증이 붕괴**했거나(표본 0/상수 타깃/한쪽 클래스) **시계열 분할이 잘못**됐다는 신호.
- 이 상태에서는 OOS mean이 좋아도 **누수/과최적화 의심**이 가장 큼.

### (b) 위험/부작용
- Purged/embargo 적용 시 성능이 **단기 하락**할 수 있음(정상).
- 표본 수가 줄어 분산이 커질 수 있음 → 대신 신뢰도 상승.

### (c) 최소 실험(단일 실험 내 2~3 arms)  
**[실험 #2: CV Health & Leakage Guardrails]**
- Arm A: 현 CV 그대로 + **fold health report**(샘플 수, 타깃 분산, 결측률, 피처 상수율, 라벨 누수 의심 지표)
- Arm B: **PurgedKFold + Embargo(예: 5~10 trading days)**로 교체
- Arm C: B + **“feature timestamp audit”**(각 피처의 max timestamp ≤ decision timestamp 강제 체크; 위반 시 fail)

### (d) PASS 조건(게이트)
- Gate-1: `degenerate_folds`가 **빈 배열**(또는 0개)이어야 함
- Gate-2: fold별 `n_samples` 하한(예: 최소 N) 미달이면 실패
- Gate-3: timestamp audit 위반 **0건**, 위반 시 즉시 중단

### (3) 기대 관측치
- OOS mean이 내려가더라도 **fold 간 성능 분산 감소**, OOS min(최악) 개선 또는 과도한 outlier 감소.
- “좋았던 이유가 누수였는지” 빠르게 판별 가능.

# 3) **비용 미반영: 거래비용/슬리피지/턴오버 패널티를 목적함수에 내재화**
### (a) 왜 필요한지
- 비용을 빼면 Tech/Healthcare 개별주(8~14종) 전략은 **리밸런스로 알파가 사라지는 착시**가 흔함.
- 현재 로그가 없어서 더 위험: **실제로는 고턴오버인데 성과가 그대로**일 수 있음(실험 무력화 포함).

### (b) 위험/부작용
- 비용 모델이 보수적이면 성능이 “갑자기” 나빠짐 → 하지만 실거래 근접.
- 과도한 패널티는 포지션을 고정시켜 레짐 변화 대응이 느려짐.

### (c) 최소 실험(단일 실험 내 2~3 arms)  
**[실험 #3: Cost-Aware Objective + Turnover Control]**
- Arm A: cost=0 (기준) + 턴오버/거래횟수 측정만
- Arm B: **선형 비용(예: bps) + 스프레드 프록시(달러거래대금 기반)** 반영, 성과는 **after-cost**로 기록
- Arm C: B + **턴오버 패널티(예: L1 on Δw) 또는 min-hold(예: 2~3일)** 추가

### (d) PASS 조건(게이트)
- Gate-1: after-cost 기준에서 OOS mean이 baseline 대비 **의미 있게 유지/개선**(최소 개선폭은 내부 기준으로 고정)
- Gate-2: 연환산 턴오버/거래일당 turnover가 **상한 이하**(예: 전략 정책치)
- Gate-3: 특정 1~2종목에 과도하게 비용이 집중되면 fail(운영 리스크)

### (3) 기대 관측치
- gross는 비슷해도 **after-cost가 달라지며**, “성능 정체”가 비용 때문인지 분해 가능.
- 리밸런스 로그에서 비용 상위 날짜/종목이 드러남.

# 4) **서바이버십/유니버스: US Tech+Healthcare 8~14 종목 제약을 “포인트-인-타임”으로 강제**
### (a) 왜 필요한지
- “미국주식 only, Tech+Healthcare 중심, 8~14개”는 단순 필터가 아니라 **백테스트 공정성**과 직결:
  - 섹터 분류(예: GICS) 업데이트 시점 누수
  - 상장폐지/합병/티커 변경 미반영 시 서바이버십
- ETF 매매 금지 조건도 **엔진 레벨에서 차단**해야 운영 리스크 감소.

### (b) 위험/부작용
- PIT 유니버스 적용 시 과거에 접근 불가한 종목이 제거되어 성능 하락 가능(정상).
- 데이터 소스/매핑 오류 시 종목 수가 8~14를 못 맞출 수 있음 → 이 경우는 fail-fast가 맞음.

### (c) 최소 실험(단일 실험 내 2~3 arms)  
**[실험 #4: PIT Universe & Constraints Enforcement]**
- Arm A: 현 유니버스 + **제약 위반 리포트(종목수/섹터/국가/ETF 여부)**만 추가
- Arm B: **PIT 섹터/상장 상태(디리스팅 포함)**로 유니버스 생성(Tech+Healthcare만)
- Arm C: B + **포트폴리오 레벨 제약 하드코딩**  
  - (i) holdings count: 8~14 강제  
  - (ii) ETF ticker 매수/매도 시도 즉시 fail  
  - (iii) US listing만 허용

### (d) PASS 조건(게이트)
- Gate-1: 매 리밸런스마다 holdings count가 **항상 8~14**
- Gate-2: ETF 주문 시도 **0건**
- Gate-3: PIT 불일치(미래 섹터/미래 생존) 의심 이벤트 **0건**(감지 룰 기반)

### (3) 기대 관측치
- “전략이 실제 제약 하에서 돌아가는지”가 보장됨.
- 서바이버십 제거로 성능이 변하면 그 변화를 원인으로 확정 가능.

# 5) **노출/레짐/운영 리스크: 현금화/과소노출(0~0.84) 원인 규명 + 레짐 기반 스케일링(ETF는 지표로만)**
### (a) 왜 필요한지
- 현재 exposure min/max가 `0.0 / 0.8388` → 어떤 날은 **완전 현금**일 수 있음.  
  “성능이 안 움직임”은 종종 (i) 게이트가 계속 risk-off를 때리거나 (ii) 신호가 0으로 클리핑되는 경우.
- ETF는 매매 금지지만 **관측 지표(레짐/리스크온오프)**로는 유용: QQQ/XLV/SMH/SPY, VIX 대용(가능하면).

### (b) 위험/부작용
- 레짐 필터는 잘못 설계하면 알파를 깎고 거래 기회를 놓침.
- 과도한 최소 노출 강제는 drawdown 악화 가능.

### (c) 최소 실험(단일 실험 내 2~3 arms)  
**[실험 #5: Exposure Diagnostics + Regime Scaling (ETF-as-indicator)]**
- Arm A: 현 전략 + **exposure 결정 경로(reason trace) 로깅**  
  - 예: “signal=0”, “risk_gate=off”, “insufficient names”, “constraint clip”
- Arm B: A + **레짐 지표 기반 스케일**(예: QQQ 추세/변동성 구간에 따라 target gross 0.3~1.0; ETF는 거래 안 함)
- Arm C: B + **drawdown-aware throttle**(최근 DD가 일정 이상이면 turnover/노출 자동 축소)

### (d) PASS 조건(게이트)
- Gate-1: “exposure=0” 발생일의 reason이 **항상 로그로 설명 가능**(미설명 0건)
- Gate-2: OOS min(최악 성과) 또는 tail metric이 **개선**(단순 mean보다 우선)
- Gate-3: 노출이 장기간 0 근처로 붙으면 fail(전략 무력화)

### (3) 기대 관측치
- 노출이 왜 줄었는지(신호 vs 제약 vs 데이터 결측) 즉시 분해.
- 레짐 스케일이 “리스크만 줄이고 수익은 유지”하는지 after-cost로 확인.

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐) — 실행 체크리스트

### A) **Trigger(리밸런스 트리거)**
- 리밸런스가 실제로 발생했는지 `rebalance.*`에서 일자별로 확인
- 트리거 조건(요일/월말/신호변화 임계값)이 너무 빡세서 **항상 no-trade**인지 확인
- “no-trade라도 로그를 남기고 reason_code로 분류” 강제

### B) **Apply(신호→포트 적용)**
- 신호가 생성됐지만 제약/정규화에서 **전부 0으로 클립**되는지 확인  
  - 예: z-score 후 clip, exposure cap, min-hold 충돌
- “pre-constraint weights” vs “post-constraint weights”를 모두 저장해서 어디서 0이 되었는지 고정

### C) **Exposure(노출/현금화)**
- exposure=0 날짜를 모아서 원인을 4분류로 카운팅:
  1) 신호 결측/0
  2) 유니버스 부족(8~14 미달)
  3) 리스크 게이트(risk-off)
  4) 비용/슬리피지로 인해 최적화가 trade=0 선택
- max exposure가 0.84에서 멈추는 이유(상한/정규화/헤지 로직)를 한 줄로 로그화

### D) **Cost(비용)**
- gross 성과는 움직이는데 net이 안 움직이면 비용/턴오버 문제
- 반대로 gross도 안 움직이면 “실험 미적용/포지션 동일” 가능성이 큼 → #1 실험으로 우선 차단
- 종목별 비용 기여도(top-k)와 거래 빈도를 매일 출력

### E) **Regime(레짐/시장 상태)**
- ETF(지표) 기반으로 시장 국면을 태깅만 해도 원인 분해가 빨라짐(매매 X)
  - 예: QQQ 추세 상/하, XLV 상대강도, SMH 변동성, SPY 변동성 구간
- “전략이 특정 레짐에서만 거래/성과 발생”이면, 레짐별 성과 테이블을 고정 산출(48h 루프 기본 리포트로)

## 48시간 자동 루프 운영 형태(공통 게이트)
- **Fail-fast 게이트**: 메타데이터 비어있음(file/run_hash/lane_hash), 로그 미생성(rebalance), ETF 주문 시도, PIT 위반, degenerate fold 발생
- **관측치(매 런 공통)**:  
  - (1) holdings count 분포(8~14 충족률)  
  - (2) exposure 시계열(min/mean/max) + exposure=0 reason histogram  
  - (3) turnover/거래수 + after-cost 성과  
  - (4) fold health + leakage audit 결과  
  - (5) champion vs candidate “weights/trades diff” 존재 여부

위 5개 실험(#1~#5)은 “케이스 폭발” 없이도, 현재 로그에서 드러난 **degenerate folds + rebalance 로그 붕괴 + no-delta**를 먼저 끝내고, 그 다음에야 전략 개선이 유효하게 돌아가도록 만드는 우선순위입니다.
