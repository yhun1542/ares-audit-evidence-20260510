## 1. Priority #1 — Signal Fire Audit (누락 점검)

### (a) 왜 필요한가
- Candidate JSON에 새 모듈 포함됐으나 **실제 trade log에 신호 적용 건수 = 0** 가능성
- 코드 경로: 모듈 등록 → 스코어 계산 → 게이트 통과 → 사이즈 반영 **어디서 끊기는지** 확인 필수

### (b) 위험/부작용
- 디버그 로깅 과다 시 런타임 10%↑
- 잘못된 수정 시 기존 Champion 동작 훼손

### (c) 최소 실험

| ID | 실험 정의 | 게이트 | 기대 관측치 |
|----|-----------|--------|-------------|
| **P1-E1** | `--dry-run --verbose-signals` 플래그 추가, 모듈별 fire count 로그 | 로그 파일 생성 | 각 모듈 fire ≥ 1 확인 |
| **P1-E2** | fire=0 모듈 → threshold 50% 완화 후 tuning 재실행 | tuning_mean 변화 ≥ 0.5% | Δ mean ≠ 0 |
| **P1-E3** | fire>0 but position=0 → sizing gate 로그 삽입 | sizing 거부 로그 존재 | 원인 식별 |

### (d) PASS 조건
```
fire_count > 0 for ALL active modules
AND position_applied > 0 at least 1 fold
```

## 2. Priority #2 — Sizing Cap / Kelly Dilution 점검

### (a) 왜 필요한가
- Kelly fraction cap이 0.1 등 보수적 → 강한 시그널도 1% position으로 희석
- 결과: 정답 맞춰도 PnL 미미 → mean 정체

### (b) 위험/부작용
- cap 상향 시 MDD 악화 (worst_mdd -15% 초과 위험)
- 과최적화: 특정 fold에서만 유효

### (c) 최소 실험

| ID | 실험 정의 | 게이트 | 기대 관측치 |
|----|-----------|--------|-------------|
| **P2-E1** | `kelly_cap: 0.1 → 0.15` 단일 변경 | worst_mdd ≤ -0.12 | tuning_mean ↑ 3%+ |
| **P2-E2** | `kelly_cap: 0.2` + `max_position: 0.08` | worst_mdd ≤ -0.13 | lockbox_mean ↑ |
| **P2-E3** | Adaptive cap (volatility-scaled) 모듈 적용 | fold14_mdd 개선 | 레짐별 cap 자동 조절 |

### (d) PASS 조건
```
lockbox_mean ≥ 1.80 AND worst_mdd ≥ -0.13
```

## 4. Priority #4 — Cost Model Realism (비용 미반영 점검)

### (a) 왜 필요한가
- 현재 slippage 0.05% 가정 → 실제 mid-cap Tech 0.1~0.2%
- Commission $0 가정 → IB/Schwab 실제 $0이나 **spread 미반영**

### (b) 위험/부작용
- 비용 상향 시 수익률 급락 → 전략 폐기 가능성
- 과도한 비용 가정 = 좋은 전략도 reject

### (c) 최소 실험

| ID | 실험 정의 | 게이트 | 기대 관측치 |
|----|-----------|--------|-------------|
| **P4-E1** | `slippage: 0.05% → 0.10%` | tuning_mean ≥ 1.5 | Δ mean 측정 |
| **P4-E2** | `slippage: 0.15%` (worst-case) | tuning_mean ≥ 1.3 | 생존 가능 여부 |
| **P4-E3** | Trade frequency cap (월 20회 → 10회) | 동일 mean 유지 | 비용 절감 효과 |

### (d) PASS 조건
```
tuning_mean ≥ 1.50 at slippage=0.10%
```

## 5. Priority #5 — Leakage Audit (누수 점검)

### (a) 왜 필요한가
- tuning/lockbox **완전 동일 결과** = 누수 또는 코드 버그
- 정상이라면 lockbox는 약간 낮아야 함 (unseen data)

### (b) 위험/부작용
- False alarm: 우연히 동일할 수 있음 (낮은 확률)
- 누수 발견 시 전체 결과 무효 → 재실행 필요

### (c) 최소 실험

| ID | 실험 정의 | 게이트 | 기대 관측치 |
|----|-----------|--------|-------------|
| **P5-E1** | Data pipeline에 `shuffle=True` 의도적 삽입 후 결과 변화 확인 | 결과 변화 無 = 누수 | Δ ≠ 0 이면 정상 |
| **P5-E2** | Lockbox 기간 1개월 shift → 결과 변화 확인 | mean ± 5% 변화 | 동일하면 누수 |
| **P5-E3** | Feature importance 중 미래 데이터 포함 여부 체크 | 미래 feature = 0% | target leak 없음 |

### (d) PASS 조건
```
lockbox_mean ≠ tuning_mean (within 0.01 tolerance is suspicious)
```

□ fold15_mean ≥ 1.0 확인

# ===== HOUR 36-48: Integration & Promote =====
□ 모든 PASS 실험 병합 → candidate_final_20260103.json
□ python3 experiment_system/tools/aub_autopilot.py --registry ... --run --select-best
□ PASS 시 champion_v6로 승격

## 성능 정체 시 디버그 트리 (자동화용)

```
성능 Δ < 0.5%?
├─ 트리거 문제?
│   └─ fire_count == 0 → threshold 완화
├─ 적용 문제?
│   └─ position_size == 0 → sizing cap 상향
├─ 노출 문제?
│   └─ holding_days < 3 → exit 조건 완화
├─ 비용 문제?
│   └─ gross vs net 차이 > 10% → 비용 모델 점검
└─ 레짐 문제?
    └─ 단일 레짐만 테스트 → fold 확장
```
