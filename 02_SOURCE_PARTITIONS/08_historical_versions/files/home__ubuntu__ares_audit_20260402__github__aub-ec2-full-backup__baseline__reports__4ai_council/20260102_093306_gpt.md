## 24~48시간 TOP5 우선순위 (코드/아키텍처/전략) — **명령형 체크리스트**

### 1) **관측/로그 계약(Contract) 복구 + 지표 불일치 제거 (운영 리스크 1순위)**
- [ ] **`oos_mean` 불일치(1.88 vs 2.63) 원인 제거**: 동일 입력/동일 기간/동일 비용/동일 집계로 “단일 평가 함수”로만 산출하게 고정
- [ ] **`worst_mdd: None` 금지**: MDD 계산을 필수 단계로 만들고, 누락 시 실험 FAIL 처리
- [ ] **리밸런스 로그 형식 고정**: `rebalance.csv` + `rebalance.jsonl`(라인 JSON) 둘 다 항상 생성
- [ ] **툴 경로 오류 제거**: `--base-log`에 문자열(`--base-log`)이 그대로 들어간 케이스 방지(인자/경로 validate)
- [ ] **Artifacts에 “필수 산출물” 체크섬 추가**: 없으면 자동 루프에서 다음 단계로 진행 금지

**(a) 왜 필요한지**
- 현재 `aub_rebalance_pinpoint`가 **파일 부재/JSON 파싱 실패**로 무력화됨 → 비용/턴오버/리밸런스 이상 탐지가 불가
- `oos_mean` 상이 + `worst_mdd None`은 **평가 파이프라인이 단일 진실(ONE TRUTH)이 아님**을 의미 → 48시간 자동 루프가 잘못된 챔피언을 고착시킬 위험

**(b) 위험/부작용**
- [ ] 과거 챔피언/리포트와 수치가 달라져 “퇴행”처럼 보일 수 있음(하지만 정상화 과정)
- [ ] 로그 양 증가(디스크/IO) → 보관 기간/압축 필요

**(c) 최소 실험(아래 공용 실험 E1/E3 참조)**
- E1, E3 적용

**(d) PASS 조건**
- [ ] 동일 실험을 **서로 다른 도구로 평가해도 oos_mean 오차 ≤ 1%**
- [ ] `worst_mdd`가 항상 수치로 채워짐(누락=0회)
- [ ] `rebalance.csv/jsonl`가 생성되고 `aub_rebalance_pinpoint`가 **에러 없이 리포트 생성**

### 2) **누수(Leakage) + 서바이버십 + 시점정합(As-of) 우선 점검 (리스크 1순위)**
- [ ] 특징량/라벨 생성 시 **미래 데이터 참조 차단**(가격/거래대금/재무/이벤트 모두)
- [ ] **Purged/Embargo 검증**: 라벨 윈도우와 겹치는 구간을 학습에서 제거(시간 누수 방지)
- [ ] 유니버스 **as-of 고정**: “현재 상장 종목 리스트” 사용 금지(서바이버십 편향 차단)
- [ ] 분할/배당/심볼변경/합병 처리의 시점 정합 검증

**(a) 왜 필요한지**
- 성능이 “안 움직임/과도하게 좋음/특정 기간만 좋음”의 최빈 원인이 누수·서바이버십
- Tech+Healthcare 8~14종목처럼 소수 종목이면 **한두 이벤트 누수로 성능이 폭발/고착** 가능

**(b) 위험/부작용**
- [ ] 누수 제거 후 성능 하락 가능(정상)
- [ ] 데이터 소스가 as-of를 지원하지 않으면 구현 비용 상승

**(c) 최소 실험(아래 공용 실험 E2 참조)**
- E2 적용(shift/sentinel)

**(d) PASS 조건**
- [ ] “미래 shift(+1~+5)”에서 성능이 **유의미하게 개선되지 않음**
- [ ] “과거 lag(+1~+5)”에서 성능이 **완전 붕괴하지 않음**(누수 의심 신호 제거)
- [ ] 폴드별 성능 분산이 과도하지 않음(특정 폴드 독식 완화)

### 3) **비용/턴오버/체결 가능성(Execution) 반영 강화 (비용 미반영 리스크)**
- [ ] **기본 비용 모델 고정**: 커미션+슬리피지(스프레드) + 충격비용(거래대금 대비)
- [ ] **턴오버 게이트**: 리밸런스가 잦을수록 FAIL 처리(또는 포지션 유지 최소기간)
- [ ] **체결 가능성 게이트**: ADV 대비 참여율(Participation) 상한 도입
- [ ] 리밸런스 로그에 각 주문의 “예상 비용/실현 비용/거래대금 비율” 기록

**(a) 왜 필요한지**
- 현재 리밸런스 로그가 깨져 있어 비용 원인 분해가 불가
- 소수 종목(8~14) + Tech는 갭/변동성 확대 국면에서 비용 민감

**(b) 위험/부작용**
- [ ] 비용을 현실화하면 수익률 하락 가능(정상)
- [ ] 과도한 제약은 기회 손실/신호 약화

**(c) 최소 실험(공용 E3)**
- E3 적용(비용 스트레스 + 참여율 캡)

**(d) PASS 조건**
- [ ] 비용 1x→2x로 올려도 **oos_mean이 급락하지 않음**(예: -20% 이내)
- [ ] 월간(또는 리밸런스 주기 기준) turnover 상한 내 유지
- [ ] 비용 기여도가 성과를 삼키지 않음(총 PnL 대비 비용 비중 상한)

### 4) **노출/리스크 제약(Exposure)과 운영 안전장치 (과최적화·운영 리스크)**
- [ ] 포트폴리오 구성 강제: **미국주식 Tech+Healthcare만, 8~14종목 유지**
- [ ] 단일 종목 비중 상한, 섹터 내부 쏠림 상한(Tech/Healthcare 내에서도 과집중 방지)
- [ ] **순/총 익스포저 밴드** 고정(현재 0.47~0.84는 “의도된 범위인지”에 맞춰 하드게이트)

**(b) 위험/부작용**

**(c) 최소 실험(공용 E4)**
- E4 적용(종목 수/비중/익스포저 clamp)

**(d) PASS 조건**
- [ ] 종목 수가 항상 8~14 유지(이탈=0회)
- [ ] 익스포저가 목표 밴드 내 유지(이탈=0회)
- [ ] oos_min 개선 또는 worst-case 손실(최저 구간 성과/드로다운) 개선

## 48시간 자동 루프용 “공용 실험(3~5개)” — **총 5개만 운용**
아래 5개만 돌리고, 위 TOP5 제안은 이 실험들을 재사용해서 검증한다(케이스 폭발 방지).

### **E1) Eval/Log Contract 실험**
1) **실험 정의**
- 평가 함수 단일화 + 산출물 필수화: `metrics.json`(oos_mean, oos_min, worst_mdd, turnover, cost) + `rebalance.csv/jsonl`
2) **게이트**
- 산출물 누락/파싱 실패/`worst_mdd None`이면 즉시 FAIL
3) **기대 관측치**
- 도구 간(oos 평가 vs diagnoser) 수치가 거의 동일해지고, rebalance pinpoint가 정상 동작


### **E2) Leakage/Survivorship Sentinel 실험**
1) **실험 정의**
- 동일 파이프라인에서 feature를 **+k일 미래로 shift** / **-k일 과거로 lag**(k=1,3,5) 한 버전들을 자동 생성해 비교
2) **게이트**
- 미래 shift가 기준 대비 성능을 크게 개선하면 FAIL(누수 의심)
- 과거 lag에서 성능이 “비정상 급락(예: 50%+ 붕괴)”하면 FAIL(시점정합 문제 의심)
3) **기대 관측치**
- 미래/과거 변형에 대해 성능이 합리적으로 열화되며, 특정 변형에서만 폭발하는 패턴이 사라짐


### **E3) Cost/Turnover Stress 실험**
1) **실험 정의**
- 비용 0x/1x/2x + ADV 참여율 상한(예: 5~10%)을 스윕(단, 한 번에 3개 조합만)
2) **게이트**
- 2x 비용에서 oos_mean 급락/음수 전환/턴오버 상한 초과 시 FAIL
3) **기대 관측치**
- 비용 민감도가 낮은 구조(리밸런스 빈도 감소, 과도한 미세매매 제거)로 유도됨


### **E4) Exposure Clamp 실험 (8~14종목 + 비중/노출 제약)**
1) **실험 정의**
- 종목 수 8~14 강제, 단일 종목/그룹 비중 상한, 순/총 익스포저 밴드 하드 적용
2) **게이트**
- 제약 위반 0회, 그리고 oos_min 또는 하방 지표 개선 없으면 FAIL(제약만 늘고 실익 없음)
3) **기대 관측치**
- 성능 평균이 조금 줄더라도, 최악구간 성능/안정성 개선


### **E5) Regime-based Scaling 실험(전략 최소 패치)**
1) **실험 정의**
- ETF 관측지표(예: SPY/QQQ/XLV 추세, 변동성 proxy)로 레짐 점수 산출 → 익스포저 목표를 2~3단계로만 조절
2) **게이트**
- 레짐 적용 후 turnover/비용이 증가하면 FAIL
- oos_min 개선 또는 worst_mdd 개선이 없으면 FAIL
3) **기대 관측치**
- 레짐 전환(급락/급등)에서 손실 완화, 성능 하방 꼬리 감소

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐) — 명령형 트리
아래를 **순서대로** 실행해 병목을 한 번에 하나만 고정한다.

### A) Trigger(신호 발생) 문제인지
- [ ] 일별/주별 **신호 발생률(진입/청산 횟수)** 시계열을 저장하고, 최근 OOS 구간에서 분포 변화 탐지
- [ ] 상위 기여 종목(Tech/Healthcare 각 1~3개)의 신호 빈도만 따로 분해(소수 종목 편향 확인)

### B) Apply(신호 적용/포지션 사이징) 문제인지
- [ ] “신호는 맞는데 사이징이 망함” 탐지: 동일 신호로 **고정 1/N 사이징 vs 현재 사이징** PnL을 나란히 기록
- [ ] 사이징이 변동성 급등에서 과도하게 커지는지(또는 너무 빨리 0으로 줄어드는지) 점검

### C) Exposure(노출 드리프트) 문제인지
- [ ] 순/총 익스포저, 단일종목 비중, 섹터 내 쏠림의 **일별 히스토그램** 저장
- [ ] 성능 정체 구간에서 “익스포저가 같은데 성과만 죽었는지” vs “익스포저가 변했는지” 분리

### D) Cost(비용/턴오버) 문제인지
- [ ] 총 PnL을 **Gross / Cost / Net**으로 분해해 로그에 고정
- [ ] 정체 구간에서 비용 비중이 급증했는지(스프레드 확대/턴오버 증가) 확인
- [ ] 비용 0x와 1x의 성능 차이가 커지면 “신호 품질”이 아니라 “실행 품질” 문제로 분류

### E) Regime(시장 국면) 문제인지
- [ ] 레짐을 2~3개로만 단순 분류(예: Risk-on / Risk-off / Sideways)하고 각 레짐별 성과 테이블 고정
- [ ] “레짐별로만 성과가 존재”하면 신호 변경보다 **노출 스케일링(E5)** 우선
- [ ] Tech/Healthcare 간 레짐 민감도 차이(Tech 고베타/Health 상대 방어)를 분리 기록

이 순서대로 하면, “성능이 안 움직임”을 **신호 부족 / 적용 실패 / 노출 드리프트 / 비용 잠식 / 레짐 미스매치** 중 하나로 빠르게 귀속시키고, 자동 루프에서 다음 액션을 안정적으로 선택할 수 있다.
