## TOP1) 리밸런스/트레이드 로그 스키마 고정 + 재현가능성(해시) 복구 (운영 리스크 최우선)
**현재 징후(ONE TRUTH 기반)**  
- `aub_rebalance_pinpoint`가 **rebalance 로그를 못 읽음**(CSV 경로/JSON 파싱 실패) → “왜 성능이 안 움직였는지” 추적 불가  
- `lane_hash/run_hash: None` → 동일 실험 재현/캐시/비교 불가  
- `worst_mdd: None` → 핵심 리스크 지표 계산/저장 누락 가능

### (a) 왜 필요한지
- 성능 정체/노델타(“No-Delta Diagnoser”)는 **대부분 ‘실제로는 같은 트레이드’**가 반복되거나, 비용/리밸런스가 누락되어 “지표만” 움직이는 케이스가 많습니다.  
- 로그가 깨져 있으면 **원인 분해(트리거→적용→노출→비용)**가 불가능합니다.

### (b) 위험/부작용
- 로그/스키마 변경으로 과거 결과와 비교가 어려워질 수 있음(단, 해시/버전으로 해결 가능).
- 성능 자체는 그대로인데 “보이던 성능”이 내려갈 수 있음(그게 정상).

### (c) 최소 실험 2~3개
**실험 1: Rebalance log 단일 포맷 강제(JSONL 권장)**
- (1) 실험 정의:  
  - 모든 리밸런스 이벤트를 `rebalance.jsonl`로 저장(한 줄=한 이벤트).  
  - 필수 필드: `ts, universe_version, weights_before/after, trades, turnover, est_cost, realized_cost(if any), price_source, signals_hash, lane_hash, run_hash`
- (2) 게이트:  
  - `aub_rebalance_pinpoint.py`가 base/cand 모두에서 100% 로드 성공  
  - 이벤트 수(리밸런스 횟수)가 백테스트 기간/주기와 일치
- (3) 기대 관측치:  
  - “노델타” 케이스에서 **트레이드 0, turnover 0**이 반복되는지 즉시 확인 가능  
  - 성능 변화가 없어도 “왜”가 보임

**실험 2: lane_hash/run_hash 생성 강제 + 실험 메타 고정**
- (1) 실험 정의:  
  - 데이터 범위, 피처 세트, 비용 모델, 유니버스, 리밸런스 주기, 시드 등을 직렬화해 `lane_hash` 생성  
  - 실행별 `run_hash`는 코드 커밋/도커 이미지 해시 포함
- (2) 게이트:  
  - 모든 결과 JSON에 `lane_hash/run_hash != None`  
  - 동일 설정 재실행 시 lane_hash 동일
- (3) 기대 관측치:  
  - 실험 간 “같은 실험인데 다르게 나온” 현상 제거  
  - 캐시/재현 기반의 48시간 루프 안정화

**실험 3: worst_mdd 계산 파이프라인 추가**
- (1) 실험 정의:  
  - OOS 구간 기준 `worst_mdd`, `max_dd_duration`, `tail_5pct` 저장
- (2) 게이트:  
  - champion/cand 모두 `worst_mdd`가 null 아님
- (3) 기대 관측치:  
  - OOS mean만 오르는 “과최적화” 후보를 빠르게 컷

### (d) PASS 조건
- **48시간 내** `rebalance_pinpoint`가 base/cand 모두 로드 성공 + `lane_hash/run_hash/worst_mdd`가 전 실험에서 채워짐  
- 노델타 케이스 1건 이상에서 “트레이드/턴오버/비용” 레벨로 원인이 특정됨

## TOP2) Fold degeneracy(퇴화 폴드) 차단: 누수/분할/라벨 정합성 가드레일
**현재 징후**
- `degenerate_folds: [1,2,3,8]` → 폴드 내 표본이 부족하거나, 타깃이 상수이거나, 분할이 깨졌거나(시간 누수/필터 누수) 가능성이 큼.

### (a) 왜 필요한지
- 폴드가 퇴화하면 **OOS mean이 “그럴듯하게” 나와도** 신뢰가 무너집니다.  
- 퇴화 폴드는 **과최적화 + 데이터 누수**의 대표적인 전조입니다.

### (b) 위험/부작용
- 가드레일을 걸면 실험 실패가 늘고, 단기적으로 “챔피언 갱신”이 느려질 수 있음(정상).
- 데이터가 적은 구간에서는 학습 자체가 불가할 수 있음(유니버스/기간 조정 필요).

### (c) 최소 실험 2~3개
**실험 1: 퇴화 폴드 자동 실패(Fail-fast)**
- (1) 실험 정의:  
  - 각 폴드에 대해 `n_samples`, `n_assets`, `target_std`, `label_unique_count` 체크  
  - 조건 미달 시 해당 실험 전체를 FAIL로 마킹(챔피언 후보 제외)
- (2) 게이트:  
  - 퇴화 폴드 발생 시 실험이 “성공”으로 기록되지 않음
- (3) 기대 관측치:  
  - 겉보기 OOS 향상 실험이 대거 사라지고, 남는 실험의 재현성이 상승

**실험 2: Purged walk-forward + embargo 적용**
- (1) 실험 정의:  
  - 리밸런스 주기(예: 1D/1W) 기반으로 라벨 산출 기간만큼 **purge**, 추가로 **embargo k일** 적용  
- (2) 게이트:  
  - purge/embargo 적용 후에도 학습 폴드 표본 수 임계치 이상 유지  
- (3) 기대 관측치:  
  - 누수로 얻던 성능이 사라지면 OOS mean 하락(정상), 대신 안정성 지표 개선

**실험 3: 피처/라벨 타임스탬프 정합성 검사(lookahead scanner)**
- (1) 실험 정의:  
  - 각 피처가 참조하는 원천 데이터의 `available_time`을 기록하고, `decision_time` 이후 참조 시 FAIL  
- (2) 게이트:  
  - lookahead 0건이어야 PASS
- (3) 기대 관측치:  
  - “이상하게 잘 나오던” 실험의 상당수가 누수로 판명될 가능성

### (d) PASS 조건
- degenerate_folds 리스트가 **빈 리스트**(또는 0~1개 이하로 감소)  
- purge/embargo 적용 후에도 OOS가 **과도한 드랍 없이**(예: -X% 이내) 유지되면 누수 가능성 낮아짐

## TOP3) 비용(슬리피지/스프레드/임팩트) 모델 강제 + 턴오버 게이트 (비용 미반영 방지)
**현재 징후**
- 리밸런스 로그 자체가 불완전하여 “실제 거래 비용이 반영되는지”가 불명확.  
- 성능 정체/노델타에서 흔히 비용 모델이 “0 또는 고정값”으로 박혀 의미가 없어지는 경우가 많음.

### (a) 왜 필요한지
- 미국주식(Tech+Healthcare) 집중(8~14종목)은 **개별 종목 유동성 차이**가 커서, 비용 미반영이면 전략이 왜곡됩니다.  
- “OOS mean은 좋은데 실전은 망하는” 1순위 원인이 비용/슬리피지입니다.

### (b) 위험/부작용
- 비용을 넣으면 성능이 내려갈 수 있음(정상).  
- 너무 보수적인 비용으로 전략이 과도하게 거래를 회피할 수 있음.

### (c) 최소 실험 2~3개
**실험 1: 3단 비용 모델 A/B/C (고정→스프레드→임팩트)**
- (1) 실험 정의:  
  - A: 고정 bps (예: 5~15bps)  
  - B: `half_spread + fee` (일별 평균 스프레드 추정치 사용)  
  - C: `half_spread + k * (trade_dollar / ADV)^α` 임팩트
- (2) 게이트:  
  - 각 모델에서 `turnover`, `est_cost`, `net_return`이 로그에 남아야 함
- (3) 기대 관측치:  
  - 전략이 “비용에 민감한지”가 드러남(민감하면 과거 성능이 비용 착시였을 가능성)

**실험 2: 턴오버 상한 게이트(정책 제약)**
- (1) 실험 정의:  
  - 리밸런스당 turnover 상한(예: 20~35%) 또는 월간 turnover 상한 적용  
- (2) 게이트:  
  - 상한 위반 시 리밸런스 스킵/스케일 다운 규칙이 일관되게 적용
- (3) 기대 관측치:  
  - 성능이 비슷한데 turnover가 내려가면 “실전화” 진전

**실험 3: 비용 민감도 리포트 자동생성**
- (1) 실험 정의:  
  - 동일 신호로 비용만 바꾼 3개 결과를 나란히 저장(넷/그로스/비용 비중)
- (2) 게이트:  
  - 챔피언 선정 시 “비용 C에서의 OOS”를 최소 기준으로 사용
- (3) 기대 관측치:  
  - 과최적화 후보가 비용 C에서 탈락

### (d) PASS 조건
- 비용 모델 C에서도 OOS mean이 **양(+)**이고, `turnover`가 상식 범위(사전 정의)  
- “비용 0일 때만 좋은” 후보가 자동으로 컷

## TOP4) 유니버스/서바이버십/섹터 집중(Tech+Healthcare 8~14) 강제 + 노출 게이트
**요구사항 상 제약**
- **미국주식 only**, **Tech+Healthcare 중심**, **8~14 내외**, **ETF 매매 제외(관측지표만)**

### (a) 왜 필요한지
- 유니버스 정의가 흔들리면:  
  - 서바이버십(상장폐지/합병 누락), 룩어헤드(현재 구성으로 과거를 백테스트) 위험이 즉시 커짐  
  - 종목 수가 늘었다 줄었다 하면 노출/턴오버/리스크가 왜곡됨  
- 현재 `exposure_min/max: 0.0 / 0.8388` → “현금 비중/노출 변동”이 큰데, 원인이 신호인지 유니버스 변동인지 분리 필요.

### (b) 위험/부작용
- 섹터/종목 제한으로 기회가 줄어 성능이 낮아질 수 있음.  
- 8~14개 강제는 집중 리스크를 키울 수 있어 리스크 게이트가 필수.

### (c) 최소 실험 2~3개
**실험 1: 유니버스 버전 고정 + 서바이버십 방지 플래그**
- (1) 실험 정의:  
  - 매일/매월 유니버스 스냅샷 저장(`universe_version`)  
  - 과거 시점 백테스트는 해당 시점 스냅샷만 사용(현재 구성으로 과거 재구성 금지)
- (2) 게이트:  
  - 각 거래일에 `universe_version`이 로그에 기록  
  - 상장폐지/티커 변경 이벤트가 있을 때도 종목 타임라인이 끊기지 않음
- (3) 기대 관측치:  
  - “어느 날부터 갑자기 성능이 안 움직임”이 유니버스 변동 때문인지 즉시 판별

**실험 2: 종목 수(8~14) 하드 제약 + 섹터 필터 강제**
- (1) 실험 정의:  
  - GICS/NAICS 등으로 Tech/Healthcare만 허용(데이터 소스 기준)  
  - 최종 포트폴리오 종목 수를 8~14로 클램프(랭킹 상위 N, 하위는 0)
- (2) 게이트:  
  - 리밸런스마다 `n_holdings`가 [8,14] 범위를 벗어나면 FAIL  
- (3) 기대 관측치:  
  - 트레이드/턴오버 구조가 안정화되고, 노델타가 “종목수 변동” 때문인지 제거

**실험 3: 노출(Exposure) 하한선/상한선 게이트**
- (1) 실험 정의:  
  - 총 익스포저 하한 0.6, 상한 0.95 등 정책 범위 설정(현금 과다/레버리지 금지)  
- (2) 게이트:  
  - `exposure_min`이 0으로 떨어지는 구간이 있으면 원인 로그(신호 0/데이터 결측/게이트 컷)를 남기고 FAIL 또는 경고
- (3) 기대 관측치:  
  - 성능 정체가 “거의 안 샀기 때문”인지 즉시 보임

### (d) PASS 조건
- 전 구간에서 `n_holdings`가 [8,14] 유지 + Tech/Healthcare 비중이 정책 범위 충족  
- exposure가 정책 범위 내에서 안정(“0으로 떨어지는 날” 제거/설명 가능)

## TOP5) “No-Delta(성능 무변화)” 원인 직접 타격: 트리거→적용→노출→비용→레짐 5단 로그
**현재 징후**
- No-Delta Diagnoser가 9개 실험을 잡았고, 챔피언/후보 비교가 리밸런스 로그 결손으로 막힘.  
- 즉, 지금은 “성능이 안 움직이는 이유”가 **전략 문제인지, 적용(실행) 문제인지** 분리되지 않았음.

### (a) 왜 필요한지
- 노델타의 80%는 “신호는 달라졌는데 적용이 같음(클램프/정규화/게이트로 상쇄)” 또는 “신호는 달랐지만 거래가 0” 입니다.  
- 48시간 자동 루프는 **원인-결과 폐루프**가 있어야 진짜 학습합니다.

### (b) 위험/부작용
- 로그가 늘어 저장/IO 비용 증가.  
- 원인 분해 지표가 늘어나면 “선정 기준”이 복잡해질 수 있음(게이트 우선순위로 단순화 필요).

### (c) 최소 실험 2~3개
**실험 1: 5단 분해 로그(Trigger/Apply/Exposure/Cost/Regime) 자동 저장**
- (1) 실험 정의:  
  - Trigger: 신호 변화량(`signal_delta_norm`)  
  - Apply: 포지션 변화량(`weight_delta`, clamp 발생 여부)  
  - Exposure: 총 익스포저, 섹터 익스포저  
  - Cost: turnover, est_cost, net-after-cost  
  - Regime: 관측 ETF(매매X) 지표: `QQQ(tech)`, `XLV(health)`, `IEF/TLT(rate)`, `VIX proxy`(가능하면) 기반 상태
- (2) 게이트:  
  - 노델타 케이스에서 5단 중 최소 1단에서 “정체 지점”이 수치로 특정되어야 PASS
- (3) 기대 관측치:  
  - 예: Trigger는 변했는데 Apply가 0 → 포지션 클램프/정규화 버그  
  - Trigger부터 0 → 피처/모델이 상수 출력(데이터 결측/스케일링 오류)

**실험 2: “동일 트레이드 여부” 자동 판정기**
- (1) 실험 정의:  
  - 리밸런스별 `trades_hash` 생성(티커, 방향, 수량/비중, 가격소스)  
  - base vs cand의 trades_hash 일치율을 리포트
- (2) 게이트:  
  - 일치율이 95% 이상이면 “실질적으로 동일 전략”으로 분류하고 후보군에서 제외
- (3) 기대 관측치:  
  - 실험 수는 많았는데 실질 다양성이 없던 문제를 즉시 드러냄

**실험 3: 스케일/클램프/헤지 적용 순서 고정(결정론)**
- (1) 실험 정의:  
  - 신호→정규화→리스크스케일→(헤지/현금규칙)→클램프 순서를 고정하고 중간 산출물 저장  
- (2) 게이트:  
  - 동일 입력이면 중간 산출물이 동일(결정론)  
- (3) 기대 관측치:  
  - “패치했는데 결과가 그대로”가 적용 순서 문제인지 분리

### (d) PASS 조건
- 노델타 상위 3케이스에 대해 “정체 단계”가 5단 중 하나로 명확히 귀결  
- cand가 base와 동일 트레이드로 판정되면 자동 제외되어 실험 효율 상승

# 성능이 안 움직일 때: 원인 분해 아이디어(트리거/적용/노출/비용/레짐) — 실행 트리
아래 트리는 **질문 없이** 바로 자동 리포트로 만들 수 있는 형태입니다(각 노드에 지표 1~2개만 박아 단순화).

## 0) “정말로 안 움직였나?” (측정/로그)
- **같은 기간/같은 OOS 창**인지 확인: `oos_window_hash`
- 결과 파일이 다른데 `lane_hash`가 같으면 캐시/재실행 문제

## 1) Trigger(신호가 바뀌었나?)
- 지표: `corr(signal_base, signal_cand)`, `mean(|signal_delta|)`
- 해석:
  - 거의 동일 → 실험이 실질적으로 동일(탐색공간 중복/파라미터 무효)

## 2) Apply(신호가 포지션으로 적용됐나?)
- 지표: `mean(|weight_delta|)`, `clamp_rate`, `n_holdings`
- 해석:
  - signal_delta는 큰데 weight_delta가 0에 가까움 → **클램프/정규화/종목수제약/리스크스케일**이 차이를 눌러버림
  - n_holdings가 범위 밖/변동 큼 → 유니버스/필터 영향

## 3) Exposure(실제로 돈이 들어갔나?)
- 지표: `gross_exposure`, `net_exposure`, 섹터 익스포저(Tech/Health)
- 해석:
  - gross_exposure가 자주 0 근처 → 데이터 결측/게이트 과잉/신호 상수
  - 섹터 노출이 정책과 다름 → 유니버스/분류/필터 버그

## 4) Cost(비용이 결과를 죽였나? / 혹은 비용이 0이라 착시인가?)
- 지표: `turnover`, `est_cost_bps`, `net-gross gap`
- 해석:
  - turnover↑ & net↓ → 거래 과다(턴오버 게이트 필요)
  - 비용이 0에 가깝게 기록 → 비용 미반영(실전화 불가)

## 5) Regime(레짐에서만 먹는가?)
- 지표(관측 ETF만): `QQQ`, `XLV`, `TLT/IEF` 모멘텀/변동, 시장 변동성 proxy
- 해석:
  - 특정 레짐에서만 초과성과 → 레짐 필터/리스크 오프 스위치가 “적용 단계”에서 작동하는지 확인

## 48시간 자동 루프 운영 형태(권장 고정 순서)
1) **TOP1 로그/해시/MDD 복구** → 관측 가능성 확보  
2) **TOP2 폴드 퇴화 FAIL-FAST + purge/embargo** → 누수/과최적화 차단  
3) **TOP3 비용 모델 C + 턴오버 게이트** → 실전화 기준으로 후보 절삭  
4) **TOP4 유니버스/종목수/섹터/노출 정책 강제** → 요구사항 준수 + 변동원 제거  
5) **TOP5 노델타 5단 분해 리포트** → 성능 정체를 “단계”로 귀결해 다음 패치가 자동으로 나오게 함

이 TOP5를 통과하면, 이후부터는 “전략 파라미터 탐색”을 늘려도 케이스 폭발 없이(실질 다양성/적용 가능성/비용 반영) 자동 루프가 학습하는 구조가 됩니다.
