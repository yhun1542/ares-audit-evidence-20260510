[진단: Degenerate Folds (폴드 1,2,3,8) 비활성 문제 및 로깅 시스템 붕괴가 최우선 해결 과제]

현재 8개 중 4개의 폴드가 퇴화(Degenerate)된 상태임에도 OOS Mean이 3.32라는 것은, 나머지 폴드에서 극심한 과적합(Overfitting)이 발생했거나 특정 시기에만 거래가 몰려있음을 시사합니다. 로그 파일 로딩 실패로 인해 원인 파악이 불가능한 상태이므로, **'가시성 확보'**와 **'죽은 구간 소생'**이 최우선입니다.

### 1. 우선순위 TOP 5 제안 (48시간 루프)

#### Action 1: Rebalance Logger 포맷 강제 수정 및 검증
*   **(a) 필요성:** `Expecting value: line 1 column 1` 에러는 로그 파일이 비어있거나(Flush 안됨) 경로가 잘못됨을 의미. 거래 내역 없이는 과최적화 진단 불가.
*   **(b) 리스크:** I/O 오버헤드 증가 가능성 (미미함).
*   **(c) 실험 (Experiments):**
    1.  `FIX_LOG_FLUSH`: 매 Step/Bar마다 강제 `file.flush()` 호출 및 JSONL 포맷 유효성 검사 로직 추가.
    2.  `LOG_ALL_SIGNALS`: 체결된 거래뿐만 아니라, 필터링(Reject)된 신호까지 모두 로깅하도록 레벨 격상.
*   **(d) PASS 조건:** `aub_rebalance_pinpoint.py`가 에러 없이 파싱되고, Fold 1,2,3,8의 로그 파일 사이즈가 0바이트가 아님.

#### Action 2: Universe & Data Availability 점검 (Survivorship Bias)
*   **(a) 필요성:** Fold 1, 2, 3(과거 구간 추정)이 Degenerate 된 원인이 Tech/Healthcare 종목 8~14개가 해당 시점에 상장되어 있지 않거나 데이터가 없어서일 가능성 높음.
*   **(b) 리스크:** 유니버스 교체 시 전체 하이퍼파라미터 튜닝 다시 필요.
*   **(c) 실험 (Experiments):**
    1.  `UNIVERSE_DYNAMIC`: 고정 종목 리스트 대신, 각 폴드 시작 시점 기준 시총 상위 Tech/HC 종목을 동적으로 로딩.
    2.  `FILL_METHOD_CHECK`: 데이터 누락(NaN) 처리 방식이 `Drop`이 아닌지 확인. `ForwardFill`로 변경 후 신호 발생 여부 확인.
*   **(d) PASS 조건:** Degenerate Folds 목록에서 최소 2개 이상 제거(활성화).

#### Action 3: 진입 장벽(Threshold) 완화 스트레스 테스트
*   **(a) 필요성:** Tech/HC 섹터 특성상 변동성이 죽는 구간에서 필터가 너무 타이트하여 거래가 0이 될 수 있음.
*   **(b) 리스크:** False Positive 진입 증가로 MDD 악화 가능성.
*   **(c) 실험 (Experiments):**
    1.  `RELAX_VOL_FILTER`: 최소 변동성/거래량 요구치를 현재의 50% 수준으로 하향 조정.
    2.  `FORCE_ENTRY_TEST`: 랜덤 엔트리를 섞어서 시스템이 해당 구간에서 '거래 자체'는 가능한지(코드 오류 vs 로직 필터링) 구분.
*   **(d) PASS 조건:** Fold 1,2,3,8의 `exposure_max` > 0.1 기록.

#### Action 4: ETF(QQQ/XLV) 레짐 필터 민감도 조정
*   **(a) 필요성:** ETF를 관측지표로만 사용 중이나, 해당 지표의 이동평균선/RSI 등이 '하락장'으로 인식되어 개별 종목 매수를 전면 차단하고 있을 가능성.
*   **(b) 리스크:** 하락장 방어 능력 상실.
*   **(c) 실험 (Experiments):**
    1.  `REGIME_OFF`: ETF 기반 마켓 필터를 끄고 개별 종목 시그널만으로 백테스트 수행.
    2.  `REGIME_LAG_REDUCE`: 레짐 판단에 사용하는 지표의 룩백(Lookback) 기간을 1/2로 단축.
*   **(d) PASS 조건:** OOS Mean의 하락폭이 10% 이내이면서, Exposure Time이 20% 이상 증가.

#### Action 5: 슬리피지 및 비용 모델 현실화 (Worst-case)
*   **(a) 필요성:** 현재 `oos_min`이 음수(-0.02)로, 샤프지수가 높아도 실제 운영 시 손실 가능성 존재. Tech/HC는 호가 공백이 발생할 수 있음.
*   **(b) 리스크:** 성과 지표 대폭 하락으로 챔피언 폐기 가능성.
*   **(c) 실험 (Experiments):**
    1.  `COST_DOUBLE`: 슬리피지와 수수료를 현재 설정의 2배로 적용.
    2.  `LIQUIDITY_PENALTY`: 일평균 거래량 하위 20% 종목 매매 시 추가 페널티 부여.
*   **(d) PASS 조건:** 비용 증가 후에도 OOS Mean > 1.5 유지.

### 3. 성능 정체 시 원인 분해 (Debugging Logic)

성능 지표가 움직이지 않을 때, 다음 순서로 병목을 점검하십시오.

1.  **Trigger (신호 발생):** 전략 로직이 `Buy` 신호를 생성하는가?
    *   *Check:* `Raw Signal Count`가 0인지 확인. 0이면 지표(Indicator) 계산 로직 오류 혹은 데이터 NaN 문제.
2.  **Filter (여과):** 신호는 있는데 `Reject` 되는가?
    *   *Check:* 로그에서 `Reject Reason` 집계 (예: `Liquidity`, `Regime`, `Max Position`). 특정 필터가 90% 이상을 막고 있다면 그 필터가 과적합의 주범.
3.  **Execution (체결):** 주문은 나갔는데 체결이 안 되는가?
    *   *Check:* 시가/고가/저가 데이터 오류로 인한 `Limit Order` 미체결 확인.
4.  **Exposure (비중):** 체결은 됐는데 비중이 너무 작은가?
    *   *Check:* 포트폴리오 최적화(Mean-Variance 등) 모듈이 특정 자산에 0.001% 비중만 할당하는지 확인 (최적화 솔버 오류).
5.  **Cost (비용):** 수익은 났는데 비용이 다 깎아먹는가?
    *   *Check:* `Gross Profit` vs `Net Profit` 괴리율 확인. 회전율(Turnover)이 과도하게 높은지 점검.
