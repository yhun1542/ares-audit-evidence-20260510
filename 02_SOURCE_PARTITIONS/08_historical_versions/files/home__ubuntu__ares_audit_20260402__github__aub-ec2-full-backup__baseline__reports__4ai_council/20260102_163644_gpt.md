## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — **명령형 체크리스트**

### 1) **실험/리밸런스 로그 파이프라인 복구(재현성·감사 가능성)**
**왜 필요?**  
- 현재 `aub_rebalance_pinpoint`가 **입력 파일 포맷/경로 문제로 완전히 실패**(csv/jsonl 둘 다 로딩 실패).  
- Champion에 `worst_mdd=None`, `lane_hash/run_hash=None` → **성과가 “좋아 보이는” 상태 자체가 감사 불가**(운영 리스크 최상위).  
- 성능이 안 움직일 때 원인 분해(트리거/적용/노출/비용)를 하려면 **리밸런스 이벤트/체결 가정 로그가 필수**.

**위험/부작용**  
- 로깅/스키마 변경으로 과거 리포트/툴 호환 깨짐  
- 단기적으로 “성능 개선”이 아니라 “측정 가능성 개선”이라 체감 성과는 0일 수 있음(하지만 우선순위 1)

**연결 최소 실험(공유 실험 사용)**: **E1, E5**  
**PASS 조건(이 제안 자체)**  
- `aub_rebalance_pinpoint.py`가 **base/cand 모두에서 non-empty 리밸런스 로그**를 읽고 리포트를 생성  
- 모든 run에 `run_hash/lane_hash/config_hash/data_hash`가 박힘  
- `worst_mdd`가 항상 산출(None 금지)

---

### 2) **누수/과최적화 1차 차단: degenerate fold 제거 + 검증 프로토콜 교정**
**왜 필요?**  
- `degenerate_folds: [1,2,3,8]`는 **검증 자체가 무너진 상태**(레이블 누수/빈 구간/동일 구간 재사용/샘플 수 부족 등).  
- OOS mean이 나와도 “우연/오류” 가능성이 높아 다음 패치를 해도 성능이 “안 움직이는” 것처럼 보임.

**위험/부작용**  
- 올바른 검증으로 바꾸면 OOS 평균이 내려갈 수 있음(하지만 신뢰도는 올라감)  
- purged/embargo 적용 시 유효 샘플 감소 → 변동성 증가 가능

**연결 최소 실험**: **E2, E4**  
**PASS 조건**  
- `degenerate_folds`가 **빈 배열**  
- IS/OOS 격차(예: Sharpe/mean)가 **급격히 벌어지지 않음**(과최적화 징후 완화)  
- OOS min(현재 -0.0257)이 **동일 레짐/기간에서 악화되지 않음**

---

### 3) **비용/체결/차입/슬리피지 미반영 제거(‘가짜 알파’ 제거)**
**왜 필요?**  
- 비용 미반영은 누수 다음으로 흔한 “성능 고정/붕괴” 원인.  
- Tech/Healthcare 8~14종목 집중은 **회전율/갭리스크/이벤트 리스크**가 커서, 비용 모델 없으면 최적화가 “비용 0인 세상”으로 달림.

**위험/부작용**  
- 비용을 넣으면 성능이 즉시 크게 하락할 수 있음(그 경우가 오히려 유익: 모델이 현실적이지 않았다는 증거)  
- 비용 모델 파라미터를 또 최적화하면 과최적화 재발 가능 → **민감도(robustness) 실험만** 하라

**연결 최소 실험**: **E3, E5**  
**PASS 조건**  
- (비용 적용 후) OOS 성능이 **기존 대비 -20% 이내**로 유지되거나, 하락 시 **원인이 회전율/슬리피지로 명확히 분해**됨  
- 턴오버가 상한(예: 일간/주간)을 초과하면 자동 Fail 처리

---

### 4) **서바이버십/코퍼레이트액션/유니버스 위생(미국 Tech+Healthcare 8~14로 고정)**
**왜 필요?**  
- 서바이버십/상장폐지/분할·배당 조정 오류는 OOS가 “안 움직이거나” “특정 구간만 과도하게 좋게” 만드는 대표 원인.  
- “US only + Tech/Healthcare”를 강제하면, 모델이 다른 섹터/국가로 도망가며 생기는 **숨은 레짐 의존**을 줄임.  
- ETF는 거래 금지(지표만): SPY/QQQ/XLK/XLV는 **레짐/리스크 지표**로만 사용.

**위험/부작용**  
- 진짜로 서바이버십이 섞여 있었다면 성능이 유의미하게 하락 가능(정상)  
- 유니버스 축소로 분산 감소 → MDD가 커질 수 있어 리스크 제어가 동반되어야 함

**연결 최소 실험**: **E4, E5**  
**PASS 조건**  
- 유니버스가 항상 **미국 상장, Tech+Healthcare, 8~14 보유**를 만족(ETF 매매 0)  
- 상장폐지/심볼 변경/분할 이벤트가 있어도 가격/수익률이 깨지지 않음(비정상 스파이크 0)

---

### 5) **운영 리스크/노출 리스크: 포지션·리밸런스·레짐 게이트를 48h 루프에 고정**
**왜 필요?**  
- Champion `exposure_max ~0.84` + `worst_mdd None` 조합은 **리스크 상태를 알 수 없는 채로 돈이 들어가는 구조**.  
- 48시간 자동 루프에서는 “성능 개선”보다 “망가질 때 자동으로 멈추는 장치(게이트)”가 먼저.

**위험/부작용**  
- 게이트가 과도하면 트레이드가 줄어 성능이 평평해질 수 있음  
- 레짐 필터를 또 최적화하면 과최적화 위험 → “단순/보수적 룰”로 고정

**연결 최소 실험**: **E5(핵심), E1**  
**PASS 조건**  
- 모든 런에서 **노출/보유수/섹터/턴오버/비용/드로우다운**이 자동 산출 및 게이트 통과/실패가 기록  
- 실패 시 자동으로 “다음 루프에서 파라미터 탐색 중단 + 원인 태깅” 실행

## 48시간 자동 루프용 “실행 가능한” Patch/실험(총 5개, 케이스 폭발 금지)
아래 5개만 돌리고, 각 실험은 **(1)정의 → (2)게이트 → (3)기대 관측치** 형태로 고정.

### E1) **리밸런스 로그/스키마 패치 + lineage 강제**
1) **실험 정의**  
- 백테스트 출력에 `rebalance.jsonl`(한 줄=한 이벤트, JSON) 생성 강제  
- 필수 필드: `ts, symbol, target_w, prev_w, trade_qty, est_fill_px, est_cost_bps, adv, slippage_bps, reason(signal/risk), run_hash, data_hash`  
- `run_hash/lane_hash/config_hash`를 모든 artifact 이름에 포함(경로 에러 방지)

2) **게이트**  
- `aub_rebalance_pinpoint.py`가 base/cand 모두에 대해 **오류 없이 리포트 생성**  
- 리밸런스 이벤트 수가 0이 아니고, JSON 파싱 실패 0  
- `worst_mdd != None`

3) **기대 관측치**  
- “성능이 안 움직임”의 원인이 **리밸런스 없음/거래 0/로그 누락/포맷 불일치** 중 무엇인지 즉시 분해됨  
- 이후 실험(E2~E5)의 변화가 리밸런스 단위로 추적 가능해짐

---

### E2) **Degenerate fold 제거 + Purged Walk-Forward(embargo)**
1) **실험 정의**  
- 폴드 생성기를 교체/수정: purged walk-forward + embargo(예: 5~20 trading days 고정)  
- 각 fold에 최소 샘플/최소 거래일 조건 추가(미달 시 fold 자체를 만들지 말고 기간을 재분할)

2) **게이트**  
- `degenerate_folds == []`  
- 각 fold에 대해 “훈련 구간과 테스트 구간이 겹치는 bar 수 = 0” (purge 검증)  
- OOS min이 동일 기간 기준으로 **더 악화되면 Fail**(누수 제거로 인한 일시 하락은 허용하되, tail이 더 나빠지면 구조적 문제 가능)

3) **기대 관측치**  
- OOS mean이 내려가더라도 분산/폴드 간 편차가 줄고, 재현성이 올라감  
- “성능이 고정”의 원인이 과최적화/누수였는지 빠르게 판별됨

---

### E3) **비용/슬리피지/차입 비용 민감도 스윕(최적화 금지, 관측만)**
1) **실험 정의**  
- 비용 3점만 고정 테스트(예: 5/15/30 bps all-in + ADV 기반 슬리피지)  
- 공매도/차입 발생 시 borrow cost(보수적으로) 추가  
- 결과를 “비용 전/후 성과 + 턴오버 + 거래당 기대엣지”로 분해 저장

2) **게이트**  
- 기준 비용(중간값)에서 OOS 성과가 **-20% 초과 붕괴 시 Fail**  
- 턴오버가 상한 초과 시 Fail(상한은 고정 룰로)

3) **기대 관측치**  
- 엣지가 비용에 취약하면 “신호는 맞지만 너무 자주/너무 작은 엣지를 거래”하는 구조가 드러남  
- 이후엔 신호 개선보다 **거래 억제/리밸런스 주기/트레이드 임계값**이 핵심이라는 결론을 빠르게 얻음

---

### E4) **서바이버십/코퍼레이트 액션/유니버스(US Tech+Healthcare 8~14) 감사 패치**
1) **실험 정의**  
- 유니버스 빌더를 “당일 시점 가용 정보”로만 구성(미래 시총/지수편입 금지)  
- 상장폐지(Delist) 처리/심볼 변경/스플릿·배당 조정 파이프라인 체크  
- 최종 보유는 항상 8~14개, Tech+Healthcare로만 제한(ETF 거래는 0)

2) **게이트**  
- 유니버스가 미래 정보를 참조하는 필드 사용 시 즉시 Fail(정적 규칙 검사)  
- 가격 수익률 시계열에 “비정상 단일일 급등락” 규칙 위반 시 Fail(코퍼액션 오류 탐지)

3) **기대 관측치**  
- “특정 기간만 좋음/나쁨”이 데이터 이벤트(심볼 변경/분할) 때문인지 판별 가능  
- OOS가 내려가도 신뢰 가능한 성과선으로 바뀜

---

### E5) **48h 운영 게이트(노출/리스크/레짐) 고정 + ETF는 ‘지표만’ 사용**
1) **실험 정의**  
- 포트폴리오 규칙을 하드코딩 수준으로 고정:
  - 보유 수 8~14 강제
  - 단일 종목 최대 비중 상한
  - 총 노출 상한/하한(현재 0~0.84 → 의도한 범위로 정리)
  - 변동성 타게팅(단순) 또는 드로우다운 브레이크(단순)
- 레짐 지표로만 SPY/QQQ/XLK/XLV를 사용(매매 0). 예: 위험회피 레짐에서는 목표 노출 축소.

2) **게이트**  
- 모든 런에서 `exposure_min/max`, `n_holdings`, `max_weight`, `turnover`, `cost`가 저장되고 규칙 위반 시 Fail  
- `worst_mdd`가 산출되며 상한 초과 시 Fail

3) **기대 관측치**  
- 성능이 안 움직여도 “노출이 걸려서 못 움직이는지/레짐이 막는지/리밸런스가 줄었는지”가 즉시 보임  
- 운영 중 사고(과도한 집중, 갑작스런 턴오버 폭증)를 자동 차단

## 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래 순서대로 **위에서 아래로 단방향 점검**하라(질문 금지, 체크만).

### A. 트리거(신호 발생) 문제
- 신호 분포를 저장하고, 최근 6~12개월에서 **신호 분산이 0에 수렴**하는지 확인  
- 신호가 레짐/섹터 제한(Tech+Healthcare) 후에도 충분히 발생하는지 확인  
- 신호가 특정 1~2종목에만 몰리는지 확인(집중 → 과최적화 가능)

### B. 적용(신호→주문 변환) 문제
- 리밸런스가 “생각보다 안 일어나는”지 확인:  
  - 임계값(최소 변경폭) 때문에 trade 0  
  - 보유수 8~14 제약 때문에 후보가 잘려 trade 0  
- 리밸런스 주기/캘린더 정렬 문제(휴장/타임존)로 주문이 빠지는지 확인

### C. 노출(포지션 크기/상관) 문제
- 총 노출이 상단(예: 0.84) 근처에서 고정되어 “더 개선해도 반영이 안 되는지” 확인  
- Tech/Healthcare 내에서 상관이 높아 **실질 분산이 없는지** 확인  
- 베타가 SPY에 과도하게 붙어 레짐 변화에 수익이 상쇄되는지 확인(지표만으로 측정)

### D. 비용(거래/슬리피지/차입) 문제
- “거래당 기대엣지(예상 알파)” vs “거래당 비용” 로그로 비교  
- 회전율이 증가하면 OOS가 안 움직이는 이유가 **비용이 먹는 구조**인지 확인  
- 작은 엣지를 잦게 거래하는지(거래 빈도 과다) 확인

### E. 레짐(시장 상태) 문제
- SPY/QQQ 추세·변동성, XLK/XLV 상대강도 같은 **관측 지표**로 구간 태깅 후, 구간별 성과를 분해  
- “좋았던 레짐”에만 맞춰진 신호인지 확인(서바이버십/과최적화와 연결)

### F. 구현/데이터 오류(최우선 배제)
- degenerate fold, 리밸런스 로그 부재, 코퍼액션 오류는 성능이 “안 움직이는 것처럼” 만들거나 “가짜로 좋아 보이게” 만든다 → **E1/E2/E4로 선제 제거**  

---

### 48시간 운영 원칙(고정)
- **E1→E2→E3→E4→E5 순서로만** 진행(로그/검증 없이는 전략 수정 금지)  
- 각 루프마다: “게이트 실패 원인 태그(Leakage/Cost/Exposure/Universe/Ops)”를 1개만 찍고 다음 행동을 자동 결정  
- 성능 최적화보다 **신뢰도(누수·비용·서바이버십·운영 리스크 제거)**를 우선 달성하라
