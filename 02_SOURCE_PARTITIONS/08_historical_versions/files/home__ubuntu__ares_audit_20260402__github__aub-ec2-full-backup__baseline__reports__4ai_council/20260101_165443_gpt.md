아래는 **향후 24~48시간**에 “자동 루프(48h)”로 바로 굴릴 수 있는 **TOP5 우선순위 patch/실험**이다. (우선 점검 순서: **누수 → 과최적화 → 서바이버십 → 비용/슬리피지 → 운영 리스크**).  
**미국주식 only, Tech+Healthcare 중심(8~14 종목, ETF 매매 금지)** 기준을 유지하고, ETF는 **레짐 관측 지표**로만 쓴다.

## PRIORITY 1) “락박스 결과가 안 움직이는” 운영 리스크/평가 무결성 패치
현 상태에서 **Champion과 Candidate의 lockbox_mean/min이 완전히 동일**하게 반복되는 건, 개선이 “진짜로 없음”일 수도 있지만 **(a) 캐시/스냅샷 재사용 (b) 동일 예측 산출 (c) 평가 파이프라인이 후보 변경을 반영 못함** 가능성이 높다. 이건 최우선 운영 리스크다.

### (a) 왜 필요한지
- 실험이 실제로 다르게 돌아가도 **락박스 평가가 동일하게 고정**되면, 이후 모든 최적화/전략 논의가 무의미해짐.
- 누수/과최적화 점검 전에 **“측정이 맞는지”**부터 보장해야 함.

### (b) 위험/부작용
- 캐시를 끄면 실행 시간이 증가할 수 있음.
- RNG/병렬성 통제 강화로 성능이 “일시적으로” 흔들릴 수 있음(재현성 확보 과정에서 드러나는 변동).

### (c) 최소 실험 2~3개 (48h 루프용)
**실험 정의(공통):** 매 run마다 아래 3가지 로그를 lockbox 리포트에 강제 포함
1) `data_fingerprint`(입력 데이터 해시)  
2) `feature_fingerprint`(피처 매트릭스 해시/shape)  
3) `pred_fingerprint`(락박스 예측 벡터 해시/상위 20개 값 샘플)

- **Exp1-1: Lockbox 캐시 무효화 강제**
  - 패치: lockbox 평가 단계에 `--no-cache` 또는 캐시 키에 `candidate_file_hash` 포함.
  - 게이트: 동일 후보 재실행 시 fingerprint 동일, 다른 후보면 pred_fingerprint가 달라야 함.
  - 기대 관측치: 후보 변경 시 lockbox 예측 해시 변화가 발생.

- **Exp1-2: Seed/환경 결정성 고정**
  - 패치: 파이프라인 시작 시 seed 고정(파이썬/넘파이/토치) + 데이터 로더 순서 고정.
  - 게이트: 같은 후보 2회 run 결과가 lockbox 수익곡선/지표 완전 동일.
  - 기대 관측치: 재현성 확보(“같은 입력→같은 출력”).

- **Exp1-3: “후보 적용 여부” 단위테스트**
  - 패치: 후보 모델 로딩 후 파라미터 요약(레이어 수/가중치 checksum)을 리포트에 기록.
  - 게이트: champion vs candidate에서 model_checksum이 반드시 달라야 함.
  - 기대 관측치: 평가가 실제로 다른 모델을 읽고 있음을 확인.

### (d) PASS 조건
- **필수 PASS:** candidate 변경 시 `pred_fingerprint` 또는 `model_checksum`이 변하고, lockbox 지표가 “동일 고정”이 아닌 **변동 가능한 상태**로 확인됨.
- **실패 신호:** 후보를 바꿔도 pred_fingerprint가 동일 → 파이프라인 결함 확정.

## PRIORITY 2) 비용/슬리피지/체결 지연(운영 현실) 반영 + net 성능 게이트 추가
현재 지표에 “비용 미반영” 가능성이 있으면, 튜닝이 전부 **허상(과최적화)**이 되기 쉽다. 특히 Tech/Healthcare 8~14개 집중 포트는 회전율이 조금만 커도 net이 급격히 무너진다.

### (a) 왜 필요한지
- **gross 성능 개선**이 **net 성능 정체**로 나타나는 대표 원인이 비용/슬리피지.
- 운영 시 체결은 close 체결이 아니라 **다음날 VWAP/오픈 근처**가 많음(지연 고려 필요).

### (b) 위험/부작용
- 비용 반영하면 당연히 성능 지표가 하락할 수 있음(현실화).
- 너무 보수적 비용 모델은 전략을 과도하게 죽일 수 있음(보정 필요).

### (c) 최소 실험 2~3개
- **Exp2-1: 단순 비용 모델(필수) 삽입**
  - 패치: 거래마다 `commission + spread + impact`를 단순 모델로 차감  
    - 예: commission 1bp + spread 2bp + impact = k * (turnover) (k는 5~15bp 범위 시나리오)
  - 게이트: 모든 리포트에 gross/net 동시 출력, turnover 출력 의무화
  - 기대 관측치: gross는 유지/소폭 개선인데 net이 안 나오는 경우 즉시 식별

- **Exp2-2: 체결 지연(1-bar delay) 시뮬**
  - 패치: 신호 t에 생성 → 포지션 반영은 t+1 (또는 next open/next close)
  - 게이트: delay 적용 시에도 lockbox_mean이 특정 하한 유지
  - 기대 관측치: “종가 기준 과적합” 여부 식별(누수/실행불가 신호 방지)

- **Exp2-3: 회전율 제한(거래 억제)**
  - 패치: 일별 turnover 상한(예: 25~40%) 또는 신호 변화 임계값 미만 거래 금지
  - 게이트: net 성능 개선 또는 MDD 개선이 동반
  - 기대 관측치: 비용 민감 전략인지 확인(비용에 죽는지)

### (d) PASS 조건
- lockbox 기준:
  - `net_lockbox_mean`이 **champion net 대비 +X% 개선**(예: +3~5% 상대) 또는
  - `net_lockbox_mean` 유지하면서 `turnover` 또는 `worst_mdd` 개선
- 최소 조건: gross만 좋아지고 net이 악화되면 PASS 불가.

## PRIORITY 3) 누수/서바이버십/데이터 정합성 “하드 게이트” 추가
Tech/Healthcare는 이벤트(실적, FDA, M&A) 영향이 크고, **Point-in-Time 미준수**가 가장 흔한 누수 원인이다. 또한 유니버스가 “현재 생존 종목” 기준이면 서바이버십 편향이 바로 들어간다.

### (a) 왜 필요한지
- 누수는 락박스에서도 “안전해 보이는” 성능을 만들 수 있음.
- 유니버스 편향은 장기 백테스트를 구조적으로 왜곡.

### (b) 위험/부작용
- 누수 제거하면 성능이 내려갈 수 있음(하지만 그게 현실).
- 데이터 소스/정합성 개선은 단기 구현 부담이 있음.

### (c) 최소 실험 2~3개
- **Exp3-1: “타임스탬프 정렬” 강제 검사**
  - 패치: 피처별 `available_time`을 두고, 학습/예측 시점보다 늦은 데이터가 섞이면 즉시 실패(raise)
  - 게이트: 누수 의심 row count = 0
  - 기대 관측치: 기존에 성능이 높던 구간에서 누수 에러가 터지면 원인 확정

- **Exp3-2: Corporate Action / delist 처리 점검**
  - 패치: (가능한 범위에서) delist return, split/dividend 조정, 휴장일 정합성 검사 리포트
  - 게이트: 가격 점프/0거래일 등 이상치 탐지 로그가 기준치 이내
  - 기대 관측치: 특정 종목이 성능을 “가짜로” 끌어올렸는지 확인

- **Exp3-3: 유니버스 고정(8~14) “사전 정의 + 변동 금지” 모드**
  - 패치: 백테스트 전체 구간에 대해 동일 티커 리스트를 사용(Tech+HC 혼합), 중도 교체 금지(교체는 별도 실험)
  - 게이트: run 메타에 `universe_hash` 고정
  - 기대 관측치: 유니버스 변경으로 생기는 착시 제거

### (d) PASS 조건
- 누수 검사 0건 + 유니버스/데이터 해시 고정 + 비용 반영 상태에서 성능이 유지(혹은 하락폭 제한)되면 PASS.
- 누수 적발 시: 성능이 좋아도 즉시 FAIL(우선 수정).

## PRIORITY 4) 레짐(위험온/오프) “관측 기반” 리스크 오버레이 (ETF는 지표로만)
ETF 매매는 금지이므로, **QQQ/XLV/SPY/TLT(또는 SHY)/VIX** 등을 “관측 지표”로만 써서 **포지션 사이징/노출 차단**을 한다. Tech+HC 집중은 레짐에 민감해서 MDD 개선 여지가 크다.

### (a) 왜 필요한지
- 동일 알파라도 레짐별 분산이 크게 달라 **worst_mdd**가 생김.
- 레짐 오버레이는 모델을 바꾸지 않고도 “운영 리스크”를 줄이는 빠른 패치.

### (b) 위험/부작용
- 잘못된 레짐 규칙은 상방을 깎아먹음.
- 레짐 규칙이 많아지면 과최적화 위험(규칙은 1~2개로 제한).

### (c) 최소 실험 2~3개
- **Exp4-1: 변동성 게이트(단일 룰)**
  - 패치: VIX(또는 SPY realized vol) 상위 분위 구간에서는 총 익스포저를 50~70%로 축소
  - 게이트: lockbox worst_mdd 개선(예: -0.090 → -0.075 이하)
  - 기대 관측치: 고변동 구간 손실 꼬리 감소

- **Exp4-2: QQQ/XLV 모멘텀 기반 Tech 편향 제한**
  - 패치: `QQQ momentum < 0`이면 Tech 비중 cap을 낮추고 Healthcare 비중 상향(티커는 여전히 8~14 범위 내)
  - 게이트: MDD 개선 + mean 유지(하방 보호가 상방 훼손을 과도하게 만들지 않는지)
  - 기대 관측치: Tech drawdown 구간에서 포트 손실 완화

- **Exp4-3: 상관 급등 시 포지션 스케일 다운**
  - 패치: 보유 종목 간 20일 상관 평균이 임계값 초과하면 전체 레버리지/익스포저 축소
  - 게이트: worst_mdd 및 tail loss 개선
  - 기대 관측치: “다 같이 무너지는 날” 방어

### (d) PASS 조건
- lockbox에서 **worst_mdd 개선**이 명확하고(mean이 소폭 감소하더라도) **risk-adjusted 개선**이 확인되면 PASS.
- 비용 반영 후에도 효과가 유지되어야 함.

## PRIORITY 5) 포트폴리오 구성(8~14종) 규칙의 과최적화/노출 쏠림 방지 패치
8~14종 집중 포트는 “한 종목/한 팩터”에 쏠리면 성능이 정체되거나 특정 폴드에서 깨진다. 모델보다 **포트 구성 규칙**이 병목인 경우가 많다.

### (a) 왜 필요한지
- tuning_mean은 오르는데 lockbox가 안 오르는 패턴은 **구성 규칙의 과최적화/불안정** 신호일 수 있음.
- 극단 포지션이 비용/슬리피지를 키움.

### (b) 위험/부작용
- 제약을 걸면 상방이 제한될 수 있음.
- 너무 많은 제약은 복잡도만 올림(제약은 2~3개까지만).

### (c) 최소 실험 2~3개
- **Exp5-1: 단일 종목 최대 비중 cap**
  - 패치: max weight 12~18% (N=8~14이면 현실적)
  - 게이트: worst_mdd 또는 fold별 분산 개선
  - 기대 관측치: 특정 종목 의존 감소

- **Exp5-2: 리스크 패리티(근사) 포지션 사이징**
  - 패치: 동일 달러 비중 대신 20~60일 변동성 역수로 스케일(간단 버전)
  - 게이트: 동일 mean 대비 MDD/변동성 개선
  - 기대 관측치: 고변동 종목이 포트를 망가뜨리는 현상 감소

- **Exp5-3: 거래 “쿨다운”**
  - 패치: 진입 후 최소 보유기간(예: 3~5거래일) 또는 신호 반전 2회 확인 후 청산
  - 게이트: turnover 하락 + net 개선
  - 기대 관측치: 미세 신호에 의한 과잉매매 억제

### (d) PASS 조건
- 비용 반영 net 기준으로 **mean 유지 또는 개선** + **turnover 감소** 또는 **worst_mdd 개선**이 동반되면 PASS.

# 48시간 자동 루프용 “실행 체크리스트”(명령형)
아래 순서대로 적용/실행하라.

1) **평가 무결성 패치부터 적용하라 (PRIORITY 1)**  
   - lockbox 리포트에 `data/feature/pred fingerprint`, `model_checksum`, `universe_hash`, `seed`를 강제 출력하라.  
   - candidate 바꿨는데 fingerprint가 같으면 즉시 파이프라인 버그로 분기하라.

2) **비용/지연 체결을 기본 시뮬에 포함하라 (PRIORITY 2)**  
   - gross/net, turnover, trade count를 모든 리포트의 1페이지에 고정 표기하라.  
   - 1-bar delay 평가를 “옵션”이 아니라 “기본 게이트”로 추가하라.

3) **누수/서바이버십 하드 게이트를 넣어라 (PRIORITY 3)**  
   - point-in-time 위반 탐지 시 해당 run을 FAIL 처리하라(성능이 좋아도 폐기).  
   - 유니버스는 8~14 Tech+HC 티커로 고정 모드를 기본값으로 두어라.

4) **레짐 오버레이는 1~2개 규칙만 실험하라 (PRIORITY 4)**  
   - VIX/realized vol 기반 익스포저 축소부터 먼저 붙여라.  
   - QQQ/XLV는 “관측 지표”로만 사용하라(매매 금지).

5) **포트 제약은 단순하게, net+MDD 개선을 노려라 (PRIORITY 5)**  
   - max weight cap + 변동성 스케일 중 하나만 먼저 넣고, 나머지는 다음 루프에 올려라.

# 성능이 안 움직일 때: 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래를 “한 장 진단 리포트”로 매 run마다 자동 출력하라. (질문 없이 바로 추가하라.)

## A. Trigger(신호 자체가 변하는가?)
- 신호 분포(평균/표준편차/상하위 분위) 시계열
- 종목별 신호 상관(너무 높으면 다 같은 신호)
- **IC(Information Coefficient)**: 다음날/5일 수익과의 상관(학습 구간 vs 락박스 비교)

**정체 트리거:** 신호 분포가 거의 고정, 혹은 락박스에서 IC≈0

## B. Apply(신호가 포지션으로 제대로 적용되는가?)
- 포지션 생성 전/후의 top-k 종목 리스트 비교(신호→선정 매핑)
- 제약으로 인한 “클리핑 비율”(cap에 걸린 비중 비율)
- 리밸런싱 타이밍(신호 t가 포지션 t에 반영되는지, t+1인지)

**정체 트리거:** 신호는 변하는데 포지션이 안 변함(룰/코드 버그 또는 과도한 제약)

## C. Exposure(무엇에 노출돼서 먹고/깨지는가?)
- 섹터(Tech vs Healthcare) 비중, 단일 종목 최대 비중
- 팩터 근사 노출: 베타(SPY), 성장(대형 Tech 편향), 변동성(IV proxy)
- 보유 종목 간 평균 상관/집중도(HHI)

**정체 트리거:** 수익이 특정 1~2종목에 과의존 또는 상관 급등 구간에서 일괄 손실

## D. Cost(비용이 성능을 죽이는가?)
- gross vs net 격차(월별/분기별)
- turnover, 평균 보유기간, 거래 횟수
- 슬리피지 민감도(impact k를 5/10/15bp로 스윕했을 때 성능 탄력)

**정체 트리거:** gross는 괜찮은데 net이 0 근처로 눌림

## E. Regime(언제만 먹히는가?)
- VIX/realized vol 분위별 성과
- QQQ 추세(상승/하락)별 성과
- XLV 대비 QQQ 상대강도 구간별 성과

**정체 트리거:** 특정 레짐에서만 수익이 나고 나머지 레짐에서 상쇄

- 48시간 동안은 위 TOP5 중 **동시에 2개 이상 대수술하지 말고**, 아래 우선순위를 고정하라:  
  1) 평가 무결성(필수) → 2) 비용/지연(필수) → 3) 누수 게이트(필수) → 4) 레짐 오버레이(선택) → 5) 포트 제약(선택)
- 각 실험은 **하나의 변화만** 넣고(One change), 리포트에 fingerprint/turnover/gross-net을 고정 출력하라.
