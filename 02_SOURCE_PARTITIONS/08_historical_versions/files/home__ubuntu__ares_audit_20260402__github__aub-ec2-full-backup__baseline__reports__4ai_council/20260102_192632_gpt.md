## 24~48시간 TOP5 우선순위(명령형 체크리스트)

### 1) **누수/서바이버십/타임스탬프 정합성 “센티넬”을 먼저 박아라**
- [ ] 모든 feature/label에 대해 **as-of timestamp** 강제(룩어헤드 차단) + shift 규칙 단일화
- [ ] **survivorship-free universe** 확인(상장폐지/합병/티커변경 포함 여부 로그)
- [ ] 학습/검증/실거래 구간 경계에 **purge+embargo** 적용(최소 1~5bar, 신호 주기 기준)
- [ ] 누수 감지용 **Leakage Sentinel 테스트(의도적 누수/비누수 대비)** 자동 실행

**(a) 왜 필요한지**
- 현재 `degenerate_folds: [1,2,3,8]` 는 데이터 커버리지/경계누수/리밸런스 이벤트 부족이 원인인 경우가 가장 흔함.
- OOS mean 값이 콘솔 출력(2.6276)과 챔피언 메타(3.3249)로 **불일치** → 평가 파이프라인의 시점/샘플 정의가 흔들릴 가능성.

**(b) 위험/부작용**
- purge/embargo로 데이터가 줄어 **OOS mean 일시 하락** 가능(정상적인 “현실화”).
- survivorship-free 적용 시 과거 우주가 확대/변경되어 성능이 “리셋”될 수 있음.

**(c) 최소 실험(공유 실험 풀 사용)**  
- E1, E3 사용(아래 “공유 실험 5개” 참조)

**(d) PASS 조건**
- degenerate fold가 **0개**(또는 전체 fold의 5% 미만)로 감소
- Leakage Sentinel에서 **(누수 on) >> (누수 off)** 차이가 명확하고, (누수 off)의 성능은 과도하게 튀지 않음
- 동일 artifact로 재실행 시 OOS mean이 **±1~2% 이내**로 재현(결정성)

---

### 2) **비용/체결/슬리피지/차입비용 반영 + MDD 산출을 “게이트”로 올려라**
- [ ] 거래비용(수수료+슬리피지) + **체결 지연(다음 bar 체결)** 강제
- [ ] 공매도/헤지 사용 시 **borrow fee / hard-to-borrow 프록시**(최소 고정 bps라도) 반영
- [ ] `worst_mdd: None` 없애기: **equity curve 저장/로드**, MDD/turnover/exposure 계산을 필수화
- [ ] 비용 반영 전/후 성능 차이를 리포트에 고정 섹션으로 출력

**(a) 왜 필요한지**
- “성능이 안 움직임”의 1순위 원인은 대개 **비용/턴오버 드래그** 또는 **체결 가정 과낙관**.
- MDD가 None이면 리스크 게이트가 작동하지 않아 **과최적화가 살아남기 쉬움**.

**(b) 위험/부작용**
- 비용 반영 후 성능 급락 가능(하지만 이게 현실).
- 체결 지연 적용 시 신호 설계(특히 단기 모멘텀)가 무력화될 수 있음.

**(c) 최소 실험**
- E2 사용(필수), E5(노출/턴오버 통제 동반)

**(d) PASS 조건**
- 비용 포함 OOS mean이 비용 미포함 대비 과도하게 붕괴하지 않음(예: **드로우다운은 증가하더라도** Sharpe/승률이 완전 붕괴하지 않을 것)
- turnover가 목표 범위로 수렴(예: 일간 기준 **연환산 300~800%** 같은 내부 기준을 하나 고정)
- worst_mdd가 항상 계산되며, 리포트에 **숫자로** 남음

---

### 3) **CV/폴드 건강도(특히 degenerate fold) 자동 차단 + 레짐 분해를 기본 탑재**
- [ ] fold별 거래 횟수/노출시간/종목수 커버리지 “헬스체크”로 degenerate fold를 사전에 FAIL 처리
- [ ] 시계열 CV에 purge+embargo, 샘플 가중치(시장 변동성 구간) 옵션을 고정
- [ ] 결과를 “전체 평균”만 보지 말고 **레짐(변동성/금리/섹터 상대강도)** 별로 슬라이스

**(a) 왜 필요한지**
- degenerate fold는 단순 버그(리밸런스 없음/필터 과강)일 수도 있고, 전략이 특정 구간에서 **아예 거래를 못 하는 구조**일 수도 있음.
- 레짐 슬라이스 없이 평균만 최적화하면 **서바이버십+과최적화**가 합쳐져 “움직이지 않는” 챔피언이 나옴.

**(b) 위험/부작용**
- FAIL 게이트가 강해지면 통과 실험 수가 줄어 탐색 속도 저하.
- 레짐별 최적화로 “케이스 폭발” 위험(그래서 레짐은 2~3개 축만 고정).

**(c) 최소 실험**
- E3(필수), E1(정합성 연계)

**(d) PASS 조건**
- fold health gate 통과율이 0%/100%로 쏠리지 않고(예: 20~80%) 안정적
- 레짐별 성능 분산이 줄어듦(특정 레짐에서만 기형적으로 좋은 패턴 감소)

### 4) **리밸런스 로그/아티팩트/스키마를 고쳐 “pinpoint 불능” 상태를 끝내라**
- [ ] `aub_rebalance_pinpoint.py`가 **CSV/JSONL/JSON(artifact)** 를 자동 탐색/파싱하도록 스키마 통일
- [ ] 런마다 `lane_hash/run_hash` 강제 생성 + 결과 리포트/로그에 박기
- [ ] 리밸런스 이벤트(시각, 종목, 목표/실현 수량, 비용, 사유)를 JSONL로 저장(없으면 FAIL)

**(a) 왜 필요한지**
- 현재 pinpoint가 `--base-log` 파일 미존재 + `rebalance.csv` 파싱 실패로 **원인 추적이 불가능**.
- 성능이 안 움직일 때는 “무슨 거래가 났는지”가 1차 증거인데, 지금은 증거가 없음.

**(b) 위험/부작용**
- 로그 용량 증가/IO 증가(하지만 48시간 루프에서는 필수 비용).
- 스키마 변경 시 기존 리포트 파서가 깨질 수 있음(버전 필드로 완화).

**(c) 최소 실험**
- E4 단독(운영 실험)

**(d) PASS 조건**
- pinpoint 리포트가 **항상 생성**되고, “리밸런스 없음/파싱 실패”가 0건
- 동일 run_hash로 재생성 시 리밸런스 이벤트가 1:1 일치

### 5) **전략 레이어: ‘미국주식 Tech+Healthcare 8~14종목’ 제약을 “하드코드 게이트”로 고정 + 노출/턴오버 제어**
- [ ] 거래 유니버스: 미국 상장 **Tech+Healthcare**에서만 선택(섹터 분류 소스 고정)  
- [ ] 보유 종목수 **8~14 하드 제약**, 리밸런스 시 벗어나면 FAIL
- [ ] ETF는 **관측 지표(레짐/헤지 신호)** 로만 사용(매매 금지 게이트)
- [ ] 총 노출/베타/섹터 쏠림에 상한(예: gross/net, 단일종목 최대 비중) + 변동성 타게팅

**(a) 왜 필요한지**
- 현재 `exposure_min/max: 0.0 / 0.8388` 로 보아, 구간별로 **현금화/무노출**이 발생할 수 있음 → 성능 “정체”의 전형.
- 종목수/섹터 제약을 나중에 붙이면, 앞단 최적화가 **잘못된 해**를 찾게 됨(운영 제약을 학습에 포함시켜야 함).

**(b) 위험/부작용**
- 제약으로 알파가 줄어드는 대신 안정성이 올라감(단기 성과 감소 가능).
- Tech/HC 내부에서도 팩터 쏠림이 생길 수 있음(대형주 편중 등).

**(c) 최소 실험**
- E5(필수), E2(비용/턴오버와 결합), E3(폴드 건강도와 결합)

**(d) PASS 조건**
- 모든 OOS 구간에서 보유 종목수 8~14 준수율 100%
- 노출(예: net/gross)이 목표 밴드 내 유지(무노출 비율 급감)
- 비용 포함 성과가 “거래 수/턴오버 증가” 없이 개선 또는 유지

# 공유 “패치/실험” 5개 (48시간 자동 루프용: 실험 정의 → 게이트 → 기대 관측치)
> 아래 5개만 실제로 돌리고, 위 TOP5 제안은 이 5개를 조합해 커버한다(케이스 폭발 방지).

## E1) Data As-Of / Leakage Sentinel 패치
1) **실험 정의**
- feature 생성 시각/종가 확정 시각을 명시하고, 모든 feature를 `t` 기준으로 **t-1까지의 정보만** 사용하도록 강제
- 의도적 누수 버전(예: t의 close 사용)을 함께 돌려 Sentinel로 간격 확인
2) **게이트**
- 누수 off에서 degenerate fold 발생 시 FAIL
- 누수 on/off 성능차가 미미하면(예: <10%) FAIL(센티넬 무력)
3) **기대 관측치**
- 누수 on은 과대 성능, 누수 off는 현실 성능으로 내려가며 fold 안정화
- OOS mean 불일치(2.62 vs 3.32) 축소(동일 정의로 수렴)

## E2) 비용/체결지연/MDD 산출 강제 패치
1) **실험 정의**
- 다음 bar 체결, 슬리피지 bps, 수수료, (공매도 시) borrow bps를 고정 파라미터로 주입
- equity curve 저장 → worst_mdd 계산
2) **게이트**
- worst_mdd가 None이면 FAIL
- 비용 포함 후 turnover가 상한 초과 시 FAIL
3) **기대 관측치**
- “좋았던 실험”이 비용에 의해 정렬되며, 진짜 견고한 후보만 남음

## E3) CV Purge/Embargo + Fold Health Gate + 레짐 슬라이스 리포트
1) **실험 정의**
- time-series CV에 purge/embargo 적용
- fold별 거래수/노출시간/종목 커버리지로 health score 산출
- 레짐(예: VIX/금리/QQQ-XLV 상대강도 등 ETF는 지표로만) 별 OOS 분해
2) **게이트**
- health score 하한 미달 fold가 있으면 FAIL
3) **기대 관측치**
- degenerate fold 제거, “특정 구간만 먹히는” 패턴이 리포트에서 바로 보임

## E4) 리밸런스 로그 스키마 통일 + pinpoint 복구
1) **실험 정의**
- 리밸런스 이벤트 JSONL 저장(필드 고정: ts/symbol/target_qty/fill_qty/cost/reason)
- `aub_rebalance_pinpoint.py` 입력 자동탐색(artifact JSON 포함) + 파싱 robust
- run_hash/lane_hash 강제
2) **게이트**
- pinpoint 리포트 생성 실패 시 FAIL
- rebalance 이벤트 0인데 포지션이 변하면 FAIL(로그 누락)
3) **기대 관측치**
- “왜 성능이 안 움직였는지”가 거래 단위로 추적 가능(원인 규명 속도↑)

## E5) 제약 내 전략(8~14 Tech+HC) + 노출/턴오버 제어
1) **실험 정의**
- 유니버스/섹터 하드필터(Tech+HC), 보유 8~14 강제
- 포지션 상한/변동성 타게팅/노출 밴드 적용
- ETF는 레짐 지표로만 사용(매매 금지 검사)
2) **게이트**
- 보유 종목수/섹터 위반 1회라도 FAIL
- 무노출(현금) 비중이 상한 초과(예: 30%+)면 FAIL
3) **기대 관측치**
- 노출 max/min이 더 안정적(0 노출 구간 감소), 비용 포함 성능 변동폭 감소

## 성능이 안 움직일 때 “원인 분해” 실행 트리(트리거/적용/노출/비용/레짐)
아래는 **질문 없이 바로 돌리는** 진단 순서(각 단계는 로그/리포트로 자동 출력하게 패치).

### A) Trigger(신호 생성) 레벨
- [ ] 신호 발생률(바/일 단위) + 상/하위 분위수 분포가 기간별로 유지되는지 출력
- [ ] 신호가 대부분 0/상수면 **feature 스케일/결측 처리/필터 과강** 의심
- [ ] 누수 on/off 대비 격차로 “가짜 알파” 여부 확인(E1)

### B) Apply(매매 규칙 적용) 레벨
- [ ] 제약(8~14종목, 섹터, 리밸런스 주기) 적용 전/후로 **거래 수가 얼마나 줄었는지** 분해
- [ ] 리밸런스가 실제로 발생했는지(이벤트 로그) 확인(E4)
- [ ] 체결 지연 적용 시 성능 붕괴면 “신호-체결 간 시간차 민감” (초단기 구조)로 분류(E2)

### C) Exposure(노출/포지션) 레벨
- [ ] net/gross exposure 시계열 + 무노출 비중 출력(현재 min 0.0이 핵심 경고)
- [ ] 단일종목 최대비중/상위 3개 비중 합계(집중도) 출력 → 과최적화/서바이버십 징후
- [ ] Tech vs HC 내부 비중 쏠림 출력(섹터 제약이 있어도 내부 편향 존재)

### D) Cost(비용/턴오버) 레벨
- [ ] PnL을 **gross PnL / cost / net PnL** 로 분해해서 비용 기여율(%) 출력
- [ ] turnover와 net 성능의 상관을 출력(턴오버가 높을수록 성능 악화면 “비용 지배”)
- [ ] borrow/슬리피지 민감도(±x bps)에서 전략 순위가 뒤집히면 “비용 취약”으로 태깅(E2)

### E) Regime(레짐) 레벨  *ETF는 지표로만*
- [ ] (예) VIX 고/저, (예) 금리(2Y/10Y) 상승/하락, (예) QQQ vs XLV 상대강도 국면으로 OOS를 4~6분면 분해(E3)
- [ ] 특정 레짐에서만 성능이 나오면 → (1) 그 레짐 감지 신호를 명시적으로 쓰거나 (2) 그 레짐만 거래하도록 “거래 게이트”를 추가
