## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — “명령형 체크리스트”
> 우선순위 기준: **누수 → 과최적화 → 서바이버십 → 비용 미반영 → 운영 리스크**를 먼저 제거/계측하고, 그 다음 **노출/레짐**을 조정.  
> 제안은 **5개 patch/실험(각 patch 안에서 2~3개 variant sweep)**만 실행.

---

# 1) [P0] 데이터 누수/시간정합(PIT) + 서바이버십 “센티널” 패치
### (a) 왜 필요한지
- OOS가 “안 움직이거나” 특정 구간에서만 과하게 좋을 때 1순위는 **룩어헤드/리밸런스 시점 오류/피처 as-of 미정합** 가능성.
- Tech+Healthcare(8~14종목)처럼 유니버스가 작을수록, **한두 개 누수**가 전체 성능을 지배하기 쉬움.

### (b) 위험/부작용
- 누수 제거 후 성능이 단기 급락할 수 있음(정상).
- PIT 강제 시 피처 결측이 늘어 신호 약화 가능.

### (c) 최소 실험(2~3개 variant, 48h 루프에 포함)
**실험 정의(1): `exp_pit_sentinel_v1`**
- Variant A: 모든 피처를 **+1 거래일 lag 강제**(의도적 성능 하락 유도)
- Variant B: 이벤트(실적발표일/가이던스/공시 추정치 업데이트) **±3거래일 embargo** 적용
- Variant C: **price/volume-only**(fundamental/estimate/news 계열 피처 전부 off)로 비교

**게이트(2):**
- A(강제 lag)에서 OOS가 “개선”되면 즉시 **누수 의심 FAIL**
- B(embargo) 적용 시 OOS가 비정상적으로 붕괴(예: -50% 이상)하면 **이벤트 시점 누수 의심 FAIL**
- C 대비 A/B의 상대 변화로 “피처군 누수 후보”를 라벨링(자동 리포트 출력)

**기대 관측치(3):**
- 정상이라면 A는 성능 하락, B는 소폭 하락/유사, C는 가장 보수적 기준선.
- 문제 있으면: A가 오히려 좋아지거나, B에서 성능이 과도 붕괴.

**PASS 조건:**
- A가 의미 있게 악화(정상), B는 과도 붕괴 없이 유사 범위, C 대비 “비정상적 초과” 패턴 없음.
- 누수 의심 구간/피처가 특정되면 다음 루프에서 해당 피처군 PIT 수정 커밋까지 자동으로 연결.

# 2) [P0] 비용/슬리피지/회전율(턴오버) “순성과” 패치
### (a) 왜 필요한지
- 현재 로그에 **rebalance 데이터가 누락/파싱 실패**했고(핀포인트 실패), 이 상태는 비용/체결 가정이 사실상 블랙박스일 가능성이 큼.
- 8~14종목 집중 포트는 리밸런스 빈도/회전율이 높으면 **순성과가 0으로 수렴**하기 쉬움.

### (b) 위험/부작용
- 비용을 넣으면 단기 지표(OOS mean)가 떨어질 수 있음(정상).
- 턴오버 페널티는 알파를 “눌러” 신호 반응성이 감소 가능.

### (c) 최소 실험(2~3개 variant)
**실험 정의(1): `exp_cost_model_v1`**
- Variant A: 고정비용 **5bp/side**
- Variant B: 고정비용 **15bp/side**
- Variant C: **ADV 기반 임팩트**(예: k * (order/ADV)) + 최소 5bp floor

+ 공통: 턴오버(일/주) 계산, 목표함수에 **턴오버 페널티(λ * turnover)** 옵션 on

**게이트(2):**
- 비용 5→15bp로 올렸을 때 성능이 “역전”되거나 민감도가 비정상적으로 낮으면(=비용이 적용 안 되는 신호) **FAIL**
- 주간 턴오버가 상한(예: 150~250%/week 같은 과도치) 초과 시 **FAIL**

**기대 관측치(3):**
- 비용 증가에 따라 OOS가 단조 감소(정상), 대신 **턴오버가 감소**하거나 신호가 더 “굵어짐”.
- 비용 적용이 제대로면 net/gross PnL 갭이 일정하게 확대.

**PASS 조건:**
- (A,B,C)에서 **순성과가 부호 유지** 또는 최소한 OOS min이 개선(꼬리 리스크 감소) + 턴오버 상한 이내.

# 3) [P0] 운영 리스크: Rebalance 로그/스키마 표준화 + 핀포인트 도구 “Fail-fast” 패치
### (a) 왜 필요한지
- 현재 상태에서 `aub_rebalance_pinpoint.py`가 **입력 파일 부재/JSON 파싱 실패**로 리포트 생성 불가.
- 이건 전략 문제가 아니라 **자동 루프의 관측 불능(operability failure)** 이라 최우선으로 고쳐야 함.
- `worst_mdd: None`도 리스크 게이트가 사실상 무력화된 신호.

### (b) 위험/부작용
- 로그량 증가/디스크 사용 증가.
- 스키마 변경으로 기존 파서가 깨질 수 있음(버전 필드로 완화).

### (c) 최소 실험(2~3개 variant)
**실험 정의(1): `patch_rebalance_telemetry_v1`**
- Variant A: 리밸런스 로그를 **JSONL 단일 포맷**으로 강제(각 이벤트: ts, universe, weights_pre/post, trades, fills, cost, reason, signal_snapshot)
- Variant B: 동일 내용을 **CSV도 병행**(핀포인트/스프레드시트 확인용)
- Variant C: 런 종료 시 **schema self-check + 샘플 5라인 파싱 테스트** 실패하면 런 자체를 FAIL 처리

**게이트(2):**
- 핀포인트 스크립트가 base/cand 모두에서 **에러 없이 리포트 생성** 못하면 FAIL
- `worst_mdd`, exposure min/max, turnover, cost가 모두 채워지지 않으면 FAIL

**기대 관측치(3):**
- `/reports/rebalance_pinpoint.md`에 “어느 날짜에 무엇이 달라져 PnL이 갈렸는지”가 최소 3개 포인트로 요약됨.
- “성능이 안 움직이는 이유”가 리밸런스 빈도/노출/비용 중 하나로 귀결 가능.

**PASS 조건:**
- 다음 1회 루프에서 핀포인트 리포트 자동 생성 + 핵심 리스크 메트릭(특히 MDD/비용/턴오버) 누락 0.

# 4) [P1] 노출/집중(8~14종목) 제어 패치: 변동성 타겟 + 포지션 상한 + 현금 게이트
### (a) 왜 필요한지
- 현재 노출이 min/max 0.47~0.84로 보이는데(그리고 MDD가 None), **드로우다운 통제가 계측/강제되지 않는** 가능성이 큼.
- Tech+Healthcare 집중은 레짐 바뀔 때 상관이 급상승 → “한 번에 같이 맞는” 리스크.

### (b) 위험/부작용
- 노출을 줄이면 OOS mean이 낮아질 수 있음(대신 OOS min/MDD 개선 기대).
- 포지션 상한은 강한 알파를 희석.

### (c) 최소 실험(2~3개 variant)
**실험 정의(1): `exp_exposure_controller_v1`**
- Variant A: 포트폴리오 **vol targeting 10%**(추정 vol로 레버리지/현금 자동 조절)
- Variant B: vol targeting 15%
- Variant C: **max single-name 12%**, **min holdings 8**, 신호 부족 시 현금(또는 동일 섹터 내 저변동 종목)로 채움

**게이트(2):**
- 섹터(Tech/Healthcare) 외 종목 편입 시 FAIL(유니버스 하드가드)
- holdings < 8 또는 single-name > cap 발생 시 FAIL
- MDD 계산이 누락되면 FAIL(3번 패치와 연동)

**기대 관측치(3):**
- exposure 범위가 더 안정(예: 0.3~0.7 같은 형태) + OOS min 개선.
- 리밸런스가 “자주 크게”가 아니라 “덜 자주/작게”로 이동.

**PASS 조건:**
- OOS mean이 크게 훼손되지 않으면서(예: -5~10% 이내) OOS min 또는 worst_mdd가 명확히 개선.

# 5) [P1] 레짐 오버레이(ETF는 관측지표만): Risk-on/off 디레버 + 섹터 내부 방어 모드
### (a) 왜 필요한지
- Tech는 금리/리스크 프리미엄에 민감, Healthcare는 방어적 성향.  
- 레짐 필터가 없으면 “좋은 알파 + 나쁜 레짐”에서 성능이 상쇄되어 **성능이 안 움직이는** 패턴이 흔함.
- ETF는 **매매 금지**, 신호의 “날씨”로만 사용(QQQ/XLK/XLV + VIX + 10Y).

### (b) 위험/부작용
- 레짐 필터가 과도하면 기회 손실.
- 오버레이가 또 다른 과최적화 축이 될 수 있음(단순 규칙 유지).

### (c) 최소 실험(2~3개 variant)
**실험 정의(1): `exp_regime_overlay_v1`**
- Variant A: VIX > 20 이면 gross exposure를 **-30%**
- Variant B: QQQ < 50DMA 이면 gross exposure **-40%**
- Variant C: 10Y 20일 변화율 상위 구간이면(급등) “장기듀레이션 Tech” 가중치 축소, Healthcare 비중 상대 확대(단, 총 보유 8~14 유지)

**게이트(2):**
- 레짐 규칙이 연속으로 N일(예: 20일) 노출 0 근처를 만들면 FAIL(과도한 방어)
- 오버레이 적용 후 비용/턴오버가 증가하면 FAIL(방어가 리밸런스만 늘리는 경우)

**기대 관측치(3):**
- OOS mean보다 **OOS min / tail 구간**이 먼저 개선.
- 리밸런스 핀포인트에서 “급락 구간 손실 완화”가 관측됨.

**PASS 조건:**
- OOS min 개선(또는 worst_mdd 개선) + mean 손실이 제한적.

# 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래 트리를 **리포트에 자동으로 채우는 형태**로 만들고, 어디가 0/고정/역전되는지 찾는 방식으로 분해.

## A. Trigger(신호 발생) 문제
- [ ] 신호 발생률(hit rate): 일별/주별 “진입 신호 발생 건수”가 고정/0인지 확인
- [ ] 신호 분포: 스코어가 상위/하위로 벌어지는지(분산) vs 항상 비슷한지(죽은 피처)
- [ ] 지연/타임스탬프: 신호 생성 시각이 체결 가능 시각보다 앞서는지(PIT 위반)

## B. Apply(집행/리밸런스) 문제
- [ ] 목표 가중치→주문→체결이 **동일 값으로 반복**되는지(라운딩/최소주문/현금부족)
- [ ] 리밸런스가 너무 잦아 “항상 미세조정만” 하다 비용으로 상쇄되는지
- [ ] `rebalance_pinpoint`로 성능 차이가 나는 날짜의 **트레이드/코스트/가중치 변화**를 1:1 대조

## C. Exposure(노출) 문제
- [ ] gross/net 노출이 거의 상수인지(예: 항상 0.8 근처) → 알파가 노출에 묻힘
- [ ] 단일 종목/상관 그룹이 PnL을 지배하는지(기여도 상위 1~2개 종목 집중)
- [ ] 8~14 유지가 깨져 사실상 3~5개로 축소되는지(집중 리스크)

## D. Cost(비용) 문제
- [ ] 비용 전/후 PnL 갭이 말이 되는지(비용이 적용 안 되거나 과도 적용)
- [ ] 턴오버-성과 상관: 턴오버 높은 구간에서 성과가 하락하는지
- [ ] ADV 대비 주문 크기가 큰 날 손실이 커지는지(임팩트 필요 신호)

## E. Regime(시장 레짐) 문제
- [ ] QQQ/XLK/XLV 추세, VIX, 10Y 변화로 구간을 나누고 **구간별 성과표** 자동 생성
- [ ] “레짐별로는 좋지만 합치면 0”인지(상쇄) vs “모든 레짐에서 0”인지(알파 부재)
- [ ] Tech/Healthcare 상대강도(예: XLK/XLV 비율)의 방향성과 포지션이 일치하는지

---

## 즉시 실행 TOP5 요약(명령형)
1) **PIT/누수 센티널** 구현하고 lag/embargo/price-only 3-variant로 누수 여부를 먼저 확정하라.  
2) **비용/슬리피지/턴오버**를 순성과 기준으로 강제하고 5/15bp+임팩트 3-variant 민감도 게이트를 걸어라.  
3) **리밸런스 로그 스키마를 표준화**하고 핀포인트 도구가 실패하면 런 자체를 FAIL 처리하라(MDD 포함).  
4) **노출/집중 컨트롤러(8~14)**를 vol-target+cap+cash 게이트로 추가하고 OOS min/MDD 개선을 목표로 검증하라.  
5) **레짐 오버레이(ETF는 관측만)**를 VIX/QQQ추세/금리 규칙으로 단순하게 붙여 tail 개선 여부를 확인하라.
