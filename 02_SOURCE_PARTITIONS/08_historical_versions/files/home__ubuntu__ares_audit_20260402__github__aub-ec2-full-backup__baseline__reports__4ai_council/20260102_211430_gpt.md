## TOP5 우선순위 (24~48h) — “명령형 체크리스트”
(누수/과최적화/서바이버십/비용 미반영/운영 리스크 **우선**)

# 1) **리밸런스/실행 로그 무결성 복구 (운영 리스크 최우선)**
### (a) 왜 필요한지
- `aub_rebalance_pinpoint`가 **입력 파일을 못 찾고(JSON 파싱 실패)** 있어, “성능이 왜 안 움직였는지”를 **리밸런스 단위로 분해 불가**.
- `lane_hash/run_hash: None`, `worst_mdd: None` → 실험 재현/추적/리스크 산출이 깨진 상태(자동 루프에서 치명적).

### (b) 위험/부작용
- 로그 포맷 변경 시 기존 리포트/대시보드 파서 깨짐.
- “기록만 추가”해도 디스크/IO 증가(48h 루프에서 비용).

### (c) 최소 실험(동일 실험 안의 2~3 체크)
**[EXP-01] Rebalance Telemetry Patch**
- (체크1) 리밸런스 이벤트를 **단일 포맷(jsonl)** 로 강제 기록: `timestamp, symbol, target_w, prev_w, delta_w, fill_px, slippage_bps, fees, turnover, reason`.
- (체크2) `run_hash/lane_hash`를 **입력 데이터 해시 + 코드 커밋 + 설정 해시**로 생성해 결과물에 주입.
- (체크3) `worst_mdd`를 산출(최소 daily equity curve 기반)하여 champion JSON에 **항상 존재**하게 강제.

### (d) PASS 조건 (게이트)
- `aub_rebalance_pinpoint.py`가 **base/cand 모두**에서 리밸런스 로그를 읽고, “상위 turnover 구간/손익 기여도 Top-N”을 출력한다.
- 각 실험 산출물에 `run_hash/lane_hash/worst_mdd`가 **NULL 없이** 존재.
- 48h 루프 1회 실행에서 로그 누락률 0%, json 파싱 실패 0%.

### 48시간 자동 루프 형태
- (1) 실험 정의: EXP-01 적용 후 1회 full run
- (2) 게이트: 위 PASS 조건 자동 assert
- (3) 기대 관측치: “성능 변화”가 아니라 **원인분해 가능 상태**로 전환(리밸런스/턴오버/비용/슬리피지 기여가 보임)

# 2) **Degenerate folds 제거 (과최적화/검증 붕괴 우선 제거)**
현재 `degenerate_folds: [1,2,3,8]` → 폴드 일부가 거래 0이거나, 샘플 부족/분포 붕괴로 **OOS 통계가 허상**일 가능성 큼.

### (a) 왜 필요한지
- OOS mean이 좋아 보여도 폴드가 퇴화하면 “실제 강건성”이 없다.
- 자동 튜닝이 degenerate 폴드에서 우연히 맞춘 설정을 챔피언으로 올릴 위험(과최적화).

### (b) 위험/부작용
- 폴드 제약을 강화하면 통과 실험 수가 줄어 단기적으로 “개선 속도”가 느려질 수 있음.

### (c) 최소 실험
**[EXP-02] Fold Health Gate + Time-split 재정의**
- (체크1) 각 폴드에 대해 최소 조건을 강제:
  - 폴드당 거래 수 `>= N_min` (예: 50)
  - 폴드당 유효 리밸런스 수 `>= R_min`
  - 폴드 내 종목 수(8~14) 유지율 `>= S_min`
- (체크2) 폴드 생성 방식을 **시간 블록(rolling) + purge gap**으로 고정(누수 완화 포함).
- (체크3) 폴드별 성능 집계 시 **degenerate 폴드 즉시 FAIL**(평균 계산에 포함 금지).

### (d) PASS 조건
- `degenerate_folds`가 빈 배열.
- OOS mean뿐 아니라 `oos_min`이 일정 수준 이상으로 개선/안정:
  - 예: `oos_min >= 0` (또는 최소 -x% 이내)
- 폴드별 거래/리밸런스 통계 리포트가 자동 저장.

### 48시간 루프
- (1) 실험 정의: EXP-02 적용하여 기존 챔피언 설정 재평가(재런)
- (2) 게이트: degenerate 0 + 최소 통계 충족
- (3) 기대 관측치: “평균 수익”이 내려가더라도 **통계 신뢰도 상승**(분산/최저치가 정상화)

# 3) **비용(슬리피지/수수료/스프레드/임팩트) 강제 반영 (비용 미반영 점검)**
현재 리밸런스 로그 자체가 깨져 비용/턴오버를 pinpoint 못 하고 있고, 노출 최대 0.84 수준이면 리밸런싱/비용에 성과가 잠식될 수 있음.

### (a) 왜 필요한지
- Tech+Healthcare(8~14개) 집중은 회전이 높아질 수 있어 **슬리피지 민감**.
- 비용 모델 미반영 시 OOS가 “움직이지 않는 것”처럼 보이거나, 실거래에서 급격히 악화.

### (b) 위험/부작용
- 비용을 보수적으로 넣으면 백테스트 성능이 즉시 하락(하지만 이게 정상).
- 과도한 비용 페널티는 거래를 죽여 신호 검증을 방해 가능.

### (c) 최소 실험
**[EXP-03] Cost Model On + Turnover Budget Gate**
- (체크1) 거래비용을 최소 2항으로 분해해 반영:
  - 고정 수수료(커미션/fees)
  - 변동 비용(스프레드/슬리피지 bps = base_bps + k * sqrt(ADV 대비 주문비중))
- (체크2) 종목별 **ADV 기반** 주문 제한(impact 방지) + 주문 미충족 시 로깅.
- (체크3) 포트폴리오 **턴오버 상한**(일/리밸런스당) 걸고 초과 시 포지션 변경을 클립.

### (d) PASS 조건
- 비용 포함/미포함 성과가 모두 저장되고, 두 결과의 차이가 리포트에 명시.
- 비용 포함 후에도 OOS가 완전 붕괴하지 않을 것:
  - 예: `oos_mean_cost >= 0` 또는 baseline 대비 하락폭이 합리적 범위(턴오버와 상관으로 설명 가능)
- turnover/슬리피지 기여 Top10이 rebalance pinpoint에서 출력.

### 48시간 루프
- (1) 실험 정의: EXP-03으로 챔피언 재평가 + 비용 민감도 함께 산출
- (2) 게이트: turnover 상한 준수 + 비용 리포트 생성
- (3) 기대 관측치: “성능이 안 움직임”이 **비용/턴오버 때문인지** 즉시 분해 가능

# 4) **누수/서바이버십/룩어헤드 차단 게이트 (가장 흔한 원인)**
Tech/Healthcare는 지수 편입/퇴출, M&A, 상장폐지, 심볼 변경이 잦아 **서바이버십** 위험이 크고, 리밸런스 시점과 가격/재무 업데이트 시점이 엇갈리면 **룩어헤드**가 생김.

### (a) 왜 필요한지
- “OOS 평균은 괜찮은데 실전 성과가 정체/악화”의 최상위 원인이 누수/서바이버십인 경우가 많음.
- 자동 루프에서 한 번 섞이면 이후 실험 전체가 오염됨.

### (b) 위험/부작용
- 엄격한 as-of 정합성 적용 시 샘플 수 감소, 성능 하락 가능(정상).
- 데이터 소스/스냅샷 구축 비용 증가.

### (c) 최소 실험
**[EXP-04] Leak/Survivorship Gate (As-of + Universe 스냅샷)**
- (체크1) 모든 피처/라벨에 대해 `as_of_timestamp`를 강제하고, **리밸런스 시점 이전에 이용 가능했던 값만** 사용.
- (체크2) 유니버스를 “현재 구성”이 아니라, 각 시점의 **당시 생존 유니버스 스냅샷**으로 재구성(상폐/합병 포함).
- (체크3) 룩어헤드 스모크 테스트:
  - 가격을 `t+1`로 의도적으로 쉬프트하면 성능이 비정상 급등하는지 확인(급등하면 누수 의심).

### (d) PASS 조건
- as-of 위반(미래 데이터 참조) 0건(로그/어설션).
- 쉬프트 테스트에서 성능이 “비정상 급등”하지 않음(임계치 기반 FAIL).
- 유니버스 구성 변동 로그가 남고, 상폐/심볼 변경 이벤트가 추적 가능.

### 48시간 루프
- (1) 실험 정의: EXP-04 게이트를 항상-on으로 넣고 전 실험 공통 적용
- (2) 게이트: 위반 0, 쉬프트 테스트 정상
- (3) 기대 관측치: 성능이 내려가도 **신뢰 가능한 백테스트**로 정렬

# 5) **노출/레짐/헤지 적용의 “무효화(no-delta)” 원인 제거 (적용/노출 레벨 점검)**
이미 “No-Delta Diagnoser”가 돌아갔고, “성능이 안 움직임”은 보통 아래 중 하나:
- (트리거) 신호가 변해도 거래로 연결이 안 됨(클립/버짓/필터)
- (적용) 타깃이 계산돼도 리밸런스 엔진이 무시/스냅
- (노출) 헤지/현금/상한 때문에 노출이 눌려 알파가 안 드러남
- (비용) 비용이 알파를 상쇄
- (레짐) 시장 국면에서 신호가 꺼져 있음(특히 Tech/HC는 QQQ/XLV 레짐 민감)

### (a) 왜 필요한지
- 현재 `exposure_min/max: 0.0 / 0.8388` 이고, “0 노출 구간”이 길면 실험 간 차이가 다 지워짐(no-delta).
- 헤지/스케일 파라미터가 있어도 실제 적용이 클립되면 효과가 0.

### (b) 위험/부작용
- 노출을 억지로 키우면 drawdown/변동성 급상승.
- 레짐 게이트를 잘못 두면 거래가 사라져 또 degenerate 유사 상태.

### (c) 최소 실험
**[EXP-05] Delta Visibility Patch (Trigger→Apply→Exposure 분해 로그 + 레짐 관측지표)**
- (체크1) 리밸런스마다 아래를 **반드시** 기록:
  - raw_signal_strength(종목별)
  - post_filter_signal
  - target_w_pre_clip / target_w_post_clip
  - hedge_w (있는 경우)
  - final_exposure, cash
- (체크2) “무효화 원인 카운터”를 집계:
  - `filtered_out_count`, `clipped_count`, `turnover_blocked_count`, `min_trade_blocked_count`
- (체크3) **ETF는 매매 금지**, 관측지표로만 사용:
  - QQQ(Tech), XLV(Healthcare), IWM(리스크)로 레짐 태그를 붙여 성과/노출을 조건부로 리포트.

### (d) PASS 조건
- 실험 간 raw_signal은 변하지만 final_exposure가 동일한 상황을 자동 탐지:
  - “신호 변화 대비 노출 변화 상관 < 임계치”면 FAIL(무효화)
- 무효화 Top 원인(예: clip/turnover/cost)이 1~2개로 수렴하고, 해결 타깃이 명확해짐
- 레짐별(예: QQQ 추세/변동) 성과/노출 차이가 리포트로 분해됨

### 48시간 루프
- (1) 실험 정의: EXP-05 공통 로깅 + 레짐 태깅
- (2) 게이트: 무효화 탐지/원인 집계가 리포트에 존재
- (3) 기대 관측치: “안 움직임”이 **어느 단계에서 0이 되는지** 즉시 보임

## 성능이 안 움직일 때 “원인 분해 트리” (트리거/적용/노출/비용/레짐)
아래를 **순서대로** 자동 진단(위 EXP-01~05가 이 분해를 가능하게 만드는 패치임).

1) **Trigger(신호 생성)**
- 신호 분산이 줄었나? (cross-sectional std, 상위/하위 스코어 스프레드)
- 신호가 특정 섹터/몇 종목에만 몰리나? (8~14 내에서 concentration)
- 시그널이 레짐에서 항상 0/중립인가?

2) **Apply(리밸런스 엔진 적용)**
- target_w가 실제 주문으로 변환되나?
- min trade size / 거래단위 / 제한조건 때문에 대부분 무시되나?
- “post_clip == pre_clip”이 과도하게 반복되나?

3) **Exposure(실제 시장 노출)**
- 노출이 장기간 0(현금)인가?
- 상한(0.84) 근처에서 클립되며 실험 간 차이가 지워지나?
- 헤지가 알파를 상쇄하나? (헤지 전/후 PnL 분해)

4) **Cost(비용/슬리피지)**
- turnover 급증 구간에서 성과가 사라지나?
- 비용 포함/미포함 차이가 대부분을 설명하나?
- ADV 대비 주문 비중이 커서 임팩트가 과대인가?

5) **Regime(시장 국면)**
- QQQ/XLV 레짐 태그별로 알파가 한쪽에서만 나오나?
- 변동성 급등 국면에서만 깨지나?
- 레짐 필터가 너무 강해 거래가 사라지나(=degenerate 유사)?

## 24~48시간 실행 순서 (중요도 순, 그대로 실행)
1. **EXP-01** 로그/해시/MDD 무결성 패치 → pinpoint 도구가 “반드시” 돌게 만들기  
2. **EXP-02** degenerate fold 게이트 + time-split/purge → OOS 신뢰도 복구  
3. **EXP-03** 비용 모델 온 + turnover 예산 → 비용 미반영 제거  
4. **EXP-04** as-of/서바이버십/쉬프트 테스트 → 누수 차단  
5. **EXP-05** Trigger→Apply→Exposure 로깅 + 레짐 태그(ETF는 관측만) → “안 움직임” 분해 완료

(이 5개가 돌아가면, 이후에야 비로소 전략 파라미터(스케일/헤지/필터)를 만져도 “왜 좋아졌는지/왜 0인지”가 추적 가능해집니다.)
