## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — 명령형 체크리스트

### 1) **리밸런스/체결/비용 로그 파이프라인을 “ONE TRUTH”로 복구**
- **왜 필요한지**
  - 현재 `aub_rebalance_pinpoint`가 **리밸런스 로그를 못 읽음**(`--base-log` 없음, JSON 파싱 실패) → 비용/턴오버/체결지연/슬리피지로 성능이 “안 움직이는” 원인을 분해 불가.
  - `worst_mdd: None`, `lane_hash/run_hash: None`도 **리포팅 누락/스키마 불일치** 신호.
- **위험/부작용**
  - 로그 스키마를 바꾸면 과거 리포트/도구가 깨짐(회귀 리스크).
  - “기록만” 늘고 성능은 그대로일 수 있음(하지만 원인 규명에 필수).
- **최소 실험(아래 공통 실험 Exp# 재사용)**
  - Exp2(비용모델 민감도) + Exp3(리밸런스/노출 게이트) 적용에 필요한 로그를 먼저 통일.
  - Exp1(누수 점검)에서 “시그널 생성 시각 vs 체결 시각” 검증을 로그로 강제.
- **PASS 조건**
  - 모든 run에서 아래 파일이 **항상 생성/파싱 가능**:
    - `rebalance.jsonl`(또는 csv) + `fills.jsonl` + `costs.jsonl` + `positions_eod.csv`
  - 각 리밸런스 이벤트에 대해 최소 필드 존재:
    - `ts_decision, ts_submit, ts_fill, symbol, target_w, prev_w, fill_px, ref_px, est_cost, realized_cost`
  - `aub_rebalance_pinpoint.py`가 **base/cand 둘 다 성공적으로 로드**.

---

### 2) **데이터 누수(look-ahead) / 시간정렬 / 폴드 퇴화(degenerate_folds) 우선 차단**
- **왜 필요한지**
  - `degenerate_folds: [1,2,3,8]`은 **CV 분할/샘플 부족/레이블 누수/동일 구간 중복** 가능성을 강하게 시사.
  - OOS mean이 나와도 “진짜 엣지”인지 “시간여행”인지 판단 불가.
- **위험/부작용**
  - 누수 차단 후 성능 급락 가능(정상).
  - 폴드 재구성으로 과거 챔피언과 직접 비교가 어려워질 수 있음 → run_hash/lane_hash로 비교 가능하게 해야 함.
- **최소 실험**
  - Exp1(누수/시간정렬 강제) + Exp4(레짐 게이트)로 “특정 구간만 먹히는 가짜 엣지” 제거.
- **PASS 조건**
  - 모든 피처/레이블이 **결정시각 기준으로 최소 1바/1일 이상 lag**가 보장됨(정책으로 강제).
  - degenerate_folds가 **0** 또는(불가피 시) “퇴화 사유”가 리포트에 명시되고 해당 폴드가 스코어에서 제외/패널티 처리됨.
  - “라벨 시프트(+1) vs (+0)” 테스트에서 +0이 유의하게 좋으면 즉시 FAIL(누수 의심).

---

### 3) **비용/슬리피지/턴오버를 성능목표에 선반영(과최적화 방지)**
- **왜 필요한지**
  - 리밸런스 데이터를 못 읽는 상태에서 전략은 **턴오버로 수익을 착시**하기 쉽고, “성능이 안 움직임”이 사실 **비용에 다 깎인 결과**일 수 있음.
  - ETF 매매는 제외라도, 개별주(Tech/Healthcare)도 프리미엄/갭/뉴스로 슬리피지가 큼.
- **위험/부작용**
  - 비용모델이 과도하면 유망 전략을 과소평가.
  - 너무 보수적으로 잡으면 트레이드가 거의 안 나가 “노출 0” 상태로 퇴행 가능.
- **최소 실험**
  - Exp2(비용모델 민감도 스윕) + Exp3(턴오버/리밸런스 빈도 게이트).
- **PASS 조건**
  - 비용 3단(낙관/기준/보수)에서 **OOS 평균이 단조 붕괴하지 않음**(최소 기준/보수에서 생존).
  - `turnover`, `trade_count`, `avg_slippage_bp`가 리포트에 고정 출력되고, OOS 성능과 상관(착시 여부)이 관측됨.

---

### 4) **운영 리스크(노출/집중/거래불능) 게이트를 하드코딩**
- **왜 필요한지**
  - 현재 `exposure_max ~0.84`, `exposure_min 0` → “거의 현금 ↔ 급노출” 스위칭일 가능성. 이 패턴은 운영에서 가장 많이 깨짐(갭, 이벤트, 체결 실패 시 손익 급변).
- **위험/부작용**
  - 게이트가 과하면 수익 기회 차단.
  - 너무 많은 제약은 “아무것도 안 하는” 전략으로 수렴.
- **최소 실험**
  - Exp3(노출/포지션/리밸런스 게이트 A/B) + Exp5(유니버스/집중 제한).
- **PASS 조건**
  - 단일 종목 비중 상한, 섹터 편중 상한, 하루 거래 횟수/턴오버 상한을 걸었을 때 **OOS mean 유지 또는 소폭 하락(허용)** + `oos_min` 개선.
  - 최악 구간 `worst_mdd`가 **None이 아니라 계산되어 출력**(측정 불능 상태 제거).

---

### 5) **서바이버십/유니버스 변동을 축소한 “고정 8~14종목 Tech+Healthcare” 베이스라인 확정**
- **왜 필요한지**
  - 유니버스가 동적으로 바뀌면(상장폐지/편입/데이터 가용성) **서바이버십/데이터 가용성 편향**이 쉽게 섞임.
  - 48시간 자동 루프에서는 “유니버스 고정”이 재현성과 디버깅 속도를 올림.
- **위험/부작용**
  - 고정 유니버스는 기회 손실(중소형 성장주 등).
  - 특정 메가캡에 과적합 가능 → 집중 제한과 함께 가야 함.
- **최소 실험**
  - Exp5(고정 유니버스 + 분산/집중 페널티) + Exp4(레짐 필터를 지표로만 사용).
- **PASS 조건**
  - 고정 유니버스에서 폴드 퇴화 감소, 리밸런스 로그 안정화, 성능 변동 원인(레짐/비용/노출) 분해가 쉬워짐.
  - 종목 수가 8~14로 유지되고, 거래는 **개별주만** 발생(ETF는 지표만).

---

## 공통 “실행 가능한 Patch/실험” 5개만 정의 (48시간 자동 루프 형태)

아래 5개만 **실제로 돌리는 실험 슬롯**으로 고정하고, 위 TOP5 우선순위는 이 5개를 조합해 해결.

---

### Exp1) 누수/시간정렬 강제 패치
1) **실험 정의**
   - 모든 피처를 `t`에서 계산하되, 의사결정/체결은 `t+1`(또는 다음 바)로 강제.
   - “라벨/목표 수익”도 동일한 기준으로 재정렬(look-ahead 차단).
   - 폴드 생성 시 **시간 연속/중복 금지**(purged walk-forward 또는 embargo 적용).
2) **게이트**
   - degenerate_folds 발생 시 run FAIL 처리(또는 해당 폴드 제외 + 패널티 로그).
   - `feature_timestamp <= decision_timestamp` 위반 1건이라도 발견 시 즉시 FAIL.
3) **기대 관측치**
   - 성능 급락 가능(정상) + 대신 폴드 안정화.
   - `oos_min`이 더 현실적인 값으로 내려가거나, 변동성이 줄어듦.
   - “성능이 안 움직이는” 원인이 누수 제거로 명확해짐(진짜 엣지 여부 판별).

---

### Exp2) 비용/슬리피지 민감도 스윕(3단)
1) **실험 정의**
   - 동일 전략에 비용만 3단으로 적용:
     - Low / Base / High (예: 고정 수수료 + 슬리피지 bp + 갭 페널티)
   - 결과를 **같은 리포트에 나란히** 출력.
2) **게이트**
   - High 비용에서 성능이 완전히 붕괴하면(예: OOS mean < 0 또는 oos_min 급락) “턴오버 의존”으로 태그.
   - `turnover` 상위 분위(예: 90p) 초과 시 경고/FAIL(운영불가).
3) **기대 관측치**
   - 비용 민감도가 크면 “전략 개선”이 아니라 “거래 줄이기/리밸런스 제어”가 우선 과제임이 확정됨.

---

### Exp3) 리밸런스/노출 게이트 A/B (운영 리스크 제어)
1) **실험 정의**
   - A: 기존 로직 유지
   - B: 아래 제약을 하드 적용
     - 총 노출 상한(예: 0.7~0.8), 최소 노출(예: 0.1) 또는 “현금 전환 조건”을 명시
     - 일일 턴오버 상한
     - 단일 종목 비중 상한(예: 15~20%)
     - 리밸런스 빈도 제한(예: 주 2~3회 또는 신호 변화 임계치)
2) **게이트**
   - 체결 로그 누락 시 FAIL(Exp0로깅과 연동).
   - 제약 적용 후 거래가 0에 수렴하면 FAIL(“전략 비활성화”).
3) **기대 관측치**
   - OOS mean이 약간 내려가도 `oos_min`/MDD가 개선되면 운영 적합도 상승.
   - “성능이 안 움직임”이 사실상 **과도한 리밸런스 노이즈**였는지 판별 가능.

---

### Exp4) 레짐 관측지표(ETF는 매매 금지, 필터만)
1) **실험 정의**
   - 매매는 개별주만. 레짐 판단 지표로만 ETF/지수 사용(예: QQQ, XLV, SPY, IWM).
   - 레짐 플래그(예: risk-on/off, 헬스케어 방어 국면)를 만들어
     - 포지션 크기 스케일링(베타 축소/확대)
     - 신호 적용 중지(“no-trade zone”) 중 하나만 선택해 단순 적용
2) **게이트**
   - 레짐 플래그가 OOS에서 특정 기간에만 과도하게 작동하면(거의 항상 on/off) FAIL(과최적화 의심).
3) **기대 관측치**
   - `oos_min` 개선(극단 구간 방어).
   - 성능 정체 시 “레짐 미스매치” 여부를 빠르게 확인 가능.

---

### Exp5) 고정 유니버스(8~14) + 집중/분산 페널티
1) **실험 정의**
   - 유니버스를 고정(Tech+Healthcare 중심, 8~14개):
     - 예시(13): MSFT, AAPL, NVDA, AMD, GOOGL, AMZN, META, AVGO, ORCL, UNH, JNJ, LLY, ABBV
   - 섹터는 2개(Tech/Healthcare)로 제한, **ETF 매매 없음**.
   - 집중 페널티(단일 종목/상관군 과집중) 또는 간단한 리스크 패리티 스케일만 추가.
2) **게이트**
   - 종목 수가 8~14를 벗어나면 FAIL.
   - 특정 1~2개 종목에 성과가 과도하게 귀속(성과 기여도 상위 2종목 > 70% 등) 시 경고/FAIL(서바이버십/집중 리스크).
3) **기대 관측치**
   - 리밸런스/비용/노출의 원인 분해가 쉬워지고, 실험 간 비교가 안정화.
   - 성능이 안 움직일 때 “유니버스 변화”라는 변수를 제거.

---

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐) — 실행 지시서

### A) 트리거(신호가 생성되는가?)
- **신호 발생률을 강제 로깅**: `signal_nonzero_rate`, `avg_abs_signal`, `signal_flip_rate`
- **진단 규칙**
  - 신호가 거의 0 → 임계치/정규화/스케일링 오류 또는 데이터 결측으로 무효화
  - flip_rate 과다 → 노이즈 기반, 비용에 먹힘(Exp2/Exp3 우선)

### B) 적용(신호가 포지션으로 반영되는가?)
- **결정→주문→체결 체인 로깅**: `decision_ts`, `submit_ts`, `fill_ts`, `reject_reason`
- **진단 규칙**
  - submit은 있는데 fill이 없음 → 유동성/가격제한/데이터 스키마 문제
  - fill은 있는데 포지션이 안 변함 → 포지션 병합/라운딩/클램프 버그(상한이 0으로 걸렸을 가능성)

### C) 노출(리스크가 실제로 실렸는가?)
- **노출 분해 지표**: `gross_exposure`, `net_exposure`, `single_name_max_w`, `HHI(집중도)`
- **진단 규칙**
  - 노출이 0~0.1에 고착 → 게이트가 너무 강함 또는 신호 약함
  - 노출이 0↔0.8로 점프 → 리밸런스 스케줄/레짐 플래그의 스위치형 동작(Exp3/Exp4로 완화)

### D) 비용(수익이 비용에 상쇄되는가?)
- **비용 기여도 로깅**: `gross_pnl`, `cost_pnl`, `net_pnl`, `slippage_bp`, `turnover`
- **진단 규칙**
  - gross는 좋은데 net이 평평 → 비용/슬리피지 문제(Exp2로 확인 후 Exp3로 억제)
  - gross 자체가 평평 → 신호 엣지/레짐 미스(Exp1/Exp4로 확인)

### E) 레짐(먹히는 구간이 사라졌는가?)
- **기간 분할 리포트**: 월별/분기별 OOS, 변동성 구간, 금리 쇼크 구간(지표로만)
- **진단 규칙**
  - 특정 국면에서만 성과 → 레짐 필터가 필요(Exp4), 또는 과최적화(Exp1/Exp2로 검증)

## 48시간 운영 순서(자동 루프에 그대로 넣기)
1) **로그/스키마 고정 → 도구가 읽게 만들기** (TOP1 즉시)
2) **Exp1 실행(누수/폴드 퇴화 제거) → 실패 시 다음 실험 중단**
3) **Exp2 실행(비용 3단)으로 “턴오버 착시” 여부 확정**
4) **Exp3 실행(노출/리밸런스 게이트 A/B)로 운영가능 영역 찾기**
5) **Exp4/Exp5는 마지막에 한 번씩만**(레짐/유니버스 변수를 고정해 원인 분해 완성)

이 구성으로 “실험 슬롯 5개”만 고정해도, 누수/과최적화/서바이버십/비용 미반영/운영 리스크를 우선순위대로 48시간 안에 압축 점검할 수 있음.
