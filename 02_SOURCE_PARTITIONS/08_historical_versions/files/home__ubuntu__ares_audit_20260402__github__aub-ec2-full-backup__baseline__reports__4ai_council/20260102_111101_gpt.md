## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — **명령형 체크리스트**
(누수/과최적화/서바이버십/비용 미반영/운영 리스크 우선)

1) **리밸런스/지표 로깅 파이프라인 복구 + “ONE TRUTH” 지표 버전 고정**
- 현재 `aub_rebalance_pinpoint`가 `--base-log` 경로 오류 + CSV/JSON 파싱 실패로 **원인추적 불능** 상태.
- 동시에 “Champion OOS Mean 2.6276” vs “Current Champion oos_mean 1.8815”로 **지표 정의/버전 불일치 가능성**이 큼.

2) **누수/서바이버십/룩어헤드 1차 차단(데이터 timestamp / PIT / purged CV)**
- Tech/Healthcare 8~14 종목은 **표본이 작아** 작은 누수도 성능이 과대평가되기 쉬움.

3) **거래비용/슬리피지/회전율 비용을 “학습/선정 단계”에 강제 반영**
- 비용 미반영은 OOS가 “안 움직이거나” 실거래에서 급락하는 최상위 원인.
- 현재 exposure 0.47~0.84면 리밸런스/헤지/현금비중 로직이 성능에 큰 영향을 주는데, 비용까지 얹으면 랭킹이 바뀔 수 있음.

4) **리스크/운영 리스크 계측(최소 MDD 포함) + 노출/섹터/포지션수(8~14) 가드레일 고정**
- `worst_mdd: None`은 운영 리스크 신호(계산 누락/로그 누락/런 실패 은폐).
- “노출이 흔들리는데 성능이 정체”는 보통 **리스크 예산이 불안정**하거나 **게이트가 성능 대신 노출만 맞추는** 현상으로 발생.

5) **레짐(시장 국면) 분해 리포트 자동화(Tech/HC 중심, ETF는 관측지표만)**
- 성능이 안 움직일 때는 대개 “레짐별로 +/−가 상쇄”되고 있음.
- ETF(예: QQQ/XLV)는 **매매 금지**, 다만 국면/베타/상관 관측 지표로만 사용.

# 실행 가능한 Patch/실험(총 4개만) — 48시간 자동 루프 형태
아래 **E1~E4**만 돌리면 TOP5 전체를 커버하도록 설계(케이스 폭발 방지).  
각 TOP5 제안은 “최소 실험 2~3개” 요구를 **E1~E4 조합**으로 충족.

---

## E1) **Rebalance 로그/지표 버전 고정 Patch**
### (1) 실험 정의
- 리밸런스 이벤트를 **단일 스키마(JSONL)** 로 강제 기록:
  - timestamp, universe(as-of), holdings(before/after), target weights, fills(가정 체결가), turnover, estimated_cost, realized_cost(있다면), exposure, cash, hedge(if any)
- `aub_rebalance_pinpoint` 입력을 `--base-log` “파일 경로”로만 받게 검증(문자열 `--base-log` 자체를 경로로 쓰는 실수 차단).
- OOS 지표 산출에 **metric_version**을 강제 주입(예: `oos_mean_v3`), 리포트에 함께 출력.

### (2) 게이트 (PASS 조건)
- pinpoint 도구가 **base/cand 모두**에서 리밸런스 로그를 정상 로드하고,
- 최근 챔피언 1회 재현(run)에서:
  - 리밸런스 건수/턴오버/노출(min/max)이 기존 리포트와 **±1% 이내**로 재현
  - `worst_mdd`가 **None이 아니어야 함**

### (3) 기대 관측치
- “성능 정체” 원인이 **신호 문제가 아니라 리밸런스/노출/비용/게이트 문제**인지 즉시 분리 가능.
- OOS Mean 불일치(2.62 vs 1.88)가 **지표 버전/집계 구간 차이**인지 드러남.

---

## E2) **누수/서바이버십/룩어헤드 차단 Patch (PIT + Purged/Embargo CV)**
### (1) 실험 정의
- 모든 피처/라벨에 “as-of timestamp”를 강제:
  - 재무/가이던스/임상/규제 이벤트 등은 **공시 시점 이후**에만 사용
- 유니버스 구성에 서바이버십 차단:
  - delisted 포함(가능하면), 거래정지/합병/상폐 처리 로직 명시
- CV를 **Purged K-Fold + Embargo**로 변경(타임시리즈 누수 차단)

### (2) 게이트 (PASS 조건)
- 누수 진단 체크리스트를 자동 통과:
  - 피처 최대 timestamp ≤ 예측 시점 timestamp
  - fold 간 label overlap(인접 구간) 제거(embargo 적용 로그로 증명)
- OOS 성능이 단기적으로 하락하더라도:
  - fold 간 분산(표준편차)이 **감소**하거나,
  - 최악 구간(oos_min)이 **개선/안정**되면 PASS(“진짜 성능”으로 수렴)

### (3) 기대 관측치
- 과최적화/룩어헤드로 부풀려진 성능이면 **OOS mean은 내려가도 oos_min이 올라가거나** 변동이 줄어듦.
- 반대로 진짜 알파면 성능 유지 + 안정성 상승.

---

## E3) **비용/회전율 내재화 Patch (거래비용 + Turnover Cap)**
### (1) 실험 정의
- 비용 모델을 최소 2요소로 고정:
  - (a) 스프레드/슬리피지: `k * ATR` 또는 `bps_by_liquidity`
  - (b) 고정 수수료/세금(0으로 두더라도 항목은 유지)
- 리밸런스에 turnover cap 적용(예: 일별/리밸런스당 총 turnover 상한)
- 목적함수/선정 기준에 **cost-adjusted OOS**를 기본으로 사용

### (2) 게이트 (PASS 조건)
- 비용 반영 후에도:
  - cost-adjusted OOS mean이 기존 대비 **-X% 이내**(급락 방지, 예: -15% 이내) 또는
  - turnover가 **의미 있게 감소**(예: -25% 이상)하면서 oos_min이 악화되지 않으면 PASS
- “비용 0 vs 비용>0” 비교에서 성능 차이가 비정상적으로 크면(=과도한 회전 알파) **FAIL로 간주하고 원인추적**

### (3) 기대 관측치
- 성능이 “안 움직이는” 이유가 사실상 **비용이 다 먹는 구조**인지 즉시 판별.
- 회전율이 줄면 OOS가 더 안정적으로 움직이는 경향.

---

## E4) **리스크/노출/포지션 가드레일 Patch (8~14 종목, Tech+HC 중심)**
### (1) 실험 정의
- 포지션 수를 8~14로 하드 고정(미국주식 only, ETF 매매 제외)
- 섹터 편중 가드(Tech+Healthcare 중심이되 단일 종목/단일 섹터 상한)
- 노출 타겟팅(예: gross/net 범위) + MDD/드로우다운 계산을 리포트/게이트에 편입
- (옵션) 헤지(지수 ETF 매매는 금지 조건이라면) **헤지는 “현금 비중/리스크 축소”로 대체**하고, ETF는 관측지표(베타 추정)로만 사용

### (2) 게이트 (PASS 조건)
- `worst_mdd` 산출 및 리포트 상시 출력 + 임계치 경보:
  - worst_mdd가 과거 챔피언 대비 **악화 제한**(예: +20%p 이상 악화 금지)
- exposure_min/max가 목표 범위 내에서 안정(예: min ≥ 0.6, max ≤ 0.9 같은 내부 기준; 현재 0.47~0.84는 “낮은 구간 원인” 후보)
- 포지션 수 8~14 유지율 100%

### (3) 기대 관측치
- 성능 정체가 “알파 부족”이 아니라 **노출/리스크 예산이 흔들려 상쇄**되는 문제였는지 분리.
- oos_min 개선(최악 구간 방어) 가능.

# TOP5 제안별: 왜 필요한지 / 위험 / 적용 실험(2~3개) / PASS
(각 항목은 **E1~E4 조합**만 사용)

## 1) 로깅/지표 버전 고정
- (a) 필요: 현재 pinpoint가 깨져 **원인분해 불가**, OOS mean 불일치로 **의사결정 기준이 흔들림**
- (b) 위험: 로깅 추가로 런타임/디스크 증가, 기존 리포트와 수치가 달라 “성능 하락처럼 보이는 착시”
- (c) 최소 실험: **E1 + E4**
- (d) PASS: pinpoint 정상동작 + worst_mdd 산출 + OOS 지표 버전 불일치 해소(리포트에 version 명시)

## 2) 누수/서바이버십 차단
- (a) 필요: 소수 종목(8~14) + Tech/HC 이벤트성 데이터는 누수에 매우 취약
- (b) 위험: 단기 성능 하락(“진짜 성능”으로 내려앉는 과정), 데이터 소스 제약으로 유니버스 축소
- (c) 최소 실험: **E2 + E1**
- (d) PASS: 누수 체크 0건 + oos_min 안정화(또는 fold 분산 감소)

## 3) 비용/회전율 반영
- (a) 필요: 비용 미반영은 OOS 정체/실전 붕괴 1순위, 특히 리밸런스 많은 전략에서 치명적
- (b) 위험: 비용 모델 과대추정 시 “과보수적”으로 알파를 죽임, turnover cap이 신호 반영을 제한
- (c) 최소 실험: **E3 + E1**
- (d) PASS: cost-adjusted 기준에서 급락 방지 + turnover 감소 + oos_min 비악화

## 4) 리스크/노출/포지션 가드레일
- (a) 필요: worst_mdd 누락은 운영 리스크, exposure가 넓게 흔들리면 성능이 국면마다 상쇄됨
- (b) 위험: 가드레일이 과하면 수익 기회 제한(과규제), 특정 장세에서 언더퍼폼 고착
- (c) 최소 실험: **E4 + E1 + E3**
- (d) PASS: worst_mdd 산출/관리 + 포지션수 준수 + 노출 안정 + 비용 반영 후에도 oos_min 유지

## 5) 레짐 분해 자동화(ETF는 관측만)
- (a) 필요: “성능이 안 움직임”은 레짐별 +/− 상쇄가 가장 흔함. Tech/HC는 금리/리스크온오프에 민감
- (b) 위험: 레짐 정의를 늘리면 과최적화(분할 과다)로 이어질 수 있음
- (c) 최소 실험: **E4 + E2**
- (d) PASS: 레짐별 성과표에서 “어느 구간이 발목 잡는지”가 1회 루프로 특정되고, 그 구간에서 누수/비용/노출 중 최소 1개 원인이 수치로 드러남

# 성능이 안 움직일 때: 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래 순서대로 “상위에서 하위로” 깎아내리면 48시간 내 병목이 드러남(질문 없이 실행 가능).

## A. 트리거(신호 발생) 문제
- **체크**: 예측/스코어 분포가 접히는지(분산↓, 상위-하위 격차↓), 신호 업데이트 빈도 저하
- **관측 지표**: 일별 cross-sectional score std, top-bottom spread, 신호 변경률(%)
- **대표 원인**: 피처 timestamp 정렬 실패(미래값 제거 후 신호가 약해짐), 결측 대체가 신호를 평탄화

## B. 적용(리밸런스/제약/게이트) 문제
- **체크**: “원하는 포트폴리오”와 “실행된 포트폴리오”의 괴리
- **관측 지표**: target vs post-trade weight L1 distance, 제약 위반으로 인한 clip 비율, 체결 가정 영향
- **즉시 조치**: E1로 리밸런스 로그를 복구하고 괴리 원인을 수치로 고정

## C. 노출(베타/섹터/현금/헤지) 문제
- **체크**: 성과가 베타/현금비중 변화에 의해 상쇄되는지
- **관측 지표**: exposure time-series, sector exposure(Tech/HC 내 편중), cash ratio, (관측용) QQQ/XLV 대비 회귀 베타
- **대표 원인**: 특정 기간에 exposure_min(현재 0.47)이 낮아져 “기회 손실”, 혹은 반대로 노출 과다로 MDD 확대

## D. 비용(거래비용/회전율) 문제
- **체크**: gross 성과는 있는데 net에서 죽는지
- **관측 지표**: gross vs net 차이, turnover, 비용/수익 비율(cost / gross pnl)
- **즉시 조치**: E3로 비용을 목적함수에 내재화 + turnover cap

## E. 레짐(국면) 문제
- **체크**: 레짐별로 성과 부호가 바뀌어 평균이 0으로 수렴하는지
- **권장 레짐 분해(과다 분할 금지)**:
  - (1) 금리상승/하락(예: 10Y 변화 방향)
  - (2) 변동성 상/하(VIX 구간)
  - (3) 성장주 우위/열위(관측용 QQQ vs XLV 상대강도)
- **관측 지표**: 레짐별 OOS mean/min, 레짐 전환 직후 손익, 레짐별 turnover 변화

## 24~48시간 실행 순서(루프에 그대로 넣기)
1) **E1 먼저 실행** → 리밸런스/지표/리스크 로그를 “신뢰 가능한 ONE TRUTH”로 고정  
2) **E2 실행** → 누수/서바이버십 제거 후 성능/안정성 변화를 관측  
3) **E3 실행** → 비용/회전율로 OOS 정체의 진짜 원인을 확인  
4) **E4 실행** → 노출/리스크 가드레일로 oos_min과 MDD를 안정화  

이 4개만으로, “성능이 안 움직이는” 상태를 **트리거/적용/노출/비용/레짐** 중 어디에서 막히는지 2일 내에 숫자로 고정할 수 있음.
