## TOP5 우선순위 제안 (코드/아키텍처/전략)

### 1) (누수 최우선) “시간 정합성/누수 차단” 하드닝
**(a) 왜 필요한지**
- 현재 champion 대비 candidate 개선폭이 크지 않음(락박스 평균 1.3295 → 1.3388). 이 구간에서 가장 흔한 함정이 **미세 누수/시간정렬 오류**로 얻은 “가짜 개선”입니다.
- 특히 Tech/Healthcare는 이벤트(실적, FDA, M&A) 영향이 커서 **데이터 타임스탬프** 한 틱만 어긋나도 성능이 인위적으로 올라갑니다.

**(b) 위험/부작용**
- 누수 방지 조치 후 성능이 떨어질 수 있음(기존 개선분이 누수 기반이었을 가능성).
- 학습/검증 분리가 강화되면서 분산이 커져 “PASS”가 더 어려워질 수 있음.

**(c) 최소 실험(2~3개) — 단, 1개 실험군(E1) 안에서 변형 토글로 처리**
- **E1-A: Feature/Label time-shift 감도 테스트**  
  - 모든 feature를 **+1 bar 지연**(t-1만 사용)시켜 성능 급락 여부 확인.
- **E1-B: Purged/Embargo CV (purge window + embargo)**  
  - 이벤트 근처 정보 누수 차단. (특히 실적/급등락 구간)
- **E1-C: “미래 참조” 가능 컬럼 블랙리스트 자동탐지**  
  - 컬럼 생성 시점/집계창 기반으로 미래 포함 가능성 있는 피처를 규칙으로 제거(rolling window right-closed 강제 등).

**(d) PASS 조건**
- (필수) **락박스 mean ≥ champion 락박스 mean(1.3295) - 0.01** 범위 내 유지하면서  
- (필수) **worst_mdd ≤ -0.0902355776** 보다 악화 금지(= 더 나빠지면 FAIL)  
- (강한 PASS) E1-A에서 성능이 “0에 수렴”하진 않되, **이상한 과도한 붕괴/급등 패턴이 없어야** 함(누수 의심 제거).

**48시간 자동 루프 형태**
- (1) 실험 정의: `E1_leakage_hardening` (A/B/C 토글)
- (2) 게이트: lockbox mean, worst_mdd, fold14_mdd 유지 + 변형간 성능 일관성
- (3) 기대 관측치: “개선폭은 줄어도” 성능이 **안정화**되고, 후보 간 변동이 감소

### 2) (서바이버십) “Point-in-time Universe + Delist/CorpAction” 정합성 보강
**(a) 왜 필요한지**
- 미국 개별주 8~14 종목 집중 포트는 **표본 수가 작아 서바이버십 편향**의 충격이 큼.
- Tech/Healthcare는 상장폐지/인수합병/티커변경이 빈번 → 과거 데이터가 “승자만 남는” 형태가 되면 락박스가 부풀려집니다.

**(b) 위험/부작용**
- 진짜로 “견고했던” 성능이 서바이버십 제거로 낮아질 수 있음(정상).
- 데이터 소스/매핑이 복잡해지면 운영 리스크(티커 매핑 오류)가 증가.

**(c) 최소 실험(2~3개) — 단일 실험군(E2) 안에서 옵션 비교**
- **E2-A: Point-in-time tradable universe 강제**  
  - 각 일자에 “당시 거래 가능(상장 상태)”만 포함.  
- **E2-B: Delist 리턴/Corp action 처리 검증 스위트**  
  - split/dividend/merger/delist 케이스를 리플레이 테스트(가격/수익률 연속성).
- **E2-C: “룩백 생존 필터” 제거/고정**  
  - “최근 N년 생존” 같은 필터가 있으면 제거하거나 당시 시점 기준으로만 판단.

**(d) PASS 조건**
- (필수) **락박스 mean ≥ champion-0.015** (서바이버십 제거로 소폭 하락 허용)  
- (필수) worst_mdd 악화 금지  
- (강한 PASS) “상장폐지/이벤트 구간” 포함 폴드에서 성능 붕괴가 줄어듦(꼬리 리스크 감소)

**48시간 자동 루프**
- (1) 실험 정의: `E2_pit_universe_corpaction`
- (2) 게이트: 데이터 무결성(누락/중복/급격한 가격 점프) + 성능(락박스/최악 MDD)
- (3) 기대 관측치: 평균은 비슷하거나 약간 하락하더라도 **최악 케이스(worst_mdd) 안정화**

### 3) (비용 미반영) “거래비용/슬리피지/턴오버 패널티”를 락박스 기준으로 내재화
**(a) 왜 필요한지**
- 8~14 종목 집중 + Tech/Healthcare 변동성 → 리밸런싱이 잦으면 **백테스트 알파가 비용으로 소멸**하기 쉽습니다.
- 비용을 뒤에서 빼는 게 아니라, **신호/포지션 생성 단계에서 비용을 의사결정에 반영**해야 과최적화가 줄어듭니다.

**(b) 위험/부작용**
- 단기 성능(평균 수익)이 감소할 수 있음.
- 비용모델이 과보수면 트레이드가 거의 안 나가 신호가 “멈춘 것처럼” 보일 수 있음.

**(c) 최소 실험(2~3개) — 단일 실험군(E3) 내 모델 비교**
- **E3-A: 고정 비용 + 스프레드(보수적) 2-레벨**  
  - low/high 비용 시나리오를 동시에 기록(민감도).
- **E3-B: Turnover penalty를 목적함수/스코어에 직접 삽입**  
  - 예: score = alpha - λ * turnover (λ 2~3개 그리드만)
- **E3-C: 리밸런싱 게이트(최소 변화 임계값, min trade size)**  
  - 작은 변동은 거래하지 않도록 “no-trade band” 적용.

**(d) PASS 조건**
- (필수) **high-cost 시나리오에서도 lockbox mean이 champion 대비 -0.02 이내**  
- (필수) turnover(또는 거래횟수)가 의미 있게 감소(예: -20% 이상)  
- (강한 PASS) worst_mdd 개선 또는 동일, 그리고 성능 분산 감소

**48시간 자동 루프**
- (1) 실험 정의: `E3_cost_turnover_integrated`
- (2) 게이트: (고비용)락박스 성능 + turnover 감소 + 주문수(운영가능성)
- (3) 기대 관측치: 평균 수익은 조금 줄어도 **실전 가능성이 증가**하고 락박스 안정성↑

### 4) (과최적화/노출) “노출 제약(섹터/단일종목/베타/변동성) + 8~14 종목 강제” 오버레이
**(a) 왜 필요한지**
- 종목 수가 적을수록 성능이 “운 좋게 맞춘 특정 종목”에 종속되기 쉽습니다(서바이버십/과최적화 확대).
- Tech/Healthcare 중심이라도 **단일 종목/서브산업(반도체/바이오) 쏠림**이 커지면 최악 MDD가 튑니다.

**(b) 위험/부작용**
- 알파를 제한할 수 있음(좋은 종목에 더 못 실음).
- 제약이 과하면 포트가 벤치마크(예: QQQ/XLV 관측지표)와 지나치게 비슷해질 수 있음.

**(c) 최소 실험(2~3개) — 단일 실험군(E4) 내 제약 강도만 2~3단**
- **E4-A: 포지션 수 8~14 강제 + 상위 K만 매수(또는 롱/현금)**  
- **E4-B: 단일 종목 최대비중(예: 12~15%) + 섹터/산업 상한**  
- **E4-C: 포트 베타/변동성 타겟팅(간단형)**  
  - 예: 20D realized vol 타겟, 또는 SPY beta 상한(ETF는 “지표/헤지 계산용”으로만)

**(d) PASS 조건**
- (필수) worst_mdd가 악화되지 않을 것(= -0.0902보다 더 나빠지면 FAIL)  
- (필수) 포지션 수가 규칙(8~14) 유지 + 단일종목 쏠림 완화(최대비중 하락)  
- (강한 PASS) lockbox_mean 유지(±0.01~0.015)하면서 drawdown 꼬리 축소

**48시간 자동 루프**
- (1) 실험 정의: `E4_exposure_overlay_8to14`
- (2) 게이트: 제약 충족 여부(항상) + 성능(락박스/최악 MDD)
- (3) 기대 관측치: 평균 수익 큰 변화 없이 **최악 손실/변동성 감소**

### 5) (레짐/적용) “레짐 감지 → 신호 적용 강도 조절(게이팅)”으로 락박스 정체 타파
**(a) 왜 필요한지**
- 성능이 안 움직이는 흔한 이유는 “신호 자체가 나쁜 게 아니라, **적용되는 구간이 섞여** 평균이 상쇄”되기 때문입니다.
- Tech/Healthcare는 금리/유동성/리스크온오프 레짐에 따라 동일 신호의 기대값이 달라짐.

**(b) 위험/부작용**
- 레짐 분류 자체가 과최적화될 수 있음(특히 피처가 많으면).
- 게이팅이 잦으면 포지션 공백/급격한 전환이 생겨 비용 증가 가능.

**(c) 최소 실험(2~3개) — 단일 실험군(E5) 내 “단순 레짐”만**
- **E5-A: 단일 레짐 지표 1개로만 게이트(단순/견고)**  
  - 예: VIX 수준/기울기, 금리(10Y) 변화율, SPY 200D 추세(ETF는 “지표”로만)
- **E5-B: 레짐별 리스크 스케일링(포지션 사이즈만 조절)**  
  - 신호는 동일, 레짐이 나쁘면 노출 0.5x/0x.
- **E5-C: 레짐별 리밸런싱 빈도 조절**  
  - 변동성 레짐에서만 리밸런싱 간격 확대(비용 절감).

**(d) PASS 조건**
- (필수) 레짐별로 성능이 “방향성 있게” 달라져야 함(관측 가능한 분리)  
- (필수) lockbox_mean 개선(>= champion +0.005) 또는 worst_mdd 개선 중 1개 이상  
- (강한 PASS) 개선이 tuning이 아니라 **lockbox에서** 재현

**48시간 자동 루프**
- (1) 실험 정의: `E5_regime_gate_simple`
- (2) 게이트: 레짐 분리의 재현성(폴드 간) + 락박스 성능 개선
- (3) 기대 관측치: 평균은 소폭이라도 **락박스에서만큼은 개선** 또는 최악 MDD 감소

# 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
다음은 **원인 규명용 로그/진단을 “추가 질문 없이” 바로 넣을 수 있는 분해 체크리스트**입니다.

## A) 트리거(신호 발생) 문제
- **신호 분포 드리프트**: 예측/스코어의 평균, 표준편차, 상/하위 1% 클립 비율을 날짜별로 저장
- **신호 상관 붕괴**: 과거 60D IC/RankIC가 0 근처로 수렴하는지 폴드별 기록
- **피처 고장 탐지**: 결측률, 0-분산 컬럼, 리샘플링 후 계단형 값 증가 여부(특히 기업행동 후) 알람

## B) 적용(포지션 생성/리밸런싱) 문제
- **거래가 실제로 발생하는지**: day별 주문 수, 체결(가정) 수, no-trade band로 막힌 비율
- **제약이 알파를 상쇄하는지**: 제약 없는 목표 포트 vs 제약 적용 후 포트의 cosine similarity/overlap 기록
- **리밸런싱 타이밍 문제**: 신호 생성 시각과 거래 시각(다음날 오픈/클로즈)이 일관적인지 점검

## C) 노출(집중/베타/섹터) 문제
- **단일종목 기여도 분해**: PnL 기여 상위 1~2개가 전체의 몇 %인지(서바이버십/과최적화 힌트)
- **베타/섹터 노출 모니터**: SPY/QQQ/XLV(ETF는 관측지표)로 rolling beta, 섹터 비중 추적
- **테일 이벤트 민감도**: 상위 변동성 5% 구간에서 성능이 무너지는지 별도 집계

## D) 비용(슬리피지/스프레드/임팩트) 문제
- **알파 대비 비용 비율**: gross PnL vs cost PnL을 폴드/락박스에서 분해
- **턴오버-성과 곡선**: turnover decile별 성과를 내서 “많이 돌릴수록 손해”인지 확인
- **비용 민감도**: low/high cost에서 샤프/락박스 mean이 급변하면 실전 취약

## E) 레짐(시장 환경) 문제
- **레짐별 성과 테이블**: (예: VIX high/low, 금리 상승/하락, SPY 추세 상/하) 별 성과를 고정 포맷으로 저장
- **레짐 전환 시점 손실 집중**: 전환 전후 ±10일 PnL 누적을 기록(게이팅 필요성 판단)
- **레짐 분류 안정성**: 분류 지표가 너무 자주 왕복하면(토글 빈번) 오버트레이드 유발

## 바로 실행(현재 커맨드 흐름 유지)
아래 3개 커맨드 실행 후 생성되는 리포트/레지스트리에 **E1~E5를 후보로 등록**하는 형태로 맞추면 됩니다.

```bash
python3 experiment_system/tools/aub_autopilot.py --registry experiment_system/config/module_registry.yaml --run --select-best
python3 experiment_system/tools/system_autopilot.py --spec experiment_system/config/system_candidates.yaml --run
python3 experiment_system/tools/aub_next_fix.py --registry experiment_system/config/module_registry.yaml --output baseline/reports/next_fix.md
```

- `next_fix.md`에 위 **E1~E5 체크리스트를 “게이트/관측치 템플릿”**으로 자동 삽입되게 패치(운영 리스크↓, 반복성↑)하는 것이 48시간 내 가장 효율적인 진행입니다.
