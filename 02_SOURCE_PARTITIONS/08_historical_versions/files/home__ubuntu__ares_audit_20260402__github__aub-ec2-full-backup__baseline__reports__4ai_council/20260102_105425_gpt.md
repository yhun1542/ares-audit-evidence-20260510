또한 **실험 수 케이스 폭발 방지**를 위해, **유니크 실험은 5개(E1~E5)만** 정의하고 TOP5 제안에서 **재사용**합니다. (각 제안당 2~3개 실험을 “참조”하지만, 전체 유니크 실험 수는 5개 유지)

## TOP1) 데이터/로그 무결성 패치 (리밸런스 로그 + 지표 산출 누락)
현재 징후:
- `aub_rebalance_pinpoint`가 **base-log 파일/포맷 문제로 실패** (`--base-log`가 literal로 들어감, JSON 파싱 실패)
- `worst_mdd: None` → **핵심 리스크 지표 계산/저장 누락 가능**
- Champion OOS mean이 1.88 vs diagnoser 2.63으로 **지표 출처/버전 불일치 가능**

### (a) 왜 필요한지
- **성능이 “안 움직이는” 가장 흔한 원인**이 전략이 아니라 *평가/로그 파이프라인 고장*임.
- 리밸런스/턴오버/슬리피지/드로우다운이 안 잡히면 **누수·과최적화·비용 미반영을 영원히 못 잡음**.

### (b) 위험/부작용
- 로그 포맷 변경이 과거 리포트/도구와 호환성 깨뜨릴 수 있음.
- “지표 재산출”로 인해 단기적으로 champion 성능 수치가 변동(정정)될 수 있음(필수적인 통증).

### (c) 최소 실험(2~3개)  → **E1, E3 참조**
- **E1 (필수)**: 리밸런스/거래 로그 아티팩트 표준화 + worst_mdd 산출 강제
- **E3 (연동)**: 비용/턴오버 스트레스 테스트가 로그에 의해 막히는지 함께 확인

### (d) PASS 조건
- `aub_rebalance_pinpoint.py`가 **base/cand 모두**에서 리밸런스 데이터를 읽고,
  - (i) 거래수/턴오버/평균 보유기간/슬리피지 적용 결과를 출력
  - (ii) `worst_mdd`가 None이 아닌 값으로 기록
- 동일 run_hash에 대해 `oos_mean`이 **도구 간 ±1~2% 이내**로 일치(오차 원인 추적 가능 상태)

## TOP2) 누수(lookahead)/서바이버십/폴드 퇴화 “우선 차단”
### (a) 왜 필요한지
- Tech+Healthcare 8~14종목은 표본이 작아서 **누수/서바이버십이 있으면 OOS가 ‘안 움직이거나’ 이상하게 안정적으로 보이는 현상**이 자주 발생.
- “degenerate_folds: []”는 좋은 신호지만, **label/feature 정렬(시점) 오류는 별개 문제**.

### (b) 위험/부작용
- 누수/서바이버십이 실제로 있었다면 성능이 급락할 수 있음(그러나 그게 정상).
- 데이터 소스 변경(상장폐지 포함 등)은 백테스트 일관성 깨짐 → 기준선 재설정 필요.

### (c) 최소 실험(2~3개) → **E2, E5 참조**
- **E2 (필수)**: “시점 쉬프트/라벨 퍼뮤트” 누수 테스트(강제 붕괴 테스트)
- **E5 (연동)**: 레짐/구간별 OOS 분해로 특정 기간만 과대 성능인지 확인

### (d) PASS 조건
- E2에서:
  - Feature를 **+1 trading day** 쉬프트(lookahead 제거 방향) 시 성능이 **유의미하게 하락**(예: OOS mean 30%+ 하락 또는 Sharpe 급락)해야 정상
  - Label 퍼뮤트 시 성능이 **0 근처**로 붕괴해야 정상
- E5에서 특정 1~2구간만 “압도적 기여”가 아니라, 구간별 성능 분포가 **극단적으로 편향되지 않음**

## TOP3) 비용(슬리피지/스프레드/수수료) 미반영 + 과회전(턴오버) 우선 점검
### (a) 왜 필요한지
- 8~14개 집중 포트는 리밸런스가 잦으면 비용 충격이 큼.
- “성능이 안 움직임”이 사실은 **거래비용을 넣는 순간 상쇄되는 구조**일 수 있음.
- 비용이 로그에 없으면 전략 개선이 전부 무의미해짐.

### (b) 위험/부작용
- 현실적 비용을 넣으면 성능 급락 가능(그러나 운영 진입 전 필수).
- 비용 모델이 과보수적이면 과도하게 보수적으로 수렴할 수 있음 → 스트레스 범위(0/5/10/20bps)로 균형.

### (c) 최소 실험(2~3개) → **E3, E1 참조**
- **E3 (필수)**: 0/5/10/20bps 슬리피지 + 고정 수수료 + 스프레드 근사 적용한 OOS 재평가
- **E1 (연동)**: 거래 로그 기반으로 *실제 turnover/체결가정*이 계산되는지 검증

### (d) PASS 조건
- 슬리피지 10bps 기준에서:
  - OOS mean/Sharpe가 0bps 대비 **급붕괴(-50% 이상)** 하지 않을 것(급붕괴면 회전/엣지 구조 문제)
  - Turnover가 상식 범위(예: 일간 100%+ 같은 극단 값이 지속적으로 나오지 않음)
- “비용 포함 성능”이 챔피언 선정 기준에 **하드코딩**(즉, 비용 제외 점수로 챔피언이 뽑히지 않게)

## TOP4) 노출(Exposure) 드리프트/리스크 게이팅(ETF는 지표만)으로 운영 리스크 축소
현재 징후:
- exposure min/max가 **0.47 / 0.84**로 넓음 → 시장 레짐에서 노출이 자동으로 들쭉날쭉할 가능성

### (a) 왜 필요한지
- 운영에서 가장 위험한 건 “전략 엣지”보다 **노출 관리 실패로 인한 MDD 확대**.
- ETF 매매는 금지이므로(규칙) **QQQ/XLV 등을 ‘관측지표’로만** 써서 risk-off 시 **현금 비중 확대로 스케일다운**하는 게 합리적.

### (b) 위험/부작용
- 강한 상승장에서 리스크-오프가 오탐이면 수익을 깎을 수 있음.
- 게이트가 과민하면 매매 빈도/노이즈가 늘 수 있음 → 히스테리시스(연속 n일 조건)로 완화.

### (c) 최소 실험(2~3개) → **E4, E3 참조**
- **E4 (필수)**: QQQ/XLV realized vol, drawdown, trend를 지표로 한 **노출 스케일러(0.3~1.0)** 적용
- **E3 (연동)**: 스케일러 적용 전후의 turnover/비용 민감도 비교

### (d) PASS 조건
- worst_mdd가 **의미 있게 감소**(예: 상대 -15% 이상 개선)하면서
- OOS mean/Sharpe가 **과도하게 훼손되지 않음**(예: -10% 이내 손상)
- 노출 min/max 폭이 축소(예: max 0.84→0.75 이하, min 0.47→0.55 근방으로 “의도한 범위”로 수렴)

## TOP5) 레짐/구간별 성능 분해 + “안 움직임” 원인 고립(전략이 아니라 평가/적용/노출 문제일 수 있음)
### (a) 왜 필요한지
- “성능이 안 움직임”은 크게 5가지 축에서 발생:
  1) 트리거(시그널) 자체가 무의미  
  2) 적용(리밸런싱/지연/체결 가정)에서 엣지 소실  
  3) 노출(포지션 사이징/상관)로 알파가 상쇄  
  4) 비용(슬리피지/회전)으로 알파가 상쇄  
  5) 레짐 편중(특정 구간만 먹힘)
- 이걸 분해하지 않으면 “패치”가 랜덤워크가 됨.

### (b) 위험/부작용
- 구간 분해는 표본을 더 쪼개므로 통계적 노이즈가 증가 → **게이트를 ‘방향성’ 중심**으로 설정.

### (c) 최소 실험(2~3개) → **E5, E2 참조**
- **E5 (필수)**: 레짐/구간별 OOS 리포트 자동 생성(고변동 vs 저변동, 금리 상승/하락 근사, 빅테크 주도/헬스케어 주도 등은 지표로만)
- **E2 (연동)**: 레짐별로도 누수 테스트가 동일하게 붕괴하는지 확인

### (d) PASS 조건
- 레짐별 성능의 “기여도”가 한 구간에 과도하게 몰리지 않음(예: 상위 20% 구간이 전체 성과의 80% 이상 차지 같은 형태면 위험)
- 레짐 전환 구간에서 turnover/비용이 폭증하지 않음(폭증하면 E4/E3로 제어)

# 48시간 자동 루프용: **유니크 실험 5개(E1~E5)** 명령형 체크리스트

## E1) 리밸런스/거래 로그 표준화 + worst_mdd 강제 산출
1) **실험 정의**
   - 백테스트 출력물을 다음 3종으로 강제 저장:
     - `rebalance.jsonl`(각 리밸런스 시점별: timestamp, target weights, filled weights, cash, turnover, est_cost)
     - `fills.csv`(심볼별 체결 가정 내역)
     - `metrics.json`에 `worst_mdd` 포함
   - `aub_rebalance_pinpoint.py`가 읽는 입력 포맷을 고정(경로 문자열 `--base-log` literal 같은 실수 방지)
2) **게이트**
   - 도구가 base/cand 모두에서 파싱 성공 + 리포트 생성
   - worst_mdd != None
3) **기대 관측치**
   - “성능 불일치(1.88 vs 2.63)”의 원인이 **지표 산출/샘플 범위/버전** 중 무엇인지 로그로 추적 가능

## E2) 누수/서바이버십 강제 붕괴 테스트
1) **실험 정의**
   - (A) feature timestamp를 +1 day 쉬프트(lookahead 제거 방향)한 백테스트
   - (B) label permutation(랜덤 섞기) 백테스트
2) **게이트**
   - (A) 성능 유의미 하락
   - (B) 성능 0 근처로 붕괴
3) **기대 관측치**
   - 누수가 있으면 (A)에서도 성능이 유지되거나 (B)에서도 비정상적으로 높게 나옴 → 즉시 차단 신호

## E3) 비용/턴오버 스트레스(0/5/10/20bps) + 비용 포함 챔피언 선정
1) **실험 정의**
   - 동일 전략/리밸런스에서 슬리피지 0/5/10/20bps, 수수료 고정(예: 0.5~1.0달러/체결 등) 시나리오 OOS 비교
   - 선택 점수를 **비용 포함 점수**로 교체(하드코딩)
2) **게이트**
   - 10bps에서 성능 급붕괴 여부 확인(급붕괴면 회전/엣지 구조 문제로 판정)
3) **기대 관측치**
   - “좋아 보이는데 운영에서 안 됨”을 사전에 제거
   - turnover 상위 구간/원인(리밸런스 규칙/신호 변동성)이 로그로 드러남

## E4) ETF는 관측지표만: QQQ/XLV 기반 노출 스케일러(현금 비중 확대)
1) **실험 정의**
   - QQQ/XLV의 (i) 20D realized vol (ii) 60D drawdown (iii) 추세(예: MA)로 risk score 산출
   - risk score에 따라 포트폴리오 전체 가중치 스케일: 1.0 / 0.7 / 0.4 / 0.2 (나머지 현금)
2) **게이트**
   - worst_mdd 개선(상대 -15% 이상 같은 방향성 목표)
   - OOS mean 과도 훼손 방지(예: -10% 이내)
3) **기대 관측치**
   - 레짐 악화 구간에서 손실이 줄고, 노출 범위가 의도대로 수렴

## E5) 레짐/구간별 성능 분해 리포트 자동 생성
1) **실험 정의**
   - OOS를 레짐별로 분해 출력:
     - 고변동/저변동(관측: QQQ realized vol)
     - 시장 추세 상/하(관측: QQQ MA)
     - 헬스케어 상대강도(관측: XLV/QQQ 비율)
   - 각 레짐에서: OOS mean, worst_mdd, turnover, hit-rate 요약
2) **게이트**
   - “한 구간 올인” 편중 여부가 리포트로 즉시 판별 가능
3) **기대 관측치**
   - 성능 정체의 원인이 “레짐 편중 vs 비용 vs 노출” 중 어디인지 빠르게 고립

# 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐) — 실행 체크리스트

## 1) 트리거(시그널) 문제
- **명령:** 시그널 분포를 날짜별로 저장하고(평균/표준편차/상위 신호 종목), OOS에서 신호가 상수/포화되는지 확인
- **명령:** E2 퍼뮤트에서 성능이 유지되면 → 트리거가 아니라 누수/평가 문제로 판정

## 2) 적용(리밸런스/지연/체결) 문제
- **명령:** E1 로그로 “신호→목표비중→체결비중” 3단계를 시점별로 비교(슬리피지/제약으로 목표를 못 지키는지)
- **명령:** 리밸런스 주기 1D/2D/5D를 *추가 케이스로 늘리지 말고* 현재 주기에 대해 “실제 turnover의 원인(몇 종목이 돌리는지)”만 분해

## 3) 노출(사이징/상관/집중) 문제
- **명령:** 일별 net/gross exposure, 상위 3종목 기여도, 섹터(Tech/Healthcare) 내 편중을 저장
- **명령:** E4 적용 전후로 exposure 범위와 MDD가 같이 움직이는지 확인(노출 문제면 여기서 즉시 반응)

## 4) 비용(회전/슬리피지) 문제
- **명령:** E3에서 0→10bps로 갈 때 성능 민감도가 비정상적으로 크면 “엣지<비용” 구조로 판정
- **명령:** turnover 상위 10% 날짜를 찍고 그 날짜의 신호 분산/레짐(변동성)을 함께 기록(원인이 레짐인지 규칙인지 분리)

## 5) 레짐 편중 문제
- **명령:** E5에서 레짐별 성과/리스크/비용을 같이 보고, 성과가 특정 레짐(예: 저변동 상승장)에만 몰리면 E4 같은 게이트가 필수
- **명령:** 레짐별로 “성과는 좋은데 비용이 큰지”까지 같이 보아야 함(성과만 보면 착시)

## 24~48시간 실행 순서(우선순위대로, 중단 기준 포함)
