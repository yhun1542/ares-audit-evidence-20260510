아래는 **24~48시간 자동 루프**에서 바로 돌릴 수 있게, **누수/과최적화/서바이버십/비용 미반영/운영 리스크**를 최우선으로 점검하는 **명령형 체크리스트**다.  
(미국주식 only, Tech+Healthcare 중심 8~14종목 유지, ETF 매매 제외/관측지표만)

---

## TOP5 우선순위(코드/아키텍처/전략)

### 1) (운영 리스크) 아티팩트/로그 무결성 + 재현성 고정
**왜 필요한지**
- 현재 상태에서 `file:` 비어있고 `lane_hash/run_hash=None`, `worst_mdd=None` → **챔피언 결과의 재현/감사 불가**.
- `aub_rebalance_pinpoint`가 **base-log 경로 오류 + cand-log JSON 파싱 실패**로 완전 무력화 → 리밸런스/턴오버/비용 진단 불가.
- 성능이 “안 움직이는” 원인이 모델이 아니라 **파이프라인 누락/실패**일 확률이 큼.

**위험/부작용**
- 로그/스키마 강제는 단기적으로 실험 실패율을 올림(하지만 “조용히 망가지는” 것보다 낫다).
- fail-fast 도입 시, 당장 일부 레거시 아티팩트 로드가 중단될 수 있음.

**연결 실험(공유 실험 ID 사용)**  
- **E1**(아래 공통 실험 정의 참조) 변형: `rebalance.{csv,jsonl}` 강제 생성 + JSON schema validate on write  
- **E1** 변형: `champion_v*.json`에 `run_hash/lane_hash/data_hash/cost_hash` 필수 필드로 fail-fast

**PASS 조건**
- `aub_rebalance_pinpoint.py`가 **base/cand 모두 로딩 성공**하고 pinpoint 리포트 생성
- 챔피언 JSON에 `file/run_hash/lane_hash/worst_mdd`가 **항상 채워짐**
- “실험 성공인데 진단 불가” 케이스 0건

---

### 2) (누수/과최적화) Degenerate folds 제거 + 시간누수/라벨누수 차단
**왜 필요한지**
- `degenerate_folds: [1,2,3,8]`는 OOS 통계가 **의미 없거나 과최적화**로 치우칠 가능성 큼(학습/평가 샘플 부족, 타임스플릿 붕괴, 결측 처리 오류 등).
- Tech/HC 8~14종목이면 특히 **폴드 단위 표본 붕괴**가 자주 발생.

**위험/부작용**
- 누수 차단(라그/엠바고/퍼지)을 강화하면 단기 OOS 평균이 내려갈 수 있음(“진짜 성능”으로 수렴).
- 폴드가 정상화되면 이전 챔피언 대비 성능 비교가 불리해 보일 수 있음(하지만 필수 정리).

**연결 실험**
- **E2** 변형: Purged walk-forward + embargo 도입(예: 5~20 trading days)
- **E2** 변형: 모든 특징에 “최소 1바/1일” 강제 lag(동일 시점 종가/체결 기반 특징이면 더 큼)
- **E2** 변형: 유니버스/상장폐지 포함(서바이버십 제거) 스냅샷 검증(가능하면 CRSP류, 아니면 최소한 delist/merge 이벤트 처리)

**PASS 조건**
- `degenerate_folds`가 0 또는 허용 임계치(예: 전체 폴드의 10% 이하)로 감소
- OOS 성능이 소폭 하락해도 **oos_min 개선 또는 tail 리스크 개선(worst_mdd 산출+악화 방지)**가 확인
- “폴드별 성과가 한 폴드에만 의존” 현상이 감소(폴드 성과 분산 축소)

---

### 3) (비용 미반영) 거래비용/슬리피지/임팩트 모델을 OOS 게이트에 포함
**왜 필요한지**
- 현재 `exposure_max≈0.84`면 회전율이 조금만 커도 비용이 성과를 잡아먹음.
- 리밸런스 로그가 깨져있는 현 상태에선 비용 추정/턴오버 분석 자체가 불가 → **실전 성능 붕괴** 가능.

**위험/부작용**
- 비용을 넣으면 백테스트 성능이 떨어질 수 있음(정상).
- 비용 파라미터 과대 적용 시 과도한 보수화로 알파를 버릴 위험.

**연결 실험**
- **E3** 변형: 슬리피지 0/5/15 bps 민감도(종목별 유동성(ADV) 기반으로 스케일 옵션 포함)
- **E3** 변형: 턴오버 페널티(예: 일/주간 turnover target, 초과 시 penalty) 또는 리밸런스 밴드(±x%) 적용

**PASS 조건**
- “비용 포함 OOS”에서 **oos_mean 유지(또는 소폭↓) + oos_min 개선** 중 하나를 만족
- 평균 turnover가 목표 범위로 수렴(예: 주간 turnover 상한 설정 시 상한 준수율 ≥ 95%)
- 비용 민감도(0→15bps)에서 성과가 **비정상적으로 급락하지 않음**(모델이 고턴오버에 의존하지 않음)

---

### 4) (전략/운영) 8~14 Tech+Healthcare 유니버스/포트 제약을 하드-인포스
**왜 필요한지**
- “미국주식 only, Tech+Healthcare 중심(8~14)”이 **전략 정의의 일부**인데, 이게 소프트면 실험마다 유니버스가 흔들리며 결과 비교가 무의미해짐.
- `exposure_min=0.0`은 “노출 0” 구간이 발생했다는 뜻 → 레짐 게이트가 없는데도 0이면 **신호/제약/결측 처리 문제** 가능.

**위험/부작용**
- 하드 제약은 성능을 일부 제한할 수 있음(정상).
- 종목수 강제는 신호가 약할 때 억지 포지션을 만들 수 있어 tail 악화 가능 → 게이트 필요.

**연결 실험**
- **E4** 변형: 종목수 8~14 강제(미달 시 “현금”이 아니라 **동일 섹터 내 차선 신호**로 채우거나, 명시적 리스크-오프 규칙으로 축소)
- **E4** 변형: 포지션 상한/하한(예: max weight 15%, min active weight 3% 등) + gross/net 노출 캡

**PASS 조건**
- 모든 날짜에서 보유 종목 수가 8~14 범위 준수율 ≥ 99%
- 단일 종목 쏠림(최대 비중)과 섹터 편중이 목표 범위 내 유지
- `exposure_min`이 0이 되는 케이스가 **정책적으로 설명 가능(리스크-오프)**하거나 제거

---

### 5) (레짐/리스크) ETF는 “관측지표”로만: 레짐 게이트/리스크 오프 구현
**왜 필요한지**
- Tech/HC는 레짐 의존성이 큼(금리/리스크온오프).
- ETF 매매는 금지지만, **XLK/XLV/QQQ/SPY/VIX(또는 VIX proxy)**를 관측지표로 쓰면 “노출 조절”로 tail을 줄일 수 있음.

**위험/부작용**
- 게이트가 과민하면 노출이 자주 줄어 알파가 희석될 수 있음.
- 레짐 신호가 지연되면 고점/저점에서 반대로 작동할 수 있음.

**연결 실험**
- **E5** 변형: ETF 기반 risk-off 트리거(예: SPY/QQQ 단기 모멘텀↓ + 변동성↑이면 gross exposure 상한 축소)
- **E5** 변형: 섹터 상대강도(XLK vs XLV, QQQ vs SPY)로 Tech/HC 내 비중 스케일(종목 매매는 그대로, **스케일만**)

**PASS 조건**
- `oos_min` 개선(최우선) 또는 worst MDD 개선
- 노출 축소 구간이 “시장 스트레스” 구간과 정합(이상하게 횡보장에서만 꺼지지 않음)
- 게이트 적용 후 turnover/비용이 과도하게 증가하지 않음

---

# 48시간 자동 루프용 “공통 실험 5개”(케이스 폭발 방지)

아래 **E1~E5**만 돌리고, 위 TOP5는 각 실험의 **서브-변형(토글/파라미터)**로 해결한다.

## E1) Artifact/Log Schema & Rebalance Output Patch
1) **실험 정의**
- 리밸런스 로그 `rebalance.csv` + `rebalance.jsonl`를 매 런 강제 생성
- JSONL은 line-delimited JSON + schema validate
- champion json 필수 필드: `run_hash, lane_hash, data_hash, code_hash, cost_model_hash, worst_mdd`
2) **게이트**
- 진단 툴 2종(`no_delta`, `rebalance_pinpoint`)이 자동으로 성공해야 다음 실험 결과를 “유효”로 인정
3) **기대 관측치**
- “데이터는 좋은데 리포트가 비어있음/파싱 실패” 클래스의 장애가 0으로 수렴
- 이후 E2~E5에서 성능 변화가 없더라도 **왜인지 추적 가능**

---

## E2) Time-split Integrity (Purged WF + Embargo + Feature Lag)
1) **실험 정의**
- purged walk-forward 적용, 폴드 경계에 embargo 삽입
- 모든 피처 최소 lag 강제(동일 bar 정보 사용 금지)
- 유니버스 생성 시점/상장폐지 처리(서바이버십 체크)
2) **게이트**
- `degenerate_folds==0` 또는 임계 이하
- 훈련/검증/테스트 구간 overlap 0(시간 인덱스 기준)
3) **기대 관측치**
- OOS 평균이 내려가도, tail(oos_min, MDD)이 더 “현실적”으로 변함
- 폴드별 편차가 줄고 특정 폴드에 대한 과의존이 감소

---

## E3) Cost Model + Turnover Control Sensitivity
1) **실험 정의**
- 슬리피지 0/5/15bps, (가능하면) ADV 기반 임팩트 옵션
- turnover penalty 또는 리밸런스 밴드 적용
2) **게이트**
- 비용 포함 성능이 비용 0 대비 “전멸”하지 않을 것(턴오버 의존 모델 탈락)
- 평균 turnover 상한 준수
3) **기대 관측치**
- “알파는 있는데 비용으로 사라지는지”가 즉시 분리됨
- 실전 근접 성능으로 수렴

---

## E4) Portfolio Constraint Hardening (8~14, Caps, Exposure Floor)
1) **실험 정의**
- 보유 8~14 강제 + 단일비중 상한 + gross/net 캡
- 노출 0 발생 시 원인(게이트/결측/제약)을 로그로 태깅
2) **게이트**
- 제약 위반 0(또는 로그에 예외 사유가 명시될 것)
- 포트폴리오가 항상 “정의된 전략” 범위 내
3) **기대 관측치**
- 변동 큰 기간에 쏠림 감소, tail 개선 가능
- 성능이 그대로면 “전략 정의가 흔들려서 생긴 착시”를 제거

---

## E5) ETF-Indicator Regime Gate (No Trading)
1) **실험 정의**
- XLK/XLV/QQQ/SPY/VIX proxy를 입력으로 “gross exposure 스케일”만 조절
- 리스크오프 시 포지션 수는 유지하되(8~14) 총 노출만 축소(또는 하한 존재)
2) **게이트**
- risk-off 빈도 상한(예: 전체의 10~30% 범위; 과다 차단 방지)
- turnover 증가율 제한
3) **기대 관측치**
- oos_min/worst MDD 개선이 우선적으로 관측
- 노출 히스토그램이 레짐과 정합

---

# 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐)

아래는 **결과가 정체**될 때, 어디가 막혔는지 자동으로 갈라내는 트리 형태의 점검 순서다(질문 없이 실행 가능).

## A. 트리거(신호 생성) 문제
- **신호 엔트로피/분산** 로그: 예측값이 거의 상수(또는 클리핑)인지 확인
- 상위/하위 버킷 스프레드(예: top-minus-bottom) 일관성 체크
- 폴드별 feature importance/IC가 “한 폴드만 과대”인지 확인(과최적화 냄새)

## B. 적용(리밸런싱/체결/라운딩) 문제
- 목표비중→실현비중 괴리(라운딩/최소주문/거래불가) 추적
- 리밸런스 캘린더가 의도대로 동작하는지(주간/일간) 및 휴장 처리
- 리밸런스 로그 누락/파싱 실패(E1로 해결)

## C. 노출(포지션 수/스케일/리스크) 문제
- `exposure_min=0` 발생일을 태깅:  
  - (1) 레짐 게이트 때문인지  
  - (2) 제약 충돌로 포트 구성 실패인지  
  - (3) 결측/유니버스 비었는지
- 보유 종목 수가 8~14를 벗어난 날이 있는지(전략 정의 붕괴)
- 최대비중/섹터 편중이 tail을 만들고 있는지

## D. 비용(슬리피지/스프레드/임팩트/차입) 문제
- “비용 전 PnL” vs “비용 후 PnL” 분해(일별/종목별)
- turnover와 성과의 상관: 고회전일수록 PnL이 죽는지
- 유동성 낮은 종목(Tech/HC 중 mid-cap)에서 임팩트가 지배적인지

## E. 레짐(시장 상태) 문제
- ETF 관측지표로 구간을 라벨링(리스크온/오프, 금리민감, 변동성 급등)
- 레짐별 성과 테이블(평균/하방/샤프)로 “언제만 먹히는지” 확인
- 레짐 게이트를 적용해 **tail만 개선되는지**(평균은 그대로여도 통과 가치 있음)

---

## 실행 순서(48시간 내 권장)
1) **E1 즉시**: 로그/스키마/리밸런스 출력부터 정상화(진단 가능 상태 확보)
2) **E2**: degenerate folds 제거 + 누수 차단(백테스트 신뢰성 회복)
3) **E3**: 비용/턴오버로 “실전 붕괴” 여부 판별
4) **E4~E5**: 전략 정의 고정(8~14 Tech/HC) + 레짐 기반 tail 방어

이 순서로 돌리면, 성능이 오르든 안 오르든 **“왜” 안 움직였는지**가 48시간 안에 분해된다.
