## 24~48시간 TOP5 우선순위 (명령형 체크리스트)
아래 5개는 **누수/과최적화/서바이버십/비용 미반영/운영 리스크**를 먼저 잠그고, 그 다음 **Tech+Healthcare 8~14종목(미국주식 only, ETF 매매 제외)** 제약 하에서 성능을 “움직이게” 만들기 위한 **실행 가능한 patch/실험 5개**로 제한한다. (각 항목: 최소 2~3 실험, 48시간 루프용 게이트 포함)

---

# 1) (누수 최우선) 피처 타임스탬프/라벨 누수 차단 패치
### (a) 왜 필요한지
- 최근 후보(`exp_macro_alpha_shadow`)가 **tuning_min이 0.05로 급락** → fold/구간에 따라 “정보가 있는 날”만 먹는 패턴(누수/비정상 피처/시점 불일치) 가능성이 큼.
- lockbox가 평균은 비슷해도 **worst_mdd가 악화(-0.1118)** → 누수성 피처는 특정 국면에서 급락을 유발하기 쉬움.

### (b) 위험/부작용
- 누수 제거 후 단기 성능 하락 가능(진짜 알파 vs 누수 알파 구분).
- 피처 시프트/엠바고 적용 시 거래 신호가 느려져 기회손실 가능.

### (c) 최소 실험 2~3개 (48h 루프형)
**실험 정의**
1. **Feature “asof” 강제 패치**: 모든 피처에 `available_at`을 부여하고, 예측시점 t에서 `available_at <= t`만 사용.
2. **1-bar shift stress test**: 전 피처를 일괄 `shift(+1)`(또는 +1 trading day)한 버전으로 재학습/재백테스트.
3. **Purged/Embargo CV**: 학습-검증 경계에 purge window(예: 5~10 trading days) + embargo를 적용한 CV로 재평가.

**게이트(자동 중단/FAIL 조건)**
- (G1) shift(+1)에서 성능이 **비정상적으로 급락**(예: lockbox_mean이 champion 대비 -15% 이상)하면 “시점누수 가능” 플래그 → 해당 피처 그룹을 강제 제외하는 ablation으로 전환.
- (G2) purged CV에서 tuning_mean은 유지되는데 lockbox가 급락하면 과최적화 플래그.

**기대 관측치**
- 누수성 피처가 있으면: (i) shift(+1)에서 급락, (ii) purged CV에서 급락, (iii) 특정 피처/그룹 제거 시 성능/안정성 회복.

### (d) PASS 조건
- lockbox_mean ≥ **1.80**(champion 1.7925 상회) AND lockbox_min ≥ **1.15**
- worst_mdd ≥ **-0.10**
- shift(+1) 버전이 원본 대비 **과도한 붕괴 없이**(예: lockbox_mean -10% 이내) 유지

---

# 2) (비용 미반영) 슬리피지/스프레드 비용 모델 강화 + 턴오버 제한
### (a) 왜 필요한지
- Tech/Healthcare라도 8~14종목 집중은 리밸런싱이 잦으면 비용에 취약.
- 비용이 모델에 반영되지 않으면 tuning에서만 좋아지고 lockbox/실거래에서 무너짐(전형적 실패).

### (b) 위험/부작용
- 비용 반영으로 단기 샤프 하락 가능(진짜/가짜 알파 분리 과정).
- 턴오버 제한이 알파의 “속도”를 죽일 수 있음.

### (c) 최소 실험 2~3개
**실험 정의**
1. **가변 슬리피지 모델**: (고정 bps) → (ATR/가격/유동성 기반 bps)로 확장. 예: `slippage_bps = base + k * (ATR/Price)` 형태.
2. **턴오버 페널티**: 목적함수(또는 포지션 업데이트)에 `λ * turnover` 페널티 추가.
3. **리밸런스 주기 스윕(운영친화)**: daily → 2D/3D(또는 신호 변화 시에만)로 변경한 2~3개만 시험.

**게이트**
- (G1) 비용을 +50% 상향해도 lockbox 성능이 **급격히 붕괴**하면 FAIL(비용 민감 전략).
- (G2) turnover가 champion 대비 감소하지 않으면(예: -20% 미만) FAIL.

**기대 관측치**
- “비용에 강한” 구조면 비용 상향 스트레스에서도 lockbox_mean이 크게 안 무너지고, drawdown이 완만해짐.

### (d) PASS 조건
- lockbox_mean ≥ **1.79** 유지(대폭 하락 금지) AND worst_mdd ≥ **-0.10**
- turnover ≥20% 감소(또는 거래횟수/리밸런스 횟수 감소) + 비용 스트레스(+50%)에서 성능 하락 ≤10%

# 3) (서바이버십/유니버스) Tech+Healthcare 8~14 종목 유니버스 “as-of” 고정 + 상장폐지/티커변경 처리
### (a) 왜 필요한지
- “현재 살아남은 종목만”으로 학습하면 backtest가 과대평가(서바이버십 바이어스).
- 집중 포트(8~14)는 유니버스 정의가 결과에 큰 영향을 줌.

### (b) 위험/부작용
- 과거에 존재했으나 지금은 없어진 종목 포함 시 데이터 공백/품질 이슈로 운영 복잡도 증가.
- 유니버스가 커지면(또는 변동이 커지면) 모델 안정성이 흔들릴 수 있음.

### (c) 최소 실험 2~3개
**실험 정의**
1. **As-of 유니버스 스냅샷**: 각 거래일 t에 “t 시점에 섹터 분류상 Tech/Healthcare였고 거래가능했던 종목”만 포함.
2. **Corporate action/티커 매핑 검증**: ticker change, delisting, split 데이터가 가격/리턴에 정확히 반영되는지 일괄 점검.
3. **유니버스 안정성 실험(폭 제한)**: Tech+Healthcare 내에서 (A) mega/large 중심 vs (B) 동일가중 broad(단 8~14 선별은 유지) 두 가지로만 비교.

**게이트**
- (G1) as-of 적용 후 성능이 “급상승”하면 기존 결과가 누수/바이어스였을 가능성 → FAIL로 간주하고 champion 교체 금지(원인 규명 우선).
- (G2) 데이터 누락률/결측률이 임계치(예: 0.5% 이상)면 FAIL(운영 리스크).

**기대 관측치**
- 진짜 알파면 as-of 적용 후에도 성능이 크게 안 꺾이고, 구간별 변동성이 감소.

### (d) PASS 조건
- lockbox_mean champion 대비 **-3% 이내 유지**(유니버스 정합성 비용 감안)
- 결측/오류율 기준 통과 + worst_mdd 악화 없음(≤ -0.10)

# 4) (과최적화/레짐) “ETF는 관측지표만” 레짐 게이트로 노출(베타/섹터) 제어
### (a) 왜 필요한지
- 후보가 MDD가 더 나쁘고(fold14_mdd -0.0997, worst_mdd -0.1118) 구간 취약성이 보임 → 레짐(리스크온/오프)에서 노출을 자동 조절해야 안정화.
- ETF 매매는 금지지만, **XLK/XLV/QQQ/SPY** 등을 레짐 관측으로 쓰는 건 운영상 강력.

### (b) 위험/부작용
- 게이트가 과하게 작동하면 수익 기회를 많이 놓침(under-exposure).
- 레짐 신호가 지연되면 “늦게 줄이고 늦게 늘리는” 문제가 발생.

### (c) 최소 실험 2~3개
**실험 정의**
1. **리스크 레짐 스케일러**: 관측지표(예: QQQ의 20D 추세, SPY 실현변동, XLK/XLV 상대강도)로 총 익스포저를 0.5~1.0 범위에서 스케일.
2. **MDD 보호 게이트(전략 내부)**: 최근 N일 변동성/드로우다운이 임계 초과 시 신규 진입/증액 제한(단, 기존 포지션 청산은 규칙대로).
3. **섹터 로테이션 감지(관측만)**: XLK vs XLV 상대모멘텀에 따라 Tech/Healthcare 내에서 **Tech 비중 상한**만 조절(종목은 기존 선택 로직 유지).

**게이트**
- (G1) 레짐 게이트 적용 후 turnover가 증가하면 FAIL(운영/비용 악화).
- (G2) 상시 익스포저가 과도하게 줄어 CAGR(또는 mean)이 크게 하락하면 FAIL.

**기대 관측치**
- lockbox_min 개선, worst_mdd 완화, 구간별 성능 분산 감소(“안정화” 형태).

### (d) PASS 조건
- worst_mdd ≥ **-0.095** (champion 수준 회복/개선)
- lockbox_min ≥ **1.20**로 개선(최저 성능 바닥 올리기) + turnover 비증가

---

# 5) (운영 리스크) 48시간 자동 루프 “재현성/데이터 신선도/실패 격리” 패치
### (a) 왜 필요한지
- 자동 루프에서 성능이 안 움직이는 가장 흔한 원인이 **(i) 실험이 사실상 동일**, (ii) 데이터 업데이트 실패, (iii) 캐시/seed/스펙 불일치로 인한 비교 불가임.
- 운영 안정성이 없으면 챔피언/후보 비교가 무의미해짐.

### (b) 위험/부작용
- 로그/검증 단계가 늘어나 런타임 증가.
- 엄격한 검증은 일부 실험을 “실행 전”에 차단(진행량 감소).

### (c) 최소 실험 2~3개
**실험 정의**
1. **실험 서명(hash) 강제**: 데이터 스냅샷 ID + 코드 커밋 + config를 해시로 기록, 동일 해시 재실행은 자동 스킵.
2. **데이터 신선도 게이트**: 가격/펀더멘털/매크로 등 입력별 `last_updated` 체크 후 stale면 FAIL(또는 shadow run로 격리).
3. **실패 격리 + 자동 회귀 테스트**: (a) backtest 단위 테스트(lookahead, NaN 폭발, 비정상 turnover) 통과해야 본 실험 실행.

**게이트**
- (G1) 입력 데이터가 stale면 “실험 결과 저장 금지”.
- (G2) 재현성 체크(동일 seed 2회)가 허용 오차 밖이면 FAIL.

**기대 관측치**
- 실험 다양성이 증가(“같은 실험 반복” 제거), 결과 비교 신뢰도 상승, 운영 중단 감소.

### (d) PASS 조건
- 48시간 동안 (i) 중복 실험 0건, (ii) stale 데이터로 저장된 결과 0건
- 동일 config 재실행 성능 편차가 허용범위 이내(예: 주요 지표 ±1~2%p 이내)

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래 순서로 **원인 트리(디버그 루프)**를 고정하고, 각 단계에서 “관측지표”를 로그로 남겨라.

1) **Trigger(신호 생성) 문제**
- 관측: 신호 분포(평균/표준편차), 극단값 비율, 신호-미래수익 상관(IC) 롤링, 구간별 히트율.
- 분해: (a) 피처 드리프트(최근 구간에서 분포 붕괴), (b) 결측/0 채움으로 신호가 0에 붙음, (c) 레이블 정의/시프트 불일치.
- 조치: 피처 표준화 기준을 “train-only”로 고정, 결측률 임계 초과 피처 자동 제외.

2) **Apply(포지션 반영/리밸런싱) 문제**
- 관측: 주문 생성 횟수, 포지션 변화량, 리밸런싱 빈도, 제한조건(최대비중/최소보유일) 때문에 신호가 “클립”되는 비율.
- 분해: 좋은 신호가 나와도 (a) 제약으로 반영 안 됨, (b) 동률 처리/정렬 버그로 종목 선택이 흔들림.
- 조치: “신호 상위 K → 실제 채택된 K” 일치율 로깅, 클립률이 높으면 제약 재설계.

3) **Exposure(노출) 문제**
- 관측: 베타(SPY/QQQ), 섹터 노출(Tech vs Healthcare), 상관 구조(포트 상호상관), 단일종목 기여도(상위 1~3 종목이 PnL의 몇 %인지).
- 분해: 알파가 아니라 베타/모멘텀에 기대고 있거나, 8~14 집중에서 한두 종목이 다 먹는 구조(불안정).
- 조치: 베타 목표 범위(예: 0.2~0.8) 설정 후 벗어나면 스케일, 종목 기여도 상한(리스크 패리티/캡) 실험.

4) **Cost(비용) 문제**
- 관측: gross vs net 성능 차이, 회전율, 거래당 기대수익 대비 비용(bps), 슬리피지 스트레스(×1.5/×2) 민감도.
- 분해: 알파가 “bps 단위”인데 거래가 잦아 비용에 다 깎임.
- 조치: 턴오버 페널티/리밸런스 완화/체결가 보수화.

5) **Regime(국면) 문제**
- 관측(ETF는 관측지표): QQQ 추세, SPY 변동성, XLK/XLV 상대강도, drawdown 국면에서의 신호 성능(conditional IC).
- 분해: 특정 레짐에서만 유효한 신호(예: 리스크온에서만).
- 조치: 레짐별로 익스포저 스케일/진입 제한(위 4번 패치).

## 바로 실행 순서(48시간 루프에 맞춘 우선순위)
1) **누수 차단(1번)** → 결과 신뢰도 확보  
2) **비용 모델+턴오버(2번)** → 실거래 근접화  
3) **서바이버십/as-of 유니버스(3번)** → 백테스트 과대평가 제거  
4) **레짐 게이트(4번)** → worst_mdd/lockbox_min 개선  
5) **운영 재현성(5번)** → 자동 루프가 “진짜 실험”을 돌게 함  

원하면, 위 5개를 `module_registry`에 매핑되는 형태(파일/모듈 단위)로 “실험 스펙 템플릿(yaml/json)”까지 바로 떨어뜨리는 패치 목록으로 정리해도 되지만, 질문은 하지 않고 현재 규칙대로 여기서 멈춘다.
