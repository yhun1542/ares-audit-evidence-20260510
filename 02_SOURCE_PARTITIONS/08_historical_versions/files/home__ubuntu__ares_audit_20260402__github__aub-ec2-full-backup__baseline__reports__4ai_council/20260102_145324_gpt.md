## TOP5 우선순위(24~48h) — “명령형 체크리스트”
(누수/과최적화/서바이버십/비용 미반영/운영 리스크부터)

---

### 1) **리밸런스 로그/아티팩트 무결성 복구(운영 리스크 최우선)**
**왜 필요한지**
- `aub_rebalance_pinpoint`가 **base-log 파일 없음**, `rebalance.csv`를 **JSON으로 파싱**하다가 깨짐 → “무슨 변화가 실제로 거래로 반영됐는지”를 못 봄.
- “No-Delta(성능 무변화)”가 **진짜 전략 문제인지, 단순히 변경이 적용/실행되지 않은 문제인지** 구분 불가.
- `worst_mdd: None`도 지표 산출 파이프라인 누락/예외 가능성.

**위험/부작용**
- 로깅/스키마 수정이 기존 리포트 도구들과 충돌(과거 실험 재현성 깨질 수 있음).
- 성능 변화 없이도 “보이는 것”만 달라져 혼란 가능 → 버전 태깅 필수.

**최소 실험(공용 실험 세트 중 사용: E5)**
- (E5-1) **리밸런스 이벤트를 단일 포맷(JSONL)로 강제**: `timestamp, universe_hash, weights_before/after, turnover, est_cost, fill_price_proxy`를 매 리밸런스마다 append.
- (E5-2) `aub_rebalance_pinpoint.py`가 **CSV/JSONL 자동 감지**하도록 수정(확장자 기준) + `--base-log` 기본값을 “최근 champion run artifact”로 자동 해석.
- (E5-3) 백테스트 종료 시 `metrics.json`에 **worst_mdd 항상 채우기**(NaN이면 원인 스택트레이스 포함).

**PASS 조건**
- 리밸런스 로그가 **양쪽(base/cand) 모두 로드**되고 pinpoint 리포트가 생성됨(에러 0).
- 각 실험에서 “실제로 바뀐 종목/가중치/턴오버”가 리포트로 확인 가능.
- `worst_mdd`가 None이 아닌 수치로 기록(산출 실패 시 run 자체 FAIL 처리).

### 2) **누수/서바이버십/타임스탬프 정합성 감사(리서치 리스크 최우선)**
**왜 필요한지**
- Tech+Healthcare 8~14종목 “고정 유니버스”는 구현이 쉽지만, **현재 시점 종목을 과거에 그대로 적용하면 서바이버십**이 생김.
- 펀더멘털/어닝즈/가이던스/리포트 기반 피처는 **발표 시점(공시 시각) 오정렬**로 룩어헤드가 가장 흔함.
- “성능이 안 움직임”은 종종 **게이트가 너무 강해 변화가 실제로 반영되지 않거나**, 반대로 **누수로 과거부터 이미 과대추정**된 상태일 수 있음.

**위험/부작용**
- 누수 제거 시 OOS 하락이 “개선”처럼 보이지 않을 수 있음(하지만 신뢰도는 상승).
- 유니버스 as-of 재구성은 데이터 의존(소스/라이선스) 및 구현 비용 증가.

**최소 실험(공용 실험 세트: E2)**
- (E2-1) **피처-라벨 시간검증 자동 테스트 추가**: 각 피처 컬럼에 `available_ts`를 강제하고, 학습/예측 시점이 `available_ts` 이전이면 run FAIL.
- (E2-2) **Purged/Embargoed CV**(예: 5fold, embargo 5~10bar)로 fold 누수 차단 후 기존 champion 재평가.
- (E2-3) **유니버스 서바이버십 패치**: (가능하면) “as-of 시가총액/상장상태 기준 Top Tech+Healthcare 8~14”를 각 날짜에 재구성. (당장 데이터가 없으면 최소한) 현재 고정 리스트 사용 시 리포트에 **SURVIVORSHIP WARNING**를 강제 출력.

**PASS 조건**
- 누수 테스트(E2-1) 0건 통과 + embargo CV에서 성능이 “급락/급등” 없이 합리적(극단 변동이면 원인 규명 전까지 배포 금지).
- 서바이버십 경고가 사라지거나(데이터로 해결), 최소한 실험 결과가 “survivorship on/off”로 비교 가능.

---

### 3) **거래비용/슬리피지 모델링 + 턴오버 제어(비용 미반영 리스크)**
**왜 필요한지**
- 현재 노출(exposure) 0.47~0.84면 사실상 상시 포지션인데, 리밸런스가 잦으면 **비용이 PnL을 잠식**.
- “No-Delta”는 종종 비용을 넣으면 다 동일하게 눌려서 구분이 안 나거나, 반대로 비용 미반영으로 과대평가되어 **개선이 의미 없게** 됨.

**위험/부작용**
- 비용 모델이 과도하면 전략이 과소거래로 퇴화(신호 반영이 느려짐).
- 종목별 스프레드/유동성 추정이 부정확하면 편향 발생.

**최소 실험(공용 실험 세트: E1)**
- (E1-1) **비용 2단 모델 A/B**를 고정:
  - A: `cost = bps_fixed(예: 3~8bp) * turnover`
  - B: `cost = spread_proxy + impact_proxy(ADV 기반)` (ADV 없으면 시총/가격 기반 근사)
- (E1-2) **턴오버 상한 게이트**: 48시간 루프에서 후보가 `avg_turnover > X`면 자동 FAIL(또는 점수 페널티).
- (E1-3) **리밸런스 빈도 실험**: 동일 신호에서 rebalance를 (daily vs 2-day vs weekly)로만 바꿔 비용 민감도 관측.

**PASS 조건**
- 비용 포함 OOS에서 **순성과(After-cost)**가 유지되거나, 최소한 “best 후보가 비용 민감도에서 우세”가 명확.
- 평균 턴오버가 상한 내로 수렴(상한은 시스템 표준값으로 고정) + 성능의 fold 분산 감소.

---

### 4) **노출/헤지/포지션 한도 게이트(과최적화·운영 리스크 동시 대응)**
**왜 필요한지**
- 현재 exposure min/max가 0.47~0.84로 넓음 → 신호가 약해도 **항상 위험자산 노출**일 수 있음.
- 8~14 종목이면 단일 종목 리스크가 커서, 포지션 한도/섹터 중립이 없으면 **운영에서 한 번에 깨짐**.

**위험/부작용**
- 제약을 걸면 백테스트 수익률이 내려갈 수 있음(하지만 tail risk/재현성이 개선).
- 과도한 중립화는 알파를 죽일 수 있음.

**최소 실험(공용 실험 세트: E3)**
- (E3-1) **단일 종목 max weight**(예: 15~20%) + **최소 보유 종목 수**(예: 8) 강제.
- (E3-2) **목표 노출(target gross/net) 밴드**를 좁힘(예: gross 0.6~0.8) + 밴드 밖이면 신호 스케일링으로 자동 조정.
- (E3-3) (헤지 존재 시) 헤지 비율을 “신호 강도”가 아닌 **고정 규칙(상한/하한)**으로만 움직이게 하여 과최적화 감소.

**PASS 조건**
- MDD/변동성 지표가 계산되고(우선 1번 패치 선행), 제약 적용 후 **worst_mdd 개선 또는 동일 수준 유지** + OOS 평균이 유의미하게 훼손되지 않음.
- 포지션 집중도가 낮아지고(예: HHI 감소), 리밸런스 시 급격한 체결량/턴오버 스파이크가 줄어듦.

### 5) **레짐(상태) 관측 기반 게이트 추가(성능 정체 원인 분해용)**
**왜 필요한지**
- “성능이 안 움직일 때”는 종종 **한 레짐에서만 먹히는 구조**인데, 실험들이 모두 같은 기간/같은 레짐에 묻혀 차이가 안 보임.
- ETF는 매매 금지지만, **관측 지표(예: QQQ/XLV, VIX, UST2Y/10Y)** 로 상태를 태깅하면 원인 분해가 쉬움.

**위험/부작용**
- 레짐 분류가 과도하면 데이터마이닝 위험(레짐 수를 늘리면 과최적화).
- 게이트가 거래를 너무 막아 노출이 지나치게 낮아질 수 있음.

**최소 실험(공용 실험 세트: E4)**
- (E4-1) **2-state 레짐 태그만 추가**(거래 규칙 변화 없음):  
  - Risk-on/off: `VIX` 또는 `QQQ 20d trend` + `rates trend` 같은 단순 조건  
  → 성과/턴오버/히트레이트를 레짐별로 리포팅.
- (E4-2) 레짐에 따라 **리밸런스 빈도만 변경**(신호는 동일): risk-off에서는 rebalance 완화(비용+whipsaw 감소 관측).
- (E4-3) 레짐에 따라 **노출 밴드만 조정**(예: risk-off gross 상한 낮춤).

**PASS 조건**
- 레짐별 성과 테이블에서 “어떤 상태에서 죽는지”가 명확히 분리(분리가 안 되면 레짐 태그가 의미 없으므로 제거).
- 레짐 적용 실험(E4-2/3)이 비용/턴오버/드로우다운 중 최소 1개를 개선하면서 OOS 평균을 과도하게 훼손하지 않음.

## 48시간 자동 루프용 “실행 가능한 실험” 5개만 고정(E1~E5)
아래 5개를 **매 48시간 루프에서 항상** 돌리고, 후보 전략 변경은 이 안에서만 평가되게 고정하라.

1. **E5: 로그/리밸런스/지표 산출 무결성**  
   - (1) 실험 정의: 로깅 스키마/로더 수정 + worst_mdd 필수화  
   - (2) 게이트: 리포트 생성 실패/None 지표면 즉시 FAIL  
   - (3) 기대 관측치: pinpoint 리포트에 “변경이 거래로 반영됨”이 보임

2. **E2: 누수/서바이버십/embargo CV**  
   - (1) 정의: available_ts 검사 + purged CV + 유니버스 as-of(또는 경고)  
   - (2) 게이트: 룩어헤드 1건이라도 발견 시 FAIL  
   - (3) 기대 관측치: fold 성능 분산이 안정화, 과대 성과가 현실화

3. **E1: 비용모델 A/B + 턴오버 상한**  
   - (1) 정의: fixed bps vs impact proxy + 상한 게이트  
   - (2) 게이트: after-cost OOS가 기준 미만이면 FAIL  
   - (3) 기대 관측치: 고턴오버 후보가 자동으로 걸러지고 순성과 중심으로 순위 재정렬

4. **E3: 포지션 한도/노출 밴드/헤지 상한**  
   - (1) 정의: max weight, min names, gross/net 밴드  
   - (2) 게이트: 집중도/노출 위반 시 FAIL  
   - (3) 기대 관측치: tail risk 감소, 리밸런스 스파이크 감소

5. **E4: 레짐 태그(관측) + 레짐별 빈도/노출만 조정**  
   - (1) 정의: 2-state 레짐 + 조정 1개만 적용(빈도 또는 노출)  
   - (2) 게이트: 레짐 분리력이 없거나 거래를 과도 차단하면 FAIL  
   - (3) 기대 관측치: “안 움직이는 이유”가 레짐/비용/노출 중 어디인지 분해 가능

## 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래 순서로 **기계적으로** 분해하라(질문 없이 자동 리포트로).

1) **Trigger(신호가 실제로 바뀌었나?)**
- 관측: 예측 스코어 분포(평균/표준편차), 상위/하위 종목 랭크 변동률
- 트리거: “스코어 분산이 0에 수렴” 또는 “랭크 상관이 0.99+로 고정” → 실험이 실질적으로 동일

2) **Apply(변경이 실행에 반영됐나?)**
- 관측: 리밸런스 전/후 weights diff, turnover, 주문 수
- 트리거: weights diff ≈ 0인데 스코어는 변함 → 실행 레이어(스케일/클램프/라운딩)가 신호를 죽임

3) **Exposure(노출이 결과를 덮나?)**
- 관측: gross/net, 상위 보유 비중, 현금비중, 섹터 편중
- 트리거: 노출 밴드가 너무 빡빡/너무 넓어서(현재처럼 0.47~0.84) 전략 차이를 덮음

4) **Cost(거래비용이 알파를 상쇄하나?)**
- 관측: turnover와 after-cost 성과의 상관, 비용 항목 비중
- 트리거: before-cost는 차이나는데 after-cost가 동률 → 비용 민감도가 핵심

5) **Regime(기간이 특정 상태라 차이가 안 나는가?)**
- 관측: 레짐별 hit-rate / drawdown / turnover
- 트리거: 특정 레짐에서만 전략 간 차이가 나고 전체 기간에선 상쇄 → 레짐 태깅 후 게이트/노출 조정이 필요

---

### 즉시 실행 순서(24~48h)
1) **E5 먼저 고쳐서** “변경이 거래로 반영/비반영”을 확인 가능하게 만들어라.  
2) **E2로 누수/서바이버십을 봉인**해 결과 신뢰도를 확보하라.  
3) 그 다음 **E1+E3로 비용/노출을 현실화**해 후보 간 차이를 벌려라.  
4) 마지막으로 **E4로 성능 정체의 원인을 레짐 단위로 분해**하라.

(위 5개(E1~E5) 이외의 케이스 확장은 금지하고, 48시간 루프에서 이 5개만 반복 갱신하도록 고정하라.)
