# TOP1) 데이터 누수(lookahead/asof/corp action) “완전 봉인”
### (a) 왜 필요한지
- 현재 `candidate_20260101_194908...`는 **lockbox_mean/min이 크게 개선(1.554 / 0.334)** 되었는데, 이런 형태는 “진짜 개선”일 수도 있지만 **asof merge/리밸런싱 시점/실적 발표 시각/분할·배당 조정** 누수에서 가장 자주 나온다.
- 누수는 성능을 “조금”이 아니라 “다른 게임”으로 바꾼다. 가장 먼저 제거해야 한다.

### (b) 위험/부작용
- 누수 제거 시 **성과가 급락**할 수 있음(정상).
- 과거 결과와 재현성이 깨지면서 “원래 맞던 것”처럼 보이던 가설이 폐기될 수 있음(정상).

### (c) 최소 실험 2~3개 (→ **Exp1**로 통합 실행)
- **Exp1-A (Asof/Lag Sentinel)**: 모든 feature join을 “결정시점 T” 기준 **asof join + 최소 1bar lag** 강제. forward-fill 최대 허용 길이 제한.
- **Exp1-B (Earnings/News Timing Guard)**: 실적/가이던스/이벤트성 feature가 있다면 **발표시간 이후에만 반영**되도록 타임스탬프 규칙 강제(장전/장후/장중).
- **Exp1-C (Corp Action Integrity)**: split/dividend adjustment가 가격/거래량/펀더멘털에 섞일 때 “미래 조정값”이 들어오지 않도록 점검(특히 adj close 사용 방식 고정).

### (d) PASS 조건
- (필수) **Leakage test 0건**: 미래시점 참조/동일봉 사용/잘못된 fill 감지 0.
- (성능 게이트) lockbox_mean이 champion 대비 **-0.10 이내 하락**이면 “통과”(누수 제거는 성능 하락이 있어도 합리 범위면 OK).  
  + 추가로 **worst_mdd ≤ -0.10 악화 금지**.

# TOP2) 과최적화 방지(검증 구조/선택편향) — “tuning ↔ lockbox 갭 제어”
### (a) 왜 필요한지
- tuning_mean과 lockbox_mean이 둘 다 높은데, **선정 절차가 조금만 잘못돼도** (여러 후보 중 최고만 선택) lockbox도 “우연히” 좋아 보일 수 있다.
- 특히 자동 루프(48h)에서는 **선정 편향**이 누적되기 쉬움.

### (b) 위험/부작용
- purged CV/embargo 적용 시 탐색 속도 저하.
- 기존 챔피언/후보의 상대 순위가 바뀔 수 있음.

### (c) 최소 실험 2~3개 (→ **Exp5**로 통합 실행)
- **Exp5-A (Purged K-Fold + Embargo)**: 이벤트/리밸런싱 윈도우를 고려해 fold 경계 누수 차단(엠바고 구간 적용).
- **Exp5-B (Selection Guardrail)**: “후보를 많이 뽑고 최고만 채택”을 제한 → 후보 수/시도 수 대비 기대 유의성 보정(간단히는 **동일 seed 다회 재현성** 게이트).
- **Exp5-C (Stability Metric 추가)**: tuning 성능이 아니라 **fold별 분산/최악 fold** 기반으로 1차 컷.

### (d) PASS 조건
- **tuning_mean - lockbox_mean 갭**이 champion 대비 **개선(축소)** 또는 최소 **악화 금지(+0.05 이내)**.
- lockbox_min이 **0 이상 유지**(지금 후보가 lockbox_min 0.334로 매우 좋음 → 이 특성을 보존하는 게 핵심).

# TOP3) 서바이버십/유니버스 편향(미국 Tech+Healthcare, 8~14종목) — “point-in-time 고정”
### (a) 왜 필요한지
- 8~14개 소수 종목에서 서바이버십 편향은 치명적이다.  
  “지금까지 살아남은 우량 Tech/HC”만 쓰면 **과거도 우량만 있었던 것처럼** 착시가 난다.
- 또한 리밸런싱 시점의 유니버스가 흔들리면 모델이 “유니버스 변화”를 알파로 착각한다.

### (b) 위험/부작용
- 과거에 존재했지만 현재 없는 티커 포함 시 데이터 품질 이슈(결측/거래정지/합병) 증가.
- 백테스트 처리(상장폐지/거래불능)의 규칙이 성과에 영향을 줌.

### (c) 최소 실험 2~3개 (→ **Exp2**로 통합 실행)
- **Exp2-A (Point-in-time Universe Snapshot)**: 결정시점 T에 존재/거래가능한 종목만 포함, 다음 리밸런싱까지 고정.
- **Exp2-B (Delist/Corp Event Handling)**: 상장폐지·인수합병·거래정지 시 **강제 현금화/대체 규칙**을 명시적으로 구현(운영 규칙으로 고정).
- **Exp2-C (Sector Constraint Enforcer)**: GICS/NAICS 기준으로 **Tech+Healthcare만**, 그리고 포트폴리오 종목 수 **8~14 강제**(빈 슬롯은 현금).

### (d) PASS 조건
- 유니버스 스냅샷 적용 후에도 lockbox_mean이 champion 대비 **-0.10 이내**.
- “상장폐지 이벤트 구간”에서 **비정상 급등락(가격 0/무한 수익률)** 같은 데이터 아티팩트 0건.

# TOP4) 비용/슬리피지 미반영 + 회전율 통제 — “순익(net)으로만 평가”
### (a) 왜 필요한지
- 소수 종목/자주 바꾸는 전략은 비용에 취약하다.  
- 현재 지표만 보면 비용 반영 여부가 명시되어 있지 않으므로, **gross 성과가 좋아도 실전(net)이 망가질** 가능성을 먼저 제거해야 한다.

### (b) 위험/부작용
- 비용을 넣으면 성능이 떨어짐(정상).
- 비용 모델이 과보수적이면 알파를 과도하게 억제할 수 있음.

### (c) 최소 실험 2~3개 (→ **Exp3**로 통합 실행)
- **Exp3-A (Broker+Spread+Slippage 모델 고정)**: 거래대금 대비 슬리피지(예: k * ADV fraction) + 고정 커미션을 net PnL에 반영.
- **Exp3-B (Turnover Penalty/Constraint)**: 목적함수에 turnover 패널티 추가 또는 리밸런싱 시 변경폭 제한(포지션 델타 캡).
- **Exp3-C (Execution Timing Stress)**: “close 체결” 가정만 쓰지 말고 **next open/ VWAP 근사**로 한 번 더 재채점.

### (d) PASS 조건
- **net 기준** lockbox_mean이 champion 대비 **개선(≥ +0.05)** 또는 최소 동급(±0.00) 유지하면서
- worst_mdd가 **-0.09보다 악화 금지**(현재 챔피언 worst_mdd -0.0902).

# TOP5) 레짐/리스크 오버레이(ETF는 관측만) + 운영 리스크(48h 자동 루프 안정화)
### (a) 왜 필요한지
- 현재 후보는 lockbox_min이 양수로 매우 좋지만, 실전에서는 “특정 레짐에서만 강한 구조”가 숨어 있을 수 있다.
- ETF는 거래 금지지만, **레짐 감지 지표**로 쓰면 Tail 방어에 도움된다.
- 48시간 자동 루프에서는 “성능”보다 먼저 **재현성/중단 내성/락박스 무결성**이 중요하다.

### (b) 위험/부작용
- 오버레이가 과도하면 수익 상단을 깎음.
- 운영 안전장치가 너무 엄격하면 실험 속도가 떨어짐.

### (c) 최소 실험 2~3개 (→ **Exp4**로 통합 실행, 운영은 Gate로 포함)
- **Exp4-A (ETF Regime Indicator, non-traded)**: 관측지표로만 사용  
  - 예: `QQQ / XLV` 모멘텀(Tech risk-on/off)  
  - `XBI` 변동성/드로우다운(바이오 리스크)  
  - `TLT` 모멘텀(금리 민감 레짐)  
  → 레짐에 따라 **포지션 총노출/리스크 예산**만 조절(종목 선택 로직은 유지).
- **Exp4-B (Tail Gate Overlay)**: 레짐 지표가 위험 신호면 **현금 비중 확대 / 포지션 수 축소(8~14 범위 내)**.
- **Exp4-C (Ops Hardening Gate)**: 자동 루프에서  
  - seed 고정, 데이터 버전 해시, 결과물 아카이빙  
  - lockbox 접근은 read-only, 후보 선정 로그/재현 로그 강제 저장

### (d) PASS 조건
- worst_mdd가 champion 대비 **개선(>-0.0902)** 또는 최소 **-0.09 유지**, 동시에 lockbox_mean **-0.05 이내 하락**까지만 허용(방어 목적).
- 48h 반복 실행 시 **동일 입력 → 동일 출력(해시 일치)** 100%.

## 48시간 자동 루프용: **실행 가능한 Patch/실험 5개** (정의 → 게이트 → 기대 관측치)

2) **Exp5: Purged CV + Selection Guardrails**
- (1) 실험 정의: purged k-fold + embargo + 안정성 지표로 후보 컷
- (2) 게이트: tuning-lockbox 갭 악화 금지(+0.05 이내), lockbox_min ≥ 0 유지
- (3) 기대 관측치: 후보 간 서열이 바뀌어도 “재현 가능한 상위권”이 좁혀짐

3) **Exp2: Point-in-time Universe + Delist Handling**

4) **Exp3: Net Cost Model + Turnover Control**
- (1) 실험 정의: 슬리피지/스프레드/커미션 + 회전율 페널티 + 체결시점 스트레스

- (3) 기대 관측치: gross는 떨어져도 net이 안정화, turnover가 눈에 띄게 감소

- (2) 게이트: worst_mdd 개선 또는 -0.09 유지, 재현성 100%
- (3) 기대 관측치: 극단 구간의 손실 꼬리 감소(특히 worst_mdd/lockbox_min 방어)

# 성능이 안 움직일 때(plateau) 원인 분해 아이디어 — 트리거/적용/노출/비용/레짐
아래 순서대로 “관측 지표를 분리”해서 병목을 고정밀로 찾는 쪽으로 진행하라.

## 1) Trigger(신호 자체) 문제인지?
- **관측**: 종목별/일별 IC(스피어만) 분포, IC의 레짐별 분해(금리상승/하락, 변동성 상/하)
- **트리거 고장 징후**: IC 평균이 0 근처인데 백테스트만 좋음 → 누수/선정편향 가능성 우선

## 2) Application(언제/어떻게 적용) 문제인지?
- **관측**: “신호 생성 시점 → 주문 체결 시점” 지연별 성능(0, +1 bar, next open)
- **적용 고장 징후**: close 가정에서만 좋고 next open에서 붕괴 → 타이밍 누수/체결 가정 과대

## 3) Exposure(포지션 구성/제약) 문제인지?
- **관측**: 섹터(Tech/HC 내부 서브섹터), 단일종목 비중 상한, 8~14 종목 충족률, 현금비중
- **노출 고장 징후**: 성과가 사실상 1~2개 종목에 의해 좌우 → 집중 리스크/서바이버십 의심

## 4) Cost(비용/회전율) 문제인지?
- **관측**: turnover, 거래대금/ADV 비율, 비용 전/후 성과 갭, 슬리피지 민감도
- **비용 고장 징후**: gross는 개선되는데 net이 정체 → turnover 페널티/리밸런싱 빈도/체결가정부터 고정

## 5) Regime(시장 상태 의존) 문제인지?
- **관측**: QQQ/XLV, XBI, TLT 상태별 성과 테이블 + worst_mdd가 발생한 레짐 태깅
- **레짐 고장 징후**: 특정 레짐에서만 알파, 반대 레짐에서 tail 손실 → Exp4 오버레이로 방어 후 재측정
