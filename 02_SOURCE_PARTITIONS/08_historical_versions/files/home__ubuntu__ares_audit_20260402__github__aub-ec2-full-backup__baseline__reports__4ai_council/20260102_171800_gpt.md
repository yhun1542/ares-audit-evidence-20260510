## 다음 24~48시간 TOP5 우선순위 (코드/아키텍처/전략) — **명령형 체크리스트**
(누수/과최적화/서바이버십/비용 미반영/운영 리스크를 최우선으로 점검)

---

### 1) **운영/재현성 리스크 제거 (로그/아티팩트/지표 불일치 즉시 해소)**
**왜 필요한지**
- 현재 상태에서 `file: (empty)`, `lane_hash/run_hash: None`, `worst_mdd: None` → 챔피언이 “무엇인지/어떻게 나왔는지” 재현 불가.
- `rebalance_pinpoint`가 `--base-log` 누락 + `rebalance.csv`/`jsonl` 파싱 실패 → **48시간 자동 루프의 핵심 관측(리밸런스/턴오버/비용)**이 증발.
- `Champion OOS Mean`이 3.32 vs diagnoser 2.63 → **지표 정의/집계 불일치** 가능(과최적화/누수보다 먼저 터지는 운영 결함).

**위험/부작용**
- 로깅/스키마 강제 후 과거 실험 일부가 “불합격” 처리되어 단기적으로 후보가 줄어듦.
- 지표 정의를 통일하면 챔피언 성능이 “하락”해 보일 수 있음(사실상 정정).

**연계 최소 실험(공유됨)**: **E1, E2**
- (아래 “실행 패치/실험 5개” 참조)

**PASS 조건**
- `no_delta_diagnoser`, `rebalance_pinpoint`가 **에러 없이 끝나고** 동일 실험에 대해 핵심 지표가 **±1% 이내로 일치**.
- 모든 런에서 `file/lane_hash/run_hash/worst_mdd`가 **필수 필드로 채워짐**(NULL 금지).
- 리밸런스 로그(거래/체결/턴오버/비용)가 **항상 생성**되고 파서가 **항상 읽음**.

### 2) **Degenerate folds(교차검증 붕괴) 제거 = 과최적화/누수 의심 1순위**
**왜 필요한지**
- `degenerate_folds: [1,2,3,8]` → 다수 폴드가 무효/빈 거래/동일 포지션/노출 0 등으로 붕괴했을 확률이 높음.
- 폴드 붕괴는 OOS 평균을 “좋게” 만들거나(거래 없음) “임의로” 흔들어 **No-Delta/불안정**을 유발.

**위험/부작용**
- 폴드 건강성 강제(최소 거래수/최소 노출 등) 후 성능 하락 가능.
- 데이터가 부족한 구간이 제외되면 표본이 줄어 분산 증가.

**연계 최소 실험(공유됨)**: **E2, E4**
- (아래 “실행 패치/실험 5개” 참조)

**PASS 조건**
- `degenerate_folds`가 **빈 배열**.
- 각 폴드별 `trades>0`, `avg_gross_exposure>0.2` 같은 **헬스 체크 통과율 100%**.
- OOS 분산(폴드 간 표준편차)이 **이전 대비 감소**(또는 동일 수준 유지).

---

### 3) **비용/슬리피지/턴오버 미반영 제거 (실거래 성능과 백테스트 괴리 차단)**
**왜 필요한지**
- rebalance 로그 부재는 비용 추정 불가로 직결.
- Tech/Healthcare 단일주 8~14개 운용은 리밸런스 잦으면 비용 민감(특히 고변동 종목).
- “성능이 안 움직이는” 경우, 실제로는 비용이 알파를 먹고 있을 수 있음(특히 최적화가 미세 개선만 만들 때).

**위험/부작용**
- 비용 모델 적용 후 과거 성능이 크게 악화될 수 있음(현실 반영).
- 턴오버 캡은 알파를 일부 희생할 수 있음.

**연계 최소 실험(공유됨)**: **E3, E1**
- (아래 “실행 패치/실험 5개” 참조)

**PASS 조건**
- post-cost 성능 지표가 **pre-cost 대비 합리적 감소폭**(예: 연 -1~3%p 수준) 안에서 유지되고, 전략 비교 순위가 안정적.
- 연환산 턴오버가 설정 상한 내(예: **연 3~8회전** 등)로 들어옴.
- 비용/슬리피지 항목이 리밸런스 로그에서 **항상 관측**됨.

---

### 4) **서바이버십/데이터 누수/룩어헤드 방지 (Tech+Healthcare 단일주에서 특히 치명적)**
**왜 필요한지**
- 유니버스가 “현재 생존자 기반”이면 Healthcare(바이오)에서 상장폐지/인수/합병 편향이 커짐.
- 펀더멘털/이벤트 데이터가 리포트 날짜 기준으로 즉시 반영되면 룩어헤드가 발생.
- No-Delta는 “모델이 이미 누수로 포화” 또는 “누수 제거 시 모두 무력화” 양쪽 신호일 수 있음 → 먼저 판별해야 함.

**위험/부작용**
- 누수 제거/포인트-인-타임 적용 시 성능 급락 가능(그게 정상일 수 있음).
- 데이터 공급/스토리지 비용 증가.

**연계 최소 실험(공유됨)**: **E4, E2**
- (아래 “실행 패치/실험 5개” 참조)

**PASS 조건**
- **누수 방지 버전**이 기존 대비 성능이 다소 하락하더라도, 폴드 붕괴 없이 “거래/노출/턴오버”가 정상적으로 형성.
- 룩어헤드 테스트(shift/lag)에서 성능이 비정상적으로 유지되지 않음(= “진짜 알파”일 가능성 증가).

### 5) **전략 레벨: 노출/보유종목수/섹터 제약(Tech+Healthcare 8~14) + ETF는 ‘관측’만**
**왜 필요한지**
- 현재 `exposure_max ~0.84`, `exposure_min 0.0` → 어떤 구간은 완전 관망(0 노출)일 수 있고, 이게 폴드 붕괴/No-Delta를 만들 수 있음.
- “미국주식 only, Tech+Healthcare 중심 8~14개”를 **엔진에서 강제**해야 실험이 누적될수록 규칙이 흐려지지 않음.
- ETF는 매매 제외 조건이므로 **레짐 관측 지표(필터/게이트)**로만 사용.

**위험/부작용**
- 제약이 강해지면 최적화 자유도가 줄어 OOS 평균이 소폭 하락 가능.
- 레짐 필터가 과도하면 거래 기회 감소(노출 0 빈발).

**연계 최소 실험(공유됨)**: **E5, E3**
- (아래 “실행 패치/실험 5개” 참조)

**PASS 조건**
- 매 리밸런스에서 보유 종목 수가 **8~14 유지**(결측 시 대체 규칙 명시).
- Tech+Healthcare 비중이 **정책 범위 내**(예: 합계 80%+).
- gross/net exposure가 **정의된 범위 유지**(예: gross 0.3~0.9, net -0.2~0.8 등).

## 실행 가능한 Patch/실험 (총 5개만 실행) — 48시간 자동 루프 형태
아래 5개만 “유니크 실험”으로 실행하고, 위 TOP5 제안에는 **이 5개를 재사용**하여 케이스 폭발을 막음.

---

### **E1) Logging/Schema Hardening (운영 안정화 패치)**
1) **실험 정의**
- 출력 아티팩트 스키마를 강제:
  - champion JSON에 `file, lane_hash, run_hash, worst_mdd, exposure stats, turnover, cost summary` 필수화
  - 리밸런스 로그를 **항상 JSONL**로 저장(한 줄=한 리밸런스, 체결/비용/슬리피지 포함)
- `aub_rebalance_pinpoint.py`가 현재 포맷(JSONL)만으로도 동작하게 파서 수정(“csv/jsonl 둘 다”가 아니라 “표준 1개”로 수렴)

2) **게이트 (FAIL FAST)**
- 실험 시작 시: 이전 런 대비 필수 필드 누락 시 즉시 실패
- 파서: 샘플 로그 10줄을 읽어 비용/턴오버/보유수 필드가 없으면 실패

3) **기대 관측치**
- `rebalance_pinpoint.md`가 “No rebalance data” 없이 생성
- OOS mean 등 핵심 지표가 diagnoser/runner 간 **수치 불일치가 사라짐**

---

### **E2) Fold Health + Purged Walk-Forward (degenerate fold 제거)**
1) **실험 정의**
- Walk-forward를 “purged + embargo”로 전환(룩어헤드 방지)
- 각 폴드에 **헬스 체크** 강제:
  - 최소 거래 횟수, 최소 평균 노출, 최소 리밸런스 횟수
  - 헬스 미달 폴드는 점수 계산에서 제외가 아니라 **실험 자체 FAIL**로 처리(조용히 평균내지 않기)

2) **게이트**
- `degenerate_folds == []`
- 폴드별 `avg_gross_exposure >= 0.2` & `rebalance_count >= N`(N은 현재 설정값 기반) 미충족 시 FAIL

3) **기대 관측치**
- OOS 평균이 단기 하락할 수 있으나, 실험 간 분산이 감소하고 “No-Delta”가 줄어듦(진짜 변화가 보이기 시작)

---

### **E3) Cost Model + Turnover Cap (비용/운영 현실화)**
1) **실험 정의**
- 거래비용을 백테스트 내재화:
  - 고정 bps + 변동(일중 변동성/스프레드 근사) 슬리피지
  - 리밸런스 시 turnover 기반 비용 자동 계산/로그
- turnover cap(예: 일/주/월 단위 상한) + 초과 시 리밸런스 스킵/완화 로직

2) **게이트**
- 비용이 리밸런스 로그에 항상 기록(누락 시 FAIL)
- 연환산 turnover가 상한을 초과하면 FAIL(또는 페널티 점수로 강등)

3) **기대 관측치**
- “미세한 알파 개선” 후보들이 비용 반영 후 사라지고, **소수의 견고한 후보만 남음**
- 성능 변화가 없던 구간에서 “비용 드래그”가 수치로 드러남

---

### **E4) Survivorship/Lookahead Audit Run (데이터 편향 제거 시험)**
1) **실험 정의**
- 유니버스를 **포인트-인-타임**으로 고정(당시 존재 종목 + 상폐 반영)
- 펀더멘털/이벤트/리밸런스 입력을 최소 1~2 영업일 lag 적용(룩어헤드 제거)
- “누수 탐지 A/B”: (기존 입력) vs (lagged 입력) 동일 설정으로 OOS 비교

2) **게이트**
- lag 적용 후에도 폴드 헬스 체크(E2) 통과 못하면 FAIL
- 성능이 lag에도 비정상적으로 동일(=누수 의심 지속)이면 FAIL 플래그

3) **기대 관측치**
- 정상이라면 lag 적용 시 성능 일부 하락 + 대신 **안정성 지표(폴드 일관성)** 개선
- 만약 성능이 거의 안 변하면: 신호가 가격 기반이거나(정상) / 다른 경로 누수(비정상)로 범위가 좁혀짐

---

### **E5) Portfolio Constraints Patch (8~14 종목, Tech+Healthcare 강제 + ETF는 레짐 관측만)**
1) **실험 정의**
- 종목 선택/리밸런스 레이어에 제약 강제:
  - 보유 종목수 8~14 강제
  - Tech+Healthcare(예: GICS 섹터) 합계 비중 최소치 강제
  - 단일 종목 최대 비중(예: 12~18%) + 최소 비중(유령 포지션 방지)
- ETF(예: QQQ/XLK/XLV)는 **매매 금지**, 단:
  - 레짐 지표(추세/변동성)로만 사용해 노출 상한/하한을 조정(“관측→게이트”)

2) **게이트**
- 모든 날짜에 `holdings_count in [8,14]` 위반 시 FAIL
- 섹터 비중 규칙 위반 시 FAIL
- 노출이 0에 붙는 구간이 일정 비율 이상이면 FAIL(예: 10% 초과)

3) **기대 관측치**
- “노출 0”로 인한 가짜 안정성이 줄고, OOS의 의미 있는 변화가 관측됨
- 섹터 일관성으로 레짐 노이즈가 줄고 drawdown 프로파일이 안정화될 가능성

## 성능이 안 움직일 때(=No-Delta) 원인 분해 아이디어 — 트리 형태 체크리스트
아래는 “원인이 어디에 있는지”를 **트리거/적용/노출/비용/레짐**으로 강제 분해하는 실행 항목임.

### A) Trigger(신호 생성) 문제
- **명령**: 신호 시계열의 “변동성/엔트로피”를 출력하라  
  - `signal_std`, `nonzero_rate`, `rank_autocorr`, `topK 교체율`
- **판정**:
  - 신호가 거의 상수/0이면 → 특징량이 죽었거나 전처리/정규화가 과도함
  - 신호는 움직이는데 성능이 정체면 → 적용/비용/레짐으로 이동

### B) Apply(주문/리밸런스 적용) 문제
- **명령**: 신호→목표비중→체결비중 3단계를 모두 로깅하라(E1 필수)  
  - `target_weight`, `executed_weight`, `clipped_weight(제약으로 잘린 비중)`
- **판정**:
  - target은 변하는데 executed가 안 변하면 → 제약/턴오버 캡/리밸런스 빈도 문제
  - clip 비중이 크면 → 제약이 과도하거나 스케일링이 잘못됨

### C) Exposure(노출/포지션 구조) 문제
- **명령**: gross/net 노출, 롱/숏 비중, 상위 3종목 비중, 현금비중을 구간별로 분해하라  
  - 특히 `exposure_min=0` 원인을 “레짐 필터”인지 “폴드 붕괴”인지 분리
- **판정**:
  - gross가 장기간 낮으면 → 전략이 사실상 관망(알파가 있어도 관측 불가)
  - 상위 종목 쏠림이 심하면 → 분산 부족으로 성능 변동이 “운”에 가려짐

### D) Cost(비용) 문제
- **명령**: 알파 기여를 “pre-cost PnL”과 “cost drag”로 분해하라(E3)  
  - turnover×bps, 슬리피지 추정치, 체결 실패/부분체결까지 기록
- **판정**:
  - pre-cost는 개선되는데 post-cost가 정체면 → 턴오버/슬리피지 최적화로 방향 확정
  - cost가 항상 0이면 → 비용 로깅/모델이 죽어있음(운영 결함)

### E) Regime(시장 국면) 문제
- **명령**: 관측용 ETF(QQQ/XLK/XLV 등)로 레짐을 버킷팅하라(매매 금지)  
  - 예: 추세(상/하), 변동성(상/중/하) 6분면으로 OOS를 분해
- **판정**:
  - 특정 레짐에서만 유효하면 → 레짐 게이트(노출 상한/하한)로 성능 “움직임”을 만들 수 있음
  - 모든 레짐에서 평평하면 → 신호 자체/데이터 누수/비용 중 하나로 회귀

## 48시간 루프 실행 순서(권장)
1) **E1 → E2** (운영/폴드 붕괴부터 제거: 관측 가능 상태 만들기)  
2) **E3** (비용 현실화로 가짜 후보 제거)  
3) **E4** (누수/서바이버십 최종 판정)  
4) **E5** (Tech+Healthcare 8~14 강제 + 노출 안정화로 전략 형태 고정)

이 순서로 돌리면 “성능이 안 움직이는” 상태가 **관측 불가(로그/폴드 붕괴)**인지, **현실화(비용/누수 제거)로 알파가 사라진 것**인지, **전략 제약/노출 설계 문제**인지 48시간 내에 갈라낼 수 있음.
