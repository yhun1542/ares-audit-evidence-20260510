아래는 **24~48시간 내 자동 루프(48h)로 굴릴 수 있는 TOP5 우선순위 patch**입니다. 우선순위는 **누수/과최적화/서바이버십/비용 미반영/운영 리스크**를 먼저 밟습니다. (미국주식 only, Tech+Healthcare 중심, **8~14 종목**, ETF는 **관측지표로만**)

## TOP5 (24~48h) 우선순위 패치

### 1) [DATA] 누수(lookahead) + CV degenerate_folds(1,2,3,8) 즉시 제거
**(a) 왜 필요한지**
- 현재 champion에 **degenerate_folds가 다수** → 일부 폴드가 비정상(학습/검증 경계 깨짐, 표본 0, 라벨 누수, 시계열 섞임)일 확률이 큼.
- oos_mean이 높게 보여도(3.32) **누수/폴드 붕괴면 의미 없음**. 가장 먼저 “진짜 OOS”인지 확정해야 함.

**(b) 위험/부작용**
- 누수 제거 후 성능이 급락할 수 있음(정상).
- 데이터 정렬/시차 강제 시 트리거가 줄어 거래 빈도가 감소할 수 있음.

**(c) 최소 실험 2~3개 (48h 루프 형태)**
- **실험 정의**
  1. **Purged Walk-Forward + Embargo 적용**: 라벨 horizon(예: 1~5D)만큼 purge, embargo(예: 5~10 bar) 추가.
  2. **Feature timestamp 강제 shift**: 모든 피처를 “t 시점에서 알 수 있는 값”만 남기고 **최소 1 bar 지연(shift=1)** 버전과 기존 버전을 A/B.
  3. **Leakage unit test 배치**:  
     - (i) 미래값 참조 금지(특정 컬럼/리샘플링 후 forward-fill 확인)  
     - (ii) train/val 기간 겹침 0 보장  
     - (iii) 라벨 계산에 사용된 price series가 피처에 섞이지 않았는지 검사
- **게이트(자동 중단 조건)**
  - degenerate_folds **0** 아니면 FAIL.
  - train/val time overlap 발생 시 즉시 FAIL.
  - shift 적용 후 성능이 “비정상적으로” 개선(예: oos_mean 급상승)하면 누수 의심으로 FAIL(리뷰 큐로 격리).
- **기대 관측치**
  - oos_mean은 보통 하락/안정화. 대신 **oos_min 개선** 또는 변동성 감소가 나타나야 정상.
  - 폴드별 성능 분산 감소(과최적화 신호 감소).

**(d) PASS 조건**
- degenerate_folds = **[]**
- 각 폴드 validation 구간의 샘플 수/거래 수가 최소 기준 충족(예: fold당 거래 N_min 이상)
- shift=1 버전이 baseline 대비 성능이 큰 폭으로 “튀지” 않고(누수 제거의 일관성), oos_min이 악화되지 않음

---

### 2) [COST/REALISM] 비용(스프레드/슬리피지/지연) 미반영 제거 + 과도 회전(턴오버) 게이트
**(a) 왜 필요한지**
- oos_mean이 높아도 **비용 반영 전이면 허상**일 가능성이 큼.
- Tech/HC 대형주는 낮아 보이지만, **고빈도 리밸런스/시그널 뒤집힘**이면 비용이 성과를 잠식.

**(b) 위험/부작용**
- 거래가 줄며 성과가 감소할 수 있음(정상).
- 지나친 turnover cap은 알파를 “죽일” 수 있음.

**(c) 최소 실험 2~3개**
- **실험 정의**
  1. **비용 스윕(cost sweep)**: (낙관/기준/보수) 3단계  
     - 예: bps = 2/5/10 + 슬리피지(체결가 불리) + 고정수수료(있다면)
  2. **1-bar execution delay(신호→다음 bar 체결)** 강제 vs 즉시체결 A/B
  3. **Turnover cap / trade-noise 필터**:  
     - 포지션 변경이 임계값(예: 10~20% notional) 미만이면 거래 생략  
     - 또는 신호 강도 상위 q%만 실행
- **게이트**
  - “보수 비용”에서 net 성과가 음수면 FAIL(전략 구조 재검토로 라우팅)
  - turnover가 기준 상한(예: 월 300~500% 등 내부 기준) 초과 시 FAIL
- **기대 관측치**
  - gross 성과는 유지되면서 **net이 덜 무너지는 구조**가 남아야 함.
  - 1-bar delay에서 성과가 크게 붕괴하면 “현실 체결 불가/과최적화 신호” 가능성 상승.

**(d) PASS 조건**
- 보수 비용에서도 oos_mean이 기준 이상 유지(내부 기준치) + oos_min이 과도 악화 없음
- delay 적용에도 성과가 “완전 붕괴”하지 않음(신호의 시간 정합성 확보)

### 3) [OPS] 재현성/메타데이터(run_hash/lane_hash/file=None) 즉시 복구 (운영 리스크 제거)
**(a) 왜 필요한지**
- 현재 champion이 **file 없음, lane_hash/run_hash 없음, worst_mdd None** → 산출물이 추적 불가/재현 불가.  
- 자동 루프에서는 “성능”보다 먼저 **산출물 신뢰성**이 생명.

**(b) 위험/부작용**
- 초기엔 개발 작업량이 늘고, 실험 속도가 잠시 느려짐.
- 로그/아티팩트 저장으로 비용(스토리지/IO) 증가.

**(c) 최소 실험 2~3개**
- **실험 정의**
  1. **Deterministic build**: seed 고정 + 데이터 스냅샷 해시 + 피처코드 버전 해시를 run_hash로 강제
  2. **Artifact contract**: 각 실행마다 (config, universe, 기간, 비용모델, 결과 요약, equity curve, trades) 저장 없으면 “실패” 처리
  3. **Worst MDD 계산/저장 강제**: None이면 파이프라인 FAIL로 처리
- **게이트**
  - run_hash/lane_hash/file 중 하나라도 None이면 FAIL
  - 동일 config 재실행 시 핵심 지표(거래수, oos_mean 등) 불일치하면 FAIL
- **기대 관측치**
  - 성능 변화보다 **결과의 안정적 재현**이 먼저 나타남.
  - “원인불명 성능 변동”이 급감.

**(d) PASS 조건**
- 동일 커밋+데이터 스냅샷에서 결과가 반복 재현됨
- worst_mdd가 항상 계산되어 리포트에 포함됨

### 4) [STRATEGY] 레짐(리스크온/오프) 게이트: ETF는 지표로만 사용
**(a) 왜 필요한지**
- Tech/Healthcare는 국면에 따라 베타/금리 민감도가 바뀜.  
- 레짐 필터 없이 단일 시그널이면 **oos_min(바닥 성과)**가 깨지기 쉬움.

**(b) 위험/부작용**
- 필터가 과도하면 거래 기회가 줄어 성과가 낮아질 수 있음.
- 레짐 정의 자체가 과최적화 포인트가 될 수 있음(단순하게 유지 필요).

**(c) 최소 실험 2~3개**
- **실험 정의**
  1. **리스크오프 차단 게이트**(매매는 개별주만):  
     - 관측지표: SPY 추세(예: 50d<200d), VIX 레벨/변화, (XLK/XLV 상대강도)  
     - 게이트 ON일 때만 신규 진입/레버리지 확대 허용
  2. **변동성 타겟팅 포지션 사이징**: 종목별/포트폴리오 변동성에 따라 노출 자동 축소/확대
  3. **드로우다운 기반 “킬스위치”**: rolling DD가 임계 초과 시 현금화/노출 축소(일시적)
- **게이트**
  - 필터 추가 후 거래수가 너무 급감(예: 기존 대비 -70% 이상)하면 FAIL(필터 과도)
  - oos_min이 개선되지 않거나 worst_mdd 악화 시 FAIL
- **기대 관측치**
  - 평균(oos_mean)보다 **하방(oos_min, MDD)**이 먼저 개선.
  - 레짐오프 구간에서 불필요한 트레이드 감소 → 비용/슬리피지도 동반 개선.

**(d) PASS 조건**
- oos_min 개선 + worst_mdd 감소(또는 안정화)
- 비용 반영 net에서 성과 유지

### 5) [PORTFOLIO] 8~14 종목(Tech+Healthcare) 고정 유니버스 + 집중도/노출 하한 설정
**(a) 왜 필요한지**
- exposure_min=0.0, max=0.84 → 종종 “아무 것도 안 들거나” 특정 시점 “과집중” 가능.
- 자동 루프에서 종목 선택이 흔들리면 서바이버십/룩업(티커 변경) 리스크가 커짐.

**(b) 위험/부작용**
- 유니버스 고정은 기회 손실을 유발할 수 있음.
- 강제 분산은 단일 종목 알파가 강할 때 성과를 희석할 수 있음.

**(c) 최소 실험 2~3개**
- **실험 정의**
  1. **고정 유니버스(12종)로 표준화**(미국, Tech+HC, 대형/유동성):  
     - Tech: AAPL, MSFT, NVDA, GOOGL, AMZN, META  
     - HC: UNH, LLY, JNJ, ABBV, MRK, ISRG  
     (이 12개만 매매, ETF는 지표로만)
  2. **포트폴리오 제약 추가**:  
     - 단일 종목 max weight(예: 15~20%)  
     - 최소 보유 종목 수(예: ≥8) 또는 최소 분산 조건  
  3. **노출 하한/상한**: exposure를 [min,max]로 관리(예: 0.2~0.9) + 레짐 게이트와 결합
- **게이트**
  - 제약 추가 후 oos_mean 급락 + oos_min도 악화면 FAIL(제약 과도)
  - 실제 체결 가능한 거래수/유동성 기준 위반 시 FAIL
- **기대 관측치**
  - 집중도 하락 → MDD 및 oos_min 안정화.
  - 종목/구간 바뀜에 따른 “성능 불연속”이 줄어듦.

**(d) PASS 조건**
- oos_min/ worst_mdd 개선 또는 변동성 감소
- 노출이 의도 범위 내로 유지되고(0 근처 드랍 감소) 결과 재현성 유지

# 성능이 안 움직일 때 “원인 분해” 체크리스트 (트리거/적용/노출/비용/레짐)

아래를 **한 번에 다 바꾸지 말고**, 각 축을 분리해 “어디서 죽는지”를 로그로 고정하세요.

## A) 트리거(신호 발생) 문제
- **명령형 체크**
  - 신호 발생 횟수(일/주) 시계열을 저장하고 급감/급증 구간을 표시하라
  - 피처 분포 drift(평균/분산/상관)와 라벨 분포를 폴드별로 리포트하라
- **증상 → 원인**
  - 트레이드가 거의 없음 → 게이트 과도 / 조건식 버그 / 데이터 결측 증가
  - 특정 시점부터 신호 폭주 → 피처 스케일 깨짐 / 리샘플링/정렬 문제 / 분모 0

## B) 적용(체결/딜레이/슬리피지) 문제
- **명령형 체크**
  - “신호시점 가격” vs “체결가격” 차이를 항상 기록하라(슬리피지 모델 포함)
  - 0-delay와 1-bar delay 성과 차이를 상시 비교하라
- **증상 → 원인**
  - 1-bar delay에서 성과 붕괴 → 미세 타이밍 알파(현실성 낮음) / 누수

## C) 노출(포지션 사이징/집중/상관) 문제
- **명령형 체크**
  - exposure time-series, 상위 종목 weight, 유효 보유종목 수를 매 실행 저장하라
  - 포트폴리오 상관/베타(대비 SPY) 추정치를 리포트하라
- **증상 → 원인**
  - exposure가 0 근처로 잦게 떨어짐 → 게이트/제약 충돌 / 신호 품질 부족
  - 특정 종목이 수익 대부분 → 집중 리스크, OOS에서 붕괴 가능

## D) 비용(턴오버/스프레드) 문제
- **명령형 체크**
  - gross→net 브릿지(거래비용/슬리피지/수수료)를 항목별로 저장하라
  - turnover와 net 성과의 상관을 측정하라
- **증상 → 원인**
  - gross는 좋은데 net이 0 → 과도 회전 / 비용 모델 과소추정

## E) 레짐(시장국면) 문제
- **명령형 체크**
  - 레짐 지표(SPY 추세, VIX, XLK/XLV 상대강도 등) 구간별 성과를 분해하라
  - 레짐별 confusion: “레짐오프인데 진입한 거래” 비율을 계산하라
- **증상 → 원인**
  - 특정 하락장/고변동 구간에서만 깨짐 → 레짐 게이트 부재/약함

## 24~48h 실행 순서(명령형)
1. **Patch#1(누수+폴드)부터 즉시 적용**하고 degenerate_folds=0을 만들라.  
2. **Patch#2(비용/딜레이/턴오버)로 net 현실성**을 확정하라.  
3. **Patch#3(재현성/아티팩트 계약)**으로 run_hash/lane_hash/file/worst_mdd None을 전부 금지하라.  
4. 그 다음에만 **Patch#4(레짐 게이트)**를 붙여 oos_min/MDD를 깎아라.  
5. 마지막으로 **Patch#5(유니버스/제약/노출 범위)**로 운영 안정성을 고정하라.

원칙: 위 5개를 동시에 섞지 말고, **각 patch는 48h 루프에서 “게이트 통과 여부”로 자동 승격/폐기**되게 구성하라.
