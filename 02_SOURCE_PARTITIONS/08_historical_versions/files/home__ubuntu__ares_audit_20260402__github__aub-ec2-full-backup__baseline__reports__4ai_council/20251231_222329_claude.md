## 🔴 PRIORITY 1: 성능 정체 원인 분해

### 왜 필요한지
- Champion/Candidate 차이 < 0.15% → 실험이 노이즈 수준
- 변경이 실제로 적용되는지, 적용돼도 노출이 없는지 진단 필요

### 원인 분해 체크리스트 (순서대로 점검)
```
□ [1] TRIGGER: 신호가 발생하는가?
    → 최근 252일 중 각 모듈별 signal firing rate 측정
    
□ [2] APPLICATION: 신호가 포지션에 반영되는가?
    → signal→position 전환율 (sizing 단에서 0으로 가는 비율)
    
□ [3] EXPOSURE: 반영된 포지션이 실제 수익에 기여하는가?
    → 포지션별 contribution attribution
    
□ [4] COST: 비용이 수익을 먹고 있는가?
    → slippage/commission 추정 vs gross return 비교
    
□ [5] REGIME: 현재 구간이 전략에 불리한가?
    → VIX>25, SPY<200MA 구간 비율
```

### 최소 실험 (3개)
| ID | 실험 | 게이트 | 기대 관측치 |
|---|---|---|---|
| P1-A | `signal_firing_audit.py` - 모듈별 firing rate | 자동 | 어떤 모듈이 0% firing인지 |
| P1-B | `position_leakage.py` - sizing 단계 누수 | 자동 | kill된 신호 비율 |
| P1-C | `regime_mask.py` - high-vol 구간 수익률 | 자동 | 구간별 Sharpe 분해 |

### PASS 조건
- 3개 중 최소 1개에서 **명확한 bottleneck 식별** (firing<5% 또는 kill>50%)

## 성능 미변동 시 원인 트리 (빠른 참조)

```
성능 안 움직임
├─ 신호 미발생 (Trigger)
│   └─ 확인: firing_rate < 5%
├─ 신호 있으나 sizing=0 (Application)
│   └─ 확인: position_kill_rate > 50%
├─ 포지션 있으나 수익 無 (Exposure)
│   └─ 확인: contribution ≈ 0
├─ 수익 있으나 비용 상쇄 (Cost)
│   └─ 확인: gross - net > 2%p
└─ 전체 레짐 불리 (Regime)
    └─ 확인: VIX>25 기간 > 40%
```
