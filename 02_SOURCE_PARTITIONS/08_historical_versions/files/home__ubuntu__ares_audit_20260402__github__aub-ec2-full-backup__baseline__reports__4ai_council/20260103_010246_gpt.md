# 1) 다음 24~48시간 TOP5 우선순위 (코드/아키텍처/전략)
아래 5개는 **각각 1개의 실험(단, 2~3개 arm 포함)**으로 설계해 48시간 자동 루프에 바로 태울 수 있게 구성.

## P1. (운영) 리밸런스 로그/메트릭 재현성 패치
### (a) 왜 필요한지
- 현재 `rebalance_pinpoint`가 입력을 못 읽어 **전략 변경이 어디서 발생했는지 추적 불가**.
- `worst_mdd: None`, `lane_hash/run_hash None`이면 **챔피언/후보 비교가 불가능**(운영 사고로 직결).

### (b) 위험/부작용
- 로그 포맷을 바꾸면 과거 아카이브와 호환성 이슈.
- 메트릭 재계산으로 기존 챔피언 성능이 달라 보일 수 있음(실상은 “이제야 정확해짐”).

### (c) 최소 실험(1개 실험, 3-arm)
**실험명: LOG-INTEGRITY-001**
- Arm A: 현행 그대로(베이스라인)
- Arm B: `rebalance.csv/jsonl` **경로 자동탐색 + 포맷 검증(첫 줄 JSON/CSV 시그니처 체크)** 패치
- Arm C: `run_hash/lane_hash` 강제 생성(설정+데이터+코드 커밋 해시), `worst_mdd` 산출 강제(없으면 run fail)

### (d) PASS 조건 (게이트)
- `rebalance_pinpoint.md`가 **후보/챔피언 모두에 대해** “리밸런스 이벤트 N건, 상위 기여 요인”을 출력.
- 모든 run artifact에 `run_hash/lane_hash` 존재 + `worst_mdd` 수치 존재.
- 실패 시: **성능 비교/자동 승격을 금지**(hard gate).

**48시간 루프 형식**
- (1) 실험 정의: 위 3-arm 실행
- (2) 게이트: 로그 파싱 100% 성공 + 핵심 메트릭 non-null
- (3) 기대 관측치: “성능 무변화”여도 **원인(리밸런스/포지션 변화) 추적 가능**한 리포트 생성

## P2. (누수/과최적화) Degenerate fold 제거 + Purged Walk-Forward
### (a) 왜 필요한지
- degenerate fold는 **학습/검증 분할이 실질적으로 무의미**하거나 데이터 누락/정렬 문제가 있다는 신호.
- 누수 방지(embargo/purge) 없이 시계열 CV를 돌리면 OOS가 허상일 수 있음.

### (b) 위험/부작용
- 제대로 분할하면 성능이 내려갈 수 있음(“진짜 실력”만 남음).
- 표본 감소로 분산 증가.

### (c) 최소 실험(1개 실험, 3-arm)
**실험명: CV-FIX-002**
- Arm A: 현행 CV
- Arm B: **Purged K-Fold(lookback/label horizon 만큼 purge) + embargo** 적용
- Arm C: **Anchored Walk-Forward**(고정 학습창 누적 + 고정 검증창), fold마다 최소 샘플/거래수 미달 시 fold drop

### (d) PASS 조건
- `degenerate_folds`가 **빈 리스트**(또는 drop된 fold 명시)로 수렴.
- 각 fold에서 최소 요건 충족:  
  - 검증 구간 거래 수 ≥ X(시스템 기본값)  
  - 검증 구간 유효 일수 ≥ Y  
- OOS mean이 Arm B/C에서 Arm A 대비 급락하더라도 **“누수 제거 후 안정성”**이 우선(급락=정상 시그널일 수 있음).

**48시간 루프**
- (1) 실험 정의: 3-arm CV 재구성
- (2) 게이트: fold 유효성/거래수/기간 만족
- (3) 기대 관측치: OOS가 내려가도 **분산 감소 + min 성능의 해석 가능성 증가**

---

## P3. (서바이버십) US Tech+Healthcare 8~14종목 유니버스 “강제” + PIT(시점고정)
### (a) 왜 필요한지
- 유니버스가 흔들리면 성능 변화가 **신호가 아니라 구성 효과**가 됨.
- 서바이버십(현재 살아남은 종목만 사용)과 룩어헤드(미래 구성요소 반영)로 OOS가 부풀 가능.

### (b) 위험/부작용
- PIT 데이터(과거 구성/분류)를 제대로 못 만들면 빈 유니버스/거래 불가가 늘어날 수 있음.
- 8~14 강제는 기회 제한으로 수익률 상단을 제한할 수 있음.

### (c) 최소 실험(1개 실험, 3-arm)
**실험명: UNIV-PIT-003**
- Arm A: 현행 유니버스
- Arm B: **Tech+Healthcare만** + “항상 8~14 유지”(부족하면 현금 유지) + 최소 유동성/가격 필터
- Arm C: Arm B + **PIT 섹터 분류/상장폐지 처리**(해당 시점에 존재하지 않는 종목은 접근 불가)

### (d) PASS 조건
- 모든 리밸런스 시점에서 보유 종목 수가 **8~14** 범위를 벗어나면 run fail(하드 게이트).
- 과거 시점에 존재하지 않는 티커 접근 0건.
- 섹터 비중: Tech+Healthcare 합 100% (현금 제외).

**48시간 루프**
- (1) 실험 정의: 3-arm 유니버스 빌더 교체
- (2) 게이트: 8~14 유지, PIT 위반 0
- (3) 기대 관측치: 성능이 변하면 “유니버스 효과 vs 신호 효과” 분리 가능

## P4. (비용) 거래비용/슬리피지/임팩트/borrow 스트레스 테스트 내장
### (a) 왜 필요한지
- 비용 미반영은 OOS를 가장 쉽게 “움직이게” 만들지만, 실전에서 바로 붕괴.
- Tech/Healthcare라도 종목별 유동성 차이가 커서 **turnover 전략은 비용에 민감**.

### (b) 위험/부작용
- 비용을 넣으면 전략이 무력화될 수 있음(그게 현실).
- 보수적 비용 가정은 과도한 현금화로 기회손실.

### (c) 최소 실험(1개 실험, 3-arm)
**실험명: COST-REALISM-004**
- Arm A: 비용 0(진단용)
- Arm B: 기본 비용(commission + spread/2 + 단순 슬리피지 bps)
- Arm C: 스트레스 비용(Arm B × 2 + borrow/HTB 가정 + 임팩트 bps)

### (d) PASS 조건
- Arm B에서 OOS mean이 Arm A 대비 하락하더라도, **전략 생존** 기준:
  - 순수익(세전) 양(+) 유지 또는 시스템 기준치 이상
  - 회전율(turnover) 상한 내
  - “gross PnL - cost”에서 cost가 지배하지 않을 것(예: 비용이 gross의 일정 비율 초과 시 fail)

**48시간 루프**
- (1) 실험 정의: 3-arm 비용 민감도
- (2) 게이트: turnover/비용비중 상한
- (3) 기대 관측치: 성능 정체의 원인이 “비용에 의한 상쇄”인지 즉시 판별

## P5. (전략/운영) ETF “매매 금지” 준수 + 관측지표 기반 노출 스케일링(현금)
### (a) 왜 필요한지
- 현재 컨텍스트에 `hedge_025` 등 힌트가 있는데, **ETF 매매가 들어가면 규칙 위반**.
- 대신 ETF는 **관측지표(regime/리스크 온오프)**로만 쓰고, 포지션은 개별 종목 + 현금으로 노출 조절해야 함.

### (b) 위험/부작용
- 현금 비중 증가로 수익률 상단 제한.
- regime 필터가 과하면 “항상 꺼져있는” 전략이 되어 성능 정체.

### (c) 최소 실험(1개 실험, 3-arm)
**실험명: REGIME-CASH-005** (ETF는 지표만 사용: SPY/XLK/XLV/QQQ 등)
- Arm A: 고정 노출 상한(예: max exposure 0.85), 필터 없음
- Arm B: ETF 기반 변동성/추세 지표로 **exposure scalar(0~1)** 적용(매매는 종목만)
- Arm C: Arm B + drawdown 기반 디레버(예: 최근 N일 DD > 임계면 scalar 추가 하향)

### (d) PASS 조건
- 거래 로그에서 **ETF 주문/체결 0건**(하드 게이트).
- `exposure_min/max`가 설계 범위 내(예: max ≤ 0.85, min ≥ 0).
- OOS min(하방) 또는 MDD가 개선되면 우선 채택(평균보다 생존성 우선).

**48시간 루프**
- (1) 실험 정의: 3-arm 노출 스케일러
- (2) 게이트: ETF 거래 0, 노출 상한 준수
- (3) 기대 관측치: 성능이 안 오르더라도 **하방/변동성/거래빈도** 변화로 regime 모듈 유효성 판단

# 2) “성능이 안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래를 **리포트에 고정 항목으로 추가**해서, 매 48시간 루프마다 자동 비교(챔피언 vs 후보)하도록 패치/계측하라.

## A. Trigger(신호가 나오는가?)
- 체크:
  - 신호 발생 빈도(일/주), 0 신호 기간 길이
  - 상위 K 종목 스코어 분포(평균/표준편차), 동률/클리핑 여부
- 증상→원인:
  - 신호 거의 없음 → 임계값 과도 / 결측치로 필처리 / 섹터필터로 풀 축소
  - 스코어가 항상 비슷 → 피처가 상수화(정규화/스케일 버그)

## B. Apply(신호가 주문으로 변환되는가?)
- 체크:
  - “진입 후보 수” → “주문 수” → “체결 수” 단계별 드랍률
  - 제약(8~14, 섹터, 노출상한, 포지션 한도)으로 인해 주문이 0 되는 비율
- 증상→원인:
  - 후보는 많은데 주문 0 → 게이트 로직이 과도 / 상호 모순 제약

## C. Exposure(노출이 성과를 좌우할 만큼 유지되는가?)
- 체크:
  - 일별 gross exposure 분포(평균/95p/max), 현금 비중
  - 포지션 크기 분포(최소단위로 라운딩되어 “거의 0”이 되는지)
- 증상→원인:
  - 성능 무변화 + 노출이 낮음 → 스케일러가 항상 0 근처 / 리스크 모델이 과민
  - 노출 max는 큰데 성능 무변화 → 종목 선택이 랜덤/상쇄(롱만이면 섹터 베타만 먹는지 점검)

## D. Cost(비용이 PnL을 상쇄하는가?)
- 체크:
  - gross PnL, cost, net PnL을 분리해서 시계열로 출력
  - turnover와 cost의 상관(회전율↑인데 net이 안 움직이면 비용 문제)
- 증상→원인:
  - gross는 움직이는데 net이 평평 → 비용/슬리피지 모델 과소/과대 또는 과매매

## E. Regime(레짐에서 전략이 “꺼져” 있거나 반대로 “잘못 켜져” 있는가?)
- 체크:
  - 레짐 상태별(ON/OFF) 성과 분리, ON 비율
  - 레짐 전환 직후 성과(지연/선행 문제)
- 증상→원인:
  - ON 비율이 극단(0%/100%) → 지표 스케일/임계값 버그
  - 전환 직후 손실 반복 → 지연 적용 필요(예: 다음 리밸런스부터 적용)

## 24~48시간 실행 순서(명령형 체크리스트)
1. **LOG-INTEGRITY-001부터 실행**: rebalance 파싱/해시/메트릭 non-null 하드게이트 설치  
2. **CV-FIX-002 실행**: degenerate fold 제거 + purge/embargo 적용  
3. **UNIV-PIT-003 실행**: Tech+Healthcare + 8~14 강제 + PIT 위반 0  
4. **COST-REALISM-004 실행**: 비용 0/기본/스트레스 3-arm으로 생존성 확인  
5. **REGIME-CASH-005 실행**: ETF 거래 0 하드게이트 + 현금 노출 스케일링만 허용  

이 5개가 돌아가면, “성능이 안 움직임”은 더 이상 막연한 현상이 아니라 **(신호/게이트/노출/비용/레짐) 중 어디에서 상쇄되는지**가 리포트로 자동 분해된다.
