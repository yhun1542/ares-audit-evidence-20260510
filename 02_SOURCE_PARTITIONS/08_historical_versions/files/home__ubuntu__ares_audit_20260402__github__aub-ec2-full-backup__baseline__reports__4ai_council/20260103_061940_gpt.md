## 24~48시간 TOP5 우선순위 (코드/아키텍처/전략) — **명령형 체크리스트**
(공통 전제: **미국주식 only**, **Tech+Healthcare 8~14개**, **ETF 매매 금지(관측지표만)**, **48시간 자동 루프**에서 “실험 정의→게이트→기대 관측치”로 돌린다.)

---

# 1) **리밸런스/로그 아티팩트 무결성 복구 (운영 리스크 최우선)**
### (a) 왜 필요한지
- 현재 `aub_rebalance_pinpoint`가 **base-log/cand-log 로딩 실패** → “무엇이 성능을 만들었는지(트리거/체결/리밸런스)” 추적 불가.
- `lane_hash/run_hash=None`, `worst_mdd=None` 등 **핵심 메타가 비어** 있어 재현성/감사 불가(자동 루프에서 가장 치명적).

### (b) 위험/부작용
- 로깅/스키마 변경으로 기존 리포트 파서가 깨질 수 있음.
- 리밸런스 이벤트를 세밀히 남기면 저장/IO 비용 증가(하지만 지금은 “관측 불가”가 더 큰 리스크).

### (c) 최소 실험(공유 실험 풀에서 재사용)
- **[E1] 리밸런스 로그/메타 강제 생성 패치**
- **[E2] 폴드/데이터 누수 센티널 리포트에 “리밸런스 요약” 연결(리밸런스가 0건이면 FAIL 처리)**

### (d) PASS 조건
- `rebalance_pinpoint`가 **base/cand 모두**에서 리밸런스 데이터를 읽고, “변경점 Top-N”을 출력.
- 모든 런에서 `run_hash/lane_hash`가 채워지고, `worst_mdd`가 계산/기록됨.
- 리밸런스 이벤트가 0건이거나 비정상(예: 거래일 수 대비 1% 미만)일 경우 자동 FAIL로 종료.

---

# 2) **degenerate_folds 제거 + 누수(Leakage)/과최적화 방지 게이트 추가**
### (a) 왜 필요한지
- 현재 `degenerate_folds: [1,2,3,8]` → OOS 평균이 좋아도 **검증 구조가 무너진 상태**(사실상 운 좋게 맞은 값일 가능성 급증).
- “No-Delta Diagnoser”가 돌아도 **폴드 자체가 퇴화**하면 개선/악화가 관측 불가능(“성능이 안 움직임”의 대표 원인).

### (b) 위험/부작용
- 정화된 CV(예: purged/embargo) 적용 시 성능이 단기적으로 떨어질 수 있음(하지만 현실성↑).
- 데이터량이 적으면 폴드 제약이 더 빡세져 학습 불안정 가능.

### (c) 최소 실험
- **[E2] Purged K-Fold + Embargo + As-of 조인(미래 데이터 차단) + 폴드 최소 샘플/거래일 게이트**
- **[E5] (간접) 레짐/노출 게이트로 “폴드별 노출 편향”도 같이 진단**

### (d) PASS 조건
- `degenerate_folds`가 **빈 배열**.
- 각 폴드에서 (i) 유효 거래일 수 (ii) 신호 발생 바 수 (iii) 실제 리밸런스 수가 **최소 기준**을 만족(기준 미달이면 FAIL).
- OOS `oos_min`이 극단적으로 악화(예: -X% 이하)하면 FAIL. *(X는 시스템 기존 분포 기반으로 고정값으로 박아 자동화)*

---

# 3) **거래비용/슬리피지/턴오버를 OOS에 강제 반영 (비용 미반영 리스크 제거)**
### (a) 왜 필요한지
- 현재 리포트에서 비용/리밸런스 로그가 불완전 → **실현 수익과 백테스트 수익 괴리** 가능성이 큼.
- Tech/Healthcare 8~14개 운용은 포지션 집중이 쉬워 **턴오버/슬리피지**가 성능을 “안 움직이게” 만들 수 있음(미세 알파가 비용에 상쇄).

### (b) 위험/부작용
- 비용을 현실화하면 “챔피언 성능”이 내려가 보일 수 있음(정상).
- 너무 보수적 비용모델은 알파를 과소평가할 수 있음(하지만 자동 루프에서는 보수적이 안전).

### (c) 최소 실험
- **[E3] Net OOS 전용 런: 수수료+슬리피지+스프레드(고정 bps + 변동성 연동) + 턴오버 캡**
- **[E1] 비용 구성요소(슬리피지/수수료/스프레드/추정체결가격)를 리밸런스 로그에 함께 기록**

### (d) PASS 조건
- `gross_oos_mean - net_oos_mean` 갭이 **상식 범위**(비정상적으로 0에 가까우면 비용이 적용 안 된 것 → FAIL).
- 턴오버가 캡 이하로 유지되며, net 기준으로도 OOS가 챔피언 대비 “의미 있게” 열화되지 않음(자동 기준: 챔피언 net 대비 -ε 이상).

---

# 4) **서바이버십/코퍼레이트 액션(상폐/합병/스플릿) 처리로 “가짜 안정성” 제거**
### (a) 왜 필요한지
- Tech/Healthcare를 “현재 살아남은 강자”로만 고르면 **서바이버십 바이어스**가 성능을 과대평가.
- 상폐/인수/합병/티커 변경을 무시하면 OOS가 특정 구간에서 **조용히 왜곡**(“성능이 안 움직임/리밸런스 없음”과도 연결).

### (b) 위험/부작용
- PIT(시점 일치) 유니버스로 바꾸면 단기 성능이 떨어질 수 있음(정상).
- 데이터 소스/매핑이 부실하면 결측이 늘어 폴드가 다시 퇴화할 수 있음(E2 게이트로 방지).

### (c) 최소 실험
- **[E4] PIT 유니버스 + delisting return(상폐수익) 반영 + 티커/식별자 매핑 고정**
- **[E2] 누수 센티널에 “유니버스 시점 일치/식별자 불변성 체크” 추가**

### (d) PASS 조건
- 동일 기간 재실행 시 유니버스/시그널/리밸런스가 **완전 재현**(해시 일치).
- 상폐/티커변경 이벤트가 있는 종목에서 수익률 공백이 0으로 메워지지 않고(=조용한 오류 방지), 이벤트 로그가 남음.
- PIT 전환 후에도 `degenerate_folds` 0 유지.

---

# 5) **노출/레짐(시장 국면) 게이트로 “알파가 안 먹히는 기간”을 자동 완화**
### (a) 왜 필요한지
- 현재 노출 max ~0.84로 보이며, 레짐이 바뀌면 **알파가 희석되거나 비용만 발생**.
- ETF는 매매 금지지만 **관측지표**로는 매우 유용(예: XLK/XLV 상대강도, QQQ 추세, VIX 등) → “진입/축소” 게이트로 사용 가능.

### (b) 위험/부작용
- 레짐 필터가 과하면 거래가 줄어 OOS 평균이 떨어질 수 있음.
- 지표 선택을 잘못하면 “필터가 알파를 먹어버림” (E5에서 관측치로 검증).

### (c) 최소 실험
- **[E5] ETF 관측 기반 노출 스케일링(매매 X):**
  - 예: `exposure = base_exposure * f(trend(QQQ), rel_strength(XLK,XLV), vol(VIX))`
- **[E3]와 결합: 노출 축소가 net 성능/턴오버를 어떻게 바꾸는지 동시 측정**

### (d) PASS 조건
- `oos_min` 개선(왼쪽 꼬리 완화) 또는 `worst_mdd` 감소가 관측됨.
- 노출이 [0, 0.75] 같은 하드 범위 내에서 안정적으로 유지(리밸런스 로그로 검증).
- “필터 적용 전후”에서 거래비용/턴오버가 기대 방향으로 감소.

## 48시간 자동 루프에 넣을 **공유 실험(3~5개로 제한)** 정의
아래 5개만 돌리고, TOP5 제안은 이 실험들을 “재사용”해서 검증한다.

### **[E1] Rebalance+Meta Logging 강제 패치 (Ops)**
1) **실험 정의**
- 모든 런에서 `rebalance.jsonl(or csv)` 생성 강제
- `run_hash/lane_hash`, `worst_mdd`, 비용 breakdown, 주문/체결 추정가를 동일 스키마로 기록
- `aub_rebalance_pinpoint` 입력 경로를 “실제 생성물”로 자동 연결(하드코딩 금지)

2) **게이트**
- 파일 존재/파싱 성공/이벤트 0건이면 FAIL
- 메타 누락(None) 있으면 FAIL

3) **기대 관측치**
- pinpoint 리포트가 항상 생성되며, 성능 변화의 원인이 “리밸런스/노출/비용” 중 어디인지 바로 보임

---

### **[E2] Purged+Embargo CV + Leakage Sentinel (Leak/Overfit)**
1) **실험 정의**
- Purged K-Fold(시간 분리) + embargo 구간
- feature/label as-of 조인 강제, 미래 참조 탐지(최소 1-bar lag 검사)
- 폴드별 유효표본/신호발생/거래횟수 리포트

2) **게이트**
- `degenerate_folds` 발생 시 FAIL
- 미래 참조 탐지 시 FAIL
- 폴드별 최소 기준 미달 시 FAIL

3) **기대 관측치**
- OOS 평균이 요동치더라도 “검증이 살아있음”이 보장
- “성능이 안 움직임”이 데이터/폴드 문제인지 즉시 분리됨

---

### **[E3] Net 성능 전용 비용모델 + Turnover Cap (Cost)**
1) **실험 정의**
- 수수료+슬리피지(bps) + 스프레드(변동성/유동성 대용치 연동) 반영
- 턴오버 캡(일/주 단위) 및 초과 시 주문 축소/스킵 규칙

2) **게이트**
- net/gross 갭이 0에 수렴하면 FAIL(비용 미적용 의심)
- 턴오버 캡 위반 지속 시 FAIL

3) **기대 관측치**
- “gross는 좋은데 net이 안 움직이는” 구조가 드러나며, 개선 방향(턴오버 vs 알파)이 명확해짐

---

### **[E4] PIT Universe + Delisting Return + ID Mapping (Survivorship)**
1) **실험 정의**
- Tech+Healthcare 8~14개를 “시점 기준”으로 고정(PIT): 섹터 분류/시총/유동성 기준을 백테스트 시점으로 재구성
- delisting return 반영
- ticker가 아니라 영속 ID로 조인(가능한 범위에서)

2) **게이트**
- 재실행 시 유니버스 해시 불일치면 FAIL
- 상폐/티커 변경 이벤트가 수익률 공백/결측으로 누락되면 FAIL

3) **기대 관측치**
- 성능이 다소 낮아져도 “현실 성능”으로 수렴
- 특정 기간 이상하게 좋은/나쁜 구간이 서바이버십 때문인지 판별 가능

---

### **[E5] ETF 관측 기반 레짐/노출 스케일링 (Exposure/Regime)**
1) **실험 정의**
- ETF는 **매매하지 않고** 관측지표만 사용:
  - 예: `trend(QQQ)`, `XLK/XLV 상대강도`, `VIX 수준/변화`
- 노출을 0~cap 범위에서 연속 스케일(급격한 ON/OFF 금지)

2) **게이트**
- 노출이 cap 초과 또는 노출 급변(일정 임계치) 시 FAIL
- 거래횟수 급감으로 폴드 퇴화 시 FAIL(E2 연동)

3) **기대 관측치**
- `oos_min` 및 `worst_mdd` 개선(왼쪽 꼬리 감소)
- 비용(E3)과 결합 시 net 성능 방어

# 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래 순서대로 **원인 하나씩 제거**(로그 기반)한다.

## A. 트리거(신호 발생) 계층
- **신호가 실제로 발생했나?** (폴드별 신호 바 수, 종목별 신호 빈도)
- 발생했는데도 성능이 동일하면 → B로

## B. 적용(포지션/리밸런스) 계층
- **리밸런스가 실행됐나?** (E1에서 이벤트 0건/소수면 즉시 원인)
- 실행됐는데 포지션 변화가 미미하면:
  - 가중치가 클리핑/정규화로 죽었는지(상한/하한/현금비중)
  - 주문 스킵 규칙이 과도한지(턴오버 캡, 최소 주문단위)

## C. 노출(Exposure) 계층
- 노출이 **항상 비슷**(예: 0.8 근처 고정)하면 레짐 대응 실패
- 노출이 **너무 낮아** 알파가 희석되면 신호 강도/스케일링 점검
- E5로 “노출이 상황에 따라 변하는지” 관측

## D. 비용(Cost) 계층
- gross는 변하는데 net이 안 움직이면 → 비용이 알파를 상쇄
- E3에서 (턴오버, 거래빈도, 비용 breakdown)으로 어떤 비용이 큰지 분해:
  - 스프레드 기여 vs 슬리피지 기여 vs 수수료 기여

## E. 레짐(Regime) 계층
- 특정 국면(고변동/하락추세/섹터 로테이션)에서만 무력화될 수 있음
- ETF 관측지표(매매 X)로 구간 태깅:
  - QQQ 추세 상/하, VIX 상/하, XLK vs XLV 강약
- “구간별 성능”이 거의 동일하면 → 신호가 시장과 무상관/무효일 가능성↑ (신호 재정의 필요)

## 24~48시간 실행 순서(자동 루프에 바로 얹는 형태)
1) **E1 먼저 적용** → 리밸런스/메타가 기록되지 않으면 이후 모든 실험이 무의미하므로 즉시 차단  
2) **E2 적용** → degenerate_folds 제거/누수 차단(검증 구조 복구)  
3) **E3 적용** → net 기준으로 “움직이는지” 확인(비용 상쇄 여부 확정)  
4) **E4 적용** → 서바이버십/상폐 처리로 현실성 고정  
5) **E5 적용** → 레짐/노출로 왼쪽 꼬리 및 MDD 방어 관측

이 5개만으로도 지금 상태(리밸런스 로그 부재, 폴드 퇴화, 비용/현실성 불명, 레짐 미제어)에서 “왜 성능이 안 움직이는지”를 48시간 내에 구조적으로 분해 가능하다.
