## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — **명령형 체크리스트**
(우선순위는 **누수 → 과최적화 → 서바이버십 → 비용 → 운영리스크** 순서로 배치)

---

# 1) **리밸런스/트레이드 로그 파이프라인 복구(운영리스크 + 비용/노출 검증 불가 상태 해소)**
### (a) 왜 필요한지
- 현재 `aub_rebalance_pinpoint`가 **base-log/cand-log 모두 로드 실패** → “성능이 안 움직임”의 원인이 **(i) 거래가 안 나감 (ii) 거래는 나가는데 비용/제약에 막힘 (iii) 기록이 누락됨** 중 무엇인지 분해가 불가능.
- `worst_mdd: None`도 함께 보여 **리스크 지표 계산/저장 파이프**가 빈틈일 가능성 큼.

### (b) 위험/부작용
- 로그 스키마 변경 시 기존 리포트/대시보드가 깨질 수 있음.
- 로그를 자세히 남기면 디스크/IO 비용 증가.

### (c) 최소 실험(단일 실험에 3-arm로 묶어서 48h 루프에 태움)
**실험명: `exp_log_schema_rebalance_v1` (3 arms)**
- **Arm A (보수)**: 현재 JSON 출력 유지 + `rebalance.jsonl`를 *추가*로 병행 출력(append-only)
- **Arm B (표준화)**: `rebalance.csv` 제거하고 JSONL 단일화 + 스키마 버전 필드 추가(`schema_version`)
- **Arm C (검증 강화)**: 런 종료 시 “리밸런스 이벤트 0건이면 FAIL” 게이트 추가(단, 완전 캐시 전략 등 예외는 allowlist)

### (d) PASS 조건(게이트)
- 리포트가 **base/cand 모두**에서 `rebalance`를 읽어 **pinpoint 리포트 생성 성공**.
- 모든 런에서 다음 최소 필드 존재: `ts, symbols, target_w, fill_w, turnover, est_cost, reason_code`.
- `worst_mdd`가 None이 아닌 값으로 산출/저장(최소 1개 OOS fold라도).

**48시간 자동 루프 형태**
1) **실험 정의**: 위 `exp_log_schema_rebalance_v1` 실행(3 arms)
2) **게이트**: 리포트 생성 성공 + rebalance 이벤트/필드 검증 + MDD 산출
3) **기대 관측치**: “거래 0건/과도한 턴오버/게이트 컷” 중 하나로 **성능 정체 원인이 즉시 분해**됨

# 2) **시계열 누수(lookahead) 하드 차단: feature/label 정렬 & as-of 강제**
### (a) 왜 필요한지
- Tech/Healthcare 소수 종목(8~14)에서 성능이 “안 움직이거나” 비정상적으로 좋을 때, 최빈 원인은 **리샘플/정렬 과정의 1-bar 누수**(예: 당일 종가로 만든 feature로 당일/익일 리턴을 예측).
- 특히 corporate action 조정(분할/배당) + 리턴 계산 + 리밸런스 타이밍이 엇갈리면 누수가 매우 쉽게 생김.

### (b) 위험/부작용
- 누수 제거 시 IS 성능 급락 가능(정상).
- 너무 엄격한 as-of 적용으로 결측 증가 → 거래 감소.

### (c) 최소 실험(단일 실험 3-arm)
**실험명: `exp_no_lookahead_alignment_v2`**
- **Arm A**: 모든 feature를 `t-1 close`까지만 사용(리밸런스는 `t open` 체결로 가정)
- **Arm B**: feature는 `t`까지 허용하되, label(수익률)을 반드시 `t+1`부터로 강제 + “동일 timestamp 사용 금지” assert
- **Arm C**: 위 A 또는 B + *forward-fill 제한* (최대 ff-limit=1) 적용하여 “미래 데이터가 길게 전파”되는 누수 차단

### (d) PASS 조건(게이트)
- 누수 탐지 assert 0건.
- OOS에서 `oos_min`이 **악화하지 않거나**(±5% 이내) 오히려 개선되면 강한 PASS 신호.
- “거래 횟수/노출”이 급감하면 FAIL(모델이 데이터 결측으로 죽은 것).

**48시간 자동 루프**
1) **실험 정의**: `exp_no_lookahead_alignment_v2`
2) **게이트**: 누수 assert + 거래/노출 최소치 + OOS min 안정성
3) **기대 관측치**: 성능이 떨어지더라도 **분산↓/fold 퇴화↓**가 관측되면 “정상화 진행”으로 간주

# 3) **서바이버십/종목 우주 고정(8~14 Tech+Healthcare) + delist 처리**
### (a) 왜 필요한지
- “미국주식 only, Tech+Healthcare, 8~14개”는 표본이 작아서 **우주가 조금만 흔들려도** 결과가 과최적화/서바이버십 영향을 크게 받음.
- delist/합병/티커 변경을 현재 파이프가 무시하면 OOS가 “안 움직이거나” 특정 구간에서 비정상적으로 매끈해질 수 있음.

### (b) 위험/부작용
- 우주를 엄격히 고정하면 기회 손실로 평균 수익률 하락 가능.
- delist 이벤트 처리 로직이 잘못되면 갑자기 0가로 수렴하는 등 백테스트 망가짐.

### (c) 최소 실험(단일 실험 3-arm)
**실험명: `exp_universe_pit_v1`**
- **Arm A (고정 리스트)**: 대표 Tech+Healthcare 10~12개로 고정(예: AAPL/MSFT/NVDA/GOOGL/AMZN/META + UNH/JNJ/LLY/PFE/ABBV 등에서 8~14로 제한)  
  - *중요*: ETF 매매는 금지, 단 관측지표는 허용(아래 5번에서)
- **Arm B (PIT 섹터 필터)**: 날짜별로 섹터 분류를 point-in-time으로 고정(가능하면) + 8~14개 유지
- **Arm C (delist 강제 처리)**: delist/merge 발생 시 cash 처리 규칙 + 마지막 거래일 이후 가격 사용 금지

### (d) PASS 조건(게이트)
- 백테스트 기간 전체에서 “우주 크기 8~14” 유지(예외 발생 시 로그에 이유 코드 필수).
- delist 이벤트 발생 시 **다음날부터 해당 심볼 거래/가격 참조 0건**.
- OOS의 fold 간 편차(표준편차)가 감소하면 PASS(과최적화/서바이버십 억제 신호).

**48시간 자동 루프**
1) **실험 정의**: `exp_universe_pit_v1`
2) **게이트**: 우주 크기/심볼 무결성 + delist 규칙
3) **기대 관측치**: 평균은 비슷하거나 소폭 하락해도 **최저 성능(oos_min)과 분산이 안정화**되면 성공

# 4) **비용/슬리피지/턴오버를 “게이트”로 승격(비용 미반영 최우선 차단)**
### (a) 왜 필요한지
- 지금 노출이 `0.47~0.84`로 높고, 리밸런스 로그가 불명확한 상황에서 비용이 빠져있으면 “개선이 안 보임”이 아니라 **개선이 허상**일 수 있음.
- Tech 대형주는 스프레드는 작아도, 잦은 리밸런스면 턴오버 비용이 성과를 잠식.

### (b) 위험/부작용
- 비용을 넣는 즉시 OOS가 내려갈 가능성 큼(정상).
- 비용 모델이 과도하면 과보수적으로 변해 거래가 멈출 수 있음.

### (c) 최소 실험(단일 실험 3-arm)
**실험명: `exp_cost_model_gate_v1`**
- **Arm A**: 고정 bps 비용(예: 2~5bps) + 커미션 0 가정
- **Arm B**: 스프레드 기반(ATR 또는 intraday range proxy) 비용 + 최소 bps floor
- **Arm C**: Arm B + **턴오버 상한 게이트**(예: 1회 리밸런스 당 turnover > X면 주문 스케일다운)

### (d) PASS 조건(게이트)
- “Gross”가 아니라 **Net-of-cost** 기준으로 OOS mean이 챔피언 대비 유지 또는 개선.
- turnover, 거래횟수, 비용이 리포트에 항상 기록(1번 로그 복구와 연결).
- 비용 적용 후에도 노출이 한쪽으로 고착(항상 0.8대)되면 FAIL(사이징/제약 문제).

**48시간 자동 루프**
1) **실험 정의**: `exp_cost_model_gate_v1`
2) **게이트**: net 성과 + turnover 상한 + 비용 기록
3) **기대 관측치**: 성과가 떨어져도 “턴오버-성과” 상관이 드러나 원인(과매매 vs 신호) 분해 가능

# 5) **레짐(관측지표 ETF) 기반 “노출/헤지 스케일”만 동적으로(전략 과복잡화 없이)**
> ETF는 **매매 금지**, **관측지표로만** 사용

### (a) 왜 필요한지
- “성능이 안 움직임”은 종종 **노출이 레짐과 무관하게 고정**되어 알파가 이득을 못 보는 구조에서 발생.
- Tech/Healthcare 편중이면 시장/금리/리스크오프 레짐에서 손실 구간이 비슷해지기 쉬움.

### (b) 위험/부작용
- 레짐 신호가 늦으면 고점에서 줄이고 저점에서 늘리는 역효과 가능.
- 레짐을 너무 세분화하면 과최적화.

### (c) 최소 실험(단일 실험 3-arm)
**실험명: `exp_regime_exposure_scaler_v1`**
- **Arm A**: QQQ(Tech proxy) 20D 모멘텀 < 0이면 전체 gross 노출을 0.7배로 축소
- **Arm B**: XLV(Healthcare proxy) 상대강도( XLV/QQQ )가 상승하면 헬스케어 비중 상한 +10% (단, 종목 8~14 유지)
- **Arm C**: VIX proxy(가능하면) 또는 SPY 변동성 proxy 상승 시 리밸런스 빈도/턴오버 목표를 낮춰 비용 억제

### (d) PASS 조건(게이트)
- 레짐 스케일 적용 후 `oos_min` 개선(최소 낙폭 완화) 또는 MDD 개선이 관측되면 PASS.
- 레짐 스케일로 인해 거래가 0으로 수렴하면 FAIL(알파 전달 실패).

**48시간 자동 루프**
1) **실험 정의**: `exp_regime_exposure_scaler_v1`
2) **게이트**: oos_min / MDD 개선 + 거래 지속성
3) **기대 관측치**: 평균 수익보다 **최악 구간 방어**가 먼저 개선되는 패턴이 나오면 성공 가능성 큼

## 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래를 **로그 기반으로 순서대로 ‘차단/확인’**하면 원인이 빠르게 좁혀짐.

### A. Trigger(신호 생성) 문제
- **신호 분산이 0에 가까움**: 대부분의 날짜에 score가 거의 동일 → 종목 간 랭킹이 고정
- **신호가 결측/ffill 과다**: 실제로는 동일 값이 반복 → 거래가 줄거나, 의미 없는 미세 변화로 과매매
- **누수 제거 후 IS 급락 + OOS 안정화**: “성능 정체”가 아니라 정상화 과정일 수 있음

### B. Apply(적용/정렬) 문제
- 리밸런스 타이밍이 잘못되어 **동일 봉 데이터로 의사결정 + 체결**(룩어헤드)
- 신호는 정상인데 **주문 생성 시점에 심볼/가격이 NaN** → 주문 무효/스킵

### C. Exposure(노출/사이징) 문제
- 노출이 `0.47~0.84`로 **항상 높은데 성능이 정체**면:
  - 사이징이 사실상 “항상 풀 인” → 알파 차이가 성과로 전달되지 않음
  - 포지션 상한/하한/현금비중 규칙이 잘못 작동
- 반대로 거래가 거의 없고 노출이 고정이면:
  - **리밸런스 임계값(threshold)**이 너무 크거나
  - “변경 폭 < 최소 주문 단위”로 모두 컷되고 있을 수 있음

### D. Cost(비용) 문제
- gross 기준 개선이 있는데 net이 정체/악화면:
  - 턴오버가 지나치게 크거나
  - 리밸런스 빈도가 레짐에 비해 과도
- 비용이 아예 없으면 “개선이 안 보임”이 아니라 **개선이 허상**일 가능성

### E. Regime(시장 국면) 문제
- Tech/Healthcare는 레짐에 민감:
  - 금리/변동성 상승 레짐에서 Tech 모멘텀이 깨지면 알파가 묻힘
- 레짐 대응이 없으면:
  - 평균은 유지돼도 `oos_min`이 계속 낮게 고정되는 패턴이 반복

1) `exp_log_schema_rebalance_v1`
