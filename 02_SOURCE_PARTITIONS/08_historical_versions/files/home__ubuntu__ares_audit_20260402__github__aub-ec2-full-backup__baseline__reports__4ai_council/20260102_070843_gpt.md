## 다음 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — **명령형 체크리스트**

### 1) **누수(Leakage) 최우선 차단: “발행시점/라그” 강제 + 피처 정렬 감사**
**(a) 왜 필요한지**
- Tech/Healthcare 8~14종목처럼 소수·고상관 바스켓은 **미세 누수**만 있어도 tuning만 과대, lockbox는 정체/붕괴가 흔함.
- ETF(관측지표)·거시·금리·VIX류는 특히 **“발행/업데이트 시점”** 누수가 빈번.

**(b) 위험/부작용**
- 단기적으로 성능(특히 tuning_mean) 하락 가능. 그러나 하락폭이 크면 “지금까지가 누수 성능”일 확률이 높음.
- 라그 강제가 과도하면 신호가 늦어져 회전율/추세추종 성격이 변할 수 있음.

**(c) 최소 실험 2~3개 (단일 배치로 실행; 케이스 폭발 금지)**
- **실험 A (Leakage Lag Batch)**  
  1) ETF/지표 피처 전부 `t-1` 라그 강제  
  2) “발행시점 라그” 가정(예: 매크로/변동성/금리성 지표) `t-2` 강제  
  3) 가격 기반(OHLCV) 피처만 유지 + 나머지 제거(누수 상한선 확인용)

**(d) PASS 조건**
- `lockbox_mean`가 **champion 대비 -5% 이내**로 유지되면서,  
  - tuning_mean 하락폭이 상대적으로 더 크면(=과적합/누수 제거 시그널) **PASS**  
- 또는 `lockbox_min`이 **0.33 → 0.60+**로 개선(최악 구간 내구성 개선)되면 PASS

**48시간 자동 루프 형태**
1) 실험 정의: `feature_lag_guard` 모듈 추가(피처별 허용 라그 테이블), batch 3-variant  
2) 게이트: “피처 timestamp <= decision_time - lag” 위반 0건 + 성능 PASS 조건  
3) 기대 관측치: tuning 하락/lockbox 유지(또는 lockbox_min 개선), 피처 중요도 상위가 “미래성/비정상 지표”에서 “가격/리스크”로 이동

### 2) **비용/체결/회전율 현실화: 슬리피지+스프레드+턴오버 상한 + 노트레이드 밴드**
**(a) 왜 필요한지**
- 소수 종목 전략은 신호가 자주 바뀌면 **거의 항상 “비용 미반영 알파”**가 됨.
- champion과 candidate의 차이(평균은 champion 우세, MDD는 candidate 우세)는 **비용/회전율/리밸런싱 규칙** 하나로 뒤집힐 수 있음.

**(b) 위험/부작용**
- 비용 모델이 과하면 거래가 줄어 성능이 죽을 수 있음(특히 mean-reversion 계열).
- 체결 제약(거래대금/참여율)까지 넣으면 “거래 불가능 구간”이 늘어 백테스트 공백 처리 필요.

**(c) 최소 실험 2~3개 (단일 배치)**
- **실험 B (Cost & Turnover Batch)**  
  1) 보수적 비용: `spread/2 + k*ATR` 기반 슬리피지(일괄)  
  2) 턴오버 캡: 일간/주간 turnover 상한(예: 30~50%)  
  3) 노트레이드 밴드: 목표비중 변화가 ±X% 이하면 리밸런싱 스킵

**(d) PASS 조건**
- 비용 포함 `lockbox_mean`이 **champion 대비 -3% 이내**이면서  
  - `worst_mdd`가 **동일 또는 개선**, 그리고  
  - turnover가 **의미 있게 감소(예: -20% 이상)** 시 PASS  
- 추가로 운영 관점 PASS: 거래 수/일이 과도하게 폭증하지 않을 것(자동루프 안정성)

**48시간 자동 루프 형태**
1) 실험 정의: `execution_cost_model_v2` + `rebalance_hysteresis` + `turnover_cap`  
2) 게이트: 비용이 0 또는 음수로 찍히는 버그 0건, 거래 수/일 상한 준수  
3) 기대 관측치: tuning_mean 소폭 감소, lockbox 성능 유지/최악값 개선, turnover 하락

### 3) **서바이버십/상장폐지/심볼변경/스플릿 운영 리스크 제거: Point-in-time Universe + 코퍼릿액션 검증**
**(a) 왜 필요한지**
- 8~14종목을 “현재 유명한 Tech+Healthcare”로 고정하면 서바이버십이 사실상 내장됨.
- 자동 운용 루프에서 가장 흔한 장애는 **심볼 변경/데이터 결측/분할 반영 오류**로 인한 포지션 폭주.

**(b) 위험/부작용**
- PIT(시점별 구성) 데이터 소스가 빈약하면 구현 난이도↑.
- delist 처리(0으로 소멸 vs 마지막가 청산) 방식에 따라 성과 왜곡 가능.

**(c) 최소 실험 2~3개 (단일 배치)**
- **실험 C (Survivorship & Corporate Actions Batch)**  
  1) PIT 유니버스 로더 적용(최소: “해당 시점에 거래가능 + 섹터(Tech/HC) + 시총/유동성 컷”)  
  2) delist/거래정지 처리 룰 2안 비교: (i) 마지막 유효가 청산 (ii) 보수적 헤어컷 청산  
  3) split/dividend 조정 일관성 테스트(조정가 vs 비조정가 혼용 탐지)

**(d) PASS 조건**
- PIT 적용 후에도 `lockbox_mean`이 **급락하지 않을 것(예: -10% 초과 하락이면 FAIL로 원인추적 우선)**  
- delist 처리 2안 간 성능이 “극단적으로 벌어지지 않을 것”(= 생존편향 의존 낮음)  
- 운영 게이트: 결측/심볼변경 발생 시 자동 스킵/대체 로직으로 루프 중단 0회

**48시간 자동 루프 형태**
1) 실험 정의: `pit_universe_loader` + `corporate_action_sanity` + `delist_handler`  
2) 게이트: (i) look-ahead 없는 구성 산출 로그 저장 (ii) 결측률/조정가 체크 리포트 생성  
3) 기대 관측치: 성능 소폭↓라도 lockbox 안정성↑, 백테스트 “이상치 스파이크” 감소

### 4) **과최적화(Overfit) 억제: Purge/Embargo + 안정성(스태빌리티) 기반 피처/규칙 축소**
**(a) 왜 필요한지**
- champion tuning_mean이 높고 lockbox도 좋지만, “높은 tuning 대비 lockbox 개선 폭”이 작아지면 **모델 자유도 과다** 신호일 수 있음.
- Tech/HC는 레짐 변동(금리·리스크온오프)에 민감 → 과거 특정 국면에 맞춘 규칙이 고착되기 쉬움.

**(b) 위험/부작용**
- 지나친 단순화는 알파 자체를 제거할 수 있음.
- Purge/Embargo를 강하게 걸면 학습 데이터가 줄어 분산↑.

**(c) 최소 실험 2~3개 (단일 배치)**
- **실험 D (Anti-Overfit Validation Batch)**  
  1) Purged K-fold + embargo(예: 5~20거래일)로 재평가(누수성 상관 제거)  
  2) 피처 중요도/선정 “스태빌리티” 기준 도입: fold 간 상위 피처 교집합만 유지  
  3) 파라미터 범위 축소(탐색공간 축소) + 조기중단(early stopping)로 복잡도 하향

**(d) PASS 조건**
- Purged/Embargo 적용 후 `lockbox_mean`이 기존 대비 **유의미하게 덜 흔들릴 것**(fold 간 분산 감소)  
- `lockbox_min` 또는 최악 fold 성능이 개선되면 PASS(= 내구성↑)  
- “선정된 피처 수/규칙 수”가 줄어도 성능이 유지되면 PASS(운영 안정성↑)

**48시간 자동 루프 형태**
1) 실험 정의: `cv_purge_embargo` + `feature_stability_selector` + `search_space_shrinker`  
2) 게이트: fold 경계/embargo 적용 로그, 선택 피처 리스트 버전 고정(재현성)  
3) 기대 관측치: tuning 과대 개선 사라짐, lockbox 하방 경직(최악값) 개선

### 5) **전략 노출/레짐 리스크 제어: “ETF는 관측지표”로만 쓰는 단순 레짐 게이트 + 드로다운 브레이크**
**(a) 왜 필요한지**
- candidate가 MDD가 더 낮은 것은 “위험노출이 더 억제된 구조”일 가능성. 이를 **의도적으로 제어변수화**해야 재현 가능.
- Tech/HC 8~14는 사실상 (i) QQQ 베타 (ii) 금리 민감도 (iii) 리스크오프 충격에 동시 노출.

**(b) 위험/부작용**
- 레짐 게이트가 잦으면 “시장 참여 시간”이 줄어 평균수익 하락 가능.
- 지표(ETF/VIX 등)도 라그/누수 관리 실패 시 1번 이슈로 회귀.

**(c) 최소 실험 2~3개 (단일 배치)**
- **실험 E (Regime & DD Overlay Batch)**  *(ETF는 매매 금지, 관측만)*  
  1) 간단 레짐 게이트 1개: 예) QQQ 추세(200D) 하회 시 총노출 50%로 축소  
  2) 리스크오프 필터 1개: 예) VIX/변동성 지표 급등(라그 적용) 시 신규 진입 제한  
  3) 드로다운 브레이크: 최근 X일 DD가 임계치 초과 시 리밸런싱 빈도/노출 축소

**(d) PASS 조건**
- `worst_mdd`가 **champion 대비 20~30% 이상 개선**되면서 `lockbox_mean`이 **-5% 이내**면 PASS  
- 레짐 게이트 발동 비율이 과도하지 않을 것(예: 전체 기간의 40% 초과로 현금화면 FAIL로 재튜닝)

**48시간 자동 루프 형태**
1) 실험 정의: `regime_gate_observer`(QQQ/XLV/VIX 등 관측) + `exposure_scaler` + `dd_brake`  
2) 게이트: 지표 라그 강제(1번 룰 재사용), 게이트 발동 로그/재현성 저장  
3) 기대 관측치: 평균은 약간 희생, 최악구간 방어 및 MDD 개선, 수익분포의 꼬리 리스크 감소

## 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐) — 체크리스트

### A. 트리거(신호 발생) 문제
- 신호가 거의 0/상수인지 확인: **예측 스코어 분산, 상위/하위 분위 스프레드** 로그화
- 신호가 발생해도 포지션으로 번역이 안 되는지 확인: **리밸런싱 빈도, 목표비중 변화량 분포**
- 피처 드리프트: 최근 3~6개월 피처 분포가 학습 분포와 얼마나 다른지(KS/PSI) 기록

### B. 적용(게이트/제약) 문제
- 게이트가 과도하게 막는지 확인: **게이트 발동률, 발동 시 손익 기여**
- 턴오버 캡/노트레이드 밴드가 “알파를 죽이는지” 확인:  
  - (i) 제약 ON/OFF의 **그로스 알파 차이**  
  - (ii) 제약으로 인한 **미체결/미반영 비중 변화 누적**

### C. 노출(Exposure) 문제
- 단일 팩터(시장/금리/성장주)로 수렴했는지 확인:  
  - 포트폴리오의 **QQQ 베타, XLV 베타**, (가능하면) 금리 proxy(TLT 등) 베타를 롤링으로 추적(관측지표로만)
- 8~14종목에서 사실상 상관=1로 뭉개지는지 확인: **평균 상관/유효 종목수(Effective N)**

### D. 비용(Cost) 문제
- “비용이 알파를 다 먹는지” 확인:  
  - 총 PnL을 **gross / cost / net**으로 분해  
  - 비용의 대부분이 어느 구성인지(스프레드 vs 슬리피지 vs 리밸런싱 횟수) 로그화  
- 거래 가능성 제약: **거래대금 대비 참여율** 위반 횟수 점검(운영 리스크로도 직결)

### E. 레짐(Regime) 문제
- 성과가 특정 국면에만 나는지: 레짐별(리스크온/오프, 금리상승/하락)로 **성과 테이블** 출력
- lockbox 최악 구간이 동일 레짐에서 반복되는지 확인 → 그 레짐에만 노출 축소/진입 제한을 최소 규칙으로 추가
