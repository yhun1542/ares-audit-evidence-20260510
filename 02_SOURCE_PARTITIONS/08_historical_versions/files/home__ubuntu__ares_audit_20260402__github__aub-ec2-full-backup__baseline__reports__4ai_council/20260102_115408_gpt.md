## 24~48시간 TOP5 우선순위(코드/아키텍처/전략) — **명령형 체크리스트**
(우선순위는 **누수/과최적화/서바이버십/비용 미반영/운영 리스크**를 먼저 태우는 순서)

---

# 1) **리턴/피처 누수 + 서바이버십(상장폐지) 선제 차단**
### (a) 왜 필요한지
- 현재 로그에 **Champion file 경로가 비어있고**, OOS 수치도 (1.88 vs 2.63)처럼 출처가 흔들림 → “좋아진 척/안 움직인 척”이 가장 흔한 원인이 **타임스탬프 정렬/캐시/룩어헤드**.
- Tech+Healthcare 8~14종목 소수 포트폴리오는 **단 1개의 룩어헤드**가 OOS를 가짜로 끌어올리거나(혹은 반대로) 실험 간 차이를 죽임.

### (b) 위험/부작용
- 누수 제거 후 단기적으로 성능 급락 가능(정상).
- 피처 usable-delay를 늘리면 시그널이 둔화되어 턴오버↓, 기회↓.

### (c) 최소 실험(2~3개) — **E1: “AS-OF 정렬 강제” 패치 (단일 실험군)**
- [ ] **E1-1**: 모든 비가격 피처(펀더/실적/애널리스트/리비전/가이던스)를 `asof_date <= trade_decision_time - 1day`로 강제(거래 결정을 D일 장마감/장시작 중 무엇으로 가정하든 **일관된 컷**).
- [ ] **E1-2**: 가격 기반 피처도 `t` 종가를 쓰면 **실거래는 t+1**로 강제(동일 봉 체결 금지).
- [ ] **E1-3**: 서바이버십 체크: 백테스트 기간 내 **delisted ticker 포함/대체가격 처리(마지막 거래일 이후 현금화 규칙)** 적용 여부를 리포트로 강제 출력.

### (d) PASS 조건(게이트)
- [ ] OOS mean이 떨어져도 괜찮음. 대신:
  - [ ] **Fold 간 편차(분산) 감소** 또는 `oos_min` 악화 방지(예: `oos_min`이 기존 대비 -10% 이내)
  - [ ] “누수 의심” 자동진단 리포트에서 **위반 0건**(룩어헤드/동일봉 체결/미래 데이터 참조)
  - [ ] 실험 해시/데이터 스냅샷이 고정되어 **재현성 100%**(동일 run_hash에 동일 결과)

---

# 2) **거래비용/슬리피지 미반영(또는 이중반영) 즉시 교정**
### (a) 왜 필요한지
- 소수 종목(8~14) + 리밸런스가 조금만 잦아도 **비용이 알파를 삼키는 구조**.
- 반대로 비용이 “0”이면 과최적화가 급격히 쉬워져 OOS가 가짜로 좋아짐.
- 현재 `aub_rebalance_pinpoint`가 **리밸런스 로그를 못 읽는 상태**라 비용/턴오버 검증 자체가 막혀 있음.

### (b) 위험/부작용
- 비용 모델을 올리면 성능 하락 가능(정상).
- 너무 보수적 비용(impact 과대) → 거래가 거의 사라져 노출/성과가 죽음.

### (c) 최소 실험(2~3개) — **E2: “비용 모델 3점 캘리브레이션” (단일 실험군)**
- [ ] **E2-1 (Low)**: 수수료+스프레드 최소(예: 1~2bp + fixed commission).
- [ ] **E2-2 (Base)**: 현실적(예: 5~10bp + participation 기반 impact).
- [ ] **E2-3 (High)**: 스트레스(예: 15~25bp + impact 강화).
- [ ] 모든 버전에서 **턴오버/거래횟수/총비용/비용 차감 전후 수익**을 동일 포맷으로 출력.

### (d) PASS 조건(게이트)
- [ ] 비용을 Low→Base→High로 올리면 **성과가 단조 감소(모델 일관성)**.
- [ ] Base에서 `oos_mean`이 급락해도 괜찮으나, **턴오버가 합리 범위로 내려오고**(예: 일평균 turnover 상한 설정) `oos_min`이 붕괴하지 않을 것.
- [ ] 리밸런스 로그가 생성/파싱 가능(아래 #5와 연결 게이트).

---

# 3) **과최적화/폴드 퇴화(degenerate) + 노출(Exposure) 튐 제어**
### (a) 왜 필요한지
- 현재 exposure min/max가 **0.47 ~ 0.84**로 보임 → 전략이 “항상 비슷한 위험”을 지지 않고, 일부 구간에서 신호가 꺼지거나 리스크가 눌리는 형태.
- worst_mdd가 None인 점은 **리스크 집계 파이프라인 결손** 가능성 → 과최적화 탐지가 약해짐.

### (b) 위험/부작용
- 노출을 강하게 고정하면 알파 구간에서 수익 상단이 줄 수 있음.
- 규제가 늘면 모델이 “안 움직이는” 것처럼 보일 수 있음(하지만 운영적으로 안전).

### (c) 최소 실험(2~3개) — **E3: “포지션/노출 규격화” (단일 실험군)**
- [ ] **E3-1**: 종목 수를 항상 8~14로 강제(Tech+Healthcare only), 결측 시 현금 보유.
- [ ] **E3-2**: 단일 종목 max weight(예: 12~18%) + 섹터별 캡(Tech/HC 둘 다 과쏠림 방지).
- [ ] **E3-3**: 노출 타겟 밴드(예: gross 0.70~0.85)로 “시그널 스케일링”만 허용(임의 레버리지 금지).

### (d) PASS 조건(게이트)
- [ ] `degenerate_folds`가 계속 0 유지 + fold별 성능 분산 감소.
- [ ] exposure min/max가 목표 밴드로 수렴(예: min ≥ 0.65, max ≤ 0.90 같은 운영 기준 충족).
- [ ] worst_mdd가 **계산되어 숫자로 출력**(None 금지) + 비용 반영 MDD도 함께 출력.

# 4) **레짐(위험-on/off) 트리거를 ETF “관측지표”로만 붙여, 불필요한 거래/드로우다운 억제**
*(ETF 매매 금지, **지표로만** 사용)*

### (a) 왜 필요한지
- Tech/HC는 레짐 민감도가 커서, 동일 신호라도 **시장 리스크 구간**에서 손실이 커짐.
- “성능이 안 움직임”은 종종 레짐 필터가 항상 같은 값(항상 on/off)이라서 발생 → 트리거의 활성도/분포를 강제 점검해야 함.

### (b) 위험/부작용
- 필터가 과하게 꺼지면 기회 손실(상승장 초입 miss).
- 레짐 지표가 늦으면 손실 회피가 늦음.

### (c) 최소 실험(2~3개) — **E4: “레짐 게이트 2단” (단일 실험군)**
- [ ] **E4-1**: QQQ vs XLV 상대강도(또는 SPY 모멘텀)로 risk-on/off를 산출(ETF는 가격만 참조).
- [ ] **E4-2**: 변동성 프록시(예: VIX 지수 직접 데이터가 없으면 SPY/QQQ 실현변동)로 risk-off 시 **노출 스케일링**(0.85→0.55 등).
- [ ] **E4-3**: 레짐이 바뀔 때만 리밸런스 허용(그 외에는 홀딩 유지)로 턴오버 절감.

### (d) PASS 조건(게이트)
- [ ] 레짐 상태 분포가 “항상 한쪽”이 아니어야 함(예: 2년 중 risk-off가 최소 10~20% 구간 존재).
- [ ] risk-off 구간에서 **MDD/손실 꼬리**가 감소(비용 포함).
- [ ] 턴오버가 유의미하게 감소하면서 `oos_min`이 개선 또는 유지.

# 5) **운영/관측(Logging) 결손 즉시 복구: 리밸런스 로그·아티팩트·재현성**
### (a) 왜 필요한지
- 현재 상태에서 치명적:
  - `Error loading --base-log: No such file`
  - `rebalance.csv`가 JSON 파서에 걸림(포맷/경로/생성 실패 가능)
  - Champion의 `file:` 경로가 비어 있음
- 이 상태면 “전략이 안 움직임”이 아니라 **파이프라인이 안 움직이거나, 결과를 잘못 읽는 것**일 수 있음.

### (b) 위험/부작용
- 로그/아티팩트 저장으로 디스크/비용 증가.
- 포맷 변경 시 기존 리포트 도구 호환 깨짐(버전 핀 필요).

### (c) 최소 실험(2~3개) — **E5: “리밸런스 이벤트 표준화 + 파서 고정” (단일 실험군)**
- [ ] **E5-1**: 리밸런스 로그를 **JSONL 단일 포맷**으로 고정(각 이벤트: timestamp, universe, holdings, trades, est_cost, realized_cost, turnover, exposure).
- [ ] **E5-2**: `aub_rebalance_pinpoint.py` 입력을 “파일 경로”로만 받게 하고, 기본값 `--base-log` 같은 placeholder가 그대로 들어오면 **즉시 실패(fail-fast)**.
- [ ] **E5-3**: Champion artifact에 `file path + data snapshot id + config hash + git sha`를 필수 필드로 강제(없으면 run 실패).

### (d) PASS 조건(게이트)
- [ ] rebalance pinpoint가 **base/cand 둘 다 100% 로딩 성공**.
- [ ] 모든 run에서 champion 메타가 비어있지 않음(file/run_hash/lane_hash/config_hash).
- [ ] 동일 설정 재실행 시 결과 동일(또는 seed 차이만큼만 변동) + 리포트 생성이 항상 성공.

## 48시간 자동 루프 형태(실험 정의 → 게이트 → 기대 관측치)
아래 **5개(E1~E5)**만 돌리고, 그 외는 금지(케이스 폭발 방지).

1) **E1(누수/서바이버십)**  
- 정의: AS-OF 정렬/동일봉 체결 금지/상장폐지 처리 리포트  
- 게이트: 누수 위반 0, 재현성 100%, fold 분산↓  
- 기대 관측치: OOS가 “진짜 값”으로 재정렬(상승/하락보다 **변동 구조가 정상화**)

2) **E2(비용 3점 캘리브레이션)**  
- 정의: Low/Base/High 비용에서 동일 전략 재평가  
- 게이트: 비용↑ → 성과↓ 단조성, turnover 합리화, 로그 완비  
- 기대 관측치: “비용에 견디는 알파인지”가 즉시 판별됨

3) **E3(노출/종목수 규격화)**  
- 정의: 8~14 강제 + weight cap + exposure band  
- 게이트: exposure 밴드 충족, degenerate 0, MDD 산출  
- 기대 관측치: tail risk 감소, OOS min 안정화

4) **E4(레짐 게이트)**  
- 정의: ETF는 지표로만(모멘텀/변동) → 노출 스케일링 + 레짐 전환 시만 리밸런스  
- 게이트: 레짐 분포 정상, risk-off MDD↓, turnover↓  
- 기대 관측치: “좋을 때만 리스크”가 아니라 “나쁠 때 덜 맞는” 구조로 이동

5) **E5(운영/로그 복구)**  
- 정의: JSONL 리밸런스 표준화 + fail-fast + champion 메타 강제  
- 게이트: pinpoint 로딩 성공, 아티팩트 완전성, 재현성  
- 기대 관측치: “안 움직임”의 1순위 원인(파이프라인/관측 결손) 제거

# 성능이 안 움직일 때 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래를 **트리 형태로 순서대로** 잘라서 원인을 고정(각 단계는 “관측 가능 로그”가 있어야 다음으로 진행).

## A. 트리거(신호가 변하나?)
- [ ] 신호 시계열의 일간 변화율/랭크 변동이 거의 0이면 → **피처가 고정/누락/미래값 클램프** 가능  
- [ ] 신호는 변하는데 포지션이 안 변하면 → B로

## B. 적용(리밸런스 엔진이 신호를 반영하나?)
- [ ] “목표 비중(target)”은 변하는데 “주문(trade)”이 0이면 → **거래 제약(캡/최소주문/현금/슬리피지 한도)**이 막고 있음  
- [ ] 주문은 생성되는데 체결/포트 업데이트가 없으면 → **시뮬레이터 상태머신/날짜 인덱스/가격 바인딩** 문제

## C. 노출(Exposure가 성과를 죽이나?)
- [ ] exposure가 특정 값에 고정되면 → **스케일링 함수가 항상 포화(saturation)** 또는 레짐 필터가 상시 off/on  
- [ ] exposure가 크게 출렁이면 → **리스크 타겟/현금 규칙/결측 처리**가 불안정

## D. 비용(알파를 삼키거나, 반대로 0이라 과최적화 유발?)
- [ ] 비용 차감 전후 성과 차이가 비정상적으로 크면 → **이중 비용 반영/impact 과대**  
- [ ] 비용이 항상 0이면 → **로그 미생성 또는 비용 모델 미연결**  
- [ ] turnover가 높은데 성과가 그대로면 → **대부분이 비용으로 상쇄** 또는 **리밸런스가 사실상 의미 없는 미세 조정**

## E. 레짐(필터가 항상 같은 상태인가?)
- [ ] 레짐 지표 분포가 한쪽으로 쏠리면 → **트리거 정의/윈도우/정규화 오류**  
- [ ] 레짐 전환이 있어도 매매가 동일하면 → **레짐→노출 매핑이 적용되지 않음(코드 경로 누락)**

## F. 관측/리포트(“안 움직임”이 계산/표시 문제인가?)
- [ ] champion 메타(file/worst_mdd/log path)가 비어있으면 → **실제로는 돌았는데 못 읽는 것** 가능성이 최상위  
- [ ] base-log/cand-log 포맷 불일치면 → **pinpoint/diagnoser가 잘못된 입력을 읽고 결론을 냄**

## 즉시 실행 순서(권장)
- [ ] **E5 먼저**(로그/아티팩트 복구) → 관측 불능 상태 제거  
- [ ] 그 다음 **E1**(누수/서바이버십) → “진짜 OOS” 고정  
- [ ] **E2**(비용) → 생존 가능한 알파인지 확인  
- [ ] **E3 → E4** 순으로 안정화/레짐 대응(턴오버·꼬리손실 줄이기)

위 5개만 48시간 루프에 태우면, “성능이 안 움직임”이 **(1) 파이프라인/관측 결손**인지, **(2) 누수 제거로 정상화되며 재평가가 필요한지**, **(3) 비용/노출/레짐 중 어디가 병목인지**가 강제로 분해됩니다.
