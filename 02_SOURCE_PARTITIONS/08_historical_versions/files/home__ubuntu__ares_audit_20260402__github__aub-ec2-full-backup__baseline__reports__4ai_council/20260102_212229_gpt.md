## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — 명령형 체크리스트

### 1) **리밸런스/로그/메타데이터 파이프라인을 먼저 고쳐 “관측 가능” 상태로 만들기 (운영 리스크 최우선)**
- **왜 필요**  
  - `aub_rebalance_pinpoint`가 **base-log 경로 오류** + **CSV를 JSON으로 파싱**하며 실패 → 현재는 “왜 성능이 안 움직이는지”를 구조적으로 못 봄.  
  - `worst_mdd: None`, `lane_hash/run_hash: None`, `Next Commands` 비어있음 → 실험 재현/추적 불가(운영 리스크).
- **위험/부작용**  
  - 로그 포맷 변경으로 기존 리포트/툴 호환 깨짐(단, 48시간 내 해결 가능).
- **최소 실험(아래 공용 실험 E1/E3 사용)**: E1, E3  
- **PASS 조건**  
  - 리밸런스 로그가 **단일 표준 포맷(JSONL 권장)**으로 매 실행 생성되고, `rebalance_pinpoint`가 에러 없이 diff 리포트 생성.  
  - 모든 런에서 `run_hash/lane_hash`, `worst_mdd`가 채워짐.

---

### 2) **누수/시점 정합성(Execution lag) + Fold degeneracy(퇴화) 제거 (과최적화/누수 우선 점검)**
- **왜 필요**  
  - `degenerate_folds: [1,2,3,8]`은 CV가 “학습이 사실상 무의미한 fold”를 포함했다는 신호(데이터 누락/타임스플릿 오류/정렬 오류).  
  - OOS가 “움직이지 않는” 가장 흔한 원인이 **(a) lookahead/누수 제거 후 신호 붕괴** 또는 **(b) fold 퇴화로 평가가 무작위화**.
- **위험/부작용**  
  - 누수 제거/시점 지연을 정확히 적용하면 단기적으로 OOS mean이 떨어질 수 있음(정상적인 비용).
- **최소 실험(아래 공용 실험 E2 사용)**: E2 (+E1로 검증 로그)  
- **PASS 조건**  
  - `degenerate_folds == []`  
  - “피처 타임스탬프 ≤ 주문결정 시점” 위반 건수 0  
  - OOS 분포가 최소한 **fold별 표준편차/표본수**가 정상적으로 산출(퇴화 없음)

---

### 3) **거래비용/슬리피지/턴오버를 “항상” 반영 + 비용 미반영 실험을 차단 (비용 미반영 우선 점검)**
- **왜 필요**  
  - 비용이 빠지면 신호 개선이 실거래에서 재현 불가 → OOS가 안 움직이거나, 움직여도 운영에서 바로 붕괴.  
  - 현재 `exposure_min/max: 0.0 / 0.8388` + 리밸런스 로그 부재 → 턴오버/체결비용이 병목인지 판단 불가.
- **위험/부작용**  
  - “좋아 보이던” 전략이 비용 반영 후 성능 급락(하지만 이게 진짜).
- **최소 실험(아래 공용 실험 E3 사용)**: E3 (+E1로 리포트 생성)  
- **PASS 조건**  
  - 모든 백테스트 결과에 `gross_return`, `net_return`, `total_cost_bps`, `turnover`가 자동 포함  
  - 비용 ON/OFF 비교에서, 비용 OFF 대비 성능이 과도하게 붕괴하지 않음(예: net이 gross의 60% 이상 유지 같은 내부 기준을 고정)

---

### 4) **레짐/리스크 게이트로 노출(Exposure) 스케일링 (서바이버십 다음으로 “레짐 미반영” 점검)**
- **왜 필요**  
  - 테크/헬스케어는 레짐 민감(금리/변동성/리스크온·오프). 레짐 게이트 없이 신호만 미세개선하면 “no-delta”로 수렴하기 쉽다.  
  - ETF는 **매매하지 않고 관측지표로만** 사용 가능 → SPY/QQQ/XLK/XLV/VIX류(지수)로 **노출 스위치/스케일**만 제어.
- **위험/부작용**  
  - 과도한 게이트는 기회 손실(캐시 비중 증가) / 과최적화 위험(게이트 규칙이 데이터에 맞춰질 수 있음).
- **최소 실험(아래 공용 실험 E4 사용)**: E4 (+E3로 비용 포함)  
- **PASS 조건**  
  - `worst_mdd` 개선(또는 `oos_min` 개선)  
  - 노출이 “불연속 점프” 대신 규칙 기반으로 설명 가능(리포트에 게이트 발동률/상태전이 포함)

---

### 5) **유니버스(미국주식 Tech+Healthcare 8~14) 고정 + 서바이버십/상폐/티커변경 처리 (서바이버십 점검)**
- **왜 필요**  
  - “현재 살아남은 대형주만”으로 백테스트하면 서바이버십 편향이 OOS에서 no-delta/불안정으로 나타남.  
  - 최소 48시간 루프에서는 **고정 8~14 종목 + 상폐/티커변경 방어 로직**을 먼저 깔아야 운영 리스크가 줄어듦.
- **위험/부작용**  
  - 고정 유니버스는 분산이 줄고 특정 종목 리스크가 커질 수 있음(그래서 리스크 게이트/비중제한이 필수).
- **최소 실험(아래 공용 실험 E5 사용)**: E5 (+E2/E3로 정합성·비용 동시)  
- **PASS 조건**  
  - 유니버스가 런마다 흔들리지 않고(재현 가능), 결측/상폐 이벤트에서 **백테스트 중단 없이** “중립 처리(현금화/대체 규칙)” 수행  
  - 종목 수가 항상 8~14 범위를 유지

## 48시간 자동 루프용 “실행 가능한 Patch/실험” 5개(케이스 폭발 방지)
아래 E1~E5만 돌리면 위 TOP5를 전부 커버하도록 구성.

---

### E1) **리밸런스/런 메타데이터 표준화 Patch**
1) **실험 정의**
- 리밸런스 로그를 **JSONL 단일 포맷**으로 저장(권장 스키마: timestamp, symbol, target_w, prev_w, qty, price, cost_bps, reason, gate_state).
- `run_hash/lane_hash`, `worst_mdd`, `turnover`, `total_cost_bps`를 결과 JSON에 강제 기록.
- `aub_rebalance_pinpoint.py`가 `--base-log`에 파일 미존재 시 **즉시 실패 + Next Commands에 수정 커맨드 출력**(침묵 실패 금지).

2) **게이트(실험 통과 조건)**
- `rebalance_pinpoint`가 base/cand 둘 다에서 리밸런스 diff 리포트 생성(에러 0).
- Champion 산출물에 `worst_mdd != None`, `run_hash != None`, `lane_hash != None`.

3) **기대 관측치**
- “성능이 안 움직임”을 **리밸런스/노출/게이트 발동/비용** 단위로 분해 가능해짐.
- degenerate fold/데이터 누락이 있으면 즉시 로그에서 표출.

---

### E2) **시점 정합성(Execution lag) + Purged/Embargo CV + Degenerate fold 제거 Patch**
1) **실험 정의**
- 모든 피처/라벨을 **주문 시점 기준으로 1-bar(또는 1-day) 지연** 적용(예: 오늘 종가로 내일 시가/종가 체결).
- Purged K-fold(시간축) + embargo(예: 5~10 bar)를 적용해 정보누수 차단.
- fold 생성 시 데이터 부족/상수 타깃 등 “퇴화 조건”을 탐지해 fold를 자동 제외하지 말고 **실패로 처리**(원인 고치기).

2) **게이트**
- `degenerate_folds == []`
- “피처 타임 > 주문 시점” 위반 0
- 각 fold에 대해 표본 수/타깃 분산/클래스 비율(또는 수익률 분산)이 최소 기준 이상

3) **기대 관측치**
- OOS mean이 단기 하락할 수 있으나, fold별 변동/왜곡이 줄고 재현성이 상승.
- “no-delta”가 누수 제거로 인한 신호 붕괴인지, 평가계 문제였는지 즉시 판별.

---

### E3) **거래비용/턴오버 상시 반영 + 비용 미반영 런 차단 Patch**
1) **실험 정의**
- 비용 모델을 고정: (예) 왕복 6~15bps + 스프레드/슬리피지(가격×bps) + 최소 수수료(옵션/공매도는 이번 범위 밖이면 금지).
- 포지션 변경량 기반 `turnover` 계산을 표준화하고 리포트에 강제 포함.
- 비용 파라미터가 비활성화된 런은 **실패로 처리**.

2) **게이트**
- 결과물에 `net_return`, `gross_return`, `total_cost_bps`, `turnover` 필수 포함
- `turnover`가 상한(예: 일 30~60% 같은 내부 기준) 초과 시 FAIL(운영 불가)

3) **기대 관측치**
- “개선이 비용에 먹히는지”가 바로 보임.
- 이후 전략 패치(E4/E5)가 비용을 줄이는 방향으로 유도됨.

---

### E4) **ETF 관측지표 기반 레짐/노출 게이트 Patch (매매는 개별주만)**
1) **실험 정의**
- 관측지표(매매 금지): SPY/QQQ/XLK/XLV(+VIX 대체 지표 가능)를 사용해 **노출 스케일**만 결정.  
  - 예: (SPY 추세 양호 AND 변동성 낮음) → exposure=1  
  - 중립 → exposure=0.5  
  - 위험 → exposure=0~0.25
- 게이트는 룰 1~2개로 단순화(과최적화 방지), 로그에 gate_state 기록(E1 연동).

2) **게이트**
- `worst_mdd` 또는 `oos_min` 개선(최소 기준을 고정)
- 게이트 발동률이 극단적이지 않음(항상 0 또는 항상 1이면 FAIL)

3) **기대 관측치**
- 하방 꼬리(oos_min) 개선, 드로우다운 완화.
- 노출 변동의 원인이 “게이트 상태”로 설명 가능.

---

### E5) **Tech+Healthcare 8~14 종목 고정 유니버스 + 상폐/티커변경 방어 Patch**
1) **실험 정의**
- 고정 유니버스(예시 14개, 필요시 8~14로 축소):  
  - Tech: AAPL, MSFT, NVDA, AMZN, GOOGL, META, AVGO, ORCL  
  - Healthcare: UNH, LLY, JNJ, MRK, ABBV, TMO  
- 데이터 결측/거래정지/상폐/티커변경 발생 시:  
  - 즉시 해당 종목 목표비중 0으로 강제(현금화) + 이벤트 로그 기록  
  - 포트폴리오가 8개 미만으로 떨어지면 비중을 현금으로 둠(억지 대체 종목 금지: 누수/편향 방지)

2) **게이트**
- 백테스트가 이벤트 상황에서도 중단 없이 완료
- 런 간 유니버스가 완전히 동일(재현성), 종목 수 8~14 유지(미만이면 현금 처리 로그가 있어야 PASS)

3) **기대 관측치**
- 서바이버십/데이터 이슈로 인한 “가짜 안정성” 감소.
- 운영 중 장애(데이터 결측으로 런 실패) 급감.

---

## 성능이 안 움직일 때 원인 분해 아이디어 (트리거/적용/노출/비용/레짐) — 실행 체크리스트
아래는 “no-delta”를 **재현 가능하게 쪼개는** 순서(상단일수록 우선).

1) **트리거(신호 발생) 문제**
- 신호 발생 횟수/종목별 히트율을 로그로 고정 출력(E1).
- “신호가 거의 안 뜸” vs “신호는 뜨는데 수익이 안 남”을 분리.

2) **적용(Execution/정렬) 문제**
- 피처 타임스탬프와 체결 타임스탬프를 나란히 저장(E2).  
- 체결이 항상 다음 바로 이동했는지(지연 적용) 검증: 위반 0이어야 함.

3) **노출(Exposure/제약) 문제**
- `exposure_min/max`만 보지 말고, **시간에 따른 exposure 히스토그램**을 저장(E1).  
- 상한/하한 제약이 너무 강해 “대부분 현금”이면 전략이 아무리 좋아도 no-delta.

4) **비용(턴오버/슬리피지) 문제**
- 비용을 gross 대비 몇 % 먹는지(=cost_drag) 고정 출력(E3).  
- 종목별/리밸런스별 비용 상위 10건을 출력(E1+E3).

5) **레짐(시장 상태) 문제**
- 관측지표로 레짐 라벨을 붙여서 성과를 조건부로 분해(E4):  
  - Risk-on / Neutral / Risk-off 별 OOS mean, oos_min, mdd를 따로 출력.  
- 레짐별로 성과가 “한쪽만 좋음”이면 노출 게이트가 정답이고, “전부 나쁨”이면 신호 자체 문제.

6) **서바이버십/데이터 품질 문제**
- 결측/정지/상폐 이벤트 카운트를 리포트 최상단에 고정(E5).  
- 특정 기간만 유난히 결측이 많으면 그 기간 성과가 무의미할 수 있음.

---

## 24~48시간 실행 순서(권장)
1) **E1 먼저 적용 → 관측 가능 상태 확보**  
2) **E2 적용 → 누수/퇴화 fold 제거**  
3) **E3 적용 → 비용/턴오버 상시 반영**  
4) **E4 적용 → 레짐 기반 노출 스케일링**  
5) **E5 적용 → 유니버스/서바이버십 운영 방어**

이 5개만으로, 현재 로그 에러/퇴화 fold/비용 미반영/레짐 미반영/운영 리스크를 한 번에 우선 정리하면서 “왜 성능이 안 움직이는지”를 48시간 루프에서 계속 좁혀갈 수 있다.
