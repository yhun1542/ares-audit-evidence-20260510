# 1) TOP5 우선순위 제안(24~48h)

## P1. 데이터 누수(lookahead) / 라벨-피처 정렬 깨짐 “최우선 봉쇄”
### (a) 왜 필요한지
- 현재 상태에 **worst_mdd: None** 같이 “리스크 지표 미산출/미기록” 신호가 있고, “No-Delta Diagnoser”가 **9 experiments**를 찾았는데도 **성능이 안 움직이는 상황**은 누수/정렬 오류가 있어도 흔히 발생한다(특히 피처 시프트/리밸런스 시점).
- 누수는 OOS 평균을 가짜로 끌어올리거나, 반대로 게이트에서 다 죽여 “no-delta”처럼 보이게 만들 수 있다.

### (b) 위험/부작용
- 누수 봉쇄 패치 후 단기적으로 성능이 급락할 수 있음(정상 반응일 수 있음).
- 과거 챔피언과의 비교가 “동일 평가 파이프라인”이 아니면 혼선 발생.

### (c) 최소 실험(아래 E1~E5 재사용)
- **E1(Leakage Sentinel)**: 피처를 의도적으로 +1일/−1일 시프트한 A/B
- **E3(Rebalance Replay/로그)**: 실제 의사결정 시점(T-1 close? T open?)이 코드와 로그에 일치하는지 확인

### (d) PASS 조건(게이트)
- E1에서 **+1일 시프트 모델 성능이 명확히 붕괴**해야 함(예: OOS mean이 0 근처로 급락, 최소 성능도 동반 악화).  
  붕괴가 없으면 **누수 의심 → 즉시 FAIL**.
- 리밸런스 타임스탬프가 **“의사결정 시점 < 체결 시점”**을 항상 만족(로그로 검증). 위반 시 FAIL.

## P2. 비용(슬리피지/스프레드/차입/리밸런스) 미반영/과소반영 “강제 현실화”
### (a) 왜 필요한지
- Tech+Healthcare 12종목이라도 리밸런스 잦으면 비용이 수익을 잠식한다.
- 현재 로그에서 **rebalance pinpoint가 입력 파싱 실패** → 비용/턴오버를 제대로 계측 못하고 있을 확률이 높다(운영 리스크 + 성능 no-delta 원인).

### (b) 위험/부작용
- 비용을 현실화하면 성능이 하락(정상). 다만 **비용 민감도가 과도**하면 전략 구조 자체가 불안정.
- 차입비용/헤지 비용을 넣으면 “헤지로 개선”처럼 보이던 효과가 사라질 수 있음.

### (c) 최소 실험
- **E2(Cost Stress Test)**: 비용 0 / 기본 / 2배(또는 3배) 스트레스
- **E3(Rebalance Replay/로그)**: 턴오버/체결횟수/체결가 산출이 실제로 기록되는지 확인

### (d) PASS 조건
- 비용 0 → 기본 비용으로 갈 때 성능 하락이 **합리적 범위**여야 함  
  (예: OOS mean이 “조금” 낮아지되, **기본 비용에서도 양(+)** 유지. 비용 2배에서는 감소하되 완전 붕괴까지는 아니거나, 붕괴 시 턴오버가 원인임을 로그로 설명 가능해야 함).
- 턴오버, 거래횟수, 추정 슬리피지/비용이 **매 리밸런스마다 로그로 산출**되어야 함(누락 시 FAIL).

## P3. 운영/관측성(Observability) 결함 즉시 수리: 리밸런스 로그/아티팩트 포맷 “단일화 + 하드 게이트”
### (a) 왜 필요한지
- 현재 메시지:  
  - `Error loading --base-log: No such file`  
  - `Expecting value: line 1 column 1`  
  → **리밸런스 데이터가 없거나 포맷이 깨짐**.  
- 이 상태에서 “성능이 안 움직임”은 **원인 분해 불가**(트리거/노출/비용/레짐 어느 쪽도 확인 불가).

### (b) 위험/부작용
- 로그를 강제하면 런타임/디스크 비용 증가.
- “하드 게이트” 도입으로 일시적으로 실험이 많이 FAIL될 수 있음(정상: 나쁜 실험을 조기에 막는 효과).

### (c) 최소 실험
- **E3(Rebalance Replay/로그 단일화)**: csv/jsonl 둘 다 쓰지 말고 하나로 고정 + 스키마 검증
- **E5(Exposure/Regime Gate)**: worst_mdd가 None이면 즉시 FAIL하도록 게이트 추가(지표 미산출 런 차단)

### (d) PASS 조건
- `aub_rebalance_pinpoint`가 **입력 2종(베이스/캔드) 모두 성공적으로 로드**하고 리포트를 생성해야 함.
- 매 런에서 최소 다음 필드가 존재(없으면 FAIL):
  - timestamp(의사결정/체결 분리), symbol, side, target_weight, filled_price(또는 모델), shares/notional
  - turnover, estimated_cost, gross_exposure, net_exposure
  - **worst_mdd (None 금지)**

## P4. 서바이버십/유니버스 편향 차단: “PIT 유니버스 + Corporate Action 정합성” 고정
### (a) 왜 필요한지
- 유니버스가 매번 바뀌거나(선정 로직), 상장폐지/병합/스플릿 반영이 비일관이면 성능이 **안 움직이거나**(신호가 랜덤화) **가짜로 좋아질 수 있음**(서바이버십).
- 48시간 자동 루프에서는 **유니버스 고정(12종목)**이 원인 분리를 가장 빠르게 만든다.

### (b) 위험/부작용
- 유니버스 고정은 “확장성”을 잠시 포기(단기 디버그 목적).
- PIT(시점가용) 데이터 요구가 커져 데이터 파이프 비용 증가 가능.

### (c) 최소 실험
- **E4(PIT+Liquidity 고정 유니버스 실험)**: 위 12종목만으로 end-to-end 재평가
- **E1(Leakage Sentinel)**: PIT 유니버스에서도 누수 센티널이 정상 작동하는지 재확인

### (d) PASS 조건
- 고정 유니버스에서도 성능/비용/노출/리밸런스 로그가 **완전 재현**되어야 함(재현성 확보).
- corporate action 반영(스플릿/배당 조정)의 기준이 명시되고, 가격/수익률 산출이 **단일 정의**로 고정되어야 함(정의 흔들리면 FAIL).

## P5. 노출(Exposure)/헤지/레짐 게이트로 과최적화 억제 + “no-delta” 원인 분해 가능화
### (a) 왜 필요한지
- 현재 노출 범위가 **0.47 ~ 0.84**로 보이는데(무슨 노출인지 정의 필요하나), 자동 루프에서는 노출 드리프트가 성능을 가리거나, 반대로 성능을 “헤지 착시”로 만들 수 있다.
- 레짐(변동성/금리/성장주 충격)에서 “항상 같은 반응”이면 성능이 정체(no-delta)로 보인다.

### (b) 위험/부작용
- 게이트가 너무 강하면 거래 빈도/기회가 감소해 수익 감소.
- 변동성 타겟이 비용을 올릴 수 있음(잦은 리밸런스).

### (c) 최소 실험
- **E5(Exposure/Regime Gate + Vol targeting)**: gross/net, sector, single-name cap 강제
- **E2(Cost Stress)**: 노출 제약 후 비용 민감도 재측정

### (d) PASS 조건
- gross/net 노출, single-name max weight, 섹터 비중이 항상 제약 내.
- worst_mdd가 산출되고(필수), OOS min이 악화되지 않거나(또는 악화 시 비용/레짐 로그로 설명 가능).
- 비용 2배 스트레스에서도 “전략 로직이 완전 붕괴”하지 않고, 붕괴 시 원인이 **턴오버/노출/레짐 중 하나로 특정** 가능해야 함.

# 2) 48시간 자동 루프용 “실행 실험” 5개(E1~E5)
각 실험은 (1)정의 (2)게이트 (3)기대 관측치로 고정한다.

---

## E1. Leakage Sentinel (피처/라벨/체결 시점 누수 탐지)
1) **실험 정의**
- 동일 코드에서 피처를 **−1일 / +1일 시프트**한 두 런을 추가 생성
- “의사결정 시점” 기준으로 피처가 미래를 보지 않도록 강제(shift 방향별 성능 비교)

2) **게이트**
- **+1일 시프트 성능 붕괴**가 없으면 FAIL(누수 강력 의심)
- −1일 시프트는 보통 성능 악화/완만 악화가 정상(오히려 개선되면 정렬 정의 재검토)

3) **기대 관측치**
- +1일 시프트: OOS mean 급락, 히트레이트/IC가 비정상 변화
- 정상 파이프라인이면 “미래 정보 주입”이 사라져 성능이 크게 꺾임

---

## E2. Cost Stress Test (비용 민감도/턴오버 구조 확인)
1) **실험 정의**
- 동일 리밸런스/신호에서 비용만 3단계:
  - C0: 0
  - C1: 기본(스프레드+슬리피지+수수료+차입비용)
  - C2: 2배(또는 3배) 스트레스

2) **게이트**
- C1에서 **여전히 양(+)의 OOS mean**(또는 최소한 “전략이 비용에 먹히지 않는 구조”임을 로그로 증명)
- C2에서 붕괴 시에도 원인이 **턴오버/체결횟수/슬리피지**로 계량 가능해야 함(로그 누락이면 FAIL)

3) **기대 관측치**
- 비용 증가에 따라 성능이 단조 감소
- 턴오버가 높은 구간/종목이 명확히 드러남

---

## E3. Rebalance Replay + 로그 포맷 단일화(운영 리스크 제거)
1) **실험 정의**
- 리밸런스 산출물을 **단일 포맷(jsonl 권장)**으로 저장하고 스키마 검증
- base/candidate 각각 리밸런스 로그를 남겨 `aub_rebalance_pinpoint`가 비교 가능하게 함
- 파일 경로를 “런 아티팩트 디렉토리” 아래로 강제(상대경로/깨진 `--base-log` 제거)

2) **게이트**
- 리밸런스 로그 **파싱 실패 0건**
- 리밸런스 이벤트 수, turnover 합계가 백테스트 요약과 일치(불일치 시 FAIL)

3) **기대 관측치**
- “성능 no-delta”의 원인이 **리밸런스가 실제로 거의 없었는지**, 또는 **리밸런스는 있는데 비용/체결이 누락**인지 즉시 분해됨

---

## E4. PIT 고정 유니버스(12종목) + 유동성/코퍼레이트액션 정합성
1) **실험 정의**
- 위 12종목만 거래(48h 동안 유니버스 고정)
- 가격/수익률 계산 정의 단일화(Adj Close/Total Return 중 하나로 고정)
- 유동성 필터는 “경고 로그”만 남기고(거래 차단 X) 원인 관측에 집중

2) **게이트**
- 유니버스 변동 0(고정)
- 결측/정지/스플릿 이벤트 발생 시 처리 규칙이 로그로 남아야 함(없으면 FAIL)

3) **기대 관측치**
- 유니버스/데이터 변동성이 제거되어 신호/비용/노출의 문제로 원인이 수렴

---

## E5. Exposure/Regime 게이트 + 리스크 지표 강제 산출(worst_mdd None 금지)
1) **실험 정의**
- gross/net 노출 캡, single-name max weight, 섹터(Tech/HC) 내 비중 밴드 고정
- 변동성 타겟(예: 포트폴리오 ex-ante vol 목표) 또는 드로우다운 가드(소프트) 중 1개만 적용
- 리스크 지표(worst_mdd 등) 계산을 “필수”로 승격

2) **게이트**
- worst_mdd **반드시 수치로 산출(None 금지)**
- 노출/비중 제약 위반 0
- 제약 추가 후에도 리밸런스/비용 로그가 정상 산출(누락 시 FAIL)

3) **기대 관측치**
- 성능이 안 움직이던 원인이 “노출 드리프트/레짐 노출”인지 가시화
- 최소 성능(oos_min)과 MDD의 안정화 여부가 관측됨

# 3) 성능이 안 움직일 때 “원인 분해” 아이디어(트리거/적용/노출/비용/레짐)
아래를 **명령형 체크리스트**로 1회전(48h)마다 자동 출력/저장하도록 고정하라.

## A. Trigger(신호 발생) 문제
- [ ] 신호 발생률(% days with non-zero target)과 종목별 신호 빈도를 기록하라.
- [ ] IC/RankIC(신호 vs 다음 구간 수익률)를 종목별/전체로 기록하라.
- [ ] 신호가 0에 붙어있거나(클리핑) 상수화되면 즉시 FAIL 처리하라.

## B. Apply(포지션 적용/리밸런스) 문제
- [ ] “의사결정 시점”과 “체결 시점”을 분리 로그로 남겨라(동일하면 FAIL).
- [ ] 타깃 가중치 → 실제 체결 가중치 오차(슬리피지/체결불가)를 기록하라.
- [ ] 리밸런스 이벤트 수가 0 또는 비정상적으로 낮으면(전략이 사실상 비활성) FAIL 플래그를 세워라.

## C. Exposure(노출) 문제
- [ ] gross/net 노출 시계열, 종목 최대 비중, 섹터 비중(Tech/HC)을 저장하라.
- [ ] 노출이 좁은 구간에 고정(예: 항상 0.5 근처)되면 포지션 사이징/스케일러 버그를 의심하라.
- [ ] 헤지가 있다면(지표용 ETF는 거래 금지지만, 내부 헤지 로직이 있으면) 헤지 노출/차입비용을 분리 기록하라.

## D. Cost(비용) 문제
- [ ] turnover(일/주/리밸런스별), 거래횟수, 추정 슬리피지, 총비용을 분리 저장하라.
- [ ] “비용=0”에서만 좋아지고 기본 비용에서 죽으면, 전략을 **턴오버 구조 개선** 대상으로 분류하라(신호 개선이 아니라 구조 개선).

## E. Regime(레짐) 문제
- [ ] 관측 지표로 SPY/QQQ/XLK/XLV 수익률, VIX(가능하면)를 함께 저장하라.
- [ ] 레짐별(저변동/고변동, QQQ 상승/하락)로 성능을 분해 출력하라.
- [ ] 특정 레짐에서만 작동하면 “레짐 필터”를 전략 구성요소로 승격하되, 다음 루프에서는 **필터 1개만** 실험하라(E5에 포함).

## 즉시 적용할 “하드 게이트”(운영 안정성)
- [ ] worst_mdd가 None이면 런을 **즉시 FAIL** 처리하라.
- [ ] 리밸런스 로그 파싱 실패(0바이트/JSON 깨짐/경로 누락) 시 런을 **즉시 FAIL** 처리하라.
- [ ] 비용/턴오버 로그가 한 항목이라도 누락되면 런을 **즉시 FAIL** 처리하라.
