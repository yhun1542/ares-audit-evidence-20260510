## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — **명령형 체크리스트**
우선 점검 순서: **누수 → 과최적화 → 서바이버십 → 비용 미반영 → 운영 리스크**

---

### 1) **리밸런스/실험 로그 체인 복구(운영 리스크 최우선)**
**(a) 왜 필요한지**
- `aub_rebalance_pinpoint`가 **입력 경로 오류(`--base-log` 문자열 그대로) + CSV/JSON 파싱 실패**로 작동 중단.
- `worst_mdd: None` → 핵심 리스크 지표가 계산/저장되지 않는 상태 가능(평가 파이프라인 불완전).
- 성능 “안 움직임”이 **전략 문제가 아니라 관측/로깅 단절**일 수 있음.

**(b) 위험/부작용**
- 로깅 포맷 변경 시 과거 아티팩트와 호환성 깨질 수 있음.
- 리밸런스 로그가 커져 저장/IO 비용 증가.

**(c) 최소 실험(아래 공통 실험 중에서만 사용) 2~3개**
- **E1(필수)** 리밸런스 로그/경로/포맷 표준화 패치 적용
- **E2(권장)** 비용모델 로그까지 함께 기록(거래비용 검증)
- **E4(선택)** 노출/턴오버 게이트를 로그로 확인(관측 가능성 확보)

**(d) PASS 조건**
- `rebalance_pinpoint`가 **Base/Cand 모두에서** 리밸런스 이벤트를 읽고, “No rebalance data found”가 **0회**.
- `worst_mdd`가 **항상 실수값으로 산출**(None 금지)되고 리포트에 포함.
- 48시간 루프 동안 **실험 결과가 동일 조건 재실행 시 재현 가능(해시/seed 고정)**.

---

### 2) **거래비용/슬리피지/턴오버 미반영 제거(비용 리스크)**
**(a) 왜 필요한지**
- 지금 OOS가 움직이지 않거나 “좋아 보이는데 실거래에서 붕괴”의 1순위 원인: **비용 미반영 + 과도한 턴오버**.
- Tech+Healthcare 8~14종목 집중은 리밸런스 빈도/체결영향에 취약.

**(b) 위험/부작용**
- 비용을 넣으면 OOS 평균이 하락할 수 있음(하지만 “진짜 성능”에 수렴).
- 비용모델을 과하게 잡으면 보수적으로 변해 기회 손실.

**(c) 최소 실험 2~3개**
- **E2(필수)** 비용모델 On + 슬리피지(스프레드/충격) + 최소 커미션
- **E4(권장)** 턴오버 상한/리밸런스 스로틀로 비용 민감도 확인

**(d) PASS 조건**
- 비용 반영 후에도 **cost-adjusted OOS mean**이 베이스 대비 **-5% 이내**(방어적 기준) 또는 **+0% 이상**(공격적 기준).
- 연환산 턴오버가 설정 상한(예: 4~12x/yr 범위) 내.
- 비용 로그가 “추정치/실제체결가정/턴오버”로 분해되어 리포트에 출력.

---

### 3) **데이터 누수/시간정렬/피처 생성 체인 검증(누수 리스크)**
**(a) 왜 필요한지**
- OOS “정체”는 누수와 반대처럼 보이지만, 실제로는 **누수 방지 패치/리샘플링 변화**로 신호가 사라져 정체될 수 있음.
- Tech/Healthcare 팩터(모멘텀/리비전/퀄리티)에서 **발표일/리포팅 지연(lookahead)** 누수가 자주 발생.

**(b) 위험/부작용**
- 누수 제거하면 성능이 단기 하락 가능(정상).
- 너무 보수적인 lag 적용은 신호를 약화.

**(c) 최소 실험 2~3개**
- **E3(필수)** “as-of join”/발표지연 lag 강제 + 피처 시점 스냅샷
- **E5(선택)** 레짐별 성능 분해로 “누수 제거 후 어느 레짐에서만 사라졌는지” 확인

**(d) PASS 조건**
- 모든 피처가 `t` 시점에 **`t` 이전 정보만** 사용했음을 자동검증(샘플링/조인 테스트 통과율 100%).
- Lag(예: 1~5거래일) 변경에도 성능이 “0으로 붕괴”하지 않고 완만히 변화(누수 의심 완화).
- Fold별 degenerate(현재는 empty 유지)가 계속 empty.

---

### 4) **서바이버십/유니버스 고정(US Tech+Healthcare 8~14) + 리컨스티튜션 규칙화**
**(a) 왜 필요한지**
- 8~14개 종목 집중은 **유니버스 구성 규칙**이 성능을 좌우(서바이버십/리컨스티튜션 편향).
- ETF는 매매 제외지만 **XLK/XLV는 관측지표로 사용**해야 레짐/섹터 드리프트를 분리 가능.

**(b) 위험/부작용**
- 유니버스를 너무 엄격히 고정하면 신호가 줄어 성능 하락.
- 리컨스티튜션 주기 변경은 턴오버/비용 증가.

**(c) 최소 실험 2~3개**
- **E3(필수)** 유니버스 생성 시 “당시점 구성 가능 종목만” + 상장폐지 처리 + 가격/볼륨 필터를 `as-of`로 고정
- **E4(선택)** 종목 수 8/10/12/14 중 **딱 2개 값만** 비교(케이스 폭발 금지: 예 10 vs 14)

**(d) PASS 조건**
- 백테스트에서 “미래에만 존재하는 티커”가 0건.
- 리컨스티튜션 이벤트 로그가 남고(편입/편출/사유), 편출 종목 수익률 처리(상장폐지/합병) 규칙이 문서/코드로 일치.
- 종목 수 변화(10→14) 시 비용/턴오버와 성능이 논리적으로 동반 변화(비정상 점프 없음).

---

### 5) **노출/헤지/리스크 게이트(과최적화+운영 안정성)**
**(a) 왜 필요한지**
- 현재 노출 min/max가 약 **0.47~0.84**로 “항상 들고 있음”에 가깝고, 레짐 변화에서 MDD가 커질 수 있음.
- `worst_mdd: None` 상태면 리스크 게이트가 사실상 작동 불능.

**(b) 위험/부작용**
- 게이트가 과도하면 수익 기회 감소.
- 헤지(지수/섹터)는 “매매 제외(ETF)” 제약이 있으므로 **관측 기반의 현금 비중 조절** 쪽으로 설계해야 함(ETF 거래 금지 준수).

**(c) 최소 실험 2~3개**
- **E4(필수)** 노출/변동성 타깃/최대 드로다운 기반 “현금 비중 게이트”
- **E5(권장)** 레짐(금리/변동성/섹터 상대강도)에서 게이트가 언제 켜지는지 관측

**(d) PASS 조건**
- `worst_mdd`가 기준(예: -20% 이내)으로 관리되거나, 베이스 대비 **악화 금지**.
- 노출이 레짐 악화 시 자동으로 내려가며(예: 0.8→0.4), 그 이벤트가 로그로 남음.
- OOS min(하방) 악화가 베이스 대비 -5%p 이상 나빠지지 않음.

## 공통 “실행 가능한 patch/실험” 5개만 운용 (48시간 자동 루프 형태)
아래 **E1~E5만** 돌리고, 각 우선순위는 이 실험들을 조합해 검증한다.

---

### E1) Rebalance/Metric Logging 표준화 패치 (운영 복구)
**(1) 실험 정의**
- 리밸런스 이벤트를 **항상 JSONL**로 기록: `timestamp, universe, target_weights, current_weights, trade_list, turnover, est_cost, reason_codes`
- `aub_rebalance_pinpoint.py` 입력을 “문자열 `--base-log`”가 아니라 **실제 파일 경로**로 강제 검증.
- `worst_mdd`를 계산/저장 파이프라인에 강제(없으면 실패 처리).

**(2) 게이트**
- 실행 시작 시: `base_log`/`cand_log` 존재 확인 + 확장자/첫 라인 JSON 검사 통과 못 하면 즉시 FAIL.
- 리밸런스 이벤트 1건 이상 기록되지 않으면 FAIL(전략이 “리밸런스 없음”이면 그 사유코드 필수).

**(3) 기대 관측치**
- `rebalance_pinpoint.md`에 “구간별 리밸런스 차이/턴오버/비용”이 표로 출력.
- `worst_mdd`가 None → 실수값으로 전환.

---

### E2) 비용모델 On (수수료+슬리피지+턴오버 분해)
**(1) 실험 정의**
- 비용을 `commission + spread_slippage + impact`로 분해 적용.
- 결과 리포트에 **gross vs net**(비용 차감 전/후) 모두 출력.

**(2) 게이트**
- net 성과가 gross 대비 비정상적으로 개선되면(비용 부호 오류) FAIL.
- 비용이 0으로 고정되면 FAIL(거래가 있는데 비용 0은 버그).

**(3) 기대 관측치**
- 턴오버가 높은 구간에서 net 성과가 합리적으로 하락.
- 성능 정체의 원인이 “비용에 의해 상쇄”인지 바로 드러남.

---

### E3) 누수/서바이버십 방지: as-of 유니버스+피처 스냅샷
**(1) 실험 정의**
- 모든 데이터 조인을 “as-of(시점 기준)”로 강제.
- 펀더멘털/리비전/이벤트성 데이터는 발표 지연 lag(예: 2영업일) 기본 적용.
- 유니버스는 US Tech+Healthcare에서 **당시점 거래 가능(가격/볼륨) + 상장폐지 처리** 포함.

**(2) 게이트**
- 랜덤 샘플 N건에 대해 “피처 타임스탬프 ≤ 거래결정 시점” 위반 0건.
- 미래 티커 참조 0건.

**(3) 기대 관측치**
- 성과가 일부 하락해도 fold 간 분산이 줄고, OOS min이 안정화되는 패턴이 나오면 정상.
- 성능 정체가 “누수 제거에 따른 신호 약화”인지 확인 가능.

---

### E4) 노출/턴오버 게이트(현금비중) + 종목수 10 vs 14 2점 비교
**(1) 실험 정의**
- 포지션 수: **10 vs 14**만 비교(2점만).
- 게이트: (a) 최대 노출 상한, (b) 변동성 타깃, (c) 턴오버 상한 초과 시 리밸런스 스로틀(현금 유지).

**(2) 게이트**
- 노출 min/max가 설정 범위를 벗어나면 FAIL.
- 턴오버 상한 초과가 반복되면 FAIL(전략이 게이트를 무시).

**(3) 기대 관측치**
- 비용모델(E2) 적용 시, 턴오버 억제 전략이 net 성과에서 상대 우위.
- 레짐 악화 구간에서 노출이 자동 하향하고 MDD가 완화.

---

### E5) 레짐/드리프트 관측(ETF는 “지표”로만 사용)
**(1) 실험 정의**
- 거래는 US 개별주(Tech+Healthcare)만.
- 관측 지표로만: **XLK, XLV, QQQ, IWM, VIX(또는 VIX proxy)**의 추세/변동성/상대강도.
- 리포트에 “레짐 버킷(저변동/고변동, 성장우위/방어우위)”별 성과를 자동 분해.

**(2) 게이트**
- 레짐 분해가 데이터 부족/결측으로 실패하면 FAIL(관측 파이프라인 문제).
- 동일 레짐에서 성과가 극단적으로 출렁이면(표본 부족 경고) WARN 표시 필수.

**(3) 기대 관측치**
- “왜 성능이 안 움직이는지”가 레짐별로 드러남: 신호는 특정 레짐에서만 유효/무효.
- E4 게이트가 켜지는 조건이 레짐과 정렬되는지 확인.

---

## 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐)
아래를 **순서대로** 잘라서 확인(관측 불가하면 E1부터 복구).

### A. Trigger(신호 생성) 문제
- **증상**: 예측/스코어 분포가 시간에 따라 거의 동일, 상위/하위 구분 약함.
- **조치**: 스코어 분산, 상관(전일/전주), 상위-하위 기대수익(그로스)을 리포트에 고정 출력(E3/E5).

### B. Apply(적용/매핑) 문제
- **증상**: 스코어는 움직이는데 포트폴리오 타깃 웨이트가 안 변함(또는 반대로 과도 변동).
- **조치**: `score → rank → weight` 단계별 로그(상위 N, weight clip, 제한조건 충돌) + 리밸런스 reason code(E1).

### C. Exposure(노출/제약) 문제
- **증상**: 노출이 항상 0.47~0.84 같은 좁은 범위에 고정, 레짐 변화에 무감.
- **조치**: 노출/현금비중이 레짐 지표에 반응하는지(E4/E5), 제약 충돌 시 어떤 제약이 바인딩인지 로그.

### D. Cost(비용) 문제
- **증상**: gross는 개선인데 net이 정체/악화, 고턴오버 구간에서만 무너짐.
- **조치**: 비용 분해(commission/spread/impact), 턴오버 히스토그램, 리밸런스 빈도(E2/E4).

### E. Regime(레짐) 문제
- **증상**: 특정 시기만 잘 되고 최근 구간에서만 정체(성장→가치, 금리, 변동성).
- **조치**: XLK/XLV 상대강도, VIX 레벨/변화율로 버킷팅한 레짐별 성과(E5). 레짐별로 “신호/게이트” 둘 다 분해.

---

## 48시간 루프 운용 순서(고정)
1. **E1 먼저 실행** → 로깅/리밸런스/리스크지표(worst_mdd) 복구 없으면 나머지 중단  
2. **E2+E3 병행** → “비용 반영 + 누수/서바이버십 차단” 상태의 기준선 생성  
3. **E4 실행** → 노출/턴오버 게이트로 net 안정화 테스트(종목수 10 vs 14만)  
4. **E5 실행** → 정체 원인을 레짐으로 라벨링하고 다음 패치 방향을 좁힘  

이 구성으로 24~48시간 내에 “전략이 안 좋아서 정체인지 / 관측·비용·누수·유니버스·게이트 중 어디서 죽는지”를 강제로 분리할 수 있다.
