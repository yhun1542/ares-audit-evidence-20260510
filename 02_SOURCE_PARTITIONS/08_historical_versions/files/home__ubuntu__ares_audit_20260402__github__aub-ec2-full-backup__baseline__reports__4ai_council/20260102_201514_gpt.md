아래는 **다음 24~48시간**에 바로 돌릴 수 있는 **명령형 체크리스트(Top5 우선순위)**다. 우선순위는 **누수 → 과최적화/폴드 붕괴 → 비용 미반영 → 운영/로그 리스크 → 레짐 리스크** 순으로 잡았다.  
또한 “제안(실행 patch/실험)”은 **총 5개(E1~E5)**로 제한하고, 각 Top5 항목은 **이 5개 실험을 2~3개씩 재사용**해 요구사항을 충족한다. (케이스 폭발 방지)

---

## 0) 즉시 관측된 이상(ONE TRUTH 기반) — 먼저 고쳐야 “움직임”이 보임
- **degenerate_folds: [1,2,3,8]** → OOS 평균이 유의미해도 **검증 자체가 무너진 상태**일 가능성 큼.
- **rebalance pinpoint가 로그를 못 읽음**(CSV/JSON 파싱 실패) → “트리거/적용/노출” 어디서 멈추는지 추적 불가.
- **worst_mdd: None**, **lane_hash/run_hash: None** → 성능이 안 움직일 때 **재현/원인분해 불가**(운영 리스크 최상급).

---

# 실행 실험(총 5개) — 48시간 자동 루프 형태로 정의
각 실험은 (1) 실험 정의 → (2) 게이트(중단/합격 조건) → (3) 기대 관측치 로 구성.

---

## E1) 누수/폴드 붕괴 방지 “시간 정합성 패치 + Walk-forward 재검증”
### (1) 실험 정의
- **모든 피처/라벨을 as-of 시점으로 강제**:  
  - 가격/펀더멘털/이벤트성 데이터는 `t`일 종가로 계산되면 **주문은 t+1 시가/종가**로 체결되도록 시프트.
- **Purged/Embargo CV 적용**(최소 embargo 5~10 trading days): 인접 구간 누수 차단.
- **폴드 품질 리포트 출력**: fold별 샘플 수, 분산, 타깃 분포, IC(또는 hit-rate) 로그.

### (2) 게이트
- `degenerate_folds`가 **0~1개 이하**로 감소하지 않으면 **다음 실험(E2~E5) 진행 금지**(검증 기반이 무너짐).
- OOS가 개선되든 악화되든, **fold 품질 리포트가 정상 출력**되어야 PASS.

### (3) 기대 관측치
- degenerate fold 급감.
- OOS mean이 다소 내려가더라도(누수 제거로 흔함) **OOS min이 “말이 되는 범위”로 안정**.
- “왜 성능이 안 움직이는지”를 fold별로 분해 가능.

---

## E2) 비용/슬리피지/턴오버를 net 성과에 반영 (과대평가 제거)
### (1) 실험 정의
- **거래비용 모델을 net 리턴에 강제 반영**:
  - 기본: 고정 수수료 + 슬리피지(예: `k * (daily_vol) * |Δw|` 형태) + 스프레드 프록시(일정 bps).
- **턴오버/리밸 빈도/체결가 가정**을 함께 로깅.
- 결과는 **gross / cost / net**을 반드시 분리 출력.

### (2) 게이트
- `net_oos_mean`이 `gross_oos_mean` 대비 과도하게 붕괴하면(예: net이 gross의 50% 미만) **전략 자체가 비용 민감** → 이후 실험(E4/E5)은 “턴오버 감소” 방향으로만 허용.
- 최소 기준: `avg_turnover`가 사전에 정의한 상한(예: 일 20~30% 등) 초과 시 FAIL 처리(자동 중단).

### (3) 기대 관측치
- “성능이 안 움직임”이 사실은 **비용에 의해 상쇄**되는지 즉시 판별.
- 이후 모든 실험이 “현실적인 net 성과”를 기준으로 비교 가능.

---

## E3) 리밸런스/런 메타데이터 로깅 복구 (운영 리스크 제거)
### (1) 실험 정의
- **rebalance 로그를 단일 포맷으로 강제**(권장: JSONL):
  - 각 리밸 이벤트마다: timestamp, target_weights(8~14종목), prev_weights, Δw, 체결가 가정, 비용, 노출(exposure), 트리거 원인.
- **파일 경로/포맷 검증**을 “실험 시작 전”에 수행(없으면 즉시 FAIL).
- `lane_hash`, `run_hash`를 **실험 설정+데이터 스냅샷+코드 커밋 해시**로 생성해 출력.
- `worst_mdd` 계산을 파이프라인 필수 산출물로 편입.

### (2) 게이트
- `aub_rebalance_pinpoint`가 **base/cand 모두 성공적으로 로드**하고, 리포트를 생성해야 PASS.
- 동일 run_hash로 재실행 시 핵심 지표(OOS mean/min, turnover, exposure)가 **동일(오차 허용범위 내)**해야 PASS.

### (3) 기대 관측치
- “트리거는 떴는데 포지션 적용이 안 됨/노출이 0으로 잠김” 같은 케이스를 즉시 잡음.
- 성능 무변동 시 “실제로 거래가 없었는지”를 증명 가능.

---

## E4) No-Delta(리밸 불발)/노출 클램프 원인 제거 + 8~14종목 제약 준수
### (1) 실험 정의
- **트리거 히트율, 리밸 적용률, 포지션 수(holdings_count) 강제 로깅**:
  - trigger_hit_rate, rebalance_apply_rate, avg_holdings_count(목표: 8~14), exposure(min/max).
- “No-Delta Diagnoser” 결과를 이용해:
  - (a) 스케일링/헤지/클램프 때문에 Δw≈0 되는지,
  - (b) 리스크 모델/정규화에서 전부 상쇄되는지
  를 자동 판정.
- **유니버스 고정(US Tech+Healthcare, 8~14)**을 명시적으로 강제(생존편향 방지용 날짜 스냅샷 필요):
  - 예시(13종목): AAPL MSFT NVDA GOOGL AMZN META AVGO AMD / UNH LLY JNJ ABBV MRK  
  - (실험에서는 “항상 같은 리스트”를 쓰되, 향후에는 “당시 시점 상장/거래가능” 스냅샷으로 확장)

### (2) 게이트
- `rebalance_apply_rate`가 너무 낮으면(예: 5% 미만) → **전략이 실제로는 거의 안 움직이는 상태**로 간주하고 FAIL.
- `avg_holdings_count`가 8~14를 벗어나면 FAIL(요구사항 위반).
- exposure가 장기간 0 근처면 FAIL(신호/적용 문제로 분류).

### (3) 기대 관측치
- 성능이 안 움직였던 이유가 **(1) 트리거 미발생 (2) 발생했으나 적용 0 (3) 적용했으나 비용으로 상쇄 (4) 노출 클램프** 중 어디인지 단번에 분리.

---

## E5) 레짐(Tech ↔ Healthcare, 리스크-온/오프) 분해 + 최소 스위치 실험
### (1) 실험 정의
- ETF는 매매하지 말고 **관측 지표로만 사용**:
  - 관측: QQQ(Tech 베타), XLV(헬스케어 베타), VIX(변동성), IEF/TLT(금리 민감) 등.
- 간단한 레짐 스위치 1개만 시험(케이스 폭발 금지):
  - 예: `VIX > threshold` 또는 `QQQ 추세 하락`이면 **exposure 상한을 낮추고(예: 0.4)** 헬스케어 비중을 상향.
- 성과를 **레짐별 조건부로 리포트**(risk-on, risk-off 구간 분리).

### (2) 게이트
- 전체 OOS mean이 조금 내려가도, **OOS min 개선(꼬리 위험 완화)** 또는 worst_mdd 개선이 있으면 PASS.
- 레짐 분해 리포트가 없으면 FAIL(원인분해 목적 미달).

### (3) 기대 관측치
- “평균은 좋은데 최소가 나쁨” 문제를 **레짐 미스매치**로 설명/완화 가능.
- Tech 집중 구간과 Healthcare 방어 구간의 역할이 분리되어 디버깅 가능.

---

# 1) 다음 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) 제안
아래 Top5는 “무조건 이 순서로” 처리(상위가 안 되면 하위 의미가 약해짐).

---

## TOP1) 운영/로그 파이프라인 복구(리밸 로그, run_hash, MDD) — **재현/원인분해의 전제**
### (a) 왜 필요한지
- 현재 rebalance pinpoint가 **입력 파일 자체를 못 읽음** → 전략이 “안 움직이는지/움직였는데 성과가 없는지”를 구분 불가.
- worst_mdd가 None이면 **리스크 기준 의사결정 불가**.

### (b) 위험/부작용
- 로깅이 늘면 디스크/시간 비용 증가.
- 포맷 통일 과정에서 과거 리포트 호환이 깨질 수 있음(마이그레이션 필요).

### (c) 최소 실험(공유 실험 참조)
- **E3**(필수)
- **E4**(리밸 적용률/노출 로깅까지 같이)
- **E2**(리밸 로그에 비용 항목까지 포함시켜 net 분해 가능)

### (d) PASS 조건
- `aub_rebalance_pinpoint`가 base/cand 모두 로드 성공 + 리포트 생성.
- run_hash 재실행 시 핵심 지표 재현.
- worst_mdd 산출 필수화.

---

## TOP2) 누수/폴드 붕괴 제거 — OOS가 “진짜”인지부터 확정
### (a) 왜 필요한지
- degenerate_folds 다수는 **검증이 무의미**해지는 대표 신호(누수, 샘플 부족, split 오류).

### (b) 위험/부작용
- 누수 제거 후 OOS mean이 하락할 수 있음(정상).
- embargo/purge로 학습 데이터가 줄어 분산이 커질 수 있음.

### (c) 최소 실험
- **E1**(필수)
- **E3**(fold 리포트/설정이 run_hash에 포함되도록)
- **E5**(레짐별로 fold 붕괴가 특정 구간에 몰렸는지 확인)

### (d) PASS 조건
- degenerate_folds 0~1개 이하.
- fold별 분포/샘플 수/IC 리포트가 정상.

---

## TOP3) 비용 미반영 제거 — “움직여도 돈이 안 되는” 상태 차단
### (a) 왜 필요한지
- 미국주식(특히 대형 Tech)은 스프레드가 작아도 **턴오버가 크면 net 성과가 사라짐**.
- 현재 리밸 데이터가 없어서 비용/턴오버가 블라인드.

### (b) 위험/부작용
- 비용 모델 가정이 틀리면 과도 보수/낙관 가능.
- 비용 반영 후 전략이 전반적으로 죽어 보일 수 있음(현실 반영 결과).

### (c) 최소 실험
- **E2**(필수)
- **E3**(비용이벤트가 로그에 남도록)
- **E4**(턴오버가 no-delta/클램프 문제인지, 과도 리밸인지 분리)

### (d) PASS 조건
- gross/net 분리 리포트 제공.
- net 기준으로도 비교 가능한 챔피언/후보 정렬이 가능.

---

## TOP4) “성능이 안 움직임”의 1차 원인: 트리거/적용/노출 고장(No-Delta) 제거
### (a) 왜 필요한지
- diagnoser가 돌아갔다는 것은 **No-Delta가 자주 발생**했을 가능성이 높음.
- exposure max가 0.838인데도, 기간별로 0에 붙어 있으면 “거래가 사실상 없음”일 수 있음.

### (b) 위험/부작용
- 트리거를 민감하게 하면 턴오버 급증 → 비용으로 악화(E2와 같이 봐야 함).
- holdings 제약(8~14) 때문에 신호 표현력이 줄 수 있음.

### (c) 최소 실험
- **E4**(필수)
- **E3**(리밸 이벤트 없음을 증명해야 함)
- **E2**(턴오버 증가가 net을 죽이는지 확인)

### (d) PASS 조건
- trigger_hit_rate / apply_rate / avg_holdings_count / exposure 로그가 모두 존재.
- apply_rate가 의미 있는 수준으로 회복 + holdings 8~14 유지.

---

## TOP5) 레짐(Tech/Healthcare) 기반 tail-risk 완화 — OOS min 방어
### (a) 왜 필요한지
- OOS mean만 올리면 과최적화로 “한 방에 무너지는” 구조가 되기 쉬움.
- Tech/HC 혼합의 목적은 평균이 아니라 **최저 성과(OOS min), MDD 방어**에 있음.

### (b) 위험/부작용
- 레짐 스위치 임계값이 또 다른 과최적화 축이 될 수 있음(단 1개 규칙만).
- 평균 수익이 일부 희생될 수 있음.

### (c) 최소 실험
- **E5**(필수)
- **E1**(레짐 분해가 누수/폴드 문제를 가리지 않도록)
- **E2**(risk-off 전환이 거래를 늘려 비용이 증가하는지 확인)

### (d) PASS 조건
- OOS min 또는 worst_mdd의 개선.
- 레짐별 조건부 성과 리포트 제공.

---

# 2) 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래 트리를 **위에서 아래로 순서대로** 자동 점검 항목으로 박아라(질문 금지, 자동 판정).

## A. 트리거(리밸 신호 생성) 레이어
- **체크**
  - trigger_hit_rate(일/주 단위)
  - 신호 값의 분산(거의 상수면 고장)
  - 레짐/기간별 트리거 빈도
- **대표 고장**
  - 필터가 너무 빡세서 신호가 거의 0
  - as-of 정렬 오류로 신호가 NaN → 기본값 0

## B. 적용(포트폴리오 최적화/정규화/클램프) 레이어
- **체크**
  - rebalance_apply_rate(트리거 대비 실제 Δw 발생 비율)
  - Δw 분포(대부분 0이면 No-Delta)
  - 제약(holdings 8~14, exposure cap/floor)이 Δw를 죽이는지
- **대표 고장**
  - 스케일링/헤지/정규화가 서로 상쇄 → 결과가 항상 기존과 동일
  - 리스크 모델이 singular/빈 데이터 → 최적화가 fallback으로 “그대로 유지”

## C. 노출(exposure) 레이어
- **체크**
  - exposure time-series(0 근처 고착 여부)
  - 섹터(Tech/HC) 노출 비중
- **대표 고장**
  - “risk-off 규칙”이 항상 켜져 exposure가 상시 축소
  - 롱만인데도 방어 로직이 과도해 현금화

## D. 비용/체결 레이어
- **체크**
  - gross vs net 괴리
  - turnover와 비용의 상관
- **대표 고장**
  - 수익의 대부분이 미세한 알파인데 거래가 잦아 net 0
  - 리밸 시점이 너무 촘촘(일간 리밸이 필요 이상)

## E. 레짐(시장 상태) 레이어
- **체크**
  - VIX 고/저, 금리 급변, QQQ 추세 구간별 성과
  - Tech vs HC 기여도 분리(기여도/조건부 평균)
- **대표 고장**
  - 전략이 risk-on에서만 작동하는데 sample이 risk-off로 치우침
  - 헬스케어가 방어가 아니라 “동시에 같이 빠지는” 기간에 노출 과다

# 3) 48시간 루프에서의 실행 순서(중단 게이트 포함)
- [ ] **E3 실행**(로그/메타/MDD 복구) → FAIL이면 즉시 중단(다음 실험 금지)
- [ ] **E1 실행**(누수/폴드 붕괴 제거) → degenerate_folds 개선 실패 시 중단
- [ ] **E2 실행**(비용 net 반영) → net 성과/턴오버 기준선 확립
- [ ] **E4 실행**(No-Delta/노출/8~14 holdings 강제) → “안 움직임” 원인 확정
- [ ] **E5 실행**(레짐 스위치 1개) → OOS min / MDD 방어 확인

이렇게 하면 “성능이 안 움직임”이 **(검증 붕괴) / (거래 없음) / (거래는 있는데 비용으로 상쇄) / (레짐 미스매치)** 중 어디인지 48시간 안에 분리된다.
