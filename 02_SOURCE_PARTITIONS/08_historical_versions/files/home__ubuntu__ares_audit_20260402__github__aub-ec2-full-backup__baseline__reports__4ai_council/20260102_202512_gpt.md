## TOP5 우선순위 (24~48시간) — **명령형 체크리스트**  
(누수/과최적화/서바이버십/비용 미반영/운영 리스크부터 선처리, 48h 자동 루프 형태)

---

# 1) **운영/로깅 파이프라인 복구 (rebalance/metrics/champion 메타데이터)**
### (a) 왜 필요한지
- `aub_rebalance_pinpoint`가 **입력 파일 부재/포맷 불일치(JSON 파싱 실패)**로 멈춤 → “왜 성능이 안 움직이는지”를 비용/회전/노출 단계에서 분해 불가.
- `Champion`에 `file`, `lane_hash`, `run_hash`, `worst_mdd=None` → **재현성/감사(audit) 불가** + 리스크 지표 누락.

### (b) 위험/부작용
- 로그 스키마 변경 시 기존 리포트/대시보드가 깨질 수 있음.
- 성능 자체는 즉시 안 오를 수 있으나, **48시간 루프의 실패율/블라인드 구간**을 제거하는 “필수 운영 패치”.

### (c) 최소 실험(단일 실행 3-arm로 처리)
**[실험 1: “Rebalance & Metrics Schema Hardening”]**
- Arm A(현행): 현재 JSON/CSV 출력 유지
- Arm B: `rebalance.jsonl`(line-delimited JSON) 강제 + `rebalance.csv` 동시 출력 + 파일 경로 표준화
- Arm C: Arm B + `champion.json`에 `lane_hash/run_hash/git_sha/data_snapshot_id/cost_model_id` 강제 기록 + `worst_mdd` 계산 강제

### (d) PASS 조건 (게이트)
- **Gate-1(운영)**: `aub_rebalance_pinpoint.py`가 base/cand 모두에서 **에러 없이 리포트 생성**
- **Gate-2(지표)**: `worst_mdd`/turnover/cost/exposure time-series가 모두 채워짐(Null 0%)
- **Gate-3(재현성)**: 동일 `run_hash`로 리런 시 핵심 지표(OOS mean 등) ±허용오차 이내 재현

### 48h 자동 루프 형태
1) **실험 정의**: 출력 스키마/경로/메타데이터 강제 + 리스크지표 계산 강제  
2) **게이트**: pinpoint 리포트 생성 성공, 필수 컬럼/지표 결측 0%  
3) **기대 관측치**: “리밸런스 타이밍/거래비용/노출 공백” 원인이 즉시 가시화

# 2) **누수/폴드 퇴행(degenerate folds) 제거: Purged Walk-Forward + Fold Health Check**
### (a) 왜 필요한지
- `degenerate_folds: [1,2,3,8]`는 보통 아래 중 하나:
  - **누수 방지용 split이 잘못되어 학습/검증 데이터 길이가 0에 가까움**
  - 특정 기간에 **필터/결측 처리로 샘플이 증발**
  - 리밸런스/라벨 정렬에서 **미래 데이터 참조**를 피하려다 fold가 깨짐  
→ OOS가 “안 움직이거나” 특정 실험만 유리해지는 전형적 원인.

### (b) 위험/부작용
- Purge/Embargo 적용 시 유효 샘플 감소 → 단기적으로 OOS mean 하락 가능.
- 하지만 누수 제거 후에도 성능이 유지되면 **진짜 알파**일 확률이 상승.

### (c) 최소 실험(단일 실행 3-arm)
**[실험 2: “CV Split Robustness & Leakage Guard”]**
- Arm A: 현행 CV
- Arm B: **Purged Walk-Forward**(라벨 horizon + embargo 적용) + fold별 최소 샘플 강제
- Arm C: Arm B + **Fold Health Check로 degenerate fold 발생 시 즉시 실패 처리**(early fail) + 원인 로그 출력(결측/필터/정렬)

### (d) PASS 조건
- **Gate-1**: degenerate_folds = `[]`
- **Gate-2**: 각 fold의 valid 샘플 수가 최소치 이상(예: 전체의 ≥5% 또는 절대 N≥K)  
- **Gate-3**: OOS mean이 Arm A 대비 -X% 이상 급락하지 않음(예: -10% 이내) + OOS min 악화 제한

### 48h 자동 루프
1) **실험 정의**: split/purge/embargo/health-check를 CV 레이어에 고정  
2) **게이트**: fold 퇴행 0, 샘플 수 기준 충족  
3) **기대 관측치**: “성능 정체=누수 제거로 원래 성능이 사라짐 vs 데이터 파이프 문제”가 분리됨

# 3) **거래비용/슬리피지/회전(턴오버) “반영 + 제어” 패치**
### (a) 왜 필요한지
- 현재 출력에서 비용/리밸런스 로그가 깨져 있어, **비용 미반영** 가능성이 큼(또는 반영돼도 검증 불가).
- Tech+Healthcare(대형주 중심)라도 잦은 리밸런스면 **turnover가 알파를 삼킴**.  
- 성능 “안 움직임”은 종종 **gross alpha는 있는데 net에서 상쇄**되는 케이스.

### (b) 위험/부작용
- 비용/슬리피지 모델을 현실화하면 OOS mean이 떨어질 수 있음(하지만 이것이 진실).
- 과도한 turnover cap은 기회 손실(추세 전환 대응 둔화).

### (c) 최소 실험(단일 실행 3-arm)
**[실험 3: “Costed PnL + Turnover Control”]**
- Arm A: 현행 비용 모델(또는 비용 0에 준하는 상태)
- Arm B: **고정 수수료+스프레드+슬리피지**(예: bps 모델, ADV 기반 간단 충격) 적용 + 로그에 cost 분해 기록
- Arm C: Arm B + **턴오버 상한/거래 임계치**(예: |Δw| 합이 일정 이하이면 no-trade, 또는 rebalance band) 적용

### (d) PASS 조건
- **Gate-1**: net PnL이 gross PnL 대비 과도하게 붕괴하지 않음(비용이 합리 범위로 추정됨)
- **Gate-2**: turnover가 목표 범위 내(예: 일/주 기준 상한)로 내려가며 OOS mean 악화가 제한됨  
- **Gate-3**: “비용/슬리피지 기여도 리포트”가 생성되어 원인 추적 가능

### 48h 자동 루프
1) **실험 정의**: 비용 모델을 net 기준으로 고정 + turnover 제약 on/off 비교  
2) **게이트**: 비용 분해 로그 생성, turnover 상한 충족  
3) **기대 관측치**: 성능 정체가 “알파 부족”인지 “비용에 의한 상쇄”인지 즉시 판별

# 4) **노출(Exposure) 0 구간 제거 + 포트폴리오 구성 규칙 안정화 (8~14종 강제)**
### (a) 왜 필요한지
- `exposure_min=0.0`는 장기간 캐시화 가능성을 시사 →  
  - 신호 임계치/정규화 문제  
  - 선택 종목 수 부족  
  - 리스크 게이트가 과도  
→ “아무것도 안 하는 전략”이 되면 성능이 안 움직이는 게 정상.

### (b) 위험/부작용
- 노출 하한을 강제하면 하락장에서 MDD가 커질 수 있음.
- 종목 수 강제는 약한 신호를 억지로 편입하는 부작용 가능.

### (c) 최소 실험(단일 실행 3-arm)
**[실험 4: “Exposure Floor & Top-K Portfolio Rule”]**  
- **Universe(미국주식 only / Tech+Healthcare / 8~14)** 예시(고정):  
  - Tech: AAPL, MSFT, NVDA, AVGO, GOOGL, AMZN, META, CRM  
  - Healthcare: LLY, UNH, ABBV, MRK (총 12)  
- Arm A: 현행 선택/임계치
- Arm B: **Top-K(예: K=10~12) 강제 + 동적 스케일링**(항상 8~14 보유)  
- Arm C: Arm B + **exposure floor(예: 0.6)** + risk-off 시에만 floor 완화(단, ETF는 “지표”로만 사용: XLK/XLV/QQQ 관측)

### (d) PASS 조건
- **Gate-1**: 보유 종목 수가 8~14 범위를 대부분의 리밸런스에서 만족
- **Gate-2**: exposure가 장기간 0으로 떨어지는 구간 제거(예: 전체 기간의 95% 이상에서 exposure>0.3)
- **Gate-3**: OOS min/드로우다운이 비정상적으로 악화되지 않음(리스크지표가 계산된다는 전제)

### 48h 자동 루프
1) **실험 정의**: 종목 수/노출 하한을 규칙으로 고정하고 “리스크-오프는 지표 기반”으로만 허용  
2) **게이트**: 8~14 유지, exposure 공백 제거  
3) **기대 관측치**: 성능 정체가 “노출 부족” 때문인지 즉시 분리

# 5) **레짐(Tech↔Healthcare 상대강도) 기반의 단순 2-슬리브 배분 실험 (ETF는 관측만)**
### (a) 왜 필요한지
- Tech/Healthcare는 레짐에 따라 상대 우위가 크게 바뀜.  
- “한 가지 룰”로 고정하면 특정 국면에서 알파가 죽어 **최근 성능이 안 움직이는** 현상 발생.

### (b) 위험/부작용
- 레짐 신호가 늦거나 노이즈면 잦은 슬리브 전환 → 비용 증가.
- 과최적화 위험(레짐 규칙을 복잡하게 만들면 즉시 망가짐).

### (c) 최소 실험(단일 실행 3-arm)
**[실험 5: “2-Sleeve Regime Tilt (Indicator-only ETFs)”]**
- 관측 지표(매매 금지): XLK, XLV, QQQ (또는 SMH/IHI는 보조)  
- Arm A: 현행(섹터 틸트 없음)
- Arm B: **XLK/XLV 상대모멘텀**(예: 20/60일)로 Tech/Healthcare 예산만 60/40↔40/60 정도로 단순 전환  
- Arm C: Arm B + **전환 히스테리시스(밴드/쿨다운)**로 churn 감소

### (d) PASS 조건
- **Gate-1**: 슬리브 전환 횟수/턴오버가 Arm B에서 폭증하지 않음(Arm C가 특히 중요)
- **Gate-2**: OOS mean이 Arm A 대비 유의미 개선(예: +5% 이상) 또는 OOS min 개선(좌측 꼬리 완화)
- **Gate-3**: 레짐 신호→슬리브→종목선정→성과의 연결이 로그로 설명 가능

### 48h 자동 루프
1) **실험 정의**: “지표 기반 슬리브 예산”만 추가(전략 복잡도 최소)  
2) **게이트**: churn 제한 + OOS 개선  
3) **기대 관측치**: 성능 정체가 “레짐 미스매치”인지 판별

## 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래 트리를 **순서대로 강제 점검**해서, “알파가 없어서”인지 “있는데 구현에서 죽는지”를 분리.

### A. Trigger(신호 생성) 단계
- **누수 체크**: feature/label time alignment, corporate action 반영 시점, 리밸런스 시점의 종가/체결가 사용 규칙  
- **신호 분포 체크**: 스코어가 상수화(표준편차≈0) / 특정 구간 NaN 급증 / clipping으로 평탄화  
- **진단 로그(필수)**: 날짜별 top/bottom score, score std, NaN rate, feature drift(간단 PSI)

### B. Apply(포지션 생성/리밸런스) 단계
- **리밸런스 이벤트 존재 여부**: 실제로 주문이 나가는지(“신호는 바뀌는데 포지션이 안 바뀜” 흔함)  
- **제약조건 과도 여부**: min trade size, band, exposure cap/floor, 리스크 게이트가 항상 막는지  
- **진단 로그**: “의도 포지션 vs 체결 포지션” diff, trade skip reason 코드화

### C. Exposure(노출) 단계
- **exposure=0 구간 원인 분해**  
  1) 종목 선택 실패(선정 종목 수 0)  
  2) 임계치 미충족(스코어 전부 cut)  
  3) 리스크-오프가 과잉 발동  
- **필수 지표**: exposure 시계열, 보유 종목 수 시계열, cash 비중, 게이트 발동 횟수

### D. Cost(비용) 단계
- **gross→net 브리지**를 항상 출력:  
  - gross PnL  
  - fees  
  - spread/slippage  
  - market impact(단순 bps라도)  
  - borrow(숏이 있으면)  
- **턴오버×비용 탄력성**: turnover가 조금만 늘어도 net이 꺾이는지 곡선으로 확인

### E. Regime(국면) 단계
- Tech/Healthcare 상대강도, 금리 민감도, risk-on/off 구간에서 성과가 갈리는지 분해  
- ETF는 **관측 지표**로만 사용: XLK, XLV, QQQ로 다음을 로그화  
  - “레짐 신호 값”  
  - “슬리브 배분”  
  - “슬리브별 PnL 기여”

## 48시간 루프에 바로 넣을 “실행 순서” (명령형)
1) **로그/스키마 패치 먼저 적용**해서 rebalance/metrics/champion 메타데이터를 강제 생성하라.  
2) **Purged walk-forward + fold health check**를 켜고 degenerate fold를 0으로 만들어라.  
3) **비용 모델 on + turnover control**을 넣고 gross/net 분해 리포트를 생성하라.  
4) **8~14종 강제 + exposure floor**로 “안 하는 전략” 가능성을 제거하라.  
5) **2-슬리브 레짐 틸트**를 단순 규칙으로만 추가하고(히스테리시스 포함) churn을 게이트로 막아라.

위 5개는 서로 의존성이 있어, **(1)→(2)→(3)** 까지가 “성능이 안 움직이는 문제”의 80%를 원인 규명/고정시키는 경로다.
