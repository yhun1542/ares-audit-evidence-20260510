아래는 **24~48시간 내 우선순위 TOP5**를 “누수/과최적화/서바이버십/비용 미반영/운영 리스크” 순으로 잠그는 형태로 제시한다. 전부 **48시간 자동 루프**에서 돌릴 수 있게 **(1) 실험 정의 → (2) 게이트 → (3) 기대 관측치**를 포함했다.  
또한 “제안은 3~5개 실험으로 제한” 조건을 맞추기 위해, 전체 실험을 **E1~E5(총 5개)**로 고정하고 각 우선순위 항목에서 이를 재사용한다.

---

## TOP1) (운영/재현성) 로그·아티팩트 계약(Contract) 고정 + Rebalance Pinpoint 복구
### (a) 왜 필요한지
- 현재 상태에서 **run_hash/lane_hash None**, **worst_mdd None**, **rebalance pinpoint가 base-log/CSV/JSON 파싱 실패** → “성능이 왜 안 움직이는지”를 계량으로 못 잡는다.
- 48시간 자동 루프는 **로그 스키마가 흔들리면 진단이 불가능**해져서 최적화가 “눈가림”이 된다.

### (b) 위험/부작용
- 스키마 고정 과정에서 과거 결과와의 호환이 깨질 수 있음(리포트 비교 단절).
- 로그가 많아져 비용/스토리지 증가(운영비 리스크).

### (c) 최소 실험(2~3개)  *(아래 E1 재사용)*
- **[E1-1]** rebalance 로그를 **단일 포맷(JSONL)** 로 강제 저장하고 로더를 해당 포맷 우선으로 읽게 패치
- **[E1-2]** 모든 run에 **manifest.json(데이터 스냅샷 해시, universe, 비용모델, 시드, 코드 커밋)** 강제 기록
- **[E1-3]** 백테스트 종료 시 **worst_mdd/turnover/cost_drag** 반드시 산출(없으면 실패로 처리)

### (d) PASS 조건
- `aub_rebalance_pinpoint.py`가 **base/cand 모두 로드 성공**하고, “No rebalance data found”가 사라질 것
- 모든 run에 `run_hash`, `lane_hash`, `worst_mdd`가 **None이 아니어야 함**
- 리포트에 **turnover + net-of-cost**가 항상 출력(누락 시 FAIL)

---

## TOP2) (누수/과최적화) Degenerate folds 제거 + Purged/Embargo CV로 누수 게이트
### (a) 왜 필요한지
- `degenerate_folds: [1,2,3,8]`은 보통 아래 중 하나:
  - fold가 비어있거나 클래스/신호가 한쪽으로 쏠림(학습 무의미)
  - 시간축 분할이 깨져 **lookahead(누수)** 또는 **데이터 중복**이 발생
- 이 상태에서 OOS mean이 높아도 “진짜”가 아닐 가능성이 커서, 이후 전략 패치가 전부 과최적화로 굳을 수 있다.

### (b) 위험/부작용
- 누수 제거하면 성능이 “즉시” 내려갈 수 있음(하지만 내려가는 게 정상일 수 있음).
- Purged CV 도입 시 학습 데이터가 줄어 분산 증가.

### (c) 최소 실험(2~3개)  *(아래 E2 재사용)*
- **[E2-1]** Purged KFold(+ embargo N일)로 교체하고, fold별 샘플 수/타깃 분포/결측률 **헬스 리포트** 출력
- **[E2-2]** feature 생성 단계에 **시점 검증 unit check** 추가(미래 값 참조 탐지: 인덱스/타임스탬프 역전, shift 방향 점검)
- **[E2-3]** “동일 데이터가 train/test에 동시에 등장” 탐지(키 기반 중복 체크)

### (d) PASS 조건
- `degenerate_folds == []` (0개)
- Purged CV 적용 후에도 `oos_mean`이 **기존의 70% 이상 유지**(예: 3.32 → 2.32 이상)  
  + 대신 **분산/최악 구간(worst_mdd)이 계산 가능**해야 함
- 누수 탐지 체크에서 **0건**이어야 함(1건이라도 나오면 즉시 FAIL)

## TOP3) (서바이버십/우주선정) “미국 Tech+Healthcare 8~14개” 고정 우주로 PIT(시점정합) 강제
### (a) 왜 필요한지
- 서바이버십/리밸런싱 우주 변동이 섞이면 **OOS가 안 움직이거나(상쇄)** 혹은 **가짜로 좋아질** 수 있다.
- 요구사항이 “US stocks only, Tech+Healthcare 중심 8~14개(ETF 매매 제외)”이므로 우주를 고정해 **원인 분해가 가능**해야 한다.

### (b) 위험/부작용
- 우주를 고정하면 알파 원천(종목 확장)이 줄어 성능이 떨어질 수 있음.
- 특정 대형주 편중 리스크(단일종목 이벤트).

### (c) 최소 실험(2~3개)  *(아래 E3 재사용)*
- **[E3-1]** 우주를 12개 내외로 고정(예: Tech 7~8 + Healthcare 4~5)하고 모든 실험이 동일 우주를 사용하게 강제  
  - 예시(미국 상장, Tech/HC): AAPL/MSFT/NVDA/GOOGL/AMZN/META/AVGO/AMD + LLY/JNJ/UNH/MRK (총 12)
- **[E3-2]** PIT 데이터 계약: “당일 종가로 의사결정이면 체결은 다음날 시가” 같은 **결정/체결 시점 분리**를 manifest에 박제
- **[E3-3]** 우주 변경/결측 발생 시 “보수적 처리(현금/비중 축소)”로 통일(임의 대체 금지)

### (d) PASS 조건
- 모든 run에서 universe가 **manifest에 동일 해시**로 기록
- 우주 고정 후에도 전략이 **비정상적 노출(항상 0 또는 항상 max)** 로 붕괴하지 않을 것
- 종목별 기여(attribution)에서 “없는 종목”이 등장하면 FAIL(데이터/우주 혼선)

## TOP4) (비용 미반영) Net-of-cost 백테스트 + turnover/impact 게이트(운영 가능성)
### (a) 왜 필요한지
- 현재 출력에 비용/슬리피지가 1급 지표로 보이지 않고, 노출 최대가 0.84까지 가는 상황에서 비용이 빠지면 **실전 성능과 괴리**가 커진다.
- “성능이 안 움직인다”의 흔한 원인이 **알파 변화 < 비용 변화**인 케이스다(특히 리밸런싱 잦을 때).

### (b) 위험/부작용
- 비용 모델을 넣는 순간 성능이 급락할 수 있음.
- 과도한 turnover 억제는 신호 반응성을 떨어뜨림.

### (c) 최소 실험(2~3개)  *(아래 E4 재사용)*
- **[E4-1]** 거래비용 모델 최소 포함: 고정 수수료 + bid/ask spread(ATR/가격 기반 근사) + 슬리피지(거래대금 대비)
- **[E4-2]** **turnover 상한**(예: 일 30% / 주 80% 등)과 **최소 주문 단위/체결 실패 처리**를 백테스트에 반영
- **[E4-3]** 성과지표를 `gross`, `net`, `cost_drag`, `turnover`로 분해 리포팅(항상 출력)

### (d) PASS 조건
- `net_oos_mean >= gross_oos_mean * 0.85` (비용으로 15% 이상 날아가면 구조 문제로 FAIL)
- `cost_drag`가 특정 구간에서 급증하면(상위 5% 날짜) 그 날짜의 리밸런스/노출 변화 로그가 **pinpoint로 추적 가능**해야 함
- turnover 상한 적용 후에도 oos_min이 악화되지 않을 것(악화 시: 과거 과매매였다는 신호)

## TOP5) (레짐/노출) 48시간 루프용 “노출 게이트 + Tech/Healthcare 레짐 스위치” 추가 (ETF는 관측만)
### (a) 왜 필요한지
- 현재 노출이 0~0.84로 넓고, 성능이 “안 움직임”은 종종 **트리거는 변하는데 적용(포지션)에서 막히는** 구조(게이트/클램프/리밸 타이밍)에서 발생한다.
- ETF는 매매 금지지만 **레짐 관측 지표**로는 유용(XLK, XLV, QQQ, IHI 등).

### (b) 위험/부작용
- 레짐 스위치는 잘못 잡으면 whipsaw(잦은 전환)로 비용 증가.
- 노출 게이트가 너무 보수적이면 알파를 죽임.

### (c) 최소 실험(2~3개)  *(아래 E5 재사용)*
- **[E5-1]** 레짐 지표(관측): `XLK/XLV 상대강도`, `QQQ 모멘텀`, `VIX 레벨` 중 1~2개만 사용해 단순 스위치  
  - 매매는 **고정 12종목 내에서** Tech 비중↑ / Healthcare 비중↑ 로만 구현
- **[E5-2]** 노출 게이트: 변동성 급등 시 총노출 상한을 자동 축소(예: 0.84 → 0.5), 평시 복귀
- **[E5-3]** “신호는 있는데 포지션이 안 바뀌는” 현상 탐지: `target_weight` vs `filled_weight` 괴리 로그화

### (d) PASS 조건
- 레짐 적용 후 `worst_mdd`가 개선(또는 oos_min이 덜 나빠짐)하면서 `oos_mean`이 크게 훼손되지 않을 것(예: mean -10% 이내)
- 노출 게이트가 발동한 날의 손실 꼬리가 줄어들어야 함(꼬리 리스크 완화가 목표)

# 48시간 자동 루프용 “실험 5개” 정의(고정)
아래 5개만 돌리면 위 TOP1~TOP5를 전부 커버한다.

## E1) 로그/아티팩트 계약 고정 + Pinpoint 복구
1) **실험 정의**
- rebalance 로그를 JSONL로 통일, 로더/리포트가 해당 포맷을 우선 사용
- manifest에 run_hash/lane_hash/코드커밋/데이터해시/우주/비용모델을 강제 기록
- worst_mdd/turnover/cost_drag 누락 시 run 실패 처리
2) **게이트**
- pinpoint 스크립트가 base/cand 모두 로드 성공
- worst_mdd != None, run_hash/lane_hash != None
3) **기대 관측치**
- “No rebalance data found” 소멸
- 이후 모든 실험에서 성능 변동의 원인을 리밸런스 단위로 추적 가능

## E2) Purged/Embargo CV + 누수/중복 탐지로 degenerate folds 제거
1) **실험 정의**
- time-series purged CV 적용, fold health 리포트 생성, 누수/중복 탐지 체크 추가
2) **게이트**
- degenerate_folds == 0
- 누수 탐지 0건
3) **기대 관측치**
- oos_mean이 떨어질 수 있으나, 대신 fold별 성능이 “설명 가능”하게 변함(분산/샘플 수 정상화)

## E3) 고정 우주(8~14, Tech+HC) + PIT 결정/체결 시점 박제
1) **실험 정의**
- 12개 내외 우주 고정, 결측/상폐/휴장 처리 규칙 단일화, 결정/체결 시점 분리
2) **게이트**
- universe hash가 매 run 동일
- “존재하지 않는 종목 기여” 0건
3) **기대 관측치**
- 성능은 소폭 변해도, 종목/섹터 기여 분해가 안정화(서바이버십 의심 제거)

## E4) 비용+슬리피지 + turnover 상한(net-of-cost)
1) **실험 정의**
- 비용/슬리피지 모델 포함, turnover cap, 체결 실패/부분체결 규칙 반영
2) **게이트**
- net_oos_mean >= gross_oos_mean * 0.85
- turnover가 상한 내 유지
3) **기대 관측치**
- “성능이 안 움직임”이 사실상 비용 드래그였는지 즉시 판별 가능
- 과매매 전략이면 net 성능이 급격히 악화(구조 변경 필요 신호)

## E5) 레짐 관측(ETF는 지표만) + 노출 게이트 + target vs fill 괴리 로깅
1) **실험 정의**
- XLK/XLV/QQQ 등으로 레짐을 관측하고, 12개 종목 내에서 Tech/HC 비중만 조절
- 변동성/리스크 지표로 총노출 상한 자동 조정
- target_weight와 fill_weight 괴리를 기록
2) **게이트**
- oos_min 또는 worst_mdd 개선(둘 중 하나는 개선)
- mean 성능 하락 -10% 이내
3) **기대 관측치**
- 꼬리 구간 손실 감소(운영 리스크 감소)
- “트리거는 있었는데 적용이 안 됨”이 로그로 드러남

# 성능이 “안 움직일 때” 원인 분해 아이디어(트리거/적용/노출/비용/레짐)
아래 트리를 그대로 리포트/대시보드 체크리스트로 박아 넣으면, 다음 루프에서 원인이 자동 분류된다.

## 1) 트리거(신호) 레벨: 신호가 변하고 있나?
- **신호 분포 드리프트**: 예측/스코어 평균·표준편차가 기간별로 0에 수렴하면 “모델이 죽음”
- **상위/하위 랭크 안정성**: Top-k 종목이 매일 거의 동일이면 과도한 스무딩/클램프
- **특정 종목만 신호 독점**: 1~2개가 신호를 다 먹으면 과최적화/데이터 이슈 가능

## 2) 적용(포트폴리오 생성) 레벨: 신호가 포지션으로 반영되나?
- **target_weight 변화량 vs 실제 포지션 변화량** 비교  
  - target은 변하는데 포지션이 그대로면: 리밸런스 조건/최소 주문/게이트가 막는 중
- **리밸런스 빈도/타이밍**: 신호 업데이트 주기와 체결 주기가 어긋나면 알파 상쇄
- **제약 충돌 로그**: 노출 상한, 종목별 상한, 섹터 상한이 동시에 걸려 “항상 비슷한 포트”가 되는지 확인

## 3) 노출(리스크) 레벨: 베타/섹터 노출이 원인인가?
- **시장 베타(관측: SPY/QQQ)** 추정 후, 수익의 대부분이 베타면 알파가 아니라 레짐 의존
- **Tech vs Healthcare 순노출**이 한쪽으로 고정되면 레짐 변화에 성능이 둔감/역행

## 4) 비용 레벨: 알파가 비용에 눌리나?
- `gross - net = cost_drag`를 일별로 보고, **상위 cost_drag 날짜**의 공통점(리밸런스 폭/스프레드/변동성)을 pinpoint로 연결
- turnover가 낮은데도 net이 나쁘면: 슬리피지 모델/체결 가정/데이터 타임스탬프 오류 가능

## 5) 레짐 레벨: 잘 되는 구간/안 되는 구간이 섞여 상쇄되나?
- **레짐별(예: QQQ 추세↑/↓, XLK-XLV 상대강도↑/↓)** 로 성과를 분해해 “상쇄” 여부 확인
- 레짐에 따라 최적 파라미터가 갈리면, 단일 챔피언 고집이 “무변화”로 보일 수 있음 → E5로 단순 스위치부터 검증
