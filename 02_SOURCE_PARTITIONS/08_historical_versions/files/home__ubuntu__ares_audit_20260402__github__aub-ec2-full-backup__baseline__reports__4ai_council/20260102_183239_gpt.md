## 24~48시간 우선순위 TOP5 (코드/아키텍처/전략) — **명령형 체크리스트**

> 최우선 점검 순서: **누수 → 과최적화/폴드 퇴화 → 서바이버십 → 비용 미반영 → 운영/로깅 리스크**  
> 운용 제약: **미국주식 only, Tech+Healthcare 중심, 8~14 종목, ETF는 관측지표만(매매 금지)**  
> 형태: 48시간 자동 루프에 바로 넣을 수 있게 **(1) 실험 정의 (2) 게이트 (3) 기대 관측치**로 작성

# 1) **데이터 누수/서바이버십 가드레일을 “강제 실패(FAIL FAST)”로 넣기**
### (a) 왜 필요한지
- 현재 리포트에 **degenerate_folds [1,2,3,8]**가 찍혀 있음 → 스플릿이 깨지거나(학습/검증 구간이 비정상), 피처가 미래 정보를 포함할 때 자주 동반됨.
- “성능이 안 움직임”은 종종 **(i) 누수로 이미 과대평가된 champion 고착** 또는 **(ii) 서바이버십/코퍼레이트액션 누락으로 백테스트 신뢰 붕괴**에서 발생.

### (b) 위험/부작용
- 누수/서바이버십을 막으면 **백테스트 성능이 단기적으로 하락**할 수 있음(정상적인 현상).
- 데이터 제약이 강해져 실험 실패율 증가(하지만 “잘못된 성공”을 제거).

### (c) 최소 실험(2~3 variants를 하나의 실험세트로)  
**실험세트 #1: Leak/Survivorship Sentinel (48h 루프 상시 실행)**  
(1) **실험 정의**
- 아래 체크를 “하나라도 위반 시 전체 런 FAIL”로 강제:
  - **time-index 정합성**: 모든 피처는 `t` 시점까지의 정보만 사용(예: `shift(1)` 강제), `asof` merge만 허용
  - **라벨 누수 탐지**: 피처-라벨 상관이 비정상적으로 높으면 경고/FAIL(예: 단기 수익률 라벨에 동일 기간 가격변화가 들어갔는지)
  - **서바이버십**: 유니버스는 “현재 상장 종목”이 아니라 **시점별 상장 가능 집합**을 사용(가능하면 CRSP/Polygon/Quandl 등 “delisted 포함” 소스). 불가하면 최소한 “최근 구성으로 과거를 재구성” 금지.
  - **코퍼레이트액션**: split/dividend 반영(Adj Close 사용 시 원천/일관성 체크)
- variants(동일 실험세트 내 A/B):
  - A: strict(모든 위반 FAIL)
  - B: warn(위반 로깅만, FAIL은 하지 않음) → strict 전환 전 영향 확인용

(2) **게이트**
- degenerate_folds == 0
- train/val/test 구\dband 겹침 0 (샘플 인덱스 중복 0)
- 누수 감지 카운트 0 (strict 기준)
- 유니버스 생성 로그에 “시점 t 기준 구성” 증빙 라인 존재

(3) **기대 관측치**
- 초기엔 OOS mean이 하락할 수 있으나, **oos_min이 개선/안정**되는 방향이 정상
- “원인 불명 성능 정체”가 아니라 **실패 이유가 로그로 분해**되어 남음

### (d) PASS 조건
- 48시간 동안 FAIL 없이 3회 이상 연속 성공
- degenerate_folds 0 유지
- 누수/서바이버십 경고 0(또는 warn→strict 전환 후 0)

# 2) **폴드 퇴화(degenerate_folds) 제거: 워크포워드/퍼지(purge)/엠바고(embargo)로 고정**
### (a) 왜 필요한지
- degenerate_folds는 **과최적화 + 성능 고착 + 재현 불가**의 1등 원인.
- 특히 주식 시계열에서 “인접 구간 정보 누수”가 빈번 → purge/embargo 없이 CV하면 OOS가 의미 없음.

### (b) 위험/부작용
- 표본 수 감소로 성능 분산 증가(단기 성능 흔들림).
- 실험 속도 저하(하지만 48h 루프면 감내 가능).

### (c) 최소 실험(실험세트 #2: Splitter Fix Pack)
(1) **실험 정의**
- CV를 아래로 강제:
  - **Walk-forward**: `[Train: 2~3y] -> [Val: 3m] -> [Test: 3m]` 식 롤링
  - **Purge window**: 라벨 산출 구간 길이만큼 train/val 경계에서 제거
  - **Embargo**: val/test 직전 `N`일(예: 5~20 trading days) train에서 제외
- variants(A/B/C):
  - A: purge만
  - B: purge+embargo(10d)
  - C: purge+embargo(20d)

(2) **게이트**
- degenerate_folds == 0
- 각 fold의 샘플 수 하한(예: fold당 최소 200 trading days equivalent) 충족
- fold별 OOS 표준편차가 비정상 급등 시 FAIL(예: baseline 대비 2배 초과)

(3) **기대 관측치**
- OOS mean이 과대평가에서 내려오더라도 **oos_min/드로우다운 안정화**
- “챔피언이 바뀌지 않음” 현상이 줄고, 바뀌면 이유가 설명 가능해짐

### (d) PASS 조건
- 3회 연속 런에서 degenerate_folds 0
- oos_min이 0 근처에서 음(-)으로 급락하는 꼬리가 줄어듦(예: baseline 대비 하위 5% 개선)

# 3) **비용/슬리피지/충격을 “의사결정에 직접 반영” (비용 미반영 제거)**
### (a) 왜 필요한지
- 지금 상태에서 **rebalance 로그가 로드 실패**(CSV/JSONL 없음, 포맷 불명) → 회전율·거래비용이 통제되지 않으면 “성능이 안 움직임”이 아니라 “실제로는 비용으로 상쇄”일 수 있음.
- Tech/Healthcare 8~14종목은 집중 포트폴리오라 **리밸런싱 빈도/체결 가정**이 성과를 좌우.

### (b) 위험/부작용
- 비용을 넣으면 성과 하락 가능(정상).
- 비용 파라미터에 과최적화 위험 → **고정된 보수적 비용**으로 시작해야 함.

### (c) 최소 실험(실험세트 #3: Cost-in-the-loop)
(1) **실험 정의**
- 매 거래 시 비용을 성과/최적화에 포함:
  - 수수료: 0으로 두더라도 스프레드/슬리피지는 반영
  - 슬리피지(보수): `max(1bp, k * daily_vol)` 또는 고정 2~10bp
  - 충격(선택): `impact ~ c * (|trade| / ADV)` 단순모형
- variants(A/B/C):
  - A: 2bp 고정
  - B: 5bp 고정
  - C: 2bp + ADV 충격(상한 캡 포함)

(2) **게이트**
- 일별 turnover(총 |Δw|) 상한: 예) 0.6/day 초과일 비율 < 5%
- 비용 차감 후 OOS mean이 baseline 대비 과도 붕괴 시 FAIL(예: -30%p 이상)
- 리밸런스 로그(JSONL) 생성 성공 + 스키마 검증 통과

(3) **기대 관측치**
- “수익은 있는데 실제 운용은 안 됨”을 제거
- 실험 간 차이가 비용/회전율로 설명되는지 분해 가능

### (d) PASS 조건
- 비용 포함 기준으로도 oos_min이 음수 꼬리를 줄임
- turnover가 게이트 내로 들어오면서 OOS mean 손실이 제한적(예: A와 B 차이 설명 가능)

# 4) **운영/재현성 리스크 제거: run_hash/lane_hash + 리밸런스 로그 포맷을 고정**
### (a) 왜 필요한지
- 현재 “lane_hash/run_hash: None”, “worst_mdd: None”, 리밸런스 로그 로드 실패 → **비교 불가/회귀 불가**라서 “성능이 안 움직임”이 아니라 “움직여도 감지 불가” 상태.
- 48h 자동 루프는 로깅/아티팩트 표준화가 없으면 곧 고장남.

### (b) 위험/부작용
- 저장/IO 증가(비용).  
- 표준화 도중 기존 파서/도구 깨질 수 있음(단기).

### (c) 최소 실험(실험세트 #4: Observability Contract)
(1) **실험 정의**
- 모든 런이 아래 산출물을 **반드시** 남기게 강제(없으면 FAIL):
  - `run_hash`(config+code+data snapshot 해시), `lane_hash`(전략/유니버스/비용모형 식별)
  - `rebalance.jsonl` (timestamp, symbol, target_w, prev_w, trade_w, price, notional, cost_bps, cost_$)
  - `metrics.json` (oos_mean, oos_min, worst_mdd **계산값 필수**, turnover, hit-rate 등)
  - champion 파일 경로/이름 표준화: `champion_<run_hash>.json`
- variants(A/B):
  - A: 저장 최소(요약 + 리밸런스)
  - B: 저장 확장(중간 신호/스코어까지 덤프) — 디버그용

(2) **게이트**
- `worst_mdd != None`
- `lane_hash != None` AND `run_hash != None`
- rebalance pinpoint 도구가 base/cand 모두에서 로드 성공

(3) **기대 관측치**
- “안 움직임”이 **진짜 성능 정체인지, 파이프라인 관측 불가인지** 즉시 구분됨
- 챔피언 교체/회귀가 재현 가능해짐

### (d) PASS 조건
- 48시간 내 5회 연속 런에서 필수 산출물 누락 0
- `aub_rebalance_pinpoint.py`가 에러 없이 리포트 생성

# 5) **전략 레벨: 8~14 종목(Tech+Healthcare) 고정 유니버스 + 노출(Exposure) 게이트로 “안정적 변화” 만들기**
### (a) 왜 필요한지
- 현재 exposure_min/max: **0.0 / 0.8388** → 노출이 자주 0으로 꺼지면(현금화) 성과 신호가 희석되어 “변화가 작게 보이는” 현상이 생김.
- 유니버스가 흔들리거나(매번 종목 교체) 노출이 들쭉날쭉하면, 개선이 있어도 분산에 묻힘.

### (b) 위험/부작용
- 유니버스 고정은 기회 손실 가능.
- 노출 하한을 두면 급락장에서 방어력 감소 가능 → 하한은 “약하게”부터.

### (c) 최소 실험(실험세트 #5: Stable Universe + Exposure Gate)
(1) **실험 정의**
- 유니버스(미국주식, Tech+Healthcare) 8~14개로 고정(예: 12개):
  - Tech(7): AAPL, MSFT, NVDA, GOOGL, AMZN, META, AVGO  
  - Healthcare(5): LLY, UNH, JNJ, ABBV, MRK  
  *(예시는 고정 유니버스 템플릿. 데이터 가용/상장기간에 맞춰 과거부터 존재하는 티커만 유지)*
- ETF는 매매 금지, **관측 지표**로만 사용(예: QQQ/XLV의 추세/변동성 레짐 태깅).
- 노출 게이트 variants(A/B/C):
  - A: exposure 하한 0.15 (완전 0 방지)
  - B: exposure 하한 0.05
  - C: “레짐이 Risk-off면 하한 0” (ETF 관측으로만 결정)

(2) **게이트**
- 유니버스 종목 수 8~14 유지(이탈 시 FAIL)
- 월간 turnover 상한(예: < 6.0) 또는 리밸런스 빈도 상한(예: 주 1회)
- exposure=0 상태가 전체 일수의 10% 초과 시 FAIL(A/B에 한함)

(3) **기대 관측치**
- 성능 변화가 “노출/리밸런스/비용” 요인으로 더 명확히 설명됨
- oos_min이 개선되거나 최소한 분산이 감소

### (d) PASS 조건
- baseline 대비 oos_mean이 크게 오르지 않아도, **oos_min 및 worst_mdd(필수 로그)가 개선**되면 PASS
- 노출이 0으로 꺼지는 빈도 감소 + turnover 게이트 충족

## 성능이 안 움직일 때 “원인 분해” 아이디어 (트리거/적용/노출/비용/레짐)
아래를 **매 런마다 자동 리포트**로 뽑아 “정체 원인”을 기계적으로 분해하라.

### A) Trigger(신호가 발생하는가?)
- `signal_nonzero_rate`(스코어/포지션 제안이 0이 아닌 비율)
- `rank_stability`(종목 순위의 일관성; Spearman rank IC)
- `decision_flip_rate`(전일 대비 top-k 구성 변화율)
- 트리거 정체 패턴:
  - 항상 비슷한 순위 → **피처가 둔감/스케일 고정**
  - 너무 자주 뒤집힘 → **노이즈/과민 반응**

### B) Apply(제약/게이트가 신호를 죽이나?)
- “원 신호 포지션” vs “게이트 적용 후 포지션” 비교:
  - `clipped_weight_mass`(캡/하한/섹터중립 등이 잘라낸 총량)
  - `blocked_trade_ratio`(거래하고 싶었는데 비용/최소거래단위로 막힌 비율)
- 적용 정체 패턴:
  - clipped가 크면 → **제약이 너무 강함**(혹은 신호 스케일 과대)

### C) Exposure(노출이 실제로 움직이나?)
- `avg_gross_exposure`, `pct_days_exposure_0`, `exposure_autocorr`
- 노출 정체 패턴:
  - exposure가 0 근처에 고착 → **risk gate 과도 / 신호 미약 / 비용 게이트 과도**
  - exposure가 상한에 고착 → **레버/캡 설계 미흡**

### D) Cost(비용이 알파를 먹나?)
- `gross_return` vs `net_return`(비용 차감 전후)
- `cost_drag_bps_per_day`, `turnover_per_day`, `impact_share`
- 비용 정체 패턴:
  - gross는 개선인데 net이 그대로 → **회전율/슬리피지 모델이 핵심 병목**

### E) Regime(레짐에서만 먹히나?)
- 관측용 ETF(매매 금지)로 레짐 태그:
  - QQQ/XLV의 추세(200DMA), 변동성(VIX 대용), 금리(IEF/TLT 등은 관측만)
- 레짐 분해 리포트:
  - `OOS by regime` (risk-on/off, high/low vol)
- 레짐 정체 패턴:
  - 특정 레짐에서만 유효 → **레짐 조건부 노출/리밸런스**로 바꿔야 함

## 실행 순서(48h) — 그대로 붙여넣는 운영 체크리스트
1) **실험세트 #4(로깅/해시/리밸런스 포맷)** 먼저 넣어라 (관측 불가 상태 제거).  
2) **실험세트 #2(워크포워드+purge/embargo)** 로 degenerate_folds를 0으로 만들어라.  
3) **실험세트 #1(누수/서바이버십 FAIL FAST)** 를 strict로 전환하라.  
4) **실험세트 #3(비용 in loop)** 로 gross→net 괴리를 고정하라.  
5) 마지막으로 **실험세트 #5(고정 유니버스+노출 게이트)** 로 “변화가 보이게” 만들어라.

이 5개가 돌아가면, “성능이 안 움직임”은 더 이상 상태 설명이 아니라 **어느 레이어(Trigger/Apply/Exposure/Cost/Regime)가 막는지** 매번 자동으로 진단 가능한 형태로 바뀐다.
