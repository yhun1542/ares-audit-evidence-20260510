아래는 **다음 24~48시간**에 바로 굴릴 수 있게, **누수/과최적화/서바이버십/비용 미반영/운영 리스크를 최우선**으로 점검하는 **TOP5 우선순위 패치(각 1개 “주 실험” + 조건부 후속)**입니다.  
(미국주식 only, **Tech+Healthcare 8~14종목** 고정, **ETF는 관측지표만** 사용)

## TOP1) 리밸런스 로그/재현성 파이프라인 복구 (운영 리스크 최우선)
### (a) 왜 필요한지
- 현재 **Rebalance Pinpoint가 실패**: `--base-log` 경로가 실제 파일이 아니고, `rebalance.csv`도 JSON 파싱 에러 → **거래/리밸런스 비교가 불가**.
- 이 상태는 “성능이 안 움직임”의 원인을 **비용/회전율/체결/리밸런싱 타이밍**에서 분해할 수 없게 만듦(진짜 원인 은폐).

### (b) 위험/부작용
- 로그 스키마 변경으로 과거 실험과 비교가 잠시 깨질 수 있음.
- 로그 I/O 증가로 런타임 소폭 증가.

### (c) 최소 실험(24~48h 자동 루프용)
**[E1: 필수/즉시] 리밸런스 이벤트를 단일 JSONL로 표준화 + base/cand 자동 연결**
- **실험 정의**
  - 매 리밸런스마다 `rebalance.jsonl`에 1줄 기록:
    - timestamp, universe, target_weights, executed_weights, turnover, est_cost, realized_cost(가능시), slippage_model, exposure, cash, prices_snapshot_hash, signal_hash, run_hash, lane_hash
  - `aub_rebalance_pinpoint.py`는 `--base-log`가 `--base <champion_json>`에서 **자동으로 동일 run_hash의 rebalance.jsonl을 찾도록** fallback.
- **게이트**
  - (G1) base/cand 모두 `rebalance.jsonl` 발견률 100%
  - (G2) 파일 1줄이라도 JSON 파싱 실패 = 즉시 FAIL
- **기대 관측치**
  - pinpoint 리포트가 “No rebalance data found”가 아니라, **리밸런스 차이(회전율/노출/비용) top-k**를 출력

**[E2: 조건부] MDD 계산/로그 누락 보강(worst_mdd None 제거)**
- **게이트**: E1 PASS 시에만
- **기대 관측치**: champion/cand 모두 worst_mdd가 실수로 채워지고, drawdown curve가 리포트에 포함

### (d) PASS 조건
- `rebalance_pinpoint.md`가 base/cand 모두에 대해 **리밸런스 차이 근거(턴오버/비용/노출/주문수)**를 출력
- `worst_mdd`가 None이 아닌 값으로 기록(계산 파이프라인 정상)

## TOP2) 비용(수수료/슬리피지/스프레드) 미반영/과소반영 즉시 교정 (성과 “정지” 원인 1순위)
### (a) 왜 필요한지
- OOS가 “안 움직임”/“no-delta”인 상황에서 가장 흔한 원인이 **비용이 상수처럼 처리되거나 누락**되어, 전략 변경이 실현손익에 반영되지 않는 케이스.
- 특히 Tech/Healthcare 대형주는 스프레드가 작아 보여도 **턴오버가 증가하면** 성과가 쉽게 상쇄됨.

### (b) 위험/부작용
- 비용을 현실화하면 단기적으로 OOS 평균이 하락할 수 있음(정상).
- 비용 파라미터가 과보수적이면 과도하게 거래를 억제할 수 있음.

### (c) 최소 실험
**[E1: 필수/즉시] “2단 비용모델” 패치 + 비용 민감도 고정 리포트**
- **실험 정의**
  - 거래비용 = `commission_per_share + spread_component + slippage_component`
  - spread_component: `k_spread * (bid_ask_spread_estimate)` (스프레드 추정은 ATR/price 또는 고정 bps로 시작)
  - slippage_component: `k_impact * (|dollar_volume_traded| / ADV)^alpha`
  - 리포트에 매 리밸런스별 `gross_pnl`, `cost`, `net_pnl`, `turnover` 반드시 출력
- **게이트**
  - (G1) net_pnl = gross_pnl - cost 항등식 샘플 100% 일치
  - (G2) turnover 0인데 cost>0 발생 시 FAIL(버그)
- **기대 관측치**
  - “전략 변경이 비용/턴오버에 어떤 영향을 주는지”가 수치로 분리됨
  - no-delta 케이스가 비용항에서 설명되는지 여부가 드러남

**[E2: 조건부] 비용 파라미터 3점 민감도(낮음/기준/높음) 자동 스윕**
- **게이트**: E1 PASS 시
- **기대 관측치**: OOS mean이 비용 스케일에 따라 단조 감소/안정 구간 확인(비용이 지배적인지 판단)

### (d) PASS 조건
- net 성과 리포트가 **턴오버/비용 분해를 항상 포함**
- 비용 파라미터 변경 시 OOS가 “완전히 무반응”이면(민감도 0) 비용이 실제로 적용 안 되는 버그로 간주 → FAIL

## TOP3) 누수/라벨 정렬/워크포워드 스플릿 검증 (과최적화·무효학습 방지)
### (a) 왜 필요한지
- “OOS가 정지”는 (1) 모델이 바뀌어도 **실제 트레이딩 신호가 동일**하거나, (2) 라벨/피처 정렬이 꼬여서 **학습이 무의미**하거나, (3) 스플릿이 잘못되어 **동일 데이터 반복**일 때 자주 발생.
- 누수는 성과를 가짜로 올리거나, 반대로 방어코드가 작동해 업데이트가 막혀 “no delta”처럼 보이게 함.

### (b) 위험/부작용
- 스플릿/정렬을 고치면 기존 champion과의 연속성이 끊기며, 단기 성과가 변동할 수 있음.
- 엄격한 워크포워드는 성과가 낮아 보일 수 있으나 현실성은 상승.

### (c) 최소 실험
**[E1: 필수/즉시] “시간정렬 무결성 테스트”를 학습 전 강제 (fail-fast)**
- **실험 정의**
  - 각 샘플에 대해:
    - feature_timestamp < decision_timestamp ≤ execution_timestamp < label_window_end 를 강제 체크
  - purge/embargo(예: label horizon만큼) 적용 여부를 로그로 남김
- **게이트**
  - (G1) 위 부등식 1건이라도 위반 시 실험 전체 FAIL
  - (G2) fold별 train/test 날짜 구간이 겹치면 FAIL
- **기대 관측치**
  - 누수/정렬 문제가 있으면 즉시 적발되어 “성과가 안 움직임”의 가짜 원인 제거

**[E2: 조건부] “신호 동일성 검사”(모델 바꿔도 주문이 같은지)**
- **게이트**: E1 PASS
- **기대 관측치**
  - run 간 `signal_hash`/`target_weights` 상관이 0.99 이상이면 “변경이 신호에 전파되지 않음”을 즉시 확인

### (d) PASS 조건
- 시간정렬/스플릿 무결성 테스트 100% 통과
- 서로 다른 실험(run_hash) 간 신호/목표비중이 의미 있게 달라지는지(상관 과도하게 높지 않음) 확인

## TOP4) Universe(Tech+Healthcare 8~14) 강제 + 서바이버십 방지 (성과 왜곡 제거)
### (a) 왜 필요한지
- 종목 유니버스가 실험마다 흔들리면:
  - OOS 변화가 전략이 아니라 **구성 변화**에서 발생
  - 서바이버십/룩어헤드(상장폐지 종목 누락, 지수 편입 정보 사용) 위험 증가
- “ETF 매매 제외” 조건에서, 유니버스가 고정되지 않으면 실제 운용과 괴리 발생.

### (b) 위험/부작용
- 고정 유니버스는 기회 감소로 성과가 낮아질 수 있음(대신 해석가능성↑).
- 데이터 공급원이 서바이버십-프리 지원이 약하면 구현 난이도 증가.

### (c) 최소 실험
**[E1: 필수/즉시] Universe 고정 + 섹터 검증 + 상장폐지/거래정지 처리 규칙 추가**
- **실험 정의**
  - Tech/Healthcare에서 8~14개 **고정 리스트**를 코드 레벨에서 강제(실험마다 동일).
  - 각 종목: 거래정지/결측 시 **대체 규칙**(현금 보유 or 동섹터 내 예비 종목 1~2개) 단 하나로 고정.
  - ETF(예: QQQ/XLK/XLV/SPY/VIX)는 **지표 피처만** 허용(주문 금지 assert).
- **게이트**
  - (G1) 매일 universe 크기 8~14 유지, 섹터 비중(Tech+Health) 100% 아니면 FAIL
  - (G2) ETF 주문 발생 시 즉시 FAIL
- **기대 관측치**
  - 실험 간 변동이 “전략 로직”에서만 발생하게 정리됨
  - 서바이버십/운영 예외(결측/정지)가 PnL을 깨는 문제 감소

**[E2: 조건부] 서바이버십 스모크 테스트**
- **게이트**: E1 PASS
- **기대 관측치**: 특정 구간에서 결측/스플릿/티커 변경 이벤트가 있어도 포트폴리오 가치가 비정상 점프하지 않음

### (d) PASS 조건
- 유니버스/섹터/ETF주문 금지 규칙이 런타임에서 강제되고, 위반 0건
- 결측/정지 이벤트가 발생해도 백테스트가 조용히(규칙대로) 처리됨

## TOP5) 레짐(시장 국면) 관측지표로 “노출 게이트” 추가 (노출/리스크 정렬)
### (a) 왜 필요한지
- 현재 exposure가 min/max 0.47~0.84로 꽤 높음. 레짐이 불리할 때도 계속 노출되면 OOS 개선이 “정체”되기 쉬움.
- ETF는 매매하지 않더라도 **국면 신호(리스크온/오프)**로는 유용(조건 준수).

### (b) 위험/부작용
- 게이트가 과도하면 기회손실(underexposure)로 평균 수익 저하 가능.
- 게이트가 모델과 상호작용하며 과최적화될 수 있음(간단한 룰부터 시작).

### (c) 최소 실험
**[E1: 필수/즉시] “단순 레짐 게이트”로 목표 노출 상한 조절**
- **실험 정의**
  - 관측지표(매매 금지):
    - QQQ/XLK/XLV/SPY의 20/60일 모멘텀, 20일 변동성, VIX(가능하면)
  - 룰(예시 수준의 단순함 유지):
    - risk_off 조건(예: SPY 20<60 AND VIX 상승)일 때 `target_gross_exposure_cap = 0.35~0.50`
    - else `cap = 0.85`
  - 종목 선택 로직은 유지하되, **스케일링만 변경**
- **게이트**
  - (G1) 리스크오프 구간에서 실제 exposure가 cap을 초과하면 FAIL
  - (G2) cap 적용이 turnover를 급증시키면 FAIL(예: 기존 대비 +50% 이상)
- **기대 관측치**
  - worst_mdd(계산 가능해졌다는 전제 하에) 감소 또는 tail 손실 완화
  - OOS mean이 크게 악화되지 않으면서 변동성/낙폭 개선

**[E2: 조건부] 레짐별 성과 분해 리포트 자동 생성**
- **게이트**: E1 PASS
- **기대 관측치**: risk_on/off 별 net_pnl, hit-rate, turnover, cost가 표로 분리됨

### (d) PASS 조건
- 리스크오프 구간 MDD 또는 하방 꼬리가 개선(정량 기준은 기존 champion 대비 최소 1개 지표 개선)
- turnover/비용 폭증 없이(게이트 통과) 노출이 의도대로 제어됨

# 성능이 “안 움직일 때” 원인 분해 아이디어 (트리거/적용/노출/비용/레짐)
아래 트리는 **다음 루프부터 자동 로그로 진단** 가능하게 구성.

## 1) Trigger(실험 변경이 발생했나?)
- 체크리스트
  - `config_hash`, `code_git_sha`, `feature_set_hash`, `model_hash`를 매 런에 기록
  - 서로 다른 run인데 `model_hash` 동일하면: **학습이 안 돌거나 캐시가 고정**
- 관측지표
  - 변경 대비 `signal_hash` 변화율(또는 상관)
- 고장 패턴
  - “실험은 바뀌었는데 signal_hash가 거의 동일” → 적용 단계 문제(TOP3-E2로 잡힘)

## 2) Apply(신호가 주문으로 반영되나?)
- 체크리스트
  - 리밸런스 시 `target_weights` vs `executed_weights` 차이(추적 오차) 기록
  - 주문 금지 룰(ETF 등) assert
- 관측지표
  - 평균/최대 tracking error, 주문 거부 사유 카운트
- 고장 패턴
  - executed_weights가 매번 이전 포지션과 유사 → 주문 생성/체결 로직이 막힘

## 3) Exposure(노출이 성과를 지배하나?)
- 체크리스트
  - gross/net exposure, cash, 상한/하한 클램프 발동 횟수 기록
- 관측지표
  - 성과와 exposure 상관, 리스크오프 구간 exposure 분포
- 고장 패턴
  - exposure가 항상 비슷(0.47~0.84 좁은 밴드) → 모델 차이가 스케일링에서 제거됨(게이트/클램프 확인)

## 4) Cost(비용이 알파를 상쇄하나? 혹은 아예 적용이 안 되나?)
- 체크리스트
  - gross_pnl, cost, net_pnl을 리밸런스 단위로 분해
  - turnover와 cost의 단조 관계 체크(턴오버↑면 cost↑)
- 관측지표
  - cost / gross_pnl 비율, net이 0 근처로 눌리는 구간
- 고장 패턴
  - 비용 파라미터 바꿔도 net이 무반응 → 비용 미적용 버그(TOP2 게이트로 적발)

## 5) Regime(국면 의존으로 OOS 평균이 평평해졌나?)
- 체크리스트
  - risk_on/off 라벨을 ETF 지표로만 생성(매매 금지)
- 관측지표
  - 레짐별 mean, mdd, turnover, cost
- 고장 패턴
  - 특정 레짐에서만 이기고 나머지에서 지속 손실 → 노출 게이트(TOP5)로 완화

# 48시간 자동 루프 실행 순서(명령형 체크리스트)
1) **TOP1-E1** 적용 → rebalance.jsonl 표준화 + pinpoint 복구 (FAIL-FAST)  
2) **TOP2-E1** 적용 → 2단 비용모델 + gross/cost/net 분해 리포트  
3) **TOP3-E1** 적용 → 시간정렬/스플릿 무결성 테스트(위반 시 즉시 중단)
