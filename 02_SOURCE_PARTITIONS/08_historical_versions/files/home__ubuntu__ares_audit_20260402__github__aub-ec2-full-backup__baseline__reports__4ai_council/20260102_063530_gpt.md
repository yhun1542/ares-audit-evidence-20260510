## 24~48시간 우선순위 TOP5 (명령형 체크리스트)

1) **누수(lookahead)·정렬(time alignment) 최우선 봉쇄**
- 피처/라벨 “as-of” 정렬을 강제하고, 일/분해상도 혼용 시 타임스탬프 라운딩 규칙을 고정하라.
- corporate action(분할/배당) 반영 시점이 라벨보다 “미래”로 새지 않게 단위테스트를 추가하라.
- “+1 bar shift(미래로 한 칸 민 피처)”에서도 성능이 유지되면 즉시 누수로 간주하고 롤백하라.

2) **비용(슬리피지/스프레드/충격)·회전율(턴오버) 미반영 리스크를 먼저 고정**
- 거래비용을 최소 2~3개 시나리오(bps)로 스윕하고, 결과의 민감도를 리포트로 남겨라.
- 모델이 비용을 이기지 못하면 “신호 개선”이 아니라 “매매 빈도/리밸런싱/포지션 캡”부터 손봐라.

3) **과최적화(튜닝 평균↑, 최저/꼬리↓) 패턴을 ‘purged walk-forward’로 차단**
- 현재 상태에서 tuning_min이 크게 흔들리는 후보(예: last PASS candidate의 tuning_min -1.41)는 과최적화/누수/레짐 의존 가능성이 높으니, purged/embargo CV로 재평가하라.
- 튜닝-락박스 갭이 큰 구성요소(피처/정규화/리밸런싱 룰)를 우선 격리하라.

4) **서바이버십·유니버스 변동 리스크를 “고정 8~14 종목(Tech+Healthcare)”로 잠가라 (미국주식 only)**
- 동적 구성(지수 편입/시총 상위 자동선정)을 금지하고, 고정 화이트리스트로만 백테스트/실거래를 일치시켜라.
- ETF는 **매매 금지**, 레짐/필터 관측지표로만 쓰되(예: XLK/XLV/QQQ/SPY), 신호 입력 시점 누수만 철저히 검사하라.

5) **48시간 자동 루프 운영 리스크(재현성/롤백/드리프트) 최소화**
- 데이터 스냅샷 해시 + 코드 커밋 해시 + 실험 스펙 해시를 아티팩트로 남기고, “같은 입력=같은 결과”를 강제하라.
- 실패 시 자동으로 Champion으로 롤백하는 게이트를 시스템 레벨에서 고정하라.

## 공통 “실행 가능한 patch/실험” 패키지 (3~5개로 제한, 48시간 루프용)
아래 **E1~E5**만 돌리고, 각 TOP5 제안은 이 중 2~3개를 **재사용**해서 검증하라(케이스 폭발 금지).

### E1) Leakage Sentinel 패치 (누수 탐지 하네스)
1) **실험 정의**
- 피처 전체(또는 핵심 피처군)를 **+1 거래일(또는 +1 bar) 미래로 시프트**한 버전으로 동일 백테스트 수행
- 라벨을 기간 내에서 블록 셔플(예: 월 단위)한 “가짜 세계”에서도 성능 측정
2) **게이트**
- 시프트/셔플에서 성능이 **의미 있게 붕괴**하지 않으면(락박스 mean이 0 근처로 수렴하지 않거나, 샤프 유사 유지) 즉시 FAIL
3) **기대 관측치**
- 정상이라면: 시프트/셔플 성능 급락 + 포지션이 랜덤화 + turnover/노출 구조 붕괴

### E2) Cost/Turnover Stress 패치 (비용·회전율 민감도)
1) **실험 정의**
- 거래비용을 (예: 5/15/30 bps + 스프레드) 3단계로 스윕
- 결과에 **turnover, 평균 보유기간, 거래횟수**를 함께 로깅
2) **게이트**
- 비용 15bps에서 성능이 과도하게 붕괴하면(락박스 mean이 Champion 대비 -10%p 이상, 또는 worst_mdd 급악화) 전략 구조를 먼저 수정
3) **기대 관측치**
- 견고한 전략이면 비용 상승에도 성능이 완만히 감소하고, turnover가 통제 범위 내

### E3) Purged Walk-Forward CV 패치 (과최적화 차단)
1) **실험 정의**
- 시간축 CV를 **purged + embargo**로 교체(라벨 호라이즌만큼 purge, 추가 embargo 적용)
- 튜닝 선정 기준을 “mean만”이 아니라 **min/꼬리(worst fold)** 포함으로 변경
2) **게이트**
- tuning_mean만 높고 tuning_min이 심각하게 낮은 구성은 자동 탈락
- 선정 모델의 lockbox_mean이 Champion 대비 -3%p 이상이면 FAIL
3) **기대 관측치**
- 과최적화였으면: purged 적용 시 성능 급락/선정 모델이 바뀜
- 견고하면: tuning/lockbox 갭이 줄어듦

### E4) Exposure Clamp + Rebalance Throttle 패치 (MDD·운영 리스크 완화)
1) **실험 정의**
- 단일 종목 최대 비중 캡(예: 12~15%) + 일일(또는 주기) 리밸런싱 최소 간격 + turnover 상한
- (ETF는 매매 금지) XLK/XLV 상대강도 같은 레짐 지표는 **“리스크 오프 시 총 익스포저 축소”** 용도로만 사용
2) **게이트**
- worst_mdd 개선이 없고 성능만 떨어지면(Champion 대비 lockbox_mean -5%p 이상) FAIL
3) **기대 관측치**
- 정상이라면: MDD 감소/턴오버 감소/수익률 약간 희생 또는 유사 유지

### E5) Static Universe Lock + Survivorship Guard 패치
1) **실험 정의**
- **고정 8~14 종목 화이트리스트(Tech+Healthcare, US only)**로 유니버스를 잠그고, 전 기간 동일 유니버스로 재백테스트
- split/dividend 처리 로그를 남기고, 결측/상장폐지(가능 시) 처리 경로를 명시
2) **게이트**
- 유니버스 고정 후 성능이 급변하면(락박스 mean 변동 과대) 기존 성과의 “구성 편향/서바이버십” 의심으로 FAIL 처리
3) **기대 관측치**
- 정상이라면: 성능이 완만히 변화, 노출/종목 기여가 설명 가능해짐

## TOP5 제안별 (a)필요성 (b)위험/부작용 (c)최소 실험(공통 E1~E5에서 2~3개) (d)PASS 조건

### 1) 누수·정렬 봉쇄
(a) 왜 필요한지  
- 현재 Champion이 tuning/lockbox 모두 높지만, 후보에서 **tuning_min 급락(-1.41)** 같은 “꼬리 붕괴”가 보이는 건 누수/정렬 오류/레짐 의존의 전형적 징후다.  
(b) 위험/부작용  
- 누수 제거 후 성능이 “진짜로” 낮아질 수 있다(단, 이건 부작용이 아니라 정상화).  
(c) 최소 실험  
- **E1**, **E3**, (데이터/유니버스 의심 시) **E5**  
(d) PASS 조건  
- E1에서 시프트/셔플 성능이 **명확히 붕괴**  
- E3 적용 후 tuning-락박스 갭 축소(예: lockbox_mean이 선정 기준에 의해 안정적으로 따라옴)  
- E5 고정 유니버스에서도 성능이 설명 가능한 범위로 유지(급격한 “마법 같은” 개선/악화 금지)

---

### 2) 비용·회전율 반영
(a) 왜 필요한지  
- Tech/Healthcare 8~14 종목은 유동성은 대체로 좋지만, **회전율이 높으면 비용이 알파를 잠식**한다. “백테스트는 좋은데 실거래가 망가지는” 1순위 원인이다.  
(b) 위험/부작용  
- 비용 모델을 올리면 성능이 떨어져 보일 수 있음(현실 반영).  
- 과도한 비용 패널티는 트레이드 자체를 사라지게 만들어 신호 검증이 어려워질 수 있음.  
(c) 최소 실험  
- **E2**, **E4**  
(d) PASS 조건  
- 비용 15bps 기준에서도 lockbox_mean이 Champion 대비 **-5%p 이내**  
- turnover가 명시한 상한(내부 기준) 내로 내려가고, worst_mdd가 악화되지 않음

---

### 3) 과최적화 차단(선정 규칙/검증 체계 교체)
(a) 왜 필요한지  
- Champion은 worst_mdd가 약 -9.3%로 나쁘진 않지만, 후보는 MDD가 더 낮아도 tuning_min이 크게 깨진다. 이는 **선정 기준이 mean 중심**이라 꼬리를 무시했을 가능성이 있다.  
(b) 위험/부작용  
- purged/embargo를 도입하면 튜닝 점수가 떨어질 수 있음(하지만 일반화는 좋아져야 한다).  
(c) 최소 실험  
- **E3**, (누수 동반 의심 시) **E1**  
(d) PASS 조건  
- 선정된 모델의 **tuning_min이 0 이상(또는 내부 하한)으로 개선**  
- lockbox_mean이 Champion 대비 **-3%p 이내**에서 유지되거나, worst_mdd가 의미 있게 개선(예: -9.3% → -7% 이하로 완화)

---

### 4) 익스포저/리스크(드로우다운) 운영형 패치
(a) 왜 필요한지  
- 후보의 MDD가 더 낫게 나왔던 점은 “리스크 통제”가 성능의 병목일 수 있음을 시사한다.  
- 소수 종목(8~14) 포트는 단일 종목/하위섹터 쏠림이 곧 MDD로 직결된다.  
(b) 위험/부작용  
- 캡/스로틀이 과하면 수익 상단을 깎고, 리밸런싱이 줄면 신호 반응이 늦어진다.  
(c) 최소 실험  
- **E4**, (비용 민감도와 함께) **E2**  
(d) PASS 조건  
- worst_mdd가 Champion 대비 **개선 또는 동일**  
- lockbox_mean 하락이 **-5%p 이내** + turnover 감소가 동반(“덜 거래해서 덜 벌었다”가 아니라 “덜 거래해도 유지”가 목표)

---

### 5) 유니버스/서바이버십 및 운영 재현성 강화
(a) 왜 필요한지  
- 유니버스가 바뀌면 백테스트는 “역사 재작성”이 된다. 특히 Tech는 상위 종목이 장기간 승자편향을 만들기 쉽다.  
- 48시간 루프에서 재현성이 없으면 성능 변화 원인을 추적 불가능하다.  
(b) 위험/부작용  
- 고정 유니버스는 기회가 줄어 단기 성능이 낮아질 수 있다(대신 신뢰도가 상승).  
(c) 최소 실험  
- **E5**, (운영/비용 관점에서) **E2**  
(d) PASS 조건  
- 고정 유니버스에서도 성능이 “설명 가능”하게 유지(급변 금지)  
- 실험 재실행 시(동일 스냅샷/해시) 결과가 통계적 오차 범위 내로 재현

## 성능이 안 움직일 때 “원인 분해” 트리거 (Trigger→적용→노출→비용→레짐) 체크리스트

### A) Trigger(신호 발생) 문제
- 피처 분포 드리프트: 평균/분산/결측률이 학습 구간과 달라졌는지 로그로 확인하라.
- IC(정보계수) 또는 단순 랭크 상관을 **pre-trade** 기준으로 기록하라(매매/리스크 적용 전 “순수 알파” 측정).

### B) 적용(Application: 포지션 생성/리밸런싱) 문제
- 신호는 있는데 포지션이 “클립/제로화”되는지 확인하라(캡, 최소 주문 단위, 리밸런싱 최소 간격 때문에).
- 신호→주문 변환 파이프라인에서 타임스탬프가 하루 밀리는지(또는 당일 종가 사용) 점검하라. (누수/역누수 모두 성능을 왜곡)

### C) 노출(Exposure: 베타/섹터/단일종목) 문제
- 포트의 베타(대략 SPY/QQQ 회귀), 섹터 편향(Tech/Healthcare 내부 하위군) 노출을 매일 기록하라.
- 성능 정체 구간이 “시장 방향성(베타)”에 좌우되는지, 아니면 알파가 사라졌는지 분해하라:  
  - **포트 수익 = 베타 성분 + 잔차(알파)** 형태로 일별 회귀 리포트 생성

### D) 비용(Cost) 문제
- pre-cost / post-cost 성과를 분리해서 저장하라. 정체의 1순위는 대부분 “비용이 알파를 먹음”이다.
- turnover와 체결가정이 바뀌면 결과가 크게 움직이므로, E2 스윕 결과를 “민감도 곡선”으로 고정 리포트화하라.

### E) 레짐(Regime) 문제
- XLK vs XLV 상대강도, VIX(관측), SPY 추세(관측) 같은 레짐 지표를 **매매가 아니라 게이트/노출 축소**에만 사용하라.
- 레짐별로 성과를 나눠보라: (추세/횡보/고변동) 3분할만 해도 원인이 드러난다.

## 바로 실행 순서(24~48h, 명령형)
1) **E1 누수 센티넬을 먼저 추가/실행**하고, 통과 전까지 다른 개선을 “효과”로 해석하지 마라.  
2) **E2 비용 스윕 리포트**를 생성해서, 현재 전략이 비용에 취약한지부터 확정하라.  
3) **E3 purged walk-forward로 선정 규칙을 교체**하고, tuning_min(꼬리) 기반 탈락을 자동화하라.  
4) **E4 익스포저 캡+리밸런싱 스로틀**을 적용해 MDD/턴오버 동시 개선을 노려라.  
5) **E5 유니버스 고정(8~14 Tech+Healthcare, US only)** 및 재현성 해시를 붙여, 결과 변동의 원인을 추적 가능하게 만들어라.

위 5개(E1~E5)만으로도 누수/과최적화/서바이버십/비용/운영 리스크를 먼저 잠그면서, Champion 대비 “진짜 개선”인지 빠르게 판별할 수 있다.
