# TOP5 우선순위 제안

## 1) (운영/아키텍처) “리밸런스/평가 로그 스키마 고정” + 진단 도구 입력 호환
**왜 필요한지**
- 현재 상태에서 `aub_rebalance_pinpoint.py`가 **base-log 누락** + **CSV/JSON 파싱 실패**로 리밸런스 기반 진단이 멈춤.
- `worst_mdd: None`도 **핵심 리스크 지표가 산출/저장되지 않는 운영 리스크**. 성능이 “안 움직이는” 원인이 전략이 아니라 **관측 불능(telemetry 결함)**일 수 있음.

**위험/부작용**
- 로그 포맷 변경 시 과거 리포트/대시보드 호환 깨짐(회귀).
- 스키마 강제는 초기엔 실패가 늘어 파이프라인이 자주 멈출 수 있음(하지만 의도된 fail-fast).

**최소 실험(공유 실험 사용)**
- **E1 + E5 + E4**를 함께 실행(아래 실험 정의 참고)

**PASS 조건**
- [ ] 모든 run에서 `rebalance.csv` 또는 단일 `rebalance.jsonl`이 **항상 생성**되고, pinpoint가 0 error로 완료
- [ ] `worst_mdd`, turnover, cost, exposure min/max가 **모두 non-null**로 저장
- [ ] 동일 seed에서 champion 재실행 시 핵심 요약지표(oos_mean/oos_min)가 **±1~2% 이내 재현성** 확보(관측 노이즈 축소)

---

## 2) (누수 우선) “시점 정렬(Time Alignment) 강제” + 피처/라벨 미래정보 감지 게이트
**왜 필요한지**
- “No-Delta Diagnoser에서 실험 9개 찾음”인데도 성능이 정체/일관성 불명 → 흔한 원인이 **(a) 피처가 이미 안전해서 변화가 없거나 (b) 변화가 반영되지 않거나 (c) 미래정보가 섞여 지표가 왜곡**.
- Tech/Healthcare는 실적/가이던스/임상 이벤트 등 이벤트성 데이터에서 **발표시각/거래일 정렬 누수**가 빈번.

**위험/부작용**
- 올바른 시점 정렬을 하면 과거 성능이 **하락**할 수 있음(정상).
- 게이트가 너무 엄격하면 실험이 자주 fail(하지만 누수 방지 최우선).

**최소 실험**
- **E2 + E5** (필요 시 E1로 로그까지 확정)

**PASS 조건**
- [ ] “미래정보 의심 시그널(lookahead sentinel)”이 0건(또는 허용 임계치 이하)
- [ ] 학습/검증 fold에서 “피처 시점 > 의사결정 시점” 발생률 0
- [ ] 누수 차단 후에도 oos_mean이 **극단적 붕괴 없이** 유지(예: -30% 이내)되면 정상 범주, 붕괴 시 누수 의존 가능성 큼

---

## 3) (비용 미반영 우선) “거래비용/슬리피지/충격비용 모델을 게이트에 포함”
**왜 필요한지**
- 현재 리밸런스 로그가 불안정한 상태에서 성능만 보면, **회전율이 높아도 모르는** 상황이 발생.
- Tech/Healthcare 단일주식(ETF 매매 제외)에서 포트폴리오가 8~14 종목이면, 리밸런스 시 **체결비용/스프레드/시장충격**이 성과를 지배할 가능성이 큼.

**위험/부작용**
- 비용을 넣으면 성능이 내려가 “안 움직이는” 것처럼 보일 수 있음(실제에 가까워짐).
- 비용 파라미터가 과도하면 과보수적이 되어 신호를 죽일 수 있음.

**최소 실험**
- **E3 + E4 + E5**

**PASS 조건**
- [ ] 비용 반영 후에도 oos_mean이 **유의미하게 양(+)**이고 oos_min이 0 근처로 붕괴하지 않음
- [ ] turnover(예: 월간/분기)와 비용이 리밸런스 횟수와 정합(“비용=0인데 거래 있음” 같은 모순 0)
- [ ] 비용 민감도(파라미터 2단)에서 성능이 단조롭게 악화하는지 확인(비정상적 역전이면 구현 오류 의심)

---

## 4) (서바이버십/우주) “US Tech+Healthcare 유니버스의 Point-in-Time 구성 + delist 반영”
**왜 필요한지**
- 서바이버십 바이어스는 OOS가 “좋게 유지되는데 실제는 안 됨” 혹은 실험 간 차이가 안 나는 형태로도 나타남.
- 8~14개 집중 포트에서는 유니버스 구성 오류가 **결과를 거의 고정**시킬 수 있음(예: 항상 살아남은 대형주만 남는 경우).

**위험/부작용**
- delist 포함/과거 구성원 복원 시 데이터 결측 처리 증가로 파이프라인 실패 증가.
- 유니버스가 바뀌면 전략 성능이 흔들리며 “챔피언” 비교가 어려워질 수 있음(그래서 게이트/로그가 선행돼야 함).

**최소 실험**
- **E2 + E4** (필요 시 E1로 리밸런스/선정 사유 로깅)

**PASS 조건**
- [ ] 각 시점(t)에서 유니버스가 “그 시점에 존재하던 종목”으로만 구성됨(상장일 이전 포함 0)
- [ ] delist/합병/티커 변경 이벤트가 포트폴리오 시계열에서 “갑자기 사라짐”으로 처리되지 않고, 현금화/대체 규칙으로 일관 처리
- [ ] 유니버스 교정 후 성과 변동이 있어도, **신호-노출-비용 분해**가 가능한 로그 확보(원인 추적 가능 상태)

---

## 5) (과최적화/레짐) “레짐 기반 노출 게이트(ETF는 지표로만) + OOS 최소치 방어”
**왜 필요한지**
- 현재 `oos_min: 0.43`처럼 바닥 성능이 낮고, exposure가 0.47~0.84로 비교적 높게 유지. 레짐 전환(금리/리스크오프)에서 Tech/HC는 드로우다운이 커질 수 있음.
- ETF는 매매하지 않고 **관측지표**로만 사용하여 “리스크오프 때 노출을 줄이는 게이트”를 구성하면, 과최적화 없이도 OOS_min 방어가 가능.

**위험/부작용**
- 레짐 게이트는 상승장에서 수익을 깎음(기회비용).
- 레짐 지표 임계치 튜닝이 과해지면 또 다른 과최적화가 됨 → 임계치는 1~2개 고정, 민감도 실험 2단만.

**최소 실험**
- **E5 + E3** (필요 시 E4로 노출 변화 로깅)

**PASS 조건**
- [ ] oos_min 개선(바닥 방어) 또는 worst_mdd 하락(더 나은 MDD) 중 1개 이상 달성
- [ ] 레짐 게이트 발동 시 exposure가 설계대로 감소(로그로 확인)
- [ ] 상승장 구간에서 성능 훼손이 과도하지 않음(예: oos_mean -10~15% 이내면 수용)

# 공유 실험 5개 (E1~E5): 48시간 자동 루프용 템플릿

## E1) 로그/스키마 강제 + 리포트 재현성
1) **실험 정의**
- rebalance 출력 포맷을 단일화: `rebalance.jsonl`(필수), 필요 시 CSV는 파생 생성
- run 요약에 `worst_mdd`, turnover, cost, exposure min/max를 필수 필드로 강제(없으면 run 실패)
2) **게이트**
- pinpoint/diagnoser가 0 error로 종료
- 요약 필드 non-null, 타입 검증 통과
3) **기대 관측치**
- 진단 리포트가 “데이터 없음/파싱 실패” 없이 생성
- 동일 config 재실행 시 요약지표 변동폭 축소

---

## E2) 누수 감지/차단: time alignment sentinel
1) **실험 정의**
- 각 피처에 대해 “최소 사용 가능 시각(availability timestamp)”을 두고, 의사결정 시각보다 미래면 마스킹/결측 처리
- 이벤트성 데이터(실적/뉴스/임상)에는 발표 후 next-trading-day 적용(룰 고정)
2) **게이트**
- (피처 타임스탬프 > decision time) 발생률 0
- 훈련/검증 구간 경계에서 forward-fill이 미래를 침범하지 않는지 체크
3) **기대 관측치**
- 누수 의존 전략이면 성능 급락 + 신호 중요도/선정 종목 급변
- 정상 전략이면 성능은 일부 하락하더라도 일관성 유지

---

## E3) 비용 모델 포함(스프레드+충격) + 비용 민감도 2단
1) **실험 정의**
- 거래당 비용 = 고정커미션(또는 0) + half-spread + k * (|trade|/ADV) 형태로 단순화
- k는 2단(예: 낮음/높음)만 비교
2) **게이트**
- 거래가 발생하면 비용도 항상 >0 (0 비용 거래 0건)
- ADV 결측 종목은 거래 불가/패널티 규칙으로 일관 처리
3) **기대 관측치**
- turnover 높은 전략의 순성과 급락
- 비용 민감도가 높을수록 oos_mean 단조 감소(비단조면 구현 오류 가능)

---

## E4) 서바이버십 방지: point-in-time 유니버스 + delist 처리
1) **실험 정의**
- 매 거래일 t의 후보군은 “t 시점에 상장돼 있고 거래가능(가격/거래량 존재)” 종목만
- delist/합병 발생 시: 다음 리밸런스에서 강제 청산/현금화 규칙 고정
2) **게이트**
- 상장일 이전/상폐 이후 데이터 사용 0건
- 티커 변경은 동일 식별자(perm-id)로 연결되었는지 검사
3) **기대 관측치**
- 과거 특정 구간 성능 재조정(대체로 하락이 정상)
- 포트 구성의 종목 교체 빈도/패턴이 현실적으로 변화

---

## E5) 레짐 관측(ETF는 지표만) 기반 노출 게이트
1) **실험 정의**
- 매매는 개별주(US Tech+HC 8~14)만
- 레짐 지표(관측용 ETF/인덱스 예: QQQ, XLV, IWM, TLT, VIX proxy 중 1~2개만 선택)로
  - risk-off 조건 시 목표 노출을 0.3~0.5로 축소
  - risk-on 조건 시 기존 노출 유지
- 임계치는 1개 규칙, 민감도는 2단만
2) **게이트**
- 레짐 플래그와 실제 exposure 변화가 로그상 일치
- 게이트 발동 횟수 과다(예: 전체 일수의 50% 이상)면 실패(과민반응)
3) **기대 관측치**
- oos_min 개선 또는 worst_mdd 개선
- 상승장에서는 일부 수익 희생 발생

---

# (요청 3) 성능이 “안 움직일 때” 원인 분해 아이디어 — 트리거/적용/노출/비용/레짐 트리

아래 순서대로 **관측 가능(로그로 증명)** 한 것부터 제거:

## A. 트리거(신호가 생성되나?)
- [ ] 신호 값 분산이 너무 작아 “항상 비슷한 랭킹”인지 확인(표준편차/유니버스 내 순위 변동률)
- [ ] 리밸런스 날에만 신호가 바뀌는지(일중/일간 갱신 주기 불일치)
- [ ] 결측/마스킹(E2) 이후 신호가 사실상 0/상수로 붕괴했는지

## B. 적용(신호가 포지션으로 반영되나?)
- [ ] 목표 포지션(top 8~14)과 실제 체결 포지션이 동일한지(거래가능 필터/가격 결측 때문에 계속 스킵되는지)
- [ ] 리밸런스 로직이 “변경 필요 없음”으로 과도하게 판단하는지(허용밴드/라운딩/최소 주문 단위)

## C. 노출(익스포저가 움직이나?)
- [ ] exposure min/max가 고정 범위에 갇혀(예: 항상 0.7 근처) 레버/현금 조절이 안 되는지
- [ ] 레짐 게이트(E5) 발동 시 실제 노출 감소가 일어나지 않는지(플래그만 존재)

## D. 비용(순성과가 눌리나?)
- [ ] turnover가 높은데 비용이 0이거나 너무 낮게 잡혀 있는지(E3 게이트)
- [ ] ADV/스프레드 결측으로 비용이 비정상(0 또는 무한) 처리되는 구간이 있는지

## E. 레짐(시장이 바뀌었나?)
- [ ] 성과가 특정 구간(금리 급등/리스크오프)에서만 붕괴하는지 → 레짐 구간별 oos_mean/oos_min 분해
- [ ] Tech/HC 내부에서 팩터(퀄리티/밸류/모멘텀) 노출이 한쪽으로 과도하게 쏠리는지(팩터 프록시로 점검)

---

## 24~48시간 실행 순서(명령형 체크리스트)
- [ ] **E1 먼저**: 로그/스키마/지표(non-null) 강제 → 진단 불능 상태 제거
- [ ] **E2 다음**: 시간정렬 누수 게이트로 “좋았던 성과가 가짜인지” 먼저 확인
- [ ] **E3 병행**: 비용 모델 포함 + 민감도 2단으로 “거래 가능한 전략인지” 판별
